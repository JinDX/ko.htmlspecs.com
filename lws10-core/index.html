초록

Linked Web Storage Protocol 명세는 애플리케이션이 상호 운용 가능한 방식으로 외부에 저장된 데이터에 안전하고 권한이 부여된 접근을 할 수 있도록 하는 것을 목표로 한다.

이 문서의 상태

이 절은 발행 당시 이 문서의 상태를 설명한다. 현재 W3C 발행물과 이 기술 보고서의 최신 개정판 목록은 W3C 표준 및 초안 색인에서 확인할 수 있다.

이는 비공식 제안이다.

이 문서는 Linked Web Storage Working Group에서 권고안 트랙을 사용하여 작업 초안으로 발행했다.

작업 초안으로의 발행은 W3C와 그 회원들의 승인을 의미하지 않는다.

이는 초안 문서이며 언제든지 다른 문서로 갱신, 대체 또는 폐기될 수 있다. 이 문서를 진행 중인 작업이 아닌 다른 것으로 인용하는 것은 적절하지 않다.

이 문서는 W3C 특허 정책에 따라 운영되는 그룹에서 작성했다. W3C는 이 그룹의 산출물과 관련하여 이루어진 특허 공개의 공개 목록을 유지하며, 해당 페이지에는 특허 공개 지침도 포함되어 있다. 개인이 필수 청구항을 포함한다고 믿는 특허를 실제로 알고 있는 경우, 그 개인은 W3C 특허 정책 제6절에 따라 해당 정보를 공개해야 한다.

2. 소개

이 명세는 Linked Web Storage (LWS) 프로토콜을 정의하며, 이 프로토콜은 클라이언트 애플리케이션이 에이전트의 신원과 권한에 따라 웹 리소스에 접근하고 관리할 수 있도록 합니다.

리소스 서버가 연결된 리소스의 계층을 관리하고 이에 대한 접근을 제공하는 방식을 표준화함으로써, 이 프로토콜은 사용자가 서로 다른 클라이언트 애플리케이션으로 동일한 저장 데이터와 상호작용할 수 있도록 합니다. 이러한 연결된 리소스는 컨테이너와 포함 관계를 통해 정의되며, 이러한 관계는 항목이 어디에 위치하는지 설명하고, 메타데이터는 리소스 간의 관계를 설명합니다.

이 프로토콜은 이러한 리소스에 대한 생성, 읽기, 갱신 및 삭제의 표준 작업을 정의합니다. 각 리소스는 URI로 식별됩니다. 클라이언트는 루트 컨테이너에서 리소스 계층을 탐색하며, 서버 응답에 제공된 링크를 통해 포함된 리소스와 그 관계를 발견합니다.

에이전트의 신원은 Linked Web Storage 서버 외부에 있을 수 있는 신원 제공자를 통해 확인됩니다. 이러한 느슨한 결합은 서버가 자격 증명을 반드시 직접 관리하는 것은 아니라는 의미이며, 대신 서버는 신뢰할 수 있는 신원 제공자가 발급한 토큰인 서명된 인증 자격 증명을 수신하고 검증할 수 있습니다. 따라서 사용자는 기존 신원을 준수 서버에 제시할 수 있으며, 항상 해당 서버만을 위한 신규 또는 기존 계정을 필요로 하지는 않습니다. LWS는 사용자 인증을 활용하며, 이는 예를 들어 OpenID Connect, SAML 2.0 및 자체 서명된 제어 식별자(CIDs) 명세에서 정의됩니다.

인가는 요청 에이전트가 리소스에 접근하거나 해당 리소스에 대한 작업을 수행할 권한이 있는지를 결정합니다. 준수 LWS 서버는 각 리소스에 대해 리소스 관리자를 지정하며, 이 관리자는 리소스가 비공개인지(즉, 소유자만 이용 가능), 제한되는지(즉, 정의된 사용자 집합만 이용 가능), 공개인지(즉, 모든 사용자가 이용 가능)를 결정합니다. 서버는 각 클라이언트 요청을 처리할 때 리소스 관리자의 접근 결정을 적용합니다.

이 명세는 다음 사용자를 대상으로 합니다:

  • 다음에 접근하는 클라이언트 애플리케이션을 구축하는 개발자: 저장소 리소스
  • 다음에 대한 접근을 중개하는 준수 서버를 구축하는 개발자: 저장소 리소스

서로 다른 LWS 서버 인스턴스는 각각 연결된 리소스의 자체 계층을 유지합니다. 에이전트는 동일한 식별 정보를 사용하여 여러 서버를 탐색할 수 있으며, 각 서버 리소스에 대한 접근은 해당 서버의 리소스 관리자가 부여한 권한에 따라 결정됩니다. 모든 LWS 서버 인스턴스가 가능한 모든 에이전트 식별자를 지원한다고 보장되지는 않습니다. 특정 LWS 서버 인스턴스는 에이전트에게 특정 신원 제공자를 통해 자신을 식별하도록 요구할 수 있으며, 이는 해당 서버 인스턴스가 관리하는 리소스에 접근하기 위한 것입니다.

2.1 리소스 접근

LWS 프로토콜은 어떤 주체가 일부 리소스를 다음 대상에게 제공할 수 있는 표준 상호작용을 정의합니다: 에이전트.

  • 제공 리소스 - (이용 가능한 리소스? 게시된 리소스?) (UCS에 정의되어 있지 않음) 서비스가 상호작용을 위해 노출하는 네트워크로 접근 가능한 엔터티로, 이 문서에 정의된 프로토콜을 사용하여 조회하거나 조작할 수 있습니다.
  • 요청 에이전트 - (엔터티라는 UCS 용어) 엔터티로서 (예: 클라이언트, 사용자 또는 프로세스), 제공 가능한 리소스와 상호작용하기 위한 요청을 시작합니다.

2.2 보안 및 개인정보 보호

리소스 관리자는 제공 리소스를 비공개로 유지하거나 누구나 이용할 수 있도록 공개하거나, 다음과 같은 제한된 집합에만 표시되도록 제한할 수 있습니다: 요청 에이전트.

  • 인증 - 다음 대상의 신원을 검증하는 과정입니다: 에이전트, 요청을 실행하는 주체입니다.
  • 인가 - 다음 대상의 권한을 결정하는 과정입니다: 에이전트, 특정 리소스에 접근하거나 다음 집합 중 하나를 수행할 권한이 있는지를 결정합니다: 작업.
  • 리소스 관리자 - (제어자, 해당 명세: UCS) 에이전트로서, 다음에 대한 접근을 제어할 권한을 가집니다: 제공 리소스.

2.3 적합성

비규범적으로 표시된 절뿐만 아니라, 이 명세의 모든 작성 지침, 다이어그램, 예시 및 참고 사항도 비규범적입니다. 이 명세의 나머지 모든 내용은 규범적입니다.

키워드 MAY, MUST, MUST NOT, OPTIONAL, RECOMMENDED, REQUIRED, SHOULD 및 SHOULD NOT를 이 문서에서는 다음에 설명된 대로 해석합니다: BCP 14 [RFC2119] [RFC8174] 단, 여기에 표시된 것처럼 모두 대문자로 나타나는 경우에만 해당합니다.

LWS 서버는 HTTP 서버이며 [rfc9112], 다음을 준수합니다: 이 명세의 모든 관련 "MUST" 문장. 구체적으로, 다음 절의 관련 규범적 "MUST" 문장을 9. 작업에서 반드시 준수해야 합니다.

LWS 클라이언트는 HTTP 클라이언트이며 [rfc9112], 이 명세의 모든 관련 "MUST" 문장을 준수합니다. 구체적으로, 관련 규범적 "MUST" 문장을 이 문서의 9. 작업에서 반드시 준수해야 합니다.

3. 용어

"인가 서버"와 "클라이언트"라는 용어는 OAuth 2.0 인가 프레임워크에 정의되어 있습니다 [RFC6749].

"최종 사용자"와 "발급자"라는 용어는 OpenID Connect Core 1.0에 정의되어 있습니다 [OPENID-CONNECT-CORE].

이 명세는 다음 용어를 정의합니다:

  • 접근 권한 부여 — 다음 주체가 생성한 데이터 객체입니다: 저장소 제어자. 이 객체는 다음 주체의 능력을 표현합니다: 에이전트, 다음 대상에 특정 행위를 수행하는 능력입니다: 저장소 리소스, 특정한 정의된 제약 조건 내에서 수행합니다.
  • 접근 프로파일 — 접근 프로파일은 유효한 접근 정책을 표현하기 위한 요구 사항을 설명합니다. 모든 접근 프로파일은 URI로 식별되며, 서버는 하나 이상의 접근 프로파일에 대한 지원을 자신의 서비스 객체에 있는 conformsTo 속성에서 해당 프로파일을 참조하여 나타냅니다. 저장소 설명 리소스에 있는 객체입니다.
  • 접근 요청 — 다음 주체가 제출한 데이터 객체입니다: 에이전트. 이 객체는 다음 대상에 특정 행위를 수행하려는 요청을 표현합니다: 저장소 리소스. 여기에는 원하는 범위와 제약 조건이 포함됩니다.
  • 에이전트 — URI로 식별되는 사람, 사회적 실체 또는 소프트웨어입니다.
  • 인증 자격 증명 — 보안 토큰으로, 다음 대상에 관한 클레임을 표명합니다: 에이전트 또는 최종 사용자. 이 토큰은 암호학적 증명으로 보호됩니다. 인증 자격 증명의 예로는 OpenID Connect ID 토큰과 같은 신원 어설션, SAML 기반 어설션 및 ZCAPs와 같은 능력 어설션이 있습니다.
  • 인증 스위트 — 정의된 검증 메커니즘으로, 구체적으로 직렬화된 인증 자격 증명에 사용됩니다.
  • 보조 리소스 — 저장소 리소스로, 다음 대상에 대해 특정 역할을 수행합니다: 저장소 리소스. 이 대상은 주 리소스라고 하며, 보조 리소스의 수명은 주 리소스에 종속됩니다. 이 명세는 링크 집합 리소스와 메타데이터 리소스를 보조 리소스의 유형으로 정의하지만, LWS 서버는 추가 종류의 보조 리소스를 자유롭게 관리할 수 있습니다(예: 접근 제어 리소스, 알림 수신함). 보조 리소스는 특정 유형의 웹 링크를 사용하여 발견합니다 [RFC8288](다음 절 참조: 9.1 리소스 메타데이터). 일부 구현에서는 일부 보조 리소스가 자신의 주 리소스와 동일할 수 있습니다.
  • 저장소 리소스 — HTTP 리소스로, 다음 문서에 정의되어 있습니다: HTTP 의미론. Linked Web Storage 프로토콜이 정의하는 읽기 작업을 지원합니다. 다음 문서에 따라, HTTP 의미론, 이 명세는 "리소스의 본질을 제한하지 않으며, 단지 리소스와 상호작용하는 데 사용할 수 있는 인터페이스를 정의합니다." [RFC9110] 이 클래스는 IRI https://www.w3.org/ns/lws#StorageResource로 식별됩니다.
  • 컨테이너 — 저장소 리소스로서, 다음의 컬렉션을 열거할 수 있습니다: 저장소 리소스. 설명된 규칙을 준수하며, 해당 규칙은 8절. 컨테이너에 있습니다. 컨테이너에 새 리소스를 생성하거나 기존 컨테이너를 삭제하는 기능은 다음에 명시된 요구 사항을 따릅니다: 9절. 작업.
  • 데이터 리소스 — 데이터를 담고 있는 저장소 리소스로, 문서, 이미지 또는 구조화된 정보 등이 해당하며, 갱신 및 삭제 작업에 대한 지원은 다음에 명시된 요구 사항을 따릅니다: 9절. 작업.
  • 포함 관계 — 다음 두 대상 간의 관계입니다: 컨테이너 및 저장소 리소스. 이 리소스의 수명 주기는 컨테이너가 관리합니다.
  • 링크 집합 리소스 — 다음의 한 유형입니다: 보조 리소스. 이 리소스의 표현은 다음을 준수합니다: 링크 집합: 미디어 유형 및 링크 관계 유형 — 링크 집합용. 링크 집합 리소스의 갱신 작업은 다음에 명시된 요구 사항을 따릅니다: 9절. 작업.
  • 메타데이터 리소스 — 보조 리소스로, 다음이 관리합니다: 저장소. 다음 대상을 설명하며, 저장소 리소스, 설명된 규칙을 준수합니다. 해당 규칙은 미정에 있습니다. 메타데이터 리소스의 수명 주기는 다음 대상에 종속됩니다: 저장소 리소스, 자신이 설명하는 대상입니다.
  • 리소스 — 리소스는 다음에서 설명하는 것과 같습니다: [WebArch] 및 [RFC3986], "URI로 식별될 수 있는 모든 것"입니다. 본질적인 특성을 메시지로 전달할 수 있는 리소스(예: 웹 페이지, 이미지, 구조화된 데이터 객체 등)는 다음과 같이 부릅니다: 정보 리소스 [WebArch].
  • 저장소 — 계층적으로 구성된 HTTP 리소스의 집합으로, 수명 주기는 다음 프로토콜에 설명된 규칙에 따라 관리됩니다: Linked Web Storage 프로토콜. 저장소는 다음으로 설명됩니다: 저장소 설명 리소스. 이 리소스는 해당 리소스에 대한 상호작용 기능을 제공하는 서비스 컬렉션을 참조합니다.
  • 저장소 제어자 — 에이전트로서, 다음에 있는 모든 리소스를 제어합니다: 저장소.
  • 저장소 설명 — 저장소 리소스로, 다음 문서의 요구 사항을 준수합니다: W3C 제어 식별자 문서 [CID-1.0]. 다음 대상을 설명하며, 저장소, 해당 대상의 서비스와 기능도 함께 설명합니다.
  • 저장소 루트 — 컨테이너로, 다음 계층의 루트에 있습니다: 포함 관계 계층, 다음에 속합니다: 저장소. 저장소 루트는 유일한 저장소 리소스로서, LWS 포함 관계 계층에서 부모가 없으며, 주 리소스도 없습니다.
  • 알림 — 다음 대상에서 발생한 이벤트를 설명하는 메시지입니다: 리소스.
  • 구독 — 수신에 대한 관심을 표현하는 등록입니다. 특정 리소스 또는 리소스 집합에 대한 알림을 수신합니다.
  • 구독자 — 에이전트로서, 다음을 생성하고 구독, 그 결과로 발생하는 알림을 수신합니다.
  • 알림 스위트 — 정의된 전달 메커니즘으로, 구체적인 채널을 통해 다음 대상에게 알림을 전송합니다: 구독자.

4. 인증

이 절은 다음 대상을 식별하는 메커니즘을 정의합니다: 에이전트 및 최종 사용자, 이들은 Linked Web Storage 서버와 상호작용합니다. 이 명세는 특정한 형식을 의무화하지 않습니다: 인증 자격 증명의 형식입니다. 다만, 기존 신원 시스템을 Linked Web Storage 인가 프레임워크와 함께 사용할 수 있는 방법을 설명합니다.

4.1 인증 자격 증명 데이터 모델

이 절에 설명된 데이터 모델은 모든 구체적인 직렬화에 대한 요구 사항을 개괄합니다: 인증 자격 증명의 직렬화입니다.

인증 자격 증명은 반드시 주체에 관한 변조를 감지할 수 있는 클레임을 포함해야 하며, 다음을 포함합니다:

  • 주체 필수 — 최종 사용자의 식별자입니다. 이는 반드시 URI여야 합니다.
  • 발급자 필수 — 다음을 발급한 엔터티의 식별자입니다: 인증 자격 증명. 이는 반드시 URI여야 합니다.
  • 클라이언트 필수 — 클라이언트 애플리케이션의 식별자입니다. 이는 가급적 URI인 것이 좋습니다.
  • 수신 대상 제한 권장 — 값의 목록으로, 가급적 인가 서버 식별자를 포함하는 것이 좋습니다.

4.2 인증 자격 증명 유효성 검사

다음의 유효성 검사에는 인증 자격 증명, 신뢰 관계가 필요하며, 이는 자격 증명의 검증자와 발급자 간의 관계입니다. 이 신뢰 관계는 허용됩니다, 수립하는 것이 대역 외 메커니즘을 통해서도 가능합니다. 신뢰를 수립하기 위한 추가 메커니즘은 검증자와 발급자 사이에서 사용되며, 특정 인증 스위트에 개괄되어 있습니다.

인증 자격 증명은 반드시 서명되어야 합니다. 권장되는 서명 방식은 비대칭 암호화를 사용하는 것입니다.

4.3 인증 자격 증명 유형 식별자

각 인증 스위트는 반드시 토큰 유형 URI와 연결되어야 합니다. 인증 스위트는 가급적 IANA "OAuth URI" 레지스트리에 정의된 URI를 사용하는 것이 좋습니다.

5. 인가

Linked Web Storage는 웹에서 보호된 데이터를 영속적으로 저장하고 관리하는 메커니즘을 설명합니다. 인가는 다음과 같은 메커니즘으로, 이를 통해 에이전트는 접근 토큰을 요청하고 제시하여 이 보호된 데이터에 접근합니다.

이 절은 OAuth 2.0에 기반한 인가 프레임워크를 정의하며 [RFC6749], 이를 기본 메커니즘으로 사용하여 접근 토큰을 획득하고 제시합니다. 서버는 이 기본 메커니즘 외에 추가 인가 메커니즘을 선택적으로 지원할 수 있습니다.

5.1 역할

LWS 인가의 역할은 OAuth 2.0의 1.1절에서 정의한 역할과 같습니다 [RFC6749]: 리소스 소유자, 리소스 서버, 클라이언트(이 명세에서는 인가 클라이언트라고 하여 모호함을 피합니다) 및 인가 서버. 저장소 서버는 LWS 저장소 명세도 준수하는 리소스 서버의 한 유형입니다.

5.2 프로토콜 흐름

이 명세는 클라이언트와 인가 서버 간의 상호작용 및 클라이언트와 준수 저장소 서버 간의 상호작용을 설명합니다.

인가 서버와 저장소 서버 간의 상호작용은 이 명세의 범위에 포함되지 않습니다. 인가 서버는 저장소 서버와 동일한 서버일 수도 있고 별도의 엔터티일 수도 있습니다.

5.2.1 인가 서버 발견

저장소 서버가 관리하는 모든 보호된 리소스에는 유효한 접근 토큰이 필요하며, 이는 신뢰할 수 있는 인가 서버가 생성합니다. 클라이언트는 신뢰할 수 있는 인가 서버의 위치를 발견할 수 있으며, 이를 위해 보호된 리소스에 인가되지 않은 HTTP 요청을 보냅니다.

401 (Unauthorized) 응답을 생성하는 저장소 서버는 반드시 다음을 보내야 합니다: WWW-Authenticate 헤더 필드, 규격에 부합하는 인증 챌린지를 하나 이상 포함하는 필드입니다. 규격에 부합하는 인증 챌린지는 반드시 다음을 포함해야 합니다: resource_metadata 매개변수, 다음 문서의 5.1절에 정의된 매개변수입니다 [RFC9728]. 그 값은 다음 문서의 URL입니다: 해당 보호된 리소스 메타데이터 문서, 요청된 리소스에 대한 문서입니다.

응답은 또한 다음을 식별하는 Link 헤더를 반드시 포함해야 합니다: 저장소, 요청된 리소스를 포함하는 저장소로, 다음에 설명되어 있습니다: 6.1.2 발견 및 바인딩. 클라이언트는 이 URI를 resource 매개변수로 제공하여 접근 토큰을 요청하며, 이는 다음에 설명되어 있습니다: 5.2.5.1 요청.

다른 헤더와 매개변수도 선택적으로 포함할 수 있습니다.

아래에 401 응답 예시가 있습니다.

예시 1 
HTTP/2 401 Unauthorized
Link: <https://storage.example/storage_1>; rel="https://www.w3.org/ns/lws#storage"
WWW-Authenticate: Bearer resource_metadata="https://storage.example/.well-known/oauth-protected-resource/storage_1/photos/img.jpg",
                error="invalid_token"

(제거될 수 있는 기능) 이슈

작업 그룹은 보호된 리소스 메타데이터 지원에 관한 구현자의 의견을 적극적으로 구하고 있습니다. 충분한 구현 경험이 수집되지 않으면 이 기능은 제거되거나 변경될 수 있습니다.

보호된 리소스 메타데이터 문서는 클라이언트가 접근 토큰을 획득하는 방법을 설명하며, 이 토큰은 리소스에 대한 것입니다. 이 문서는 반드시 OAuth 2.0 보호된 리소스 메타데이터를 준수해야 합니다 [RFC9728].

이 명세는 다음 문서를 확장합니다 [RFC9728]. 확장 사항은 다음과 같습니다: authorization_servers 매개변수는 필수이며, 보호된 리소스 메타데이터 문서에 있어야 합니다. 그 값은 반드시 다음을 포함해야 합니다: 하나 이상의 발급자 식별자, 인가 서버의 식별자입니다.

참고

보호된 리소스 메타데이터 문서의 resource 값은 요청된 리소스를 식별하며, 해당 리소스를 포함하는 저장소를 식별하지 않습니다. 이와 달리, 토큰 요청의 resource 매개변수는 저장소를 식별하며, 이 저장소가 접근 토큰의 수신 대상이 됩니다.

아래에 보호된 리소스 메타데이터 문서 예시가 있습니다.

예시 2 
{
    "resource": "https://storage.example/storage_1/photos/img.jpg",
    "authorization_servers": ["https://authorization.example"]
}

5.2.3 발견 검증 (클라이언트 수행)

클라이언트가 접근 토큰을 획득하는 데 사용하는 값은 저장소 서버가 401 (Unauthorized) 응답으로 제공합니다. 접근 토큰을 요청하기 전에 클라이언트는 반드시 다음 검사를 수행해야 하며, 각 검사는 발견된 값을 401 응답을 발생시킨 요청 URI와 비교합니다. 검사 중 하나라도 실패하면, 클라이언트는 절대로 발견된 값을 사용하여 접근 토큰을 요청해서는 안 됩니다.

  • resource_metadata URL은 반드시 동일한 스킴과 권한 구성 요소를 가져야 하며, 이는 요청 URI와 비교한 것입니다.
  • resource 값은 다음 문서의 값이며, 보호된 리소스 메타데이터 문서, 반드시 다음과 동일해야 합니다: 요청 URI, 이는 다음 문서의 3.3절에서 요구합니다 [RFC9728].
  • 클라이언트는 반드시 다음을 획득해야 합니다: 저장소 설명, 다음의 설명입니다: 저장소, Link 헤더로 식별되는 저장소입니다. 해당 StorageRoot 서비스의 serviceEndpoint는 반드시 동일한 스킴과 권한 구성 요소를 가져야 하며, 이는 요청 URI와 비교한 것입니다.
참고

이러한 검사는 보호된 리소스 메타데이터와 저장소가 모두 해당 서버를 설명하도록 보장합니다. 클라이언트가 요청을 보낸 서버이므로, 다음 문서의 7.3절에 설명된 TLS 서버 인증이 [RFC9728] 메타데이터에 적용됩니다. 이러한 검사가 없으면 악의적인 서버가 클라이언트로 하여금 접근 토큰을 획득하게 할 수 있습니다. 다른 저장소에 대한 토큰을 획득하게 한 다음 그 토큰을 재전송할 수 있습니다. 클라이언트는 저장소 설명을 캐시하여 이를 조회하는 일을 피할 수 있습니다. 매번 토큰을 요청하기 전에 조회할 필요가 없습니다. 다음을 참조하세요: 16.3 리소스 발견.

5.2.4 인가 서버 메타데이터

인가 서버는 클라이언트가 발견할 수 있도록 메타데이터 리소스를 반드시 제공해야 합니다. 엔드포인트 위치와 기능을 발견하며, 이는 다음에 설명되어 있습니다: [RFC8414]. 이 메타데이터 리소스는 반드시 다음 경로를 가진 URL에서 이용할 수 있어야 합니다: /.well-known/lws-configuration.

다음에 정의된 메타데이터 외에도 [RFC8414], LWS 인가 서버 메타데이터 문서는 다음 매개변수를 정의합니다:

  • subject_token_types_supported 선택 사항입니다. 유효한 값의 목록을 포함하는 JSON 배열이며, subject_token_type 값은 인가 서버의 토큰 엔드포인트에 제공할 수 있는 값입니다. 인가 서버는 가급적 지원하는 주체 토큰을 알리는 것이 좋으며, 이를 위해 이 항목을 서버 메타데이터 문서에 포함합니다.
  • subject_identifier_types_supported 선택 사항입니다. 주체 식별자 유형의 목록을 포함하는 JSON 배열이며, 인가 서버가 지원하는 유형입니다. 각 값은 "https:"와 같은 스킴으로 시작하는 URI이거나, 다음에 해당합니다: 분산 식별자의 경우, "did:" 뒤에 DID 메서드 이름이 옵니다(예: "did:web", "did:key"). 인가 서버는 가급적 주체 식별자 유형을 알리는 것이 좋으며, 지원하는 유형을 나타내기 위해 이 항목을 서버 메타데이터 문서에 포함합니다. 생략하면 기본값은 ["https"]입니다.

아래에 인가 서버 메타데이터 리소스 예시가 있습니다.

예시 3 
{
    "issuer": "https://authorization.example",
    "grant_types_supported": [
        "urn:ietf:params:oauth:grant-type:token-exchange"],
    "token_endpoint": "https://authorization.example/token",
    "jwks_uri": "https://authorization.example/jwks",
    "claims_supported": [
        "sub",
        "iss",
        "client_id",
        "aud"],
    "response_types_supported": [
        "token"],
    "subject_token_types_supported": [
        "urn:ietf:params:oauth:token-type:jwt",
        "urn:ietf:params:oauth:token-type:id_token"],
    "subject_identifier_types_supported": [
        "did:web",
        "did:key",
        "https"]
}

5.2.5 토큰 교환

LWS 인가 서버는 OAuth 2.0을 준수하는 인가 서버로서, 클라이언트에 접근 토큰을 발급할 수 있으며, 저장소 서버에서 사용할 수 있는 토큰입니다. 접근 토큰을 발급하려면 클라이언트가 먼저 유효한 주체 토큰을 제시해야 하며, 예를 들면 인증 자격 증명을 OAuth 2.0 토큰 교환을 통해 인가 서버에 제시합니다 [RFC8693].

5.2.5.1 요청

인가 서버의 토큰 엔드포인트는 반드시 다음을 지원해야 합니다: urn:ietf:params:oauth:grant-type:token-exchange 권한 부여 유형, OAuth 2.0 토큰 교환에 설명된 유형입니다 [RFC8693].

토큰 교환 권한 부여 유형을 수행할 때는 다음 추가 요구 사항이 적용됩니다:

  • resource 매개변수는 필수입니다. 이 매개변수의 값은 반드시 URI여야 하며, 결과 접근 토큰의 aud(수신 대상) 클레임을 채우는 데 사용됩니다. 제공된 값은 반드시 다음의 URI여야 합니다: 저장소, 요청된 리소스를 포함하는 저장소로, 해당 URI는 Link 헤더에서 제공됩니다. 인가되지 않은 응답의 헤더입니다. 인가 서버는 반드시 모든 요청을 거부해야 합니다. 해당 요청의 resource 매개변수가 알 수 없거나 신뢰할 수 없는 저장소를 식별하는 경우입니다.
  • subject_token 매개변수는 필수입니다. 이 매개변수의 값은 반드시 유효한 주체 토큰을 포함해야 하며, 예를 들면 인증 자격 증명이 있습니다.
  • 클라이언트에 접근 토큰을 반환하기 전에 인가 서버는 반드시 제시된 모든 토큰의 유효성을 성공적으로 검사해야 합니다.

토큰 요청의 비규범적 예시입니다(subject_token 매개변수는 일부가 생략되었습니다).

예시 4 
POST /token HTTP/1.1
Host: authorization.example
Content-Type: application/x-www-form-urlencoded

grant_type=urn%3Aietf%3Aparams%3Aoauth%3Agrant-type%3Atoken-exchange
&resource=https%3A%2F%2Fstorage.example%2Fstorage_1
&subject_token=eyJ0eXAiOiJhcytqd3QiLCJhbGciO...fiK51VwhsxJ-siBMR-YFiA
&subject_token_type=urn%3Aietf%3Aparams%3Aoauth%3Atoken-type%3Aid_token
5.2.5.2 응답

토큰 요청이 유효하고 클라이언트가 해당 요청을 보낼 권한을 부여받았다면, 인가 서버의 응답은 반드시 OAuth 2.0 인가 프레임워크의 5.1절을 준수해야 합니다 [RFC6749]. 결과 접근 토큰은 반드시 다음을 준수해야 합니다: OAuth 2.0 접근 토큰용 JSON 웹 토큰 프로파일 [RFC9068].

또한 접근 토큰은 다음 요구 사항을 충족해야 합니다:

  • sub(주체) — 필수입니다. 이 클레임은 반드시 다음을 식별하는 URI여야 합니다: 에이전트, 작업을 수행하는 에이전트입니다
  • iss(발급자) — 필수입니다. 이 클레임은 반드시 인가 서버의 URI여야 합니다
  • client_id(클라이언트 ID) — 필수입니다. 이 클레임은 반드시 클라이언트를 식별하는 URI여야 합니다.
  • aud(수신 대상) — 필수입니다. 이 클레임은 반드시 제공된 URI를 포함해야 하며, 클라이언트가 resource 매개변수로 제공한 URI로서, 다음의 URI입니다: 저장소. 이 값은 제한하는 데 사용됩니다. 접근 토큰이 유효한 대상 엔터티를 제한합니다.
  • exp(만료) — 필수입니다. 인가 서버는 가급적 수명이 짧은 토큰을 발급하는 것이 좋습니다. (권장: 300초 이하) 이는 토큰 도난으로 인한 노출을 제한하기 위한 것입니다.
  • iat(발급 시각) — 필수입니다.
  • jti(JWT ID) — 필수입니다.

아래에 성공적인 토큰 응답의 비규범적 예시가 있습니다.

예시 5 
HTTP/1.1 200 OK
Content-Type: application/json

{
    "access_token":"eyJ0eXAiOiJhcytqd3QiLCJhbGciOiJFUzI1NiIs...DeWt4QuZXso",
    "token_type":"Bearer",
    "expires_in":300
}

유효하지 않거나 인가되지 않은 모든 요청에는 반드시 오류 응답을 반환해야 하며, 이는 다음의 5.2절에 설명되어 있습니다: OAuth 2.0 인가 프레임워크 [RFC6749].

예시 6 
HTTP/1.1 400 Bad Request
Content-Type: application/json

{
    "error":"invalid_request"
}

5.2.6 토큰 유효성 검사 (저장소 서버 수행)

클라이언트는 접근 토큰을 획득하면 이를 저장소 서버에 제시합니다. 저장소 서버는 어떤 작업이든 수행하기 전에 이 토큰을 검증할 책임이 있습니다.

5.2.6.1 제시

클라이언트는 반드시 다음을 사용하여 저장소 서버에 접근 토큰을 제시해야 합니다: Authorization 헤더, 다음에 정의된 인증 방식을 사용하는 헤더입니다 [RFC6750].

예시 8 
Authorization: Bearer eyJ0eXAiOiJhcytqd3QiLCJhbGciOiJFUzI1NiIs...DeWt4QuZXso
5.2.6.2 유효성 검사

저장소 서버는 반드시 다음 검사를 수행하여 접근 토큰의 유효성을 검사해야 하며, 하나라도 실패하면 요청을 거부해야 합니다:

  • JWT 서명 유효성 검사: 인가 서버의 공개 키를 사용하여 JWT 서명을 검증합니다. 이 키는 다음에서 조회합니다: jwks_uri, 인가 서버 메타데이터에 지정된 URI입니다. 저장소 서버는 가급적 이러한 키를 캐시하는 것이 좋으며, 반드시 키 교체를 지원해야 합니다.
  • 발급자 유효성 검사: iss 클레임이 예상한 인가 서버 식별자와 일치하는지 검증합니다.
  • 수신 대상 유효성 검사: aud 클레임이 다음의 URI를 포함하는지 검증합니다: 저장소, 대상 리소스를 포함하는 저장소입니다.
  • 시간 유효성 검사, 시스템 간 허용되는 시계 오차를 고려합니다.
    • 현재 시각이 exp(만료) 클레임보다 이전인지 검증합니다.
    • 현재 시각이 nbf(유효 시작 시각) 클레임보다 이전이 아닌지 검증합니다. 해당 클레임이 있는 경우에 적용합니다.
    • iat(발급 시각) 클레임이 미래 시각이 아닌지 검증합니다.

유효성 검사에 실패하면 저장소 서버는 반드시 401 Unauthorized를 반환해야 하며, WWW-Authenticate 헤더를 포함해야 합니다. 이 헤더에는 resource_metadata 매개변수와 적절한 오류 매개변수를 포함합니다. 예를 들면, invalid_token, invalid_request 또는 insufficient_scope입니다.

토큰 자체는 유효하지만 인가 정책이 요청된 작업을 허용하지 않는다면, 저장소 서버는 반드시 요청을 거부해야 합니다.

6. 발견

6.1 저장소 설명 리소스

저장소 설명 리소스는 클라이언트가 사용할 수 있는 정보를 제공합니다. 다음과 상호작용할 때 사용하는 정보로, 저장소, 기능과 서비스 엔드포인트에 대한 설명을 포함합니다.

6.1.1 데이터 모델

저장소 설명 리소스는 W3C 제어 식별자 문서를 특수화한 문서입니다 [CID-1.0]. 이 리소스는 다음에 정의된 데이터 모델을 준수하며 [CID-1.0], LWS 전용 속성으로 확장됩니다.

  • id - id 속성은 필수입니다. 그 값은 반드시 정규 URI여야 하며, 다음의 URI입니다: 저장소. 다음에 따라 [CID-1.0], 이 URI는 또한 정규 URL이며, 제어 식별자 문서의 URL입니다.
  • type - type 속성은 필수입니다. 그 값은 반드시 문자열이어야 하며, 다음과 같아야 합니다: Storage. 또는 Storage와 같은 항목을 포함하는 문자열 집합이어야 합니다. (대소문자를 구분합니다).
  • capability - capability 속성은 선택 사항입니다. 그 값은 반드시 기능의 집합이어야 하며, 각 기능은 다음 속성을 포함하는 맵으로 설명됩니다. 추가 속성이 선택적으로 존재할 수 있습니다.
    • id - id 속성은 선택 사항입니다. 존재하면 그 값은 반드시 URI여야 합니다.
    • type - type 속성은 필수입니다. 그 값은 반드시 문자열 또는 문자열 집합이어야 합니다.
  • service - service 속성은 필수입니다. 그 값은 반드시 서비스의 집합이어야 하며, 각 서비스는 다음 속성을 포함하는 맵으로 설명됩니다. 추가 속성이 선택적으로 존재할 수 있습니다. 이 집합은 반드시 다음과 같은 type을 가진 서비스를 포함해야 합니다: StorageRoot.
    • id - id 속성은 선택 사항입니다. 존재하면 그 값은 반드시 URI여야 합니다.
    • type - type 속성은 필수입니다. 그 값은 반드시 문자열 또는 문자열 집합이어야 합니다.
    • serviceEndpoint - serviceEndpoint 속성은 필수입니다. 그 값은 반드시 URI여야 합니다.
예시 9: 최소 저장소 설명 리소스 
{
  "@context": [
    "https://www.w3.org/ns/cid/v1",
    "https://www.w3.org/ns/lws/v1"
  ],
  "id": "https://storage.example/",
  "type": "Storage",
  "service": [{
    "type": "StorageRoot",
    "serviceEndpoint": "https://storage.example/root/"
  }]
}

6.1.2 발견 및 바인딩

GET 및 HEAD 요청이 다음 리소스를 대상으로 할 때, 저장소 리소스, 모든 응답은 반드시 다음을 포함해야 합니다: Link 헤더, 그 대상은 다음의 정규 URI여야 합니다: 저장소. 이 헤더에는 관계 (rel) 매개변수가 포함되며, 그 값은 https://www.w3.org/ns/lws#storage와 같아야 합니다.

다음에 대한 요청은 저장소 URI, 반드시 다음을 준수하는 문서를 반환해야 합니다: 저장소 설명 리소스 데이터 모델, 미디어 유형은 application/lws+cid여야 합니다. 콘텐츠 협상으로 다른 형식이 요구되는 경우는 예외입니다.

6.1.3 저장소 기능

저장소 설명은 추가 기능에 대한 설명을 포함할 수 있으며, 다음이 지원하는 기능입니다: 저장소.

저장소가 클라이언트의 up 링크 변경을 허용하는 경우, 다음의 링크입니다: 저장소 리소스, 이를 통해 다음 간에 리소스를 이동할 수 있으며, 컨테이너, 이는 다음에 설명되어 있습니다: 9.6 리소스 이동 (컨테이너 간), 반드시 다음과 같은 type을 가진 기능을 설명해야 합니다: 해당 값은 MoveResource입니다. 클라이언트는 절대로 up 링크가 수정 가능하다고 가정해서는 안 됩니다. 이 기능이 없는 경우에 적용됩니다. 다음 속성은 MoveResource 기능에 대해 정의됩니다:

  • appliesTo - appliesTo 속성은 선택 사항입니다. 존재하면 그 값은 반드시 다음 유형의 이름을 나타내는 문자열 집합이어야 합니다: 저장소 리소스, 이 기능이 적용되는 유형이며, 예를 들면 DataResource 또는 Container입니다. 이 속성이 없으면 기능은 적용됩니다. 다음에만 적용됩니다: 데이터 리소스.
  • preservesIdentifier - preservesIdentifier 속성은 선택 사항입니다. 존재하면 그 값은 반드시 다음의 보존 여부를 나타내는 불리언이어야 합니다: 저장소가 식별자를 보존하는지, 이동한 리소스의 식별자를 보존하는지 나타냅니다. 이 속성이 없으면 클라이언트는 절대로 가정해서는 안 됩니다. 식별자가 보존된다고 가정해서는 안 되며, 반드시 갱신에 대한 응답에 의존하여 다음의 식별자를 결정해야 합니다: 리소스.
예시 10: 클라이언트가 이동할 수 있음을 알리는 저장소 설명 리소스, 컨테이너 간에 리소스를 이동할 수 있습니다 
{
  "@context": [
    "https://www.w3.org/ns/cid/v1",
    "https://www.w3.org/ns/lws/v1"
  ],
  "id": "https://storage.example/",
  "type": "Storage",
  "capability": [{
    "type": "MoveResource",
    "appliesTo": ["DataResource", "Container"],
    "preservesIdentifier": true
  }],
  "service": [{
    "type": "StorageRoot",
    "serviceEndpoint": "https://storage.example/root/"
  }]
}

6.1.4 저장소 서비스

저장소 설명 리소스는 반드시 StorageRoot 서비스를 포함해야 하며, 그 serviceEndpoint는 다음의 URI입니다: 저장소 루트 컨테이너. 다음에 연결된 추가 서비스도 저장소, 선택적으로 존재할 수 있습니다. 이러한 추가 서비스의 API 정의는 이 명세의 범위에 포함되지 않습니다.

7. 논리적 리소스 구성

7.1 컨테이너 모델

Linked Web Storage는 리소스를 다음으로 구성합니다: 컨테이너. 컨테이너는 다른 리소스에 대한 참조를 보유하는 특수한 리소스로, 해당 리소스를 멤버라고 합니다. 컨테이너는 디렉터리나 컬렉션과 유사한 구성 단위로서, 클라이언트가 리소스를 그룹화하고 발견하며, 탐색할 수 있도록 합니다. 컨테이너는 멤버 리소스에 대한 참조를 유지하며, 여기에는 컨테이너가 아닌 리소스와 추가 컨테이너 리소스가 모두 포함될 수 있어 계층적 구성이 가능합니다. 일반적으로 컨테이너 자체의 고유 콘텐츠는 최소한이며, 메타데이터나 멤버의 열거를 제외하면 거의 없습니다. 주된 역할은 하위 리소스를 모으고 구조화하는 것입니다. 저장소 시스템의 루트는 컨테이너로 지정되며, 상위 부모가 없는 최상위 구성 단위로 기능합니다. 다음의 구조는 컨테이너 표현, 다음에 정의되어 있습니다: 8.1 컨테이너 표현. 미디어 유형과 페이지 나누기 요구 사항은 다음에 정의되어 있습니다: 12. LWS 미디어 유형. 저장소는 선택적으로 루트 컨테이너로 기능하여 직접 쓰기를 허용할 수 있습니다.

모든 LWS 저장소에는 저장소 루트가 있으며, 최상위 구성 단위로 기능합니다. 저장소 루트는 부모가 없으며 다음에 대한 진입점 역할을 합니다: 저장소 계층.

LWS의 리소스는 다음 중 하나로 분류됩니다:

  • 컨테이너 — 다른 리소스를 포함하는 리소스입니다.
  • 데이터 리소스 — 데이터를 담고 있는 리소스입니다. (예: 문서, 이미지 또는 구조화된 데이터 파일).

7.2 포함 관계

포함 관계는 리소스와 그 부모 컨테이너 간의 관계이며, rel="up" 링크 관계로 표현됩니다. 서버는 반드시 Link 헤더를 포함해야 하며, rel="up"이 부모 컨테이너를 가리켜야 합니다. 이는 모든 루트가 아닌 리소스에 대한 GET 및 HEAD 요청의 응답에 적용됩니다. 

Link: </alice/notes/>; rel="up"

컨테이너의 멤버는 해당 표현에 나열되며, items 속성을 사용합니다. 서버가 이 목록을 관리하며, 클라이언트는 직접 수정할 수 없습니다. 멤버십 변경은 리소스 생성과 삭제의 부수 효과로 발생하며, 서버가 다음을 허용하는 경우에도 발생합니다: 리소스의 up 링크 수정. 이때 다음 간의 리소스 이동으로 발생합니다: 컨테이너, 이는 다음에 설명되어 있습니다: 9.6 컨테이너 간 리소스 이동.

7.3 포함 관계의 무결성

서버는 반드시 다음을 유지해야 합니다: 포함 관계의 무결성을 항상 유지해야 합니다:

  • 생성: 새 리소스가 다음에 생성되면, 컨테이너, 서버는 반드시 해당 리소스를 원자적으로 추가해야 합니다: 컨테이너의 items 목록에 추가합니다.
  • 삭제: 리소스가 삭제되면 서버는 반드시 해당 리소스를 부모에서 원자적으로 제거해야 합니다: 컨테이너의 items 목록. 다음을 삭제하려면 컨테이너, 해당 컨테이너는 비어 있어야 합니다. 단, 재귀적 삭제를 명시적으로 요청한 경우는 예외입니다.
  • 이동: 리소스의 up 링크가 변경되면 서버는 반드시 해당 리소스를 items 목록에서 원자적으로 제거해야 합니다. 이전 부모의 목록이며, 컨테이너의 목록입니다. 그리고 items 목록에 추가해야 합니다. 대상 컨테이너의 목록입니다. up 링크 변경 지원은 선택 사항이며, 그에 따른 요구 사항은 다음에 정의되어 있습니다: 9.6 리소스 이동 (컨테이너 간).
  • 고아 리소스 없음: 모든 루트가 아닌 리소스에는 반드시 다음에서 도달할 수 있어야 합니다: 저장소 루트, 다음을 통해 도달합니다: 포함 관계 계층.
  • 순환 없음: 컨테이너는 절대로 직접적으로나 간접적으로 자신을 포함해서는 안 됩니다.

7.4 리소스 식별

리소스는 URI로 식별됩니다. 리소스의 URI는 다음에서의 위치와 독립적입니다: 포함 관계 계층. 서버는 리소스를 생성할 때 URI를 할당하며, 선택적으로 클라이언트의 힌트를 반영할 수 있습니다. 하지만 클라이언트는 가급적 URI 구조가 포함 관계를 반영한다고 가정하지 않는 것이 좋습니다.

포함 관계는 메타데이터를 통해 표현됩니다. (rel="up" 링크 및 items 속성, 다음에 있는 속성입니다: 컨테이너 표현), URI 경로 구조로 표현되지 않습니다. 이러한 분리는 서버에 URI 할당의 유연성을 제공하면서 명확하게 정의된 구성 모델을 유지할 수 있도록 합니다.

7.5 컨테이너 멤버십 및 인가

클라이언트가 다음에 대한 읽기 접근 권한을 가지면, 컨테이너, 해당 컨테이너 표현은 반드시 포함된 모든 리소스의 식별자를 포함해야 합니다. 해당 컨테이너에 있으며 클라이언트가 접근할 수 있는 리소스입니다. 또한 선택적으로 다음에 포함된 리소스의 식별자도 포함할 수 있습니다: 컨테이너, 클라이언트가 접근할 수 없는 리소스입니다.

클라이언트가 다음 목록을 읽을 수 있다고 해서, 컨테이너 목록, 포함된 리소스 자체에 접근할 수 있음을 의미하지는 않으며, 그 반대도 마찬가지입니다.

8. 컨테이너

8.1 컨테이너 표현

LWS 컨테이너 표현은 컨테이너와 그 내용을 설명합니다. 이 절은 필수 속성과 선택 속성을 정의하며, application/lws+json으로 제공되는 경우에 적용됩니다. 다른 RDF 미디어 유형의 표현은 콘텐츠 협상을 통해 요청할 수 있습니다.

8.1.1 컨테이너 속성

컨테이너 표현은 반드시 다음 속성을 포함해야 합니다:

  • id: 다음의 URI입니다: 컨테이너.
  • type: 값은 "Container"입니다.
  • totalItems: 포함된 리소스의 총수를 나타내는 정수이며, 다음에 포함된 리소스 중 컨테이너, 클라이언트에 공개할 수 있는 리소스의 수입니다. 이 개수는 가급적 정확한 것이 좋지만, 선택적으로 근삿값일 수 있습니다.
  • items: 포함된 리소스 설명의 배열입니다(아래 참조). 해당 대상인 컨테이너가 비어 있으면 이는 반드시 빈 배열이어야 합니다. 다음의 컨테이너 목록이 페이지로 나뉘면 items에는 현재 페이지의 리소스만 포함됩니다. 자세한 내용은 페이지 나누기를 참조하세요.

8.1.2 포함된 리소스 설명

items 배열의 각 항목은 다음에 포함된 리소스를 설명합니다: 컨테이너. 포함된 리소스 설명은 반드시 다음을 포함해야 합니다:

  • id: 포함된 리소스의 URI입니다.
  • type: 리소스의 유형입니다. 반드시 다음이어야 합니다: "DataResource" 또는 "Container", 또는 이 두 문자열 중 하나 이상을 포함하는 배열입니다. 서버는 추가 사용자 정의 유형을 선택적으로 URI로 포함할 수 있습니다(예: ["DataResource", "http://example.org/customType"]).

포함된 리소스 설명은 가급적 다음을 포함하는 것이 좋습니다:

  • format: 리소스의 미디어 유형입니다(예: "text/plain", "image/jpeg"). 반드시 존재해야 합니다. DataResources에 적용됩니다.
  • size: 정수로 표현한 리소스의 크기이며, 단위는 바이트입니다.
  • modified: 리소스를 마지막으로 수정한 날짜와 시각이며, ISO 8601 날짜·시간 문자열로 표현합니다.

9. 작업

이 절은 Linked Web Storage (LWS) 서버가 반드시 지원해야 하는 네 가지 핵심 작업을 정의합니다. 이러한 작업은 리소스와 컨테이너를 전송 방식에 독립적으로 조작하며, 구현 세부 사항보다 의미론에 초점을 맞춥니다. 각 작업은 입력, 예상 동작 및 가능한 응답을 명시합니다. 응답에는 성공 표시, 리소스 표현(해당하는 경우) 및 오류 조건이 포함됩니다. 구현은 반드시 이러한 작업을 원자적이고 일관되게 처리해야 하며, 이는 각 작업이 완전히 성공하거나 부분적인 부수 효과 없이 실패해야 한다는 의미입니다. 오류가 발생하면 응답은 가급적 다음 대상에게 충분한 세부 정보를 제공하는 것이 좋습니다: 에이전트, 민감한 정보를 유출하지 않으면서 문제를 이해할 수 있도록 합니다.

각 핵심 작업(생성, 읽기, 갱신, 삭제)에 대해 사용할 HTTP 메서드, 필수 헤더 또는 기타 특별 고려 사항(콘텐츠 협상, 컨테이너 목록의 페이지 나누기 및 조건부 요청 포함), 서버가 수행하고 반환해야 하는 내용을 설명합니다. 표준 HTTP 상태 코드를 사용하여 결과를 나타내며, 할당량 초과와 같은 상황에 대한 추가 매핑을 제공합니다. (507 Insufficient Storage) 또는 사전 조건 실패(412 Precondition Failed)입니다. 이 바인딩은 HTTP/1.1과 관련 RFC를 준수하려고 합니다(예를 들어 [RFC7231]은 HTTP 의미론, [RFC7233]은 범위 요청, [RFC5789]은 PATCH, [RFC8288]은 웹 링크, [RFC9264]은 링크 집합에 해당합니다). 이를 통해 웹 표준과 자연스럽게 통합됩니다. 발견 가능성은 다음과 같은 메커니즘으로 강조됩니다: Link 헤더와 401 응답의 WWW-Authenticate 헤더, 하드코딩된 URI 위치를 피합니다. 모든 작업에서 메타데이터 통합이 요구되며, 원자성과 서버 관리 속성 및 사용자 관리 속성에 대한 링크 집합 사용을 보장합니다.

참고: 이 명세의 모든 예시와 마찬가지로, 이 절의 예시(HTTP 요청 및 응답 조각)는 비규범적이며 일반적인 사용법을 보여주기 위한 것입니다. 실제 요구 사항은 설명 본문과 표에 명시되어 있습니다. 또한 이 바인딩은 HTTP를 다루지만(최초 대상 프로토콜), 원칙적으로 향후 LWS 작업을 다른 프로토콜에 바인딩할 수도 있습니다. 다음의 미디어 유형 요구 사항은 컨테이너 표현, 다음에 정의되어 있습니다: 12. LWS 미디어 유형.

9.1 리소스 메타데이터

9.1.1 메타데이터

이 절은 메타데이터를 다음과 연결하는 모델을 정의합니다: 저장소 리소스. LWS 메타데이터 시스템은 웹 링크의 원칙에 기반합니다 [RFC8288]. 이를 통해 서버는 유형이 지정된 링크로 리소스 간의 관계를 설명할 수 있습니다. 메타데이터는 발견 가능성을 높이고 자기 설명적인 API를 지원하며, 리소스 작업 및 컨테이너 계층과 일치합니다.

메타데이터 모델 LWS의 모든 메타데이터는 리소스(링크 맥락)에서 시작하는 유형이 지정된 링크의 집합으로 표현됩니다. 각 링크는 다음으로 구성됩니다:

  • 링크 대상: 관련 리소스를 식별하는 URI입니다.
  • 관계 유형: 관계의 성격을 정의하는 문자열입니다.
  • 선택적 대상 속성: 링크 또는 대상 리소스를 추가로 설명하는 키-값 쌍입니다.

메타데이터는 리소스와 해당 표현을 구분하며, 해당하는 경우 여러 미디어 유형을 허용합니다. 다음의 경우, 데이터 리소스, 메타데이터에는 표현이 포함되며 각 표현에는 format과 선택적 sizeInBytes가 있습니다. 다음의 경우, 컨테이너 및 데이터 리소스, 부모를 가리키는 링크인 컨테이너 리소스 링크를 해당 리소스의 메타데이터에 포함되는 것으로 간주합니다.

링크 집합 리소스 다음의 각 리소스에 대해, 저장소, 서버는 반드시 메타데이터 링크를 독립된 리소스로 제공해야 하며, 다음을 따라야 합니다: [RFC9264].

  • 발견: 리소스의 링크 집합은 다음 관계가 있는 Link 헤더를 통해 발견할 수 있습니다: rel="linkset".
  • 미디어 유형: 링크 집합 리소스는 반드시 application/linkset+json으로 이용할 수 있어야 합니다.
  • 무결성: 'linkset' 링크는 반드시 서버가 관리하는 리소스를 가리켜야 합니다. 링크 집합 갱신은 반드시 관련 리소스 작업과 원자적으로 수행되어 일관성을 유지해야 합니다.

메타데이터 발견 클라이언트는 주로 GET 또는 HEAD 요청에 대한 응답의 Link 헤더를 통해 메타데이터를 발견합니다.

  • 저장소: 서버는 반드시 다음이 있는 Link 헤더를 포함해야 합니다: rel="https://www.w3.org/ns/lws#storage", 관련 응답에 포함합니다.
  • 포함 관계: 서버는 반드시 부모를 가리키는 rel="up"이 있는 Link 헤더를 포함해야 하며, 부모는 컨테이너입니다. 모든 루트가 아닌 리소스에 적용됩니다.
  • 선호 사항: 클라이언트는 Prefer 헤더를 선택적으로 사용할 수 있습니다 [RFC7240]. 다음 URI를 사용하여, https://www.w3.org/ns/lws#PreferLinkRelations, 특정 관계를 포함하거나 생략할 수 있습니다.

메타데이터 유형

범주 설명
시스템 관리 서버가 유지 관리하며 읽기 전용입니다. linkset, type, format, size, modified를 포함합니다.
핵심 메타데이터 클라이언트가 관리합니다(서버의 제한을 따릅니다). up, items, title, creator를 포함합니다.
사용자 정의 사용자가 생성한 사용자 정의 어휘와 색인입니다.

수정 가능성 고려 사항 클라이언트는 핵심 메타데이터를 선택적으로 수정할 수 있습니다. 상호 운용성을 보장하려면, 서버는 반드시 표준 HTTP 헤더를 사용하여 기능을 알려야 합니다:

  1. 메서드 발견: 서버는 반드시 GET 및 PATCH 작업 지원을 알려야 하며, 다음에 대한 작업입니다: 링크 집합 리소스. Allow 헤더를 통해 알립니다.

  2. 패치 형식 발견: 서버는 반드시 JSON Patch 지원을 알려야 합니다 [RFC6902]. 다음을 통해 알립니다: Accept-Patch 헤더: Accept-Patch: application/json-patch+json.

  3. 선택적 메서드: 서버는 PUT 또는 다른 패치 형식을 선택적으로 지원할 수 있습니다. 지원한다면 반드시 Allow 및 Accept-Patch 헤더에 각각 포함해야 합니다.

[!IMPORTANT] 클라이언트는 가급적 PUT 또는 특정 패치 형식의 지원을 가정하지 않는 것이 좋습니다. 리소스 헤더에 명시된 경우는 예외이며, 반드시 405 Method Not Allowed 또는 415 Unsupported Media Type 응답을 적절하게 처리해야 합니다.

메타데이터 관리 메타데이터는 리소스에 연결된 다음 대상과 상호작용하여 관리합니다: 링크 집합 리소스 URI. 서버는 반드시 ETag 헤더를 포함해야 하며, 다음에 정의된 헤더입니다: [RFC9110]. GET 및 HEAD 요청에 대한 응답에 포함합니다.

  • 부분 갱신(PATCH): 메타데이터 관리의 주요 메커니즘입니다. 서버는 반드시 application/json-patch+json을 사용하는 PATCH를 지원해야 합니다.

  • 교체(PUT): Allow 헤더에 명시되어 있으면 클라이언트는 선택적으로 전체 링크 집합을 교체할 수 있습니다. 서버가 PUT을 지원하지 않으면 반드시 405 Method Not Allowed로 요청을 거부해야 합니다.

  • 제한: 서버는 특정 링크의 수정을 선택적으로 제한할 수 있습니다. (up 또는 items 등) 시스템 무결성을 유지하기 위한 제한입니다. 서버는 반드시 클라이언트가 수정할 권한이 없는 링크를 보존해야 합니다. 패치를 적용할 때 해당됩니다. 클라이언트가 up 링크를 수정하도록 허용하는 서버는 그에 따라 리소스가 다음 간에 이동하는 것을 허용합니다: 컨테이너. 이러한 서버는 반드시 MoveResource 기능을 다음에 설명해야 합니다: 저장소 설명. 이는 다음에 설명되어 있으며, 6.1.3 저장소 기능, 그에 따른 요구 사항은 다음에 정의되어 있습니다: 9.6 리소스 이동 (컨테이너 간).

  • 수명 주기: 메타데이터의 수명 주기는 설명하는 리소스에 종속됩니다. 리소스를 삭제하면 반드시 연결된 다음 대상이 자동으로 제거되어야 합니다: 링크 집합 리소스 메타데이터.

9.2 리소스 생성

리소스 생성 작업은 새로운 제공 리소스를 기존 컨테이너에 추가합니다. 이 작업은 다음의 생성과 데이터 리소스, 하위 컨테이너의 생성을 모두 처리합니다.

입력:

  • 대상 컨테이너: 다음의 식별자입니다: 컨테이너, 새 리소스를 생성할 위치입니다.
  • 식별 힌트: 새 리소스의 식별자에 대한 선택적 제안입니다. 서버는 이 힌트를 사용할 수 있지만 반드시 사용할 필요는 없습니다.
  • 콘텐츠: 새 리소스의 초기 콘텐츠와 유형입니다.

동작:

  • 식별자 생성: 서버는 새 리소스의 최종 식별자(URI)를 결정합니다. 식별 힌트가 제공되면 서버는 이를 반영하려고 시도하면서 다음 내에서의 고유성과 유효성을 보장합니다: 컨테이너. 힌트가 제공되지 않으면, 서버가 고유 식별자를 생성합니다.
  • 컨테이너 멤버십 갱신: 서버는 새 리소스를 원자적으로 대상의 멤버십 목록에 추가합니다: 컨테이너.
  • 메타데이터 초기화: 서버는 새 리소스의 시스템 메타데이터를 초기화합니다. 리소스에 연결된 다음이 있으면, 메타데이터 리소스, 그것도 초기화합니다.

가능한 응답:

  • 생성됨: 작업이 성공했습니다. 서버는 새로 생성한 리소스의 최종 식별자를 반환합니다.
  • 대상을 찾을 수 없음: 지정된 대상 컨테이너가 존재하지 않습니다.
  • 허용되지 않음: 클라이언트의 신원은 알려져 있지만, 이 대상에 리소스를 생성할 권한이 없습니다: 컨테이너.
  • 알 수 없는 요청자: 서버가 클라이언트의 신원을 인식하지 못하며 인증을 요구합니다.
  • 충돌: 생성된 식별자를 가진 리소스가 이미 존재하거나, 다른 상태 충돌이 있습니다.
  • 알 수 없는 오류: 예상하지 못한 내부 오류가 발생했습니다.

새 리소스는 대상에 POST를 사용하여 생성합니다: 컨테이너 URI. 서버가 최종 식별자를 할당합니다. 클라이언트는 새 리소스의 초기 사용자 관리 메타데이터를 선택적으로 제공할 수 있으며, POST 요청에 하나 이상의 Link 헤더를 포함하여 다음의 구문을 따릅니다: 웹 링크, 다음에 정의되어 있습니다 [RFC8288]. 서버 관리 메타데이터는 반드시 생성 시 서버가 자동으로 생성해야 하며, 절대로 클라이언트가 제공한 링크로 덮어써서는 안 됩니다.

성공하면 서버는 반드시 201 상태 코드를 반환하고, 새 URI를 Location 헤더에 포함해야 합니다. 서버는 반드시 Link 헤더를 포함해야 하며, 주요 서버 관리 메타데이터에 대한 헤더로, 부모를 가리키는 링크를 포함합니다: 컨테이너 (rel="up"). 생성된 리소스 전용의 다음을 가리키는 링크도 포함합니다: 링크 집합 리소스 (rel="linkset"; type="application/linkset+json"). 추가 링크는 가급적 rel="type"을 포함하는 것이 좋습니다(다음을 나타냅니다: https://www.w3.org/ns/lws#Container 또는 https://www.w3.org/ns/lws#DataResource). 본문은 선택적으로 비어 있거나 리소스의 최소 표현을 포함할 수 있습니다. 모든 메타데이터 생성과 연결은 반드시 리소스 생성과 원자적으로 수행되어 일관성을 유지해야 합니다.

POST(컨테이너 URI 대상) – 서버가 할당한 이름으로 생성: POST를 사용하여 기존의 다음 내부에 새 리소스를 추가합니다: 컨테이너. 서버가 식별자를 리소스에 할당합니다. 클라이언트는 생성할 리소스의 유형을 다음과 같이 나타냅니다:

  • 다음을 생성하려면, 컨테이너, 클라이언트는 반드시 rel="type"이 있는 Link 헤더를 포함해야 하며, Container 유형을 가리켜야 합니다: Link: <https://www.w3.org/ns/lws#Container>; rel="type".
  • 다음을 생성하려면, 데이터 리소스, 클라이언트는 적절한 Content-Type 헤더와 함께 요청 본문에 리소스 콘텐츠를 포함합니다.

예시(POST로 새 데이터 리소스 생성):

POST /alice/notes/ HTTP/1.1
Host: example.com
Authorization: Bearer <token>
Content-Type: text/plain
Content-Length: 47

우유
달걀
빵
버터
사과
오렌지 주스

이 예시에서 클라이언트는 다음에 POST 요청을 보냅니다: 컨테이너 /alice/notes/. text/plain 콘텐츠(식료품 목록)를 제공합니다. /alice/notes/가 존재하고 클라이언트가 인가되었다면, 서버는 새로운 데이터 리소스를 생성하여 다음의 컨테이너 멤버십에 추가합니다.

예시(POST에 대한 응답 — 데이터 리소스):

HTTP/1.1 201 Created
Location: /alice/notes/shoppinglist.txt
Content-Type: text/plain; charset=UTF-8
Link: </alice/notes/shoppinglist.txt.meta>; rel="linkset"; type="application/linkset+json"
Link: </alice/notes/>; rel="up"
Link: <https://www.w3.org/ns/lws#DataResource>; rel="type"
Content-Length: 0

예제(존재하지 않는 컨테이너에 POST):

POST /alice/notes/ HTTP/1.1
Host: example.com
Authorization: Bearer <token>
Content-Type: text/plain
Content-Length: 4

test

만약 /alice/notes/ 가 존재하지 않으면 서버는 대상을 찾을 수 없음 결과를 보고한다: 

HTTP/1.1 404 Not Found

참고: 리소스 생성 연산은 하나의 기존 컨테이너에 리소스를 추가한다. 포함 관계 는 URI 경로 구조가 아니라 메타데이터로 표현되므로( 7. 논리적 리소스 구성) 이 명세는 한 번의 연산으로 여러 수준의 컨테이너 를 생성하는 것을 정의하지 않는다. 클라이언트는 각 컨테이너 를 개별 리소스 생성 연산으로 생성한다.

생성: 컨테이너: 새로운 컨테이너를 생성하려면 클라이언트는 기존 부모에 POST를 보냅니다: 컨테이너, Link 헤더로 Container 유형을 나타냅니다. 예를 들면 다음과 같습니다:

POST /alice/ HTTP/1.1
Host: example.com
Authorization: Bearer <token>
Content-Length: 0
Link: <https://www.w3.org/ns/lws#Container>; rel="type"

예시(POST에 대한 응답 — 컨테이너):

HTTP/1.1 201 Created
Location: /alice/notes/
Link: </alice/notes/.meta>; rel="linkset"; type="application/linkset+json"
Link: </alice/>; rel="up"
Link: <https://www.w3.org/ns/lws#Container>; rel="type"
Content-Length: 0

이 요청은 새로운 컨테이너를 /alice/notes/에 생성하며, 서버가 생성한 메타데이터에는 rel="type"의 값으로 https://www.w3.org/ns/lws#Container가 포함됩니다.

생성에 대한 추가 참고 사항(HTTP 바인딩):

  • POST는 멱등적이지 않습니다. 반복하면 중복이 생성될 수 있습니다. 클라이언트는 가급적 의도하지 않은 재시도를 피하거나 고유 식별자 또는 검사를 사용하여 이를 방지하는 것이 좋습니다.
  • 메타데이터 갱신은 원자적입니다. 서버는 반드시 다음을 보장해야 합니다: 링크 집합 리소스가 생성되고 필수 서버 관리 필드가 채워진 후에 성공을 반환해야 합니다.
  • 발견 가능성을 위해 서버는 가급적 다음이 있는 Link 헤더를 포함하는 것이 좋습니다: rel="https://www.w3.org/ns/lws#storage", 401 응답에 포함하여 하드코딩된 URI 없이 클라이언트를 안내합니다.

메타데이터 관리 및 조회(생성 관련): 메타데이터는 주로 읽기 작업을 통해 조회하지만, 생성 중에 만들어집니다. 클라이언트는 생성 직후 새 리소스 URI에 GET 또는 HEAD를 사용하여 이를 조회할 수 있습니다. 클라이언트는 Prefer 헤더를 사용하여 특정 메타데이터 링크(관계 유형을 통해) 및 속성의 포함을 요청할 수 있습니다.

9.3 리소스 읽기

기존 리소스의 표현 또는 다음의 목록을 조회합니다: 컨테이너.

  • 입력: 대상 식별자와 선택적 매개변수입니다.
  • 동작:
    • 컨테이너가 아닌 리소스의 경우, 서버는 리소스 콘텐츠를 반환합니다.
    • 다음의 경우, 컨테이너, 서버는 멤버 리소스의 목록을 반환하며, 리소스는 선택적으로 다음을 기준으로 필터링할 수 있습니다: 인가. 목록에는 각 멤버의 핵심 메타데이터를 포함해야 합니다.
  • 결과: 요청된 표현 또는 실패 알림입니다.

리소스 읽기 작업은 HTTP GET 요청으로 리소스 표현을 요청합니다(헤더만 요청하려면 HEAD를 사용합니다). 동작은 대상 URL이 다음인지에 따라 다릅니다: 컨테이너 또는 컨테이너가 아닌 리소스(데이터 리소스). 서버는 반드시 메타데이터를 통해 리소스 유형을 구분해야 합니다. 모든 응답은 반드시 8.1절에 정의된 메타데이터와 통합되어야 하며, 다음과 같은 주요 관계의 Link 헤더를 포함합니다: rel="linkset", rel="up" 및 rel="type". 서버는 반드시 읽기 중에 리소스 상태와 메타데이터 간의 원자성을 보장해야 합니다.

GET(컨테이너가 아닌 리소스) – 리소스 콘텐츠 조회: 전체 콘텐츠를 얻으려면 리소스 URI에 GET을 보냅니다(인가된 경우). 200 OK로 응답하며, 본문에는 데이터를 포함하고 Content-Type은 저장된 미디어 유형과 일치해야 합니다. 서버는 반드시 다음에 따른 범위 요청을 지원해야 하며, [RFC7233], 부분 조회를 지원합니다. 응답은 반드시 다음에 정의된 ETag 헤더를 포함해야 합니다: [RFC9110].

예시(GET으로 파일 조회):

GET /alice/notes/shoppinglist.txt HTTP/1.1
Authorization: Bearer <token>
Accept: text/plain

이 요청은 /alice/notes/shoppinglist.txt의 콘텐츠를 요청하며, 클라이언트가 텍스트 형식을 원함을 나타냅니다. 리소스가 존재하고 텍스트이며 클라이언트에게 접근 권한이 있다고 가정합니다:

HTTP/1.1 200 OK
Content-Type: text/plain; charset=UTF-8
Content-Length: 34
ETag: "abc123456"
Link: </alice/notes/shoppinglist.txt.meta>; rel="linkset"; type="application/linkset+json"
Link: </alice/notes/>; rel="up"
Link: <https://www.w3.org/ns/lws#DataResource>; rel="type"

우유
치즈
빵
과카몰레
탄산음료
초콜릿 바
해시
달걀

서버는 텍스트 콘텐츠를 반환했습니다(Content-Length에 표시된 대로 총 34바이트). 콘텐츠는 파일에 저장된 데이터와 정확히 같습니다. ETag: "abc123456"은 검증자로, 캐싱과 조건부 요청에 사용됩니다. 응답은 메타데이터 발견을 위한 Link 헤더를 포함하며, up 및 type과 같은 필수 필드를 포함합니다.

GET(컨테이너 리소스) – 목록 조회: 컨테이너의 내용: 대상 URI가 다음에 해당하면, 컨테이너(메타데이터 유형으로 결정), GET 요청은 다음의 목록을 반환합니다: 컨테이너의 멤버. 다음을 포함하는 응답은 Content-Type: application/lws+json, 컨테이너 표현이며, 다음에 정의되어 있습니다: 컨테이너 표현 절. 이 표현의 목록에는 각 멤버의 메타데이터가 포함됩니다: 리소스 식별자(필수), 유형(필수), 미디어 유형 (DataResources의 경우 필수), 크기(권장) 및 수정 타임스탬프(권장).

예시(GET으로 컨테이너 조회): 다음이 존재하고, 컨테이너, 클라이언트에게 접근 권한이 있다고 가정합니다. 탭은 동일한 요청을 서로 다른 미디어 유형으로 보여줍니다. 다음을 참조하세요: 12.1.2 콘텐츠 협상.

요청:

GET /alice/notes/ HTTP/1.1
Authorization: Bearer <token>
Accept: application/lws+json

응답 헤더:

HTTP/1.1 200 OK
Content-Type: application/lws+json
ETag: "container-etag-789"
Link: </alice/notes/.meta>; rel="linkset"; type="application/linkset+json"
Link: </alice/>; rel="up"
Link: <https://www.w3.org/ns/lws#Container>; rel="type"

응답 본문:

{
  "@context": "https://www.w3.org/ns/lws/v1",
  "id": "/alice/notes/",
  "type": "Container",
  "totalItems": 2,
  "items": [
    {
      "type": "DataResource",
      "id": "/alice/notes/shoppinglist.txt",
      "format": "text/plain",
      "size": 47,
      "modified": "2025-11-24T12:00:00Z"
    },
    {
      "type": ["DataResource", "http://example.org/customType"],
      "id": "/alice/notes/todo.json",
      "format": "application/json",
      "size": 2048,
      "modified": "2025-11-24T13:00:00Z"
    }
  ]
}

요청:

GET /alice/notes/ HTTP/1.1
Authorization: Bearer <token>
Accept: text/turtle; profile="https://www.w3.org/ns/lws/v1"

응답 헤더:

HTTP/1.1 200 OK
Content-Type: text/turtle; profile="https://www.w3.org/ns/lws/v1"
ETag: "container-etag-789"
Link: </alice/notes/.meta>; rel="linkset"; type="application/linkset+json"
Link: </alice/>; rel="up"
Link: <https://www.w3.org/ns/lws#Container>; rel="type"

응답 본문:

@prefix lws: <https://www.w3.org/ns/lws#> .
@prefix dcterms: <http://purl.org/dc/terms/> .
@prefix schema: <http://schema.org/> .
@prefix xsd: <http://www.w3.org/2001/XMLSchema#> .

<> a lws:Container ;
  lws:totalItems 2 ;
  lws:items <shoppinglist.txt>, <todo.json> .

<shoppinglist.txt> a lws:DataResource ;
  dcterms:format "text/plain" ;
  schema:size "47"^^xsd:long ;
  dcterms:modified "2025-11-24T12:00:00Z"^^xsd:dateTime .

<todo.json> a lws:DataResource, <http://example.org/customType> ;
  dcterms:format "application/json" ;
  schema:size "2048"^^xsd:long ;
  dcterms:modified "2025-11-24T13:00:00Z"^^xsd:dateTime .

이 예시에서 /alice/notes/는 컨테이너입니다. 응답은 JSON-LD와 LWS 맥락을 사용하여 필수 메타데이터와 함께 멤버를 나열합니다. 각 항목에는 type, id, format, size 및 modified 타임스탬프가 평면 속성으로 포함됩니다.

모든 경우에 서버는 반드시 다음 메타데이터를 응답 헤더에 포함해야 합니다: 다음에 정의된 ETag 헤더, [RFC9110], 그리고 Link 헤더, rel="linkset", rel="up" 및 rel="type"이 있으며, 다음임을 나타냅니다: 컨테이너.

HEAD(모든 리소스 또는 컨테이너) – 헤더/메타데이터만: LWS 서버는 반드시 HEAD를 지원해야 합니다 [RFC9110]. 다음 모두에 적용됩니다: 컨테이너 및 컨테이너가 아닌 리소스. GET과 동일한 헤더를 반환하며, (Content-Type, 메타데이터용 Link 포함) 본문은 반환하지 않습니다. 이를 통해 콘텐츠를 전송하지 않고 메타데이터를 조회할 수 있습니다.

캐싱 및 조건부 요청: LWS는 HTTP 캐싱 의미론을 활용합니다. 서버는 가급적 다음에 정의된 조건부 요청을 지원하는 것이 좋습니다: [RFC9110], 엔터티 태그(ETags) 및 날짜 기반 검증자와 같은 메커니즘을 포함합니다(예: If-Modified-Since 헤더). 리소스 또는 컨테이너 목록이 변경되지 않았다면 304 Not Modified로 응답하여 불필요한 전송을 피합니다.

발견 가능성 및 인가: 발견 가능성을 높이기 위해, 401 Unauthorized 응답에는 WWW-Authenticate 헤더와 resource_metadata 매개변수가 포함되며, 이는 다음에 설명되어 있습니다: 인가 서버 발견. 이를 통해 클라이언트는 하드코딩된 URI 없이 인가 서버를 찾을 수 있습니다.

9.4 리소스 갱신

전체 교체 또는 부분 패치를 통해 기존 [제공 리소스]의 상태를 수정합니다.

  • 입력: 대상 식별자, 새 콘텐츠 및 선택적 동시성 제약 조건입니다.
  • 동작: 서버는 변경 사항을 원자적으로 적용합니다. 동시성 제약 조건이 제공되면, 요청자가 마지막으로 읽은 이후 리소스가 수정된 경우 갱신이 거부됩니다.
  • 결과: 갱신 확인 또는 충돌 알림입니다.

리소스 갱신은 기존의 다음 콘텐츠를 수정합니다: 제공 리소스. PUT 요청(전체 리소스 교체) 또는 PATCH 요청( 부분 수정 적용)을 사용합니다. 클라이언트는 이러한 작업을 수행하려면 리소스 URL에 대한 쓰기 접근 권한을 가져야 합니다. 참고: 이 절은 리소스의 주요 콘텐츠 갱신을 설명합니다. 메타데이터를 갱신하려면 다음 절을 참조하세요: 9.3.2. LWS 서버는 반드시 리소스 URI에 대한 PUT 및 PATCH 요청을 리소스 콘텐츠만 수정하는 것으로 처리해야 하며, 기본적으로 연결된 다음에는 영향을 주지 않습니다: 링크 집합 리소스. 선택적으로 콘텐츠와 메타데이터를 하나의 원자적 작업으로 모두 갱신하려면, 클라이언트는 Link를 선택적으로 리소스 URI에 대한 PUT/PATCH 요청의 헤더에 포함하고 선호 사항을 지정할 수 있습니다: 'Prefer: set-linkset'(다음에 정의되어 있습니다: [RFC7240]). 이 경우 서버는 반드시 제공된 Link 헤더를 교체로 해석하거나, (PUT의 경우) 링크 집합에 대한 부분 갱신으로 해석해야 하며(PATCH의 경우), 콘텐츠 변경도 함께 적용합니다. 이 동작은 서버에 선택 사항이지만, 지원한다면 반드시 Prefer 헤더를 통해 명시적으로 호출해야 하며, 의도하지 않은 메타데이터 덮어쓰기를 방지하기 위한 것입니다. 결합 갱신을 지원하지 않는 서버는 반드시 해당 선호 사항을 무시하거나 501 Not Implemented로 응답해야 합니다.

PUT(전체 리소스 교체) – 리소스 URI에 PUT을 보내며, 새로운 전체 콘텐츠를 본문에 포함하고 일치하는 Content-Type을 사용합니다(일반적으로 기존 유형과 일치). PUT은 기존 리소스에 대해 멱등적입니다. 클라이언트는 가급적 다음에 정의된 조건부 요청을 사용하는 것이 좋습니다: [RFC9110], 동시에 발생한 변경 사항을 덮어쓰지 않기 위한 것입니다.

예시(PUT으로 리소스 갱신):

PUT /alice/personalinfo.json HTTP/1.1
Authorization: Bearer <token>
Content-Type: application/json
If-Match: "abc123456"
{
"name": "Alice",
"age": 30,
"city": "New London",
"state": "Connecticut"
}

이 예시에서 클라이언트는 다음 위치의 기존 JSON 리소스를 갱신합니다: /alice/personalinfo.json. 엔터티 태그가 있는 If-Match 헤더를 포함하며, (ETag) 이전 GET 또는 HEAD 요청에서 받은 태그입니다. 서버는 이 태그를 현재 엔터티 태그(ETag)와 비교합니다. 일치하면 콘텐츠를 제공된 JSON으로 교체합니다. 일치하지 않으면 서버는 갱신을 거부합니다(그동안 다른 사람이 리소스를 변경했기 때문입니다). 성공 응답: 갱신이 성공하면 서버는 200 OK로 응답하고 갱신된 표현 또는 확인 정보(새 콘텐츠나 그 일부 등)를 포함할 수 있습니다. 또는 서버는 204 No Content로 응답하여 본문 없이 성공을 나타낼 수 있습니다. (추가 정보를 전달할 필요가 없을 때 특히 일반적입니다). 예를 들면 다음과 같습니다: 

HTTP/1.1 204 No Content
  • 오류 응답: If-Match 사전 조건이 일치하지 않으면 (동시 수정), 서버는 412 Precondition Failed로 응답합니다. 리소스가 존재하지 않으면 갱신 목적의 PUT은 404 Not Found를 발생시킵니다. 클라이언트가 인가되지 않았으면 403 Forbidden(유효한 자격 증명이 제공되지 않았으면 401 Unauthorized)입니다. 요청 페이로드가 유효하지 않으면 400 Bad Request입니다.

PATCH(부분 갱신) – HTTP PATCH 메서드는 [RFC5789] 클라이언트가 새로운 전체 콘텐츠를 보내는 대신 리소스의 부분 수정을 지정할 수 있도록 합니다. 큰 리소스에서 작은 부분만 변경되어 전체 콘텐츠를 보내는 것이 비효율적인 경우나 특정 변경 사항을 적용하려는 동시 편집에 유용합니다. LWS 서버는 반드시 최소한 JSON Patch를 지원해야 합니다. (application/json-patch+json) 다음에 정의되어 있습니다: [RFC6902].

리소스 메타데이터 갱신(링크 집합에 대한 HTTP PUT / PATCH) 리소스의 메타데이터는 해당하는 다음을 수정하여 갱신합니다: 링크 집합 리소스, rel="linkset"이 있는 Link 헤더를 통해 발견합니다. 전체 교체(PUT): 다음에 PUT 요청을 보내며, 링크 집합 리소스 URI, 완전한 링크 집합 문서를 본문에 포함하여 리소스의 모든 메타데이터를 교체합니다. 부분 갱신(PATCH): 다음에 PATCH 요청을 보내며, 링크 집합 리소스 URI, 특정 링크를 추가하거나 제거하거나 수정합니다.

메타데이터에 대한 조건부 요청 여러 주체가 리소스의 메타데이터를 수정할 수 있으므로, 동시에 발생하는 덮어쓰기를 방지하는 것이 중요합니다. 서버와 클라이언트는 가급적 다음에 정의된 조건부 요청을 사용하는 것이 좋습니다: [RFC9110], 다음에 대한 PUT 및 PATCH 작업에 사용합니다: 링크 집합 리소스. 서버가 사전 조건을 충족하지 않는 조건부 요청을 받으면, 반드시 다음으로 요청을 거부해야 합니다: 412 Precondition Failed 상태 코드. 예시(PUT으로 링크 집합 교체): 클라이언트가 먼저 링크 집합을 가져옵니다. 

GET /alice/personalinfo.json.meta HTTP/1.1
Authorization: Bearer <token>
Accept: application/linkset+json
HTTP/1.1 200 OK
Content-Type: application/linkset+json
{
  "linkset": [
    {
      "anchor": "/alice/personalinfo.json",
      "describedby": [ { "href": "/schemas/personal-info.json" } ]
    }
  ]
}

클라이언트는 이제 라이선스를 추가하려고 합니다. 새롭고 완전한 링크 집합 문서를 구성하여 PUT 요청을 보냅니다.

PUT /alice/personalinfo.json.meta HTTP/1.1
Authorization: Bearer <token>
Content-Type: application/linkset+json
{
  "linkset": [
    {
      "anchor": "/alice/personalinfo.json",
      "describedby": [ { "href": "/schemas/personal-info.json" } ],
      "license": [ { "href": "https://creativecommons.org/licenses/by/4.0/" } ]
    }
  ]
}

성공하면 서버는 성공 응답을 보냅니다.

HTTP/1.1 204 No Content

갱신 규칙 요약 리소스의 콘텐츠만 변경하려면 → 리소스 자체에 PUT/PATCH를 보냅니다. 리소스의 링크(메타데이터)만 변경하려면 → 리소스에 연결된 다음에 PUT/PATCH를 보냅니다: 링크 집합 리소스. 콘텐츠와 링크를 모두 변경하려면 → 리소스 자체에 PUT/PATCH를 보내며, 적절한 Link 헤더와 'Prefer: set-linkset'을 모두 포함합니다. 둘 다 설정하는 동작은 기본적으로 비활성화되어 있습니다.

9.5 리소스 삭제

리소스와 연결된 메타데이터를 영구적으로 제거합니다.

  • 입력: 대상 식별자, 선택적 재귀 플래그(다음에 적용: 컨테이너) 및 선택적 동시성 제약 조건입니다.
  • 동작:
    • 컨테이너가 아닌 리소스의 경우, 서버는 콘텐츠와 메타데이터를 제거하고 부모의 컨테이너 멤버십을 갱신합니다.
    • 다음의 경우, 컨테이너, 서버는 일반적으로 다음이 컨테이너 비어 있어야 한다고 요구합니다. 단, 재귀적 삭제가 명시적으로 요청되고 지원되는 경우는 예외입니다.
  • 결과: 제거 확인 또는 실패 알림입니다.

리소스 삭제 작업은 위의 추상 작업에 정의된 대로 HTTP DELETE 메서드를 사용하여 구현합니다. 이 절은 입력, 동작 및 응답의 HTTP 바인딩을 명시합니다.

DELETE 요청은 제거할 리소스 또는 다음의 URI를 대상으로 합니다: 컨테이너. 클라이언트는 선택적으로 ETag가 있는 If-Match 헤더를 포함하여 동시성 검사를 수행할 수 있습니다.

삭제 및 포함 관계: 리소스가 삭제되면 서버는 반드시 해당 리소스를 원자적으로 제거해야 합니다. 부모 컨테이너의 items 목록에서 제거합니다. 부모 컨테이너의 totalItems 개수는 가급적 그에 맞게 갱신하는 것이 좋습니다.

컨테이너가 아닌 리소스의 경우, 서버는 리소스 콘텐츠와 연결된 메타데이터(링크 집합 리소스) 및 포함 관계 참조를 부모에서 제거합니다: 컨테이너.

다음의 경우, 컨테이너 리소스, 서버는 기본적으로 비재귀적 삭제를 수행합니다. 다음이 컨테이너 비어 있지 않고 재귀가 요청되지 않았다면 서버는 반드시 409 Conflict로 요청을 거부해야 합니다. 서버는 선택적으로 다음 내부의 모든 리소스에 대한 재귀적 삭제를 지원할 수 있습니다: 컨테이너, 삭제 대상 컨테이너입니다. 클라이언트는 반드시 Depth: infinity 헤더를 사용하여 재귀적 삭제를 요청해야 하며, 이는 다음에 정의되어 있습니다: [RFC4918].

성공하면 서버는 반드시 204 No Content로 응답해야 합니다. 서버는 가급적 다음에 정의된 조건부 요청을 지원하는 것이 좋습니다: [RFC9110].

클라이언트에게 인가가 없으면 서버는 반드시 403 Forbidden을 반환해야 합니다( 클라이언트의 신원은 알려져 있지만 권한이 부족한 경우). 또는 401 Unauthorized를 반환해야 합니다(유효한 인증이 제공되지 않은 경우). 리소스의 존재를 공개하는 것이 보안 위험을 초래하면, 서버는 선택적으로 대신 404 Not Found를 반환할 수 있습니다.

예시(DELETE로 컨테이너가 아닌 리소스 삭제):

DELETE /alice/notes/shoppinglist.txt HTTP/1.1
Authorization: Bearer <token>
If-Match: "abc123456"

ETag가 일치하고 클라이언트가 인가되었다고 가정하면, 서버는 리소스와 메타데이터를 삭제하고, 부모 컨테이너 /alice/notes/에서 이를 원자적으로 제거합니다:

HTTP/1.1 204 No Content

예시(재귀 없이 DELETE로 비어 있지 않은 컨테이너 삭제):

DELETE /alice/notes/ HTTP/1.1
Authorization: Bearer <token>

/alice/notes/에 리소스가 포함되어 있다고 가정하면, 서버는 삭제를 거부합니다:

HTTP/1.1 409 Conflict
Content-Type: text/plain

삭제할 수 없습니다: 컨테이너 /alice/notes/ - 컨테이너가 비어 있지 않습니다.

예시(지원되는 경우, 재귀를 사용하여 DELETE로 컨테이너 삭제):

DELETE /alice/notes/ HTTP/1.1
Authorization: Bearer <token>
Depth: infinity

서버가 재귀를 지원하고 클라이언트에게 모든 콘텐츠에 대한 권한이 있다고 가정하면, 서버는 컨테이너와 하위 항목을 원자적으로 삭제합니다:

HTTP/1.1 204 No Content

9.6 리소스 이동 (컨테이너 간)

이 명세는 다음을 이동하기 위한 전용 HTTP 메서드를 정의하지 않습니다: 제공 리소스, 한 컨테이너에서 다른 컨테이너로 이동하는 것으로, MOVE 메서드와 다릅니다. WebDAV가 정의하는 메서드입니다 [RFC4918]. 대신 이동은 다음의 갱신으로 표현합니다: 포함 관계 메타데이터, 해당 리소스의 메타데이터입니다. 클라이언트는 리소스의 다음에서 up 링크를 변경합니다: 링크 집합 리소스, 목적지를 가리키도록 변경하며, 목적지는 컨테이너입니다. 다음을 사용합니다: 갱신 리소스 작업. 서버는 해당 변경으로부터 실제 이동을 도출합니다.

이동은 다음의 연속으로 단순화할 수 없습니다: 리소스 생성 작업 이후 리소스 삭제 작업. 서버가 리소스 식별자를 할당하므로, 클라이언트가 다른 다음에 콘텐츠를 다시 생성해도, 컨테이너, 반드시 보존할 수 있는 것은 아닙니다. 원래 리소스의 식별자를 보존할 수 없을 수 있으며, 해당 식별자를 가리키는 모든 링크가 끊어질 수 있습니다. 두 요청은 원자적이지도 않습니다. 관찰자는 리소스를 두 대상 모두에서 볼 수 있습니다: 컨테이너, 또는 어느 쪽에서도 보지 못할 수 있습니다. 이동을 다음의 변경으로 표현하면, 해당 포함 관계 메타데이터, 두 문제를 모두 피할 수 있습니다. 이 변경은 리소스의 식별 정보와 콘텐츠에 영향을 주지 않기 때문입니다.

서버 지원: up 링크는 서버가 관리하며, 서버는 클라이언트가 이를 수정하도록 허용할 의무가 없습니다. 이는 다음에 설명되어 있습니다: 9.1 리소스 메타데이터. 클라이언트가 리소스의 up 링크를 수정하도록 허용하여, 그에 따라 다음 간 리소스 이동을 허용하는 서버는, 컨테이너, 반드시 다음을 설명해야 합니다: MoveResource 기능, 다음에 설명합니다: 저장소 설명. 이는 다음에 설명되어 있으며, 6.1.3 저장소 기능, 또한 반드시 이 절의 요구 사항을 구현해야 합니다. 허용하지 않는 서버는 반드시 409 Conflict와 같은 적절한 4xx 상태 코드로 요청을 거부해야 하며, 절대로 안 됩니다, MoveResource 기능을 설명해서는 안 됩니다.

이동 요청: 클라이언트는 리소스의 다음에 부분 갱신을 적용하여 리소스를 이동합니다: 링크 집합 리소스, up 링크의 대상을 목적지의 식별자로 교체하며, 목적지는 컨테이너입니다. 다음에서 요구하는 대로, 9.1 리소스 메타데이터, 서버는 반드시 application/json-patch+json을 지원해야 합니다 [RFC6902]. 이 갱신에 대한 지원입니다. 다음의 모든 수정과 마찬가지로, 링크 집합 리소스, 클라이언트는 가급적 현재 ETag를 담은 If-Match 헤더 필드를 포함하여 요청을 조건부로 만드는 것이 좋습니다. 해당 ETag의 대상은 링크 집합 리소스이며, 이는 다음에 설명되어 있습니다: 9.4 리소스 갱신. 서버는 선택적으로 조건부 요청을 요구하고 무조건부 요청을 428 Precondition Required로 거부할 수 있습니다.

목적지는 반드시 기존의 컨테이너여야 합니다. 서버는 반드시 up 링크의 대상을 다음 이외의 것으로 설정하려는 패치를 거부해야 합니다: 기존의 컨테이너. 409 Conflict와 같은 적절한 4xx 상태 코드로 거부합니다. 서버는 마찬가지로 반드시 리소스에 up 링크가 남지 않게 하는 패치를 거부해야 합니다. 모든 루트가 아닌 리소스에는 다음에서 도달할 수 있어야 하기 때문입니다: 저장소 루트.

이 명세는 목적지를 다음으로 제한하지 않습니다: 저장소, 이동할 리소스를 보유한 저장소입니다. 그러나 서버는 리소스를 다음으로 이동하는 것을 지원할 의무가 없습니다: 컨테이너, 다른 저장소에 있는 컨테이너이며, 선택적으로 이러한 패치를 적절한 4xx 상태 코드로 거부할 수 있습니다. 예를 들면 409 Conflict입니다. 이러한 패치를 수락하는 서버에는 이 절의 다른 요구 사항도 계속 적용되며, 변경을 원자적으로 적용해야 한다는 요구 사항도 포함됩니다.

참고
JSON Patch는 JSON Pointer로 변경할 값을 식별하며 [RFC6901], 여기서 배열의 멤버는 위치로 지정합니다. 따라서 up 링크의 대상을 교체하는 패치는 linkset 배열에서 리소스의 링크 맥락이 차지하는 위치와 up 배열에서 대상 객체가 차지하는 위치에 의존합니다. 클라이언트는 이러한 위치를 다음을 읽어 파악하며, 링크 집합 리소스, 조건부 요청은 패치를 적용할 때도 해당 위치가 유효하도록 보장합니다. 클라이언트는 추가로 변경을 보호할 수 있으며, test 작업을 사용합니다. 예를 들어 링크 맥락의 anchor 또는 up 링크의 현재 대상을 검사합니다. 다음의 전체 교체와 달리, 링크 집합 리소스, 이러한 패치는 다른 모든 링크를 그대로 유지하므로, 클라이언트가 변경하지 않는 링크를 다시 명시할 필요가 없습니다.

다음에 미치는 영향: 포함 관계: 갱신에 성공하면 서버는 반드시 해당 리소스를 원자적으로 제거해야 합니다. items 목록에서 제거하며, 이전 부모의 목록입니다: 컨테이너. 그리고 다음에 추가해야 합니다: items 목록, 목적지의 목록입니다: 컨테이너. totalItems 개수는 두 대상 모두에서, 컨테이너, 가급적 그에 맞게 갱신하는 것이 좋으며, 두 대상의 ETag는 컨테이너, 반드시 갱신하여 변경을 반영해야 합니다.

이동한 리소스의 콘텐츠와 사용자 정의 메타데이터는 이동의 영향을 받지 않습니다. 서버는 반드시 다음의 링크를 보존해야 합니다: 링크 집합 리소스, 클라이언트가 수정할 권한이 없는 링크이며, linkset과 같은 서버 관리 링크 및 type을 포함합니다. 보조 리소스의 수명이 이동한 리소스에 종속되어 있다면, 이동 후에도 계속 해당 리소스에 종속됩니다.

서버는 반드시 다음의 무결성을 위반하는 갱신을 거부해야 합니다: 포함 관계, 해당 무결성의 요구 사항은 다음에 있습니다: 7. 논리적 리소스 구성. 409 Conflict와 같은 적절한 4xx 상태 코드로 거부합니다. 특히 컨테이너는 절대로 자기 자신 내부로 이동하거나 자신의 하위 항목 내부로 이동해서는 안 됩니다. 다음에 순환이 생기기 때문입니다: 포함 관계 계층.

이동한 리소스의 식별 정보: 리소스의 URI는 다음에서의 위치와 독립적이며, 포함 관계 계층, 이는 다음에 설명되어 있습니다: 7. 논리적 리소스 구성. 따라서 서버는 가급적 보존하는 것이 좋습니다. 이동한 리소스의 식별자를 보존하여 기존 링크가 계속 유효하도록 하며, 가급적 그 여부를 preservesIdentifier로 선언하는 것이 좋습니다. MoveResource 기능의 속성입니다. 해당 속성이 없으면 클라이언트는 절대로 식별자가 보존된다고 가정해서는 안 됩니다.

이동한 리소스의 식별자를 보존하지 않는 서버는 반드시 응답해야 합니다. 200 OK와 함께 갱신된 다음의 표현을 반환합니다: 링크 집합 리소스, 그 anchor는 리소스의 새 식별자여야 하며, 반드시 다음을 포함해야 합니다: Content-Location 헤더 필드, 다음의 새 식별자를 담는 필드입니다: 링크 집합 리소스 자체. 이러한 서버는 가급적 이전 식별자에 대한 후속 요청에 응답하는 것이 좋습니다. 리소스 및 해당 보조 리소스의 이전 식별자에 대해 301 Moved Permanently로 응답하며, 새 식별자를 가리키는 Location 헤더 필드를 포함합니다.

이동: 컨테이너: 서버는 선택적으로 다음의 up 링크 변경을 지원할 수 있습니다: 컨테이너. 또한 반드시 지원 여부를 나타내야 하며, Container를 다음의 appliesTo 속성에 포함합니다: MoveResource 기능. 다음이 이동하면, 컨테이너, 하위 항목도 함께 이동하며, 하위 항목의 식별자에는 이동한 다음의 식별자와 동일한 요구 사항이 적용됩니다: 컨테이너. 다음의 이동은 지원하지만, 데이터 리소스, 다음의 이동은 지원하지 않는 서버는, 컨테이너, 반드시 409 Conflict와 같은 적절한 4xx 상태 코드로 해당 요청을 거부해야 하며, 절대로 Container를 appliesTo 속성에 포함해서는 안 됩니다.

인가: 서버는 절대로 up 링크에 변경을 적용해서는 안 됩니다. 단, 요청하는 에이전트가 다음 두 작업을 모두 수행하도록 인가된 경우는 예외입니다: 리소스 삭제 작업을 이동할 리소스에 수행하는 것과, 리소스 생성 작업을 목적지에서 수행하는 것입니다: 컨테이너.

다음이 이동하면, 컨테이너, 해당 컨테이너만이 부모가 변경되는 리소스입니다. 하위 항목은 서로에 대한 상대적 위치를 유지하며, 서버가 식별자를 보존하는 경우 식별자도 유지합니다. 따라서 에이전트는 목적지에서 각 하위 항목을 다시 생성하도록 인가받을 필요가 없습니다. 그러나 해당 하위 항목에 적용되는 정책은 변경될 수 있습니다. 접근은 흔히 다음 내의 위치를 기준으로 제어되기 때문입니다: 포함 관계 계층. 이러한 이유로, 다음을 이동하는 데 필요한 인가는 컨테이너, 해당 대상을 삭제하는 데 필요한 인가입니다. 재귀적으로 삭제하는 경우이며, 이는 다음에 설명되어 있습니다: 9.5 리소스 삭제. 여기에 목적지에서 생성하는 데 필요한 인가도 있어야 합니다: 컨테이너. 서버는 반드시 해당 인가를 전체 하위 트리에 대해 평가한 후 변경을 적용해야 하며, 절대로 변경을 부분적으로 적용해서는 안 됩니다.

참고

  "detail": "/alice/notes/2026/은 /alice/notes/의 하위 항목입니다"
}

알림: 리소스 이동 지원을 알리고 알림을 내보내는 서버는 가급적 성공한 이동을 하나의 Move 활동으로 설명하는 것이 좋습니다. 이는 다음에 설명되어 있으며, 10.2.3 활동 유형, 별도의 Delete 및 Create 활동 대신 사용합니다.

9.7 HTTP 상태 매핑 요약

이 표는 일반적인 LWS 응답(출처: 8절)을 HTTP 상태 코드와 페이로드에 매핑하여 일관성을 유지하며, 다음과 같은 구체적인 상황을 반영합니다: 페이지 나누기, 조건부 요청, 할당량 제약 및 메타데이터 통합:

LWS 응답 HTTP 상태 코드 HTTP 페이로드
성공(읽기 또는 갱신, 반환 내용: 데이터) 200 OK 리소스 표현이 응답 본문에 포함됩니다(GET 또는 PUT/PATCH가 콘텐츠를 반환하는 경우). 관련 헤더도 포함합니다(Content-Type, 다음과 같은 메타데이터용 Link: rel="linkset" 또는 rel="up"). 컨테이너 목록에는 규범적 맥락과 멤버 메타데이터(ID, 유형, 크기, 타임스탬프 등)가 있는 JSON-LD를 포함합니다.
생성됨(새 리소스) 201 Created 일반적으로 응답 본문이 없습니다(또는 새 리소스의 최소 표현이 있습니다). Location 헤더는 새 리소스의 URI로 설정됩니다. Link 헤더는 서버 관리 메타데이터에 사용됩니다.
삭제됨(반환할 콘텐츠 없음) 204 No Content 응답 본문이 없습니다. 리소스가 삭제되었거나 요청이 성공했으며 추가로 전달할 내용이 없음을 나타냅니다. 서버는 선택적으로 410 Gone을 영구 삭제에 사용할 수 있습니다.
잘못된 요청(유효하지 않은 입력 또는 제약 조건) 400 Bad Request 무엇이 잘못되었는지 설명하는 오류 세부 정보입니다. 서버는 가급적 다음에 정의된 표준 형식을 사용하는 것이 좋습니다: [RFC9457], 구조화된 오류 응답에 사용합니다. 예를 들어 "type", "title", "status", "detail" 및 "instance"와 같은 필드가 있는 JSON 객체입니다.
알 수 없는 요청자 401 Unauthorized 선택적 오류 세부 정보. 예를 들어 [RFC9457]에서 정의한 형식을 사용할 수 있다. WWW-Authenticate 헤더는 클라이언트가 인증할 수 있는 방법을 나타낸다.
허용되지 않음 403 Forbidden 선택적 오류 세부 정보. 예를 들어 [RFC9457]에서 정의한 형식을 사용할 수 있다.
대상을 찾을 수 없음 404 Not Found 선택적 오류 세부 정보. 예를 들어 [RFC9457]에서 정의한 형식을 사용할 수 있다.

리소스에 접근할 권한이 없는 클라이언트에게 리소스 존재 여부를 공개하고 싶지 않은 서버는 [RFC9110]에 설명된 대로 403 Forbidden 대신 404 Not Found로 응답할 수 있다.

10. 알림

이 절은 클라이언트가 변경 사항을 제때 전달받는 메커니즘을 정의하며, Linked Web Storage 서버가 관리하는 리소스의 변경 사항을 다룹니다. 이 명세는 공통 알림 데이터 모델과 구독 메커니즘을 정의합니다. 구체적인 전달 채널은 별도의 알림 스위트 명세에 설명되어 있습니다.

10.1 알림 발견

저장소는 알림을 선택적으로 지원할 수 있습니다. 알림을 지원하는 저장소는 반드시 자신의 다음 리소스의 service 배열에 서비스 객체를 명시해야 합니다: 저장소 설명 리소스. 해당 객체의 type은 NotificationService여야 합니다.

서비스 객체는 반드시 serviceEndpoint 속성을 포함해야 하며, 그 값은 구독 엔드포인트의 URI입니다. 서비스 객체는 또한 반드시 다음을 포함해야 합니다: subscriptionType 속성. 그 값은 문자열 배열이며, 각 문자열은 지원되는 구독 유형을 식별합니다.

서비스 객체에 추가 속성이 선택적으로 존재할 수 있습니다.

예시 12: 알림 기능이 포함된 저장소 설명, 해당 서비스 
{
  "@context": ["https://www.w3.org/ns/lws/v1"],
  "id": "https://storage.example/",
  "type": "Storage",
  "service": [{
    "type": "NotificationService",
    "serviceEndpoint": "https://notification.example/subscriptions",
    "subscriptionType": [
      "WebhookSubscription"
    ]
  }]
}
참고

서버는 모든 구독 유형을 지원할 의무가 없습니다. subscriptionType 배열은 이용할 수 있는 유형을 정확하게 나타냅니다.

10.2 알림 데이터 모델

알림은 JSON-LD 문서로 표현되며, Notification 유형을 가집니다. 봉투에는 전달 맥락에 관한 메타데이터가 담기며, 활동 스트림 2.0 [ACTIVITYSTREAMS-CORE] [ACTIVITYSTREAMS-VOCABULARY] 활동을 감싸며, 이 활동이 이벤트를 설명합니다.

10.2.1 봉투 속성

알림 봉투에는 다음 속성이 있습니다:

  • type — 필수입니다. 값은 반드시 다음 문자열이어야 합니다: Notification.
  • storage — 필수입니다. LWS 저장소를 식별하는 URI이며, 알림이 연결된 저장소입니다.
  • activity — 필수입니다. JSON 객체 또는 JSON 객체의 배열이며, 각 객체는 활동 스트림 2.0 데이터 모델을 준수하고, 발생한 이벤트 또는 이벤트들을 설명합니다. 다음을 참조하세요: 10.2.2 활동 속성.
예시 13: 알림 봉투 
{
  "@context": [
    "https://www.w3.org/ns/lws/v1",
    "https://www.w3.org/ns/activitystreams"
  ],
  "type": "Notification",
  "storage": "https://storage.example/",
  "activity": {
    "id": "ec4dcc48-6581-4232-81c9-584525a98693",
    "type": ["Delete"],
    "object": {
      "id": "https://storage.example/alice/notes/shopping.txt",
      "type": ["DataResource"]
    },
    "origin": "https://storage.example/alice/notes/",
    "published": "2026-03-26T10:30:00Z"
  }
}

10.2.2 활동 속성

activity 속성 내의 각 활동 객체가 반드시 준수해야 하는 것은 활동 스트림 2.0 데이터 모델입니다. 또한 반드시 다음 속성을 포함해야 합니다:

  • id — 필수입니다. 활동을 고유하게 식별하는 문자열입니다.
  • type — 필수입니다. 문자열 배열이며, 최소한 하나의 활동 스트림 2.0 활동 유형을 포함합니다.
  • object — 필수입니다. 리소스를 식별하는 JSON 객체이며, 알림이 다루는 리소스입니다. object가 반드시 포함해야 하는 속성은 다음과 같습니다:
    • id — 필수입니다. 리소스의 URI입니다.
    • type — 필수입니다. 문자열 배열로서, 최소한 하나의 리소스 유형을 포함합니다. 이 명세에 정의된 값으로는 Container 및 DataResource가 있습니다. 추가 유형 값을 선택적으로 포함할 수 있습니다.
  • published — 필수입니다. 다음에 부합하는 날짜·시간 값이며, [RFC3339], 시점을 나타냅니다. 활동이 발생한 시점입니다.

다음 속성은 선택 사항입니다:

  • actor — 행위를 수행한 에이전트를 식별하는 URI입니다.
  • target — 컨테이너를 식별하는 URI이며, 리소스가 추가된 컨테이너입니다. Create 및 Move 활동에 사용합니다.
  • origin — 컨테이너를 식별하는 URI이며, 리소스가 제거된 컨테이너입니다. Delete 및 Move 활동에 사용합니다.

10.2.3 활동 유형

서버는 반드시 다음 활동 스트림 2.0 활동 유형을 지원하여 다음의 변경을 나타내야 합니다: 저장소 리소스 변경:

  • Create — 컨테이너에 새 리소스가 생성되었습니다. target 필드는 리소스가 추가된 컨테이너를 나타냅니다.
  • Update — 기존 리소스의 콘텐츠 또는 메타데이터가 수정되었습니다.
  • Delete — 리소스가 제거되었습니다. origin 필드는 리소스가 제거된 컨테이너를 나타냅니다.

클라이언트가 컨테이너 간에 리소스를 이동하도록 허용하는 서버는, 다음에 설명된 대로, 9.6 리소스 이동 (컨테이너 간), 반드시 다음 활동 유형을 지원해야 합니다:

  • Move — 리소스가 한 컨테이너에서 다른 컨테이너로 이동되었습니다. origin 필드는 리소스가 제거된 컨테이너를 나타내고, target 필드는 리소스가 추가된 컨테이너를 나타냅니다. object 필드는 이동 후 존재하는 리소스를 설명합니다.

다른 활동 유형도 선택적으로 지원할 수 있습니다.

10.2.4 알림 일괄 처리

서버는 여러 활동을 하나의 알림으로 선택적으로 결합할 수 있으며, 해당 봉투에 활동 객체의 배열을 activity의 값으로 제공하여 수행합니다.

예시 14: 일괄 처리된 알림 
{
  "@context": [
    "https://www.w3.org/ns/lws/v1",
    "https://www.w3.org/ns/activitystreams"
  ],
  "type": "Notification",
  "storage": "https://storage.example/",
  "activity": [
    {
      "id": "a1b2c3d4-5678-9abc-def0-1234567890ab",
      "type": ["Create"],
      "object": {
        "id": "https://storage.example/alice/notes/meeting.txt",
        "type": ["DataResource"]
      },
      "target": "https://storage.example/alice/notes/",
      "published": "2026-03-26T10:30:00Z"
    },
    {
      "id": "b2c3d4e5-6789-abcd-ef01-234567890abc",
      "type": ["Update"],
      "object": {
        "id": "https://storage.example/alice/profile",
        "type": ["DataResource"]
      },
      "published": "2026-03-26T10:30:01Z"
    }
  ]
}

10.3 구독

알림을 받기 위해 구독자는 구독을 생성하며, 요청을 보냅니다. 인증된 POST 요청을 serviceEndpoint로 보내며, 해당 속성은 NotificationService에 속합니다. 요청 본문은 반드시 다음을 준수해야 합니다: application/lws+json 미디어 유형.

10.3.1 구독 요청

구독 요청은 반드시 다음 필드를 포함해야 합니다:

  • type — 필수입니다. 구독을 식별하는 문자열이며, 구독 유형을 식별합니다. 값은 반드시 다음에 나열된 유형 중 하나여야 합니다: subscriptionType, NotificationService의 배열입니다.
  • topic — 필수입니다. URI 배열로서, 리소스를 식별하며, 구독에 포함된 리소스입니다.

구독 요청은 추가 필드를 선택적으로 포함할 수 있으며, 이는 특정 구독 유형에서 요구하는 필드입니다.

예시 15: 구독 요청 
POST /subscriptions HTTP/2
Host: notification.example
Authorization: Bearer <access-token>
Content-Type: application/lws+json

{
  "@context": ["https://www.w3.org/ns/lws/v1"],
  "type": "WebhookSubscription",
  "topic": [
    "https://storage.example/alice/notes/",
    "https://storage.example/alice/profile"
  ],
  "inbox": "https://receiver.example/hooks/lws"
}

10.3.2 구독 범위

구독이 컨테이너에 대한 것이면 재귀적입니다. 구독자는 컨테이너 자체와 추이적으로 포함된 모든 리소스에 대한 알림을 받습니다. 해당 컨테이너에 포함된 리소스입니다. 구독이 데이터 리소스에 대한 것이면 해당 개별 리소스에만 적용됩니다.

10.3.3 구독 인가

서버는 반드시 다음을 생성할 때 리소스 인가를 적용해야 합니다: 구독. 만약 구독자에게 모든 대상에 대한 읽기 접근 권한에 상응하는 권한이 없다면, 해당 리소스는 topic 배열에 나열된 리소스이며, 서버는 반드시 해당 구독 요청을 거부해야 합니다.

알림 전달 시점에도 인가를 반드시 적용해야 합니다. 서버는 절대로 다음과 같은 알림을 전달해서는 안 됩니다. 해당 리소스를 구독자가 이벤트 발생 시점에 읽도록 인가받지 않은 경우입니다. 이는 모든 리소스에 적용됩니다. 다음의 범위 내에 있는 리소스입니다: 구독, 하위 컨테이너의 리소스도 포함됩니다.

만약 구독자의 리소스 또는 컨테이너 접근 권한이 해당 범위인 구독 내에서 철회되며, 이는 다음이 구독 생성된 후에 발생하면, 서버는 반드시 영향을 받는 리소스의 알림 전달을 중단해야 합니다. 서버는 가급적 전체 구독을 종료하지 않는 것이 좋습니다. 단, 다음 대상이 구독자, topic 배열의 모든 리소스에 대한 접근 권한을 잃은 경우는 예외입니다.

참고

구독 시점의 인가는 다음 대상에게 구독자, 정당한 알림 수신 근거가 있는지 검증합니다. 전달 시점의 인가는 알림이 다음 대상의 구독자, 현재 권한과 계속 일치하도록 보장하며, 다음 이후에 발생할 수 있는 인가 변경을 반영합니다: 구독 생성 이후.

10.3.4 구독 응답

성공적인 구독 생성 요청에 대한 응답이 반드시 준수해야 하는 것은 application/lws+json 미디어 유형입니다. 또한 반드시 다음 필드를 포함해야 합니다:

  • type — 필수입니다. 구독 유형과 같은 문자열이며, 해당 유형의 출처는 요청입니다.
  • subscription — 필수입니다. 다음을 나타내는 URL입니다: 구독.

10.3.5 구독 유형 식별자

각 알림 스위트는 반드시 구독 유형 문자열과 연결되어야 합니다. 구독 유형 문자열은 다음의 subscriptionType 배열에 사용됩니다: NotificationService. 또한 구독 요청의 type 필드에도 사용됩니다.

11. 접근 요청 및 권한 부여

접근 요청 및 권한 부여는 다음을 위한 메커니즘을 제공합니다: 에이전트가 접근을 요청하도록 하고, 리소스에 대한 요청입니다. 또한 저장소 제어자가 정의된 제약 조건에 따라 접근 권한을 부여하도록 합니다. 접근 요청 및 권한 부여 엔드포인트는 특수한 수신함의 한 유형으로 기능합니다.

에이전트는 다음을 제시하지 않습니다: 접근 권한 부여, 서버에 인가 토큰으로 제시하지 않습니다. 대신 접근 권한 부여는 무엇을 누구에게 인가했는지, 어떤 제약 조건에 따르는지를 기록합니다. 다음이 접근 권한 부여 생성되거나 철회(삭제)되면, 서버는 관련된 기본 접근 정책을 조정하여 변경을 반영할 책임이 있습니다. 다음 간의 상호작용은 접근 권한 부여 엔드포인트와 특정 정책 적용 계층 간의 상호작용이며, 이 명세의 범위에 포함되지 않습니다.

다음의 접근 프로파일은 이 절에 정의되어 있으며, 다음의 개념에 기반합니다: 해당 명세인 개방형 디지털 권리 언어(ODRL), 여기에는 행위, 제약 조건 및 할당 대상자가 포함됩니다. 다른 프로파일은 다른 개념 체계를 사용할 수 있습니다.

11.1 발견

저장소는 선택적으로 다음에 대한 지원을 알릴 수 있습니다: 접근 요청 및 접근 권한 부여, 자신의 저장소 설명 리소스에서 알립니다. 이러한 지원을 알리는 경우, 서비스 객체는 다음의 엔드포인트를 설명하며, 접근 요청, 반드시 다음을 가져야 합니다: type, 그 값은 문자열 AccessRequestService여야 합니다. 또한 다음의 엔드포인트를 설명하는 서비스 객체는 접근 권한 부여, 반드시 다음을 가져야 합니다: type, 그 값은 문자열 AccessGrantService여야 합니다. 서비스 객체는 가급적 conformsTo 속성을 포함하는 것이 좋으며, 그 값은 컬렉션입니다. 하나 이상의 URI로 구성되며, 다음을 식별합니다: 접근 프로파일, 해당 엔드포인트에서 지원하는 프로파일입니다. 추가 속성을 선택적으로 포함할 수 있습니다:

예시 16: 접근 요청 및 권한 부여가 포함된 저장소 설명, 해당 서비스 
{
  "@context": [
    "https://www.w3.org/ns/cid/v1",
    "https://www.w3.org/ns/lws/v1"
  ],
  "id": "https://storage.example/",
  "type": "Storage",
  "service": [
    {
      "type": "StorageRoot",
      "serviceEndpoint": "https://storage.example/root/"
    },
    {
      "type": "AccessRequestService",
      "serviceEndpoint": "https://access.example/request/",
      "conformsTo": ["https://www.w3.org/ns/lws#AccessProfile"]
    },
    {
      "type": "AccessGrantService",
      "serviceEndpoint": "https://access.example/grant/",
      "conformsTo": ["https://www.w3.org/ns/lws#AccessProfile"]
    }
  ]
}

11.2 데이터 모델

접근 요청 또는 접근 권한 부여는 데이터 객체이며, 속성을 표현합니다. 식별과 라우팅에 대한 속성 및 다음을 설명하는 access 객체를 표현합니다: 요청되거나 허용된 작업. 다음을 설명하는 프로파일은 접근 요청, ODRL 개념을 사용하며 다음에 설명되어 있습니다: 11.3 접근 프로파일.

다음 예시는 접근 요청을 보여줍니다. 이 예시는 다음에 정의된 JSON-LD 직렬화를 사용하여 표시됩니다: 11.4.1 JSON-LD 직렬화.

예시 17: 접근 요청 
{
  "@context": [
    "https://www.w3.org/ns/lws/v1"
  ],
  "type": ["AccessRequest"],
  "inbox": "https://id.example/agent/inbox/",
  "storage": "https://storage.example/",
  "access": [{
    "type": ["AccessPolicy"],
    "action": ["read", "create"],
    "assignee": "https://id.example/agent",
    "target": {
      "type": "StorageResource",
      "value": ["https://storage.example/root/projects/"]
    },
    "constraint": [
      {
        "leftOperand": "purpose",
        "operator": "eq",
        "rightOperand": "https://purpose.example/collaboration"
      },
      {
        "leftOperand": "dateTime",
        "operator": "lteq",
        "rightOperand": "2026-06-09T10:00:00Z"
      }
    ]
  }]
}

다음 예시는 접근 권한 부여를 보여줍니다. 이 예시는 다음에 정의된 JSON-LD 직렬화를 사용하여 표시됩니다: 11.4.1 JSON-LD 직렬화.

예시 18: 접근 권한 부여 
{
  "@context": [
    "https://www.w3.org/ns/lws/v1"
  ],
  "type": ["AccessGrant"],
  "storage": "https://storage.example/",
  "access": [{
    "type": ["AccessPolicy"],
    "action": ["read"],
    "assignee": "https://id.example/agent",
    "target": {
      "type": "StorageResource",
      "value": ["https://storage.example/root/projects/"]
    },
    "constraint": [
      {
        "leftOperand": "purpose",
        "operator": "eq",
        "rightOperand": "https://purpose.example/collaboration"
      },
      {
        "leftOperand": "dateTime",
        "operator": "lteq",
        "rightOperand": "2026-06-09T10:00:00Z"
      }
    ]
  }]
}

다른 속성이 선택적으로 다음에 존재할 수 있습니다: 접근 요청 및 접근 권한 부여.

11.2.1 유형

type 속성은 문서의 유형을 표현합니다.

type 속성의 값은 반드시 하나 이상의 용어 및 절대 URL 문자열이어야 합니다. 다음의 경우, 접근 요청, 값은 반드시 용어 AccessRequest를 포함해야 합니다. 다음의 경우, 접근 권한 부여, 값은 반드시 다음 용어를 포함해야 합니다: AccessGrant. 추가 유형 값을 선택적으로 포함할 수 있습니다.

이 속성은 필수입니다.

이 문서는 다음에 대해 아래 유형 값을 정의합니다: 접근 요청 및 접근 권한 부여:

  • AccessRequest — 다음 주체의 요청입니다: 에이전트, 리소스 접근에 대한 요청입니다.
  • AccessGrant — 다음 주체의 인가입니다: 저장소 제어자, 다음을 부여합니다: 리소스 접근 권한.
예시 19: type 속성 
{
  "type": ["AccessGrant"]
}

11.2.2 저장소

storage 속성은 LWS 저장소를 식별하며, 다음의 접근 요청 또는 접근 권한 부여가 적용되는 범위입니다.

storage 속성의 값은 반드시 URI여야 합니다.

이 속성은 필수입니다.

예시 20: storage 속성 
{
  "storage": "https://storage.example/"
}

11.2.3 수신함

inbox 속성은 다음과 관련된 알림을 수신하기 위한 URI를 지정합니다: 해당 접근 요청 또는 접근 권한 부여 (다음 참조: 11.6 알림).

inbox 속성의 값은 반드시 URI여야 합니다.

이 속성은 선택 사항입니다.

예시 21: inbox 속성 
{
  "inbox": "https://id.example/agent/inbox/"
}

11.2.4 접근

access 속성은 하나 이상의 다음 특성을 설명합니다: 접근 프로파일, 서버가 지원하는 프로파일에 기반합니다. 다음에 기반하는 프로파일은 ODRL 정보 모델, 다음에 설명되어 있습니다: 11.3 접근 프로파일.

access 속성의 값은 반드시 하나 이상의 객체로 구성된 컬렉션이어야 합니다.

이 속성은 필수입니다.

11.3 접근 프로파일

이 명세는 다음에 기반하는 접근 프로파일을 정의합니다: ODRL 정보 모델 및 ODRL 어휘, 다음으로 식별됩니다. 해당 URL은 https://www.w3.org/ns/lws#AccessProfile입니다.

11.3.1 유형

type 속성은 접근 정책의 유형을 표현합니다.

type 속성의 값은 반드시 하나 이상의 용어 및 절대 URL 문자열이어야 하며, 반드시 포함해야 합니다. 용어 AccessPolicy를 포함해야 합니다. 추가 유형 값을 선택적으로 포함할 수 있습니다.

이 속성은 필수입니다.

예시 22: 접근 정책 유형 
{
  "access": [{
    "type": ["AccessPolicy"]
  }]
}

11.3.2 행위

action 속성은 다음을 설명합니다: 작업, 다음 주체가 에이전트, 수행하려는 작업(요청의 경우) 또는 수행하도록 인가받은 작업(권한 부여의 경우)입니다.

action 속성의 값은 반드시 하나 이상의 문자열로 구성된 컬렉션이어야 합니다. 각 값은 반드시 다음이 인식하는 작업에 대응해야 합니다: 서버. 다음 값은 반드시 지원해야 합니다: read, modify, create 및 delete. read, modify 및 delete 값은 다음에 정의되어 있습니다: ODRL 어휘. create 값은 이 명세에 정의되어 있습니다.

이러한 행위 값은 다음과 같이 LWS 작업에 대응합니다:

  • read — 리소스 또는 메타데이터 조회(HTTP GET, HEAD)
  • modify — 기존 리소스 수정(HTTP PUT, PATCH)
  • create — 컨테이너 내에 새 리소스 생성(HTTP POST)
  • delete — 기존 리소스 제거(HTTP DELETE)

이 속성은 필수입니다.

예시 23: action 속성 
{
  "access": [{
    "action": ["read", "create"]
  }]
}

11.3.3 할당 대상자

assignee 속성은 접근을 요청하는 주체( 요청의 경우) 또는 접근 권한을 부여받는 주체(권한 부여의 경우)를 식별합니다.

assignee 속성의 값은 반드시 URI여야 합니다. 공개 접근 권한은 선택적으로 Agent 클래스를 사용하여 부여할 수 있으며, 다음의 클래스입니다: FOAF 어휘, 다음 URI로 식별됩니다: http://xmlns.com/foaf/0.1/Agent.

이 속성은 필수입니다.

예시 24: assignee 속성 
{
  "access": [{
    "assignee": "https://id.example/agent"
  }]
}

11.3.4 대상

target 속성은 리소스를 식별하며, 다음의 접근 요청 또는 접근 권한 부여가 적용되는 리소스입니다.

target 속성은 반드시 다음 속성을 포함하는 객체여야 합니다:

  • type — 용어 또는 절대 URL 문자열로서, 해당 대상 일치자의 유형을 식별합니다.
  • value — 하나 이상의 문자열로 구성된 컬렉션으로, 대상 리소스를 식별하는 데 사용합니다.

이 명세는 다음 type 값을 정의하며, 대상 객체와 함께 사용합니다:

  • https://www.w3.org/ns/lws#DataResource — 다음과 일치합니다: lws:DataResource 유형의 리소스.
  • https://www.w3.org/ns/lws#Container — 다음과 일치합니다: lws:Container 유형의 리소스.
  • https://www.w3.org/ns/lws#StorageResource — 다음과 일치합니다: 모든 저장소 리소스.

서버는 추가 유형 값을 선택적으로 지원할 수 있습니다.

이 속성은 선택 사항입니다.

예시 25: StorageResource를 가진 target 속성, 해당 유형 
{
  "access": [{
    "target": {
      "type": "StorageResource",
      "value": [
        "https://storage.example/root/2025",
        "https://storage.example/root/2026"
      ]
    }
  }]
}

11.3.5 제약 조건

constraint 속성은 요청하거나 부여하는 접근을 제한하거나 한정하는 조건을 정의합니다. 이 속성은 ODRL의 제약 조건 모델을 사용합니다.

constraint 속성의 값이 있는 경우, 그 값은 반드시 하나의 모음이어야 하며, 제약 조건 객체로 구성되어야 합니다. 각 제약 조건 객체는 반드시 다음 속성을 포함해야 합니다:

  • leftOperand — 제약 대상 피연산자를 식별하는 문자열입니다.
  • operator — 비교 연산자를 식별하는 문자열입니다.
  • rightOperand — 비교할 값입니다. 타입은 leftOperand에 따라 달라집니다.

여러 제약 조건 객체가 있는 경우, 모든 제약 조건이 반드시 충족되어야 합니다.

이 프로파일의 지원을 알리는 서버는 반드시 다음 leftOperand 값을 지원해야 합니다:

  • client — HTTP 요청의 클라이언트 식별자를 나타냅니다
  • format — 대상 HTTP 리소스의 미디어 타입을 나타냅니다
  • type — 리소스의 링크 헤더에 표현된 타입 URL을 나타냅니다
  • purpose — 요청하거나 부여하는 접근의 의도된 용도를 나타냅니다
  • dateTime — 현재 날짜와 시간을 나타냅니다

이 속성은 선택 사항입니다.

다음 예시는 이러한 제약 조건의 사용법을 보여 줍니다:

11.3.5.1 목적 제약 조건

다음 예시는 leftOperand 값으로 purpose를 사용하여 요청하거나 부여하는 접근의 의도된 용도를 설명합니다. eq 연산자를 사용하는 경우, rightOperand 값은 목적을 식별하는 URI입니다. isAnyOf 연산자를 사용하는 경우, rightOperand 값은 목적 URI의 배열이며, 명시된 목적이 나열된 값 중 하나와 일치하면 제약 조건이 충족됩니다:

예시 26: 목적 제약 조건 
{
  "access": [{
    "constraint": [
      {
        "leftOperand": "purpose",
        "operator": "isAnyOf",
        "rightOperand": [
          "https://purpose.example/collaboration",
          "https://purpose.example/research"
        ]
      }
    ]
  }]
}
11.3.5.2 클라이언트 제약 조건

다음 예시는 leftOperand 값으로 client를 사용하여 접근을 특정 클라이언트 애플리케이션으로 제한합니다. eq 연산자를 사용하는 경우, rightOperand 값은 클라이언트를 식별하는 URI입니다:

예시 27: 클라이언트 제약 조건 
{
  "access": [{
    "constraint": [
      {
        "leftOperand": "client",
        "operator": "eq",
        "rightOperand": "https://app.example/client-id"
      }
    ]
  }]
}
11.3.5.3 형식 제약 조건

다음 예시는 leftOperand 값으로 format을 사용하여 접근을 특정 미디어 타입의 리소스로 제한합니다. eq 연산자를 사용하는 경우, rightOperand 값은 IANA 미디어 타입을 식별하는 문자열입니다. isAnyOf 연산자를 사용하는 경우, rightOperand 값은 미디어 타입 문자열의 배열이며, 리소스의 미디어 타입이 나열된 값 중 하나와 일치하면 접근이 허용됩니다:

예시 28: 형식 제약 조건 
{
  "access": [{
    "constraint": [
      {
        "leftOperand": "format",
        "operator": "isAnyOf",
        "rightOperand": ["image/jpeg", "image/png"]
      }
    ]
  }]
}
11.3.5.4 리소스 타입 제약 조건

모든 저장소 리소스에는 타입 값을 나타내는 링크 헤더가 포함됩니다:

예시 29: 타입 값이 있는 링크 헤더 
Link: <https://www.w3.org/ns/lws#DataResource>; rel="type"
Link: <https://type.example/Playlist>; rel="type"

다음 예시는 leftOperand 값으로 type을 사용하여 HTTP Link 헤더에 공지된 리소스 타입을 기준으로 접근을 제한합니다. eq 연산자를 사용하는 경우, rightOperand 값은 리소스 타입을 식별하는 URI입니다. isAnyOf 연산자를 사용하는 경우, rightOperand 값은 타입 URI의 배열이며, 리소스의 타입이 나열된 값 중 하나와 일치하면 접근이 허용됩니다:

예시 30: 리소스 타입 제약 조건 
{
  "access": [{
    "constraint": [
      {
        "leftOperand": "type",
        "operator": "isAnyOf",
        "rightOperand": [
          "https://type.example/Playlist",
          "https://type.example/Song"
        ]
      }
    ]
  }]
}
11.3.5.5 시간 제약 조건

다음 예시는 leftOperand 값으로 dateTime을 사용하여 접근을 특정 시간 구간으로 제한합니다. gteq 연산자는 구간의 시작을 정의하고, lteq 연산자는 끝을 정의합니다. 시간 제약 조건의 rightOperand 값은 XML 스키마 dateTime 문자열입니다:

예시 31: 시간 제약 조건 
{
  "access": [{
    "constraint": [
      {
        "leftOperand": "dateTime",
        "operator": "gteq",
        "rightOperand": "2026-03-09T12:00:00Z"
      },
      {
        "leftOperand": "dateTime",
        "operator": "lteq",
        "rightOperand": "2026-06-09T10:00:00Z"
      }
    ]
  }]
}
11.3.5.6 제약 조건의 결합

여러 제약 조건 객체가 있는 경우, 모든 제약 조건이 반드시 충족되어야 접근이 허용됩니다. 다음 예시는 특정 클라이언트 애플리케이션에서 특정 날짜 이전에 이루어지는 접근으로 제한합니다:

예시 32: 결합된 제약 조건 
{
  "access": [{
    "action": ["read"],
    "assignee": "https://id.example/agent",
    "target": {
      "type": "StorageResource",
      "value": ["https://storage.example/root/projects/"]
    },
    "constraint": [
      {
        "leftOperand": "dateTime",
        "operator": "lteq",
        "rightOperand": "2026-06-09T10:00:00Z"
      },
      {
        "leftOperand": "client",
        "operator": "eq",
        "rightOperand": "https://app.example/client-id"
      }
    ]
  }]
}

11.4.1 JSON-LD 직렬화

이 명세는 접근 요청 및 접근 권한 부여를 위한 JSON-LD 직렬화를 정의합니다. 이 직렬화를 사용하는 문서는 반드시 @context 속성을 포함해야 하며, 그 값은 https://www.w3.org/ns/lws/v1을 포함하는 순서 있는 집합이어야 합니다. 추가 맥락 항목을 선택적으로 더 포함하여 확장 용어를 정의할 수 있습니다.

이 직렬화와 연관된 미디어 타입은 application/lws+json입니다.

{

    "https://www.w3.org/ns/lws/v1"
  ]
}

11.5 프로토콜

접근 요청 및 접근 권한 부여 엔드포인트는 LWS 컨테이너이며 반드시 이 명세에 정의된 규칙을 준수해야 합니다.

이러한 엔드포인트는 최소한 GET 및 POST 작업을 지원해야 합니다. DELETE 작업의 지원은 권장됩니다. 다른 작업도 선택적으로 지원할 수 있습니다.

이러한 엔드포인트는 반드시 요청 및 응답 페이로드 모두에 대해 11.4.1 JSON-LD 직렬화에 정의된 JSON-LD 직렬화를 지원해야 합니다. 서버는 선택적으로 추가 직렬화를 지원할 수 있습니다.

에이전트는 POST 요청을 제출하여 접근 요청을 생성하며, 제출 대상은 해당 접근 요청 엔드포인트입니다. 저장소 제어자는 접근 권한 부여를 생성하며, 이를 위해 POST 요청을 접근 권한 부여 엔드포인트에 제출합니다.

성공한 POST 작업은 반드시 Location 헤더를 포함하여 응답해야 하며, 이 헤더의 값은 새 리소스의 URL로 설정해야 합니다.

11.5.1 접근 요청 엔드포인트

  • POST / — 접근 요청을 생성합니다.
  • GET / — 접근 요청 목록을 가져옵니다.
  • GET /:id — 특정 접근 요청을 가져옵니다.
  • DELETE /:id — 접근 요청을 취소합니다.

11.5.2 접근 권한 부여 엔드포인트

  • POST / — 접근 권한 부여를 생성합니다.
  • GET / — 접근 권한 부여 목록을 가져옵니다.
  • GET /:id — 특정 접근 권한 부여를 가져옵니다.
  • DELETE /:id — 접근 권한 부여를 철회합니다.

11.6 알림

이슈 103: LWS 알림 기능 work-item

이 절은 아직 정의되지 않은 LWS의 알림 절과 일치하도록 조정해야 합니다.

알림은 에이전트 및 저장소 제어자에게 다음 항목의 변경 사항을 알리는 메커니즘을 제공합니다: 접근 요청 및 접근 권한 부여. inbox 속성이 접근 요청 또는 접근 권한 부여에 있는 경우, 서버는 가급적 해당 엔드포인트에 알림을 전달하여 할당 대상자에게 이벤트를 알리는 것이 좋습니다.

알림의 직렬화는 반드시 LWS 알림 데이터 모델의 요구 사항을 준수해야 합니다.

inbox 엔드포인트에 전달되는 알림은 반드시 알림 전달에 대해 LWS 프로토콜에 정의된 요구 사항을 준수해야 합니다.

참고

이 절에서 설명하는 알림 메커니즘은 연결된 데이터 알림 패턴과 유사하며, 이 패턴에서는 알림을 발견할 때 inbox 속성을 사용하고, 전달할 때는 POST 요청을 해당 수신함에 전송합니다.

11.6.1 알림 이벤트

서버는 가급적 다음 이벤트에 대한 응답으로 알림을 전송하는 것이 좋습니다:

  • 접근 요청 생성: 새 접근 요청이 제출되면, 저장소 제어자에게 가급적 알리는 것이 좋습니다.
  • 접근 권한 부여 생성: 새 접근 권한 부여가 생성되면, 요청한 에이전트에게 가급적 다음 위치로 알리는 것이 좋습니다: inbox에 지정된 위치이며, 관련 접근 요청에 명시됩니다.

서버는 선택적으로 다른 이벤트에 대한 응답으로 알림을 전송할 수 있습니다.

12. LWS 미디어 타입

12.1 LWS 미디어 타입

LWS 저장소 설명은 반드시 미디어 타입 application/lws+cid로 직렬화할 수 있어야 합니다. application/lws+cid 미디어 타입은 다음 문서 형식을 특수화한 문서를 식별합니다: W3C 제어 식별자 문서 [CID-1.0]. 이 문서는 LWS 어휘로 확장됩니다.

LWS 컨테이너 표현은 반드시 미디어 타입 application/lws+json을 지원해야 합니다.

LWS 컨테이너 표현은 JSON-LD 규칙을 사용하지만, LWS의 제약 조건과 요구 사항은 별도의 미디어 타입 사용을 정당화합니다.

12.1.1 LWS 프로파일

URI https://www.w3.org/ns/lws/v1은 LWS 프로파일을 식별합니다 [RFC6906]. 컨테이너의 표현은 다음 조건을 충족하면 LWS 프로파일에 부합합니다: 동일한 컨테이너 상태 및 페이지의 application/lws+json 표현과 RDF가 동형인 경우입니다. 즉, 인코딩된 RDF가 다음에 정의된 동형 관계를 충족해야 합니다: RDF 데이터셋 비교 [RDF12-CONCEPTS]. 비교 대상은 application/lws+json 표현을 JSON-LD로 해석할 때 인코딩되는 RDF입니다 [JSON-LD11]. application/lws+json 표현은 항상 LWS 프로파일에 부합합니다.

12.1.2 콘텐츠 협상

서버는 반드시 컨테이너에 대한 application/lws+json 요청을 처리해야 하며, 반드시 Content-Type 응답 헤더를 선택한 표현의 미디어 타입으로 설정해야 합니다.

클라이언트는 LWS 프로파일의 표현을 요청할 때 LWS 프로파일 URI를 RDF 미디어 타입의 profile 매개변수에 포함합니다. 이 매개변수를 정의하는 RDF 미디어 타입에는 application/ld+json [JSON-LD11], text/turtle [RDF12-TURTLE], application/trig [RDF12-TRIG], application/n-triples [RDF12-N-TRIPLES], application/n-quads가 있습니다 [RDF12-N-QUADS]. 서버가 이러한 미디어 타입을 선택하면, 응답은 반드시 LWS 프로파일에 부합해야 합니다. 즉, 반드시 application/lws+json 표현과 RDF가 동형이어야 하며, 해당 Content-Type은 반드시 동일한 profile 매개변수를 포함해야 합니다. 서버는 절대로 이러한 미디어 타입을 선택해서는 안 됩니다. 해당 미디어 타입으로 LWS 프로파일에 부합하는 표현을 생성할 수 없는 경우가 이에 해당합니다.

선택한 표현이 요청의 Accept 헤더에 따라 달라지는 경우, 응답은 가급적 Vary: Accept 헤더를 포함하는 것이 좋습니다 [RFC9110].

12.1.3 페이지 나누기

컨테이너와 같은 일부 복합 리소스는 많은 수의 리소스를 보유할 수 있습니다. 클라이언트가 목록을 점진적으로 가져올 수 있도록, 서버는 가급적 페이지 나누기를 지원하는 것이 좋습니다. 이는 컨테이너의 멤버 수가 서버에서 정한 임곗값을 초과하는 경우에 해당합니다.

12.1.3.1 페이지 나누기 모델

페이지 나누기는 링크를 기반으로 합니다. 서버는 HTTP Link 헤더로 페이지 나누기 URI를 제공합니다 [RFC8288]. 이를 통해 클라이언트는 숫자 오프셋에 의존하지 않고 전체 목록을 탐색할 수 있습니다.

목록을 페이지로 나눈 경우, 응답 본문에는 현재 페이지의 항목만 포함됩니다. 복합 리소스의 id, type, totalItems 속성은 전체 멤버십을 반영하는 반면, items는 현재 페이지의 리소스만 포함합니다.

12.1.3.2 페이지 나누기 링크 관계

페이지 나누기 URI는 다음 표준 링크 관계를 사용하는 Link 헤더로 전달됩니다:

  • rel="first": 결과의 첫 번째 페이지 URI입니다. 반드시 페이지로 나눈 응답에 있어야 합니다.
  • rel="last": 결과의 마지막 페이지 URI입니다. 선택적으로 페이지로 나눈 응답에 있을 수 있습니다.
  • rel="next": 결과의 다음 페이지 URI입니다. 반드시 후속 페이지가 있을 때 존재해야 합니다. 마지막 페이지에서는 반드시 생략해야 합니다.
  • rel="prev": 결과의 이전 페이지 URI입니다. 선택적으로 앞선 페이지가 있을 때 존재할 수 있습니다. 첫 번째 페이지에서는 반드시 생략해야 합니다.

모든 페이지 나누기 URI는 클라이언트에 불투명합니다. 클라이언트는 가급적 페이지 나누기 URI를 구성하거나 수정하지 않는 것이 좋으며, 가급적 서버에서 제공하는 URI를 사용하는 것이 좋습니다.

12.1.3.3 페이지 요청

클라이언트는 첫 번째 페이지를 얻기 위해 복합 리소스의 URI를 요청합니다. 응답에는 페이지 나누기 Link 헤더가 포함되며, 클라이언트는 이를 따라 후속 페이지를 가져옵니다. 서버는 선택적으로 다음 기능도 지원할 수 있습니다: 이전 탐색에서 얻은 페이지 나누기 URI를 통해 특정 페이지에 직접 접근하는 기능입니다.

페이지로 나눈 응답을 반환할 때, 서버는 반드시 200 OK로 응답해야 합니다. 응답 본문의 totalItems 속성은 가급적 현재 페이지의 항목 수뿐만 아니라 전체 페이지에 걸친 총 항목 수를 반영하는 것이 좋습니다.

13. JSON-LD 맥락

LWS JSON-LD 맥락은 URL https://www.w3.org/ns/lws/v1로 식별됩니다. 해당 URL을 해석하여 얻은 문서의 SHA2-256 다이제스트는 아래 표에 포함되어 있습니다:

맥락 URL 및 해시
URL: https://www.w3.org/ns/lws/v1
SHA2-256 다이제스트: 할 일: 맥락 문서가 확정되면 JSON-LD 맥락 다이제스트를 포함합니다

다이제스트는 다음과 같은 명령으로 검증할 수 있습니다: curl -sL -H "Accept: application/ld+json" https://www.w3.org/ns/lws/v1 | openssl dgst -sha256

참고
운영 시스템은 실행 시점에 원격 JSON-LD 맥락 문서를 가져오지 않는 것이 좋습니다. 맥락을 로컬에 묶어 배포하거나 캐시하면 실행 시점의 외부 인프라 의존성을 제거하고, 지연 시간을 줄이며, 맥락 조작 공격을 방지할 수 있습니다.

이 부분은 의도적으로 비워 두었습니다

15. 이식성 고려 사항

LWS 구현이 서로 다른 플랫폼, 환경, 저장소 백엔드에서 상호운용성을 유지하며 작동하도록 보장하기 위한 고려 사항을 설명하고, 저장소 제공자를 변경할 수 있도록 지원하는 수단을 제공합니다

이 부분은 의도적으로 비워 두었습니다

16. 보안 고려 사항

이 절은 비규범적입니다.

위협 모델, 보안 요구 사항, 안전한 LWS 배포를 위한 구현 지침을 다루는 정식 보안 고려 사항 절입니다.

OAuth 2.0 보안을 위한 현행 최선 관행 [RFC9700]에 설명된 권장 사항은 이 명세에 적용됩니다.

16.1 전송 보안

이 절은 비규범적입니다.

전송 계층 보안(TLS)은 변조, 위장, 정보 유출을 방지하는 중요한 메커니즘입니다. TLS로 보호되는 통신은 [RFC6125]에 따라 검증할 수 있습니다. 구현 보안 고려 사항은 "전송 계층 보안(TLS) 및 데이터그램 전송 계층 보안(DTLS)의 안전한 사용을 위한 권장 사항" [RFC9325]에서 확인할 수 있습니다.

16.2 토큰 보안

이 절은 비규범적입니다.

베어러 토큰과 디지털 자격 증명은 탈취 및 재전송에 취약합니다. 완화책에는 적절히 짧은 유효 기간 사용, 특정 수신 대상에 토큰 바인딩, 안전한 토큰 저장이 포함됩니다.

  • 짧은 유효 기간: 접근 토큰에 300초(5분) 이하의 유효 기간을 부여하는 인가 서버는 유출된 자격 증명의 잠재적 노출 범위를 제한할 수 있습니다.
  • 수신 대상 바인딩: 다음과 같은 수단으로 접근 토큰을 특정 대상 서버에 바인딩하면, aud 클레임 등을 통해 토큰이 다른 서버에서 재전송되는 것을 방지할 수 있습니다. 접근 토큰의 수신 대상에 둘 이상의 서버가 포함되면, 해당 서버 중 어느 것이든 다른 서버에 그 토큰을 재전송할 수 있습니다. 인가 서버는 단일 저장소 URI를 수신 대상으로 하는 토큰을 발급하여 이를 방지합니다. 수신 대상이 제한되지 않은 자격 증명을 처리하는 애플리케이션은 이러한 자격 증명을 다른 개체에 전송할 때 주의해야 하며, 특히 신뢰할 수 없는 인가 서버에 전송할 때 주의해야 합니다. 자격 증명 발급자가 토큰의 수신 대상을 제한할 수 없다면, 클라이언트는 다음과 같은 메커니즘을 사용할 수 있습니다: OAuth 2.0 토큰 교환 [RFC8693]. 이를 통해 수신 대상이 제한된 자격 증명을 생성한 후 다른 보안 도메인의 인가 서버와 상호작용할 수 있습니다.
  • 송신자 제한 토큰: 베어러 토큰은 이를 획득한 누구나 사용할 수 있으며, 수신 대상 제한은 유출된 토큰이 원래 대상인 저장소 서버에 재전송되는 것을 막지 못합니다. 수신 대상이 저장소이므로, 탈취된 토큰은 에이전트가 해당 저장소 내에서 접근하도록 인가된 모든 리소스에 사용할 수 있습니다. OAuth 2.0 소유 증명 입증 (DPoP)과 같은 방식으로 접근 토큰을 클라이언트 키에 바인딩하면 [RFC9449], 탈취된 토큰의 사용을 해당 키의 소유자로 제한할 수 있습니다. 보호 리소스 메타데이터 문서는 저장소 서버가 지원하는 DPoP 증명 알고리즘과 DPoP에 바인딩된 접근 토큰의 필수 여부를 dpop_signing_alg_values_supported 및 dpop_bound_access_tokens_required 매개변수를 사용하여 알릴 수 있습니다. 이 매개변수는 [RFC9728]에 정의되어 있습니다.
  • 안전한 저장: 자격 증명을 영구 저장하는 애플리케이션은 해당 객체가 안전하게 저장되도록 해야 합니다. 암호화되지 않은 토큰을 브라우저의 localStorage, URL, 로그에 저장할 때마다 해당 토큰은 유출 공격에 더 취약해집니다.

16.3 리소스 발견

이 절은 비규범적입니다.

클라이언트는 저장소 서버가 보낸 응답을 통해 인가 서버의 위치를 알게 되며, 클라이언트는 해당 저장소 서버를 신뢰하지 않을 수도 있습니다. 이 발견 과정에는 다음 고려 사항이 적용됩니다.

  • 신뢰할 수 없는 메타데이터: 악의적인 저장소 서버는 클라이언트를 클라이언트가 신뢰하지 않는 인가 서버로 유도할 수 있으며, 인증 자격 증명을 해당 인가 서버에 제시하는 클라이언트는 그 자격 증명을 노출하게 됩니다. 클라이언트는 어떤 인가 서버를 신뢰할지에 관한 자체 정책을 적용하여 이러한 위험을 줄일 수 있습니다. 5.2.3 클라이언트의 발견 검증에 있는 검사는 보호 리소스 메타데이터가 동일한 서버에서 요청된 리소스를 설명하도록 요구하여, 서버가 다른 리소스 서버에 속하는 메타데이터를 제시하는 것을 방지합니다. 또한 클라이언트가 다음과 같은 형태의 인증 자격 증명을 사용하면 노출의 영향이 줄어듭니다: 수신 대상이 전송 대상 인가 서버로 제한된 자격 증명입니다.
  • 저장소 바인딩: 클라이언트는 저장소 서버의 응답에 있는 Link 헤더에서 저장소 URI를 얻습니다. 악의적인 서버는 다른 저장소의 URI를 제공하여 클라이언트가 해당 저장소의 접근 토큰을 얻고 이를 악의적인 서버에 제시하게 할 수 있으며, 해당 서버는 그 토큰을 재전송할 수 있습니다. 따라서 클라이언트는 접근 토큰을 요청하기 전에 저장소 설명을 사용하여, 요청한 URI가 저장소 루트와 동일한 출처에서 제공되는지 확인해야 합니다. 이는 다음에 설명되어 있습니다: 5.2.3 클라이언트의 발견 검증.
  • 서버 측 요청 위조: 챌린지의 resource_metadata URL, 저장소 URI가 포함된 Link 헤더, 보호 리소스 메타데이터 문서의 발급자 식별자는 저장소 서버가 선택하며, 클라이언트는 이들이 식별하는 문서를 가져옵니다. 이러한 가져오기 작업을 다른 당사자를 대신하여 수행하는 클라이언트(예: 서버 측 애플리케이션)는 서버 측 요청 위조에 노출됩니다. 이는 다음에 설명되어 있습니다: [RFC9728]의 7.7절. 예방 조치에는 가져오기를 https 스킴으로 제한하고 내부 IP 주소 범위에 대한 요청을 차단하는 것이 포함됩니다.

16.4 접근 요청 및 권한 부여

이 절은 비규범적입니다.

  • 서버는 다음 두 엔드포인트 모두에 인가 규칙을 적용할 것을 강력히 권장합니다: 접근 요청 및 접근 권한 부여 엔드포인트입니다. 특히 다음의 쓰기 접근은, 접근 권한 부여 엔드포인트에 대한 쓰기 접근으로서, 인가된 저장소 제어자와 특정 클라이언트로 제한하는 것이 좋습니다.
  • 에이전트가 접근 요청을 생성할 때, 서버는 요청의 assignee 값이 요청 에이전트의 인증된 신원과 연관되어 있는지 검증하는 것이 권장됩니다.
  • 접근 요청 엔드포인트는 외부 에이전트의 콘텐츠를 수락하므로, 서버는 요청 빈도 제한, 페이로드 크기 제한, 제출 수락 전 인증 요구와 같은 악용 방지 조치를 구현하는 것이 권장됩니다. 이러한 보호 조치가 없으면 엔드포인트는 스팸, 리소스 고갈, 기타 형태의 원치 않는 콘텐츠에 취약할 수 있습니다.

16.5 알림

이 절은 비규범적입니다.

  • 정보 유출: 알림은 리소스의 존재 또는 변경 패턴을 드러낼 수 있습니다. 구독 및 개별 알림 전달에 대한 접근 제어는 반드시 기반이 되는 리소스의 접근 제어와 일관되어야 합니다.
  • 구독 악용: 구독 메커니즘의 악용을 방지하기 위해 요청 빈도 제한과 엔드포인트 검증을 권장합니다.

16.6 리소스 이동 (컨테이너 간)

이 절은 비규범적입니다.

  • 적용 정책의 변경: 리소스에 대한 접근은 흔히 포함 관계 계층에서 해당 리소스의 위치로 표현되는 정책의 지배를 받습니다. 따라서 리소스의 up 링크를 변경하면 해당 리소스에 접근할 수 있는 에이전트의 집합이 넓어지거나 좁아질 수 있으며, 이는 정책을 편집하지 않고 또한 리소스의 콘텐츠를 변경하지 않아도 발생합니다. 이러한 결과를 저장소 제어자와 이동을 요청하는 에이전트에게 명확히 보여 주는 것은 유용한 완화책입니다. 다만 구현에서 이를 수행하는 방법은 이 명세의 범위를 벗어납니다.
  • 권한의 결합: 리소스 이동은 원본에서의 삭제 효과와 원본 컨테이너에서 목적지 컨테이너로의 생성 효과를 결합합니다. 서버는 반드시 두 인가를 모두 평가해야 하며, 이는 9.6 리소스 이동 (컨테이너 간)에서 요구합니다. 리소스의 메타데이터를 갱신하는 인가만 평가하면 에이전트가 쓰기 권한이 없는 컨테이너에 리소스를 배치하거나, 삭제 권한이 없는 컨테이너에서 리소스를 제거할 수 있게 됩니다.
  • 컨테이너 이동: 컨테이너를 이동하면 그 하위 항목도 이동하며, 여기에는 요청한 에이전트가 알지 못하는 리소스가 포함될 수 있습니다. 해당 하위 항목의 부모는 변경되지 않지만 적용되는 정책은 바뀔 수 있으므로, 컨테이너 이동을 지원하는 서버는 반드시 이동하는 하위 트리의 재귀적 삭제에 필요한 인가를 평가해야 합니다. 이는 9.6 컨테이너 간 리소스 이동에서 요구하며, 절대로 하위 트리의 일부에 대한 인가가 실패한 이동을 부분적으로 적용해서는 안 됩니다.
  • 서버 관리 메타데이터의 제한 완화: MoveResource 기능을 기술하면 평소 서버가 자체적으로 유지하는 up 링크를 클라이언트가 쓸 수 있게 됩니다. 서버는 가급적 해당 기능을 배포 환경에서 필요로 하는 곳에만 기술하는 것이 좋으며, 가급적 appliesTo 속성을 지원해야 하는 리소스 타입으로 제한하는 것이 좋습니다. 또한 반드시 클라이언트가 수정하도록 허용되지 않은 링크를 계속 보존해야 합니다.

17. 개인정보 보호 고려 사항

이 절은 비규범적입니다.

데이터 최소화, 사용자 동의, 개인정보를 보호하는 구현 패턴을 포함한 LWS 프로토콜의 개인정보 보호 영향을 다룹니다.

자격 증명은 사용자 및 에이전트에 관한 정보를 담고 있습니다. 디지털 서명은 변조를 방지할 수 있지만, 클라이언트나 제삼자는 암호화되지 않은 자격 증명 내부의 값을 읽을 수 있습니다.

따라서 자격 증명 발급자는 필요한 정보만 포함하는 토큰을 생성하는 것이 권장됩니다. 그 용도는 인증 또는 인가이며, 필수적인 경우가 아니면 민감한 속성을 포함하지 않는 것이 좋습니다.

일반적으로 암호화되지 않은 자격 증명 데이터를 로그에 기록하는 것은 안티패턴입니다. 이것이 필요한 경우, 구현은 자격 증명을 잘라내거나 해시 처리하여 자격 증명 주체의 개인정보를 보호할 수 있습니다.

JWT에서 가명 식별자를 사용하더라도, 저장소 서버는 여전히 동일한 에이전트의 요청을 시간에 걸쳐 연관 지을 수 있습니다. 이 경우 사용자 개인정보를 보호하기 위해 클라이언트 애플리케이션은 JWT의 일괄 발급을 요청하여, 각 JWT를 한 번만 사용할 수 있습니다. 그러나 이렇게 해도 저장소 서버가 JWT 콘텐츠의 유사성이나 발신 IP 주소와 같은 다른 정보를 사용하여 요청을 연관 짓는 것을 막지는 못합니다. 가명 식별자를 사용할 때 인가 서버는 동일한 식별자를 두 번 이상 발급하지 않도록 주의해야 합니다.

17.1 접근 요청 및 권한 부여

이 절은 비규범적입니다.

  • 접근 요청 또는 접근 권한 부여는 민감한 정보를 드러낼 수 있으며, 여기에는 관련 리소스, 에이전트, 목적에 관한 정보가 포함됩니다. 서버는 이러한 리소스의 공개 범위를 저장소 제어자와 문서에 식별된 할당 대상자 등 인가된 당사자로 제한하는 것이 권장됩니다. 예를 들어 저장소 제어자는 모든 리소스를 읽고 삭제할 수 있는 반면, 다른 에이전트는 자신이 할당 대상자인 리소스에만 접근할 수 있습니다.
  • 접근 권한 부여에 클라이언트 제약 조건이 포함된 경우, 해당 서버는 다른 클라이언트가 보낸 요청에 대한 응답에서 그 권한 부여를 제외하는 것이 좋습니다. 예를 들어 에이전트가 특정 클라이언트를 사용할 때만 리소스에 접근하도록 허용되었다면, 에이전트가 다른 클라이언트를 사용할 때는 해당 권한 부여가 표시되지 않습니다.

17.2 알림

이 절은 비규범적입니다.

  • 활동 추적: 알림은 본질적으로 리소스가 언제 변경되는지 드러냅니다. 구독자는 가급적 자신이 접근하도록 인가된 리소스의 알림만 받는 것이 좋습니다.
  • 행위자 공개: 알림에 actor 속성을 포함하면 변경한 사람이 누구인지 드러납니다. 이는 일부 상황에서 부적절할 수 있습니다. actor 속성은 가급적 기본적으로 생략하는 것이 좋습니다. 서버는 선택적으로 해당 속성의 포함 여부를 설정할 수 있도록 할 수 있습니다.
  • 시점 분석: 알림이 발생하는 시점은 콘텐츠가 공개되지 않더라도 사용 패턴을 드러낼 수 있습니다.

17.3 리소스 이동 (컨테이너 간)

이 절은 비규범적입니다.

  • 의도하지 않은 노출: 리소스를 이동하는 에이전트는 목적지 컨테이너에 원본보다 더 허용적인 정책이 적용된다는 사실을 모를 수 있습니다. 리소스의 up 링크가 변경되기 전에 적용 정책의 차이를 드러내는 것은 유용한 완화책이지만, 클라이언트가 이를 수행하는 방법은 이 명세의 범위를 벗어납니다.
  • 유지되는 식별자: 이 고려 사항은 서버가 포함 관계 계층에서 식별자를 도출하는 경우에만 적용됩니다. 이러한 서버가 이동한 리소스의 식별자를 유지하면, 그 식별자는 리소스가 원래 생성된 컨테이너를 계속 드러내게 됩니다. 이 명세에서 권장하는 대로 식별자를 불투명하게 취급하는 서버는 이러한 정보를 공개하지 않습니다. 해당 식별자가 애초에 계층 내 위치를 인코딩하지 않기 때문입니다.
    이슈 207: 리소스 식별(URI 할당)에 영향을 미치는 기능 정의 storage-descriptionvocabulary

    이 고려 사항의 구체적인 예시는 작업 그룹이 저장소에서 식별자 할당 방식을 기술하는 방법을 결정한 뒤에 제시하는 것이 가장 좋습니다.

  • 리디렉션: 이전 식별자에 남겨 둔 301 Moved Permanently 응답은 리소스의 새 식별자를 에이전트에게 공개하며, 해당 에이전트는 리소스에 접근하도록 인가되지 않았을 수도 있습니다. 식별자가 포함 관계 계층에서 도출되는 경우, 계층 내 리소스의 새 위치도 추가로 공개되며, 따라서 이동 목적지 컨테이너도 드러납니다. 식별자가 불투명한 경우에는 오직 새 식별자만 공개됩니다. 서버는 가급적 동일한 접근 제어를 이러한 응답과 이동한 리소스 자체에 적용하는 것이 좋으며, 선택적으로 대신 404 Not Found로 응답할 수 있습니다.

  • 변경 관리자: W3C
  • 명세 문서: LWS-Auth의 5절

18.3 application/lws+json 미디어 타입

이 명세는 application/lws+json 미디어 타입을 문서 식별을 위해 등록하며, 구체적으로 Linked Web Storage 컨테이너 형식에 부합하는 문서를 식별합니다.

  • 타입 이름: application
  • 하위 타입 이름: lws+json
  • 필수 매개변수: 없음
  • 인코딩 고려 사항: application/lws+json 미디어 타입을 사용하는 리소스는 다음을 준수해야 합니다: application/json 미디어 타입의 모든 요구 사항입니다. 따라서 동일한 인코딩 고려 사항이 적용되며, 이는 [RFC8259]의 11절에 명시되어 있습니다.
  • 보안 고려 사항: 이 명세에 정의된 바와 같습니다.
  • 연락처: W3C Linked Web Storage 작업 그룹 <public-lws-wg@w3.org>

Linked Web Storage 형식은 JSON-LD 규칙을 사용하지만, 여러 제약 조건과 추가 요구 사항이 LWS 구현에 적용되므로 별도의 미디어 타입을 사용하는 것이 타당합니다.

18.4 application/lws+cid 미디어 타입

이 명세는 application/lws+cid 미디어 타입을 다음 문서를 식별하기 위해 등록합니다: Linked Web Storage 프로토콜에 부합하며 W3C 제어 식별자 1.0 문서 형식을 특수화한 저장소 설명 문서입니다.

  • 타입 이름: application
  • 하위 타입 이름: lws+cid
  • 필수 매개변수: 없음
  • 인코딩 고려 사항: application/lws+cid 미디어 타입을 사용하는 리소스는 application/json의 모든 요구 사항을 준수해야 합니다. 따라서 해당 미디어 타입과 동일한 인코딩 고려 사항이 적용되며, 이는 [RFC8259]의 11절에 명시되어 있습니다.
  • 보안 고려 사항: 이 명세에 정의된 바와 같습니다
  • 연락처: W3C Linked Web Storage 작업 그룹 <public-lws-wg@w3.org>
