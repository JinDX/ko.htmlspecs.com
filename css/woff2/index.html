초록

널리 배포된 WOFF 1.0의 경험을 바탕으로, 이 명세는 압축률을 높여 네트워크 대역폭 사용량을 줄이면서도 모바일 기기에서도 빠르게 압축을 풀 수 있도록 개발되었다. 이를 위해 콘텐츠를 고려하는 전처리 단계와 개선된 엔트로피 부호화를 결합하여, WOFF 1.0에서 사용한 Flate 압축보다 나은 압축을 제공한다.

1. 소개

이 문서는 WOFF2 폰트 패키징 형식을 규정한다. 이 형식은 비교적 구현하기 쉬우면서도 기존 기법보다 훨씬 높은 압축률로 폰트 데이터를 압축하고, CSS @font-face 규칙에 사용할 수 있도록 설계되었다. 이전에 개발된 WOFF 1.0 형식 [WOFF1] 대비 압축률 향상은 개선된 엔트로피 부호화와 폰트 데이터 전처리 및 최적화 단계를 통해 다양한 폰트 데이터 구조에 내재된 중복을 줄여 실현된다. WOFF 2.0의 개발 이력에 관한 자세한 내용은 WOFF 2.0 평가 보고서 [WOFF2ER]에 있다.

1.1 표기 규칙

이 문서에서 모두 대문자로 표기된 키워드 "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", "OPTIONAL"은 RFC 2119 [RFC2119]에 따라 해석한다. 이 단어들이 소문자 또는 대소문자 혼합으로 나타나면 일반적인 영어 의미에 따라 해석한다.

이 문서에는 “참고”로 표시하고 명세 본문과 구분한 텍스트가 있다. 이 참고는 구현자와 사용자에게 힌트나 지침을 제공하는 정보성 설명 또는 명확화를 위한 것이며, 규범적 텍스트의 일부가 아니다.

이 문서는 16진수 표기 "0x..."도 사용하여 매직 넘버나 태그 값 같은 이진 상수, 비트 필드 /플래그 형식, 의사 코드의 비트 연산자에 사용하는 마스크 값을 정의한다.

2. 일반 요구사항

WOFF2 형식의 주된 목적은 CSS @font-face 규칙으로 웹 문서에 연결된 폰트를 효율적으로 패키징하는 것이다. 연결된 폰트에 WOFF2 파일 형식을 지원하는 사용자 에이전트는 CSS3 Fonts 명세의 요구사항을 준수해야 한다 ([CSS3-Fonts] 제4.1절: @font-face 규칙). 특히, 이러한 연결된 폰트는 이를 참조하는 문서에서만 사용할 수 있어야 하며, 사용자 시스템의 다른 애플리케이션이나 문서에서 사용할 수 있게 해서는 안 된다.

입력 폰트 파일은 [OFF] 명세 제5절에서 설명하는 여러 폰트 데이터 테이블을 포함할 수 있다. 폰트 파일에서 테이블 순서는 달라질 수 있으며, 테이블 디렉터리의 항목은 태그의 오름차순으로 정렬해야 하지만 실제 테이블은 폰트 파일에 임의의 순서로 배치할 수 있다.

WOFF2 파일의 압축을 풀 때 디코더는 테이블 디렉터리의 항목을 테이블 태그의 알파벳 오름차순으로 정렬해야 하며, 파일의 테이블 순서는 [OFF]의 권장 사항(제8.1항 “최적화된 테이블 순서”)에 따라 배치하는 것이 바람직하다.

3. 전체 파일 구조와 기본 데이터 타입

WOFF2 파일 구조는 SFNT 및 WOFF 1.0과 비슷하며, 헤더 다음에 테이블 디렉터리, 그다음에 해당 테이블의 데이터가 온다. SFNT 구조는 TrueType [TrueType], OpenType [OpenType], ISO “Open Font Format” [OFF] 명세에 자세히 설명되어 있다. 하지만 WOFF2는 몇 가지 중요한 측면에서 SFNT와 다르다. 특히, 모든 폰트 테이블의 데이터는 전체 테이블을 포함한 단일 데이터 스트림으로 압축된다. WOFF 1.0과 마찬가지로 선택적인 확장 메타데이터 및 비공개 데이터는 각각 별도 데이터 블록으로 표현되며, 연결되어 WOFF 2.0 파일을 구성한다. 압축 폰트 데이터 스트림과 확장 메타데이터 블록에 사용하는 압축 알고리즘은 모두 Brotli [Brotli]이다.

완전한 WOFF2 파일은 여러 데이터 블록으로 구성된다. 48바이트 헤더 바로 뒤에 가변 크기 테이블 디렉터리, 선택적인 컬렉션 디렉터리(입력이 폰트 컬렉션인 경우만 존재), 압축 폰트 데이터 블록, 선택적인 확장 메타데이터 블록, 선택적인 비공개 데이터 블록이 순서대로 온다. 테이블 길이나 블록 오프셋을 4바이트 경계에 맞추도록 지정한 위치에서 최대 3개의 0바이트로 패딩하는 경우를 제외하고, 데이터 블록 사이, WOFF2 헤더와 테이블 디렉터리 사이, 또는 마지막 블록이나 테이블 뒤에는 불필요한 데이터가 있어서는 안 된다. 그런 데이터가 있으면 명세를 준수하는 사용자 에이전트는 파일을 무효로 거부해야 한다. 또한 어떤 데이터 블록이나 폰트 테이블의 오프셋과 길이가 겹치는 바이트 범위 또는 파일 끝을 넘는 범위를 나타내면 파일을 무효로 거부해야 한다.

3.1. 데이터 타입

데이터 타입
UInt8 8비트 부호 없는 정수. 
Int16 2의 보수 형식의 16비트 부호 있는 정수. 빅 엔디언으로 저장. 
UInt16 16비트 부호 없는 정수. 빅 엔디언으로 저장. 
UInt32  32비트 부호 없는 정수. 빅 엔디언으로 저장. 
255UInt16 폰트 중간 데이터 저장을 최적화하기 위한 16비트 부호 없는 정수의 가변 길이 부호화. 
UIntBase128 32비트 부호 없는 정수의 가변 길이 부호화. 

255UInt16 데이터 타입

255UInt16은 0부터 65535까지(양 끝 포함)의 부호 없는 정수를 가변 길이로 부호화한다. 이 데이터 타입은 보통 UInt16으로 표현되지만 실제로는 비교적 작은 값을 갖는 다양한 폰트 값의 중간 표현으로 사용하기 위한 것이다. 부호화하는 값에 따라 데이터 필드 길이는 1~3바이트이며, 첫 바이트의 값은 작은 값 자체를 나타내거나 추가 바이트의 형식을 정의하는 코드로 취급된다. 아래의 C 유사 의사 코드는 255UInt16 형식을 읽는 방법을 설명한다:

    Read255UShort( data )
    {
        UInt8 code;
        UInt16 value, value2;

        const oneMoreByteCode1    = 255;
        const oneMoreByteCode2    = 254;
        const wordCode            = 253;
        const lowestUCode         = 253;

        code = data.getNextUInt8();
        if ( code == wordCode ) {
            /* Read two more bytes and concatenate them to form UInt16 value*/
            value = data.getNextUInt8();
            value <<= 8;
            value &= 0xff00;
            value2 = data.getNextUInt8();
            value |= value2 & 0x00ff;
        }
        else if ( code == oneMoreByteCode1 ) {
            value = data.getNextUInt8();
            value = (value + lowestUCode);
        }
        else if ( code == oneMoreByteCode2 ) {
            value = data.getNextUInt8();
            value = (value + lowestUCode*2);
        }
        else {
            value = code;
        }
        return value;
    }

부호화는 유일하지 않다. 예를 들어 값 506은 [255, 253], [254, 0], [253, 1, 250]으로 부호화할 수 있다. 인코더는 이 중 어느 것이든 생성할 수 있으며, 디코더는 모두 허용해야 한다. 인코더는 더 짧은 부호화를 선택하는 것이 바람직하며, 같은 값에는 일관되게 같은 부호화를 선택해야 한다. 이렇게 하면 보통 압축률이 더 좋아지기 때문이다.

UIntBase128 데이터 타입

UIntBase128은 최댓값 232-1까지의 값에 적합한 또 다른 부호 없는 정수의 가변 길이 부호화이다. UIntBase128로 부호화한 수는 마지막을 제외한 모든 바이트의 최상위 비트를 설정하고 마지막 바이트의 최상위 비트는 지운 바이트열이다. 수 자체는 128진수로 각 바이트의 하위 7비트에 부호화한다. 따라서 UIntBase128 디코딩 절차는 다음과 같다. value = 0에서 시작하여 바이트 하나를 읽고 value를 이전 value × 128 + (해당 바이트와 127의 비트 AND)로 설정한다. 바이트의 최상위 비트가 false가 될 때까지 이 단계를 반복한다.

UIntBase128은 예를 들어 선행 0을 사용하여 같은 수를 서로 다른 바이트 수로 나타내는 비최적 부호화가 가능하다. 예를 들어 값 63은 한 바이트 0x3F 또는 두 바이트 이상인 [0x80, 0x3f]로 부호화할 수 있다. 인코더는 이를 허용해서는 안 되며, 가능한 가장 짧은 부호화를 생성해야 한다. 디코더는 선행 0이 있는 UintBase128 값 (바이트 0x80으로 시작하는 값), 5바이트보다 긴 UintBase128 시퀀스, 또는 232-1을 초과하는 UintBase128 값을 만나면 폰트 파일을 거부해야 한다. 아래는 UIntBase128을 읽는 방법을 설명하는 C 유사 의사 코드이다:

    bool ReadUIntBase128( data, *result )
    {
        UInt32 accum = 0;

        for (i = 0; i < 5; i++) {
            UInt8 data_byte = data.getNextUInt8();

            // No leading 0's
            if (i == 0 && data_byte == 0x80) return false;

            // If any of top 7 bits are set then << 7 would overflow
            if (accum & 0xFE000000) return false;

            *accum = (accum << 7) | (data_byte & 0x7F);

            // Spin until most significant bit of data byte is false
            if ((data_byte & 0x80) == 0) {
                *result = accum;
                return true;
            }
        }
        // UIntBase128 sequence exceeds 5 bytes
        return false;
    }

3.2. WOFF2 헤더

WOFF2 헤더의 “totalSfntSize”는 참조용일 뿐이다. 비압축 입력 폰트 파일의 크기를 나타낼 수 있지만, 변환된 'glyf' 및 'loca' 테이블이 있으면 재구성한 테이블의 비압축 크기와 압축을 푼 폰트의 전체 크기는 WOFF2 헤더에 지정한 원래 전체 크기와 크게 다를 수 있다.

4. 폰트 디렉터리

폰트 디렉터리 부분은 입력 파일의 고유한 폰트 테이블마다 하나의 항목을 갖는 테이블 디렉터리로 구성되며, 입력이 폰트 컬렉션인 경우 선택적 컬렉션 디렉터리 테이블을 포함할 수도 있다.

4.1. 테이블 디렉터리 형식

테이블 디렉터리는 아래에서 정의하는 WOFF2 디렉터리 항목의 배열이다. WOFF2 파일 헤더 바로 뒤에 오므로, 헤더에는 이 블록을 가리키는 명시적 오프셋이 없다. 크기는 정확한 내용에 따라 달라지므로 가장 좋은 디코딩 전략은 임의 접근을 시도하는 대신 파일을 스트림으로 처리하는 것이다. 각 항목은 한 폰트 데이터 테이블의 원래 크기와, 추가 변환이 적용된 경우 변환 후 크기를 지정한다. 변환된 테이블은 'flags' 필드로 식별한다. 이 필드는 알려진 테이블 태그(비트 0~5, “알려진 테이블 태그” 참조)와 변환 버전 번호(비트 6 및 7, 아래 설명 참조)를 결합하여 적용된 변환을 정의한다. 테이블 태그와 변환 버전 번호의 조합이 적용된 정확한 변환을 정한다. 현재 정의된 변환의 자세한 내용은 이 명세의 제5절에 있다.

원래 입력 폰트 파일의 테이블 디렉터리 항목이 알파벳 오름차순으로 정렬되는 것과 달리, WOFF2 항목은 테이블을 처리하여 압축 폰트 데이터 스트림에 부호화한 물리적 순서를 정의한다. 폰트 파일의 압축을 풀 때 재구성한 테이블 디렉터리를 정렬하고 재배치하는 것은 디코더의 책임이다.

폰트 디코딩을 단순화하기 위해 인코더는 변환된 테이블을 재배치하여 관련된 'glyf'와 'loca'가 항상 쌍으로 존재하고, 'loca'가 'glyf' 뒤에 오도록 해야 한다. 변환된 'loca' 항목은 재구성에 필요한 크기를 나타내는 자리 표시자이며 데이터 스트림의 바이트를 소비하지 않는다. 따라서 디렉터리에서 'loca' 항목이 변환된 'glyf' 바로 뒤에 오도록 하면 'loca' 재구성 단계를 구현하기 쉬워진다. 이는 'glyf'에 역변환(자세한 내용은 제5.1항 참조)을 적용할 때 수행한다. 테이블 순서 제약의 자세한 내용은 제5.5항을 참조한다.

각 테이블 디렉터리 항목의 형식은 다음과 같다:

flags의 해석은 다음과 같다. 비트 [0..5]는 폰트에 나타날 가능성이 큰 태그를 담은 “알려진 태그” 테이블의 인덱스를 포함한다. 태그가 이 테이블에 없으면 필드 값은 63이다. 비트 6과 7은 각 테이블에 적용한 전처리 변환 버전 번호(0~3)를 나타낸다. 'glyf'와 'loca'를 제외한 모든 폰트 테이블에서 변환 버전 0은 널 변환을 뜻하며, 원래 테이블 데이터를 Brotli 압축기에 직접 전달하여 압축 스트림에 포함한다. 'glyf'와 'loca'에서는 변환 버전 3이 널 변환을 뜻하며, 원래 데이터를 Brotli 압축기에 직접 전달하고 제5.1항 및 제5.3항에서 정의하는 전처리를 적용하지 않는다. 변환된 테이블 형식과 해당 변환 버전 번호의 자세한 내용은 이 명세의 제5절에 있다.

한 테이블에 여러 변환 버전이 정의되어 있으면 인코더는 보통 변환된 테이블 길이가 가장 작아지는 버전을 선택하는 것이 바람직하다. 다만 감소량이 무시할 만큼 작은 경우는 예외이다.

한 태그에 여러 변환 버전이 정의되어 있으면 인코더는 입력에 적용 가능한 정의된 변환 중 어느 것이든 사용할 수 있다. 디코더는 정의된 모든 변환을 허용할 수 있어야 한다. 디코더가 알 수 없는 변환 버전 번호를 지정한 항목을 만나면 폰트 전체를 거부해야 한다. 올바르게 디코딩할 수 없기 때문이다.

알려진 태그로 부호화하는지, 4바이트 태그를 명시적으로 포함하는지는 의미상 차이가 없다. 단지 압축 효율을 높이기 위한 부호화 선택이다. 마찬가지로 특정 4바이트 태그가 “알려진 테이블 태그”에 있는지는 그 태그를 웹 폰트에 포함해야 하는지에 대한 규범적 진술이 아니다. 인코더는 입력 폰트 테이블의 태그가 “알려진 테이블 태그”에 있으면 알려진 테이블 플래그를 사용해야 한다.

알려진 태그 목록에 없는 사용자 정의 태그 (또는 앞으로 정의될 새 표준 태그)를 위한 확장 메커니즘이 미리 정의되어 있다. flags 바이트의 비트 [0..5]가 63(0x3f)이면 그 뒤에 임의의 4바이트 태그 값이 온다. 그렇지 않으면 TableDirectoryEntry에서 tag 필드를 생략하고 flags의 비트 [0..5]를 사용하여 아래의 고정된 “알려진 테이블 태그”에서 태그를 얻는다. 디코더는 사용자 정의 태그로 정의한 항목을, 뒤따르는 태그가 알려진 테이블 태그 중 하나로 식별되더라도 허용할 수 있다.

flags(및 선택적 tag) 뒤에는 하나 또는 두 개의 길이 값이 UIntBase128 부호 없는 정수로 온다. origLength는 비압축 폰트에서 테이블의 길이를 지정한다. 추가 변환을 적용하는 테이블은 변환 후 테이블 길이를 지정하는 transformLength 필드를 포함해야 한다.

Brotli 압축 전에 널이 아닌 변환을 적용한 경우에만 테이블 디렉터리 항목에 transformLength가 존재한다. 변환하지 않은 테이블의 항목에는 이 필드가 없다.

변환 후 길이 필드는 [Brotli]로 압축하기 전 변환된 테이블 크기를 제공한다. 이 필드는 선택 사항이며 일부 테이블에만 존재한다(아래 “압축 데이터 형식” 설명 참조). 변환 후 길이는 압축을 푼 테이블 크기를 결정하는 데 사용할 수 있지만, 변환된 테이블의 원래 길이는 주의해서 다루어야 한다.

변환된 테이블의 재구성은 기능 보존을 보장하지만, 원래 데이터와 다른 이진 결과를 만들 수 있다. 예를 들어 'glyf'의 윤곽점 좌표는 1바이트 또는 2바이트로 부호화할 수 있고, 반복 값은 좌표 스트림에 명시적으로 반복하거나 생략할 수 있다(제어점의 플래그 바이트로 표시). 따라서 윤곽점에는 동일한 렌더링 결과를 내는 여러 표현이 가능하지만, 재구성한 글리프 레코드의 이진 데이터는 원본과 크게 다를 수 있다. 자세한 내용은 ISO “Open Font Format” [OFF] 명세 제5.3.3항을 참조한다.

따라서 변환된 테이블의 origLength는 참조용으로만 취급하고, WOFF2 데이터를 디코딩할 때 메모리 할당을 결정하는 근거로 사용하지 않는 것이 바람직하다.

4.2. 컬렉션 디렉터리 형식

컬렉션 디렉터리는 입력이 컬렉션인 경우, 즉 WOFF2 헤더의 flavor가 0x74746366('ttcf')인 경우에만 존재한다. 존재하면 테이블 디렉터리 바로 뒤에 오며, CollectionHeader와 하나 이상의 CollectionFontEntry 레코드로 구성된다.

입력이 컬렉션이면 테이블 디렉터리에는 테이블을 서로 다른 폰트가 공유하는지와 무관하게 전체 컬렉션의 고유한 테이블마다 항목 하나가 있다. 따라서 WOFF2로 압축한 컬렉션의 디렉터리는 컬렉션 파일에 포함된 모든 폰트의 모든 테이블을 포함한다.

컬렉션 디렉터리는 컬렉션 헤더로 시작하고 컬렉션 폰트 항목 배열이 뒤따른다.

컬렉션 폰트 항목은 각 폰트(개수는 CollectionHeader의 numFonts 필드로 정의)를 지정한다. 각 항목의 형식은 다음과 같다:

255UInt16index[numTables]이 폰트의 각 테이블에 대해 테이블 디렉터리 항목을 식별하는 인덱스(첫 항목의 인덱스는 0).

원래 컬렉션에서 여러 Offset Table이 같은 테이블의 오프셋을 참조하면 그 테이블을 “공유”된 것으로 본다. 인코더는 오프셋으로 정의되는 고유한 테이블마다 TableDirectoryEntry 하나를 출력해야 한다. 여러 폰트가 그 테이블을 공유하는지는 관계없다. 즉 여러 폰트의 해당 Table Record가 같은 오프셋의 공유 테이블을 참조하면 WOFF2 압축 스트림에서 그 테이블 데이터를 중복해서는 안 된다.

입력이 고유한 glyf 및 loca 테이블 여러 개를 포함한 컬렉션이면 변환, 즉 glyf와 loca의 변환을 각 테이블 쌍에 적용해야 한다. glyf 및 loca 공유는 허용되며 권장된다(컬렉션의 주요 이점 중 하나이다). 다만 공유할 수 없는 glyf /loca 쌍이 둘 이상일 수도 있다. 공유하는 경우 인코더는 두 테이블 모두 공유되며 서로 연결된 쌍임을 검증해야 한다(glyf /loca가 여러 쌍 존재하는 경우). 또한 glyf 또는 loca 중 하나만 공유하는 폰트를 포함한 컬렉션을 거부해야 한다.

컬렉션을 처리할 때 인코더는 입력 컬렉션의 내부 폰트 순서를 보존해야 하며, 각 폰트의 CollectionFontEntry에 일치하는 TableDirectoryEntry의 인덱스를 기록해야 한다.

디코더는 동일한 수의 폰트와 해당 Offset Table을 갖는 컬렉션을 복원해야 한다. 출력 컬렉션의 각 폰트의 Offset Table은 입력과 동일한 numTables를 가져야 하며, 원래 Offset Table에 DSIG가 있었다면 하나 적어야 한다. CollectionHeader의 TTC 헤더 버전이 2.0이면 디코더는 출력 TTC 헤더의 {ulDsigTag, ulDsigLength, ulDsigOffset}을 null로 설정하거나 TTC 헤더를 버전 1(0x00010000)로 변환해야 한다.

컬렉션을 처리할 때 디코더는 입력과 같은 내부 폰트 순서를 재현해야 한다. 각 내부 폰트의 테이블은 재배치할 수 있다. 여러 'glyf'/'loca' 쌍이 있는 컬렉션에서는 디코더가 CollectionFontEntry 인덱스를 검사하여 참조된 두 테이블이 서로 쌍인지 확인하고, 맞지 않으면 컬렉션을 거부해야 한다. 쌍에 대한 자세한 내용은 테이블 디렉터리 설명을 참조한다. 명세를 준수하는 사용자 에이전트는 WOFF2 디코더가 생성한 올바른 형식의 폰트 컬렉션을 로드하고 사용할 수 있어야 한다.

5. 압축 데이터 형식

WOFF2 파일의 CompressedFontData 필드는 각 폰트 테이블의 데이터를 WOFF2 테이블 디렉터리에 항목이 나타나는 순서대로 연결한 내용을 담는다. 압축을 푼 스트림의 테이블 항목 사이에는 디렉터리가 정의하지 않은 불필요한 데이터가 있어서는 안 된다. 그런 데이터가 있으면 명세를 준수하는 사용자 에이전트는 파일을 무효로 거부해야 한다. CompressedFontData 스트림은 Brotli 압축 알고리즘 [Brotli]으로 압축해야 한다. 어떤 이유로든 데이터 블록의 압축 해제가 실패하면 WOFF2 파일은 무효이며 로드해서는 안 된다.

WOFF2 테이블 데이터 디코딩은 CompressedFontData의 바이트 수준 압축을 풀어 “테이블 데이터 블록”을 얻은 뒤, 아래의 추가 디코딩을 적용하는 과정으로 규정할 수 있다. 구현은 단계를 결합하거나 일부를 점진적 또는 스트리밍 방식으로 수행할 수 있지만, 결과는 여기서 규정하는 순차 과정과 일치해야 한다.

일부 테이블(각 태그로 식별되는 glyf, loca, hmtx 등)에는 추가 변환을 적용한다. 변환하지 않으면 데이터가 그대로 압축 스트림에 나타나며 테이블 데이터 블록에서 origLength 바이트를 차지한다. 변환 여부와 버전은 flags의 최상위 두 비트로 정의한다(제4.1항 참조). 변환하는 데이터는 아래에 지정한 변환으로 추가 처리해야 하며, 이 경우 transformLength바이트를 차지한다.

압축을 풀고 재구성한 테이블 데이터는 [OFF] 명세의 형식으로 저장해야 한다. 각 재구성 항목은 유효한 checkSum을 포함해야 하며, 디코더는 각 테이블의 checkSum을 다시 계산해야 한다. 또한 glyf와 loca에 수정을 수반하는 변환을 적용하므로 디코더는 전체 폰트의 checkSumAdjustment를 다시 계산하고 갱신한 값을 head에 저장해야 한다.

변환된 테이블의 존재 여부를 알려진 테이블 플래그 값만으로 판단하지 않는 것이 바람직하다. 예를 들어 glyf는 flag = 10이고 tag가 없거나, flag = 63이고 'glyf' 태그가 뒤따르는 형태로 표현할 수 있다. 변환 버전을 정의하는 flags 값과 태그의 조합으로 적용된 변환을 판단해야 한다.

디렉터리의 origLength (비변환 테이블)와 transformLength(변환 테이블)의 합은 [Brotli]로 압축을 푼 데이터 블록 크기와 같아야 한다. 압축을 푼 크기가 위에서 설명한 디렉터리의 길이 합과 일치하지 않으면 WOFF2 파일을 로드해서는 안 된다.

현재 WOFF2에서는 세 종류의 테이블에 변환을 적용할 수 있다: 윤곽 데이터의 glyf, loca （glyf 내 각 글리프의 오프셋）, 그리고 수평 메트릭의 hmtx이다. 폰트에 해당 테이블이 있을 때 적용한다. 저작 도구는 제5.3항과 제5.5항의 추가 제약을 고려하여 적용 가능한 변환을 사용할 수 있다. glyf 변환은 제5.1항, loca 변환은 제5.3항, hmtx 변환은 제5.4항에서 규정한다.

CFF 테이블 처리와 서브루틴 펼치기.

CFF 윤곽을 갖는 OpenType 폰트 대부분은 더 작은 저장을 위해 CFF 데이터를 서브루틴화한다. WOFF2 개발 및 평가 실험에서는 인코딩 전에 CFF 서브루틴을 펼치면 Brotli가 더 효율적으로 작동하고 WOFF2 압축률이 향상되어 압축 크기가 평균 5~10% 감소하는 것으로 나타났다. 하지만 CFF 서브루틴을 펼치면 동시에 출력 파일 크기가 약 10% 증가한다.

CFF 전처리/서브루틴 펼치기는 WOFF2 인코딩 전의 외부 단계이므로 이 명세의 범위에 포함하지 않는다. 폰트 제작자는 제작 과정을 최적화하여 출력 CFF 크기를 늘리는 대신 압축 크기를 줄여 웹 전송을 빠르게 하거나(렌더링 성능도 향상됨), 서브루틴화된 데이터를 유지하여 입출력 크기를 최소화할 수 있다.

WOFF 2.0 변환은 SFNT에 내재된 중복을 줄이거나 제거하고 폰트 데이터 스트림을 재구성하여 엔트로피 부호화를 효율화한다. 재구성된 데이터는 입력 폰트의 기능을 그대로 보존하지만, 'glyf' 윤곽점 좌표의 최적화 수준이나 'loca' 오프셋 계산의 차이 등 부호화의 차이가 있을 수 있어 디코더마다 출력이 입력과 비트 단위로 일치하지 않을 수 있다. 입력의 테이블은 인코딩 과정에서 재배치되거나, 디코더가 [OFF]의 권장 순서로 재배치할 수도 있다 – 그 결과 내용이 바뀌지 않아도 오프셋은 바뀔 수 있다. 인코딩 전후 데이터 구조의 이진 차이는 최적화와 재배치에 따른 사소한 차이라도 기존 DSIG를 무효화한다. 따라서 명세를 준수하는 인코더는 입력 폰트 데이터에서 DSIG 테이블을 제거해야 하며, 그 후 변환과 엔트로피 부호화를 적용한다.

WOFF 2.0 인코더는 또한 head의 flags 필드 비트 11을 설정해야 한다 ([OFF] 참조). 이는 재생성한 폰트에 무손실 수정 변환을 적용했음을 나타낸다.

5.1. 변환된 glyf 테이블 형식

glyf는 WOFF2에서 두 형식 중 하나로 표현되며, 변환 버전(디렉터리 플래그 비트에 부호화, 제4.1항 참조)으로 정한다. 버전 3은 널 변환으로 glyf 내용을 원래의 수정되지 않은 형식으로 표현한다. 아래의 버전 0은 선택 사항이며 glyf 데이터의 일부 중복을 제거하는 데 사용할 수 있다.

이 항의 glyf 변환 버전 0은 (디렉터리 플래그로 정의, 제4.1항 참조) 중복 정보를 줄이고 실제 TrueType 글리프 윤곽을 효율적으로 부호화하기 위한 것이다. 이 수정된 변환은 MicroType Express [MTX]의 유사한 변환에 기초한다. MTX 참조는 정보성이다. 수정된 변환의 자세한 내용은 아래에 규정하며 이 절은 규범적이다.

glyf 변환은 각 글리프의 기능과 렌더링 충실도를 보존하지만, 원래 폰트와 이진 데이터가 일치하지 않는 새 글리프 레코드를 만들 가능성이 크다. [OFF] 제5.3.3항의 규칙에 따르면 한 레코드에 여러 유효한 재구성이 가능하다. 상황과 재구성된 glyf 데이터의 최적화 수준에 따라 재구성 크기는 입력의 원래 glyf보다 크거나 작거나 같을 수 있다. 이 명세와 [OFF] 모두 특정 최적화를 의무화하지 않는다. 따라서 WOFF2 디코더 구현은 글리프 레코드를 재구성할 때 충분한 메모리를 할당할 책임이 있다 – 원래 glyf 크기를 나타내는, 변환된 glyf의 origLength는 참조값으로만 사용할 수 있다.

글리프 레코드 재구성의 구현 세부 사항이나 재구성한 glyf 데이터의 최적화 수준과 무관하게, 사용자 에이전트는 재구성한 glyf 크기가 WOFF2 디렉터리의 glyf 항목에 부호화된 origLength 와 다르다는 이유로 올바르게 디코딩한 폰트를 거부해서는 안 된다.

압축 효율을 높이기 위해 glyf를 여러 하위 스트림으로 나누어 같은 종류의 데이터를 묶는다. 변환된 테이블은 각 하위 스트림의 크기를 나타내는 필드와 순서대로 이어지는 하위 스트림으로 구성된다. 디코딩 시 역변환하여 각 하위 스트림의 데이터를 다시 결합하고 원래 glyf의 각 항목에 대한 완전한 레코드를 만든다.

이 형식은 특히 유효하거나 무효인 데이터의 구분을 포함한 디코딩 과정을 설명하는 것이 가장 적합하다. 또한 이 형식은 특정 바이트열이 아니라 의미 수준에서 디코딩 결과를 규정한다.

변환된 glyf에는 bboxBitmap이 있어 각 글리프의 경계 상자를 명시적으로 부호화했는지, 좌표에서 추론할지를 나타낸다. 인코더와 디코더 모두 그 상태를 결정하는 계산을 수행해야 한다. 각 단순 글리프에 대해 인코더는 모든 윤곽점(곡선 위와 밖의 점 모두)으로 xMin, yMin, xMax, yMax를 계산하고 부호화된 경계 상자 정보와 비교해야 한다. 일치하면 경계 상자 정보를 생략해야 한다. 그렇지 않으면 계산한 값이 폰트의 값과 다르므로 해당 bboxBitmap 플래그를 설정하고 원래 값을 bboxStream에 기록해야 한다. 윤곽 수가 0인 레코드에서는 모든 경계 상자 값이 0인지 확인하고, 아니면 입력 폰트를 무효로 거부해야 한다. 빈 글리프 또는 윤곽 수 0인 글리프에서는 해당 bboxBitmap 플래그를 항상 지워야 한다. 복합 글리프에서는 해당 bboxBitmap 플래그를 항상 설정하고 원래 값을 bboxStream에 기록해야 한다.

경계 상자를 추론할 경우 디코더도 유사한 계산을 수행해야 한다. 글리프에 해당하는 bboxBitmap 비트가 설정되지 않았으면 디코딩 시 모든 윤곽점 좌표로 xMin, yMin, xMax, yMax를 계산해야 한다. bboxBitmap의 전체 바이트 수는 4 * floor((numGlyphs + 31) / 32)이다. 비트는 글리프 0이 첫 바이트의 최상위, 글리프 7이 첫 바이트의 최하위, 글리프 8이 둘째 바이트의 최상위에 대응하도록 밀집시킨다. 비트 1은 명시적 경계 상자를 나타낸다.

변환된 glyf를 읽으면 디코딩은 글리프별로 반복한다. 각 글리프에 대해 변환된 glyf가 참조하는 각 스트림에서 0바이트 이상을 읽는다. 재구성할 때는 각 글리프의 새 테이블 내 오프셋도 저장한다. 이 데이터 전체가 재구성된 loca의 내용이 된다 (자세한 내용은 아래 제5.3항의 loca 재구성 설명 참조).

글리프 레코드 재구성

재구성은 다음 단계로 부호화된 글리프 유형(단순, 복합, 빈 글리프)을 결정하면서 시작한다:

nContour에서 Int16을 읽어 재구성할 TrueType의 numberOfContours 필드에 저장한다. 해석은 TrueType과 같으며, 0이면 빈 글리프, 양수이면 단순 글리프이고 값은 윤곽 수, -1(0xffff)이면 복합 글리프이다.

빈 글리프 디코딩

빈 글리프(nContour = 0) 재구성은 간단하다. 레코드 수를 늘리고 loca에 loca[n] = loca[n-1]인 항목을 만든다. bboxBitmap이 경계 상자 값이 bboxStream에 명시적으로 있음을 나타내면 디코더는 WOFF2 파일을 무효로 거부해야 한다.

단순 글리프 디코딩

단순 글리프(nContour > 0)는 다음과 같이 계속한다:

  1. nPoints에서 numberOfContours개의 255UInt16을 읽는다. 각 값은 해당 윤곽의 점 수이다. 누적 합을 계산하고 1을 빼서 endPtsOfContours[]로 변환한다. 예를 들어 [2, 4]이면 endPtsOfContours는 [1, 5]이다. 또한 읽은 값의 합이 글리프의 전체 점 수 nPoints이다. 이 예에서 nPoints는 6이다.
  2. flags에서 nPoints개의 UInt8을 읽는다. 각각은 재구성할 윤곽의 한 점에 대응한다. 플래그 바이트의 해석은 제5.2항에서 자세히 설명한다.
  3. 각 점에 대해(nPoints회) glyph에서 좌표 바이트를 읽는다. 개수는 앞 단계의 플래그 바이트로 정하며, (flag < 0x7f)가 0~83이면 1바이트, 84~119이면 2바이트, 120~123이면 3바이트, 124~127이면 4바이트이다(각 범위 양 끝 포함). 제5.2항에 따라 디코딩하여 좌표의 delta-x와 delta-y를 재구성한다. 표준 TrueType 글리프 부호화로 이 값을 재구성한 글리프에 저장한다. [OFF] 제5.3.3항을 참조한다.
  4. glyph에서 255UInt16 하나를 읽는다. 이는 명령어 바이트 수인 instructionLength이다.
  5. instructionStream에서 instructionLength바이트를 읽어 재구성한 글리프에 명령어로 저장한다.

optionFlags의 비트 0은 추가 overlapSimpleBitmap[]의 존재를 나타낸다. 다른 비트는 예약되어 있으며 지우는 것이 바람직하다. 입력의 모든 단순 글리프에서 OVERLAP_SIMPLE이 0이면 인코더는 optionFlags의 비트 0을 지우고 overlapSimpleBitmap[]를 생략해야 한다. 적어도 한 단순 글리프에서 플래그 비트 6이 설정되어 있으면 인코더는 optionFlags의 비트 0을 1로 설정하고 추가 overlapSimpleBitmap[]를 만들어야 한다. 해당 비트는 입력의 각 단순 글리프의 플래그 비트 6 값으로 설정해야 한다.

디코더는 optionFlags의 비트 0을 검사해야 한다. 이를 통해 추가 overlapSimpleBitmap[]가 변환된 glyf에 포함되는지 판단한다. 없다면 단순 글리프 플래그를 재구성할 때 디코더는 모든 OVERLAP_SIMPLE을 0으로 설정해야 한다. 존재한다면 디코더는 해당 비트로 OVERLAP_SIMPLE을 재구성하고, 해당 값을 출력의 각 단순 글리프의 첫 플래그 바이트 비트 6으로 설정해야 한다.

복합 글리프 디코딩

복합 글리프(nContour == -1)는 다음 단계로 위의 1~5를 대체한다:

1a. compositeStream에서 UInt16을 읽고 TrueType 명세의 구성 요소 플래그 워드로 해석한다. 플래그에 따라 4~14바이트의 추가 인수가 있으며, 글리프 인덱스, arg1, arg2, 선택적 스케일 또는 아핀 행렬로 해석한다.

2a. 단계 1a에서 정한 수의 인수 바이트를 composite에서 읽어 글리프에 저장한다. 1a의 플래그에서 FLAG_MORE_COMPONENTS(비트 5)가 설정되어 있으면 1a로 돌아간다.

3a. 어떤 플래그든 FLAG_WE_HAVE_INSTRUCTIONS (비트 8)가 설정되어 있으면 glyph에서 명령어를 읽어 위의 단계 4, 5와 같은 과정으로 재구성한 글리프에 저장한다.

경계 상자 디코딩

단순 및 복합 글리프 모두 경계 상자 비트 벡터의 해당 비트가 설정되어 있으면 bbox에서 Int16 네 개를 추가로 읽어 각각 xMin, yMin, xMax, yMax로 해석하고 재구성한 글리프의 해당 필드에 기록한다. 단순 글리프에서 해당 비트가 설정되지 않았으면 윤곽의 x, y 좌표의 최솟값과 최댓값을 계산하여 경계 상자를 추론하고 저장한다.

복합 글리프는 명시적 경계 상자를 가져야 한다. 계산이 더 복잡하고, 복합 글리프 명령어와 각 구성 요소의 스케일을 고려하여 구성 요소 참조를 해석해야 하므로 순수 스트리밍 디코딩과 충돌하기 때문이다. 디코더는 복합 글리프 레코드에 경계 상자 정보가 있는지 검사해야 하며, 그 데이터가 없는 폰트를 로드해서는 안 된다.

5.2. 가변 길이 X·Y 좌표 디코딩

단순 글리프 구조는 글리프를 구성하는 모든 윤곽을 곡선 위와 밖의 좌표점 시퀀스로 정의한다. 좌표는 델타 값으로 부호화하여 이전 점과 현재 점의 해당 X, Y 좌표 사이의 증분을 나타낸다. 각 윤곽의 첫 점은 (0,0)을 기준으로 한다. 데이터 크기를 최소화하기 위해 각 점을 (flag, xCoordinate, yCoordinate) 삼중항으로 표현한다. 플래그는 별도 스트림에, 좌표는 글리프 데이터 스트림 안에 가변 길이로 부호화하며 점마다 총 2~5바이트를 사용한다.

플래그 최상위 비트는 점이 곡선 위인지 밖인지 나타낸다 (최상위가 0이면 곡선 위이다). 나머지 7비트는 X, Y의 형식을 정하고 128가지 인덱스 조합을 지정한다. 이 조합은 TrueType 데이터의 일반적인 통계 분포를 고려하여 배정한다. 좌표를 니블로 기록하면 (좌표당 4 또는 12비트) 비트를 밀집시키고, X의 최상위 비트부터 시작한 뒤 Y를 최상위부터 배치한다. 이로써 데이터 크기가 크게 줄며, 같은 종류의 값(플래그, 좌표)을 별도의 연속 스트림으로 묶으면 두 번째 단계의 엔트로피 부호화도 효율화된다.

128개 인덱스 값 각각은 다음 속성을 정의한다. 자세한 내용은 아래 표에 있다:

  • 바이트 수(이 좌표 집합의 전체 바이트 수. flag의 1바이트 포함).
  • X 좌표를 나타내는 비트 수(X bits).
  • Y 좌표를 나타내는 비트 수(Y bits).
  • X bits 값에 더하는 추가 증분(delta X).
  • Y bits 값에 더하는 추가 증분(delta Y).
  • X 좌표값의 부호(X sign).
  • Y 좌표값의 부호(Y sign).

“Byte Count”는 삼중항 (flag, xCoordinate, yCoordinate)의 전체 크기를 나타내며, 별도 스트림의 ‘flag’도 포함한다.

5.3. 변환된 loca 테이블 형식

loca는 WOFF2에서 두 형식 중 하나로 표현되며, 변환 버전(디렉터리 플래그 비트, 제4.1항 참조)으로 정한다. 버전 3은 널 변환으로 loca를 원래의 수정되지 않은 형식으로 표현한다. 버전 0은 선택 사항이지만 loca에는 glyf를 변환하는 경우 반드시 적용해야 한다. 즉 glyf와 loca 모두 변환된 형식으로 존재하거나 모두 널 변환을 적용해야 한다.

loca 변환 버전 0은 (디렉터리 플래그로 정의, 제4.1항 참조) 아래와 같이 규정한다.

변환된 loca의 transformLength는 항상 0이어야 한다. origLength는 적절한 크기여야 한다(numGlyphs+1에 글리프당 크기를 곱한다. indexFormat은 제5.1항 변환된 glyf 테이블 형식에서 정의하며, 0이면 글리프당 2바이트, 아니면 4바이트이다). 변환된 loca의 transformLength가 0이 아니거나 origLength가 위의 계산값과 다르면 디코더는 WOFF2를 무효로 거부해야 한다.

loca는 glyf를 디코딩할 때 재구성해야 한다. loca 재구성 절차는 제5.1항에서 변환된 glyf 디코딩의 일부로 규정한다. 재구성한 레코드에 대해 디코더는 각 글리프의 오프셋을 indexFormat 필드 (변환된 glyf 내)가 나타내는 형식으로 저장해야 한다.

5.4. 변환된 hmtx 테이블 형식

hmtx는 WOFF2에서 두 형식 중 하나로 표현되며, 변환 버전(디렉터리 플래그 비트에 부호화, 제4.1항 참조)으로 정한다. 버전 0은 널 변환으로 hmtx 내용을 원래의 수정되지 않은 형식으로 표현한다. 아래의 버전 1은 선택 사항이며 hmtx 데이터의 일부 중복을 제거하는 데 사용할 수 있다.

변환 버전 1은 TrueType 글리프의 중복을 이용한다. 권장 사항을 따른 윤곽에서는 왼쪽 사이드 베어링이 경계 상자의 xMin과 같을 가능성이 크다. hmtx 형식은 제5.2.4항에서 규정한다 [OFF]. 비례 및 고정폭 글리프 구간의 왼쪽 사이드 베어링 정보 배열 두 개를 포함한다. 조건을 만족하면 각 배열을 입력에서 제거하고 경계 상자 정보로 재구성할 수 있다.

UInt16 advanceWidth[] 비례 글리프 수평 메트릭의 advanceWidth를 나타내는 Uint16 스트림. 크기는 numOfHMetrics(hhea 에서 정의)와 같다.
Int16 lsb[] 비례 글리프 수평 메트릭의 왼쪽 사이드 베어링을 나타내는 Int16 스트림. Flags의 비트 0이 설정되지 않은 경우에만 존재한다. 크기는 numOfHMetrics(hhea에서 정의)와 같다.
Int16 leftSideBearing[] 고정폭 글리프 수평 메트릭의 왼쪽 사이드 베어링을 나타내는 Int16 스트림. Flags의 비트 1이 설정되지 않은 경우에만 존재한다. 크기는 (numGlyphs - numOfHMetrics)와 같다.

이 항의 변환 버전 1은 선택 사항이며 입력이 TrueType 형식(glyf를 포함)이고, hmtx의 비례 또는 고정폭 글리프 구간에서 각 leftSideBearing이 glyf의 해당 xMin과 정확히 일치할 때만 사용할 수 있다. 빈 글리프의 leftSideBearing은 특별히 검사해야 하며 hmtx 변환은 그 값이 0일 때만 적용할 수 있다.

hmtx 변환이 적용 가능하고 사용하려면 인코더는 각 글리프의 leftSideBearing이 경계 상자의 xMin과 일치하는지 (빈 글리프이면 leftSideBearing == 0) 검사해야 하며, 컬렉션에서는 대응하는 모든 glyf와 hmtx 쌍에 대해 검사해야 한다. 비례 또는 고정폭 글리프 구간에서 조건을 만족하면 인코더는 hmtx 변환 버전을 1로 설정하고, hmtx에서 해당 배열을 제거하며 해당 Flags를 설정해야 한다. 공유 hmtx가 있는 컬렉션에서는 xMin과 lsftSideBearing의 일치를 공유 hmtx와 각 glyf의 모든 조합에서 검사해야 하며, 불일치하면 hmtx 변환을 적용해서는 안 된다.

디렉터리가 hmtx 변환을 나타내면 사용자 에이전트는 Flags를 검사하고 무효이면 WOFF2를 거부해야 한다. 디코더는 글리프 경계 상자의 xMin으로 lsb[] 및/또는 leftSideBearing[]를 재구성해야 하며, 그 정보는 glyf에서 얻는다.

5.5. 테이블 순서 제약

유효한 WOFF2에 대한 다음 제약은 메모리 효율적인 전송과 디코딩을 지원하기 위한 것이다.

loca는 glyf 뒤에 있어야 한다. 단독 폰트이면 디렉터리에서 glyf와 loca 사이에 다른 테이블을 넣을 수 있다. 컬렉션이면 각 loca는 해당 glyf 바로 뒤에 있어야 한다. 예를 들어 'cmap', 'glyf', 'hhea', 'hmtx', 'loca', 'maxp' ...는 단독 폰트에 허용되지만, 컬렉션은 glyf / loca를 쌍으로 묶어야 한다. 각 쌍이 연속 블록을 이룰 필요는 없으므로 'cmap', 'glyf', 'loca', 'hhea', 'hmtx', 'glyf', 'loca', 'maxp', 'post' ...는 허용된다. loca의 추가 제약은 제5.3항에 있다.

6. 확장 메타데이터 블록

WOFF2는 확장 메타데이터 블록을 포함할 수 있다. 해석은 [WOFF 1]과 완전히 같다.

다만 WOFF 1은 메타데이터를 zlib으로 압축하지만, WOFF2에서는 메타데이터가 있으면 [Brotli]로 압축하여 별도 스트림으로 저장해야 한다. 이는 구현에 필요한 바이트 수준 압축 알고리즘의 수를 최소화하고, 대부분의 경우 Brotli가 zlib보다 높은 압축률을 얻을 것으로 예상되기 때문이다.

메타데이터 블록은 압축 폰트 스트림 바로 뒤에 있어야 한다. 시작은 항상 4바이트 경계에 정렬해야 한다. 확장 메타데이터가 있으면 필요에 따라 압축 블록 끝에 최대 세 개의 0바이트를 채워 경계를 맞춰야 한다. 메타데이터가 마지막 블록이면 그 뒤에 추가 패딩을 두지 않는 것이 바람직하다.

7. 비공개 데이터 블록

WOFF2는 임의의 데이터 블록을 포함할 수 있다. 제작자는 원하는 정보를 담을 수 있다. 이 내용은 사용자 에이전트의 폰트 사용이나 로드 동작에 영향을 주어서는 안 된다. 내용에 대해 가정하지 않는 것이 바람직하며, ASCII, Unicode, 공급업체 고유의 이진 데이터 등이 있을 수 있고 압축이나 암호화도 가능하지만 공개된 형식은 없다. 명세를 준수하는 사용자 에이전트는 구조에 대해 아무것도 가정하지 않는다. 내용을 이해하는 것은 그 블록을 담당하는 폰트 개발자나 공급업체뿐이라고 예상한다.

비공개 데이터가 있으면 마지막 블록이어야 하며, 압축 폰트 스트림과 확장 메타데이터(있다면) 뒤에 와야 한다. 비공개 데이터는 4바이트 경계에서 시작해야 하며, 필요하면 앞 블록 뒤에 최대 세 개의 0바이트를 패딩으로 삽입한다. 비공개 데이터의 끝은 WOFF2 파일의 끝과 일치해야 한다.
