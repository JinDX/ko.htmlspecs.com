요약

이 명세서는 포맷을 확장하고 디자인 토큰을 여러 컨텍스트(예: “라이트 모드”와 “다크 모드” 색상 테마 등)에서 사용할 수 있는 방법을 설명합니다.

1. 소개

이 절은 비규범적입니다.

디자인 토큰을 사용하는 소비자는 서로 다른 컨텍스트에서 적용되는 대체 값을 표현해야 하는 경우가 자주 있습니다. 다음은 그 예시이며 이에 국한되지 않습니다:

  • 테마: 라이트 모드, 다크 모드, 고대비 색상 모드 등
  • 사이징: 모바일(소), 태블릿(중), 데스크톱(대)
  • 접근성 모드: 모션 감소, 색맹 등

그러나 이러한 대체 컨텍스트는 조합 폭발에 취약하여 저장 및 관리가 번거로워질 수 있습니다.

이 포맷은 모든 컨텍스트 전반에 걸쳐 토큰의 반복 값을 중복 제거하고, 컨텍스트의 모든 순열을 열거하는 메커니즘을 설명합니다.

2. 용어

2.1 직교성

이 절은 비규범적입니다.

각각 상호 배타적인 토큰에서 작동하는 두 개 이상의 컨텍스트를 설명하는 특성으로, 즉 서로 겹치지 않습니다. 수정자는 MAY 직교일 수 있으나, 필수는 아닙니다.

가능한 한 수정자를 직교적으로 만드는 것은 인지 부하를 줄이고 사용자 오류를 감소시킵니다.

Example 1: 비직교 수정자

다음과 같은 수정자가 주어졌을 때:

  1. theme 수정자는 light와 dark 값을 가집니다. 해당 값들 중 color.button 토큰에 대한 값을 제공합니다.
  2. brand 수정자는 brandA와 brandB 값을 가집니다. 해당 값들 중 color.button 토큰에 대한 값을 제공합니다.

두 수정자 모두 color.button 토큰에 값을 제공하므로, 이는 배열 순서가 최종 값을 결정함을 의미하며, 즉 비직교입니다.

2.2 순열

순열은 리졸버 문서의 가능한 단일 순열입니다. 순열은 input과 1:1로 매핑되지만, “input”은 사용된 modifier 컨텍스트를 강조하는 반면 “순열”은 최종 토큰 집합을 강조합니다.

3. 파일타입

3.1 포맷

리졸버 문서는 표준 JSON 구문([RFC8259])을 MUST 사용해야 합니다.

도구는 문서를 정상 JSON으로 변환해도 토큰 값에 영향을 주지 않는 한 JSONC 또는 JSON5와 같은 확장을 MAY 지원할 수 있습니다.

3.2 파일 확장자

사용자는 리졸버 문서의 이름을 지정할 때 .resolver.json 파일 확장자를 SHOULD 사용해야 합니다.

3.3 MIME 타입

HTTP를 통해 리졸버 문서를 전송할 때, 사용자는 Content-Type 헤더([RFC1341])에서 기대되는 application/json MIME 타입([RFC6838])을 SHOULD 사용해야 합니다. 사용자는 사용자 정의 또는 예상치 못한 MIME 타입을 SHOULD NOT 사용해야 합니다.

4. 문법

4.1 최상위 속성

리졸버 문서는 최상위 레벨에서 다음 속성을 포함합니다:

Name Type Required Description
name string 문서에 대한 짧고 사람이 읽을 수 있는 이름.
version YYYY.MM Y 버전. 2025.10이어야 합니다.
description string 이 문서에 대한 사람이 읽을 수 있는 설명.
sets Map[string, Set] 세트의 정의.
modifiers Map[`string, Modifier] 수정자의 정의.
resolutionOrder (ReferenceObject | Set | Modifier)[] Y 세트와 수정자의 해상(적용) 순서.

4.1.1 이름

문서는 최상위 레벨에서 사람이 읽을 수 있는 name을 제공할 수 있습니다 MAY. 이는 파일명만으로 충분하지 않은 경우 하나의 리졸버 문서를 다른 문서와 구분하는 데 도움이 됩니다.

4.1.2 버전

문서는 최상위 레벨에서 버전을 제공해야 하며 MUST, 이는 2025.10이어야 합니다 MUST. 이는 향후 변경 사항이 도입되어 파괴적 변경(breaking changes)이 발생하는 경우를 대비해 예약되어 있습니다.

4.1.3 설명

문서는 최상위 레벨에서 description을 제공할 수 있습니다 MAY. 이는 name에 존재하지 않는 추가 설명이나 컨텍스트를 추가하는 데 사용될 수 있습니다.

4.1.4 세트

세트는 DTCG 포맷의 디자인 토큰 모음입니다. 세트는 sources 배열을 포함해야 하며 MUST, 직접 선언된 토큰 또는 디자인 토큰을 포함한 JSON 파일을 가리키는 reference object, 또는 이 둘의 조합이어야 합니다.

세트는 세트의 목적을 설명하는 description을 포함할 수 있습니다 MAY.

배열이 여러 소스를 선언하는 경우, 배열 순서대로 병합되며, 동일 토큰이 여러 번 선언되면 배열의 마지막 항목이 최종 값이 됩니다. 도구는 배열 순서를 MUST 존중해야 합니다.

Example 2: 원격 파일과 인라인 토큰으로 구성된 세트 
{
  "sets": {
    "color": {
      "description": "Color tokens",
      "sources": [
        { "$ref": "base/legacy.json" },
        { "$ref": "base/foundation.json" },
        { "$ref": "base/color-ramps.json" },
        { "$ref": "base/semantic.json" }
      ]
    },
    "size": {
      "description": "Dimension, margin, and spacing tokens",
      "sources": [
        {
          "space": {
            "base": {
              "100": {
                "$type": "dimension",
                "$value": { "value": 2, "unit": "rem" }
              }
            }
          }
        }
      ]
    }
  }
}

4.1.5 수정자

수정자는 set과 유사하지만, contexts 맵을 통해 조건부 포함을 허용합니다.

4.1.5.1 컨텍스트

수정자는 string 값을 토큰 소스 배열에 매핑하는 contexts 맵을 선언해야 합니다 MUST. 토큰 소스 배열은 ReferenceObject, 인라인 토큰, 또는 이 둘의 조합이어야 합니다 MUST.

수정자는 두 개 이상의 contexts를 갖는 것이 바람직합니다 SHOULD. 하나만 있으면 set과 동일하므로, 수정자는 빈 contexts 맵을 가져서는 안 됩니다 MUST NOT. 도구는 컨텍스트가 1개뿐인 수정자에 대해 오류를 발생시키는 것이 바람직합니다 SHOULD. 컨텍스트가 0개인 수정자에 대해서는 도구가 오류를 발생시켜야 합니다 MUST.

sets와 마찬가지로, 배열 순서는 반드시 존중되어야 하며 MUST, 충돌 시 배열에서 토큰의 마지막 발생이 최종 값을 생성합니다.

수정자는 컨텍스트 값 내부에서 set을 참조할 수 있습니다 MAY. 그러나 수정자는 다른 수정자를 참조해서는 안 되며 MUST NOT, 동일 수정자 내의 다른 컨텍스트조차도 참조해서는 안 됩니다.

Example 3: 색상 테마 수정자 
{
  "modifiers": {
    "theme": {
      "description": "Color theme",
      "contexts": {
        "light": [{ "$ref": "theme/light.json" }],
        "lightHighContrast": [
          { "$ref": "theme/light.json" },
          { "$ref": "theme/dark-high-contrast.json" }
        ],
        "dark": [{ "$ref": "theme/dark.json" }],
        "darkHighContrast": [
          { "$ref": "theme/dark.json" },
          { "$ref": "theme/dark-high-contrast.json" }
        ]
      },
      "default": "light"
    }
  }
}
Example 4: 세트를 참조하는 수정자

수정자는 컨텍스트 값 내부에서 set을 참조할 수 있습니다 MAY. 이는 동일 배열에 sources가 인라인되는 것과 동일합니다. 예를 들어, 다음은: 

{
  "sets": {
    "baseSize": {
      "sources": [{ "$ref": "size/base.json" }]
    }
  },
  "modifiers": {
    "size": {
      "description": "Application size",
      "contexts": {
        "small": [
          { "$ref": "#/sets/baseSize" },
          { "$ref": "device/mobile.json" },
          { "$ref": "typography/mobile.json" }
        ],
        "medium": [
          { "$ref": "#/sets/baseSize" },
          { "$ref": "device/tablet.json" },
          { "$ref": "typography/base.json" }
        ],
        "large": [
          { "$ref": "#/sets/baseSize" },
          { "$ref": "device/desktop.json" },
          { "$ref": "typography/base.json" }
        ]
      }
    }
  }
}

다음과 동일합니다:

{
  "sets": {
    "baseSize": {
      // …
    }
  },
  "modifiers": {
    "size": {
      "description": "Application size",
      "contexts": {
        "small": [
          { "$ref": "size/base.json" },
          { "$ref": "device/mobile.json" },
          { "$ref": "typography/mobile.json" }
        ],
        "medium": [
          { "$ref": "size/base.json" },
          { "$ref": "device/tablet.json" },
          { "$ref": "typography/base.json" }
        ],
        "large": [
          { "$ref": "size/base.json" },
          { "$ref": "device/desktop.json" },
          { "$ref": "typography/base.json" }
        ]
      }
    }
  }
}
4.1.5.2 설명

수정자는 사람이 읽을 수 있는 description을 선언할 수 있습니다 MAY.

4.1.5.3 기본값

수정자는 default 값을 선언할 수 있으며 MAY, 이는 contexts의 키 중 하나와 일치해야 합니다 MUST. 값이 contexts에 존재하지 않는 경우 도구는 오류를 발생시켜야 합니다 MUST.

4.1.5.4 해상도 수

문서가 생성할 수 있는 가능한 resolutions의 수는 모든 수정자에 걸친 contexts의 곱으로 예측할 수 있습니다.

Example 5: 해상도 계산
  • 각각 2개의 contexts를 가진 2개의 수정자가 있는 문서는 2 × 2, 즉 4개의 해상도를 생성할 수 있습니다.
  • 4, 3, 2개의 contexts를 각각 가진 3개의 수정자가 있는 문서는 4 × 3 × 2, 즉 24개의 해상도를 생성할 수 있습니다.

4.1.6 해상도 순서

resolutionOrder 키는 최종 토큰 결과를 생성하도록 순서가 지정된 sets 및 modifiers의 배열입니다. 순서는 중요하며, 충돌 시 배열 후반의 토큰이 이전의 토큰을 재정의합니다.

Example 6: 세트와 수정자 함께 구성하기

여러 세트와 수정자로 구성된 resolutionOrder가 주어졌을 때:

{
  "sets": {
    "size": {
      "sources": [{ "$ref": "foundation/size.json" }]
    },
    "typography": {
      "sources": [{ "$ref": "foundation/typography.json" }]
    },
    "animation": {
      "sources": [{ "$ref": "foundation/animation.json" }]
    }
  },
  "modifiers": {
    "theme": {
      "description": "Color theme",
      "contexts": {
        "light": [{ "$ref": "theme/light.json" }],
        "lightHighContrast": [
          { "$ref": "theme/light.json" },
          { "$ref": "theme/dark-high-contrast.json" }
        ],
        "dark": [{ "$ref": "theme/dark.json" }],
        "darkHighContrast": [
          { "$ref": "theme/dark.json" },
          { "$ref": "theme/dark-high-contrast.json" }
        ]
      },
      "default": "light"
    }
  },
  "resolutionOrder": [
    { "$ref": "#/sets/size" },
    { "$ref": "#/sets/typography" },
    { "$ref": "#/sets/animation" },
    { "$ref": "#/modifiers/theme" }
  ]
}

이는 단지 여러 최종 토큰 결과를 설명합니다. 최종 세트를 생성하려면 input이 필요합니다.

다음 입력이 주어질 때, 다음과 같은 해상도 순서를 얻습니다:

Input Result 
{ "theme": "light" }
  1. foundation/size.json
  2. foundation/typography.json
  3. foundation/animation.json
  4. theme/light.json
 
{ "theme": "lightHighContrast" }
  1. foundation/size.json
  2. foundation/typography.json
  3. foundation/animation.json
  4. theme/light.json
  5. theme/light-high-contrast.json
 
{ "theme": "dark" }
  1. foundation/size.json
  2. foundation/typography.json
  3. foundation/animation.json
  4. theme/dark.json
 
{ "theme": "darkHighContrast" }
  1. foundation/size.json
  2. foundation/typography.json
  3. foundation/animation.json
  4. theme/dark.json
  5. theme/dark-high-contrast.json

어떤 충돌이 있는 경우에도, 디자인 토큰의 마지막 발생이 최종 값을 생성합니다.

Example 7: 수정자에서 빈 배열

수정자는 빈 컨텍스트 배열을 포함할 수 있습니다 MAY:

{
  "modifiers": {
    // …
    "debug": {
      "description": "Enable debug mode",
      "contexts": {
        "false": [],
        "true": [{ "$ref": "debug.json" }]
      }
    }
  },
  "resolutionOrder": [
    // …
    { "$ref": "#/modifiers/debug" }
  ]
}

이는 input으로 { "debug": "true" }를 받으면 추가로 debug.json 파일을 로드합니다.

4.1.6.1 인라인 세트와 수정자

resolutionOrder에서, set 또는 modifier를 인라인으로 선언할 수 있으며 MAY, 단 객체에 name과 type 키를 추가해야 합니다:

Property Type Required Description
name string Y 고유한 이름으로, resolutionOrder 내의 다른 어떤 name과도 충돌해서는 안 됩니다 MUST NOT.
type "set" | "modifier" Y 해당 유형에 따라 "set" 또는 "modifier"여야 합니다 MUST.

도구는 인라인 객체에서 name 또는 type이 누락된 경우, 또는 name이 객체들 사이에서 중복된 경우 오류를 발생시켜야 합니다 MUST.

Editor's note: Name

세트와 수정자가 각각의 최상위 sets 및 modifiers 키에 나타날 때, 세트가 수정자와 이름을 공유하는 것은 유효합니다. resolutionOrder 배열 내부에서 name을 중복시키는 것만이 무효입니다.

Example 8: 인라인 세트와 수정자를 포함한 해상도 순서 
{
  "resolutionOrder": [
    {
      "type": "set",
      "name": "Size",
      "sources": [{ "$ref": "foundation/size.json" }]
    },
    {
      "type": "set",
      "name": "Typography",
      "sources": [{ "$ref": "foundation/typography.json" }]
    },
    {
      "type": "set",
      "name": "Animation",
      "sources": [{ "$ref": "#/sets/Animation" }]
    },
    {
      "type": "modifier",
      "name": "Theme",
      "description": "Color theme",
      "contexts": {
        "light": [{ "$ref": "theme/light.json" }],
        "lightHighContrast": [
          { "$ref": "theme/light.json" },
          { "$ref": "theme/dark-high-contrast.json" }
        ],
        "dark": [{ "$ref": "theme/dark.json" }],
        "darkHighContrast": [
          { "$ref": "theme/dark.json" },
          { "$ref": "theme/dark-high-contrast.json" }
        ]
      },
      "default": "light"
    }
  ]
}

인라인 세트 및 수정자는 어떤 방식으로도 참조되어서는 안 됩니다 MUST NOT. 도구는 reference object가 해상도 순서 항목을 가리키는 경우 오류를 발생시키는 것이 바람직합니다 SHOULD.

Example 9: 잘못된 인라인 세트 참조

다음 reference object 포인터는 어디에 나타나든 유효하지 않습니다:

{ "$ref": "#/resolutionOrder/4" }

이는 sets(순환 의존성), modifiers (순환 의존성), 또는 resolutionOrder 배열의 다른 위치(무한 재귀)에서 나타나더라도 잘못된 참조를 생성할 가능성이 매우 큽니다. 유효하지 않은 참조를 만들지 않는 경우는 드물며, 아주 작은 변경만으로도 순환 참조로 바뀔 수 있습니다.

4.1.6.2 세트와 수정자의 순서 지정

이 절은 비규범적입니다.

resolutionOrder 배열은 사용자가 원하는 어떤 순서로든 세트와 수정자를 배치할 수 있습니다. 그러나 많은 세트가 충돌을 해결하기 위해 수정자 뒤에 나타나야 하는 시나리오에서는, 예측 불가능하고 취약한 토큰 구성의 냄새일 가능성이 높습니다. 이상적으로는 수정자가 조건부 값을 충분히 잘 처리하여 거의 또는 전혀 재정의가 필요하지 않아야 합니다(직교성 참조). 실무적으로 이는 다음을 의미합니다

4.2 참조 객체

다른 JSON 문서 또는 동일 문서 내 구조를 참조할 때는 참조 객체를 사용해야 합니다 MUST. 이는 JSON Schema 2020-12에서 $ref 키를 가지며 그 문자열이 [RFC6901]에 설명된 유효한 JSON 포인터인 객체로 설명됩니다.

도구는 리졸버 문서의 모든 참조 객체를 해석해야 합니다 MUST.

참조 객체는 순환되어서는 안 되며 MUST NOT, 자기 자신을 참조하는 다른 포인터를 참조하거나 참조 객체의 부모 노드를 참조해서는 안 됩니다.

도구는 동일 문서 참조 객체를 지원해야 하며 MUST, 이는 이 리졸버 모듈을 지원하기 위한 최소 요구사항입니다. 그 beyond로, 도구는 로컬 파일 시스템의 파일 가져오기나 TCP/IP를 통한 원격 URI 등 일부 URI 유형을 지원하지 않기로 개별적으로 결정할 수 있습니다.

Example 10: 유효한 참조 객체

일반적인 참조 객체의 예시는 다음과 같습니다:

Code Result Required Support 
{ "$ref": "#/sets/MySet" }

동일 문서 내 sets/MySet을 참조합니다.

 Y 
{ "$ref": "path/to/example.json" }

이 문서를 기준으로 상대 경로인 ./path/to/example.json의 전체 내용을 참조합니다.

 
{ "$ref": "example.json#sets/MySet" }

example.json의 일부만 참조합니다: sets/MySet.

 
{ "$ref": "https://my-server.com/tokens.json" }

공개 URL에 호스팅된 원격 파일을 참조합니다.
Example 11: 유효하지 않은 참조 객체 
{
  "foo": {
    "bar": { "$ref": "#/baz/bat" }
  },
  "baz": {
    "bat": { "$ref": "#/foo/bar" }
  }
}

이 예시는 foo/bar와 baz/bat가 서로를 참조하여 최종 값이 없으므로 유효하지 않습니다.

{
  "foo": {
    "bar": {
      "baz": { "$ref": "#/foo/bar" }
    }
  }
}

부모를 참조하는 단일 참조 객체는 자신을 포함하게 되어 무한 재귀가 발생하므로 유효하지 않습니다.

4.2.1 잘못된 포인터

포인터는 동일 문서 내 어디든 가리킬 수 있습니다 MAY, 다음 예외를 제외하고:

  1. 오직 resolutionOrder만 수정자(#/modifiers/…)를 참조할 수 있습니다. 세트와 수정자는 다른 수정자를 참조해서는 안 됩니다 MUST NOT.
    • 세트에서 수정자를 참조하는 것은 inputs가 조건부 로직을 지원하지 않는 구조에 적용될 수 있어 허용되지 않습니다.
    • 다른 수정자에서 수정자를 참조하는 것은 단일 입력이 예상치 못한 수정자에 적용됨을 의미하므로 허용되지 않습니다.
  2. 참조 객체는 resolutionOrder 배열(#/resolutionOrder/…)의 어떤 항목도 가리켜서는 안 됩니다 MUST NOT. 해상도 순서는 본질적으로 문서의 많은 다른 부분을 참조합니다. 이를 복제하는 것은 복잡하고 예측하기 어려운 연쇄를 생성합니다.

도구는 어떤 잘못된 포인터를 만나더라도 오류를 발생시켜야 합니다 MUST.

4.2.2 확장

JSON Schema 2020-12가 허용하듯, 다른 키가 $ref와 함께 참조 객체에 존재할 수 있습니다 MAY. 이러한 시나리오에서, $ref와 함께 있는 로컬 키는 오버라이드로 처리되어야 합니다 MUST.

Example 12: $ref로 확장하기

일반적인 예시:

{
  "animal": {
    "color": "brown",
    "legs": 4
  },
  "lizard": {
    "color": "green",
    "$ref": "#/animal",
    "size": "small"
  }
}

#/lizard의 최종 값은 다음과 동일합니다:

{
  "color": "green",
  "legs": 4,
  "size": "small"
}

키 순서는 중요하지 않습니다. color가 로컬로 선언되었으므로 #/animal의 값을 대체합니다. 또한 새로운 속성 size를 추가하는 것은 최종 값에 덧붙여집니다.

$ref와 함께 있는 키가 객체 또는 배열을 선언하는 경우, 도구는 이를 얕게 평탄화해야 하며 MUST, 즉 객체와 배열은 병합하지 않습니다.

4.3 $extensions

$extensions 객체는 임의의 메타데이터를 선언하기 위해 어떤 set, modifier, 또는 인라인 set/modifier에도 추가될 수 있습니다 MAY. 개별 도구가 이를 사용할지 무시할지 결정합니다.

제공되는 경우, $extensions는 벤더 별 네임스페이스를 키로 가지는 객체여야 합니다 MUST. 이는 여러 도구가 충돌 없이 이 메타데이터를 사용할 수 있게 합니다.

Example 13: $extensions를 포함한 세트

다음은 figma.com 벤더를 위한 임의 메타데이터를 세트에 포함한 예시입니다:

{
  "sets": {
    "color": {
      "sources": [
        { "$ref": "colors/ramps.json" },
        { "$ref": "colors/semantic.json" }
      ],
      "$extensions": {
        "figma.com": {
          "sourceFile": "https://figma.com/file/xxxxxx",
          "updatedAt": "2025-11-01"
        }
      }
    }
  }
}

4.4 $defs

도구는 JSON Schema $defs에서 구조 정의를 허용할 수 있으나 MAY, 필수는 아닙니다. 다만, 도구는 $defs를 만나도 오류를 발생시키지 않아야 하며 MUST NOT, 지원하지 않는 경우 해당 키를 무시해야 합니다 MUST.

Editor's note: $defs

$defs 사용은 본 명세에서 정의되지 않은 동작이므로, 사용자는 이를 정의하거나 완전히 피하는 결정을 도구 제작자와 함께 내려야 합니다. 본 명세는 의도적으로 $defs 사용을 피하여 향후 충돌의 가능성을 제거합니다.

5. 입력값(Inputs)

리졸버 문서는 조건부 토큰 값이 어떻게 생성될 수 있는지에 대해서만 설명합니다 MAY. 그러나 그 조건은 어딘가에서 제공되어야 합니다. “input”이라는 용어는 도구에 전달되는 컨텍스트 값들의 임의의 선택을 의미합니다.

도구는 입력값을 JSON 직렬화 가능한 객체로 받아들여야 합니다 MUST. 예: JavaScript의 object 또는 Python의 dictionary.

수정자를 선언하는 리졸버를 로드하는 도구는, 함께 제공되는 입력값이 없을 경우 오류를 발생시키는 것이 바람직합니다 SHOULD.

Example 14: 입력값(Inputs)

다음과 같은 수정자가 주어졌을 때:

{
  "resolutionOrder": [
    {
      "type": "modifier",
      "name": "theme",
      "contexts": {
        "light": [{ "$ref": "light.json" }],
        "dark": [{ "$ref": "dark.json" }]
      }
    },
    {
      "type": "modifier",
      "name": "size",
      "context": {
        "default": [{ "$ref": "size/default.json" }],
        "large": [{ "$ref": "size/large.json" }]
      }
    },
    {
      "type": "modifier",
      "name": "beta",
      "context": {
        "false": [],
        "true": [{ "$ref": "beta.json" }]
      },
      "default": "false"
    }
  ]
}

유효한 입력값은 스키마를 따릅니다: 모든 키는 각 수정자의 name에 대응합니다. 값은 해당 수정자가 지정한 유효한 옵션입니다.

{
  "theme": "light",
  "size": "large",
  "beta": "true"
}

반면, 유효하지 않은 입력값은 알 수 없는 키, 잘못된 컨텍스트, 그리고/또는 필요한 수정자 누락을 추가합니다:

{
  "theme": "blue",
  "foo": "bar"
}

이 경우, 도구는 다음과 같은 다중 오류를 발생시키는 것이 바람직합니다 SHOULD:

  1. Error: invalid context "blue" for modifier "theme".
  2. Error: missing modifier "size".
  3. Error: unknown modifier "foo".
  4. (수정자 beta는 default를 제공했으므로 오류가 필요하지 않음)
Example 15: 입력값을 소비하는 도구

JavaScript로 작성된 가상의 도구를 사용하면, 이전 예시를 다음과 같이 소비할 수 있습니다:

import tokenTool from './token-tool.js';

tokenTool.loadResolver(
  /* Path to resolver */
  './resolver.json',

  /* Input */
  {
    theme: 'dark',
    size: 'default',
  },
);

이 가상의 도구는 매개변수로 다음을 받는 loadResolver() 메서드를 가지고 있습니다:

  1. 첫 번째 위치에는 리졸버의 파일 경로,
  2. 두 번째 위치에는 입력 객체.

이 도구는 리졸버 + 입력값을 결합하여 최종 resolution을 생성합니다.

5.1 대소문자 구분

입력값은 대소문자를 구분하지 않는 것이 바람직합니다 SHOULD. 예를 들어, { "theme": "dark" }, { "Theme": "Dark" }, { "THEME": "DARK" }는 서로 동등해야 합니다 SHOULD. 다만, 도구는 대소문자 구분에 대해 개별적인 결정을 내릴 수 있습니다 MAY.

5.2 문자열 강제

입력값의 값은 문자열이어야 합니다 MUST. 입력값에 { "beta": true } 또는 { "size": 100 }처럼 비문자열 값이 포함된 경우 도구는 오류를 발생시켜야 합니다 MUST.

6. 해상도 로직(Resolution logic)

도구는 올바른 출력을 생성하기 위해 해상도 단계들을 처리해야 합니다 MUST.

  1. 입력값 검증: 주어진 리졸버 문서에 대해 입력값이 유효한지 확인.
  2. 정렬: 최종 토큰 구조를 생성하기 위해 resolutionOrder 배열을 추적.
  3. 별칭: 최종 토큰 구조에서 토큰 별칭을 해결.
  4. 해상도: 최종 결과.

6.1 입력값 검증

도구는 모든 inputs가 제공된 modifier 컨텍스트와 일치하도록 요구해야 합니다 MUST.

리졸버가 어떠한 수정자도 선언하지 않는 경우, 이 단계를 건너뛰고 정렬로 진행하십시오.

  1. 입력 객체의 모든 키에 대해:
    1. 해당 키가 유효한 수정자에 대응하는지 확인합니다. 대응하지 않으면 오류를 발생시킵니다.
    2. 해당 키의 값이 그 수정자의 허용 값에 대응하는지 확인합니다. 대응하지 않으면 오류를 발생시킵니다.
  2. 리졸버의 모든 수정자에 대해:
    1. 그 리졸버가 기본값을 선언하지 않는 경우, 입력값에 해당 키가 제공되는지 확인합니다. 제공되지 않으면 오류를 발생시킵니다.

6.2 정렬(Ordering)

도구는 resolutionOrder 배열을 순서대로 반복 처리해야 합니다 MUST.

  1. 배열의 각 항목에 대해 그것이 set인지 modifier인지 판별하고, 배열 순서대로 단일 토큰 구조로 평탄화합니다.

    1. 항목이 set인 경우, 배열 순서대로 sources를 결합하여 단일 토큰 구조를 생성합니다.
    2. 그 외에 항목이 modifier인 경우, 입력값과 일치하는 context만 선택하여 배열 순서대로 결합해 단일 토큰 구조를 생성합니다.
    3. 충돌이 발생하는 경우, 배열에서 가장 최근의 항목을 사용합니다.

  2. resolutionOrder 배열의 끝에 도달할 때까지 반복합니다.

최종 결과는 처음부터 하나의 소스였던 것처럼 동작하는 토큰 구조가 됩니다.

Example 16: 충돌 해결(Conflict resolution) 
{
  "sets": {
    "foundation": {
      "sources": [
        {
          "color": {
            "text": {
              "default": {
                "$value": { "colorSpace": "srgb", "components": [0, 0, 0] },
                "$type": "color"
              }
            }
          }
        },
        {
          "color": {
            "text": {
              "default": {
                "$value": {
                  "colorSpace": "srgb",
                  "components": [0.1, 0.1, 0.1]
                },
                "$type": "color"
              }
            }
          }
        }
      ]
    }
  },
  "resolutionOrder": [{ "$ref": "#/sets/foundation" }]
}

여기서는 두 개의 color.text.default 토큰이 발견되었습니다. 순서가 중요하므로, 마지막 선언이 “승리”하며 최종 결과는 다음과 같습니다:

{
  "color": {
    "text": {
      "default": {
        "$value": { "colorSpace": "srgb", "components": [0.1, 0.1, 0.1] },
        "$type": "color"
      }
    }
  }
}

6.3 별칭(Aliases)

별칭은 이 단계 이전에 해결되어서는 안 됩니다 MUST NOT.

정렬이 단일 토큰 구조로 평탄화된 후, 남은 유일한 단계는 별칭을 해결하는 것입니다. 별칭은 format에 설명된 방식과 정확히 동일하게 해결됩니다:

  • 깊은 별칭은 순환적이지 않은 한 허용됩니다.
  • 별칭은 올바른 $type을 가리켜야 합니다.

6.4 해상도(Resolution)

Example 17: 테마 해상도(Theme resolution)

다음 파일 구조로 시작하여, 해상도 단계를 단계별로 살펴보겠습니다.

이름(Name) 내용(Contents)

Resolver

 
{
  "sets": {
    "foundation": {
      "sources": [{ "$ref": "foundation.json" }]
    },
    "components": {
      "sources": [{ "$ref": "components/button.json" }]
    }
  },
  "modifiers": {
    "theme": {
      "context": {
        "light": [{ "$ref": "themes/light.json" }],
        "dark": [{ "$ref": "themes/dark.json" }]
      }
    }
  },
  "resolutionOrder": [
    { "$ref": "#/sets/foundation" },
    { "$ref": "#/sets/components" },
    { "$ref": "#/modifiers/theme" }
  ]
}

Input

 
{ "theme": "dark" }

foundation.json
  • color.brand.primary (color)

components/button.json
  • button.background (color)
  • button.padding (dimension)

themes/light.json
  • theme.accent

themes/dark.json
  • theme.accent (alternate value)
  1. 입력값 검증(Validation)
    1. theme가 정의된 수정자인지 확인합니다(통과).
    2. dark가 theme 수정자에 대한 유효한 값인지 확인합니다(통과).
  2. 정렬(Ordering)
    1. 첫 번째 항목은 foundation 세트로, color.brand.primary를 제공합니다.
    2. 두 번째 항목은 components 세트로, button.background와 button.padding을 제공합니다.
    3. 세 번째이자 마지막 항목은 theme 수정자로, theme.accent를 제공합니다.
    4. 따라서 최종 해상도에는 4개의 토큰이 포함됩니다.
  3. 별칭(Alias)
    1. 토큰에 별칭이 포함되어 있다면, 이 시점에서만 해결될 수 있습니다.
  4. 해상도(Resolution)
    1. 최종 토큰 확산은 다음과 같습니다:
      1. color.brand.primary (foundation.json에서)
      2. button.background (components/button.json에서)
      3. button.padding (components/button.json에서)
      4. theme.accent (themes/dark.json에서)

핵심 포인트:

  • 입력이 { "theme": "dark" }였기 때문에 themes/light.json은 사용되지 않았습니다.

7. 번들링(Bundling)

이 절은 비규범적입니다.

리졸버 문서는 구성 목적을 위해 토큰을 여러 JSON 파일에 존재하도록 허용합니다. 그러나 이식성의 관점에서, 단일 JSON 문서만을 다루는 것이 유리할 수 있습니다.

“번들링(Bundling)”은 리졸버 문서를 단일 파일로 축약하는 과정을 의미합니다. 이를 달성하기 위한 전략은 여러 가지가 있으며, 이 문서가 설명하는 것보다 많습니다. 다만, 설명을 위해 가능한 접근 방식 중 2가지를 개괄합니다:

7.1 파일 인라인(Inlining files)

인라인은 원격 파일에 대한 모든 reference objects를 가져와 그 내용으로 대체하는 것을 포함합니다. 이는 최종 목표를 달성하는 간단한 전략이지만, 동일한 파일이 여러 번 참조될 때마다 중복이 발생합니다. 도구는 중복된 토큰에 문제 없을 수 있지만, 이 문서를 읽는 사람은 생성될 코드 라인의 수를 읽는 데 어려움을 겪을 수 있습니다.

Example 18: 인라인에 의한 번들링

5개의 파일을 참조하는 리졸버가 주어졌을 때:

{
  "sets": {
    "foundation": {
      "sources": [
        { "$ref": "foundation/colors.json" },
        { "$ref": "foundation/size.json" },
        { "$ref": "foundation/typography.json" }
      ]
    }
  },
  "modifiers": {
    "theme": {
      "contexts": {
        "light": [
          { "$ref": "foundation/colors.json" },
          { "$ref": "theme/light.json" }
        ],
        "dark": [
          { "$ref": "foundation/colors.json" },
          { "$ref": "theme/dark.json" }
        ]
      }
    }
  },
  "resolutionOrder": [
    { "$ref": "#/sets/foundation" },
    { "$ref": "#/modifiers/theme" }
  ]
}

내용을 인라인하면 다음과 같이 결과가 나올 수 있습니다:

{
  "sets": {
    "foundation": {
      "sources": [
        {
          // (contents of foundation/colors.json)
        },
        {
          // (contents of foundation/size.json)
        },
        {
          // (contents of foundation/typography.json)
        }
      ]
    }
  },
  "modifiers": {
    "theme": {
      "contexts": {
        "light": [
          {
            // (contents of foundation/colors.json)
          },
          {
            // (contents of theme/light.json)
          }
        ],
        "dark": [
          {
            // (contents of foundation/colors.json)
          },
          {
            // (contents of theme/dark.json)
          }
        ]
      }
    }
  },
  "resolutionOrder": [
    { "$ref": "#/sets/foundation" },
    { "$ref": "#/modifiers/theme" }
  ]
}

파일의 내용은 가독성을 위해 생략/축약되었습니다. 그 내용은 무엇이든 될 수 있으며 번들링 주제와 직접적인 관련은 없습니다.

foundation/colors.json이 문서에서 3번 참조되었으므로, 인라인은 동일한 내용의 3개의 복사본을 생성한다는 점에 유의하세요.

7.2 파일에 $defs 사용하기(Using $defs for files)

$defs에 설명된 바와 같이, $defs는 리졸버 문서에서 정의된 동작이 없습니다. JSON Schema의 이 기능을 지원하도록 도구가 결정한 경우에만 사용할 수 있습니다.

이 전략은 최상위에 $defs 키를 생성하고, 각 최상위 키에 해당 파일의 내용을 포함시키는 것을 포함합니다.

$defs를 사용하는 유일한 단점은, 리졸버 문서의 최소 요구사항이 아니기 때문에 일부 도구는 이를 무시하기로 선택할 수 있다는 점입니다.

Example 19: $defs를 사용한 번들링

인라인 섹션과 동일한 리졸버가 주어졌을 때, 새로운 최상위 $defs 키를 생성하고, 각각 파일명과 그 내용에 해당하는 키와 값을 추가할 수 있습니다:

{
  "sets": {
    "foundation": {
      "sources": [
        { "$ref": "#/$defs/foundation~1colors.json" },
        { "$ref": "#/$defs/foundation~1size.json" },
        { "$ref": "#/$defs/foundation~1typography.json" }
      ]
    }
  },
  "modifiers": {
    "theme": {
      "contexts": {
        "light": [
          { "$ref": "#/$defs/foundation~1colors.json" },
          { "$ref": "#/$defs/theme~1light.json" }
        ],
        "dark": [
          { "$ref": "#/$defs/foundation~1colors.json" },
          { "$ref": "#/$defs/theme~1dark.json" }
        ]
      }
    }
  },
  "resolutionOrder": [
    { "$ref": "#/sets/foundation" },
    { "$ref": "#/modifiers/theme" }
  ],
  "$defs": {
    "foundation/colors.json": {
      // (contents of foundation/colors.json)
    },
    "foundation/size.json": {
      // (contents of foundation/size.json)
    },
    "foundation/typography.json": {
      // (contents of foundation/typography.json)
    },
    "theme/light.json": {
      // (contents of theme/light.json)
    },
    "theme/dark.json": {
      // (contents of theme/dark.json)
    }
  }
}

이 방법을 사용하면 중복을 줄일 뿐만 아니라, 길이가 늘어나지 않으면서 원래 리졸버 문서의 포맷과 형태를 보존할 수 있습니다.

이름에 “/” 문자가 사용될 때는 [RFC6901]에 따라 서브패스로 처리되지 않도록 ~1로 이스케이프해야 한다는 점을 유의하십시오. 또한 파일명이 # 프래그먼트 문자 뒤에 나타나기 때문에, “[filename].json”은 실제 파일이 아니라 동일 문서의 한 지점을 가리킨다는 점도 유의하십시오(그렇지 않으면 “#” 앞에 나타났을 것입니다).

8. 적합성(Conformance)

비규범적으로 표시된 절뿐만 아니라, 이 명세의 모든 작성 지침, 다이어그램, 예제 및 노트는 비규범적입니다. 그 외의 모든 내용은 규범적입니다.

이 문서의 키워드 MAY, MUST, MUST NOT, SHOULD, SHOULD NOT은 BCP 14 [RFC2119] [RFC8174] 에서 설명된 대로, 그리고 여기 표시된 것처럼 대문자로 나타날 때에만 해석되어야 합니다.

리졸버 명세를 구현하는 도구는 다음을 수행해야 합니다 MUST:

  • 해상도 프로세스 지원: 입력값 검증, 기본 세트 평탄화, 수정자 적용, 별칭 처리, 충돌 해결을 포함하여 정의된 해상도 로직을 구현합니다.
  • 입력값 검증: 제공된 수정자 입력값이 정의된 수정자 및 허용 값과 일치하는지 확인합니다.
  • 별칭 정확히 해결: 재귀 참조 및 순환 종속성 탐지를 포함하여 토큰 참조를 정확히 처리합니다.
  • 토큰 속성 보존: 해상도 프로세스 전반에 걸쳐 추가 토큰 속성(예: $extensions)을 유지합니다.
  • 오류를 우아하게 처리: 잘못된 입력값 또는 순환 참조와 같은 문제에 대해 의미 있는 오류 메시지를 제공합니다.
