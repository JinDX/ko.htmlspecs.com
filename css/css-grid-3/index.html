요약

이 모듈은 CSS Grid 컨테이너에 대해 추가적인 레이아웃 모드로 'masonry layout(벽돌식 레이아웃)'을 도입합니다.

CSS는 구조화된 문서(HTML, XML 등)의 렌더링을 화면, 인쇄물 등에서 기술하기 위한 언어입니다.

1. 소개

이 섹션은 규범적이지 않습니다.

그리드 레이아웃은 CSS에서 박스와 그 내용의 크기 및 위치를 강력하게 제어할 수 있는 레이아웃 모델입니다. 그리드 레이아웃은 2차원 레이아웃에 최적화되어 있습니다: 즉, 콘텐츠의 정렬이 두 축 모두에서 필요한 경우에 적합합니다.

일반적인 그리드 레이아웃으로 많은 레이아웃을 표현할 수 있지만, 항목을 두 축 모두에서 그리드로 제한하면 웹에서 흔히 사용하는 일부 레이아웃을 표현할 수 없게 됩니다.

이 모듈은 그러한 제한을 없애고, 항목을 한 축에서는 그리드와 같은 트랙에 배치하면서 다른 축에서는 차례대로 쌓이도록 하는 레이아웃 시스템을 정의합니다. 항목은 지금까지 배치된 항목의 레이아웃 크기를 기준으로 남은 공간이 가장 많은 열(또는 행)에 배치됩니다. 이 모듈은 CSS Grid에 새로운 그리드 항목 배치 전략을 추가하고, CSS Box Alignment에는 새로운 정렬 기능을 확장합니다.

1.1. 배경 및 동기

1.1.1. 자동 배치 항목을 활용한 폭포식 레이아웃

Masonry 레이아웃은 “waterfall layout(폭포식 레이아웃)”이라고도 불리며, 여러 항목(주로 이미지 또는 짧은 기사 요약)이 기둥에 하나씩 배치되는 일반적인 웹 디자인 패턴입니다. 이 방식은 석공의 벽돌 쌓기와 유사한 형태로 항목들이 배치됩니다. 다단 레이아웃과 달리, 다단 레이아웃에서는 첫 번째 열에 콘텐츠가 채워지고 두 번째 열로 넘칠 때까지 이어지지만, masonry 레이아웃에서는 새로운 항목마다 레이아웃 상단에 더 가까운 기둥이 선택되어 배치됩니다.

Pinterest 검색 결과 페이지가 이 레이아웃의 대표적인 예시입니다:

여기서 각 항목의 높이는 다릅니다 (내용과 열의 너비에 따라 달라집니다). DOM을 확인하면 (시각적인 콘텐츠만으로는 순서를 알 수 없지만) 각 항목이 그 시점에서 가장 낮은 높이의 열에 배치된 것을 알 수 있습니다.

이 레이아웃은 겉보기에는 다단 레이아웃과 비슷하지만, 스크롤을 아래로 내리면 자연스럽게 레이아웃의 "나중" 항목들(즉, 검색 결과에서 덜 관련된 항목)로 이어진다는 장점이 있습니다.

이전 CSS 레이아웃 모델로는 각 항목의 높이를 미리 알거나 자바스크립트를 사용해 콘텐츠의 크기나 배치를 측정하지 않는 한 이러한 레이아웃을 구현할 수 없습니다.

masonry 컨테이너와 auto로 위치가 지정된 항목을 함께 사용하면 이러한 masonry 레이아웃을 구현할 수 있습니다.

1.1.2. 일차원 그리드 레이아웃

그리드 레이아웃은 두 축에서 강력한 트랙 크기 지정과 명시적 배치를 제공하지만, 때로는 한 차원에서만 항목의 정렬이 필요한 경우가 있습니다.

masonry 컨테이너와 명시적으로 위치가 지정된 항목을 함께 사용하면 이러한 일차원 그리드 레이아웃을 구현할 수 있습니다.

Douglas Graham이 제공한 이 예시는 각 항목을 명시적으로 지정된 열에 배치하지만, 행은 존재하지 않습니다. 대신 각 열의 항목들이 차례대로 쌓입니다. 이 레이아웃은 그리드 레이아웃에서는 구현할 수 없습니다. 인접한 열의 항목들 간 "확장" 관계가 고정되어 있지 않고, 각 항목의 상대적 높이와 배너 또는 광고 항목의 포함 여부에 따라 달라지기 때문입니다. 또한 플렉스 레이아웃에서도 구현할 수 없습니다. 항목의 소스 순서(읽기, 순차적 탐색, 1열 모바일 레이아웃에서 사용됨)가 두 열 사이를 오가게 되기 때문입니다.

1.2. 값 정의

이 명세는 CSS2의 속성 정의 관례를 따르며, [CSS2]와 값 정의 문법([CSS-VALUES-3])을 사용합니다. 이 명세에서 정의되지 않은 값 유형은 CSS Values & Units [CSS-VALUES-3]에서 정의됩니다. 다른 CSS 모듈과 조합하면 이 값 유형의 정의가 확장될 수 있습니다.

각 속성 정의에 나열된 속성별 값 외에도, 이 명세에서 정의된 모든 속성은 CSS-wide 키워드도 속성 값으로 허용합니다. 가독성을 위해 별도로 나열하지 않았습니다.

2. 벽돌식 레이아웃 모델

Masonry 레이아웃은 한 축에서는 그리드 레이아웃과 유사하게 미리 정의된 트랙에 항목을 배치하고, (그리드 축), 다른 축에서는 플렉스 레이아웃처럼 자유롭게 흐르도록 배치합니다. (쌓기 축) 그리드 레이아웃과 유사하며 플렉스 레이아웃과는 달리, masonry 레이아웃의 자동 배치 기능은 트랙의 길이가 최대한 비슷하도록 항목을 트랙에 분배합니다.

그리드 항목은 일반 그리드 컨테이너와 완전히 동일하게 blockify 처리됩니다.

(명확성을 위해, 그리드 항목과 그리드 트랙은 masonry 컨테이너에서 각각 masonry 항목과 masonry 트랙이라고 부를 수 있습니다.)

별도로 명시하지 않는 한, 모든 CSS 속성은 일반 그리드 컨테이너와 동일하게 동작합니다. 예를 들어, order 속성으로 항목의 배치 순서를 다르게 지정할 수 있습니다.

참고: 서브그리드 항목도 지원되지만, 서브그리딩은 그리드 축에서만 동작합니다. 자세한 내용은 § 3.2 서브그리드를 참고하세요.

masonry 컨테이너는 그 내용이 masonry 레이아웃에 참여하는 박스입니다. masonry 컨테이너는 열 masonry 컨테이너로 쌓기 축이 block axis인 경우, 또는 행 masonry 컨테이너로 쌓기 축이 inline axis인 경우입니다.

벽돌식 컨테이너 비교
열 Masonry 
grid-template-columns: 1fr 2fr 3fr;
행 Masonry 
grid-template-rows: 1fr 2fr 3fr;

2.1. 재배치 및 접근성

masonry 레이아웃은 일반적으로 앞쪽으로 진행됩니다 (다음 항목을 현재 항목의 아래나 끝에 배치해서, 자연스러운 "읽기 순서"와 일치함), 하지만 경우에 따라 이 두 가지가 임의로 전환될 수 있습니다. 간단한 경우에는 item-slack 속성으로 block 축의 작은 크기 차이 때문에 발생하는 역행 느낌을 줄일 수 있습니다. 하지만 자동 배치와 명시적 배치 또는 확장 항목이 혼합되는 경우에는, 어느 정도 역행 현상이 발생할 수 있습니다.

예를 들어, 다음 마크업 샘플에서 네 번째 항목은 스팬 항목으로 첫 번째 줄의 남은 빈 열에 들어갈 수 없습니다. 결국 가장 높이가 높은 첫 번째 열에 배치되며, 그 아래에 있는 몇몇 항목(스팬이 1인 항목)은 빈 열에 "위"에서 배치되어 자연스러운 읽기 순서를 위반하게 됩니다. 
<section class=masonry>
  <div class=item>1</div>
  <div class=item>2</div>
  <div class="item tall">3</div>
  <div class="item wide">4</div>
  <div class=item>5</div>
  <div class=item>6/div>
  <div class=item>7</div>
</section>
<style>
.masonry {
  //FIXME display:masonry or something
  grid-template-columns: repeat(5, auto);
}
.item { height: 50px; }
.item.wide { grid-column: span 3; }
.item.tall { height: 90px; }
</style>
마찬가지로, 특정 트랙에 명시적으로 배치한 항목이 그 뒤에 빈 공간을 남길 수 있으며, 이후 자동 배치 항목들이 시각적으로 순서에서 벗어나 배치될 수 있습니다.

저자들은 이러한 현상을 인지하고, 역행이 최소화되어 포커스와 읽기 순서를 더 쉽게 따라갈 수 있는 레이아웃을 설계해야 합니다. 또는, 항목에 고유한 순서가 없는 경우 reading-flow 속성으로 UA가 읽기 및 선형 탐색을 위해 항목을 재배치할 수 있도록 해야 합니다.

자동 배치 항목은 기본적으로 재배치가 되어야 할까요?

역행을 줄이는 기법:

  • item-slack의 적절한 값을 사용하는 것. 즉, 크기가 비슷한 트랙들 사이에서 불필요한 차별화를 피할 만큼 충분히 크면서, 의미 있는 차이가 무시되지 않을 정도로만 사용하는 것.

  • 관련 항목들을 그룹화하는 방식으로 명시적 배치를 활용하고, 항목의 자연스러운 순서를 방해하지 않도록 배치하는 것

  • 그리드 축에서 스팬 크기가 섞이고 쌓기 축에서 항목 크기가 다양한 경우를 피하는 것, 이는 항목의 순서가 뒤틀릴 수 있습니다(위의 예 참고).

그리드 레이아웃과 플렉스 레이아웃처럼 저자들은 order 속성으로 항목을 재배치할 수 있습니다. 같은 주의점이 적용됩니다. CSS Grid Layout 2 § 4 재배치 및 접근성과 CSS Flexbox 1 § 5.4.1 재배치 및 접근성을 참고하세요.

3. Masonry 트랙 명세

그리드 축에서는, 그리드 레이아웃의 모든 트랙 명세 기능을 사용할 수 있습니다:

  • 트랙 크기, 라인 이름, 영역 지정은 masonry 컨테이너의 그리드 축에서 그리드 레이아웃과 동일하게 지정할 수 있습니다.

  • 명시적 그리드와 암시적 그리드도 일반 그리드 컨테이너와 동일하게 형성됩니다.

  • 항목은 이 그리드 템플릿에 배치될 수 있고, 그리드 레이아웃과 동일하게 동작합니다.

단, 자동 배치 항목은 실제로 배치되는 트랙뿐만 아니라 모든 트랙의 크기 산정에 기여합니다; 자세한 내용은 § 3.4 그리드 축 트랙 크기 지정을 참고하세요.

참고: 자동 배치 항목은 배치되는 즉시 레이아웃되어야 하므로, 각 트랙이 얼마나 “채워졌는지” 알 수 있어야 하며 (따라서 다음 자동 배치 항목이 들어갈 트랙을 결정할 수 있음), 트랙 자체가 반드시 명확한 크기를 미리 가져야 하므로 항목들이 레이아웃 중에 사용 가능한 공간을 알 수 있습니다.

3.1.1. 고유 트랙과 repeat()

자동 반복 기반 트랙을 허용해야 할까요? 이런 정의가 합리적인가요? Grid Layout에서도 동작해야 할까요? [Issue #10915]

Grid Layout에서는 모든 그리드 항목이 그리드에 먼저 배치된 후, 그리드 트랙이 크기 지정됩니다. 즉, auto-fill/auto-fit 반복은 auto와 같은 고유 크기 트랙을 포함할 수 없습니다 (repeat() 함수 내 또는 고정 트랙 목록과 함께), 왜냐하면 레이아웃 알고리즘이 이미 해당 트랙에 어떤 항목이 들어갈지, 트랙 크기가 얼마나 될지, 사용 가능한 공간에 얼마나 반복이 들어갈지 결정해야 하기 때문입니다.

Masonry Layout에서는, masonry 항목 배치와 레이아웃이 상호 연동되고 다소 단순화되어, 이러한 제한이 반드시 필요하지 않습니다. 크기 산정에 약간의 휴리스틱 정의가 필요하지만, 자동 반복은 masonry 컨테이너에서는 고유 크기 트랙을 포함할 수 있습니다 (그리고 masonry-template-tracks의 초기값이 이를 사용합니다!).

To determine the number of repetitions that a repeat() function resolves to, run layout as defined in § 3.4.2 Optimized Track Sizing, with the following changes:

  • auto-fill/auto-fit 반복 함수는 한 번만 확장합니다.

  • 항목 배치는 무시합니다. (즉, 모든 항목이 masonry-track: auto로 간주)

  • masonry 항목이 span이 1보다 크면, 해당 항목이 virtual masonry item에 기여할 각 고유 크기마다, 먼저 해당 span이 차지하는 gap의 전체 크기를 빼고, span 값으로 나누기. 그런 뒤 span-1 항목으로 간주하여 그 값을 사용함.

이렇게 계산된 고유 크기 트랙은 (repeat() 인자에 들어간 것 포함, 단일 반복에서 가져옴) 해당 repeat() 함수가 몇 번 반복될지 결정하는 데 사용됩니다.

동기

이 간소화된 레이아웃 휴리스틱은 “충분히 괜찮은” 기준으로, 빠르고 일관성을 유지합니다.

배치 무시는 개념의 일관성을 위해 필요합니다; 반복이 몇 개 필요한지 알기 전에는, 명확한 배치가 지정된 항목이 어떤 트랙에 배치될지 알 수 없기 때문입니다.

스팬 항목을 span-1 항목으로 분할하면 repeat()를 여러 번 확장할 필요를 없애며, 동일 키워드가 반복마다 크기가 다르게 나오는 비일관성을 피할 수 있습니다.

또한 전체 레이아웃이 훨씬 저렴해집니다— 각 고유 트랙 크기만 고려하면 되고 repeat() 확장을 실제로 할 필요도 없습니다. 예를 들어 auto repeat(auto-fill, min-content auto)에서는, auto 키워드 모두가 이 휴리스틱 레이아웃에서 동일 크기로 해석됩니다; masonry-template-tracks: auto와 masonry-template-tracks: min-content 각각이 어떤 결과가 되는지만 알면 그 크기를 사용하면 됩니다.

3.2. 서브그리드

서브그리딩은 중첩된 masonry 컨테이너(와 그리드 컨테이너)가 트랙 크기를 공유할 수 있도록 허용합니다. 부모의 해당 축이 그리드 축이면, 서브그리드 축은 부모 컨테이너에서 그리드 컨테이너 명세대로 상속합니다; 부모의 해당 축이 쌓기 축이면, 서브그리드 축은 masonry처럼 동작합니다.

참고: 이로 인해 양축 모두 masonry가 되면, 이중 축 masonry 템플릿을 사용하는 masonry 컨테이너의 일반 동작으로 처리됩니다. 즉, grid-template-columns: none; grid-template-rows: masonry와 같이 동작합니다.

masonry 레이아웃에서는, 자동 배치되는 서브그리드는 부모 그리드의 라인 이름을 상속하지 않습니다, 그렇게 되면 항목 배치가 레이아웃 결과에 따라 달라지기 때문입니다; 하지만 서브그리드의 트랙은 여전히 부모의 트랙에 정렬됩니다.

다음은 서브그리드 예제입니다: 
<style>
.grid {
  //FIXME: display: inline-grid; or something
  grid-template-rows: auto auto 100px;
  align-content: center;
  height: 300px;
  border: 1px solid;
}

.grid > * {
  margin: 5px;
  background: silver;
}
.grid > :nth-child(2n) {
  background: pink;
}

.grid subgrid {
  display: grid;
  grid: subgrid / subgrid;
  grid-row: 2 / span 2;
  grid-gap: 30px;
}
.grid subgrid > * { background: cyan; }
</style>

<div class="grid">
  <item>1</item>
  <item>2</item>
  <item>3</item>
  <subgrid>
    <item style="height:100px">subgrid.1</item>
    <item>sub.2</item>
    <item>s.3</item>
  </subgrid>
  <item>4</item>
  <item>5</item>
  <item style="width: 80px">6</item>
  <item>7</item>
</div>

서브그리드의 첫 번째 항목 ("subgrid.1")이 부모 그리드 2번째 행의 고유 크기에 어떻게 기여하는지 주목하세요. 서브그리드가 명확한 위치를 지정했으므로 어떤 트랙을 차지할지 알 수 있습니다. 또한 부모의 쌓기 축을 서브그리드화하면 서브그리드의 masonry 레이아웃이 inline axis에서 적용됨을 확인할 수 있습니다.

서브그리드가 masonry 컨테이너인 경우, submasonry라고 부를 수 있습니다.

3.3. 트랙 반복: repeat() 표기법

이 명세는 repeat() 표기법에 대해 새로운 키워드와 masonry 전용 동작을 도입합니다.

3.3.1. repeat(auto-areas)

repeat() 표기법의 새로운 auto-areas 값은 해당 축에서 grid-template-areas / masonry-template-areas 값이 명시된 영역의 수에 맞게 명시적 트랙의 총 개수가 일치하도록 반복 횟수를 나타냅니다. 반복에 여러 트랙이 지정된 경우, 마지막 반복은 트랙 수에 맞게 잘릴 수 있습니다.

참고: auto-fit은 항상 한 번 이상 전체 트랙을 반복하지만, auto-areas의 반복 횟수는 0이 될 수도 있습니다 (이미 충분한 명시적 트랙이 있는 경우), 마지막 반복이 부분적으로 적용될 수도 있습니다.

grid-template-areas / masonry-template-areas 값이 none이면, 이 값은 auto-fit과 동일하게 동작합니다.

참고: 이 값은 일반 그리드 컨테이너와 masonry 컨테이너 모두에 적용됩니다.

실제로 이 값이 필요한지 불분명합니다. 명시적 그리드는 이미 grid-auto-columns / grid-auto-rows / masonry-auto-tracks에서 필요한 만큼 값을 가져옵니다. [Issue #10854]

3.3.2. repeat(auto-fit)

masonry 컨테이너(일반 그리드 컨테이너와 동일)에서 auto-fit은 auto-fill과 유사하게 동작하지만, 빈 트랙은 접힘(collapsed) 처리됩니다. 하지만 트랙 크기를 산정한 후 배치가 이루어지므로, masonry 컨테이너는 트랙이 실제로 사용될지 휴리스틱을 사용해 결정합니다:

  • 명시적으로 배치된 항목이 차지하는 모든 트랙은 사용된 것으로 간주합니다.

  • 자동 배치 항목 전체의 span 합계를 N이라 할 때, 비어 있는 트랙 중 앞에서 N번째까지는 사용된 것으로 간주합니다.

auto-fit 반복으로 생성된 트랙 중 이 휴리스틱으로 사용되지 않은 트랙은 "빈(empty)" 것으로 간주되며 접힘(collapsed) 처리됩니다. 접힌 트랙에는 자동 배치 항목이 들어갈 수 없습니다.

참고: 자동 배치 항목의 span이 1보다 크고, 명시적으로 배치된 항목들이 빈 공간을 남긴 경우, auto-fill에서는 자동 배치 항목이 트랙에 배치될 수 있지만 auto-fit에서는 해당 트랙이 접혀 배치되지 않을 수 있습니다.

3.4. 그리드 축 트랙 크기 지정

트랙 크기 지정은 CSS Grid와 동일하게 동작하지만, 내재 크기 산정에 기여하는 항목을 고려할 때 다음과 같습니다:

  • 해당 트랙에 명시적으로 배치된 모든 항목이 기여하고,

  • 자동 그리드 위치를 가진 모든 항목도 기여합니다 (실제로 해당 트랙에 배치되는지와 관계없이).

예를 들어, 그리드 축에 두 개의 열이 있고,

  • 항목 A, B, C는 명시적 위치가 없습니다.

  • 항목 D는 첫 번째 열에 명시적으로 배치되어 있습니다.

이 경우, A, B, C, D 항목 모두가 첫 번째 열의 크기 산정에 기여하며, 두 번째 열에는 A, B, C만(그리고 D는 제외) 기여합니다.

자동 그리드 위치와 span이 있는 항목의 경우, 가능한 모든 시작 위치에 배치된 것으로 간주하며, 그에 따라 기여합니다.

예를 들어, 그리드 축에 5개의 열이 있고, 가운데는 100px로 고정되어 있으며, 나머지 두 개는 auto 크기입니다. 트랙 크기 산정 시, 2개의 트랙을 span하고 내재 크기가 220px인 항목은 복사된 것으로 간주하여 다음과 같이 처리합니다:

  • 그리드 라인 1에서, 첫 번째와 두 번째 트랙에 각각 110px씩 기여

  • 그리드 라인 2에서, 두 번째 트랙에 120px 기여

  • 그리드 라인 3에서, 네 번째 트랙에 120px 기여

  • 그리드 라인 4에서, 네 번째와 다섯 번째 트랙에 각각 110px씩 기여

참고: 이 알고리즘은 각 트랙이 실제로 배치되는 모든 항목을 충분히 수용할 만큼 크게 되도록 보장하며, 배치와 트랙 크기 산정 사이에 의존성 순환이 발생하지 않게 합니다. 하지만 항목 크기의 변동이 클 경우에는, 트랙이 필요 이상으로 커질 수 있습니다: 모든 항목이 그리드 축에 명시적으로 배치되어 있거나 모든 항목의 크기가 동일한 경우 (또는 span 항목의 경우 해당 크기의 배수일 때)만 정확히 맞게 됩니다.

3.4.1. 서브그리드 항목 기여도

일반 그리드 컨테이너 또는 masonry 컨테이너의 트랙 크기를 산정할 때, submasonry에서 자동 그리드 위치를 가진 항목은 다음과 같이 처리됩니다:

  • 해당 항목은 submasonry가 span할 수 있는 모든 그리드 트랙에 배치된 것으로 간주합니다. (submasonry에 명확한 그리드 위치가 있으면 span된 트랙에만, 자동 그리드 위치면 부모 그리드의 모든 트랙에)

  • 해당 항목은 배치될 수 있는 각 edge에서 최대 margin/border/padding 기여도를 받습니다. 항목이 서브그리드 전체를 span하면 양쪽 edge 모두 적용합니다. (CSS Grid Layout §9 참고)

3.4.2. 최적화된 트랙 크기 산정

트랙 크기 산정은 span 크기와 배치가 같은 항목들을 하나의 가상 항목으로 집계하여 최적화할 수 있습니다:

  1. 다음 속성을 기준으로 모든 masonry 항목을 항목 그룹으로 분리합니다:

    • 항목의 span

    • 항목의 배치(어떤 트랙에 놓일 수 있는지)

    • 항목의 baseline-sharing group

    참고: 예를 들어, span이 2이고 두 번째 트랙에 배치된 항목은 span 2이지만 자동 그리드 위치인 항목과 다른 그룹에 속합니다.

  2. 각 항목 그룹에 대해, 해당 그룹 내 모든 항목의 내재 크기 기여값 중 최대값을 갖는 가상 masonry 항목을 생성합니다.

    항목이 baseline alignment를 적용하는 경우, 가상 masonry 항목의 baseline은 해당 항목들을 하나의 가상 트랙에 모두 배치하여 공유 baseline 및 shim을 찾은 뒤, 그룹의 내재 크기 기여값을 그에 따라 증가시킵니다.

  3. 각 가상 masonry 항목의 가상 복사본을, 그리드 축 트랙의 해당 위치마다 배치하여, 트랙 크기 산정 알고리즘을 실행합니다. 결과 트랙 크기가 masonry 컨테이너의 트랙 크기가 됩니다.

참고: 이 최적화는 위 설명과 동일한 결과를 내야 합니다; 아니라면 오류이므로 CSSWG에 보고 바랍니다.

4.1. Masonry 항목 배치 지정: grid-column-* 및 grid-row-* 속성

grid-column-* 및 grid-row-* 속성 (및 단축 속성들)은 항목의 그리드 축에 적용되며, 일반 그리드 레이아웃과 동일하게 배치가 이루어집니다.

4.2. 배치 정밀도: item-slack 속성

이름: item-slack
값: <length-percentage> | infinite
초기값: 1em
적용 대상: masonry 컨테이너
상속: 아니오
백분율: 그리드 축의 content box 크기에 대해 상대적임 (masonry 컨테이너)
계산값: 계산된 <length-percentage> 값
정식 순서: 문법 순서대로
애니메이션 유형: 길이로 처리

masonry 컨테이너는 각 masonry 항목을 현재 가장 덜 채워진 masonry 트랙에 배치함으로써 채워집니다. 여러 트랙이 덜 채워진 상태로 동률일 때는 순서대로 배치하는 것이 보기 좋습니다. 하지만 트랙 높이가 아주 약간만 다를 때, 순서대로 채워지지 않으면 어색해 보일 수 있습니다. 왜냐하면 그 높이 차이가 의미 있게 다르게 인식되지 않기 때문입니다.

item-slack 속성은 트랙을 "같은 높이"로 간주하는 임계값(tie threshold)을 지정하여, 해당 값 이내에서는 순서대로 채워지도록 합니다.

<length-percentage>

masonry 컨테이너에서 tie threshold를 지정합니다. 배치 위치가 최단 위치에서 지정한 거리 이내라면 "동률(tied)"로 간주하여 모두 똑같이 좋은 위치가 됩니다.

참고: 초기값은 "충분히 가까움"을 나타내기에 적절한 작은 거리(1em)입니다.

infinite

tie threshold를 무한대로 지정합니다. 이 경우 트랙 길이를 고려하지 않고 항목이 순서대로만 배치됩니다.

참고: 이 값은 연속된 항목들이 쌓기 축에서 매우 다른 위치에 배치될 수 있으므로 독자에게 혼란을 줄 수 있습니다. 초기값(`1em`)이 너무 작으면, `infinite` 대신 더 큰 값(예: `10em` 또는 `50vh`)을 사용하는 것이 좋습니다.

4.3. Masonry 레이아웃 및 배치 알고리즘

grid axis의 각 트랙마다, 0으로 초기화된 실행 위치(running position)를 유지합니다. 또한 자동 배치 커서(auto-placement cursor)도 유지하며, 처음에는 첫 번째 라인을 가리킵니다.

order-modified document order의 각 항목에 대해:

  1. 항목이 definite grid position을 grid axis에 갖는 경우, 해당 위치를 사용합니다.

    이 경우 placement 커서도 갱신해야 할까요?

    그 외에는 다음 하위 단계로 grid axis 배치를 해결합니다:

    1. grid axis의 암시적 그리드의 첫 번째 라인에서 시작해, 해당 라인에 항목을 배치한다고 했을 때 span하는 grid axis 트랙 중 가장 큰 실행 위치(running position)를 찾고, 이를 max_pos라 합니다.
    2. 이전 단계를 라인 번호를 증가시키며 반복하여, 항목이 그리드 내에 더 이상 들어갈 수 없을 때까지 계속합니다.
    3. possible lines를, max_pos가 최소가 되는 라인과, 해당 max_pos에 tie threshold 이내인 모든 라인으로 합니다.
    4. auto-placement cursor 이상인 possible lines 중 첫 번째 라인을 항목의 grid axis 위치로 선택; 해당 라인이 없다면 그냥 첫 번째 라인을 선택합니다.
    5. auto-placement cursor를 항목의 마지막 라인으로 갱신합니다.
  2. 항목을 grid axis 트랙의, 자신이 span하는 트랙들의 실행 위치(running position) 중 최대 위치에 배치합니다.
  3. 항목의 containing block 크기를 계산한 뒤 레이아웃합니다. span된 grid axis 트랙의 실행 위치를 max_pos + outer size + grid-gap로 설정합니다.

참고: 이 알고리즘은 항목이 가능한 가장 위쪽에 배치될 수 있는 트랙을 선택합니다. 동률이 있을 경우, 가장 최근에 배치된 항목의 뒤에서 가장 이른 트랙을 선택하여 (동률이 있어도 항상 "앞으로" 진행하도록 합니다).

4.3.1. 포함 블록(Containing Block)

containing block은 grid item이 masonry layout에 참여할 때, grid axis에서 항목의 grid area와 stacking axis에서 grid container의 content box로 구성됩니다.

4.3.2. 배치 및 쓰기 모드(Placement and Writing Modes)

참고: grid layout과 마찬가지로, masonry 레이아웃 및 배치는 쓰기 모드(writing mode)에 민감합니다. 예를 들어, direction: rtl에서는, 항목이 왼쪽에서 오른쪽이 아닌 오른쪽에서 왼쪽으로 배치됩니다. inline axis가 grid axis이든 stacking axis이든 적용됩니다.

다음은 예제로, direction: rtl을 grid axis에 적용한 것입니다:

    //FIXME display: inline-grid; or something
    direction: rtl;
    grid-template-columns: repeat(4, 2ch);
    border: 1px solid;

  item:nth-child(2n+1) {
    background: pink;
    height: 4em;
  }
  </style>

<div class="grid">
  <item>1</item>
  <item style="grid-column:span 2">2</item>
  <item>3</item>
  <item>4</item>
</div>

6. 정렬 및 간격(Alignment and Spacing)

Gutters는 두 축 모두에서 지원됩니다. stacking axis에서는, 인접한 항목 쌍의 margin box 사이에 gap이 적용됩니다. margin은 어느 축에서도 합쳐지지 않습니다.

grid axis에서는, 정렬(alignment)이 일반 grid container와 동일하게 동작합니다.

stacking axis에서는, content-distribution이 전체 콘텐츠에 대해 적용되며, block 컨테이너에서의 동작과 유사합니다. 더 구체적으로, alignment subject는 masonry box로, 이는 모든 margin box를 감싸는 최소한의 사각형입니다.

참고: alignment subject는 stacking axis에서 항상 하나만 존재하므로, align-content / justify-content 값은 결국 start, center, end 및 baseline alignment로 요약됩니다. (normal 및 stretch의 동작은 start와 동일하며, distributed alignment 값은 fallback alignment와 같이 동작합니다.) grid item이 grid container의 content box를 stacking axis에서 넘치는 경우, masonry box가 grid container의 content box보다 커집니다.

stacking axis에서 더 정교한 정렬을 지원할 필요가 있을까요? 어떻게 해야 할까요?

6.1. 쌓기 축에서의 기준선 정렬(Baseline Alignment in the stacking axis)

baseline alignment는 grid axis 트랙 내부에서는 일반 grid container와 동일하게 동작하며, grid container의 기준선도 해당 축에서 일반 grid container와 동일하게 결정됩니다.

Baseline alignment는 stacking axis에서는 지원되지 않습니다. 이 축에서 grid container의 첫 번째 기준선 집합은 첫 번째 점유된 트랙의 첫 grid item의 alignment baseline에서 생성되며, 마지막 기준선 집합은 마지막에 배치된 grid item에서 생성됩니다.

이 속성은 항목이 행 또는 열로 배치되는지, 그리고 해당 트랙 내부에서 항목이 처음-끝 또는 끝-처음 순서로 정렬되는지 제어합니다.

이 속성에 대해 두 가지 논쟁이 남아 있습니다: a) 이름을 어떻게 할지, b) 배치의 주축(primary direction)을 설명하는지, 아니면 항목이 배치되는 트랙의 방향을 설명하는지. 즉, 여기서 주축(primary axis)이 주 배치 축(primary placement axis)인지, 주 트랙 축(primary track axis)인지. flex layout과 grid layout에서는 동일하지만, masonry layout에서는 주 배치 방향이 트랙을 가로질러 다릅니다. [Issue #11480]

auto

레이아웃 모드에 따라 row 또는 column으로 계산됩니다:

  • flex container 및 grid container에서는 row로 계산됩니다.

  • masonry container에서는, grid-template-rows가 none이 아니고, grid-template-columns가 none이면, 행 트랙을 나타내는 값으로 계산됩니다; 아니면 열 트랙을 나타내는 값으로 계산됩니다.

row

트랙 중심 옵션 행(즉, inline axis와 평행한 트랙/라인)에 배치됨을 나타냅니다. flex layout과 grid layout에서는 inline axis에서 처음-끝 순서로 배치되고, block axis에서는 masonry layout에서 처음-끝 순서로 배치됨을 나타냅니다.

흐름 중심 옵션 행 우선(row-primary) 항목 배치, 즉 inline axis에서 처음-끝 순서로 배치, flex layout에서는 flex 행(row) 라인 생성, masonry layout에서는 열(grid track) 생성

column

트랙 중심 옵션 행(즉, inline axis와 평행한 트랙/라인)에 배치됨을 나타냅니다. flex layout과 grid layout에서는 inline axis에서 처음-끝 순서로 배치되고, block axis에서는 masonry layout에서 처음-끝 순서로 배치됨을 나타냅니다.

흐름 중심 옵션 행 우선(row-primary) 항목 배치, 즉 inline axis에서 처음-끝 순서로 배치, flex layout에서는 flex 행(row) 라인 생성, masonry layout에서는 열(grid track) 생성

row-reverse

row와 동일하지만, 끝-처음 순서로 배치

column-reverse

column과 동일하지만, 끝-처음 순서로 배치

항목 교차 축 배치 모드: item-cross/item-wrap

이름: item-wrap, item-cross
값: [ auto | nowrap | wrap ] || [ normal | reverse ] | wrap-reverse
초기값: auto
적용 대상: flex container, grid container, masonry container
상속: 아니오
백분율: N/A
계산값: 명시된 값 그대로
정식 순서: 문법 순서대로
애니메이션 유형: 불연속(discrete)

주축(primary axis)과 반대되는 축에서의 배치를 제어합니다.

auto

flex container에서는 nowrap으로, 그 외에는 wrap으로 계산됩니다.

nowrap

항목은 주 배치 축(primary placement axis)에서 공간이 부족해도 계속 배치됩니다. flex layout에서는 단일 행 flex container가 되고, grid layout에서는 주 배치 축에 필요한 만큼 암시적 트랙이 생성됩니다.

wrap

주 배치 축의 공간이 부족하면 항목이 래핑됩니다. flex layout에서는 다중 행 flex container가 되고, grid layout에서는 주 배치 축에서 명시적 트랙이 부족할 때 다음 행/열로 넘어갑니다.

normal

주 트랙 축(primary track axis)과 반대되는 축에서 처음-끝 순서로 배치됩니다.

reverse

주 트랙 축과 반대되는 축에서 끝-처음 순서로 배치됩니다.

wrap-reverse

wrap reverse로 계산됩니다.

참고: 이 값은 기존 flex-wrap 값과의 일관성을 위해 존재합니다.

이 속성의 해석 및 네이밍은 item-direction/item-track의 축 해석에 따라 달라집니다. [Issue #11480]

항목 배치 패킹 모드: item-pack 속성

이름: item-pack
값: normal | dense || balance
초기값: normal
적용 대상: flex container, grid container, masonry container
상속: 아니오
백분율: N/A
계산값: 명시된 값 그대로
정식 순서: 문법 순서대로
애니메이션 유형: 불연속(discrete)

이 속성은 항목이 트랙에 어떻게 배분되는지 레이아웃별로 제어합니다.

normal

레이아웃 모드의 기본 패킹 전략을 사용합니다.

dense

앞에서 건너뛴 빈 공간에 항목을 다시 배치(backtracking)할 수 있게 합니다. (앞 항목이 너무 커서 해당 공간에 들어가지 못했던 경우 생기는 공간에 해당)

예를 들어, flex layout에서는 충분한 빈 공간이 남아 있는 앞 라인에 항목을 배치할 수 있습니다.

balance

flex layout에서는 각 라인(마지막 라인 포함)에 콘텐츠 양을 균형 있게 배분합니다. (text-wrap-style: balance와 유사)

masonry layout으로 전환하는 제안 중 하나는 이 item-pack 속성에 collapse 값을 추가하는 것입니다. [Issue #11243]

dense 패킹이 masonry에도 적용되어야 할까요? masonry에서는 모든 빈 공간에 항목을 레이아웃해야 하므로 비용이 많이 들 수 있습니다; Grid는 단순히 정수값만 조작하면 됩니다. [Issue #9326]

테스트

이 명세의 내용과 관련된 테스트는 이와 같은 “테스트” 블록에 문서화될 수 있습니다. 이러한 블록은 비규범적입니다.

    준수성 클래스

    이 명세에 대한 준수성은 세 가지 준수성 클래스에 대해 정의됩니다:

    스타일 시트
    CSS 스타일 시트.
    렌더러
    UA가 스타일 시트의 의미를 해석하여 해당 스타일 시트를 사용하는 문서를 렌더링함.
    작성 도구
    UA가 스타일 시트를 작성함.

    스타일 시트가 이 명세를 준수하려면, 이 모듈에서 정의한 문법을 사용하는 모든 구문이 CSS의 일반 문법 및 각 기능에 대한 개별 문법에 따라 유효해야 합니다.

    렌더러가 이 명세를 준수하려면, 스타일 시트를 적절한 명세대로 해석할 뿐 아니라, 이 명세에서 정의한 모든 기능을 올바르게 파싱하고 문서를 올바르게 렌더링해야 합니다. 단, UA가 장치의 한계로 인해 문서를 올바르게 렌더링하지 못하더라도, UA가 비준수라고 하지는 않습니다. (예: 단색 모니터에서 색상을 렌더링할 필요는 없음)

    작성 도구가 이 명세를 준수하려면, 이 모듈의 CSS 일반 문법 및 각 기능의 개별 문법에 맞게 스타일 시트를 작성하고, 스타일 시트의 모든 준수성 요구사항을 만족해야 합니다.

    부분 구현

    저자가 미래 호환성 구문 분석 규칙을 활용하여 대체값을 지정할 수 있도록, CSS 렌더러는 반드시 사용 가능한 수준의 지원이 없는 at-rule, 속성, 속성값, 키워드 및 기타 구문적 구성요소를 무효로 간주하고 적절히 무시해야 합니다. 특히, UA는 지원하지 않는 구성값만 무시하고 지원하는 값만 적용하는 식으로 선택적으로 무시해서는 안 됩니다: 어떤 값이 무효로 간주되면(지원하지 않는 값은 반드시 무효), CSS 요구사항에 따라 전체 선언을 무시해야 합니다.

    불안정 및 독점 기능의 구현

    향후 안정화될 CSS 기능과 충돌을 피하기 위해, CSSWG는 불안정 기능과 독점 확장 구현 시 최선의 관행을 따르도록 권장합니다.

    비실험적 구현

    명세가 Candidate Recommendation 단계에 도달하면, 비실험적 구현이 가능하며, 구현자는 명세대로 올바르게 구현됨을 입증할 수 있는 CR 레벨 기능에 대해 접두어 없는(unprefixed) 구현을 배포해야 합니다.

    CSS의 구현 간 상호운용성을 확립하고 유지하기 위해, CSS 워킹 그룹은 비실험적 CSS 렌더러에 대해 구현 보고서(필요 시 해당 테스트케이스 포함)를 W3C에 제출한 후 CSS 기능에 대한 접두어 없는 구현을 배포할 것을 요청합니다. W3C에 제출된 테스트케이스는 CSS 워킹 그룹에 의해 검토 및 수정될 수 있습니다.

    테스트케이스 및 구현 보고서 제출에 대한 추가 정보는 CSS 워킹 그룹 웹사이트 https://www.w3.org/Style/CSS/Test/에서 확인할 수 있습니다. 문의는 public-css-testsuite@w3.org 메일링 리스트로 보내면 됩니다.
