요약

이 명세는 앵커 위치 지정을 정의합니다. 위치가 지정된 요소가 페이지의 하나 이상의 “앵커 요소”를 기준으로 자신의 크기와 위치를 정할 수 있도록 합니다.

CSS는 구조화된 문서(HTML, XML 등)의 렌더링을 화면, 인쇄물 등에서 기술하기 위한 언어입니다.

1. 소개

CSS 절대 위치 지정은 작성자가 박스를 페이지 어디에나 배치할 수 있도록 해주며, 다른 박스들의 레이아웃과는 상관없이 오직 포함 블록만을 고려합니다. 이러한 유연성은 매우 유용할 수 있지만, 동시에 매우 제한적일 수도 있습니다. 종종 다른 박스를 기준으로 위치를 지정하고 싶기 때문입니다. 앵커 위치 지정 (position-anchor, position-area 속성과/또는 앵커 함수 anchor()와 anchor-size()를 통해) 작성자가 이러한 요구를 달성할 수 있게 하며, 절대적으로 위치된 박스를 페이지의 하나 이상의 다른 박스에 "앵커링"할 수 있게 합니다 (해당 박스의 앵커 참조). 또한 여러 가능한 위치를 시도하여 겹침/오버플로우를 피하는 "최적"의 위치를 찾을 수 있습니다.

예를 들어, 작성자는 툴팁을 타겟 요소 위에 중앙 맞춤하여 배치하고 싶지만, 만약 툴팁이 화면 밖으로 나가게 된다면, 툴팁을 타겟 요소 아래에 배치하고 싶을 수 있습니다. 다음 CSS로 이를 구현할 수 있습니다: 
.anchor {
  anchor-name: --tooltip;
}
.tooltip {
  /* Fixpos는 포함 블록 관계를 신경 쓸 필요가 없음을 의미합니다;
     툴팁은 DOM 어디든 위치할 수 있습니다. */
  position: fixed;

  /* 모든 앵커링 동작은 기본적으로 --tooltip 앵커를 참조합니다. */
  position-anchor: --tooltip;

  /* 툴팁의 하단을 앵커의 상단에 맞춥니다;
     수평 쓰기 모드에서는 툴팁과 앵커를 가로로 중앙 정렬합니다. */
  position-area: block-start;

  /* 툴팁이 창을 넘어가면 자동으로 위치를 바꿔서
     툴팁의 상단이 앵커의 하단에 맞추게 합니다. */
  position-try: flip-block;

  /* 너무 넓어지는 것을 방지 */
  max-inline-size: 20em;
}

1.1. 값 정의

이 명세는 CSS 속성 정의 규칙을 [CSS2]에서 따르며, 값 정의 문법은 [CSS-VALUES-3]를 사용합니다. 이 명세에서 정의되지 않은 값 타입은 CSS 값 & 단위 [CSS-VALUES-3]에서 정의됩니다. 다른 CSS 모듈과 조합하면 이러한 값 타입의 정의가 확장될 수 있습니다.

각 속성 정의에 명시된 속성별 값 외에도, 이 명세에서 정의된 모든 속성은 CSS 전역 키워드도 속성 값으로 허용합니다. 가독성을 위해 명시적으로 반복하지 않았습니다.

CSS에서 셀렉터 매칭을 제외한 대부분의 연산처럼, 이 명세의 기능은 평탄화된 요소 트리에서 동작합니다.

2. 앵커 결정

2.1. 앵커 생성: anchor-name 속성

이름: anchor-name
값: none | <dashed-ident>#
초기값: none
적용 대상: 주요 박스를 생성하는 모든 요소
상속됨: 아니오
백분율: 해당 없음
계산값: 명시된 대로
정식 순서: 문법에 따름
애니메이션 타입: 불연속

anchor-name 속성은 요소가 앵커 요소임을 선언하며, 해당 요소의 주요 박스는 앵커 박스가 됩니다. 그리고 타겟으로 사용될 앵커 이름 목록을 지정합니다. 값은 다음과 같이 정의됩니다:

none

이 속성은 아무런 효과가 없습니다.

<dashed-ident>#

만약 요소가 주요 박스를 생성한다면, 그 요소는 앵커 요소가 되며, 명시된 대로 앵커 이름 목록을 갖게 됩니다. 각 앵커 이름은 트리 범위 이름입니다.

그렇지 않으면, 속성은 아무런 효과가 없습니다.

앵커 이름은 고유할 필요가 없습니다. 모든 요소가 주어진 박스의 타겟 앵커 요소가 될 수 있는 것은 아닙니다. 따라서 이름은 사용 범위가 적절히 지정된다면 여러 곳에서 재사용될 수 있습니다.

참고: 여러 요소가 동일한 앵커 이름을 공유하고, 모두 하나의 위치 지정 박스에서 볼 수 있다면, 타겟 앵커 요소는 DOM 순서상 마지막 요소가 됩니다. anchor-scope 속성을 사용하면 참조 박스에서 볼 수 있는 이름을 더 제한할 수 있습니다.

앵커 이름은 기본적으로 컨테인먼트에 의해 범위가 지정되지 않습니다; 어떤 요소가 스타일 또는 레이아웃 컨테인먼트 (혹은 이와 유사한 컨테인먼트)를 갖더라도, 그 자손의 앵커 이름은 페이지 다른 요소에서 볼 수 있습니다.

참고: 어떤 요소가 다른 요소의 내용 무시 영역에 있는 경우 (예: content-visibility: hidden 등), 해당 요소는 허용 가능한 앵커 요소가 아니며, 사실상 이름이 없는 것처럼 동작합니다.

2.1.2. 앵커의 위치

이 명세의 여러 기능은 앵커 박스의 위치와 크기를 참조합니다. 앵커 박스의 위치와 크기는 레이아웃 후에 결정되며, 이 과정에서는 position 기반 조정 (예: position: relative 또는 position: sticky)도 포함됩니다.

레이아웃 이후의 효과(예: transform)는 앵커 박스의 위치에 영향을 주지 않습니다.

참고: 앵커가 transform 또는 이와 유사한 속성의 효과를 포함하도록 선택할 수 있게 하는 기능이 향후 허용될 수 있습니다.

2.2. 앵커 이름 범위 지정: anchor-scope 속성

이름: anchor-scope
값: none | all | <dashed-ident>#
초기값: none
적용 대상: 모든 요소
상속됨: 아니오
백분율: 해당 없음
계산값: 명시된 대로
정식 순서: 문법에 따름
애니메이션 타입: 불연속

이 속성은 지정된 앵커 이름과 해당 앵커 이름의 탐색을 이 요소의 서브트리로 범위 지정합니다. § 2 앵커 결정을 참조하세요.

값의 의미는 다음과 같습니다:

none
anchor name 범위에 변화가 없습니다.
all
이 값은 이 요소 또는 그 하위 요소에 의해 정의된 모든 anchor names—하위 요소가 anchor-scope를 사용해 이미 범위가 제한되지 않은 경우—를 이 요소의 하위 요소에만 적용되도록 지정합니다. 또한 하위 요소가 이 서브트리 내의 anchor elements에만 anchor names를 일치시킬 수 있도록 제한합니다.

이 값은 같은 트리 범위 내의 anchor names에만 영향을 미치며, tree-scoped name처럼 동작합니다. (즉, anchor-scope: all은 anchor-scope: --foo, --bar, ...와 동일하게 동작하며, 모든 관련 anchor names를 나열하는 것과 같습니다.)

<dashed-ident>
이 값은 이 요소 또는 그 하위 요소에 의해 정의된 일치하는 anchor name—하위 요소가 anchor-scope를 사용해 이미 범위가 제한되지 않은 경우—를 이 요소의 하위 요소에만 적용되도록 지정합니다. 또한 하위 요소가 이 서브트리 내의 anchor elements에만 해당 anchor names를 일치시킬 수 있도록 제한합니다. <dashed-ident>는 tree-scoped name입니다.

참고: [css-scoping-1]에 따라, 두 tree-scoped name을 비교할 때, 동일한 트리에서 나온 경우에만 일치합니다.

이 속성은 implicit anchor elements에는 영향을 주지 않습니다.

디자인 패턴을 재사용할 때, anchor-scope를 사용하면 동일한 컴포넌트 간의 이름 충돌을 방지할 수 있습니다. 예를 들어, 목록의 각 항목에 위치가 지정된 요소가 있고, 그 요소들이 자신이 속한 목록 항목을 기준으로 위치를 지정하고 싶을 때, 
li {
  anchor-name: --list-item;
  anchor-scope: --list-item;
}
li .positioned {
  position: absolute;
  position-anchor: --list-item;
  position-area: inline-start;
}

anchor-scope가 없다면, 모든 li 요소들이 모든 위치가 지정된 요소에 보여지게 되어, 전부 마지막 li 요소를 기준으로 위치하게 되어, 서로 겹쳐 쌓이게 됩니다.

2.3. 앵커 찾기

이 명세의 여러 항목은 대상 앵커 요소를 찾으며, 앵커 지정자를 사용합니다. 앵커 지정자는 <dashed-ident> (그리고 tree-scoped reference) 또는 페이지의 다른 곳에 anchor-name 값과 일치해야 하거나, 키워드 auto이거나, 아무것도 없는(지정자가 없는) 경우가 있습니다.

참고: 이 조건들이 포괄하는 일반 규칙은 어떤 요소가 위치 지정 박스의 대상 앵커 요소가 되려면 해당 요소의 박스가 참조하려는 위치 지정 박스가 레이아웃되기 전에 반드시 완전히 레이아웃되어 있어야 한다는 점입니다. CSS의 레이아웃 규칙은 앵커와 위치 지정 박스, 그리고 그들의 포함 블록 간의 관계에 따라 이에 대한 유용한 보장을 제공합니다. 아래 조건 목록은 스태킹 컨텍스트 규칙을 이 목적에 필요한 부분으로 정확히 바꾼 것으로, 앵커 위치 지정에서 순환이 발생할 가능성이 없도록 합니다.

다음은 쿼리 요소 query el과 선택적 anchor specifier anchor spec이 주어졌을 때 대상 앵커 요소를 결정하는 알고리즘입니다:

  1. anchor spec이 전달되지 않은 경우, 기본 앵커 요소가 있으면 반환하고, 없으면 아무것도 반환하지 않습니다.

  2. anchor spec이 auto인 경우:

    1. Popover API가 query el에 대해 암시적 앵커 요소를 정의하고 그 요소가 query el에 대해 적합한 앵커 요소라면 해당 요소를 반환합니다.

    2. 그렇지 않으면 아무것도 반환합니다.

    참고: 향후 API에서도 암시적 앵커 요소를 정의할 수 있습니다. 그 경우 이 알고리즘에서 명시적으로 처리하여 협조가 이루어지도록 할 것입니다.

  3. 그 외의 경우, anchor spec은 <dashed-ident>입니다. 다음 조건을 모두 만족하는 트리 순서상 마지막 요소 el을 반환합니다:

    • el은 앵커 요소이며 anchor spec과 동일한 anchor name을 가집니다.

    • el의 anchor name과 anchor spec이 모두 동일한 트리 루트와 연결되어 있습니다.

      참고: anchor name은 tree-scoped name이고, anchor spec은 tree-scoped reference입니다.

    • el은 query el에 대해 적합한 앵커 요소입니다.

    위 조건을 만족하는 요소가 없다면 아무것도 반환하지 않습니다.

    참고: anchor-scope는 특정 anchor name의 가시성을 제한할 수 있으며, 이는 주어진 조회에 대해 어떤 요소가 앵커 요소가 될 수 있는지에 영향을 줄 수 있습니다.

참고: 하나의 anchor-name이 한 섀도우 트리에서 스타일로 정의된 경우, 다른 섀도우 트리의 스타일에서 anchor function이 그 값을 볼 수 없습니다. 이는 캡슐화를 보장합니다. 그러나 요소는 서로 다른 섀도우 트리에 있어도 서로 앵커로 삼을 수 있습니다. 단, anchor-name과 anchor function이 동일 트리의 스타일에서 왔을 때만 가능합니다. 예를 들어 ::part()를 사용해서 섀도우 내부 요소를 스타일링하는 경우 등입니다. (암시적 앵커 요소도 본질적으로 단일 트리에 제한되지 않지만, 그 세부 사항은 이를 할당하는 API에 따라 달라집니다.)

요소 possible anchor가 절대 위치 지정된 요소 positioned el에 대해 적합한 앵커 요소가 되려면 다음 모든 조건을 만족해야 합니다:

  • possible anchor는 요소이거나 완전히 스타일 지정 가능한 트리-존중 의사 요소(tree-abiding pseudo-element)입니다.

  • possible anchor는 positioned el에 대해 anchor-scope의 효과에 따라 범위 내에 있어야 합니다.

  • possible anchor가 positioned el보다 엄격하게 먼저 레이아웃되어야 하며, 즉 다음 중 하나가 참이어야 합니다:

    • positioned el이 possible anchor보다 더 높은 top layer에 있습니다.

    • 두 요소가 같은 top layer에 있지만 포함 블록(containing block)이 다르고, positioned el의 포함 블록이 possible anchor의 포함 블록의 포함 블록 체인에서 상위 요소(ancestor)인 경우, 즉 다음 중 하나:

      • positioned el의 포함 블록이 뷰포트이고, possible anchor의 포함 블록은 뷰포트가 아닙니다.

      • positioned el의 포함 블록이 초기 포함 블록이고, possible anchor의 포함 블록이 요소에 의해 생성되어 있으며, possible anchor의 포함 블록 체인에서 초기 포함 블록에 도달하기 전 마지막 포함 블록이 절대 위치 지정이 아니거나 트리 순서상 positioned el보다 앞에 있습니다.

      • 두 요소의 포함 블록이 모두 요소에 의해 생성되었고, positioned el의 포함 블록이 flat tree에서 possible anchor의 포함 블록의 상위 요소(ancestor)이며, possible anchor의 포함 블록 체인에서 positioned el의 포함 블록에 도달하기 전 마지막 포함 블록이 절대 위치 지정이 아니거나 positioned el보다 트리 순서상 앞에 있습니다.

    • 두 요소가 같은 top layer에 있고 동일한 포함 블록을 가지며, 둘 다 절대 위치 지정이고, possible anchor가 flat tree 순서상 positioned el보다 앞에 있습니다.

    • 두 요소가 같은 top layer에 있고 동일한 포함 블록을 가지지만, possible anchor는 절대 위치 지정이 아닙니다.

  • possible anchor가 다른 요소의 skipped contents에 있다면, positioned el도 해당 요소의 skipped contents에 있어야 합니다.

    참고: 즉, positioned el은 possible anchor와 같은 skipped "leaf" 내에 있을 때 앵커로 삼을 수 있지만, "leaf"를 넘어서 앵커로 삼을 수는 없습니다. 이는 둘을 포함하는 요소를 skipped 처리해도 positioned el이 갑자기 다른 앵커로 이동하는 일이 없으며, 페이지의 다른 곳에 위치한 요소는 skipped 요소를 앵커로 삼을 수 없게 됩니다.

2.5. 앵커 관련성

요소 el이 사용자에게 관련 있는지 판단할 때, el의 하위 요소가 위치 지정 박스의 대상 앵커 요소인 경우 (위치 지정 박스 자체가 skipped가 아니고, containing block이 el 또는 el의 하위 요소가 아닌 경우), el은 사용자에게 관련 있음으로 간주해야 합니다.

참고: 예를 들어, content-visibility: auto 서브트리 내의 앵커는 해당 앵커를 사용하는 위치 지정 박스가 skipped가 아닌 한 해당 서브트리의 내용 건너뛰기를 방지합니다. (단, 앵커와 위치 지정 박스가 둘 다 같은 content-visibility: auto 요소 아래에 있으면 서로를 순환적으로 계속 보이게 할 수는 없습니다.)

3. 앵커 기반 위치 지정

절대 위치 지정 박스는 페이지 내 하나 이상의 앵커 박스를 기준으로 자신을 위치시킬 수 있습니다.

position-area 속성은 기본 앵커 박스 기준의 편리한 그리드 기반 위치 개념을 제공합니다. 더 복잡하거나 여러 박스를 기준으로 위치를 지정하려면 anchor() 함수를 inset 속성에서 사용하여 특정 앵커 박스의 edge를 명시적으로 참조할 수 있습니다.

그 외의 경우, position-area grid의 영역을 선택하고, 해당 영역이 박스의 containing block이 됩니다.

참고: 이는 inset 속성이 position-area 기준의 오프셋을 지정하며, max-height: 100% 같은 일부 속성 값도 position-area 기준으로 적용됨을 의미합니다.

none 이외의 값은 다음 추가 효과가 있습니다:

  • normal 값은 자기-정렬 속성(self-alignment properties)에 대해 해당하는 값으로 해석됩니다. 자세한 내용은 § 3.1.4 영역별 기본 정렬을 참고하세요.

  • 모든 auto 인세트 속성(inset properties)은 0으로 해석됩니다.

  • 박스는 어느 축에서도 레거시 정렬 모드(legacy alignment mode)에 있다고 간주되지 않습니다.

3.1.1. 포지션 에어리어 그리드 해석

position-area grid는 3×3 격자로, 각 축에 네 개의 그리드 선으로 구성됩니다. 순서는 (writing mode와 containing block 기준):

  • 박스의 수정 전 containing block의 start 에지, 또는 default anchor box의 start 에지가 더 start 방향이면 그 에지

  • default anchor box의 start 에지

  • default anchor box의 end 에지

  • 박스의 수정 전 containing block의 end 에지, 또는 default anchor box의 end 에지가 더 end 방향이면 그 에지

참고: default anchor box가 수정 전 containing block의 일부 혹은 전체 밖에 있는 경우, position-area grid의 일부 행 또는 열이 0 크기일 수 있습니다.

3.1.2. <position-area> 값의 문법

포지션은 값 쌍으로 지정하며, flow-relative 또는 physical 용어로 표현할 수 있습니다. <position-area> 값의 허용 문법은 다음과 같습니다: 

<position-area> = [
  [ left | center | right | span-left | span-right
  | x-start | x-end | span-x-start | span-x-end
  | x-self-start | x-self-end | span-x-self-start | span-x-self-end
  | span-all ]
  ||
  [ top | center | bottom | span-top | span-bottom
  | y-start | y-end | span-y-start | span-y-end
  | y-self-start | y-self-end | span-y-self-start | span-y-self-end
  | span-all ]
|
  [ block-start | center | block-end | span-block-start | span-block-end | span-all ]
  ||
  [ inline-start | center | inline-end | span-inline-start | span-inline-end
  | span-all ]
|
  [ self-block-start | center | self-block-end | span-self-block-start
  | span-self-block-end | span-all ]
  ||
  [ self-inline-start | center | self-inline-end | span-self-inline-start
  | span-self-inline-end | span-all ]
|
  [ start | center | end | span-start | span-end | span-all ]{1,2}
|
  [ self-start | center | self-end | span-self-start | span-self-end | span-all ]{1,2}
]

<position-area> 값은 position-area grid의 행/열을 지정하여 영역을 선택합니다:

start, end, self-start, self-end
top, bottom, left, right
y-start, y-end, y-self-start, y-self-end
x-start, x-end, x-self-start, x-self-end
block-start, block-end, self-block-start, self-block-end
inline-start, inline-end, self-inline-start, self-inline-end
center

이 키워드가 지정하는 축에 따라 해당하는 단일 행 또는 열입니다.

anchor()에서와 마찬가지로, 일반 논리 키워드 (start, end 등)는 박스의 쓰기 모드(writing mode)와 박스의 포함 블록(containing block)을 기준으로 합니다. x-start 등은 같은 방식으로 방향을 결정하지만, 지정된 물리적 축에서 동작합니다.

self-* 논리 키워드 (self-start, x-self-end 등)도 동일하지만, 박스 자신의 쓰기 모드를 참조합니다.

span-start, span-end, span-self-start, span-self-end
span-top, span-bottom
span-y-start, span-y-end, span-y-self-start, span-y-self-end
span-x-start, span-x-end, span-x-self-start, span-x-self-end
span-block-start, span-block-end, span-self-block-start, span-self-block-end
span-inline-start, span-inline-end, span-self-inline-start, span-self-inline-end

이 키워드가 지정하는 축에 따라 인접한 두 행 또는 열: 중앙 행/열과, 단일 트랙 키워드에 따라 해당하는 나머지 행/열입니다.

(예를 들어, span-top은 첫 두 행—중앙 행과 top 행—을 span합니다.)

span-all

이 키워드가 지정하는 축에 따라 세 행 또는 열 모두를 span합니다.

일부 키워드는 참조하는 축이 모호합니다: center, span-all, 그리고 block 또는 inline 축을 명시적으로 지정하지 않는 start 등 키워드입니다. 만약 다른 키워드가 축에 대해 명확하다면, 모호한 키워드는 반대 축을 참조합니다. (예: block-start center에서 center 키워드는 inline 축을 의미합니다.) 두 키워드 모두 모호하다면, 첫 번째는 박스의 block 축을, 두 번째는 inline 축을 참조합니다. (예: span-all start는 span-all inline-start와 동일합니다.)

한 개의 키워드만 주어진 경우, 주어진 키워드가 축에 대해 명확하다면 두 번째 키워드는 span-all인 것처럼 동작합니다; 그렇지 않으면 주어진 키워드를 반복한 것처럼 동작합니다. (예: top은 top span-all과 같고, center는 center center와 같습니다.)

3.1.3. <position-area>의 계산값과 직렬화

계산값(computed value)은 <position-area> 값이 선택한 각 축의 트랙을 나타내는 두 키워드이며, 긴 논리 키워드(block-start)와 짧은 논리 키워드(start)는 동등하게 처리합니다. 직렬화는 문법(위 참조)에 나온 순서로, 논리 키워드는 짧은 형태로 직렬화됩니다 (예: start start 대신 block-start inline-start 대신).

3.1.4. 영역별 기본 정렬

각 <position-area> 값은 기본 자기-정렬(self-alignment)도 암시하며, 박스의 자기-정렬 속성(self-alignment property)이 normal일 때 사용됩니다:

  • 한 축에서 center 트랙만 선택된 경우, 해당 축의 기본 정렬은 center입니다.

  • 세 트랙 모두 선택된 경우, 해당 축의 기본 정렬은 anchor-center입니다.

  • 그 외의 경우, 해당 축의 기본 정렬은 지정되지 않은 쪽 트랙 방향입니다: 만약 축의 “start” 트랙을 지정하면 해당 축의 기본 정렬은 end 등입니다.

예를 들어, 영어와 같은 쓰기 모드(수평-tb, ltr)라면, span-x-start top 값은 수직 축에서는 start 영역에, 수평 축에서는 start와 center 영역에 해당하며, 기본 정렬은 align-self: end(박스의 하단 마진 엣지가 top 영역 하단과 맞춰짐) 및 justify-self: end(박스의 end 측 마진 엣지가 span-start 영역 end 측과 맞춰짐)입니다.
박스가 인세트 수정 포함 블록(inset-modified containing block)을 넘치지만, 원래 포함 블록(original containing block)에는 맞는 경우, 기본적으로 원래 포함 블록 내에 있도록 "이동"합니다. 이는 일반 정렬을 깨더라도 적용됩니다. 자세한 내용은 CSS Box Alignment 3 § 4.4 Overflow Alignment: the safe and unsafe keywords and scroll safety limits를 참고하세요.

이 동작은 위치 지정 박스가 예상보다 포함 블록이 작아졌더라도 박스가 보이고 원하는 영역 내에 남아있을 가능성을 높여줍니다.

예를 들어, position-area: bottom span-right 값은 위치 지정 박스가 앵커의 왼쪽 엣지부터 포함 블록의 오른쪽 엣지까지 늘어나게 하고, 기본적으로 왼쪽 정렬합니다. 그러나 위치 지정 박스가 그 공간보다 크면 (예: 앵커가 화면의 오른쪽 엣지에 매우 가까운 경우) 보이도록 왼쪽으로 이동합니다.

3.2. 앵커 기준 중앙 정렬: anchor-center 정렬 값

Name: justify-self, align-self, justify-items, align-items
New values: anchor-center

자기-정렬 속성(self-alignment properties)을 통해 절대 위치 지정 박스가 인세트 수정 포함 블록 내에서 정렬할 수 있습니다. 기존 값들과 인세트 속성을 잘 조합하면 대부분의 정렬 케이스에 충분하지만, 앵커 박스 기준 중앙 정렬(anchored positioning에서 흔한 케이스)은 세심하고 복잡한 설정이 필요합니다.

새로운 anchor-center 값은 이 케이스를 매우 간단하게 만듭니다: 위치 지정 박스에 기본 앵커 박스가 있으면, 해당 축에서 기본 앵커 박스 기준으로(가능한 한) 중앙에 배치됩니다.

또한, 모든 auto 인세트 속성은 0으로 처리됩니다.

박스가 절대 위치 지정이 아니거나, 기본 앵커 박스가 없으면, 이 값은 center처럼 동작하며 인세트 속성 해석에는 추가 효과가 없습니다.

참고: anchor-center 사용 시, 앵커가 박스의 원래 포함 블록의 엣지에 너무 가까우면, 완전히 중앙 정렬이 아니라도 원래 포함 블록 내에 남도록 "이동"합니다. 자세한 내용은 CSS Box Alignment 3 § 4.4 Overflow Alignment: the safe and unsafe keywords and scroll safety limits를 참고하세요.

3.3. 앵커 기준 인세트: anchor() 함수

절대 위치 지정 박스는 anchor() 함수를 자신의 인세트 속성의 값으로 사용하여 하나 이상의 앵커 박스의 위치를 참조할 수 있습니다. anchor() 함수는 <length>로 해석됩니다. 이 함수는 인세트 속성에서만 허용되며, 그 외에서는 사용할 수 없습니다.

Name: top, left, right, bottom
New values: <anchor()> 
<anchor()> = anchor( <anchor-name>? && <anchor-side>, <length-percentage>? )
<anchor-name> = <dashed-ident>
<anchor-side> = inside | outside
       | top | left | right | bottom
       | start | end | self-start | self-end
       | <percentage> | center

anchor() 함수는 세 개의 인자를 가집니다:

  • <anchor-name> 값은 위치 정보를 참조할 앵커 요소를 찾는 방법을 지정합니다. 가능한 값은 다음과 같습니다:

    <dashed-ident>

    찾을 앵커 이름을 지정합니다. 이 이름은 트리 범위 참조(tree-scoped reference)입니다.

    생략됨

    박스에 정의된 기본 앵커 요소를 선택합니다(가능한 경우).

    자세한 내용은 대상 앵커 요소를 참고하세요.

  • <anchor-side> 값은 대상 앵커 요소의 해당하는 변(엣지) 위치를 참조합니다. 가능한 값은 다음과 같습니다:

    inside
    outside

    어떤 앵커 박스의 변을 참조할지, 사용되는 인세트 속성에 따라 결정됩니다. inside는 인세트 속성과 동일한 변(즉, 박스의 "안쪽"에 붙임)을 참조하며, outside는 반대쪽을 참조합니다.

    top
    right
    bottom
    left

    앵커 박스의 지정된 변을 참조합니다.

    참고: 이 값들은 해당 축의 인세트 속성에서만 사용할 수 있습니다. 예를 들어, left는 left, right, 또는 수평 축의 논리 인세트 속성에서 사용할 수 있습니다.

    start
    end
    self-start
    self-end

    사용되는 앵커 박스의 동일 축 변을 참조하며, 키워드는 위치 지정 박스의 쓰기 모드(self-start, self-end) 또는 위치 지정 박스의 포함 블록(block)(start, end)을 기준으로 해석됩니다.

    <percentage>
    center

    지정된 축의 start와 end 사이의 해당 퍼센티지 위치를 참조합니다. 0%는 start와 같고, 100%는 end와 같습니다.

    center는 50%와 동일합니다.

  • 선택적 <length-percentage> 마지막 인자는 fallback 값으로, 해결 불가 anchor 함수일 때 계산될 값을 지정합니다.

anchor() 함수가 해결 가능한 anchor 함수를 나타내는 경우, 계산값 시점에 (스타일 & 레이아웃 인터리브 사용) 해당 위치 지정 박스의 <length>로 해석되며, 함수가 나타나는 속성에 해당하는 인세트 수정 포함 블록 변과 대상 앵커 요소의 지정된 border 엣지가 맞닿도록 정렬됩니다. 스크롤 컨테이너들이 대상 앵커 요소와 위치 지정 박스의 포함 블록 사이에 있을 경우, 모두 초기 스크롤 위치에 있다고 가정합니다 (자세한 사항은 § 3.4 스크롤 고려 참고).

참고: 이는 트랜지션 또는 애니메이션에서 anchor 함수를 사용하는 속성이 모든 종류의 변화에서도 "예상대로" 동작함을 의미합니다: 앵커 박스가 이동하거나, 앵커 요소가 문서에서 추가/제거되거나, anchor-name 속성이 변경되어도 등등 모두 대응됩니다.

대상 앵커 요소가 fragmented된 경우, fragment들의 border box 기준 축 정렬 bounding rectangle을 사용합니다.

예를 들어, .bar { inset-block-start: anchor(--foo block-start); }에서, anchor()는 .bar 요소의 block-start 변과 --foo 앵커의 block-start 변을 맞추는 길이로 해석됩니다.

반대로, .bar { inset-block-end: anchor(--foo block-start); }에서는 .bar 요소의 block-end 변과 --foo 앵커의 block-start 변을 맞추는 길이로 해석됩니다.

inset-block-start와 inset-block-end 값은 각각 요소의 포함 블록의 block-start와 block-end에서 인세트를 지정하므로, 같은 anchor()도 서로 다른 길이로 해석되는 경우가 많습니다.

anchor() 함수는 <length>로 해석되므로, 다른 길이와 마찬가지로 수학 함수에서 사용할 수 있습니다.

예를 들어, 아래 예제는 요소의 inset-modified containing block이 앵커 박스 기준 중앙에 위치하면서, 포함 블록을 넘치지 않도록 최대한 넓게 설정합니다: 

.centered-message {
  position: fixed;
  max-width: max-content;
  justify-self: center;

  --center: anchor(--x 50%);
  --half-distance: min(
    abs(0% - var(--center)),
    abs(100% - var(--center))
  );
  left: calc(var(--center) - var(--half-distance));
  right: calc(var(--center) - var(--half-distance));
  bottom: anchor(--x top);
}

이 방법은 예를 들어 input 요소의 오류 메시지에 적합할 수 있습니다. 중앙 정렬로 인해 어떤 입력 요소와 연결된 메시지인지 쉽게 알아볼 수 있습니다.

3.3.1. anchor()의 해석

anchor() 함수는 아래 조건을 모두 만족할 때만 해석 가능한 앵커 함수(resolvable anchor function)입니다:

  • 함수가 절대 위치 지정 박스에 적용되어야 합니다.

  • 함수의 <anchor-side>가 물리적 키워드라면, 해당 축에서 적용 가능한 인세트 속성에 지정되어야 합니다. (예: left는 left, right, 또는 수평 축의 논리 인세트 속성에서만 사용할 수 있습니다.)

  • 함수가 사용된 박스와 함수 내에 지정된 <anchor-name> 값에 대해 대상 앵커 요소가 존재해야 합니다.

이 조건 중 하나라도 거짓이면, anchor() 함수는 지정된 폴백(fallback) 값으로 계산됩니다. 폴백 값이 없으면, 해당 선언은 계산값 시점에 무효(invalid at computed-value time)가 됩니다.

3.4. 스크롤 고려

성능상의 이유로, 구현체는 대개 스크롤을 별도의 스크롤/합성(compositing) 스레드에서 처리합니다. 이 스레드는 매우 제한적인 기능만 제공하며 (간단한 이동/변환 등, 레이아웃이나 비싼 연산은 불가), 따라서 스크롤에 즉각적으로 반응할 수 있다고 간주할 수 있습니다.

스크롤이 단순히 앵커 위치 지정 요소를 이동시키는 것이라면, 이론적으로 문제는 없습니다; 움직임은 스크롤 스레드에서 처리되어 위치 지정 요소가 스크롤 콘텐츠와 함께 부드럽게 움직입니다. 하지만 앵커 위치 지정은 요소가 자신의 반대쪽 엣지 위치를 다른 스크롤 컨텍스트의 요소에 의존하게 할 수 있어서, 스크롤이 단지 한쪽 엣지만 움직이고 크기 변화가 발생해 레이아웃이 필요하게 될 수 있습니다. 이런 경우는 스크롤 스레드에서 처리할 수 없습니다!

이를 보완하면서도 다양한 요소에 앵커를 자유롭게 지정할 수 있도록, 앵커 위치 지정은 기억된 스크롤 오프셋과 스크롤 보정을 조합해서 동작합니다.

아래 내용은 기술적이지만, 요점은 다음과 같습니다:

  • 위치 지정 요소가 처음 표시되거나, 대체(fallback)를 변경할 때, 모든 앵커 참조(anchor references)의 최신 위치를 기준으로 위치가 정확하게 계산됩니다.

    이 앵커 참조가 다른 스크롤 컨텍스트에 있다면, 그들의 전체 스크롤 오프셋이 기억되고, 이후 레이아웃에서는 그 기억된 오프셋을 계속 사용합니다. (기억되는 것은 오직 스크롤 오프셋만이며, 실제 레이아웃 위치는 매번 새로 계산되어 정확하게 유지됩니다.) 위치 지정 요소가 표시되지 않게 되었다가 다시 표시되거나, 대체(fallback)를 변경하면 재계산됩니다.

  • 단 하나의 예외는 기본 앵커 요소입니다; 해당 요소가 기억된 스크롤 오프셋에서 벗어나 스크롤되면, 위치 지정 요소도 함께 이동합니다. 이때는 *순수* 위치 이동만 발생하므로, 위치 지정 요소의 크기가 바뀌거나 레이아웃이 다시 필요하지 않습니다.

결과적으로 앵커 위치 지정은 요소가 어떤 것에 앵커를 잡든 "그냥 동작"해야 하며, 다만 스크롤에 어떻게 반응할지는 제한될 수 있습니다.

절대 위치 지정 요소가 박스를 생성하기 시작할 때마다 (즉, display:none 또는 display:contents에서 다른 display 값으로 바뀔 때), CSS 애니메이션이 시작되는 시점과 동일하게 앵커 재계산 지점(anchor recalculation point)이 발생합니다.

또한 해당 요소의 대체 위치 스타일 결정 시에도 앵커 재계산 지점이 발생합니다; 그 결과 대체 스타일이 변경되면, 선택된 대체 스타일에 연결된 앵커 재계산 지점 결과를 사용합니다.

요소 abspos에 대해 앵커 재계산 지점이 발생하면, abspos가 참조하는 모든 anchor에 대해, 해당 anchor의 앵커 참조마다 기억된 스크롤 오프셋(remembered scroll offset)이 anchor의 모든 스크롤 컨테이너 상위 요소의 스크롤 오프셋 총합(현재 기준)으로 설정됩니다. 기억된 스크롤 오프셋에는 position: sticky 등 다른 스크롤 의존 위치 변화도 반영됩니다. abspos에 기본 앵커 요소가 있다면, 실제로 앵커 참조를 갖지 않아도 항상 기억된 스크롤 오프셋을 계산합니다.

모든 앵커 참조는 모든 스크롤 컨테이너가 초기 스크롤 위치에 있다고 가정해서 계산되며, 계산된 기억된 스크롤 오프셋이 추가됩니다.

변환(transform)도 스크롤과 동일한 문제가 있으므로, 앵커 위치 지정 역시 기본적으로 변환을 고려하지 않습니다. 여기서 변환의 효과도 반영할 수 있을까요?

위 방식으로 위치 지정 요소는 앵커 참조의 스크롤 위치 변화에 한번만 반응할 수 있으며, 이후 앵커가 스크롤되면 위치 지정 요소가 더 이상 해당 앵커에 연결된 것처럼 보이지 않게 됩니다 (다만 스크롤 이외의 움직임에는 계속 반응함). 이 문제는 일반적으로 해결할 수 없지만, 하나의 앵커 참조의 스크롤에는 반응할 수 있습니다; 구체적으로는 기본 앵커 요소입니다:

절대 위치 지정 박스 abspos가 수평 또는 수직 축에서 스크롤을 보정(compensate for scroll)하려면 다음 두 조건을 모두 만족해야 합니다:

  • abspos에 기본 앵커 박스가 있어야 합니다.

  • abspos가 자신의 기본 앵커 박스 또는 같은 스크롤 컨텍스트에 있는 요소에 앵커 참조를 가져야 합니다, 즉 다음 중 하나 이상:

    • 해당 축에서 abspos의 자기-정렬 속성(self-alignment property) 값이 anchor-center인 경우;

    • abspos의 position-area 값이 none이 아닌 경우

    • abspos의 사용된 값(used value)의 인세트 속성 중 하나 이상에서 anchor() 함수가 대상 앵커 요소를 참조하며, 해당 요소의 가장 가까운 스크롤 컨테이너 상위 요소가 abspos의 기본 앵커 박스와 같아야 합니다.

참고: abspos에 position options list가 있다면, 스크롤 보정 여부는 적용된 대체 스타일에도 영향을 받습니다.

abspos의 기본 스크롤 이동(default scroll shift)은 각각 수평/수직 축에 대한 길이 쌍입니다. 각 길이는 다음과 같이 계산합니다:

  • abspos가 해당 축에서 스크롤 보정 중이면, 길이는 기본 앵커 요소의 기억된 스크롤 오프셋과 지금 다시 계산한다면 얻을 기억된 스크롤 오프셋의 차이입니다.

  • 아니면 길이는 0입니다.

abspos의 레이아웃이 끝나면, 기본 스크롤 이동(default scroll shift)만큼 추가로 이동하며, 이는 transform의 영향(다른 변환에 앞서)과 비슷하게 동작합니다.

스냅샷의 정확한 타이밍 정의 필요: 매 프레임 업데이트, 스타일 재계산 이전.

기억된 스크롤 오프셋처럼, 기본 앵커 요소의 변환(transform)도 반영할 수 있을까요?

참고: 기억된 스크롤 오프셋은 anchor() 함수의 값에 영향을 미치지만, 기본 스크롤 이동(default scroll shift)은 인세트 속성 계산, 정렬 등 이후에 요소를 직접 이동시킵니다. 이는 대부분의 경우 구분이 어렵지만, round(anchor(outside), 50px)처럼 기본 앵커 요소의 위치에 비선형 변환을 적용하는 경우 동작 차이가 드러날 수 있습니다.

always

anchors-valid

박스에 기본 앵커 박스가 있지만 그 앵커 박스가 보이지 않거나 중간 박스에 의해 잘린 경우, 박스의 visibility 속성은 force-hidden으로 계산됩니다.

앵커 박스 anchor가 위치 지정 박스 abspos를 기준으로 중간 박스에 의해 잘림(clipped by intervening boxes) 처리된 경우란 anchor의 ink overflow rectangle이 anchor의 상위이면서 abspos의 포함 블록의 하위인 박스에 의해 완전히 잘려(clipped) 있는 경우입니다. 이때 clipping은 overflow에 의한 clipping, 또는 paint containment 등 overflow clip edge에 맞춰 잘리는 효과만 포함합니다.

clipped 정의가 View Transitions의 관련 개념과 일치하는지 확인 필요.

참고: "연쇄 앵커" 상황에서, 첫 abspos가 이 속성으로 숨겨지면 (앵커가 스크롤되어 사라지는 등) 그것을 앵커로 삼는 다른 abspos도 숨겨지며, 두 번째 박스가 이상한 위치에 둥둥 떠 있는 일을 막아줍니다.

4. 앵커 기반 크기 지정

절대 위치 지정 박스(absolutely positioned box)는 anchor-size() 함수를 자신의 크기 속성(sizing property)에서 한 개 이상의 앵커 박스의 크기를 참조할 수 있습니다. anchor-size() 함수는 <length>로 해석됩니다. accepted @position-try 속성에서만 허용되며, 그 외에서는 잘못된 값입니다.

4.1. anchor-size() 함수

Name: width, height, min-width, min-height, max-width, max-height, top, left, right, bottom, margin-top, margin-left, margin-right, margin-bottom
New values: <anchor-size()> 
anchor-size() = anchor-size( [ <anchor-name> || <anchor-size> ]? , <length-percentage>? )
<anchor-size> = width | height | block | inline | self-block | self-inline

anchor-size() 함수는 anchor()와 유사하며, 인자는 동일하나 <anchor-side> 키워드 대신 <anchor-size> 키워드가 들어가며, 이는 서로 반대되는 두 엣지 사이의 거리를 의미합니다.

물리적 <anchor-size> 키워드 (width 및 height) 는 각각 target anchor element의 너비와 높이를 의미합니다. anchor()와 달리, 축을 맞춰야 할 제한이 없습니다; 예를 들어, width: anchor-size(--foo height);도 유효합니다.

논리적 <anchor-size> 키워드 (block, inline, self-block, 그리고 self-inline) 은 박스의 쓰기 모드 (self-block, self-inline의 경우) 또는 박스의 쓰기 모드를 가진 포함 블록 (block, inline의 경우)에 따라 물리적 키워드에 매핑됩니다.

<anchor-size> 키워드가 생략되면, anchor-size()가 사용된 속성의 축에 맞는 키워드로 동작하는 것이 기본입니다. (예를 들어, width: anchor-size()는 width: anchor-size(width)와 동일합니다.)

anchor-size() 함수가 해석 가능한 anchor-size 함수(resolvable anchor-size function)를 나타내는 경우, 계산값(computed value) 시점에 (스타일 및 레이아웃 교차 처리를 통해) 해당 축에 따라 <length>로 해석되며, 대상 앵커 요소의 관련된 border edge들(좌/우 혹은 상/하, 지정된 축)에 의해 분리된 거리가 됩니다.

4.1.1. anchor-size()의 해석

anchor-size() 함수는 아래 모든 조건을 만족해야만 해석 가능한 anchor-size 함수입니다:

  • 함수가 절대 위치 지정 박스에 적용되어야 합니다.

  • 함수가 사용된 박스와 함수에 지정된 <anchor-name> 값에 대해 대상 앵커 요소가 존재해야 합니다.

이 조건 중 하나라도 거짓이면, anchor-size() 함수는 지정된 폴백 값으로 해석됩니다. 폴백 값이 없으면, 해당 선언은 계산값 시점에 무효가 됩니다.

5. 오버플로우 관리

앵커 위치 지정(anchor positioning)은 강력하지만, 예측하기 어려울 수 있습니다. 앵커 박스는 페이지 어디에나 있을 수 있으므로, 박스를 특정 방식(예: 앵커 위, 앵커 오른쪽 등)으로 배치하면 위치 지정 박스가 포함 블록을 넘치거나 화면 밖에 일부 위치할 수 있습니다.

이 문제를 개선하기 위해 절대 위치 지정 박스는 position-try-fallbacks 속성을 사용하여 여러 대체 위치/정렬 속성 세트를 참조할 수 있습니다 (박스의 기존 스타일에서 생성하거나, @position-try 규칙에서 명시). 초기 위치에서 박스가 넘치면 UA는 이 옵션을 하나씩 적용하며, 포함 블록을 넘치지 않는 첫 번째 옵션을 채택합니다.

position-try-order를 사용하면 박스가 가능한 공간을 최대화하는 것이 선언된 순서보다 중요할 경우, 이러한 옵션을 사용 가능한 공간에 따라 정렬할 수도 있습니다.

5.1. 대체 옵션 제공: position-try-fallbacks 속성

Name: position-try-fallbacks
Value: none | [ [<dashed-ident> || <try-tactic>] | <'position-area'> ]#
Initial: none
Applies to: 절대 위치 지정 박스
Inherited: no
Percentages: n/a
Computed value: as specified
Canonical order: per grammar
Animation type: discrete

이 속성은 절대 위치 지정 박스가 inset-modified 포함 블록을 넘칠 때 시도할 대체 위치 스타일 목록을 제공합니다. 이 position options list는 처음에는 비어 있습니다.

목록의 각 쉼표로 구분된 항목은 별도의 옵션입니다: @position-try 블록의 이름이거나, 박스의 기존 계산 스타일을 자동으로 변환하는 <try-tactic>입니다.

값의 의미는 다음과 같습니다:

none

속성은 아무 효과가 없습니다; 박스의 position options list는 비어 있습니다.

<dashed-ident>

주어진 이름의 @position-try 규칙이 있으면, 해당 position option이 position options list에 추가됩니다.

없으면, 이 값은 아무 효과가 없습니다.

<try-tactic>

박스의 계산 스타일에서 position option을 자동 생성하며, 지정된 키워드에 따라 swap due to a try-tactic을 적용하여 생성된 position option을 박스의 position options list에 추가합니다. 그리고 position options list에 추가됩니다. 

<try-tactic> = flip-block || flip-inline || flip-start
flip-block

값을 block 축에서 서로 교환합니다(예: margin-block-start와 margin-block-end 사이), 사실상 inline 축을 기준으로 미러링합니다.

flip-inline

값을 inline 축에서 서로 교환하여, 사실상 block 축을 기준으로 미러링합니다.

flip-start

start 속성의 값을 서로 교환하고, end 속성의 값도 서로 교환합니다 (예: margin-block-start와 margin-inline-start 사이), 사실상 start-start 코너에서 end-end 코너로 그은 대각선을 기준으로 미러링합니다.

여러 키워드가 주어지면, 변환(transform)은 순서대로 합성되어 하나의 position option을 생성합니다.

<dashed-ident> || <try-tactic>

이전 두 옵션의 효과를 결합합니다: 주어진 이름의 @position-try 규칙이 있다면, 해당 position option을 기본 스타일에 적용하고, 그 다음 지정한 <try-tactic>으로 변환하여 결과를 박스의 position options list에 추가합니다.

그렇지 않으면 아무 것도 하지 않습니다.

<'position-area'>

주어진 값을 가진 position-area 속성만으로 이루어진 position option을 자동으로 생성합니다.

박스의 요소 el을 두 방향 directions 사이에서 try-tactic으로 swap할 때, 스타일 집합을 반환합니다:

  1. directions가 같은 축의 반대 방향이면 “opposing”, 그렇지 않고 서로 다른 축을 지정하면 “perpendicular”입니다.

  2. el에 지정된 accepted @position-try properties 값을 확인하고, 그 결과를 styles로 둡니다.

  3. 변수 치환, env() 함수, 그리고 임의 치환 함수 등도 styles에서 치환합니다.

    env() 함수에서, 참조된 환경 변수가 방향이나 축과 연결되어 있다면 (예: safe-area-inset-top), directions에 맞게 참조 환경 변수를 바꿉니다.

    예를 들어, top: env(safe-area-inset-top);이 지정되고, directions가 up과 left라면, env()는 env(safe-area-inset-left)가 지정된 것처럼 해석됩니다. (그리고 다음 단계에서 실제로 left 속성으로 swap됩니다.)

  4. styles의 값을 directions에 대응하는 관련 속성들끼리 swap합니다.

    예를 들어, "top"과 "left"를 swap하면, margin-top과 margin-left 값을 swap하고, width와 height도 swap합니다.

    참고: directions가 같은 축의 반대라면, width나 align-self 같은 일부 속성은 swap되지 않지만, 그 값은 다음 단계에서 바뀔 수 있습니다.

  5. swap 시 변경된 방향에 맞게 속성 값을 수정합니다:

    • 인세트 속성의 경우, anchor() 함수에서 지정된 side를 새 방향에서도 기존과 같은 상대적 관계가 유지되도록 변경합니다.

      <percentage>가 사용되고, directions가 opposing일 경우, 값을 100% - 원래 값으로 변경합니다.

      예를 들어 "top"과 "left"를 swap하면, margin-top: anchor(bottom)은 margin-left: anchor(right)로 바뀝니다.

      "top"과 "bottom"을 swap하면, margin-top: anchor(20%)는 margin-bottom: anchor(80%)로 바뀝니다.

    • 크기 속성(sizing properties)의 경우, anchor-size() 함수에서 지정된 축이 새 방향에서도 기존과 같은 상대적 관계를 유지하도록 변경합니다.

      예를 들어 "top"과 "left"를 swap하면, width: anchor-size(width)는 height: anchor-size(height)로 바뀝니다.

    • 자기-정렬 속성(self-alignment properties)의 경우, directions가 opposing이면, 지정된 <self-position> (또는 left/right 키워드)을 새 방향에서도 기존과 같은 상대적 관계가 유지되도록 바꿉니다.

      예를 들어 "top"과 "bottom"을 swap하면, align-self: start는 align-self: end로 바뀝니다.

      하지만 align-self: center는 양쪽 방향 모두 같은 관계라서 바뀌지 않습니다.

      유사하게 align-self: first baseline도 <baseline-position>이므로 <self-position>과 달리 변경되지 않습니다.

    • position-area의 경우, position-area grid의 선택된 행/열이 새 방향에서도 기존과 같은 상대적 관계가 유지되도록 값을 변경합니다.

      예: "top"과 "left"를 swap하면, position-area: left span-bottom은 position-area: top span-right로 바뀝니다.

  6. styles를 반환합니다.

most-width

most-block-size

예를 들어, 다음 스타일은 팝업 리스트를 앵커 버튼 아래에 위치시키지만, 만약 오버플로우가 발생하면 팝업 리스트를 앵커 아래에 둘지, 위로 옮길지 각각의 옵션이 더 많은 공간을 제공하는지에 따라 결정합니다. 
.anchor { anchor-name: --foo; }
.list {
  position: fixed;
  position-anchor: --foo;
  position-area: block-end span-inline-end;
  align-self: start;
  position-try-fallbacks: --bottom-scrollable, flip-block, --top-scrollable;
  position-try-order: most-height;
}
@position-try --bottom-scrollable {
  align-self: stretch;
}
@position-try --top-scrollable {
  position-area: block-start span-inline-end;
  align-self: stretch;
}

flip-block 자동 생성 옵션과 --top-scrollable 옵션은 항상 동일한 사용 가능한 높이를 찾으므로, 둘 다 수직으로 컨테이닝 블록의 상단에서 앵커의 상단까지 늘어나기 때문에 지정된 순서를 유지합니다. 이로 인해 박스는 먼저 앵커에 자연 높이로 정렬을 시도하게 되고 (align-self: end를 기본 스타일에서 자동으로 반전시켜 사용), 만약 그것도 오버플로우를 유발하면 공간을 채우고 스크롤 가능하게 바뀌게 됩니다.

5.4. @position-try 규칙

@position-try 규칙은 이름이 주어진 position option을 정의하며, 박스에 적용할 수 있는 하나 이상의 위치 지정 속성 집합을 position-try-fallbacks를 통해 지정합니다.

@position-try 규칙의 문법은 다음과 같습니다:

@position-try <dashed-ident> {
  <declaration-list>
}

서문에서 지정된 <dashed-ident>는 해당 규칙의 이름입니다. 동일한 이름으로 여러 @position-try 규칙이 선언된 경우, 문서 순서상 마지막 선언이 "적용"됩니다.

@position-try 규칙은 다음 허용된 속성만 accept합니다:

  • inset 속성

  • margin 속성

  • 크기 지정 속성

  • self-align 속성

  • position-anchor

  • position-area

<declaration-list> 내의 속성에 !important를 사용하는 것은 유효하지 않습니다. 그렇게 하면 해당 속성이 무효화되지만, @property-try 규칙 전체가 무효화되지는 않습니다.

모든 @position-try 속성은 박스에 Position Fallback Origin의 일부로 적용되며, 이는 cascade origin의 새로운 단계로, 작성자 출처와 애니메이션 출처 사이에 위치합니다.

애니메이션 출처와 유사하게, revert 값을 사용하면 해당 속성이 작성자 출처의 일부인 것처럼 동작하여, 대신 사용자 출처로 되돌아갑니다. (애니메이션 출처와 마찬가지로, revert-layer는 특별한 동작 없이 명시된 대로 작동합니다.)

참고: 허용된 @position-try 속성은 박스 자체의 크기와 위치만 변경하며, 그 외의 내용이나 스타일에는 영향을 주지 않는 최소한의 속성 집합입니다. 이는 position fallback의 구현을 훨씬 단순하게 하면서 사용 가능한 공간에 따라 anchor-positioned 박스를 이동시켜야 하는 근본적인 요구를 충족합니다. 이러한 규칙이 작성자 출처의 일반 선언을 오버라이드하기 때문에, @position-try 선언이 다른 속성의 일반적인 캐스케이딩 및 상속과 부정적으로 상호작용하는 것을 제한합니다. 앞으로 컨테이너 쿼리의 확장으로 position fallback을 기반으로 요소를 쿼리할 수 있게 되어, 이 제한된 목록으로는 불가능했던 조건부 스타일링이 가능해질 것으로 기대됩니다.

참고: 서로 다른 앵커를 사용하는 여러 박스가 동일한 fallback 위치를 사용하고 싶다면, 각 박스의 앵커 요소에 대해 상대적으로 적용하면 됩니다. <anchor-name>을 anchor()에 생략하고, 각 박스의 앵커는 position-anchor에서 지정하세요.

참고: 가장 일반적인 fallback 위치 유형 (위치된 박스를 기본적으로 앵커 한쪽에 두고, 필요 시 반대쪽으로 전환)은 position-try-fallbacks의 키워드만으로도 자동으로 구현할 수 있으며, @position-try를 전혀 사용할 필요가 없습니다.

5.5. 포지션 폴백 적용

박스가 (기본 스크롤 이동에 의해 이동됨) inset-modified containing block을 넘치고, position options list가 비어 있지 않은 경우, position fallback 스타일을 결정하여 오버플로우를 피할 수 있는 옵션을 찾으려고 시도합니다.

이 수정된 스타일은 interleaving을 통해 요소에 적용되며, 레이아웃과 사용된 값에 의존하지만 계산된 값에 영향을 주고 (트랜지션 등도 트리거 가능) 합니다.

박스의 요소 el에 position option을 적용하려면, position option new styles가 주어졌을 때:

  1. new styles를 position fallback origin에 캐스케이드로 삽입한 뒤, 캐스케이드를 해석하고, el의 사용된 스타일을 결정할 만큼 레이아웃을 수행합니다.

    이 스타일 계산을 위해, 가상 anchor 재계산 지점이 계산되고, 결과적으로 얻은 가상 기억된 스크롤 오프셋을 사용하여 el의 스타일을 결정합니다.

  2. el의 사용된 스타일을 반환합니다.

요소 abspos에 대해 position fallback 스타일을 결정하기:

  1. current styles를 abspos의 현재 사용된 스타일(이전 폴백 결과일 수 있음)로 한다.

  2. 다음에 대해 option을 position options list에서 반복한다:

    1. 만약 option이 현재 abspos의 마지막 성공한 position option이라면, 다음으로 진행한다.

    2. adjusted styles를 position option option을 abspos에 적용한 결과로 한다.

    3. el rect를 abspos의 마진 박스의 크기와 위치로, cb rect를 abspos의 inset-modified containing block의 크기와 위치로 한다. 이 때 adjusted styles로 레이아웃 한다.

    4. 만약 cb rect가 어느 축에서든 음수 크기였다가 0 크기로 교정된 경우, 다음으로 진행한다.

      참고: 이는 0 크기의 el rect가 음수 크기의 cb rect 안에 있다고 간주되어 성공 옵션으로 선택되는 것을 방지합니다.

    5. 만약 el rect가 cb rect 내에 완전히 포함되지 않는다면, 다음으로 진행한다.

    6. adjusted styles와 함께 가상으로 계산된 remembered scroll offsets의 집합을 반환한다.

  3. 단언: 이전 단계가 오버플로우를 피할 수 있는 position option을 찾지 못하고 끝났다.

  4. current styles를 반환한다.

참고: el의 자손이 오버플로우해도 이 계산에는 영향을 주지 않으며, 오직 el 자신의 margin box만 고려한다.

참고: 현재 적용 중인 position option은 의도적으로 건너뛰므로, 해당 remembered scroll offsets가 갱신되지 않습니다. 다른 폴백이 모두 실패해서 현재 스타일을 유지할 경우, 모든 remembered scroll offsets는 그대로 유지됩니다.

전체 레이아웃 패스 동안, 박스가 폴백 스타일을 결정했거나(혹은 사용하지 않기로 결정했거나)나면, 이후에 레이아웃되는 박스가 이 결정을 변경할 수 없습니다.

예를 들어, 두 개의 위치 지정 박스 A와 B가 있고, A가 B보다 먼저 레이아웃된다고 가정합니다. 만약 B가 오버플로우되어 A의 컨테이닝 블록에 스크롤바가 생긴다면, 이것이 A가 다시 폴백 스타일을 재결정하도록 만들지는 않습니다. (최악의 경우, 이는 레이아웃이 순환하거나 끝나지 않을 수도 있습니다.)

즉, 레이아웃은 "뒤로 가지 않습니다".

ResizeObserver 이벤트가 결정되고 전달될 때:

  • 박스 el이 절대 위치라면, 해당 마지막 성공한 position option을 현재 사용 중인 허용된 @position-try 속성(및 값) 집합으로 설정한다.

  • 그 외에 el에 마지막 성공한 position option이 있고, 아래 중 하나라도 해당된다면, 마지막 성공한 position option을 제거한다:

    • el이 절대 위치가 아니게 된 경우

    • el의 position-try-fallbacks 계산값이 변경된 경우

    • @position-try 규칙 중 el의 position-try-fallbacks에서 참조된 것이 추가, 제거 또는 수정된 경우

    그 후, position fallback 스타일을 결정하고 el의 마지막 성공한 position option을 이제 사용 중인 허용된 @position-try 속성(및 값) 집합으로 설정한다.

참고: 이 기록/제거의 타이밍은 마지막 기억된 크기의 처리와 의도적으로 동일합니다.

구현은 position options list의 길이에 구현 정의 한계를 둘 수 있으며, 과도한 레이아웃 작업을 제한하기 위함입니다. 이 한계는 최소한 5여야 합니다.

예를 들어, 다음 CSS는 "popover"를 우선 아래에 배치하려고 시도하고, 화면에 맞지 않으면 위로 전환합니다; 기본값은 왼쪽 정렬이지만, 맞지 않으면 오른쪽 정렬로 바뀝니다. 
#myPopover {
  position: fixed;
  top: anchor(--button bottom);
  left: anchor(--button left);
  position-try-fallbacks: flip-inline, flip-block, flip-block flip-inline;

  /* popover는 버튼과 최소한 같은 너비입니다 */
  min-width: anchor-size(--button width);

  /* popover는 최소 2개의 메뉴 아이템 높이입니다 */
  min-height: 6em;
}

6. 접근성 관련 사항

앵커 포지셔닝(Anchor Positioning)이 위치가 지정된 박스와 해당 앵커들 사이에 어떤 의미론적 관계도 자동으로 생성하지 않는다는 점을 반드시 기억해야 합니다. 왜냐하면 이 기술은 매우 다양한 방식으로 사용될 수 있기 때문입니다. 작성자는 위치 지정에 의해 시각적으로 암시되는 연결만으로 요소들을 의미적으로 연결해서는 안 됩니다; 추가적인 지원 없이, 요소들은 종종 아무런 의미 있는 DOM 관계가 없기 때문에, 화면 판독기와 같은 비시각적 사용자 에이전트에서는 사용하기 어렵거나 불가능해질 수 있습니다.

웹 플랫폼에는 기존 기능과 앞으로 나올 기능 모두, 이런 연결을 명시적으로 설정할 수 있게 해줍니다. 이를 통해 비시각적 사용자 에이전트도 혜택을 누릴 수 있습니다.

예를 들어, HTML의 Popover API는 트리거 버튼을 팝오버 요소와 자동으로 연결하며, 탭 순서도 자동으로 조정합니다; 또한 트리거 버튼을 팝오버의 암시적 앵커 요소로 지정해 앵커 포지셔닝을 쉽게 사용할 수 있습니다.

더 일반적인 경우에는, ARIA 기능(예: aria-details 또는 aria-describedby 속성)을 앵커 요소에 지정해 조금 더 수동적인 방식으로 이런 정보를 제공할 수 있습니다; 위치가 지정된 요소에는 role 속성을 함께 활용하면, 비시각적 사용자 에이전트가 요소들 간의 관계를 사용자에게 안내하고, 요소 사이를 자동으로 탐색할 수 있도록 도와줍니다.

8. 부록: 스타일 & 레이아웃 인터리빙

스타일 & 레이아웃 인터리빙은 레이아웃 과정 중에 서브트리의 스타일 업데이트가 발생할 수 있고, 그로 인해 요소의 계산된 스타일에 소급적 업데이트가 일어나는 기술입니다.

이 개념에 대한 올바른 명세는 아니며, 아마도 Cascade에 들어가야 합니다. 하지만 참고용 스케치를 남겨둡니다.

참고: 스타일 & 레이아웃 인터리빙은 이미 컨테이너 쿼리와 컨테이너 쿼리 길이에 사용되고 있습니다. 10cqw와 같은 길이는 쿼리 컨테이너의 크기 정보를 사용해 계산된 길이로 해석되며, 이로 인해 레이아웃 사이즈가 변경될 때 트랜지션을 트리거할 수 있습니다.

허용된 @position-try 속성도 폴백을 해석할 때 인터리빙됩니다 (position-try 참고).

당연히 더 많은 세부 내용이 필요하지만, 지금은 "컨테이너 쿼리에서 이미 동작하는 것처럼 행동"하면 충분합니다. 그 동작도 정의되어 있지 않지만, 최소한 어느 정도 상호운용성은 있습니다.

준수 클래스

본 명세서의 준수는 세 가지 준수 클래스로 정의됩니다:

스타일 시트
CSS 스타일 시트.
렌더러
UA는 스타일 시트의 의미를 해석하고 이를 사용하는 문서를 렌더링합니다.
저작 도구
UA는 스타일 시트를 작성합니다.

스타일 시트가 이 명세서를 준수하려면 이 모듈에서 정의된 문법을 사용하는 모든 구문이 CSS 일반 문법 및 이 모듈의 각 기능별 문법에 따라 유효해야 합니다.

렌더러가 이 명세서를 준수하려면 스타일 시트를 관련 명세서에 정의된 대로 해석할 뿐 아니라, 본 명세서에서 정의한 모든 기능을 올바르게 파싱하고 문서를 그에 맞게 렌더링할 수 있어야 합니다. 단, 장치의 한계로 인해 UA가 문서를 올바르게 렌더링하지 못하더라도 UA가 비준수로 간주되지는 않습니다. (예: UA가 흑백 모니터에서 색상을 렌더링할 필요는 없습니다.)

저작 도구가 이 명세서를 준수하려면 CSS 일반 문법 및 이 모듈의 각 기능별 문법에 따라 문법적으로 올바른 스타일 시트를 작성하고, 이 모듈에서 설명한 스타일 시트의 모든 기타 준수 요구사항을 충족해야 합니다.

부분 구현

작성자가 전방 호환 파싱 규칙을 활용해 폴백 값을 지정할 수 있도록, CSS 렌더러는 반드시 지원 가능한 수준이 없는 at-rule, 속성, 속성 값, 키워드, 기타 구문 구조를 무효로 처리하고 (적절히 무시) 해야 합니다. 특히, 사용자 에이전트는 지원되지 않는 구성 값만 선택적으로 무시하고, 지원되는 값만 적용해서는 안 됩니다: 어떤 값이 무효로 간주된다면(지원되지 않는 값은 반드시 무효), CSS는 전체 선언을 무시해야 합니다.

불안정 및 독자적 기능 구현

앞으로 안정적인 CSS 기능과의 충돌을 방지하기 위해, CSSWG는 모범 사례를 따라 불안정 기능과 독자적 확장 기능을 구현할 것을 권장합니다.

비실험적 구현

명세서가 Candidate Recommendation 단계에 도달하면, 비실험적 구현이 가능하며, 구현자는 명세대로 올바르게 구현되었음을 입증할 수 있는 CR 수준의 기능에 대해 접두사 없는 구현을 배포해야 합니다.

CSS의 상호운용성을 확립하고 유지하기 위해, CSS 워킹 그룹은 비실험적 CSS 렌더러가 구현 보고서(필요하다면 해당 구현 보고서에 사용된 테스트케이스 포함)를 W3C에 제출한 후 접두사 없는 CSS 기능 구현을 배포할 것을 요청합니다. W3C에 제출된 테스트케이스는 CSS 워킹 그룹의 검토 및 수정 대상입니다.

테스트케이스 및 구현 보고서 제출에 대한 추가 정보는 CSS 워킹 그룹 웹사이트 https://www.w3.org/Style/CSS/Test/에서 확인할 수 있습니다. 질문은 public-css-testsuite@w3.org 메일링 리스트로 문의하세요.
