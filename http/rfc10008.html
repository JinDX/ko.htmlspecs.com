HTTP QUERY 메서드

초록

이 명세는 HTTP의 QUERY 메서드를 정의합니다. QUERY는 요청 대상이 동봉된 콘텐츠를 안전하고 멱등적인 방식으로 처리한 다음 그 처리 결과로 응답하도록 요청합니다. 이는 POST 요청과 유사하지만, QUERY 요청은 부분적인 상태 변경을 염려하지 않고 자동으로 반복하거나 다시 시작할 수 있습니다.

1. 소개

이 명세는 HTTP QUERY 요청 메서드를 안전하고 멱등적인 요청(9.2절, [HTTP])을 수행하는 수단으로 정의하며, 대상 리소스가 요청을 처리하는 방법을 기술하는 표현을 동봉합니다.

일반적인 쿼리 패턴은 다음과 같습니다:

GET /feed?q=foo&limit=10&sort=-published HTTP/1.1
Host: example.org

그러나 전달하는 데이터의 양이 너무 많아 요청 URI에 인코딩할 수 없다면, 이 패턴에는 문제가 생깁니다:

  • 요청이 서로 조율되지 않은 여러 시스템을 거칠 수 있으므로 크기 제한을 미리 알 수 없는 경우가 많습니다(다만 4.1절, [HTTP]에서는 송신자와 수신자가 최소 8000옥텟을 지원하도록 권고한다는 점에 유의하십시오),
  • 특정 종류의 데이터를 대상 URI에 표현하는 것은 해당 데이터를 유효한 URI로 인코딩하는 데 드는 부가 비용 때문에 비효율적입니다,
  • 요청 URI는 요청 콘텐츠보다 로그에 기록될 가능성이 높으며 북마크에도 나타날 수 있습니다,
  • 쿼리를 요청 URI에 직접 인코딩하면 가능한 모든 쿼리 입력 조합을 사실상 서로 다른 리소스로 취급하게 됩니다.

GET 사용의 대안으로, 많은 구현에서는 HTTP POST 메서드를 사용하여 쿼리를 수행하며, 아래 예제에서 이를 보여 줍니다. 이 경우 쿼리 연산의 입력은 요청 URI의 쿼리 구성 요소를 사용하는 대신 요청 콘텐츠로 전달됩니다.

쿼리를 요청하기 위한 일반적인 HTTP POST 사용 예는 다음과 같습니다:

POST /feed HTTP/1.1
Host: example.org
Content-Type: application/x-www-form-urlencoded

q=foo&limit=10&sort=-published

그러나 이 변형에서는 -- 요청을 보내는 대상인 리소스와 서버에 관한 구체적인 지식 없이는 -- 안전하고 멱등적인 쿼리가 수행된다는 사실이 명확하게 드러나지 않습니다.

QUERY 메서드는 GET과 POST 사용 사이의 간극을 메우는 해결책을 제공하며, 위 예제는 다음과 같이 표현됩니다:

QUERY /feed HTTP/1.1
Host: example.org
Content-Type: application/x-www-form-urlencoded

q=foo&limit=10&sort=-published

POST와 마찬가지로 쿼리 연산의 입력은 요청 URI의 일부가 아니라 요청 콘텐츠로 전달됩니다. 그러나 POST와 달리 이 메서드는 명시적으로 안전하고 멱등적이므로 캐싱이나 자동 재시도 같은 기능을 사용할 수 있습니다.

중요한 모든 리소스는 URI로 식별되어야 한다는 설계 원칙을 고려하여, 이 명세는 서버가 쿼리 자체 또는 특정 쿼리 결과에 URI를 할당하여 나중에 GET 요청에서 사용할 수 있도록 하는 방법을 설명합니다.

요약하면 다음과 같습니다:

표 1: 관련 메서드 속성 요약
GET QUERY POST
안전함 예 예 아닐 수 있음
멱등적임 예 예 아닐 수 있음
쿼리 자체의 URI 예 (정의상) 선택 사항 (Location 응답 필드) 아니요
쿼리 결과의 URI 선택 사항 (Content-Location 응답 필드) 선택 사항 (Content-Location 응답 필드) 선택 사항 (Content-Location 응답 필드)
캐시 가능 예 예 예, 단 이후의 GET 또는 HEAD 요청에만 해당
콘텐츠 (본문) "정의된 의미론 없음" 예상됨 (의미론은 대상 리소스에 따름) 예상됨 (의미론은 대상 리소스에 따름)

1.1. 용어

이 문서는 다음에 정의된 용어를 사용합니다: 3절, [HTTP].

또한 URI 쿼리 매개변수라는 용어를 URI의 쿼리 구성 요소에 있는 매개변수(4.2.2절, [HTTP])에 사용하고, 쿼리 콘텐츠라는 용어를 요청 콘텐츠(6.4절, [HTTP]), 즉 QUERY 요청의 콘텐츠에 사용합니다.

1.2. 표기 규칙

핵심 단어 "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY" 및 "OPTIONAL"은 이 문서에서 다음에 설명된 대로 해석해야 합니다: BCP 14 [RFC2119] [RFC8174]. 단, 여기에 표시된 것처럼 모두 대문자로 나타나는 경우에만 해당합니다.

2. QUERY 메서드

QUERY 메서드는 서버 측 쿼리를 시작하는 데 사용됩니다. 대상 URI로 식별되는 리소스의 표현을 요청하는 GET 메서드와 달리(다음에 정의됨: 7.1절, [HTTP]), QUERY 메서드는 대상 리소스에 해당 대상 리소스의 범위 내에서 쿼리 연산을 수행하도록 요청하는 데 사용됩니다.

요청 콘텐츠와 그 미디어 유형이 쿼리를 정의합니다. 원본 서버는 대상 리소스를 기반으로 연산의 범위를 결정합니다.

서버는 반드시 요청을 실패 처리해야 합니다. Content-Type 요청 필드가 ([HTTP], 8.3절) 누락되었거나 요청 콘텐츠와 일치하지 않는 경우가 이에 해당합니다.

모든 HTTP 메서드와 마찬가지로, 대상 URI의 쿼리 부분은 쿼리 대상 리소스를 식별하는 데 관여합니다. 이것이 쿼리 결과에 직접 영향을 미치는지 여부와 그 방식은 리소스에 따라 달라지며 이 명세의 범위를 벗어납니다.

QUERY 요청은 대상 리소스에 대해 안전합니다 ([HTTP], 9.2.1절). 즉, 클라이언트는 대상 리소스의 상태에 대한 어떠한 변경도 요청하거나 예상하지 않습니다. 그렇다고 해서 서버가 추가 정보를 검색할 수 있는 추가 HTTP 리소스를 생성하는 것이 금지되지는 않습니다 (2.3절 및 2.4절 참조).

또한 QUERY 요청은 멱등적입니다 ([HTTP], 9.2.2절). 예를 들어 연결 실패 후와 같이 필요할 때 재시도하거나 반복할 수 있습니다.

다음에 따라, 15.3절, [HTTP], 2xx (성공) 응답 코드는 요청이 성공적으로 수신되고 이해되어 수락되었음을 나타냅니다.

특히 200 (OK) 응답은 쿼리가 성공적으로 처리되었으며 그 처리 결과가 응답 콘텐츠로 동봉되었음을 나타냅니다.

2.1. 미디어 유형 및 콘텐츠 협상

QUERY 요청의 의미론은 요청 콘텐츠와 미디어 유형 같은 관련 메타데이터 모두에 따라 달라집니다 ([HTTP], 8.3.1절). 일반적으로 콘텐츠와 메타데이터가 일치하지 않는 요청의 문제는 반드시 4xx (클라이언트 오류) 응답으로 거부해야 합니다 ([HTTP], 15.5절).

아래 목록은 여러 실패 사례를 설명하고 구체적인 상태 코드를 권고합니다:

  • 요청에 미디어 유형 정보가 없으면 정의상 올바르지 않으며 400 (클라이언트 오류) 같은 4xx 상태 코드로 실패해야 합니다.
  • 미디어 유형이 지정되었지만 리소스에서 지원하지 않는 경우에는 415 (지원하지 않는 미디어 유형)가 적절합니다. 여기에는 특히 미디어 유형 자체는 알려져 있지만 대상 리소스에 대한 QUERY에 특화된 의미론이 없는 경우가 포함됩니다. 두 경우 모두 Accept-Query 응답 필드(3절)를 사용하여 클라이언트에 지원되는 미디어 유형을 알릴 수 있습니다.
  • 미디어 유형이 지정되었지만 실제 요청 콘텐츠와 일치하지 않는 경우에는 400 (잘못된 요청)을 반환할 수 있습니다. 즉, 서버는 요청 콘텐츠에서 미디어 유형을 추론한 다음 누락되거나 "잘못된" 값을 덮어쓰는 것이 허용되지 않습니다 (즉, "콘텐츠 스니핑").
  • 미디어 유형이 지정되어 이해할 수 있고 콘텐츠가 실제로 해당 유형과 일치하지만, 쿼리의 실제 내용 때문에 쿼리를 처리할 수 없다면 422 (처리할 수 없는 콘텐츠) 상태를 사용할 수 있습니다. 예를 들어 존재하지 않는 테이블을 식별하는, 구문상 올바른 SQL 쿼리가 있습니다.
  • 클라이언트가 Accept 필드를 사용하여 특정 응답 미디어 유형을 요청했지만 ([HTTP], 12.5.1절), 리소스에서 이를 지원하지 않는 경우에는 406 (수용할 수 없음) 상태 코드가 적절합니다.

2.2. 동등 리소스

주어진 QUERY 요청의 동등 리소스는 GET 요청에 응답하고, 해당 QUERY 요청과 그 대상을 나타내며, 메시지 콘텐츠와 메타데이터 모두를 고려하는 리소스입니다 (6절, [HTTP]). 특히 여기에는 표현 메타데이터(8절, [HTTP]), 예를 들어 콘텐츠의 미디어 유형이 포함됩니다.

즉, 동등 리소스는 QUERY를 구현하는 리소스에서 요청 콘텐츠를 반영하여 파생됩니다.

동등 리소스라는 용어는 선택된 표현 같은 다른 HTTP 측면의 동작을 정의하기 위한 수단으로 사용됩니다. 서버는 이러한 리소스에 URI를 할당할 수 있지만 반드시 할당할 필요는 없습니다 (1.1절, [URI] 참조). URI를 할당하면 이러한 리소스에 GET 요청으로 접근할 수 있게 됩니다.

2.3. Content-Location 응답 필드

성공 응답(2xx, 15.3절, [HTTP])에는 연산 결과에 해당하는 리소스의 식별자가 담긴 Content-Location 헤더 필드가 포함될 수 있습니다. 자세한 내용은 8.7절, [HTTP]를 참조하십시오. 이는 클라이언트가 표시된 URI에 GET 요청을 보내 방금 수행된 쿼리 연산의 결과를 검색할 수 있다는 서버의 주장을 나타냅니다. 표시된 리소스는 임시적일 수 있습니다.

부록 A.4.1에서 예제를 참조하십시오.

2.4. Location 응답 필드

서버는 QUERY 요청의 동등 리소스(2.2절)에 URI를 할당할 수 있습니다. 서버가 그렇게 하면 해당 리소스의 URI를 2xx 응답의 Location 헤더 필드에 포함할 수 있습니다 (다음 참조: 10.2.2절, [HTTP]). 이는 클라이언트가 표시된 URI에 GET 요청을 보내 쿼리 콘텐츠를 다시 전송하지 않고 방금 수행된 쿼리 연산을 반복할 수 있다는 주장입니다. 이 리소스의 URI는 임시적일 수 있습니다. 이후 요청이 실패하면 클라이언트는 원래 QUERY 요청 대상과 이전에 제출한 콘텐츠를 사용하여 재시도할 수 있습니다.

부록 A.4.2에서 예제를 참조하십시오.

2.5. 리디렉션

경우에 따라 서버는 사용자 에이전트를 다른 URI로 리디렉션하여 QUERY 요청에 간접적으로 응답할 수 있습니다 (다음 참조: 15.4절, [HTTP]).

상태 코드가 301 (영구 이동, [HTTP], 15.4.2절) 또는 308 (영구 리디렉션, [HTTP], 15.4.9절)인 응답은 대상 리소스가 Location 응답 필드에서 참조하는 다른 URI로 영구적으로 이동했음을 나타냅니다 ([HTTP], 10.2.2절). 마찬가지로 상태 코드가 302 (발견됨, [HTTP], 15.4.3절) 또는 307 (임시 리디렉션, [HTTP], 15.4.8절)인 응답은 대상 리소스가 일시적으로 이동했음을 나타냅니다. 네 경우 모두 서버는 사용자 에이전트가 Location에서 참조하는 새 대상 URI로 유사한 QUERY 요청을 보내 원래 QUERY 요청을 완료할 수 있음을 제안합니다.

301 또는 302 응답 후 POST를 GET 요청으로 리디렉션하는 예외는 QUERY 요청에 적용되지 않는다는 점에 유의하십시오.

QUERY에 대해 상태 코드가 303 (다른 리소스 참조, 15.4.4절, [HTTP])인 응답은 Location 응답 필드에서 참조하는 URI에 대한 일반적인 검색 요청을 통해 원래 쿼리를 완료할 수 있음을 나타냅니다 ([HTTP], 10.2.2절). HTTP에서는 새 대상 URI에 GET 요청을 보내는 것을 의미하며, 이는 다음 예제에 나와 있습니다: 부록 A.4.3.

2.6. 조건부 요청

선택된 표현(3.2절, [HTTP])은 QUERY 요청의 경우 해당 QUERY 요청의 동등 리소스(2.2절)에 대한 GET 요청의 선택된 표현과 같습니다.

조건부 QUERY는 선택된 표현(즉, 콘텐츠 협상이 이루어진 후의 쿼리 결과)이 조건부 헤더 필드에 기술된 상황에서만 응답으로 반환되도록 요청하며, 이는 다음에 정의되어 있습니다: 13절, [HTTP].

부록 A.5에서 예제를 참조하십시오.

2.7. 캐싱

QUERY 메서드에 대한 응답은 캐시할 수 있습니다. 캐시는 이를 사용하여 후속 QUERY 요청을 충족할 수 있습니다. 다음을 따릅니다: 4절, [HTTP-CACHING].

QUERY 요청의 캐시 키(2절, [HTTP-CACHING])는 반드시 요청 콘텐츠(6절, [HTTP-CACHING]) 및 관련 메타데이터(8절, [HTTP])를 반영해야 합니다.

캐시 효율을 높이기 위해 캐시는 의미상 중요하지 않은 차이를 요청 콘텐츠와 관련 메타데이터에서 먼저 제거할 수 있습니다. 예를 들어 다음과 같은 방법이 있습니다:

  • 콘텐츠 인코딩 제거 (8.4절, [HTTP]).
  • 요청의 Content-Type 필드에 있는 미디어 하위 유형 접미사로 표시되는 형식 규칙에 관한 지식을 바탕으로 정규화 (예: "+json"; 다음 참조: 4.2.8절, [RFC6838]).
  • 요청의 Content-Type 필드로 표시되는 콘텐츠 자체의 의미론에 관한 지식을 바탕으로 정규화.

이러한 변환은 오직 캐시 키를 생성하기 위한 목적으로만 수행되며, 요청 자체를 변경하지 않는다는 점에 유의하십시오.

클라이언트는 "no-transform" 캐시 지시어를 사용하여 ( 5.2.1.6절, [HTTP-CACHING]) 이러한 변환이 이루어지지 않기를 바란다는 뜻을 나타낼 수 있습니다(단, 이 지시어는 권고일 뿐입니다).

QUERY 메서드 응답의 캐싱은 GET 응답의 캐싱보다 본질적으로 복잡하다는 점에 유의하십시오. 캐시 키를 결정하려면 요청 콘텐츠를 완전히 읽어야 하기 때문입니다. QUERY 응답이 Location 응답 필드(2.4절)를 제공하여 동등 리소스의 URI를 나타낸다면 (2.2절), 클라이언트는 후속 요청에서 GET으로 전환하여 처리를 간소화할 수 있습니다.

2.8. 범위 요청

QUERY에 대한 범위 요청의 의미론은 GET에 대한 의미론과 같으며, 다음에 정의되어 있습니다: 14절, [HTTP]. 그러나 바이트 범위 요청은 (작성 시점에 정의된 유일한 범위 단위) QUERY 요청의 결과에는 별다른 가치를 제공하지 않습니다.

쿼리 형식은 결과 집합을 제한하거나 페이지별로 탐색하는 고유한 방식을 정의하는 경우가 많으며, SQL의 "FETCH FIRST ... ROWS ONLY"가 그 예입니다. 이러한 내장 기능이 HTTP 범위 요청 대신 사용될 것으로 예상됩니다.

3. Accept-Query 헤더 필드

"Accept-Query" 응답 헤더 필드는 리소스가 QUERY 메서드 지원을 직접 알리면서 사용할 수 있는 구체적인 쿼리 형식의 미디어 유형을 식별하는 데 사용할 수 있습니다.

Accept-Query에는 미디어 범위 목록(12.5.1절, [HTTP])이 "구조화 필드" 구문을 사용하여 포함됩니다 [STRUCTURED-FIELDS]. 미디어 범위는 Token 또는 String으로 구성된 List 구조화 헤더 필드로 표현되며, 매개변수가 없는 미디어 범위 값을 포함합니다.

미디어 유형 매개변수가 있다면 String 또는 Token 유형의 구조화 필드 매개변수로 매핑됩니다. Token과 String 중 어느 것을 선택하는지는 의미상 중요하지 않습니다. 즉, 수신자는 Token을 String으로 변환할 수 있습니다. 그러나 해서는 안 됩니다, 즉 수신한 유형에 따라 이들을 다르게 처리해서는 안 됩니다.

미디어 유형은 Token에 정확히 대응하지 않습니다. 예를 들어 미디어 유형은 숫자로 시작할 수 있습니다. 이러한 경우에는 String 형식을 사용해야 합니다.

지원되는 와일드카드 사용은 모든 유형에 일치하는 "*/*" 또는 표시된 유형의 모든 하위 유형에 일치하는 "xxxx/*"뿐입니다.

필드 값에 나열된 유형의 순서는 중요하지 않습니다.

Accept-Query 필드의 값은 서버에서 같은 경로를 공유하는 모든 URI에 적용됩니다. 즉, 쿼리 구성 요소는 무시됩니다. 같은 리소스에 대한 요청이 서로 다른 Accept-Query 값을 반환하면 가장 최근에 수신한 신선한 값(다음에 따름: 4.2절, [HTTP-CACHING])을 사용합니다.

예를 들면 다음과 같습니다:

Accept-Query: "application/jsonpath", application/sql;charset="UTF-8"

이 필드의 구문은 "Accept" 같은 다른 필드와 유사해 보이지만 (12.5.1절, [HTTP]), 구조화 필드이므로 반드시 다음에 명시된 대로 처리해야 합니다: 4절, [STRUCTURED-FIELDS].

4. 보안 고려 사항

QUERY 메서드에는 모든 HTTP 메서드와 동일한 일반 보안 고려 사항이 적용되며, 이는 [HTTP]에 설명되어 있습니다.

이 메서드는 요청 정보를 URI(예: 쿼리 구성 요소)에 전달하는 방식의 대안으로 사용할 수 있습니다. URI는 요청 콘텐츠보다 중개자에 의해 로그에 기록되거나 다른 방식으로 처리될 가능성이 높으므로, 일부 경우에는 이 방식이 선호됩니다. 쿼리에 민감한 정보가 포함된 다른 경우에는 URI가 로그에 기록될 가능성이 GET보다 QUERY를 사용하게 되는 이유가 될 수 있습니다.

서버가 QUERY 요청의 결과를 나타내는 임시 리소스를 생성하고(예: Location 또는 Content-Location 필드에서 사용하기 위해), 해당 리소스에 URI를 할당하며, 요청에 로그에 기록할 수 없는 민감한 정보가 포함되어 있다면, 해당 URI는 가급적 원래 요청 콘텐츠의 민감한 부분을 포함하지 않도록 선택해야 합니다.

QUERY 콘텐츠를 잘못 정규화하거나 리소스가 콘텐츠를 처리하는 방식과 크게 다른 방식으로 정규화하는 캐시는 정규화로 인해 거짓 양성이 발생하면 잘못된 응답을 반환할 수 있습니다.

교차 출처 리소스 공유(CORS)를 구현하는 사용자 에이전트의 QUERY 요청에는 "사전 요청"이 필요합니다. QUERY는 CORS 안전 목록에 포함된 메서드 집합에 속하지 않기 때문입니다 ([FETCH] 참조).

부록 A. 예제

아래 예제는 설명만을 위한 것입니다. 실제로 이렇게 짧은 쿼리를 보내야 한다면 GET을 사용하는 편이 더 나을 가능성이 높습니다.

대부분의 예제에서 사용되는 미디어 유형은 "application/x-www-form-urlencoded"입니다(브라우저 사용자 클라이언트의 POST 요청에서 사용되며, 다음에 정의되어 있습니다: "application/x-www-form-urlencoded", [URL]). 간결함을 위해 Content-Length 필드는 생략했습니다.

A.1. 간단한 쿼리

아래는 직접 응답이 있는 간단한 쿼리입니다:

QUERY /contacts HTTP/1.1
Host: example.org
Content-Type: application/x-www-form-urlencoded
Accept: application/json

select=surname,givenname,email&limit=10&match=%22email=*@example.*%22

응답:

HTTP/1.1 200 OK
Content-Type: application/json

[
  { "surname": "Smith",
    "givenname": "John",
    "email": "smith@example.org" },
  { "surname": "Jones",
    "givenname": "Sally",
    "email": "sally.jones@example.com" },
  { "surname": "Dubois",
    "givenname": "Camille",
    "email": "camille.dubois@example.net" }
]

A.2. QUERY 지원 확인

QUERY 지원을 확인하는 간단한 방법은 OPTIONS (9.3.7절, [HTTP]) 메서드가 제공합니다: 

OPTIONS /contacts HTTP/1.1
Host: example.org

응답:

HTTP/1.1 200 OK
Allow: GET, QUERY, OPTIONS, HEAD

Allow 응답 필드(10.2.1절, [HTTP])는 지정된 리소스에서 지원되는 메서드 집합을 나타냅니다.

OPTIONS 사용에는 대안이 있습니다. 예를 들어 서버의 지원 여부를 미리 알지 못해도 QUERY 요청을 시도할 수 있습니다. 그러면 서버는 요청을 처리하거나 405 (허용되지 않는 메서드, 15.5.6절, [HTTP]) 같은 4xx 상태로 Allow 응답 필드를 포함하여 응답할 수 있습니다.

A.3. QUERY 형식 확인

QUERY에서 지원되는 미디어 유형은 Accept-Query 응답 필드를 통해 확인할 수 있습니다 (3절): 

HEAD /contacts HTTP/1.1
Host: example.org

응답:

HTTP/1.1 200 OK
Content-Type: application/xhtml
Accept-Query: application/x-www-form-urlencoded, application/sql

어떤 요청 메서드에 대한 응답에 Accept-Query가 포함되는지는 접근하는 리소스에 따라 달라집니다.

Accept-Query를 확인하는 대신 QUERY 요청을 보내고, 그런 다음 -- 415 응답(지원하지 않는 미디어 유형, 15.5.16절, [HTTP]) 같은 4xx 상태인 경우 -- Accept 응답 필드를 검사할 수 있습니다 (12.5.1절, [HTTP]): 

HTTP/1.1 415 Unsupported Media Type
Content-Type: application/xhtml
Accept: application/x-www-form-urlencoded, application/sql

A.4. Content-Location, Location 및 간접 응답

다음 절에서 설명한 대로, 2.3절 및 2.4절, 성공 응답에 있는 Content-Location 및 Location 응답 필드는 (2xx, 15.3절, [HTTP]) GET 요청에 응답하는 대체 리소스를 식별하는 방법을 제공합니다. 이는 요청에서 수신한 결과를 위한 것일 수도 있고, 같은 연산을 수행하는 향후 요청을 위한 것일 수도 있습니다. 다음의 예제로 돌아가 보겠습니다: 부록 A.1: 

QUERY /contacts HTTP/1.1
Host: example.org
Content-Type: application/x-www-form-urlencoded
Accept: application/json

select=surname,givenname,email&limit=10&match=%22email=*@example.*%22

응답:

HTTP/1.1 200 OK
Content-Type: application/json
Content-Location: /contacts/stored-results/17
Location: /contacts/stored-queries/42
Last-Modified: Sat, 25 Aug 2012 23:34:45 GMT
Date: Sun, 17 Nov 2024, 16:10:24 GMT

[
  { "surname": "Smith",
    "givenname": "John",
    "email": "smith@example.org" },
  { "surname": "Jones",
    "givenname": "Sally",
    "email": "sally.jones@example.com" },
  { "surname": "Dubois",
    "givenname": "Camille",
    "email": "camille.dubois@example.net" }
]

A.4.1. Content-Location 사용

위에서 수신한 Content-Location 응답 필드는 자신이 포함된 QUERY 응답의 결과를 보유하는 리소스를 식별합니다:

GET /contacts/stored-results/17 HTTP/1.1
Host: example.org
Accept: application/json

응답:

HTTP/1.1 200 OK
Last-Modified: Sat, 25 Aug 2012 23:34:45 GMT
Date: Sun, 17 Nov 2024, 16:10:25 GMT

[
  { "surname": "Smith",
    "givenname": "John",
    "email": "smith@example.org" },
  { "surname": "Jones",
    "givenname": "Sally",
    "email": "sally.jones@example.com" },
  { "surname": "Dubois",
    "givenname": "Camille",
    "email": "camille.dubois@example.net" }
]

서버가 이 리소스를 무기한 구현하리라는 보장은 없다는 점에 유의하십시오. 따라서 오류 응답 후 클라이언트는 새로운 대체 위치를 얻기 위해 원래 QUERY 요청을 다시 수행해야 합니다.

A.4.2. Location 사용

Location 응답 필드는 원래 QUERY 요청과 같은 처리 및 매개변수에 대한 현재 결과로 GET에 응답하는 리소스를 식별합니다. 

GET /contacts/stored-queries/42 HTTP/1.1
Host: example.org
Accept: application/json

이 예제에서는 2024-11-17T16:12:01Z에 항목 하나가 제거되었으므로( Last-Modified 필드에 표시된 대로), 응답에는 항목 두 개만 포함됩니다:

HTTP/1.1 200 OK
Content-Type: application/json
Last-Modified: Sun, 17 November 2024, 16:12:01 GMT
ETag: "42-1"
Date: Sun, 17 Nov 2024, 16:13:17 GMT

[
  { "surname": "Smith",
    "givenname": "John",
    "email": "smith@example.org" },
  { "surname": "Dubois",
    "givenname": "Camille",
    "email": "camille.dubois@example.net" }
]

서버가 여전히 리소스를 노출하고 있고 쿼리 결과에 변경이 없다고 가정하면, 다음을 포함하는 후속 조건부 GET 요청은:

If-None-Match: "42-1"

304 (수정되지 않음) 응답으로 이어집니다 ( 15.4.5절, [HTTP]).

A.4.3. 간접 응답

서버는 "간접" 응답을 보낼 수 있습니다 (2.5절). 이때 상태 코드 303 (다른 리소스 참조, 15.4.4절, [HTTP])을 사용합니다.

다음의 시작 부분에 있는 요청에 대해, 부록 A.4, 서버는 다음과 같이 응답할 수 있습니다:

HTTP/1.1 303 See Other
Content-Type: text/plain
Date: Sun, 17 Nov 2024, 16:13:17 GMT
Location: /contacts/stored-queries/42

"/contacts/stored-queries/42"에 저장된 쿼리를 참조하십시오.

이는 직접 응답에 Location을 포함하는 것과 유사하지만, 쿼리 결과를 반환하지 않는다는 차이가 있습니다. 이를 통해 서버는 대체 리소스를 생성하거나 재사용하기만 할 수 있습니다. 그런 다음 이 리소스는 다음에 표시된 대로 사용할 수 있습니다: 부록 A.4.2.

A.5. 조건부 요청

QUERY를 구현하며 "application/sql" 및 "application/xslt+xml" [XSLT]을 요청 미디어 유형으로 지원하고, "text/csv"로 응답을 생성할 수 있는 리소스를 생각해 보십시오. 쿼리 대상 데이터 집합에는 RFC 문서 정보가 포함되어 있으며, 쿼리는 10년 단위로 그룹화된 정보를 반환합니다:

Accept: text/csv

A.6. 추가 쿼리 형식

다음 예제는 JSON 형태의 [RFC8259] RFC 정오표 데이터베이스에 대한 요청을 보여 줍니다.

아래 요청은 확장 가능 스타일시트 언어 변환(XSLT)을 사용하여 연도 및 정의된 정오표 유형별로 요약된 정오표 정보를 추출합니다.

QUERY /errata.json HTTP/1.1
Host: example.org
Content-Type: application/xslt+xml
Accept: application/xml, text/csv

<transform xmlns="http://www.w3.org/1999/XSL/Transform"
  xmlns:j="http://www.w3.org/2005/xpath-functions"
  version="3.0">

  <output method="text"/>

  <param name="input"/>

  <variable name="json"
    select="json-to-xml(unparsed-text($input))"/>

  <variable name="sc">errata_status_code</variable>
  <variable name="sd">submit_date</variable>

  <template match="/">
    <text>year, total, rejected, verified, hdu, reported</text>
    <text>&#10;</text>
    <variable name="en" select="$json//j:map"/>
    <for-each-group select="$en"
      group-by="substring-before(j:string[@key=$sd],'-')">
      <sort select="current-grouping-key()"/>
      <variable name="year" select="current-grouping-key()"/>
      <variable name="errata" select=
        "$en[$year=substring-before(j:string[@key=$sd],'-')]"/>
      <value-of select="concat(
        $year,
        ', ',
        count($errata),
        ', ',
        count($errata['Rejected'=j:string[@key=$sc]]),
        ', ',
        count($errata['Verified'=j:string[@key=$sc]]),
        ', ',
        count(
          $errata['Held for Document Update'=j:string[@key=$sc]]),
        ', ',
        count($errata['Reported'=j:string[@key=$sc]]),
        '&#10;')"/>
    </for-each-group>
  </template>

</transform>

부록 B. 메서드 이름 'QUERY'의 선정

"하이퍼텍스트 전송 프로토콜(HTTP) 메서드 레지스트리" (<http://www.iana.org/assignments/http-methods>)에는 "안전함" 및 "멱등적임" 속성을 갖는 다른 세 메서드가 이미 포함되어 있습니다: "PROPFIND" [RFC4918], "REPORT" [RFC3253] 및 "SEARCH" [RFC5323].

이들 중 어느 것이든 재사용하여, 이 명세에서 새 메서드 "QUERY"로 정의하는 내용과 일치하도록 갱신할 수 있었을 것입니다. 실제로 이 명세의 초기 단계에서는 "SEARCH"를 사용했습니다.

최종적으로 메서드 이름 "QUERY"를 선택한 이유는 다음과 같습니다:

  • 다른 후보들은 요청 콘텐츠에 일반적인 미디어 유형("application/xml")을 사용하며, 요청의 의미론은 전적으로 요청 콘텐츠에 따라 달라집니다.
  • 또한 이들은 모두 WebDAV 활동에서 유래했으며, 이에 대해 많은 사람이 복합적인 감정을 가지고 있습니다.
  • "QUERY"는 URI의 쿼리 구성 요소와의 관계를 잘 나타냅니다.
