HTTP/1.1

요약

하이퍼텍스트 전송 프로토콜(HTTP)은 분산형, 협업식 하이퍼텍스트 정보 시스템을 위한 무상태 애플리케이션 계층 프로토콜이다. 이 문서는 HTTP/1.1 메시지 구문, 메시지 구문 분석, 연결 관리 및 관련 보안 문제를 명세한다.

이 문서는 RFC 7230의 일부를 대체한다.

이 메모의 상태

이 문서는 인터넷 표준 트랙 문서이다.

이 문서는 인터넷 엔지니어링 태스크 포스(IETF)의 산물이다. 이는 IETF 커뮤니티의 합의를 나타낸다. 공개 검토를 거쳤으며 인터넷 엔지니어링 운영 그룹(IESG)에 의해 출판 승인을 받았다. 인터넷 표준에 대한 추가 정보는 RFC 7841의 섹션 2에서 확인할 수 있다.

이 문서의 현재 상태, 정오표 및 피드백 제공 방법에 관한 정보는 https://www.rfc-editor.org/info/rfc9112에서 얻을 수 있다.

1. 소개

하이퍼텍스트 전송 프로토콜(HTTP)은 네트워크 기반 하이퍼텍스트 정보 시스템과의 유연한 상호작용을 위해 확장 가능한 의미 체계와 자기 설명적인 메시지를 사용하는 무상태 애플리케이션 계층 요청/응답 프로토콜이다. HTTP/1.1은 다음에 의해 정의된다:

  • 이 문서
  • "HTTP Semantics" [HTTP]
  • "HTTP Caching" [CACHING]

이 문서는 HTTP 의미가 HTTP/1.1 메시지 구문, 프레이밍 및 연결 관리 메커니즘을 사용하여 어떻게 전달되는지를 명시한다. 목표는 HTTP/1.1 메시지 파서와 메시지 전달 중계자의 요구사항 전체 집합을 정의하는 것이다.

이 문서는 HTTP/1.1 메시징 및 연결 관리와 관련된 RFC 7230의 해당 부분을 폐기하며, 그 변경 사항은 부록 C.3에 요약되어 있다. RFC 7230의 다른 부분들은 "HTTP Semantics" [HTTP]에 의해 폐기된다.

1.1. 요구사항 표기

이 문서에서 단어 "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", 및 "OPTIONAL"는 모두 대문자로 표시된 경우에만 BCP 14 [RFC2119] 및 [RFC8174]에 설명된 대로 해석된다.

적합성 기준 및 오류 처리에 관한 고려사항은 Section 2 of [HTTP]에 정의되어 있다.

1.2. 구문 표기

이 명세서는 [RFC5234]의 확장된 Backus-Naur 형식(ABNF)을 사용하며, 대소문자 구분 문자열 표기를 위해 [RFC7405]에 정의된 표기법을 확장하여 사용한다.

또한 Section 5.6.1 of [HTTP]에 정의된 목록 확장도 사용하여 "#" 연산자를 통해 쉼표로 구분된 목록을 간결하게 정의할 수 있다(이는 "*" 연산자가 반복을 나타내는 방식과 유사하다). 부록 A에는 모든 목록 연산자가 표준 ABNF 표기법으로 확장된 수집된 문법이 표시되어 있다.

관례상, "obs-"로 접두어가 붙은 ABNF 규칙 이름은 역사적 이유로 남아 있는 구식 문법 규칙을 나타낸다.

다음의 핵심 규칙들은 [RFC5234] 및 해당 부록에 정의된 참조로 포함된다: ALPHA (문자), CR (캐리지 리턴), CRLF (CR LF), CTL (제어 문자), DIGIT (10진수 0-9), DQUOTE (따옴표), HEXDIG (16진수 0-9/A-F/a-f), HTAB (수평 탭), LF (라인 피드), OCTET (임의의 8비트 데이터), SP (공백), 및 VCHAR (표시 가능한 [USASCII] 문자).

아래의 규칙들은 [HTTP]에 정의되어 있다:

  BWS           = <BWS, see [HTTP], Section 5.6.3>
  OWS           = <OWS, see [HTTP], Section 5.6.3>
  RWS           = <RWS, see [HTTP], Section 5.6.3>
  absolute-path = <absolute-path, see [HTTP], Section 4.1>
  field-name    = <field-name, see [HTTP], Section 5.1>
  field-value   = <field-value, see [HTTP], Section 5.5>
  obs-text      = <obs-text, see [HTTP], Section 5.6.4>
  quoted-string = <quoted-string, see [HTTP], Section 5.6.4>
  token         = <token, see [HTTP], Section 5.6.2>
  transfer-coding =
                  <transfer-coding, see [HTTP], Section 10.1.4>

아래의 규칙들은 [URI]에 정의되어 있다:

  absolute-URI  = <absolute-URI, see [URI], Section 4.3>
  authority     = <authority, see [URI], Section 3.2>
  uri-host      = <host, see [URI], Section 3.2.2>
  port          = <port, see [URI], Section 3.2.3>
  query         = <query, see [URI], Section 3.4>

2. 메시지

HTTP/1.1 클라이언트와 서버는 메시지를 전송함으로써 통신한다. 일반 용어와 핵심 개념은 Section 3 of [HTTP]를 참조하라.

2.1. 메시지 형식

HTTP/1.1 메시지는 start-line 다음에 CRLF가 오고 그 뒤에 인터넷 메시지 형식과 유사한 형태의 옥텟 시퀀스로 구성된다: 0개 이상의 헤더 필드 행(통칭하여 "헤더" 또는 "헤더 섹션"), 헤더 섹션의 끝을 나타내는 빈 줄, 그리고 선택적인 메시지 본문.

  HTTP-message   = start-line CRLF
                   *( field-line CRLF )
                   CRLF
                   [ message-body ]

메시지는 클라이언트에서 서버로의 요청이거나 서버에서 클라이언트로의 응답일 수 있다. 문법적으로 두 종류의 메시지는 오직 start-line에서만 차이가 나며, 이는 요청의 경우 request-line이고 응답의 경우 status-line이며, 메시지 본문의 길이를 결정하는 알고리즘(Section 6)도 다르다.

  start-line     = request-line / status-line

이론적으로는 클라이언트가 요청을 받고 서버가 응답을 받는 상황이 발생할 수 있으며, 시작 행 형식의 차이로 구별할 수 있다. 하지만 실제로 서버는 요청만을 예상하도록 구현되어 있으며(응답은 알 수 없거나 잘못된 요청 메서드로 해석됨), 클라이언트는 응답만을 예상하도록 구현된다.

HTTP은 MIME(다목적 인터넷 우편 확장)의 일부 프로토콜 요소를 활용한다. HTTP와 MIME 메시지의 차이점은 부록 B를 참조하라.

2.2. 메시지 구문 분석

HTTP 메시지를 구문 분석하는 일반 절차는 start-line을 구조체로 읽고, 빈 줄이 나오기 전까지 각 헤더 필드 행을 필드 이름으로 해시 테이블에 읽어 들인 다음, 구문 분석된 데이터를 사용하여 메시지 본문이 예상되는지 판단하는 것이다. 메시지 본문이 표시된 경우, 메시지 본문 길이에 해당하는 옥텟 수가 읽히거나 연결이 종료될 때까지 스트림으로 읽는다.

수신자는 MUST US-ASCII의 상위 집합인 인코딩으로 표현된 옥텟 시퀀스로 HTTP 메시지를 구문 분석해야 한다. 특정 인코딩을 고려하지 않고 유니코드 문자 스트림으로 HTTP 메시지를 구문 분석하면 LF (%x0A)를 포함한 잘못된 다바이트 문자 시퀀스를 문자열 처리 라이브러리가 다르게 처리하는 방식으로 인해 보안 취약점이 발생한다. 문자열 기반 파서는 메시지에서 요소를 추출한 이후에만 안전하게 사용될 수 있다(예: 메시지 구문 분석이 개별 필드 행을 구분한 후 헤더 필드 값 내부에서 사용).

start-line과 필드의 행 종결자는 CRLF 시퀀스이지만, 수신자는 단일 LF를 행 종결자로 인식하고 앞선 CR을 무시할 수 있다.

송신자는 콘텐츠 이외의 프로토콜 요소 내에서 LF 바로 앞에 오지 않는 단독 CR(즉, LF 없이 오는 CR)을 생성해서는 안 된다. 그러한 단독 CR을 받은 수신자는 해당 요소를 무효로 간주하거나 각 단독 CR을 SP로 대체한 후 요소를 처리하거나 메시지를 전달해야 한다.

초기 HTTP/1.0 사용자 에이전트 구현체는 일부 초기 서버 애플리케이션이 라인 종료로 끝나지 않는 메시지 본문을 읽지 못하는 문제를 우회하기 위해 POST 요청 후 추가 CRLF를 보낼 수 있었다. HTTP/1.1 사용자 에이전트는 요청 앞뒤에 추가 CRLF를 두어서는 안 된다. 요청 메시지 본문을 라인 종료로 끝내려면, 사용자 에이전트는 종료 CRLF 옥텟을 메시지 본문 길이의 일부로 계산해야 한다.

견고성을 위해 요청 행을 수신하고 구문 분석할 것으로 예상되는 서버는 요청 행 전에 수신된 적어도 하나의 빈 행(CRLF)을 무시하는 것이 바람직하다.

송신자는 start-line과 첫 번째 헤더 필드 사이에 공백을 보내서는 안 된다.

start-line과 첫 번째 헤더 필드 사이에 공백이 포함된 수신자는 메시지를 무효로 거부하거나 공백으로 시작하는 각 행을 추가 처리 없이 소비해야 한다(즉, 적절한 형식의 헤더 필드가 수신되거나 헤더 섹션이 종료될 때까지 공백으로 시작하는 행과 그 뒤를 따르는 모든 행을 무시). 무효한 공백 선행 행을 거부하거나 제거하는 것은 이후 수신자가 요청 스머글링(Section 11.2) 또는 응답 분할(Section 11.1) 공격에 취약할 수 있는 다운스트림 수신자에 의해 잘못 해석되는 것을 방지하기 위해 필요하다.

오직 HTTP 요청 메시지만을 수신하도록 대기하거나 start-line 상으로 HTTP 요청 메시지로 보이는 것을 처리하는 서버가, 위에서 언급한 견고성 예외를 제외하고 HTTP-메시지 문법과 일치하지 않는 옥텟 시퀀스를 수신하면, 서버는 400 (Bad Request) 응답을 보내고 연결을 닫는 것이 바람직하다.

2.3. HTTP 버전

HTTP은 "<major>.<minor>" 표기법을 사용하여 프로토콜 버전을 표시한다. 이 명세서는 버전 "1.1"을 정의한다. Section 2.5 of [HTTP]는 HTTP 버전 번호의 의미를 지정한다.

HTTP/1.x 메시지의 버전은 start-line의 HTTP-version 필드로 표시된다. HTTP-version은 대소문자를 구분한다.

  HTTP-version  = HTTP-name "/" DIGIT "." DIGIT
  HTTP-name     = %s"HTTP"

HTTP/1.1 메시지가 HTTP/1.0 수신자 [HTTP/1.0] 또는 버전을 알 수 없는 수신자에게 전송될 때, HTTP/1.1 메시지는 모든 새로운 기능이 무시될 경우 유효한 HTTP/1.0 메시지로 해석될 수 있도록 구성된다. 이 명세서는 일부 새로운 기능에 대해 수신자 버전 요구사항을 부과하므로, 적합한 송신자는 구성이나 수신된 메시지를 통해 수신자가 HTTP/1.1을 지원한다고 판단하기 전까지 호환 가능한 기능만 사용한다.

HTTP 메시지를 처리하는 중계자(터널로 동작하는 중계자를 제외한 모든 중계자)는 전달된 메시지에서 자신의 HTTP-version을 보내야 하며, 업스트림 문제에 대한 우회 수단으로 의도적으로 다운그레이드 하는 경우를 제외한다. 다시 말해, 중계자는 수신 및 전송 측 모두에서 해당 중계자가 준수하는 버전과 일치하도록 메시지의 프로토콜 버전을 확인하지 않고 start-line을 무작정 전달해서는 안 된다. HTTP-version을 재작성하지 않고 메시지를 전달하면, 다운스트림 수신자가 이후 해당 송신자와의 통신에서 어떤 기능을 안전하게 사용할 수 있는지 판단할 때 통신 오류를 초래할 수 있다.

서버는 클라이언트가 사양을 잘못 구현하여 이후 버전의 응답을 올바르게 처리할 수 없다고 알려져 있거나 의심되는 경우, HTTP/1.1 요청에 대해 HTTP/1.0 응답을 보낼 수 있다. 예를 들어 클라이언트가 버전 번호를 올바르게 구문 분석하지 못하거나 중계자가 주어진 마이너 버전과 일치하지 않더라도 HTTP-version을 무작정 전달하는 것으로 알려진 경우이다. 이러한 프로토콜 다운그레이드는 특정 클라이언트 속성(예: User-Agent와 같이 잘못된 클라이언트가 보내는 값과 고유하게 일치하는 요청 헤더 필드)이 트리거되지 않는 한 수행해서는 안 된다.

3. 요청 행

request-line은 method 토큰으로 시작하며, 그 뒤에 단일 공백(SP), request-target, 또 다른 단일 공백(SP)이 오고 프로토콜 버전으로 끝난다.

  request-line   = method SP request-target SP HTTP-version

요청 행 문법 규칙은 각 구성 요소가 단일 SP 옥텟으로 구분되어야 함을 요구하지만, 수신자는 대신 공백으로 구분된 단어 경계로 구문 분석할 MAY 있으며, CRLF 종결자를 제외하고 앞이나 뒤의 공백을 무시하면서 모든 형태의 공백을 SP 구분자로 처리할 수 있다. 그러한 공백에는 하나 이상의 다음 옥텟이 포함된다: SP, HTAB, VT (%x0B), FF (%x0C), 또는 bare CR. 그러나 관대한(lenient) 구문 분석은 메시지의 수신자가 여러 명이고 각 수신자가 자체적으로 다른 견고성 해석을 가질 경우 요청 스머글링 보안 취약점을 초래할 수 있다(자세한 내용은 Section 11.2 참조).

HTTP는 요청 행 길이에 대해 사전 정의된 제한을 두지 않는다(자세한 내용은 Section 2.3 of [HTTP] 참조). 서버가 자신이 구현한 것보다 더 긴 method를 수신하면 서버는 SHOULD 501 (Not Implemented) 상태 코드를 응답해야 한다. 서버가 자신이 파싱하려 하지 않는 어떤 URI보다 더 긴 request-target을 수신하면 서버는 MUST 414 (URI Too Long) 상태 코드를 응답해야 한다(자세한 내용은 Section 15.5.15 of [HTTP] 참조).

실무에서는 요청 행 길이에 대한 다양한 임의의 제한이 존재한다. 모든 HTTP 발신자와 수신자가 최소한 8000 옥텟의 request-line 길이를 지원하는 것이 RECOMMENDED된다.

3.1. 메서드

method 토큰은 대상 리소스에 대해 수행할 요청 메서드를 나타낸다. 요청 메서드는 대소문자를 구분한다.

  method         = token

이 명세서에서 정의한 요청 메서드는 Section 9 of [HTTP]에서 찾을 수 있으며, HTTP 메서드 레지스트리 및 새로운 메서드 정의에 대한 고려사항도 그곳에 설명되어 있다.

3.2. 요청 대상

request-target은 요청을 적용할 대상 리소스를 식별한다. 클라이언트는 원하는 대상 URI로부터 request-target을 유도한다. method 및 요청이 프록시로 향하는지 여부에 따라 request-target에는 네 가지 서로 다른 형식이 있다.

  request-target = origin-form
                 / absolute-form
                 / authority-form
                 / asterisk-form

request-target에는 공백이 허용되지 않는다. 불행히도 일부 사용자 에이전트는 하이퍼텍스트 참조에서 발견된 공백을 적절히 인코딩하거나 제외하지 못하여, 잘못 형성된 request-line에서 이러한 허용되지 않는 문자가 request-target으로 전송되는 경우가 있다.

잘못된 request-line을 수신한 수신자는 request-target이 적절히 인코딩된 301 (Moved Permanently) 리다이렉트 또는 400 (Bad Request) 오류로 응답하는 것이 SHOULD 권장된다. 수신자는 자동으로 수정하여 리다이렉트 없이 요청을 처리하려고 시도해서는 안 되며, 그 이유는 잘못된 request-line이 요청 체인상의 보안 필터를 우회하기 위해 의도적으로 조작되었을 수 있기 때문이다.

클라이언트는 모든 HTTP/1.1 요청 메시지에서 Host 헤더 필드를 MUST 전송해야 한다(Section 7.2 of [HTTP] 참조). 대상 URI에 authority 구성 요소가 포함되어 있으면, 클라이언트는 userinfo 하위 구성 요소 및 그 "@" 구분자를 제외한 그 authority 구성 요소와 동일한 Host 필드 값을 전송해야 한다. 대상 URI에 authority 구성 요소가 없거나 정의되지 않은 경우, 클라이언트는 빈 필드 값을 가진 Host 헤더 필드를 전송해야 한다.

서버는 Host 헤더 필드가 없거나 Host 헤더 필드가 둘 이상 포함되어 있거나 Host 헤더 필드 값이 유효하지 않은 모든 HTTP/1.1 요청 메시지에 대해 MUST 400 (Bad Request) 상태 코드를 응답해야 한다.

3.2.1. origin-form

가장 일반적인 request-target 형식은 origin-form이다.

  origin-form    = absolute-path [ "?" query ]

CONNECT 또는 서버 전체에 대한 OPTIONS 요청(아래에 상세) 이외의 경우에 원본(origin) 서버에 직접 요청을 보낼 때, 클라이언트는 대상 URI의 절대 경로 및 쿼리 구성 요소만을 request-target으로 보내야 한다(MUST). 대상 URI의 경로 구성 요소가 비어 있으면, 클라이언트는 origin-form의 경로로 "/"를 보내야 한다(MUST). 또한 Host 헤더 필드가 전송된다(자세한 내용은 Section 7.2 of [HTTP] 참조).

예를 들어, 클라이언트가 다음 리소스의 표현을 가져오려면

http://www.example.org/where?q=now

원본 서버에서 직접 가져오기 위해 호스트 "www.example.org"의 포트 80에 TCP 연결을 열(또는 재사용)하고 다음 행들을 보낸다:

GET /where?q=now HTTP/1.1
Host: www.example.org

그 뒤에 요청 메시지의 나머지 부분이 온다.

3.2.2. absolute-form

프록시에 요청을 보낼 때(아래의 CONNECT 또는 서버 전체 OPTIONS 요청 제외), 클라이언트는 request-target으로 대상 URI를 absolute-form으로 보내야 한다(MUST). 

  absolute-form  = absolute-URI

프록시는 가능한 경우 유효한 캐시에서 그 요청을 처리하거나, 클라이언트를 대신하여 다음 인바운드 프록시 서버로 또는 대상 origin 서버로 동일한 요청을 수행하도록 요청받는다. 이러한 메시지의 "포워딩"에 대한 요구사항은 Section 7.6 of [HTTP]에 정의되어 있다.

absolute-form의 request-line 예시는 다음과 같다:

GET http://www.example.org/pub/WWW/TheProject.html HTTP/1.1

클라이언트는 request-target이 absolute-form일지라도 HTTP/1.1 요청에서 Host 헤더 필드를 전송해야 한다(MUST), 이는 오래된 HTTP/1.0 프록시를 통해 Host 정보를 전달하도록 하기 위함이다.

프록시가 absolute-form의 request-target을 가진 요청을 수신하면, 프록시는 수신된 Host 헤더 필드(있을 경우)를 무시하고 대신 request-target의 호스트 정보를 사용하여 대체해야 한다(MUST). 그러한 요청을 전달하는 프록시는 수신된 Host 필드 값을 그대로 전달해서는 안 되며, 수신된 request-target을 기반으로 새 Host 필드 값을 생성해야 한다(MUST).

원본 서버가 absolute-form의 request-target을 가진 요청을 수신하면, 원본 서버는 수신된 Host 헤더 필드(있을 경우)를 무시하고 대신 request-target의 호스트 정보를 사용해야 한다(MUST). 요청-타겟에 authority 구성 요소가 없으면 이 경우 빈 Host 헤더 필드가 전송된다는 점에 유의하라.

대다수의 HTTP/1.1 클라이언트는 absolute-form을 프록시에만 보낼 것이지만, 서버는 요청에서 absolute-form을 수락해야 한다(MUST).

3.2.3. authority-form

request-target의 authority-form은 CONNECT 요청(Section 9.3.6 of [HTTP])에만 사용된다. 이것은 터널 목적지의 uri-host와 port 번호만으로 구성되며 콜론(":")으로 구분된다.

  authority-form = uri-host ":" port

프록시를 통해 터널을 설정하기 위한 CONNECT 요청을 할 때, 클라이언트는 터널 목적지의 호스트와 포트만을 request-target으로 보내야 한다(MUST). 클라이언트는 대상 URI의 authority 구성 요소에서 호스트와 포트를 획득하되, 대상 URI가 포트를 생략한 경우 해당 스킴의 기본 포트를 전송한다. 예를 들어 "http://www.example.com"에 대한 CONNECT 요청은 다음과 같다:

CONNECT www.example.com:80 HTTP/1.1
Host: www.example.com

3.2.4. asterisk-form

request-target의 asterisk-form은 서버 전체에 대한 OPTIONS 요청(Section 9.3.7 of [HTTP])에만 사용된다. 

  asterisk-form  = "*"

클라이언트가 서버 전체에 대한 OPTIONS를 요청하려는 경우(서버의 특정 명명된 리소스가 아닌 경우), 클라이언트는 request-target으로 "*" (%x2A)만을 보내야 한다(MUST). 예를 들면

OPTIONS * HTTP/1.1

프록시가 path가 비어 있고 쿼리 구성 요소가 없는 absolute-form의 OPTIONS 요청을 수신하면, 요청 체인의 마지막 프록시는 원본 서버로 요청을 전달할 때 request-target을 "*"로 보내야 한다(MUST).

예를 들어, 다음 요청은

OPTIONS http://www.example.org:8001 HTTP/1.1

다음과 같이 마지막 프록시에 의해 전달될 것이다

OPTIONS * HTTP/1.1
Host: www.example.org:8001

호스트 "www.example.org"의 포트 8001에 연결한 후이다.

3.3. 대상 URI 재구성

request-target이 absolute-form일 때 대상 URI는 그 request-target이다. 이 경우 서버는 추가 평가를 위해 URI를 일반 구성 요소로 구문 분석한다.

그렇지 않은 경우, 서버는 대상 리소스를 식별하기 위해 연결 컨텍스트 및 요청 메시지의 다양한 부분으로부터 대상 URI를 재구성한다(Section 7.1 of [HTTP]):

  • 서버 구성에서 고정된 URI 스킴을 제공하거나 신뢰할 수 있는 아웃바운드 게이트웨이가 스킴을 제공하면 해당 스킴을 대상 URI에 사용한다. 이는 게이트웨이 서버가 클라이언트의 연결 컨텍스트를 수신하고 이를 자체 연결로 대체하여 인바운드 서버로 전달하기 때문에 대규모 배포에서 일반적이다. 그렇지 않으면 요청이 보안 연결을 통해 수신된 경우 대상 URI의 스킴은 "https"이고, 그렇지 않으면 스킴은 "http"이다.
  • request-target이 authority-form인 경우 대상 URI의 authority 구성 요소는 request-target이다. 그렇지 않으면 대상 URI의 authority 구성 요소는 Host 헤더 필드의 필드 값이다. Host 헤더 필드가 없거나 그 값이 비어 있거나 유효하지 않으면 대상 URI의 authority 구성 요소는 비어 있다.
  • request-target이 authority-form 또는 asterisk-form인 경우 대상 URI의 결합된 path 및 query 구성 요소는 비어 있다. 그렇지 않으면 대상 URI의 결합된 path 및 query 구성 요소는 request-target이다.
  • 위에서 결정된대로 재구성된 대상 URI의 구성 요소는 스킴, "://", authority, 그리고 결합된 경로 및 쿼리 구성 요소를 연결하여 absolute-URI 형태로 다시 결합할 수 있다.

예 1: 다음 메시지가 보안 연결을 통해 수신된 경우

GET /pub/WWW/TheProject.html HTTP/1.1
Host: www.example.org

대상 URI는 다음과 같다

https://www.example.org/pub/WWW/TheProject.html

예 2: 다음 메시지가 비보안 연결을 통해 수신된 경우

OPTIONS * HTTP/1.1
Host: www.example.org:8080

대상 URI는 다음과 같다

http://www.example.org:8080

대상 URI의 authority 구성 요소가 비어 있고 그 URI 스킴이 비어 있지 않은 authority를 요구하는 경우(예: "http" 및 "https"), 서버는 요청을 거부하거나 들어오는 연결 컨텍스트와 일치하는 구성된 기본값이 적용되는지 판단할 수 있다. 컨텍스트에는 주소 및 포트, 적용된 보안, 그리고 해당 서버의 구성에 특정한 로컬 정의 정보와 같은 연결 세부사항이 포함될 수 있다. 빈 authority는 추가 처리 전에 구성된 기본값으로 대체된다.

보안 연결 컨텍스트 내에서 authority에 대한 기본 이름을 제공하는 것은 클라이언트가 의도한 authority가 기본값과 다를 가능성이 있는 경우 본질적으로 안전하지 않다. 요청 컨텍스트로부터 고유하게 authority를 식별할 수 있는 서버는 그 식별자를 기본값으로 사용할 수 있다(MAY). 또는 새 클라이언트를 얻는 방법을 설명하는 안전한 리소스로 요청을 리다이렉트하는 것이 더 낫다.

클라이언트의 대상 URI를 재구성하는 것은 대상 리소스 식별 프로세스의 절반에 불과하다는 점에 유의하라. 나머지 절반은 해당 대상 URI가 서버가 응답을 보낼 의사와 능력이 있는 리소스를 식별하는지 여부를 결정하는 것이다(자세한 내용은 Section 7.4 of [HTTP] 참조).

4. 상태 행

응답 메시지의 첫 번째 행은 status-line으로, 프로토콜 버전, 공백(SP), 상태 코드, 또 다른 공백, 그리고 상태 코드를 설명하는 OPTIONAL한 텍스트 문구로 끝난다.

  status-line = HTTP-version SP status-code SP [ reason-phrase ]

status-line 문법 규칙은 각 구성 요소가 단일 SP 옥텟으로 구분되어야 함을 요구하지만, 수신자는 대신 공백으로 구분된 단어 경계로 구문 분석할 MAY 있으며, 행 종결자를 제외하고 앞뒤 공백을 무시하면서 모든 형태의 공백을 SP 구분자로 처리할 수 있다. 그러한 공백에는 하나 이상의 다음 옥텟이 포함된다: SP, HTAB, VT (%x0B), FF (%x0C), 또는 bare CR. 그러나 관대한 구문 분석은 메시지의 수신자가 여러 명이고 각 수신자가 자체적으로 다른 견고성 해석을 가질 경우 응답 분할 보안 취약점을 초래할 수 있다(자세한 내용은 Section 11.1 참조).

status-code 요소는 서버가 클라이언트의 해당 요청을 이해하고 충족하려는 시도 결과를 설명하는 3자리 정수 코드이다. 수신자는 그 상태 코드가 인식되는 경우 해당 상태 코드에 대해 정의된 의미에 따라 응답 메시지의 나머지 부분을 구문 분석하고 해석하며, 특정 코드가 인식되지 않는 경우 상태 코드 클래스에 따라 해석한다. 

  status-code    = 3DIGIT

HTTP의 핵심 상태 코드는 Section 15 of [HTTP]에 정의되어 있으며, 상태 코드의 클래스, 새로운 상태 코드 정의에 대한 고려사항 및 해당 정의를 수집하는 IANA 레지스트리가 포함된다.

reason-phrase 요소는 숫자 상태 코드와 연결된 텍스트 설명을 제공하기 위한 유일한 목적을 가진다. 이는 주로 상호작용형 텍스트 클라이언트와 더 자주 사용되던 초기 인터넷 애플리케이션 프로토콜에 대한 예의를 위한 것이다.

  reason-phrase  = 1*( HTAB / SP / VCHAR / obs-text )

클라이언트는 reason-phrase 내용이 신뢰할 수 있는 정보 채널이 아니므로 이를 무시하는 것이 SHOULD 권장된다(지역화되어 번역되거나 중계자에 의해 덮어쓰기되거나 다른 HTTP 버전을 통해 전달될 때 폐기될 수 있음). 서버는 reason-phrase가 없더라도 status-code와 reason-phrase를 구분하는 공백을 반드시 전송해야 한다(MUST), 즉 status-line은 공백으로 끝나게 된다.

5. 필드 구문

각 필드 행은 대소문자를 구분하지 않는 필드 이름, 콜론(":"), 선택적 선행 공백, 필드 행 값, 그리고 선택적 후행 공백으로 구성된다.

  field-line   = field-name ":" OWS field-value OWS

필드 값 내부의 구문 분석 규칙은 Section 5.5 of [HTTP]에 정의되어 있다. 이 섹션은 HTTP/1.1 메시지 내에서 헤더 필드의 일반적인 포함 및 추출 구문을 다룬다.

5.1. 필드 행 구문 분석

메시지는 개별 필드 이름과 무관한 일반 알고리즘을 사용하여 구문 분석된다. 주어진 필드 행 값 내부의 내용은 메시지 해석의 이후 단계(대개 메시지의 전체 필드 섹션이 처리된 후)에 구문 분석된다.

필드 이름과 콜론 사이에는 공백이 허용되지 않는다. 과거에 이러한 공백 처리의 차이는 요청 라우팅 및 응답 처리에서 보안 취약점을 초래한 바 있다. 서버는 필드 이름과 콜론 사이에 공백이 포함된 수신된 요청 메시지를 MUST 400 (Bad Request) 상태 코드로 거부해야 한다. 프록시는 응답 메시지를 하류로 전달하기 전에 그러한 공백을 제거해야 한다(MUST).

필드 행 값은 선택적 공백(OWS)에 의해 앞뒤로 둘러싸일 수 있다; 일관된 가독성을 위해 필드 행 값 앞에 단일 SP를 두는 것이 바람직하다. 필드 행 값은 그 선행 또는 후행 공백을 포함하지 않는다: 필드 행 값의 첫 번째 비공백 옥텟 앞에 나타나는 OWS 또는 마지막 비공백 옥텟 뒤에 나타나는 OWS는 필드 행에서 필드 행 값을 추출할 때 파서에 의해 제외된다.

5.2. 구식 행 접기

역사적으로 HTTP/1.x 필드 값은 각 추가 행 앞에 적어도 하나의 공백 또는 수평 탭(obs-fold)을 추가함으로써 여러 행에 걸쳐 확장될 수 있었다. 이 명세서는 "message/http" 미디어 타입(Section 10.1) 내를 제외하고 그러한 행 접기를 사용 중단(deprecate)한다.

  obs-fold     = OWS CRLF RWS
               ; obsolete line folding

송신자는 메시지에 행 접기(obs-fold)를 포함시키지 않아야 한다(MUST NOT), 즉 필드 행 값이 obs-fold 규칙에 일치하는 경우를 포함하지 않아야 한다. 단, 메시지가 "message/http" 미디어 타입으로 포장되는 경우는 예외이다.

"message/http" 컨테이너 내에 있지 않은 요청 메시지에서 obs-fold를 수신한 서버는 그 메시지를 거부하고 400 (Bad Request)을 보내거나, 바람직하게는 구식 행 접기가 허용되지 않음을 설명하는 표현과 함께 응답하거나, 수신된 각 obs-fold를 필드 값 해석 또는 하류 전달 전에 하나 이상의 SP 옥텟으로 대체해야 한다(MUST).

"message/http" 컨테이너 내에 있지 않은 응답 메시지에서 obs-fold를 수신한 프록시 또는 게이트웨이는 메시지를 폐기하고 502 (Bad Gateway) 응답으로 대체하거나, 바람직하게는 수신된 부적절한 행 접기가 수신되었음을 설명하는 표현과 함께, 수신된 각 obs-fold를 필드 값 해석 또는 하류 전달 전에 하나 이상의 SP 옥텟으로 대체해야 한다(MUST).

"message/http" 컨테이너 내에 있지 않은 응답 메시지에서 obs-fold를 수신한 사용자 에이전트는 필드 값을 해석하기 전에 수신된 각 obs-fold를 하나 이상의 SP 옥텟으로 대체해야 한다(MUST).

6. Message Body

HTTP/1.1 메시지의 메시지 본문(있을 경우)은 요청 또는 응답의 콘텐츠( 섹션 6.4 of [HTTP])을 담는 데 사용된다. 메시지 본문은 섹션 6.1에서 설명된 대로 전송 코딩이 적용되지 않은 경우에는 콘텐츠와 동일하다.

  message-body = *OCTET

HTTP/1.1 메시지에 메시지 본문이 존재하는 시기를 결정하는 규칙은 요청과 응답에서 서로 다르다.

요청에서 메시지 본문의 존재는 Content-Length 또는 Transfer-Encoding 헤더 필드로 표시된다. 요청 메시지의 프레이밍은 메서드 의미와 독립적이다.

응답에서 메시지 본문의 존재는 섹션 6.3에 상세히 설명된 대로, 응답이 응답하는 요청 메서드와 응답 상태 코드 모두에 의존한다. 이는 HTTP 의미론상 응답 콘텐츠가 허용되는 시점과 대응한다 ( 섹션 6.4.1 of [HTTP] ).

6.1. Transfer-Encoding

The Transfer-Encoding header field는 메시지 본문을 형성하기 위해 콘텐츠에 적용되었거나 적용될 전송 코딩들의 순서에 해당하는 전송 코딩 이름들을 나열한다. 전송 코딩은 섹션 7에 정의되어 있다.

  Transfer-Encoding = #transfer-coding
                       ; defined in [HTTP], Section 10.1.4

Transfer-Encoding은 MIME의 Content-Transfer-Encoding 필드와 유사한 역할을 한다. MIME에서는 7비트 전송 서비스를 통한 이진 데이터의 안전한 전송을 위해 설계되었다( [RFC2045], 섹션 6 ). 그러나 8bit-클린 전송 프로토콜에서는 안전 전송의 초점이 다르다. HTTP의 경우 Transfer-Encoding은 주로 동적으로 생성된 콘텐츠를 정확하게 구분하는 데 사용된다. 또한 전송 중에만 적용되는 인코딩과 선택된 표현의 특성인 인코딩을 구별하는 역할도 한다.

수신자는 청크 전송 코딩( 섹션 7.1 )을 파싱할 수 있어야 한다. 이는 콘텐츠 크기를 미리 알 수 없을 때 메시지 프레이밍에서 중요한 역할을 하기 때문이다. 송신자는 메시지 본문에 대해 청크 전송 코딩을 여러 번 적용해서는 안 된다(즉, 이미 청크된 메시지를 다시 청크하는 것은 허용되지 않는다). 요청의 콘텐츠에 대해 청크 이외의 전송 코딩이 적용된 경우, 송신자는 메시지가 적절히 프레이밍되도록 청크를 최종 전송 코딩으로 적용해야 한다. 응답의 콘텐츠에 대해 청크 이외의 전송 코딩이 적용된 경우, 송신자는 청크를 최종 전송 코딩으로 적용하거나 연결을 닫아 메시지를 종료해야 한다.

예를 들면,

Transfer-Encoding: gzip, chunked

는 콘텐츠가 gzip으로 압축된 다음 chunked 코딩으로 청크되어 메시지 본문을 형성했음을 나타낸다.

Content-Encoding( 섹션 8.4.1 of [HTTP] )과 달리, Transfer-Encoding은 표현의 특성이 아니라 메시지의 속성이다. 요청/응답 체인상의 수신자는 받은 전송 코딩을 디코드하거나 메시지 본문에 추가 전송 코딩을 적용할 수 있으며, 그 경우 Transfer-Encoding 필드 값도 적절히 변경해야 한다. 인코딩 매개변수에 대한 추가 정보는 이 명세서에서 정의하지 않은 다른 헤더 필드들을 통해 제공될 수 있다.

Transfer-Encoding은 메시지 본문을 포함하지 않는 HEAD 요청에 대한 응답이나 GET 요청에 대한 304 (Not Modified) 응답( 섹션 15.4.5 of [HTTP] )에서 보낼 수 있다. 이는 원본 서버가 조건 없는 GET이었더라면 메시지 본문에 전송 코딩을 적용했을 것임을 나타내기 위한 것이다. 그러나 이 표시는 필수는 아니다. 응답 체인상의 어떤 수신자(원본 서버 포함)도 필요하지 않은 경우 전송 코딩을 제거할 수 있다.

서버는 상태 코드가 1xx (Informational) 또는 204 (No Content)인 응답에는 Transfer-Encoding 헤더 필드를 보내면 안 된다. 또한 서버는 CONNECT 요청에 대한 2xx (Successful) 응답에는 Transfer-Encoding 헤더 필드를 보내면 안 된다.

서버가 이해하지 못하는 전송 코딩을 포함한 요청 메시지를 수신하면 SHOULD 501 (Not Implemented)로 응답하는 것이 바람직하다.

Transfer-Encoding은 HTTP/1.1에 추가되었다. 보통 HTTP/1.0만 지원한다고 광고하는 구현체는 전송 인코딩된 콘텐츠를 처리하지 못할 것으로 가정되며, Transfer-Encoding을 포함한 HTTP/1.0 메시지가 수신되면 청크 전송 코딩을 제대로 처리하지 못한 채 전달되었을 가능성이 있다.

클라이언트는 서버가 HTTP/1.1(또는 이후 마이너 버전)을 처리할 것임을 알지 못하는 한 Transfer-Encoding을 포함한 요청을 보내면 안 된다(MUST NOT). 이러한 지식은 명시적 사용자 구성이나 이전에 수신한 응답의 버전을 기억하는 형태일 수 있다. 서버 역시 해당 요청이 HTTP/1.1(또는 이후 마이너 버전)을 지시하지 않는 한 Transfer-Encoding을 포함한 응답을 보내면 안 된다(MUST NOT).

초기 Transfer-Encoding 구현은 메시지 프레이밍을 위한 청크 전송 코딩과 진행 표시줄을 위한 추정 Content-Length 헤더 필드를 함께 보내는 경우가 있었다. 이 때문에 Transfer-Encoding은 Content-Length를 무시하도록 정의되었으며, 상호 배타적이지 않다. 그러나 이러한 메시지를 전달하면 요청 스머글링( 섹션 11.2 ) 또는 응답 분할( 섹션 11.1 ) 공격에 취약해질 수 있으며, 특히 하류 수신자가 이 명세에 따라 메시지를 파싱하지 못하고 HTTP/1.0만 구현하는 경우 문제가 된다.

서버는 Content-Length와 Transfer-Encoding을 모두 포함한 요청을 거부하거나 Transfer-Encoding만을 기준으로 처리할 수 있다(MAY). 그럼에도 불구하고, 서버는 그러한 요청에 응답한 후 잠재적 공격을 피하기 위해 연결을 닫아야 한다(MUST).

HTTP/1.0 메시지에서 Transfer-Encoding 헤더 필드를 수신한 서버 또는 클라이언트는 메시지의 프레이밍이 잘못된 것으로 간주해야 하며(설사 Content-Length가 있어도), 메시지를 처리한 후 연결을 닫아야 한다(MUST). 송신자가 일부 메시지를 버퍼에 보유하고 있을 수 있어, 연결을 계속 사용할 경우 그 잔여가 오해를 불러일으킬 수 있기 때문이다.

6.2. Content-Length

메시지에 Transfer-Encoding 헤더 필드가 없을 때, Content-Length 헤더 필드는 잠재적 콘텐츠의 예상 크기를 10진수 옥텟 수로 제공할 수 있다. 콘텐츠를 포함하는 메시지의 경우 Content-Length 필드 값은 데이터(및 메시지)가 끝나는 위치를 결정하는 데 필요한 프레이밍 정보를 제공한다. 콘텐츠를 포함하지 않는 메시지의 경우 Content-Length는 선택된 표현의 크기를 나타낸다.

송신자는 Transfer-Encoding 헤더 필드가 있는 어떤 메시지에서도 Content-Length 헤더 필드를 보내면 안 된다(MUST NOT).

Note: 메시지 프레이밍을 위해 Content-Length를 사용하는 HTTP의 방식은 MIME에서의 사용 방식과 크게 다르다. MIME에서는 "message/external-body" 미디어 타입 내에서만 선택적으로 사용된다.

6.3. Message Body Length

메시지 본문의 길이는 다음 중 하나에 의해 결정된다(우선순위 순):

  1. HEAD 요청에 대한 모든 응답과 상태 코드가 1xx (Informational), 204 (No Content), 또는 304 (Not Modified)인 모든 응답은 헤더 필드 이후의 첫 번째 빈 줄에 의해 항상 종료되므로, 메시지 본문이나 트레일러 섹션을 포함할 수 없다.

  2. CONNECT 요청에 대한 2xx (Successful) 응답은 빈 줄로 헤더 필드가 종료된 직후 연결이 즉시 터널이 됨을 의미한다. 클라이언트는 이러한 메시지에서 수신된 어떤 Content-Length 또는 Transfer-Encoding 헤더 필드도 무시해야 한다(MUST).

  3. 메시지가 Transfer-Encoding과 Content-Length를 모두 포함하여 수신된 경우, Transfer-Encoding이 Content-Length를 무시한다. 이러한 메시지는 요청 스머글링( 섹션 11.2 ) 또는 응답 분할( 섹션 11.1 )을 시도하려는 것으로 보일 수 있으며 오류로 처리되어야 한다. 중계자가 메시지를 전달하기로 선택하는 경우, 전달하기 전에 수신된 Content-Length 필드를 먼저 제거하고 Transfer-Encoding을 처리해야 한다(MUST).

  4. Transfer-Encoding 헤더 필드가 존재하고 마지막 인코딩이 청크 전송 코딩( 섹션 7.1 )인 경우, 메시지 본문 길이는 청크된 데이터를 읽고 디코딩하여 전송 코딩이 데이터가 완전함을 나타낼 때까지 판정된다.

    Transfer-Encoding 헤더 필드가 응답에 존재하고 청크가 최종 인코딩이 아닌 경우, 메시지 본문 길이는 서버가 연결을 닫을 때까지 연결을 읽음으로써 결정된다.

    Transfer-Encoding 헤더 필드가 요청에 존재하고 청크가 최종 인코딩이 아닌 경우, 메시지 본문 길이는 신뢰할 수 있게 결정할 수 없으므로 서버는 400 (Bad Request)로 응답한 다음 연결을 닫아야 한다(MUST).

  5. Transfer-Encoding이 없고 잘못된 Content-Length 헤더 필드가 있는 메시지가 수신되면, 메시지 프레이밍은 잘못된 것이며 수신자는 이를 복구 불가능한 오류로 처리해야 한다(MUST), 단 필드 값이 쉼표로 구분된 목록으로 성공적으로 파싱될 수 있고( 섹션 5.6.1 of [HTTP] ), 목록의 모든 값이 유효하며 목록의 모든 값이 동일한 경우(이 경우 메시지는 해당 단일 값을 Content-Length 필드 값으로 사용하여 처리된다). 요청 메시지에서 복구 불가능한 오류가 발생하면 서버는 400 (Bad Request)로 응답한 뒤 연결을 닫아야 한다. 프록시가 응답 메시지에서 이 오류를 수신하면 프록시는 서버와의 연결을 닫고 수신된 응답을 폐기한 뒤 클라이언트에 502 (Bad Gateway) 응답을 보내야 한다. 사용자 에이전트가 응답 메시지에서 이 오류를 수신하면 사용자 에이전트는 서버와의 연결을 닫고 수신된 응답을 폐기해야 한다.

  6. Content-Length 헤더 필드가 유효하게 존재하고 Transfer-Encoding이 없는 경우, 그 10진 값은 예상되는 메시지 본문 길이를 옥텟 단위로 정의한다. 송신자가 표시된 옥텟 수를 모두 전송하기 전에 연결을 닫거나 수신자가 타임아웃이 발생하면, 수신자는 메시지가 불완전하다고 간주하고 연결을 닫아야 한다(MUST).

  7. 이것이 요청 메시지이고 위의 어떤 경우도 해당되지 않으면, 메시지 본문 길이는 0이다(메시지 본문이 존재하지 않음).

  8. 그렇지 않으면, 선언된 메시지 본문 길이가 없는 응답 메시지이므로 메시지 본문 길이는 서버가 연결을 닫기 전에 수신한 옥텟 수에 의해 결정된다.

완전히 수신된 닫기-구분된 응답 메시지와 네트워크 장애로 인해 부분적으로 수신된 메시지를 구분할 방법이 없으므로, 서버는 가능한 경우 인코딩 또는 길이로 구분되는 메시지를 생성하는 것이 바람직하다(SHOULD). 닫기-구분 기능은 주로 HTTP/1.0과의 하위 호환성을 위해 존재한다.

Note: 요청 메시지는 항상 길이 또는 전송 코딩에 의해 명시적으로 프레이밍되므로, 요청 메시지는 결코 닫기-구분(close-delimited)이 되지 않는다. 둘 다 없으면 요청은 헤더 섹션 직후에 끝난다.

서버는 메시지 본문이 있지만 Content-Length가 없는 요청을 411 (Length Required)로 응답하여 거부할 수 있다(MAY).

청크 이외의 전송 코딩이 적용되지 않은 한, 메시지 본문 길이를 미리 알 수 있는 경우 요청을 보내는 클라이언트는 청크 전송 코딩 대신 유효한 Content-Length 헤더 필드를 사용하는 것이 권장된다(SHOULD)—일부 기존 서비스는 청크 전송 코딩을 이해하더라도 청크에 대해 411 (Length Required)로 응답하기 때문이다. 이는 일반적으로 그러한 서비스들이 게이트웨이를 통해 구현되어 전체 요청을 버퍼링하기 전에 콘텐츠 길이를 요구하기 때문이다.

메시지 본문을 포함한 요청을 전송하는 사용자 에이전트는 유효한 Content-Length 헤더 필드 또는 청크 전송 코딩 중 하나를 반드시 전송해야 한다(MUST). 클라이언트는 서버가 HTTP/1.1(또는 이후)을 처리할 것임을 알지 못하는 한 청크 전송 코딩을 사용해서는 안 된다(MUST NOT).

연결의 마지막 요청에 대한 최종 응답이 완전히 수신되었는데도 읽을 추가 데이터가 남아 있으면, 사용자 에이전트는 남은 데이터를 폐기하거나 그 데이터가 이전 메시지 본문의 일부인지 판단을 시도할 수 있다. 이는 이전 메시지의 Content-Length 값이 잘못된 경우에 해당할 수 있다. 클라이언트는 그러한 추가 데이터를 별도의 응답으로 처리, 캐시 또는 전달하면 안 된다(MUST NOT)—그렇게 하면 캐시 오염에 취약해지기 때문이다.

7. Transfer Codings

전송 코딩 이름들은 네트워크를 통한 "안전한 전송"을 보장하기 위해 메시지의 콘텐츠에 적용되었거나 적용될 수 있는 인코딩 변환을 나타내는 데 사용된다. 이는 전송 코딩이 전송되는 표현의 속성이 아니라 메시지의 속성이라는 점에서 콘텐츠 코딩과 다르다.

모든 transfer-coding 이름은 대소문자 비구분이며, 섹션 7.3에 정의된 대로 HTTP Transfer Coding 레지스트리에 등록되어야 한다. 이들은 Transfer-Encoding 및 TE 헤더 필드에서 사용된다(후자는 "transfer-coding" 문법도 정의한다).

7.1. Chunked Transfer Coding

청크 전송 코딩은 콘텐츠를 일련의 청크로 래핑하여 각각의 크기 표시자를 갖게 하고, 선택적인 트레일러 섹션을 뒤따르게 한다. 청크는 알려지지 않은 크기의 콘텐츠 스트림을 길이-구분된 버퍼의 연속으로 전송할 수 있게 하여 송신자가 연결을 유지하고 수신자가 전체 메시지를 수신했는지를 알 수 있게 한다.

  chunked-body   = *chunk
                   last-chunk
                   trailer-section
                   CRLF

  chunk          = chunk-size [ chunk-ext ] CRLF
                   chunk-data CRLF
  chunk-size     = 1*HEXDIG
  last-chunk     = 1*("0") [ chunk-ext ] CRLF

  chunk-data     = 1*OCTET ; a sequence of chunk-size octets

chunk-size 필드는 청크 데이터의 옥텟 수를 나타내는 16진수 숫자의 문자열이다. chunk-size가 0인 청크를 수신하면 청크 전송 코딩은 완료되며, 선택적으로 트레일러 섹션이 뒤따르고 마지막으로 빈 줄로 종료된다.

수신자는 청크 전송 코딩을 파싱하고 디코드할 수 있어야 한다(MUST).

HTTP/1.1은 중계자가 전체 응답을 버퍼링할 수 있음을 보장할 수 있도록 청크된 응답의 크기를 제한하는 수단을 정의하지 않는다. 또한 매우 큰 청크 크기는 수신 구현에서 정수 변환 오버플로우 또는 정수 표현의 정밀도 손실을 초래할 수 있다. 따라서 수신자는 잠재적으로 큰 16진 숫자를 예상하고 정수 변환 오버플로우나 정밀도 손실로 인한 구문 오류를 방지해야 한다(MUST).

청크 코딩은 어떠한 매개변수도 정의하지 않는다. 매개변수가 존재하면 오류로 간주하는 것이 바람직하다(SHOULD).

7.1.1. Chunk Extensions

청크 코딩은 각 청크가 chunk-size 바로 다음에 0개 이상의 청크 확장을 포함하도록 허용한다. 이는 각 청크별 메타데이터(예: 서명 또는 해시), 메시지 중간의 제어 정보, 또는 메시지 본문 크기의 무작위화 등을 제공하기 위함이다.

  chunk-ext      = *( BWS ";" BWS chunk-ext-name
                      [ BWS "=" BWS chunk-ext-val ] )

  chunk-ext-name = token
  chunk-ext-val  = token / quoted-string

청크 코딩은 각 연결에 특화되어 있으며 각 수신자(중계자 포함)에 의해 제거되거나 재코딩될 가능성이 크므로, 청크 확장의 사용은 일반적으로 "롱 폴링"과 같이 청크 확장의 사용에 대해 클라이언트와 서버가 공유된 기대를 가지는 특수한 HTTP 서비스나 종단 간 보안 연결 내의 패딩에 제한된다.

수신자는 인식하지 못하는 청크 확장을 무시해야 한다(MUST). 서버는 요청에서 수신되는 청크 확장의 총 길이를 제공되는 서비스에 대해 합리적인 양으로 제한해야 하며, 다른 메시지 부분에 대해 적용하는 것과 동일한 길이 제한 및 타임아웃을 적용하고, 그 양을 초과하면 적절한 4xx (Client Error) 응답을 생성해야 한다.

7.1.2. Chunked Trailer Section

트레일러 섹션은 송신자가 콘텐츠 전송 중에 동적으로 생성될 수 있는 메타데이터(예: 메시지 무결성 검사, 디지털 서명 또는 후처리 상태)를 메시지 끝에 추가할 수 있게 한다. 트레일러 필드의 적절한 사용과 제한은 섹션 6.5 of [HTTP]에 정의되어 있다.

  trailer-section   = *( field-line CRLF )

청크 코딩을 메시지에서 제거하는 수신자는 수신된 트레일러 필드를 선택적으로 유지하거나 폐기할 수 있다(MAY). 수신된 트레일러 필드를 유지하는 수신자는 그 트레일러 필드를 수신된 헤더 필드와 별도로 저장/전달하거나 헤더 섹션에 병합해야 한다(MUST). 수신자는 해당 트레일러 필드의 대응하는 헤더 필드 정의가 명시적으로 병합을 허용하고 안전한 병합 방법을 지시하지 않는 한 수신된 트레일러 필드를 헤더 섹션에 병합해서는 안 된다(MUST NOT).

7.1.3. Decoding Chunked

청크 전송 코딩을 디코드하는 과정은 다음의 의사 코드로 표현할 수 있다:

  length := 0
  read chunk-size, chunk-ext (if any), and CRLF
  while (chunk-size > 0) {
     read chunk-data and CRLF
     append chunk-data to content
     length := length + chunk-size
     read chunk-size, chunk-ext (if any), and CRLF
  }
  read trailer field
  while (trailer field is not empty) {
     if (trailer fields are stored/forwarded separately) {
         append trailer field to existing trailer fields
     }
     else if (trailer field is understood and defined as mergeable) {
         merge trailer field with existing header fields
     }
     else {
         discard trailer field
     }
     read trailer field
  }
  Content-Length := length
  Remove "chunked" from Transfer-Encoding

7.3. Transfer Coding Registry

"HTTP Transfer Coding Registry"는 전송 코딩 이름의 네임스페이스를 정의한다. 이는 https://www.iana.org/assignments/http-parameters에서 유지 관리된다.

등록에는 다음 필드들이 포함되어야 한다(MUST):

  • Name
  • Description
  • Pointer to specification text

전송 코딩의 이름은 인코딩 변환이 동일하지 않는 한 콘텐츠 코딩의 이름과 중복되어서는 안 된다(이는 섹션 7.2에서 정의한 압축 코딩의 경우처럼 인코딩 변환이 동일한 경우는 예외이다).

TE 헤더 필드는 여러 전송 코딩이 허용될 때 우선순위 값을 나타내기 위해 "q"라는 의사-매개변수를 사용한다. 향후 전송 코딩 등록은 모호함을 피하기 위해 대소문자 구분 없이 "q"라는 이름의 매개변수를 정의해서는 안 된다(SHOULD NOT).

이 네임스페이스에 값을 추가하려면 IETF 검토가 필요하며(자세한 내용은 섹션 4.8 참조) 등록은 이 명세서에서 정의한 전송 코딩의 목적에 부합해야 한다(MUST).

인코딩 형식의 식별에 프로그램 이름을 사용하는 것은 바람직하지 않으며 향후 인코딩에서는 권장되지 않는다.

7.4. Negotiating Transfer Codings

TE 필드( 섹션 10.1.4 of [HTTP] )는 클라이언트가 응답에서 chunked 이외에 어떤 전송 코딩을 허용하는지와 클라이언트가 청크 전송 코딩에서 트레일러 필드를 보존할 의사가 있는지를 나타내는 데 사용된다.

클라이언트는 TE에 chunked 전송 코딩 이름을 보내면 안 된다(MUST NOT); chunked는 HTTP/1.1 수신자에게 항상 허용된다.

TE 사용의 세 가지 예시는 아래와 같다.

TE: deflate
TE:
TE: trailers, deflate;q=0.5

여러 전송 코딩이 허용될 때, 클라이언트는 선호도에 따라 소문자 구분 없이 "q" 매개변수를 사용하여 코딩의 순위를 지정할 수 있다(콘텐츠 협상 필드에서 사용하는 q값과 유사함). 순위 값은 0에서 1 범위의 실수이며, 0.001은 가장 덜 선호되고 1은 가장 선호된다; 0은 "허용되지 않음"을 뜻한다.

TE 필드 값이 비어 있거나 TE 필드가 없는 경우, 허용되는 유일한 전송 코딩은 chunked이다. 전송 코딩이 없는 메시지는 항상 허용된다.

키워드 "trailers"는 송신자가 트레일러 필드를 폐기하지 않음을 나타낸다(자세한 내용은 섹션 6.5 참조).

TE 헤더 필드는 즉시 연결에만 적용되므로, TE를 보내는 송신자는 TE 헤더 필드가 중계자에 의해 전달되는 것을 방지하기 위해 Connection 헤더 필드 내에 "TE" 연결 옵션도 함께 보내야 한다(MUST).

8. 불완전한 메시지 처리

요청이 취소되었거나 타임아웃 예외가 발생하는 등으로 인해 불완전한 요청 메시지를 수신한 서버는 연결을 닫기 전에 오류 응답을 보낼 MAY 있다.

연결이 조기에 닫히거나 청크 전송 코딩을 디코딩하는 과정에서 실패하는 경우처럼 불완전한 응답 메시지를 수신한 클라이언트는 해당 메시지를 불완전한 것으로 기록해야 하며(MUST) 불완전한 응답에 대한 캐시 요건은 Section 3.3 of [CACHING]에 정의되어 있다.

응답이 헤더 섹션의 중간(빈 줄이 수신되기 전)에 종료되고 상태 코드가 응답의 전체 의미를 전달하기 위해 헤더 필드에 의존할 가능성이 있다면, 클라이언트는 그 의미가 전달되었다고 가정할 수 없다. 이 경우 클라이언트는 다음에 취할 조치를 결정하기 위해 요청을 반복해야 할 수도 있다.

청크 전송 코딩을 사용하는 메시지 본문은 인코딩을 종료하는 0크기 청크가 수신되지 않으면 불완전하다. 유효한 Content-Length를 사용하는 메시지는 수신된 메시지 본문 크기(옥텟)가 Content-Length 값보다 작으면 불완전하다. 청크 전송 코딩도 Content-Length도 없는 응답은 연결의 종료로 종료되며, 헤더 섹션이 온전하게 수신되었다면 기반 연결에서 오류(예: TLS의 "incomplete close")가 표시되지 않는 한 완전한 것으로 간주된다(자세한 내용은 Section 9.8 참조).

9. 연결 관리

HTTP 메시징은 기저의 전송층 또는 세션층 연결 프로토콜과 독립적이다. HTTP는 오직 신뢰할 수 있는 전송과 요청의 순서 보장 및 그에 대응하는 응답의 순서 보장을 전제로 한다. HTTP 요청 및 응답 구조를 기저 전송 프로토콜의 데이터 단위에 매핑하는 것은 이 명세서의 범위 밖이다.

Section 7.3 of [HTTP]에 설명된 바와 같이, HTTP 상호작용에 사용될 구체적인 연결 프로토콜은 클라이언트 구성 및 target URI에 의해 결정된다. 예를 들어 "http" URI 스킴은 IP 위의 TCP의 기본 연결(기본 포트 80)을 가리키지만, 클라이언트는 다른 연결, 포트 또는 프로토콜을 통해 프록시를 사용하도록 구성될 수 있다.

HTTP 구현체는 현재 연결의 상태 유지, 새 연결 설정 또는 기존 연결 재사용, 연결에서 수신된 메시지 처리, 연결 실패 감지 및 각 연결 닫기 등을 포함하는 연결 관리를 수행해야 한다. 대부분의 클라이언트는 서버 엔드포인트별로 둘 이상의 병렬 연결을 포함하여 다수의 연결을 유지하고, 대부분의 서버는 공정한 사용을 보장하고 DoS 공격을 탐지하기 위해 요청 큐를 제어하면서 수천 개의 동시 연결을 유지하도록 설계된다.

9.1. 설정

다양한 전송층 또는 세션층 프로토콜을 통해 연결이 어떻게 설정되는지를 설명하는 것은 이 명세서의 범위를 벗어난다. 각 HTTP 연결은 하나의 기저 전송 연결에 매핑된다.

9.2. 응답을 요청에 연결하기

HTTP/1.1은 특정 요청 메시지와 그에 대응하는 하나 이상의 응답 메시지를 연결하기 위한 요청 식별자를 포함하지 않는다. 따라서 같은 연결에서 요청이 이루어진 순서와 응답이 도착하는 순서는 정확히 일치해야 한다고 가정한다. 하나의 요청에 대해 여러 응답이 발생하는 경우는 하나 이상의 정보 응답(1xx)이 최종 응답에 앞서 보내질 때만 발생한다.

한 연결에서 미완료 요청이 여러 개인 클라이언트는 전송한 순서대로 미완료 요청 목록을 유지해야 하며(MUST), 해당 연결에서 수신한 각 응답 메시지를 아직 최종(비-1xx) 응답을 받지 못한 첫 번째 미완료 요청에 연관시켜야 한다(MUST).

클라이언트가 미완료 요청이 없는 연결에서 데이터를 수신하면, 그 데이터는 유효한 응답으로 간주해서는 안 된다(MUST NOT). 메시지 구분이 모호해졌으므로 클라이언트는 연결을 닫는 것이 바람직하다(SHOULD), 단 수신된 데이터가 하나 이상의 CRLF만으로 구성되어 폐기할 수 있는 경우(Section 2.2 참조)를 제외한다.

9.3. 지속 연결

HTTP/1.1은 다중 요청 및 응답을 단일 연결에서 전송할 수 있는 지속 연결의 사용을 기본값으로 한다. HTTP 구현체는 지속 연결을 지원하는 것이 바람직하다(SHOULD).

수신자는 프로토콜 버전과 해당 연결에서 가장 최근에 수신된 메시지의 Connection 헤더 필드(Section 7.6.1 참조)를 기준으로 연결이 지속되는지 여부를 결정한다:

  • 연결 옵션으로 "close"가 존재하면(Section 9.6) 현재 응답 후 연결은 지속되지 않는다; 그렇지 않으면,
  • 수신된 프로토콜이 HTTP/1.1(또는 이후)인 경우 현재 응답 후 연결은 지속된다; 그렇지 않으면,
  • 수신된 프로토콜이 HTTP/1.0이고 "keep-alive" 연결 옵션이 존재하며 수신자가 프록시가 아니거나 메시지가 응답이며 수신자가 HTTP/1.0 "keep-alive" 메커니즘을 존중하려는 경우 현재 응답 후 연결은 지속된다; 그렇지 않으면,
  • 현재 응답 후 연결은 닫힌다.

지속 연결을 지원하지 않는 클라이언트는 모든 요청 메시지에서 "close" 연결 옵션을 전송해야 한다(MUST).

지속 연결을 지원하지 않는 서버는 상태 코드가 1xx (Informational)가 아닌 모든 응답 메시지에서 "close" 연결 옵션을 전송해야 한다(MUST).

클라이언트는 "close" 연결 옵션을 전송하거나 HTTP/1.0 응답에서 "keep-alive" 연결 옵션을 수신할 때까지 지속 연결에서 추가 요청을 보낼 수 있다(MAY).

연결을 지속하려면 연결의 모든 메시지는 스스로 정의된 메시지 길이(즉, 연결 종료로 정의되지 않는 길이)를 가져야 한다(자세한 내용은 Section 6 참조). 서버는 전체 요청 메시지 본문을 읽거나 응답을 전송한 후 연결을 닫아야 한다(MUST); 그렇지 않으면 지속 연결에 남아 있는 데이터는 다음 요청으로 잘못 해석될 수 있다. 마찬가지로, 클라이언트는 동일한 연결을 재사용하려면 전체 응답 메시지 본문을 읽어야 한다(MUST).

프록시 서버는 HTTP/1.0 클라이언트와 지속 연결을 유지해서는 안 된다(MUST NOT). 자세한 내용은 Appendix C.2.2 참조.

HTTP/1.0 클라이언트와의 하위 호환성에 대한 추가 정보는 Appendix C.2.2를 참조하라.

9.3.1. 요청 재시도

연결은 의도적이든 아니든 언제든지 닫힐 수 있다. 구현체는 비동기적 닫힘 이벤트에서 복구할 필요가 있음을 예상해야 한다. 클라이언트가 자동으로 미완료 요청 시퀀스를 재시도할 수 있는 조건은 Section 9.2.2 of [HTTP]에 정의되어 있다.

9.3.2. 파이프라이닝

지속 연결을 지원하는 클라이언트는 요청을 파이프라인(즉, 각 응답을 기다리지 않고 여러 요청을 전송)할 수 있다(MAY). 서버는 모든 요청이 안전한 메서드인 경우 파이프라인된 요청 시퀀스를 병렬로 처리할 수 있으나(Section 9.2.1 참조) 응답은 요청이 수신된 순서대로 동일한 순서로 전송해야 한다(MUST).

파이프라인을 사용하는 클라이언트는 연결이 모든 해당 응답을 수신하기 전에 닫히면 응답을 받지 못한 요청을 재시도해야 한다(SHOULD). 실패한 연결 후 파이프라인된 요청을 재시도할 때에는(서버에 의해 마지막 완전한 응답으로 명시적으로 닫히지 않은 연결), 클라이언트는 연결이 성립된 직후에 즉시 파이프라인해서는 안 된다(MUST NOT); 이전 파이프라인에서 남아 있는 첫 번째 요청이 에러 응답을 유발했을 수 있고, 이는 다시 전송될 때 또다시 손실될 수 있기 때문이다(자세한 내용은 Section 9.6에 설명된 TCP reset 문제 참조).

멱등(idempotent) 메서드(Section 9.2.2 참조)는 파이프라이닝에 중요하다. 왜냐하면 이들은 연결 실패 후 자동으로 재시도될 수 있기 때문이다. 사용자 에이전트는 비멱등 메서드 이후에는 최종 응답 상태 코드가 수신될 때까지 파이프라인을 사용해서는 안 된다(SHOULD NOT), 단 사용자 에이전트가 파이프라인된 시퀀스에서 부분 실패를 탐지하고 복구할 수 있는 수단이 있는 경우는 예외이다.

파이프라인된 요청을 수신한 중계자는 이를 내부로 전달할 때 파이프라인할 수 있다(MAY), 이는 아웃바운드 사용자 에이전트가 어떤 요청을 안전하게 파이프라인할 수 있는지 결정할 수 있기 때문이다. 인바운드 연결이 응답을 받기 전에 실패하면, 파이프라인된 중계자는 응답을 아직 받지 못한 idempotent 메서드의 요청 시퀀스를 재시도할 수 있다(MAY). 그렇지 않다면 중계자는 수신된 응답을 전달한 다음 해당 아웃바운드 연결을 닫아 아웃바운드 사용자 에이전트가 적절히 복구할 수 있도록 해야 한다(SHOULD).

9.4. 동시성

클라이언트는 특정 서버에 대해 동시에 열어 두는 연결 수를 제한하는 것이 바람직하다.

이전 HTTP 개정판은 연결 수의 상한을 명시했지만, 이는 많은 응용 프로그램에 비현실적임이 밝혀졌다. 따라서 이 명세서는 특정 최대 연결 수를 강제하지 않고, 대신 클라이언트가 여러 연결을 열 때 보수적일 것을 권장한다.

여러 연결을 사용하는 주된 이유는 서버 측 처리 시간이 많이 걸리거나 매우 큰 콘텐츠 전송이 다음 요청을 블록하는 "헤드 오브 라인 블로킹" 문제를 피하기 위함이다. 그러나 각 연결은 서버 자원을 소비한다.

또한 여러 연결을 사용하면 혼잡한 네트워크에서 바람직하지 않은 부작용을 초래할 수 있다. 더 많은 연결을 사용하면 초기의 동기화된 전송 동작으로 인해 혼잡이 발생할 수 있어, 적은 병렬 연결을 사용했을 때와 다른 결과를 초래할 수 있다.

서버는 단일 클라이언트로부터의 과도한 연결 수와 같이 남용 또는 DoS 공격의 특징으로 판단되는 트래픽을 거부할 수 있다는 점을 유의하라.

9.5. 장애 및 타임아웃

서버는 비활성 연결을 더 이상 유지하지 않는 시간 초과 값을 보통 가지고 있다. 프록시 서버는 클라이언트가 동일한 프록시를 통해 더 많은 연결을 만들 가능성이 있으므로 이 값을 더 높게 설정할 수 있다. 지속 연결의 사용은 클라이언트나 서버 어느 쪽에도 이 타임아웃의 길이(또는 존재)에 대한 요구사항을 부과하지 않는다.

타임아웃을 적용하려는 클라이언트 또는 서버는 연결에 대해 정상 종료(graceful close)를 수행하는 것이 바람직하다(SHOULD). 구현체는 열린 연결에서 수신된 종료 신호를 지속적으로 모니터링하고 적절히 응답해야 한다(SHOULD), 왜냐하면 양측의 신속한 종료는 할당된 시스템 자원을 회수하는 데 도움이 되기 때문이다.

클라이언트, 서버 또는 프록시는 언제든지 전송 연결을 닫을 MAY 있다. 예를 들어, 클라이언트가 새 요청 전송을 시작한 동시에 서버가 "유휴" 연결을 닫기로 결정할 수 있다. 서버 관점에서는 연결이 유휴 상태에서 닫히는 것이지만, 클라이언트 관점에서는 요청이 진행 중일 수 있다.

서버는 가능한 경우 지속 연결을 유지하고 기저 전송의 흐름 제어 메커니즘이 일시적인 과부하를 해결하도록 허용하는 것이 바람직하다(SHOULD). 연결을 종료하고 클라이언트가 재시도하도록 기대하는 방식은 네트워크 혼잡이나 서버 부하를 악화시킬 수 있다.

메시지 본문을 전송하는 클라이언트는 전송 중에 네트워크 연결에서 오류 응답이 오는지 모니터링해야 한다(SHOULD). 클라이언트가 서버가 메시지 본문을 수신하기를 원하지 않으며 연결을 닫고 있다는 응답을 보면 즉시 전송을 중단하고 자신의 쪽 연결을 닫아야 한다(SHOULD).

9.6. 종료

"close" 연결 옵션은 송신자가 응답 완료 후 이 연결을 닫을 것이라는 신호로 정의된다. 송신자는 연결을 닫을 의사가 있을 때 "close" 연결 옵션을 포함하는 Connection 헤더 필드를 전송하는 것이 바람직하다(SHOULD). 예를 들어,

Connection: close

요청 헤더 필드로서 이는 클라이언트가 이 연결에서 보낼 마지막 요청임을 나타내고, 응답에서는 동일한 필드가 서버가 응답 메시지 완료 후 이 연결을 닫을 것임을 나타낸다.

필드 이름 "Close"는 예약되어 있으므로, 해당 이름을 헤더 필드로 사용하는 것은 "close" 연결 옵션과 충돌할 수 있다.

"close" 연결 옵션을 전송한 클라이언트는 그 요청(해당 "close"를 포함한 것) 이후로 해당 연결에서 추가 요청을 보내서는 안 되며(MUST NOT) 이 요청에 대한 최종 응답을 읽은 후 연결을 닫아야 한다(MUST).

"close" 연결 옵션을 수신한 서버는 그 "close"를 포함한 요청에 대한 최종 응답을 전송한 후 연결 종료를 시작해야 한다(MUST; 아래 참조). 서버는 해당 연결에서 최종 응답으로 "close" 연결 옵션을 보내는 것이 바람직하다(SHOULD). 서버는 해당 연결에서 수신되는 추가 요청을 처리해서는 안 된다(MUST NOT).

"close" 연결 옵션을 보내는 서버는 그 "close"를 포함한 응답을 전송한 후 연결 종료를 시작해야 하며(MUST) 해당 연결에서 수신되는 추가 요청을 처리해서는 안 된다(MUST NOT).

"close" 연결 옵션을 포함하는 응답을 수신한 클라이언트는 해당 연결에서의 요청 전송을 중단하고 그 응답을 읽은 후 연결을 닫아야 하며(MUST) 추가로 파이프라인된 요청이 있으면 서버가 그것들을 처리할 것이라고 가정해서는 안 된다(SHOULD NOT).

서버가 TCP 연결을 즉시 닫는 경우, 클라이언트가 마지막 HTTP 응답을 읽지 못할 위험이 상당히 있다. 서버가 클라이언트로부터 추가 데이터를 수신하면(예: 서버의 응답을 받기 전에 클라이언트가 보낸 또 다른 요청), 서버의 TCP 스택은 클라이언트로 리셋 패킷을 보낼 것이고; 불행히도 이 리셋 패킷은 클라이언트의 미확인 입력 버퍼를 지워서 클라이언트의 HTTP 파서가 이를 읽고 해석하기 전에 소멸시킬 수 있다.

TCP 리셋 문제를 피하기 위해 서버는 일반적으로 단계적으로 연결을 닫는다. 먼저 서버는 쓰기 측만 닫아 반쪽 닫기(half-close)를 수행한다. 그런 다음 서버는 클라이언트의 해당 닫힘을 수신하거나 서버 자신의 TCP 스택이 서버의 마지막 응답을 포함한 패킷에 대한 클라이언트의 확인을 수신했다고 합리적으로 확신할 때까지 연결을 계속 읽는다. 마지막으로 서버는 연결을 완전히 닫는다.

리셋 문제에 TCP만 해당하는지 또는 다른 전송 프로토콜에서도 발생하는지는 알려져 있지 않다.

클라이언트가 반쪽 닫기로 TCP 연결을 닫는다고 해서 요청 메시지가 구분되거나 클라이언트가 더 이상 응답에 관심이 없다는 것을 의미하지는 않는다. 일반적으로 전송 신호는 HTTP/1.1이 전송과 독립적이므로 에지케이스를 신호하기 위해 신뢰할 수 없다.

9.7. TLS 연결 시작

개념적으로 HTTP/TLS는 TLS로 보호된 연결을 통해 HTTP 메시지를 전송하는 것이다([TLS13]).

HTTP 클라이언트는 또한 TLS 클라이언트로 동작한다. 적절한 포트로 서버에 연결을 시도하고 TLS 핸드셰이크를 시작하기 위해 TLS ClientHello를 전송한다. TLS 핸드셰이크가 완료되면 클라이언트는 첫 번째 HTTP 요청을 시작할 수 있다. 모든 HTTP 데이터는 TLS의 "application data"로 전송되어야 하며(MUST) 그 외에는 일반 연결처럼 취급된다(지속 연결 재사용 포함).

9.8. TLS 연결 종료

TLS는 오류가 아닌 연결 종료 전에 종료 알림(closure alerts)을 교환하여 안전한 연결 종료를 제공한다(자세한 내용은 Section 6.1 of [TLS13] 참조). 유효한 종료 알림을 수신하면 구현체는 해당 연결에서 더 이상의 데이터가 수신되지 않음을 확신할 수 있다.

구현체가 자신이 관심 있는 모든 메시지 데이터를 전송하거나 수신했음을 알게 되면, 보통 HTTP 메시지 경계를 감지함으로써, 상대의 대응 종료 알림을 기다리지 않고 종료 알림을 보낸 뒤 연결을 닫아 "incomplete close"를 생성할 수 있다.

불완전한 종료는 이미 수신된 데이터의 보안성을 문제 삼지는 않지만, 이후의 데이터가 잘리었을 가능성을 나타낼 수 있다. TLS는 HTTP 메시지 프레이밍을 직접 알지 못하므로 메시지가 완전한지 판단하려면 HTTP 데이터를 검사해야 한다. 불완전한 메시지 처리 방법은 Section 8에 정의되어 있다.

불완전한 종료를 만났을 때, 클라이언트는 다음 중 어느 하나라도 수신했으면 그 요청들을 완료된 것으로 간주하는 것이 바람직하다(SHOULD):

  1. Content-Length 헤더 필드에 지정된 만큼의 데이터

  2. 청크 전송 코딩이 사용된 경우의 종료를 알리는 0크기 청크

청크 전송 코딩도 Content-Length도 없는 응답은 유효한 종료 알림을 수신한 경우에만 완전한 것으로 간주된다. 불완전한 메시지를 완전한 것으로 처리하면 구현체를 공격에 노출할 수 있다.

불완전한 종료를 감지한 클라이언트는 우아하게 복구해야 한다(SHOULD).

클라이언트는 연결을 닫기 전에 종료 알림을 반드시 보내야 한다(MUST). 더 이상 데이터를 받지 않을 것으로 예상되는 클라이언트는 서버의 종료 알림을 기다리지 않고 단순히 연결을 닫아 서버 측에서 불완전한 종료를 생성할 MAY 있다.

서버는 클라이언트가 데이터를 끝까지 찾을 수 있는 경우가 많으므로 클라이언트로부터 불완전한 종료를 받을 준비를 해야 한다(SHOULD).

서버는 클라이언트와 종료 알림 교환을 시도해야 하며(MUST) 종료 알림을 보낸 후 연결을 닫아 클라이언트 측에서 불완전한 종료를 생성할 MAY 있다.

11. 보안 고려사항

이 섹션은 개발자, 정보 제공자 및 사용자에게 HTTP 메시지 구문 및 파싱과 관련된 알려진 보안 고려사항을 알리기 위한 것이다. HTTP 의미론, 콘텐츠 및 라우팅에 대한 보안 고려사항은 [HTTP]를 참조하라.

11.1. 응답 분할

응답 분할(일명 CRLF 인젝션)은 HTTP 메시지 프레이밍의 행 기반 특성과 지속 연결에서 요청과 응답의 순서 연관을 악용하는 다양한 웹 공격에서 사용되는 일반적인 기법이다([Klein]). 이 기법은 요청이 공유 캐시를 통과할 때 특히 심각한 피해를 줄 수 있다.

응답 분할은 공격자가 요청의 어떤 매개변수에 인코딩된 데이터를 보내고, 그 데이터가 나중에 디코드되어 응답의 헤더 필드 중 하나에 반영되는 서버(보통 애플리케이션 서버)의 취약점을 악용한다. 디코드된 데이터가 응답이 끝나고 이후 응답이 시작된 것처럼 보이도록 조작되면 응답이 분할되고, 분할된 두 번째 응답의 내용은 공격자가 제어하게 된다. 그런 다음 공격자는 동일한 지속 연결에서 다른 요청을 수행하고 수신자(중계자 포함)를 속여 분할된 두 번째 부분이 두 번째 요청에 대한 신뢰할 수 있는 응답이라고 믿게 만들 수 있다.

예를 들어, 요청-타겟 내의 매개변수가 애플리케이션 서버에 의해 읽혀 리다이렉트에 재사용되어 그 매개변수가 응답의 Location 헤더 필드에 반영될 수 있다. 매개변수가 애플리케이션에 의해 디코드되고 응답 필드에 올바르게 인코딩되지 않으면, 공격자는 인코딩된 CRLF 옥텟 및 기타 콘텐츠를 보내어 애플리케이션의 단일 응답을 두 개 이상의 응답처럼 보이게 만들 수 있다.

응답 분할에 대한 일반적인 방어는 인코딩된 CR 및 LF(예: "%0D" 및 "%0A")처럼 보이는 데이터를 필터링하는 것이다. 그러나 이는 애플리케이션 서버가 단지 URI 디코딩만 수행한다는 가정에 기반하며, 문자셋 변환, XML 엔티티 변환, base64 디코딩, sprintf 재포맷 등 더 모호한 데이터 변환이 일어날 수 있는 경우를 고려하지 못한다. 더 효과적인 완화책은 서버의 핵심 프로토콜 라이브러리 이외에서 헤더 섹션 내에 CR 또는 LF를 전송하지 못하도록 제한하는 것으로, 이는 잘못된 옥텟을 필터링하는 API로 헤더 필드 출력을 제한하고 애플리케이션 서버가 프로토콜 스트림에 직접 쓰는 것을 허용하지 않는 것을 의미한다.

11.2. 요청 스머글링

요청 스머글링([Linhart])은 서로 다른 수신자들 사이의 프로토콜 파싱 차이를 악용하여 추가 요청을 숨기는 기법으로, 이러한 추가 요청은 정책에 의해 차단되거나 비활성화되었을 수 있는 것을 겉보기에는 무해한 요청 안에 숨긴다. 응답 분할과 마찬가지로 요청 스머글링은 HTTP 사용에 대한 다양한 공격으로 이어질 수 있다.

이 명세서는 특히 메시지 프레이밍과 관련된 요청 파싱에 대해 섹션 6.3에서 요청 스머글링의 효과를 줄이기 위한 새로운 요구사항을 도입했다.

11.3. 메시지 무결성

HTTP는 메시지 무결성을 보장하는 특정 메커니즘을 정의하지 않으며, 대신 기저 전송 프로토콜의 오류 검출 능력과 완전성을 감지하기 위한 길이 또는 청크 구분 프레이밍에 의존한다. 역사적으로 단일 무결성 메커니즘의 부재는 대부분의 HTTP 통신이 비공식적이라는 점으로 정당화되었으나, HTTP의 광범위한 사용으로 인해 메시지 무결성 검증이 중요한 환경에서의 사용이 증가하고 있다.

"https" 스킴과 함께 제공되는 메커니즘(예: 인증된 암호화)은 메시지 변조로부터 보호를 제공한다. 다만 연결 종료가 메시지 절단(truncate)에 이용될 수 없도록 주의가 필요하다(자세한 내용은 섹션 9.8 참조). 사용자 에이전트는 불완전한 메시지를 거부하거나 특별하게 처리할 수 있다. 예를 들어 의료 기록 또는 약물 상호작용 정보를 표시하는 브라우저는 프로토콜에 의해 해당 정보가 전송 중 불완전하거나 만료되었거나 손상되었다고 판단되면 사용자에게 이를 표시해야 할 것이다. 이러한 메커니즘은 사용자 에이전트 확장이나 응답에 포함된 메시지 무결성 메타데이터의 존재를 통해 선택적으로 활성화될 수 있다.

"http" 스킴은 우발적이거나 악의적인 메시지 변조로부터 보호를 제공하지 않는다.

프로토콜의 확장은 중계자에 의한 원치 않는 메시지 변조 위험을 완화하는 데 사용될 수 있으며, "https" 스킴이 사용되더라도 중계자에 의한 변조 위험을 줄일 수 있다. 무결성은 메시지 인증 코드 또는 디지털 서명 같은 메커니즘을 확장 가능한 메타데이터 필드로 선택적으로 추가하여 보장할 수 있다.

11.4. 메시지 기밀성

HTTP는 메시지 기밀성이 필요할 때 이를 제공하기 위해 기저 전송 프로토콜에 의존한다. HTTP는 전송 프로토콜과 독립적으로 설계되어 다양한 형태의 암호화된 연결 위에서 사용할 수 있으며, 그러한 전송 선택은 URI 스킴이나 사용자 에이전트 구성에 의해 식별된다.

기밀 연결이 필요한 리소스를 식별하기 위해 "https" 스킴을 사용할 수 있다(자세한 내용은 섹션 4.2.2 참조).

부록 B. HTTP와 MIME의 차이

HTTP/1.1은 Internet Message Format [RFC5322] 및 Multipurpose Internet Mail Extensions (MIME) [RFC2045]에서 정의된 많은 구문 요소를 사용하여 메시지 본문을 다양한 표현과 확장 가능한 필드와 함께 전송할 수 있게 한다. 그러나 이러한 구성 요소들 중 일부는 대화형 통신의 요구에 맞게 재해석되어 MIME 구성 요소가 HTTP 내에서 사용되는 방식에 차이를 초래했다. 이러한 차이는 이진 연결에서의 성능 최적화, 새로운 미디어 타입 사용의 자유도 증가, 날짜 비교의 용이성 및 일반적인 구현의 수용을 위해 신중히 선택되었다.

이 부록은 HTTP가 MIME과 다른 구체적인 영역을 설명한다. 엄격한 MIME 환경과의 프록시 및 게이트웨이는 이러한 차이를 인식하고 필요시 적절한 변환을 제공해야 한다.

B.1. MIME-Version

HTTP는 MIME 준수 프로토콜은 아니지만, 메시지는 사용된 MIME 프로토콜의 버전을 나타내기 위해 단일 MIME-Version 헤더 필드를 포함할 수 있다. MIME-Version 헤더 필드의 사용은 메시지가 MIME 프로토콜과 완전하게 일치함을 나타낸다([RFC2045] 참조). 송신자는 HTTP 메시지를 엄격한 MIME 환경으로 내보낼 때 가능한 경우 완전한 준수를 보장할 책임이 있다.

B.2. 정규형으로의 변환

MIME은 Internet 메일 본문 부분을 전송 전에 정규형으로 변환할 것을 요구한다(자세한 내용은 Section 4 of [RFC2049] 참조). 또한 "text" 타입의 콘텐츠는 줄 바꿈을 CRLF로 표현해야 하며, 줄 바꿈 이외의 곳에서 CR 또는 LF를 사용하는 것을 금지한다([RFC2046]). 반면 HTTP는 콘텐츠 내에서 CRLF, 단독 CR 또는 단독 LF 중 어느 것을 줄 바꿈으로 사용할지에 대해서는 제한하지 않는다.

HTTP에서 엄격한 MIME 환경으로의 프록시나 게이트웨이는 텍스트 미디어 타입 내의 모든 줄 바꿈을 RFC 2049의 정규형인 CRLF로 변환해야 한다. 다만 이는 Content-Encoding의 존재나 일부 문자셋이 CR과 LF를 각각 옥텟 13과 10으로 사용하지 않는다는 사실로 인해 복잡해질 수 있다.

변환은 원본 콘텐츠에 적용된 어떤 암호화 체크섬도 손상시킬 수 있으므로, 원본 콘텐츠가 이미 정규형이라면 정규형 사용이 권장된다.

B.3. 날짜 형식 변환

HTTP/1.1은 날짜 비교를 단순화하기 위해 제한된 날짜 형식 집합(Section 5.6.7 of [HTTP])을 사용한다. 다른 프로토콜로부터의 프록시나 게이트웨이는 메시지에 존재하는 Date 헤더 필드가 HTTP/1.1 형식 중 하나에 일치하도록 보장하고 필요시 날짜를 재작성해야 한다.

B.4. Content-Encoding 변환

MIME에는 HTTP의 Content-Encoding 헤더 필드와 동등한 개념이 없다. 이는 미디어 타입에 대한 수식어로 작용하므로, HTTP에서 MIME 준수 프로토콜로의 프록시 및 게이트웨이는 Content-Type 헤더 필드의 값을 변경하거나 전송 전에 표현을 디코드해야 한다. (일부 실험적 응용에서는 ";conversions=<content-coding>" 같은 미디어 타입 매개변수를 사용했으나 이는 MIME 표준의 일부가 아니다.)

B.5. Content-Transfer-Encoding 변환

HTTP는 MIME의 Content-Transfer-Encoding 필드를 사용하지 않는다. MIME 준수 프로토콜에서 HTTP로의 프록시 및 게이트웨이는 응답 메시지를 HTTP 클라이언트에게 전달하기 전에 모든 Content-Transfer-Encoding을 제거해야 한다.

HTTP에서 MIME 준수 프로토콜로의 프록시 및 게이트웨이는 목적지 프로토콜의 제한에 따른 "안전한 전송"을 보장하기 위해 메시지가 올바른 형식과 인코딩으로 변환되도록 책임을 져야 한다. 이러한 변환이 목적지 프로토콜에서의 안전 전송 가능성을 높인다면 적절한 Content-Transfer-Encoding을 적용하고 라벨링해야 한다.

B.6. MHTML 및 행 길이 제한

MHTML([RFC2557]) 구현과 코드를 공유하는 HTTP 구현체는 MIME의 행 길이 제한을 인지해야 한다. HTTP는 이러한 제한이 없으므로 긴 행을 접지 않는다. HTTP로 전송되는 MHTML 메시지는 MHTML의 모든 관습(행 길이 제한 및 접기, 정규화 등)을 준수해야 한다. HTTP는 메시지 본문을 수정 없이 전송하며, "multipart/byteranges" 타입을 제외하고는 콘텐츠나 그 안에 포함된 MIME 헤더 행을 해석하지 않는다.

부록 C. 이전 RFC와의 변경 사항

C.1. HTTP/0.9로부터의 변경 사항

HTTP/0.9는 요청에 헤더 필드를 지원하지 않았기 때문에 이름 기반 가상 호스트(요청의 Host 헤더 필드 검사로 리소스 선택)를 지원할 메커니즘이 없다. 이름 기반 가상 호스트를 구현하는 서버는 HTTP/0.9 지원을 비활성화해야 한다. HTTP/0.9로 보이는 대부분의 요청은 실제로는 클라이언트가 request-target을 올바르게 인코딩하지 못해 잘못 구성된 HTTP/1.x 요청이다.

C.2. HTTP/1.0로부터의 변경 사항

C.2.1. 다중 호스팅 웹 서버

클라이언트와 서버가 Host 헤더 필드를 지원하고(누락 시 오류 보고), 절대 URI를 허용하도록 한 요구사항(Section 3.2)은 HTTP/1.1에서 가장 중요한 변경 사항 중 하나이다.

이전의 HTTP/1.0 클라이언트는 IP 주소와 서버 간의 일대일 관계를 가정했으며, 요청의 의도된 서버를 구분할 메커니즘이 요청이 전송된 IP 주소 외에는 없었다. Host 헤더 필드는 HTTP/1.1 개발 중 도입되었고 대부분의 HTTP/1.0 브라우저에 빠르게 구현되었으나, 완전한 도입을 보장하기 위해 모든 HTTP/1.1 요청에 추가 요구사항이 부과되었다. 이 문서 작성 시점에서는 대부분의 HTTP 기반 서비스가 요청 타깃팅을 위해 Host 헤더 필드에 의존하고 있다.

C.2.2. Keep-Alive 연결

HTTP/1.0에서는 각 연결이 요청 전에 클라이언트에 의해 설정되고 응답 후 서버에 의해 닫혔다. 그러나 일부 구현체는 RFC 2068의 Section 19.7.1에 설명된 명시적으로 협상된("Keep-Alive") 지속 연결을 구현하기도 했다.

일부 클라이언트와 서버는 이러한 이전의 지속 연결 접근 방식과 호환되기를 원할 수 있으며, "Connection: keep-alive" 요청 헤더 필드로 이를 명시적으로 협상하려고 한다. 그러나 일부 실험적 HTTP/1.0 지속 연결 구현은 결함이 있어, 예를 들어 HTTP/1.0 프록시가 Connection을 이해하지 못하면 해당 헤더를 잘못 전달하여 연결이 멈추게 될 수 있다.

이를 해결하기 위해 Proxy-Connection 헤더 필드가 도입되기도 했으나, 프록시가 여러 계층으로 배포되는 경우 동일한 문제가 발생하여 실용적이지 않았다.

결과적으로 클라이언트는 어떤 요청에서도 Proxy-Connection 헤더 필드를 보내지 않는 것이 권장된다.

또한 클라이언트는 요청에서 "Connection: keep-alive" 사용을 신중히 고려해야 한다; 이는 HTTP/1.0 서버와 지속 연결을 활성화할 수 있지만, 이러한 기능을 사용하는 클라이언트는 "hung" 요청(클라이언트가 헤더 필드 전송을 중단해야 함을 나타냄)을 모니터링해야 하며 프록시가 사용될 때는 이 메커니즘을 사용해서는 안 된다.

C.2.3. Transfer-Encoding 도입

HTTP/1.1은 Transfer-Encoding 헤더 필드를 도입했다(Section 6.1). 전송 코딩은 MIME 호환 프로토콜을 통해 HTTP 메시지를 전달하기 전에 디코딩되어야 한다.

C.3. RFC 7230으로부터의 변경 사항

HTTP의 설계 목표, 역사, 아키텍처, 적합성 기준, 프로토콜 버전 관리, URI, 메시지 라우팅 및 헤더 필드에 관한 대부분의 섹션이 [HTTP]로 이동되었다. 이 문서는 HTTP/1.1에 특정한 메시지 구문과 연결 관리 요구사항으로 축소되었다.

콘텐츠 외부에서의 단독 CR은 금지되었다. (Section 2.2)

authority-form의 ABNF 정의는 포트가 선택적인 URI의 보다 일반적인 authority 구성 요소에서 CONNECT에 요구되는 host:port 형식으로 변경되었다. (Section 3.2.3)

수신자는 모호한 메시지 프레이밍을 처리할 때 스머글링/분할 공격을 피해야 한다는 요구사항이 추가되었다. (Section 6.1)

청크 확장(ABNF)에서 ";" 및 "=" 주위의 (나쁜) 공백이 다시 도입되었다. 공백은 RFC7230에서 제거되었으나 그 변경이 기존 구현을 깨뜨리는 것으로 밝혀졌다. (Section 7.1.1)

트레일러 필드의 의미는 이제 청크 전송 코딩의 세부 사항을 초월한다. 청크 디코드 알고리즘(Section 7.1.3)은 트레일러 필드를 헤더 섹션과 분리하여 저장/전달하도록 권장하고, 수신자가 해당 필드 정의가 병합을 허용하고 병합 방법을 정의하는 경우에만 헤더 섹션으로 병합을 허용하며, 그렇지 않으면 트레일러 필드를 병합하지 말고 폐기하도록 업데이트되었다. 트레일러 부분은 이제 헤더 섹션과 더 일관되고 본문 부분과 더 구분되도록 트레일러 섹션이라고 불린다. (Section 7.1.2)

TE 헤더 필드에서 순위로 사용되는 "q"의 사용과 충돌을 피하기 위해 "q"라는 전송 코딩 매개변수는 허용되지 않는다. (Section 7.3)
