HTTP에서 Early Data 사용

초록

TLS early data를 사용하면 재생(replay) 공격의 가능성에 노출될 수 있습니다. 이 문서는 클라이언트가 early data로 전송한 HTTP 요청에 대해 서버와 통신할 수 있도록 허용하는 메커니즘을 정의합니다. 재생 위험을 완화하기 위해 이러한 메커니즘을 사용하는 기법들이 설명됩니다.

1. 소개

TLS 1.3 [TLS13] 은 얼리 데이터(제로 라운드 트립 타임(0-RTT) 데이터라고도 함)의 개념을 소개합니다. 클라이언트가 동일한 서버와 최근에 통신한 적이 있다면, 얼리 데이터는 TLS 핸드셰이크가 완료되기를 기다리지 않고 연결의 첫 번째 왕복에서 클라이언트가 서버로 데이터를 보낼 수 있게 합니다.

HTTP [HTTP] 와 함께 사용될 때, 얼리 데이터는 클라이언트가 즉시 요청을 보낼 수 있게 하여 TLS 핸드셰이크에 필요한 한두 번의 왕복 지연을 피할 수 있게 합니다. 이는 중요한 성능 향상이나, 중요한 제약이 존재합니다.

얼리 데이터를 사용할 때의 주요 위험은 공격자가 해당 요청들을 캡처하여 재생(replay)할 수 있다는 점입니다. TLS [TLS13] 은 공격자가 요청을 성공적으로 재생할 가능성을 줄이기 위해 사용할 수 있는 기술들을 설명하지만, 이러한 기술은 배포가 어렵고 여전히 성공적인 공격 가능성을 완전히 배제하지는 않습니다.

이는 자동 또는 사용자가 시작한 재시도와는 다르다는 점에 유의하십시오; 재플레이는 클라이언트의 인지 없이 공격자에 의해 시작됩니다.

HTTP에서 재플레이 위험을 완화하기 위해, 이 문서는 서버에서 이러한 위험을 제어하는 기법의 개요를 제공하고 얼리 데이터에서 요청을 보낼 때 클라이언트에 대한 요구사항을 정의합니다.

이 문서의 권고는 HTTP over QUIC에서의 0-RTT 사용([HQ])에도 적용됩니다.

1.1. 관습 및 정의

이 문서에서 단어 “MUST”, “MUST NOT”, “REQUIRED”, “SHALL”, “SHALL NOT”, “SHOULD”, “SHOULD NOT”, “RECOMMENDED”, “NOT RECOMMENDED”, “MAY”, 및 “OPTIONAL”은 BCP 14 [RFC2119] [RFC8174] 에서 설명된 바와 같이, 그리고 오직 모두 대문자로 나타날 때에만 그렇게 해석되어야 합니다.

2. HTTP의 Early Data

개념적으로, 얼리 데이터는 다른 애플리케이션 데이터와 이어붙여 단일 스트림을 형성합니다. 이는 요청이 얼리 데이터 안에 완전히 포함될 수 있거나 요청의 일부만이 얼리 데이터일 수 있음을 의미합니다. HTTP/2 [RFC7540] 또는 HTTP/QUIC [HQ] 같은 멀티플렉스 프로토콜에서는 여러 요청이 부분적으로 얼리 데이터로 전달될 수 있습니다.

이 문서가 가정하는 모델은 TLS 핸드셰이크가 완료되면 해당 TLS 연결에서 수신된 얼리 데이터가 재생된 복사본이 아님이 알려진다는 것입니다. 다만, 이것은 얼리 데이터가 다른 연결에서 재생되지 않을 것이라는 의미는 아니라는 점을 주의해야 합니다.

3. HTTP 서버에서 Early Data 지원

서버는 TLS 세션 티켓을 보낼 때 클라이언트가 향후 연결에서 얼리 데이터를 보낼 수 있도록 허용할지 여부를 결정합니다.

TLS [TLS13] 은 공격자가 얼리 데이터를 성공적으로 재생할 가능성을 줄이는 재생 감지 전략의 사용을 요구합니다. 이러한 반재생 기술은 재생 가능성을 줄이지만 완전히 제거하지는 않으며 재생 횟수에 대한 고정된 상한을 보장합니다.

서버가 얼리 데이터를 활성화할 때 재생 위험을 완화하기 위해 사용할 수 있는 여러 기법이 있습니다:

  1. 서버는 TLS 계층에서 얼리 데이터를 거부할 수 있습니다. 서버는 얼리 데이터를 선택적으로 거부할 수 없으므로, 이는 얼리 데이터로 전송된 모든 요청이 폐기됨을 의미합니다.
  2. 서버는 TLS 핸드셰이크가 완료될 때까지 얼리 데이터의 처리를 지연시키도록 선택할 수 있습니다. 처리를 연기함으로써 해당 연결이 성공적으로 완료된 경우에만 그 안의 요청이 사용되도록 보장할 수 있습니다. 이는 서버에 얼리 데이터가 재생되지 않았을 것이라는 일부 확신을 제공합니다. 서버가 얼리 데이터에서 여러 요청을 수신하면, HTTP 처리를 요청별로 지연할지 여부를 결정할 수 있습니다.
  3. 서버는 재생 위험이 너무 크다고 판단되는 경우 425 (Too Early) 상태 코드(섹션 5.2)로 응답하여 클라이언트가 개별 요청을 재시도하게 만들고 얼리 데이터를 사용하지 않도록 할 수 있습니다.

이 모든 기법은 효과가 동일하며, 서버는 자신에게 가장 적합한 방법을 사용할 수 있습니다.

특정 요청에 대해 재생 위험에 대한 허용 수준은 그 요청이 작동하는 자원에 특화되어 있으며(따라서 오리진 서버만이 알 수 있음), 얼리 데이터를 사용할 때의 주요 위험은 서버가 요청을 처리할 때 발생하는 동작들입니다. 중복 요청을 처리하면 중복된 효과와 부작용이 발생할 수 있습니다. TLS의 Appendix E.5도 중복된 요청을 처리할 때 발생하는 기타 효과를 설명합니다.

요청 메서드의 안전성([RFC7231], 섹션 4.2.1)은 이를 판단하는 한 방법입니다. 그러나 일부 자원은 안전한 메서드로도 부작용을 일으킬 수 있으므로 이 방법만으로 전적으로 신뢰할 수는 없습니다.

오리진 서버는 리소스가 요청에서 얼리 데이터를 사용하는 것이 적절한지 명시적으로 구성할 수 있도록 허용하는 것이 권장됩니다. 그런 명시적 정보가 없으면 오리진 서버는 얼리 데이터를 거부하거나 이 문서에 설명된 기법을 구현하여 TLS 핸드셰이크 완료 이전에 요청이 처리되지 않도록 해야 합니다.

요청이 일부는 얼리 데이터로, 나머지는 핸드셰이크 완료 후에 전송될 수 있습니다. 이것이 반드시 그 요청의 처리를 변경하는 것은 아니며, 중요한 것은 서버가 요청의 내용을 언제 처리하기 시작하는가입니다. 어떤 서버 인스턴스라도 핸드셰이크 완료 이전에 처리를 시작할 수 있는 경우, 모든 서버 인스턴스는 얼리 데이터의 재생 가능성과 그것이 처리에 미칠 수 있는 영향을 고려해야 합니다(참조: 섹션 6.2).

서버는 불완전한 요청을 부분적으로 처리할 수 있습니다. 값에 대해 동작을 수행하지 않고 헤더 필드를 파싱하거나 요청 라우팅을 결정하는 것은 부작용 측면에서 안전할 가능성이 높지만 다른 동작은 그렇지 않을 수 있습니다.

중계 서버(인터미디어리)는 얼리 데이터를 처리할 수 있는지 여부를 판단하기에 충분한 정보를 갖고 있지 않으므로, 섹션 5.2에서는 특정 요청이 얼리 데이터에 적합하지 않음을 오리진이 중계에 신호할 수 있는 방법을 설명합니다. 얼리 데이터를 수용하는 중계는 해당 메커니즘을 구현해야 합니다.

서버는 TLS 계층에서 얼리 데이터를 선택적으로 거부할 수 없다는 점에 유의하십시오. TLS는 서버가 얼리 데이터를 모두 허용하거나 전혀 허용하지 않는 것만을 허용합니다. 서버가 얼리 데이터를 허용하기로 결정하면, 서버는 요청을 425 (Too Early)로 거부하더라도 얼리 데이터에 있는 모든 요청을 처리해야 합니다.

서버는 early_data TLS 확장의 max_early_data_size 필드로 얼리 데이터의 양을 제한할 수 있습니다. 이는 핸드셰이크가 완료될 때까지 지연할 수 있는 요청에 대해 임의의 양의 메모리를 할당하는 것을 피하기 위해 사용될 수 있습니다.

4. HTTP 클라이언트에서 Early Data 사용

얼리 데이터를 사용하려는 클라이언트는 TLS ClientHello를 보낸 직후에 HTTP 요청을 즉시 전송함으로써 시작합니다.

본질적으로 클라이언트는 특정 요청을 얼리 데이터로 보낼지 여부를 제어할 수 있으므로 재플레이 위험을 제어할 수 있습니다. 다른 정보가 없으면 클라이언트는 얼리 데이터가 사용 가능할 때 안전한 HTTP 메서드 ([RFC7231], 섹션 4.2.1)에 해당하는 요청을 얼리 데이터로 전송할 수 있으며, 안전하지 않은 메서드(또는 안전성이 알려지지 않은 메서드)를 얼리 데이터로 전송해서는 안 됩니다.

서버가 TLS 계층에서 얼리 데이터를 거부하면, 클라이언트는 연결이 새로 열린 것처럼 다시 전송을 시작해야 합니다. 이는 얼리 데이터에 대해 낙관적으로 사용된 프로토콜([ALPN]) 과 다른 협상된 프로토콜을 사용하는 것을 포함할 수 있습니다. 얼리 데이터로 보낸 모든 요청은 클라이언트가 포기하지 않는 한 다시 전송되어야 합니다.

자동 재시도는 재플레이 공격의 가능성을 만듭니다. 공격자는 얼리 데이터를 사용하는 연결을 가로채어 그 얼리 데이터를 다른 서버 인스턴스로 복사합니다. 두 번째 서버 인스턴스는 핸드셰이크를 완료하지 않더라도 얼리 데이터를 수락하고 처리할 수 있습니다. 그런 다음 공격자는 원래 연결이 완료되도록 허용합니다. 설령 얼리 데이터가 중복으로 감지되어 거부되더라도, 첫 번째 서버 인스턴스는 연결을 완료하도록 허용할 수 있습니다. 그런 다음 클라이언트가 얼리 데이터에서 보낸 요청을 재시도하면 요청이 두 번 처리될 수 있습니다.

여러 서버 인스턴스가 얼리 데이터를 수락하거나 동일한 서버가 여러 번 얼리 데이터를 수락하는 경우에도(후자는 TLS의 요구사항 위반이지만) 재플레이가 발생할 수 있습니다.

얼리 데이터를 사용하는 클라이언트는 425 (Too Early) 상태 코드를 수신하면 요청을 재시도해야 합니다; 섹션 5.2를 참조하십시오.

중계자는 이전 홉에서 얼리 데이터가 사용되었거나 요청을 안전하게 재시도할 수 있음을 알고 있지 않는 한, 요청을 전달할 때 얼리 데이터를 사용해서는 안 됩니다(일반적으로 오프라인 구성 사용). 더 나은 정보가 없으면 중계자는 요청이 얼리 데이터로 도착했거나 Early-Data 헤더 필드가 “1”로 설정되어 도착한 경우에만 얼리 데이터를 사용할 수 있습니다(참조: 섹션 5.1).

5. HTTP의 Early Data 확장

HTTP 요청은 여러 '홉'에 걸칠 수 있으므로, 요청이 이전 홉에서 얼리 데이터로 전송되었는지 여부를 명시적으로 전달할 필요가 있습니다. 마찬가지로, 얼리 데이터가 원치 않을 때 명시적으로 재시도를 유발하는 수단이 필요합니다. 마지막으로, 클라이언트가 실제로 그런 재시도를 수행할 것인지 알 필요가 있습니다.

이 요구를 충족하기 위해 두 가지 신호 메커니즘이 정의됩니다:

  • Early-Data 헤더 필드는 요청이 클라이언트와의 TLS 핸드셰이크 완료 이전에 중계자에 의해 전달되었을 가능성이 있는 경우에 포함됩니다.
  • 425 (Too Early) 상태 코드는 서버가 가능한 재플레이 공격의 결과 때문에 요청을 처리할 수 없음을 나타내기 위해 정의됩니다.

이들은 사용자 에이전트와 오리진 서버 간의 얼리 데이터 사용에 대한 더 나은 조정, 그리고 게이트웨이(역프록시, CDN, 또는 서러게이트)가 있는 경우에도 조정을 가능하게 하도록 설계되었습니다.

게이트웨이는 주어진 요청이 얼리 데이터로 안전하게 처리될 수 있는지에 대한 구체적 정보를 갖고 있지 않은 경우가 많습니다. 많은 경우에 오리진 서버만이 재플레이 위험이 허용 가능한지 판단하는 데 필요한 정보를 가지고 있습니다. 이 확장들은 게이트웨이와 오리진 서버 간의 조정을 가능하게 합니다.

5.1. Early-Data 헤더 필드

Early-Data 요청 헤더 필드는 요청이 얼리 데이터로 전달되었고 클라이언트가 425 (Too Early) 상태 코드를 이해한다는 것을 나타냅니다.

유효한 값은 단 하나뿐입니다: “1”. 그 문법은 다음 ABNF [ABNF]에 의해 정의됩니다:

Early-Data = "1"

예를 들면:

GET /resource HTTP/1.0
Host: example.com
Early-Data: 1

클라이언트와의 TLS 핸드셰이크 완료 이전에 요청을 전달하는 중계자는 요청에 Early-Data 헤더 필드가 설정되어 있지 않다면 이를 반드시 “1”로 설정하여 전송해야 합니다(즉, 요청에 없으면 추가합니다). 중계자는 요청이 재생의 대상이 되었을 수 있고 이미 자신 또는 다른 인스턴스에 의해 전달되었을 수 있다면 Early-Data 헤더 필드를 사용해야 합니다(참조: 섹션 6.2).

중계자는 요청에 이 헤더 필드가 포함되어 있으면 이를 제거해서는 안 됩니다. Early-Data는 Connection 헤더 필드에 나타나서는 안 됩니다.

Early-Data 헤더 필드는 사용자 에이전트(즉, 요청의 원래 시작자)가 사용하도록 설계된 것은 아닙니다. 요청을 얼리 데이터로 보내는 것은 클라이언트가 이 명세를 이해하고 425 (Too Early) 상태 코드에 응답하여 요청을 재시도할 의사가 있음을 의미합니다. 얼리 데이터로 요청을 보내는 사용자 에이전트는 Early-Data 헤더 필드를 포함할 필요가 없습니다.

서버는 Early-Data 헤더 필드를 포함하는 요청을 핸드셰이크 완료를 기다림으로써 안전하게 처리할 수 없음을 알아야 합니다. Early-Data로 표시된 요청은 이전 홉에서 얼리 데이터로 전송된 것입니다. Early-Data 헤더 필드를 포함하고 안전하게 처리될 수 없는 요청은 425 (Too Early) 상태 코드로 거부되어야 합니다.

Early-Data 헤더 필드는 단일 비트의 정보를 전달하므로, 클라이언트는 최대 하나의 인스턴스만 포함해야 합니다. 서버는 다중 또는 유효하지 않은 인스턴스를 단일 인스턴스의 값 1과 동등하게 처리해야 합니다.

응답 또는 요청 트레일러에 Early-Data 헤더 필드를 포함해서는 안 됩니다.

5.2. 425 (Too Early) 상태 코드

425 (Too Early) 상태 코드는 서버가 재생될 가능성이 있는 요청을 처리할 위험을 감수하지 않겠다는 것을 나타냅니다.

얼리 데이터로 요청을 보내는 사용자 에이전트는 425 (Too Early) 응답 상태 코드를 수신하면 그 요청을 재시도할 것으로 기대됩니다. 사용자 에이전트는 자동으로 재시도하는 것이 권장되지만, 재시도는 어떠한 경우에도 얼리 데이터로 전송되어서는 안 됩니다.

모든 경우에 중계자는 425 (Too Early) 상태 코드를 전달할 수 있습니다. 중계자는 자신이 수신하고 전달한 요청에 Early-Data 헤더 필드가 포함되어 있었다면 425 상태 코드를 전달해야 합니다. 그렇지 않은 경우, 얼리 데이터로 요청을 수신한 중계자는 425 상태 코드에 응해 자동으로 해당 요청을 재시도할 수 있으나, 요청을 수신한 연결에서 TLS 핸드셰이크가 완료될 때까지 기다려야 합니다.

서버는 요청이 얼리 데이터로 수신되었거나 Early-Data 헤더 필드가 “1”로 설정되지 않는 한, 클라이언트가 요청을 재시도할 수 있다고 가정해서는 안 됩니다. 이러한 조건 중 하나가 충족되지 않으면 서버는 425 상태 코드를 발행해서는 안 됩니다.

425 (Too Early) 상태 코드는 기본적으로 캐시할 수 없습니다. 그 페이로드는 어떤 식별된 자원의 표현도 아닙니다.

6. 보안 고려사항

얼리 데이터를 사용하면 클라이언트의 요청이 재생될 위험에 노출됩니다. 재시도되거나 재생된 요청은 서버에서 다른 부작용을 초래할 수 있습니다. 이러한 부작용 외에, 재플레이와 재시도는 트래픽 분석에 사용되어 요청이나 요청이 대상으로 하는 자원에 대한 정보를 복구할 수 있습니다. 특히, 재생된 요청은 다른 응답을 유발할 수 있으며, 이는 콘텐츠가 비밀로 유지되더라도 보호된 데이터의 길이로부터 관찰될 수 있습니다.

6.1. 게이트웨이와 Early Data

게이트웨이는 오리진 서버 중 요청을 전달할 대상이 Early-Data 헤더 필드를 이해하고 425 (Too Early) 상태 코드를 올바르게 생성할 것임을 알지 못하면 얼리 데이터로 수신된 요청을 전달해서는 안 됩니다. 특정 오리진 서버의 지원이 확실하지 않은 게이트웨이는 클라이언트와의 TLS 핸드셰이크가 완료될 때까지 전달을 지연하거나 응답으로 425 (Too Early) 상태 코드를 보내야 합니다.

잠재적 오리진 서버 중 적어도 하나가 Early-Data 헤더 필드를 지원하지 않는 경우, 얼리 데이터를 활성화하여 얻을 수 있는 성능 이익은 대부분의 경우 미미하므로 게이트웨이는 얼리 데이터를 완전히 비활성화하는 것이 더 효율적일 수 있습니다.

6.2. Early Data의 일관된 처리

얼리 데이터로 도착했거나 부분적으로 도착한 요청을 일관되게 처리하는 것은 재생된 요청의 부적절한 처리를 피하는 데 중요합니다. TLS 핸드셰이크가 완료되기 전에 처리하기에 안전하지 않은 요청이라면, 모든 서버 인스턴스(게이트웨이 포함)는 합의하여 해당 요청을 거부하거나 처리를 지연해야 합니다.

얼리 데이터를 비활성화하거나 요청을 지연하거나 425 (Too Early) 상태 코드로 요청을 거부하는 것은 재플레이 공격을 완화하는 데 모두 동일하게 유효한 조치입니다. 서버 인스턴스는 이러한 조치들 중 어느 것을 구현하더라도 일관된 것으로 간주될 수 있으며, 서로 다른 인스턴스가 서로 다른 방법을 사용할 수 있습니다. 중요한 점은 서버 부하와 같은 다른 조건에 반응하여 서로 다른 완화책을 적용할 수 있다는 것입니다.

서버는 자신 및 다른 서버 인스턴스가 동일한 데이터에 대해 서로 다른 결정을 내릴 수 있는 상황이라면 핸드셰이크 완료 전에 얼리 데이터에 대해 동작을 수행해서는 안 됩니다.

6.3. 서비스 거부(DoS)

얼리 데이터를 수락하면 처리 비용이 큰 요청의 재플레이를 통해 서버가 서비스 거부에 노출될 수 있습니다. 부하가 걸린 서버는 개별 요청을 선택적으로 처리하는 대신 TLS 얼리 데이터를 전체적으로 거부하는 편이 바람직합니다. 503 (Service Unavailable) 또는 425 (Too Early) 상태 코드를 생성하면 클라이언트가 요청을 재시도하게 되어 부하가 증가할 수 있습니다.

6.4. 순서가 뒤바뀐 전달

QUIC [HQ] 같은 순서가 뒤바뀌어 전달되는 프로토콜에서는 얼리 데이터가 핸드셰이크 완료 이후에 도착할 수 있습니다. 서버는 다른 인스턴스가 동일한 요청의 재플레이를 올바르게 처리할 것이라고 신뢰할 수 있는 경우에만 핸드셰이크 완료 후에 수신된 얼리 데이터의 요청을 처리할 수 있습니다.

Early-Data
Applicable protocol:
http

standard

IETF
Specification document(s):
이 문서
Related information:
(empty)
