HTTP 캐시 그룹

요약

이 명세는 HTTP 캐시 내에 저장된 응답들 간의 관계를 설명하는 방법을 소개하며, 저장된 응답을 하나 이상의 문자열과 연결하여 그룹화할 수 있도록 합니다.

이 문서의 상태

이 문서는 인터넷 표준 트랙 문서입니다.

이 문서는 인터넷 엔지니어링 태스크 포스(IETF)의 산출물입니다. 이는 IETF 커뮤니티의 합의를 반영하고 있습니다. 공개 검토를 받았으며 인터넷 엔지니어링 지명 그룹(IESG)이 출판을 승인하였습니다. 인터넷 표준에 대한 추가 정보는 RFC 7841 2절에서 확인할 수 있습니다.

이 문서의 현재 상태, 정오표, 그리고 피드백 방법 등은 https://www.rfc-editor.org/info/rfc9875에서 확인할 수 있습니다.

1. 소개

HTTP 캐싱 [HTTP-CACHING]은 단일 리소스 단위로 동작합니다. 하나의 저장된 응답의 신선도는 다른 응답에 영향을 주지 않습니다. 이러한 세분화는 여러 자산이 서로 다른 캐싱 요구 사항을 가지는 페이지 등에서 캐싱 효율을 높일 수 있습니다.

하지만 저장된 응답들 사이의 관계를 활용하면 캐시 효율성을 높일 수 있는 경우도 있습니다.

예를 들어, 관련된 리소스 집합을 무효화해야 하는 경우가 종종 있습니다. 이는 상태를 변경하는 요청이 다른 리소스에 부수 효과를 미치기 때문일 수도 있고, 단순히 관리적 편의를 위해서일 수도 있습니다(예: "사이트의 이 부분 무효화"). 응답을 그룹으로 묶으면 URL 구조 등에 의존하지 않고 이러한 관계를 명확하게 표현할 수 있습니다.

무효화 이벤트 공유 외에도, 그룹화로 표시된 관계를 통해 캐시는 자체 동작을 최적화할 수도 있습니다(예: 캐시 제거 알고리즘 작동에 참고 등).

2절에서는 HTTP 캐시에 저장된 응답의 관계를 설명하기 위해, 해당 응답을 하나 이상의 그룹과 연관시켜 관계를 반영하는 방법을 소개합니다. 또한 캐시가 그 정보를 활용하여 그룹의 구성원에게 무효화 이벤트를 적용하는 방법도 설명합니다.

3절에서는 그러한 이벤트의 새로운 출처 하나, 즉 상태 변경 응답이 그룹 무효화를 유발할 수 있도록 하는 HTTP 응답 헤더 필드를 소개합니다.

이러한 메커니즘은 단일 캐시 내에서, 단일 오리진 서버에 연결된 저장된 응답들에 적용됩니다(2.1절 참조). 여러 캐시(예: 계층 또는 메시 구조) 간 상태 동기화나 서로 다른 오리진의 응답 연관은 다루지 않습니다.

1.1. 표기 규칙

이 문서에서 "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", "OPTIONAL" 등의 단어는 BCP 14 [RFC2119] [RFC8174]의 설명과 같이 (여기서와 같이) 전부 대문자로 등장할 때만 그 의미로 해석합니다.

이 명세는 [STRUCTURED-FIELDS]의 다음 용어를 사용합니다: List, String, Parameter.

2. Cache-Groups 응답 헤더 필드

Cache-Groups 응답 헤더 필드는 문자열 리스트( 3.1절 및 3.3.3절 및 [STRUCTURED-FIELDS] 참고)입니다. 리스트의 각 멤버는 해당 응답이 속하는 그룹을 식별하는 값입니다. 이 문자열들은 불투명하며, 서버 입장에서 의미를 가질 수 있으나 캐시는 구조나 내용에 대한 이해 없이 단지 그룹을 고유하게 식별하는 용도로만 사용합니다.

HTTP/1.1 200 OK
Content-Type: application/javascript
Cache-Control: max-age=3600
Cache-Groups: "scripts"

멤버의 순서는 중요하지 않습니다. 인식되지 않은 파라미터들은 무시해야 합니다.

구현체는 필드 값에 최소 32개 그룹, 각 멤버에 최대 32자 이상을 MUST 지원해야 합니다. 단, HTTP 필드 길이에 대한 일반적인 제한 때문에 실무에서 이 필드 값의 크기에 제약이 있을 수 있습니다.

2.1. 그룹화된 응답 식별

동일 캐시에 저장된 두 응답이 아래 모든 조건을 만족할 때 동일 그룹 소속으로 간주합니다:

  1. 둘 다 Cache-Groups 응답 헤더 필드를 가지고, 해당 리스트 안에 동일한 문자열(위치 무관, 대소문자 구분, 문자별 비교)을 포함한다.

  2. 둘 다 동일한 URI 오리진을 공유한다( 4.3.1절 및 [HTTP] 참고).

2.2. 캐시 동작

2.2.1. 무효화

캐시가 저장된 응답을 무효화할 때, 그 응답과 그룹을 공유하는( 2.1절 참고) 저장된 다른 응답을 무효화할 수 있습니다(MAY). 단, 그룹 무효화로 인한 추가 무효화는 연쇄되지 않으며, 즉 이 메커니즘은 전이적(cascade)으로 동작하지 않습니다.

캐시 확장 기능은 위 요구사항을 명시적으로 강화할 수 있습니다. 예를 들어, 타겟 캐시 제어 헤더 필드 [TARGETED]는 해당 헤더를 처리하는 캐시에 이러한 응답 무효화를 요구할 수 있습니다.

3. Cache-Group-Invalidation 응답 헤더 필드

Cache-Group-Invalidation 응답 헤더 필드는 문자열 리스트( 3.1절, 3.3.3절 및 [STRUCTURED-FIELDS] 참고)입니다. 리스트의 각 멤버는 해당 응답이 무효화하는 그룹을 식별합니다( 2.2.1절 참고).

예를 들어, 부수 효과로 두 개의 캐시 그룹에 영향을 주는 POST 요청 이후, 관련 응답은 다음과 같이 한 또는 두 그룹에 연관된 저장된 응답을 무효화해야 함을 나타낼 수 있습니다:

HTTP/1.1 200 OK
Content-Type: text/html
Cache-Group-Invalidation: "eurovision-results", "australia"

Cache-Group-Invalidation 헤더 필드는 안전한 메서드(e.g., GET, 9.2.1절, [HTTP] 참고) 요청 응답에서는 반드시 무시되어야 합니다.

캐시는 비안전 요청에 대한 응답에서 Cache-Group-Invalidation 헤더를 받으면, 리스트 내의 어떤 그룹과 공유하는 그룹이 있는 저장된 응답들을 무효화할 수 있습니다(MAY)( 2.1절 참고).

캐시 확장 기능은 위 요구사항을 명시적으로 강화할 수 있습니다. 예를 들어, 타겟 캐시 제어 헤더 필드 [TARGETED]는 캐시가 Cache-Group-Invalidation 신호를 반드시(필수) 준수하도록 명시할 수 있습니다.

멤버의 순서는 중요하지 않습니다. 인식되지 않은 파라미터들은 무시해야 합니다.

구현체는 필드 값에 최소 32개 그룹, 각 멤버에 최대 32자 이상을 MUST 지원해야 합니다. 단, HTTP 필드 길이에 대한 일반적인 제한 때문에 실무에서 이 필드 값의 크기에 제약이 있을 수 있습니다.

5. 보안 고려사항

이 메커니즘은 동일 오리진을 공유하는 리소스가 서로 무효화될 수 있도록 허용합니다. 이렇게 되면, 다수의 당사자가 관여하는 오리진(“공유 호스팅”이라 불림)에서는 한 당사자가 자신의 리소스를 타인의 리소스와 그룹으로 묶거나, 그들에게 부수 효과가 있는 신호를 보낼 수 있습니다.

이러한 위험을 줄이고자 하는 공유 호스트는 이 명세에서 정의된 헤더 필드 접근을 제어할 수 있습니다.
