RFC 9931

HTTP/1.1의 낙관적 프로토콜 전환에 관한 보안 고려 사항

이 페이지는 IETF RFC 9931(B. Schwartz, 2026년 3월)의 비공식 한국어 발췌 번역이며 IETF의 승인을 받지 않았고 전체 번역이 아닙니다. 4.1절의 세 번째 문단과 그림 1의 구체적인 공격 예시는 생략하고, 명시적으로 표시한 편집자의 비실행적 요약으로 대체했습니다. 그 밖의 프로토콜 요구 사항과 방어 규정은 원문에 따라 번역했습니다. 원문의 저작권, 라이선스, 면책 조항 및 저자 표시는 유지했습니다. 공식 영어 출판본을 기준으로 하며 생략한 위치는 공식 4.1절을 참조하세요.

초록

HTTP/1.1에서 클라이언트는 기존 연결에서 새 프로토콜로 전환하도록 요청할 수 있습니다. 이 문서는 해당 요청이 확인되기 전에 클라이언트가 보내는 데이터에 관한 보안 고려 사항을 설명하고, 관련 보안 문제를 방지하기 위해 RFC 9112와 RFC 9298에 새로운 요구 사항을 추가합니다.¶

1. 개요

이 문서는 같은 연결에서 HTTP/1.1을 다른 프로토콜로 전환할 때 발생하는 보안 고려 사항을 설명하며 다음을 제공합니다:¶

  • 관련 표준 검토;¶

  • 전환이 확인되기 전에 클라이언트가 데이터를 보낼 경우 발생할 수 있는 보안 위험 논의;¶

  • 기존 업그레이드 토큰의 보안 평가; 그리고¶

  • 구현 및 향후 표준 문서에 대한 지침.¶

[HTTP/1.1] 및 [CONNECT-UDP]에 대한 갱신 사항과 새로운 규범적 요구 사항은 각각 8 절과 6.3절에 제시됩니다.¶

이 문서의 키워드 "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", "OPTIONAL" 는 여기에 표시된 것처럼 모두 대문자로 나타나는 경우에만 BCP 14 [RFC2119] [RFC8174] 에 설명된 의미로 해석합니다.¶

3. 배경

HTTP/1.1 [HTTP/1.1] 및 이후 버전에서는 하나의 연결로 여러 요청을 처리할 수 있습니다. HTTP/2 [HTTP/2] 와 HTTP/3 [HTTP/3]에서는 각 요청을 스트림 ID로 명시적으로 구분하므로 다중화할 수 있습니다. 그러나 HTTP/1.1의 요청은 엄격히 순차적이며, 이전 요청의 종료로 다음 요청을 암묵적으로 구분합니다.¶

HTTP/1.1은 클라이언트가 연결의 나머지 부분에 사용할 프로토콜을 변경할 수 있는 유일한 HTTP 버전이기도 합니다. 이러한 전환을 요청하는 방식은 두 가지입니다. 하나는 Upgrade 헤더 필드입니다([HTTP], 7.8절). 요청에 이 필드가 포함되면 클라이언트가 해당 연결에서 HTTP/1.1 이외의 프로토콜을 사용하려 함을 나타냅니다. 서버가 변경을 수락하면 101(Switching Protocols, 프로토콜 전환) 상태 코드를 반환합니다([HTTP], 15.2.2절).¶

다른 방식은 HTTP CONNECT 메서드입니다(9.3.6절 , [HTTP]). 이는 지정된 호스트와 포트에 TCP 연결을 설정하려는 클라이언트의 의도를 나타냅니다. 수락한 경우 서버는 요청이 수락되고 TCP 연결이 설정되었음을 나타내는 2xx(Successful, 성공) 응답을 보냅니다. 이후 이 TCP 연결은 HTTP/1.1 연결이 아닌 TCP 터널로 작동합니다.¶

두 방식 모두 서버가 요청을 거부할 수 있도록 합니다. 예를 들어 7.8절 ([HTTP] )은 다음과 같이 규정합니다:¶

서버가 해당 연결에서 현재 프로토콜을 계속 사용하려는 경우, 수신한 Upgrade 헤더 필드를 무시할 수 있습니다( MAY ).¶

또한 9.3.6절 ([HTTP] )은 다음과 같이 규정합니다:¶

서버는 대상 포트 번호가 비어 있거나 유효하지 않은 CONNECT 요청을 거부해야 합니다( MUST ). 일반적으로 400(Bad Request, 잘못된 요청) 상태 코드로 응답합니다.¶

업그레이드 거부는 흔히 발생하며 다음과 같은 여러 이유가 있습니다:¶

  • 서버가 클라이언트가 제시한 업그레이드 토큰(즉, 제안한 새 프로토콜)을 하나도 지원하지 않아 HTTP/1.1을 계속 사용합니다.¶

  • 서버가 이 리소스에 대한 해당 요청에서는 제안된 프로토콜로 업그레이드해도 HTTP/1.1보다 개선되지 않는다고 판단하여 HTTP/1.1로 응답합니다.¶

  • 서버가 프로토콜 업그레이드 전에 클라이언트 인증을 요구하므로 401(Authentication Required, 인증 필요) 상태 코드를 반환하고 Authorization 응답 헤더 필드에 인증 질의를 제공합니다([HTTP], 11.6.2절).¶

  • 리소스가 이동하여 서버가 3xx(Redirection, 리디렉션) 상태 코드를 반환합니다([HTTP], 3.4절).¶

마찬가지로 서버는 다음과 같은 경우 HTTP CONNECT 요청을 자주 거부합니다:¶

  • 서버가 HTTP CONNECT를 지원하지 않습니다.¶

  • 서버 정책이 지정된 목적지를 허용하지 않습니다.¶

  • 목적지를 확인할 수 없거나, 도달할 수 없거나, 목적지가 연결을 수락하지 않습니다.¶

  • 프록시가 진행하기 전에 클라이언트 인증을 요구합니다.¶

요청을 거부한 후 서버는 해당 연결에서 수신한 바이트를 계속 HTTP/1.1에 따라 해석합니다.¶

7.8절 ([HTTP] )은 다음과 같이 규정하기도 합니다:¶

클라이언트는 요청 메시지를 완전히 전송하기 전에는 연결에서 업그레이드된 프로토콜을 사용하기 시작할 수 없습니다(즉, 메시지 중간에 전송하는 프로토콜을 바꿀 수 없습니다).¶

즉, 요청 메시지 전송 완료는 클라이언트가 새 프로토콜을 사용하기 시작하기 위한 필요 조건입니다. 그러나 서버가 요청을 거부할 수 있으므로 충분 조건은 아니라는 점을 분명히 해야 합니다.¶

경우에 따라 클라이언트는 서버가 요청한 프로토콜 전환을 수락할 가능성이 높다고 예상할 수 있습니다. 예를 들어 특정 업그레이드 토큰을 사용한 요청이 최근 성공했다면 같은 토큰을 사용하는 후속 요청도 성공할 것으로 기대할 수 있습니다. 예상이 맞으면 서버 응답을 기다리지 않고 새 프로토콜의 첫 바이트를 즉시 “낙관적으로” 보내어 지연을 줄일 수 있는 경우가 많습니다. 이 문서는 이러한 “낙관적” 동작이 보안에 미치는 영향을 살펴봅니다.¶

4. 발생 가능한 보안 문제

HTTP/1.1 연결에 서로 다른 두 당사자(클라이언트와 서버)만 관여한다면 프로토콜 전환은 새로운 보안 문제를 일으키지 않습니다. 각 당사자는 상대방이 언제든 연결로 임의의 데이터를 보낼 수 있다는 점에 이미 대비해야 하기 때문입니다. 그러나 요청이나 응답에 제3자 데이터가 포함되면 HTTP 연결에는 두 당사자보다 많은 주체가 관여하는 경우가 흔합니다. 예를 들어 브라우저(첫 번째 당사자)가 한 출처(두 번째 당사자)에 보내는 HTTP 요청의 경로, 헤더 또는 내용을 다른 출처의 웹사이트(세 번째 당사자)가 제어할 수 있습니다. WebSocket [WEBSOCKET]같은 전환 후 프로토콜도 제3자가 선택한 데이터를 전송하는 데 자주 사용됩니다.¶

제3자 데이터 출처를 신뢰할 수 없다면 제공되는 데이터는 “공격자가 제어하는” 데이터일 수 있습니다. 공격자가 제어하는 데이터와 낙관적 프로토콜 전환의 조합은 두 가지 중대한 보안 문제를 일으킵니다.¶

4.1. 요청 스머글링

요청 스머글링 공격([HTTP/1.1], 11.2절)에서는 공격자가 제어하는 데이터가 서버에서 추가 HTTP 요청으로 해석되도록 선택됩니다. 이를 통해 공격자는 클라이언트가 어떤 요청을 보낼지에 관한 자체 규칙을 우회하면서 클라이언트를 대신하여 요청할 수 있습니다. 클라이언트와 서버가 서로 주고받는 데이터를 다르게 해석하면 요청 스머글링이 발생할 수 있습니다.¶

서버가 프로토콜 전환 요청을 수락하면 이후 바이트를 새 프로토콜에 따라 해석하고, 거부하면 HTTP/1.1로 해석합니다. 그러나 클라이언트는 서버 응답의 상태 코드를 받기 전까지 어떤 해석이 적용될지 알 수 없습니다. 새 프로토콜을 낙관적으로 사용하면 서버가 새 프로토콜에 포함된 공격자 제어 데이터를 클라이언트가 보낸 추가 HTTP 요청으로 해석할 위험이 생깁니다.¶

【편집자 요약이며 RFC 원문의 번역이 아닙니다】이 부분의 구체적인 공격 예시는 생략합니다. 신뢰할 수 없는 데이터가 연결 수준 인증의 신뢰 경계를 넘을 수 있다는 위험을 설명하는 부분입니다. 원문의 인증([TLS], 4.4.2절) 및 요청 의미론([HTTP], 9.3.3절) 참조는 명세의 배경을 이해하도록 유지하지만 메시지, 페이로드 또는 실행 순서는 제공하지 않습니다.¶

4.2. 파서 취약점 악용

관련된 또 다른 공격 유형은 프로토콜 해석의 불일치를 이용하여 서버의 요청 파싱 로직에 있는 취약점을 악용합니다. 이는 서버가 HTTP 클라이언트는 신뢰하지만 전환 후 데이터 출처는 신뢰하지 않는 경우에 해당합니다. HTTP 요청 데이터의 일부 또는 전부를 공격자가 제어하지 않는다는 가정하에 서버 소프트웨어가 개발되었다면, 낙관적 전송이 이 가정을 깨뜨려 서버의 HTTP 요청 파서 취약점을 노출할 수 있습니다.¶

5. 운영상의 문제

서버가 전환 요청을 거부하더라도 연결은 HTTP/1.1에 계속 사용할 수 있습니다. 전환 거부에 대응하여 연결을 닫아야 한다는 일반적 요구 사항은 없으며, 해당 서버로 추가 HTTP 요청을 보낼 가능성이 높다면 연결 유지가 성능상 유리합니다. 따라서 전환이 거부되었다는 이유로 연결을 닫는 것은 일반적으로 적절하지 않습니다.¶

6. 기존 업그레이드 토큰을 사용하는 HTTP Upgrade에 미치는 영향

이 절에서는 작성 시점에 사용 중인 것으로 여겨지는 일부 등록된 업그레이드 토큰 [IANA-UPGR] 에 이 문서의 고려 사항이 미치는 영향을 설명합니다.¶

6.1. "TLS"

“TLS” 계열 업그레이드 토큰은 [RFC2817]에 정의되어 있으며 서버가 업그레이드를 거부할 가능성을 올바르게 강조합니다. 클라이언트가 이를 무시하고 TLS 데이터를 낙관적으로 보내더라도 그 결과는 유효한 HTTP/1.1이 될 수 없습니다. TLS 연결의 첫 옥텟은 22(ContentType.handshake)여야 하지만 HTTP/1.1 메서드에서는 이 문자를 허용하지 않기 때문입니다( [TLS]의 5.1절 및 [HTTP/1.1]의 3절참조). 준수하는 HTTP/1.1 서버는 이를 파싱 오류로 처리하고 추가 요청을 처리하지 않은 채 연결을 닫습니다.¶

6.2. "WebSocket"/"websocket"

4.1절 ([WEBSOCKET] )은 다음과 같이 규정합니다:¶

클라이언트는 시작 핸드셰이크를 보낸 후 추가 데이터를 보내기 전에 서버의 응답을 기다려야 합니다( MUST ).¶

따라서 WebSocket 프로토콜은 HTTP Upgrade의 낙관적 사용을 이미 금지합니다. 또한 클라이언트에서 서버로 보내는 프레임에 높은 엔트로피의 마스킹을 적용하도록 요구합니다(5.1절 , [WEBSOCKET]).¶

6.3. "connect-udp"

5절 ([CONNECT-UDP] )은 다음과 같이 규정합니다:¶

클라이언트는 UDP 프록시 요청에 대한 응답을 받기 전에 HTTP 데이터그램으로 UDP 패킷을 낙관적으로 보내기 시작할 수 있습니다( MAY ).¶

그러나 HTTP/1.1에서 이 “프록시 요청”은 HTTP Upgrade 요청입니다. 공격자가 제어하는 UDP 목적지 주소가 유효하지 않은 경우 등 특정 상황에서는 업그레이드가 거부될 가능성이 높습니다. 또한 “connect-udp” 프로토콜 스트림에는 클라이언트 기기의 다른 애플리케이션에서 온 UDP 패킷과 같은 신뢰할 수 없는 데이터가 포함될 수 있습니다. 따라서 요청 스머글링 공격이 가능해집니다. 이를 방지하기 위해 이 문서는 위 문구를 다음과 같이 대체하여 HTTP/1.1에서는 어떠한 낙관적 전송도 허용하지 않습니다:¶

클라이언트는 사용 중인 HTTP 버전이 HTTP/2 이상인 경우에만 UDP 프록시 요청의 응답을 받기 전에 HTTP 데이터그램으로 UDP 패킷을 낙관적으로 보내기 시작할 수 있습니다( MAY ). 요청 스머글링 위험 때문에 HTTP/1.x에서는 UDP 패킷을 낙관적으로 보내서는 안 됩니다( MUST NOT ).¶

6.4. "connect-ip"

“connect-ip” 업그레이드 토큰은 [CONNECT-IP]에 정의되어 있습니다. 11절 ([CONNECT-IP] )은 HTTP/1.1에서 클라이언트가 패킷을 낙관적으로 보내는 것을 금지하여 이 문제를 방지합니다.¶

7. 향후 업그레이드 토큰에 대한 지침

이 문서에서 논의하는 보안 문제를 줄이거나 없애는 좋은 설계 사례가 이미 여러 가지 있으며 향후 명세에도 적용할 수 있습니다:¶

  • HTTP Upgrade의 낙관적 사용을 금지합니다(4.1절 , [WEBSOCKET] 및 11절 , [CONNECT-IP]).¶

  • HTTP/1.1 처리를 의도적으로 종료하는 고정 프리앰블을 삽입합니다(3.4절 , [HTTP/2]).¶

  • 클라이언트에서 서버로 보내는 데이터에 높은 엔트로피의 마스킹을 적용합니다(5.1절 , [WEBSOCKET]).¶

향후 업그레이드 토큰 명세는 여기서 논의한 보안 문제를 고려하고 구현에서 이를 방지하는 방법을 명확히 안내해야 합니다.¶

7.1. 요청 메서드 선택

“TLS” 같은 일부 업그레이드 토큰은 일반적인 모든 HTTP 메서드와 함께 사용할 수 있도록 정의되어 있습니다. 업그레이드된 프로토콜은 HTTP 의미론을 계속 제공하며 해당 HTTP 요청에 대한 응답을 전달합니다.¶

6절 에서 언급한 다른 업그레이드 토큰은 HTTP 의미론을 유지하지 않으므로 메서드가 중요하지 않습니다. 이 토큰들은 모두 내용이 없는 GET 요청에 대해서만 규정되어 있습니다.¶

향후 업그레이드 토큰 명세에서는 HTTP 메서드가 그 밖의 측면에서 중요하지 않고 요청에 메시지 내용을 실을 필요도 없다면, 내용이 없는 GET 요청으로 사용을 제한해야 합니다. 이는 다른 업그레이드 토큰과의 일관성을 높이고 서버 구현을 단순화합니다.¶

8. HTTP CONNECT의 요구 사항

이 문서는 이 절의 나머지 내용을 포함하도록 [HTTP/1.1] 을 갱신합니다. 이 절의 요구 사항은 HTTP/1.1에만 적용됩니다.¶

신뢰할 수 없는 TCP 클라이언트를 대신하여 CONNECT 요청을 보내는 프록시 클라이언트는 다음 중 하나 또는 둘 다를 수행해야 합니다( MUST ):¶

  1. 2xx(Successful, 성공) 응답을 기다린 후에만 TCP 페이로드 데이터를 전달합니다.¶

  2. “Connection: close” 요청 헤더를 보냅니다.¶

이 두 가지 동작 중 적어도 하나를 구현하지 않는 프록시 클라이언트는 간단한 요청 스머글링 공격에 취약합니다([HTTP/1.1], 11.2절).¶

작성 시점에 일부 프록시 클라이언트는 위와 같은 취약점이 있는 것으로 여겨집니다. 완화 조치로서 프록시 서버는 CONNECT 요청을 거부할 때 해당 연결에서 추가 요청을 처리하지 않고 기반 연결을 닫아야 합니다( MUST ). 요청에 “close” 연결 옵션이 포함되어 있는지와 관계없이 이 요구 사항이 적용됩니다.¶

이 완화 조치는 올바르게 구현된 클라이언트에서도 연결 설정을 느리게 만드는 경우가 많으며, 특히 407(Proxy Authentication Required, 프록시 인증 필요) 응답을 반환할 때 그렇습니다. 이 공격에 취약하지 않은 HTTP/2 또는 HTTP/3을 사용하면 이러한 성능 저하를 피할 수 있습니다.¶

성능 최적화를 위해, 클라이언트가 신뢰할 수 없는 TCP 페이로드를 전달하기 전에 2xx(Successful, 성공) 응답을 기다리는 것으로 알려져 있다면(즉, 위 항목 1을 준수한다면), 프록시 서버는 이 완화 조치를 비활성화할 수 있습니다( MAY ). 요청의 User-Agent 헤더 필드와 사용자 에이전트 공급업체의 준수 관련 문서를 사용하여 준수하는 클라이언트를 식별할 수 있습니다.¶
