    HTTP 헤더 필드 매개변수의
                               문자 인코딩 및 언어 지정

개요

   기본적으로 하이퍼텍스트 전송 프로토콜(HTTP) 메시지의
   헤더 필드 값에는 US-ASCII 부호화 문자 집합에 속하지 않는 문자를
   쉽게 담을 수 없다. RFC 2231은
   다목적 인터넷 메일 확장(MIME) 헤더 필드 값 안의
   매개변수에 사용할 인코딩 방식을 정의한다. 이 문서는
   HTTP 헤더 필드에 적합한 인코딩을 규정하며, 이는
   RFC 2231에서 정의한 인코딩의 단순화된 프로파일과 호환된다.

   이 문서는 RFC 5987을 폐기한다.

   자세한 정보는 RFC 7841의 2절에 있다.

   이 문서의 현재 상태, 정오표 및

   https://www.rfc-editor.org/info/rfc8187.

1.  서론

   US-ASCII 부호화 문자 집합([RFC0020]) 밖의 문자를
   HTTP 헤더 필드([RFC7230])에서 사용하는 것은 간단하지 않다:

   o  HTTP 명세는 필드 값에 비 US-ASCII 문자를 사용하는 것을 권장하지 않으며,
      이를 확장 배커스-나우르 형식(ABNF)의 "obs-text"
      생성 규칙에 포함한다([RFC7230], 3.2절).

   o  또한 필드 값의 기본 문자 인코딩 방식에 대해서는 규정하지 않는다.
      따라서 비 US-ASCII 문자를 사용하려면
      개별 필드의 정의에서 이를 규정하거나
      다른 종류의 대역 외 정보가 필요하다.

   o  마지막으로, 일부 API는 HTTP 메시지에서 얻은
      옥텟 시퀀스를 문자 시퀀스로 매핑하기 위해
      기본 문자 인코딩 방식을 가정한다. 예를 들어 XMLHttpRequest
      API([XMLHttpRequest])는 인터페이스 정의 언어의
      "ByteString" 타입을 사용하므로 사실상 ISO-8859-1
      문자 인코딩 방식([ISO-8859-1])을 사용하게 된다.

   한편, RFC 2231은 MIME 헤더 필드 안의
   매개변수에 대한 인코딩 방식을 정의한다([RFC2231]). MIME 메시지는
   HTTP 메시지와 달리 비바이너리 전송 수단을 통해 보내야 한다.
   이 문서는 HTTP 헤더 필드에 적합한 인코딩을 규정한다.
   이 인코딩은 다음 명세에 정의된 인코딩의 단순화된 프로파일과 호환된다:
   RFC 2231. 이 방식은 일반적인 "매개변수"
   ("name=value") 구문을 사용하는 모든 HTTP 헤더 필드에 적용할 수 있다.

   이 문서는 [RFC5987]을 폐기하고 그 상태를 "역사적"으로 변경한다.
   변경 사항은 부록 A에 요약되어 있다.

      참고: 이 문서의 나머지 부분에서 RFC 2231은
      채택한 기능을 선택한 이유를 설명하기 위해서만 참조한다.
      따라서 이 참조는 전적으로 정보 제공 목적이다.

      참고: 이 인코딩은 HTTP를 통해 전송되는 메시지 페이로드에는 적용되지 않는다.
      예를 들어 미디어 타입 "multipart/form-data"를 사용하는 경우의 페이로드
      ([RFC7578])가 이에 해당한다.

2.  표기 규칙

   이 문서의 키워드 "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT",
   "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY",
   "OPTIONAL"은 다음 명세에 설명된 의미로 해석한다:
   [RFC2119].

   이 명세는 [RFC5234]에 정의된 ABNF 표기법을 사용한다.
   참조를 통해 포함되는 핵심 규칙은
   [RFC5234]의 부록 B.1에 정의된 ALPHA(영문자), DIGIT(십진수 0-9), HEXDIG
   （십육진수 0-9/A-F/a-f）및 LWSP(선형 공백)이다.

   이 명세는 [RFC6365]에 정의된 용어, 즉
   "문자 인코딩 방식"(이하 "문자 인코딩"으로 줄임),
   "charset" 및 "부호화 문자 집합"을 사용한다.

   이는 RFC 2231과 다르다는 점에 주의한다. 해당 RFC는 "문자 인코딩 방식"을
   나타내는 데 "문자 집합"이라는 용어를 사용한다.

3.   RFC 2231 와의 비교 및 인코딩 정의

   RFC 2231은 MIME에 대한 여러 확장을 정의한다. 아래 절에서는
   이러한 확장을 HTTP 헤더 필드에 적용할 수 있는지와 적용 방법을 논의한다.

   요약하면 다음과 같다:

   o  매개변수 이어 붙이기는 필요하지 않다(3.1절).

   o  문자 인코딩과 언어 정보는 유용하므로
      간단한 부분 집합을 규정한다(3.2절). 그리고

   o  인코딩된 단어의 언어 지정은 필요하지 않다
      （3.3절）.

3.1.  매개변수 이어 붙이기

   [RFC2231]의 3절은 MIME 헤더에 적용되는
   길이 제한을 처리하는 방식을 정의한다. 이러한 제한은
   HTTP에는 적용되지 않는다([RFC7231], 부록 A.6).

   따라서 매개변수 이어 붙이기는 이 명세에서 정의하는
   인코딩의 일부가 아니다.

3.2.  매개변수 값의 문자 인코딩 및 언어 정보

   [RFC2231]의 4절은 매개변수 값에 언어 정보를
   포함하는 방법과 비 ASCII 문자를 인코딩하는 방법을 규정하여,
   MIME 및 HTTP 헤더 필드의
   매개변수에 적용되는 제한을 처리한다.

   그러나 RFC 2231은 반드시 구현해야 하는 문자 인코딩을 규정하지 않아,
   송신자가 어떤 인코딩을 사용할지 결정하기 어렵다.
   따라서 이 명세를 구현하는 수신자는
   "UTF-8" 문자 인코딩 [RFC3629]을 반드시 지원해야 한다(MUST).

   또한 RFC 2231은 문자 인코딩 정보를 생략할 수 있도록 한다.
   이 명세에서 정의하는 인코딩은
   이를 허용하지 않는다.

3.2.1.  정의

   확장 매개변수 값의 존재는 보통
   별표 문자로 끝나는 매개변수 이름으로 표시한다. 그러나
   이는 단지 관례일 뿐이며, 확장 매개변수 값은
   이 확장을 사용하는 헤더 필드의 정의에서
   명시적으로 규정해야 한다(4절 참조).

   확장 매개변수 값의 ABNF는 다음과 같다:

RFC 8187            Charset/Language Encoding in HTTP     September 2017


     ext-value     = charset  "'" [ language ] "'" value-chars
                   ; like RFC 2231's <extended-initial-value>
                   ; (see [RFC2231], Section 7)

     charset       = "UTF-8" / mime-charset

     mime-charset  = 1*mime-charsetc
     mime-charsetc = ALPHA / DIGIT
                   / "!" / "#" / "$" / "%" / "&"
                   / "+" / "-" / "^" / "_" / "`"
                   / "{" / "}" / "~"
                   ; as <mime-charset> in Section 2.3 of [RFC2978]
                   ; except that the single quote is not included
                   ; SHOULD be registered in the IANA charset registry

     language      = <Language-Tag, see [RFC5646], Section 2.1>

     value-chars   = *( pct-encoded / attr-char )

     pct-encoded   = "%" HEXDIG HEXDIG
                   ; see [RFC3986], Section 2.1

     attr-char     = ALPHA / DIGIT
                   / "!" / "#" / "$" / "&" / "+" / "-" / "."
                   / "^" / "_" / "`" / "|" / "~"
                   ; token except ( "*" / "'" / "%" )

   확장 매개변수의 값 부분(ext-value)은
   다음 세 부분으로 이루어진 토큰이다:

   1.  필수(REQUIRED) 문자 인코딩 이름(charset),

   2.  선택적(OPTIONAL) 언어 정보(language), 그리고

   3.  실제 값을 나타내는 문자 시퀀스(value-chars).
       각 부분은 작은따옴표 문자로 구분한다.

   문자 인코딩 이름과 언어 태그는 모두
   US-ASCII 부호화 문자 집합으로 제한되며 대소문자를 구분하지 않고 일치 여부를 판단한다
   （[RFC2978]의 2.3절 및 [RFC5646]의
   2.1.1절 참조).

   값 부분에서 attr-char에 포함되지 않는 문자는
   지정된 문자 인코딩을 사용하여 옥텟 시퀀스로 인코딩한다.
   그런 다음 해당 옥텟 시퀀스를 다음 규정에 따라 퍼센트 인코딩한다:
   [RFC3986]의 2.1절.

   생성자는 "UTF-8"([RFC3629]) 문자 인코딩을 반드시 사용해야 한다(MUST).
   확장 문자 인코딩(mime-charset)은
   향후 사용을 위해 예약되어 있다.

      참고: 수신자는 인코딩 오류를 견고하게 처리할 수 있도록 준비하는 것이 좋다.
      예를 들어 형식이 잘못되거나 불완전한 퍼센트 이스케이프 시퀀스,
      또는 디코딩할 수 없는 옥텟 시퀀스가 이에 해당한다.
      이 명세는 특정 동작을 강제하지 않는다.
      예를 들어 다음 전략은 모두 허용된다:

      *  매개변수를 무시한다.

      *  디코딩할 수 없는 옥텟 시퀀스를 제거한다. 또는

      *  디코딩할 수 없는 옥텟 시퀀스를 대체 문자로 바꾼다.
         예를 들어 유니코드 문자 U+FFFD
         （REPLACEMENT CHARACTER）를 사용할 수 있다.

3.2.2.  역사적 참고 사항

   RFC 7230의 token 생성 규칙([RFC7230], 3.2.6절)은
   RFC 2231에서 사용하는 생성 규칙([RFC2045]의
   5.1절에서 가져옴)과 달리 중괄호("{" 및 "}")를 제외한다.
   따라서 attr-char 생성 규칙에서도
   이 두 문자를 제외한다.

   여기서 정의하는 <mime-charset> ABNF는
   [RFC2978]의 2.3절과 달리 작은따옴표
   문자를 허용하지 않는다(RFC 정오표 ID 1912 [Err1912]도 참조). 실제로
   이 문서를 작성하는 시점에는 해당 문자를 사용한
   문자 인코딩 이름이 등록되어 있지 않다.

   RFC 2231과의 하위 호환성을 위해 이 명세에서 정의하는 인코딩은
   일반적인 매개변수 구문과 달리
   quoted-string 표기법을 허용하지 않는다. 범용
   파서 구성 요소를 사용하는 구현은 quoted-string
   표기법의 사용을 감지하지 못하여, 이 형식이 유효하지 않더라도
   받아들일 수 있다.

   [RFC5987]은 ISO-8859-1([ISO-8859-1]) 지원도 요구했다.
   레거시 코드와의 호환성을 위해 수신자가
   이 인코딩도 지원하도록 권장한다.

3.2.3.  예

   "token"을 사용하는 비확장 표기법:

     foo: bar; title=Economy

   "quoted-string"을 사용하는 비확장 표기법:

     foo: bar; title="US-$ rates"

   유니코드 문자 U+00A3("£", POUND SIGN)를 사용하는
   확장 표기법:

     foo: bar; title*=utf-8'en'%C2%A3%20rates

   참고: 유니코드 파운드 기호 문자 U+00A3은
   UTF-8 문자 인코딩으로 옥텟 시퀀스 C2 A3으로 인코딩된 후
   퍼센트 인코딩되었다. 또한 공백 문자는 attr-char에 포함되지 않으므로
   %20으로 인코딩되었다는 점에 주의한다.

   유니코드 문자 U+00A3("£", POUND SIGN)
   및 U+20AC("€", EURO SIGN)를 사용하는 확장 표기법:

     foo: bar; title*=UTF-8''%c2%a3%20and%20%e2%82%ac%20rates

   참고: 유니코드 파운드 기호 문자 U+00A3은
   UTF-8 문자 인코딩으로 옥텟 시퀀스 C2 A3으로 인코딩된 후
   퍼센트 인코딩되었다. 마찬가지로 유니코드 유로 기호 문자 U+20AC은
   옥텟 시퀀스 E2 82 AC으로 인코딩된 후 퍼센트
   인코딩되었다. 또한 HEXDIG는 소문자와 대문자를 모두 허용하므로
   수신자는 두 형식을 모두 이해해야 한다. 언어
   정보는 선택 사항이지만 문자 인코딩은 그렇지 않다.

3.3.  인코딩된 단어의 언어 지정

   [RFC2231]의 5절은 [RFC2047]에서 정의한 인코딩을 확장하여
   인코딩된 단어의 언어 지정도 지원한다. 현재 폐기된 HTTP/1.1 명세인 RFC 2616은
   RFC 2047을 참조했다
   （[RFC2616], 2.2절）. 그러나 어떤 헤더 필드에
   적용되는지는 명확하지 않았다. 따라서 HTTP/1.1 명세의 현재 개정판은
   다음 명세에 정의된 인코딩 형식의 사용을 더는 권장하지 않는다: RFC
   2047（[RFC7230]의 3.2.4절 참조).

   따라서 이 명세는 이 기능을 포함하지 않는다.

4.  HTTP 헤더 필드 정의에서의 사용 지침

   확장을 사용하는 HTTP 헤더 필드 명세는
   3.2절에 정의된 확장을 사용한다는 점을 명확히 밝히는 것이 바람직하다.
   이를 위한 간단한 방법은 이 명세를 규범적으로 참조하고
   특정 헤더 필드 매개변수의 ABNF에
   ext-value 생성 규칙을 포함하는 것이다.





Reschke                      Standards Track                    [Page 7]

RFC 8187            Charset/Language Encoding in HTTP     September 2017


   예를 들면 다음과 같다:

     foo         = token ";" LWSP title-param
     title-param = "title" LWSP "=" LWSP value
                 / "title*" LWSP "=" LWSP ext-value
     ext-value   = <see RFC 8187, Section 3.2>

      참고: 다음 절에 정의된 매개변수 값 이어 붙이기 기능,
      즉 [RFC2231]의 3절에 있는 기능 때문에 동일한 이름의 확장 매개변수를
      여러 개 둘 수 없다. 이어 붙이기 처리가
      모호해지기 때문이다. 따라서
      이 확장을 사용하는 명세는 이러한 경우를 금지하여
      RFC 2231과의 호환성을 유지하는 것이 좋다.

      참고: 이 명세는 별표로 끝나는
      매개변수 이름에 새로운 해석을 자동으로 부여하지 않는다.
      앞서 설명했듯이 여기서 정의한 구문을 채택할지는
      비확장 매개변수의 명세에서 결정한다.
      그렇지만 일부 기존 구현은
      매개변수 이름이 별표로 끝나면
      자동으로 이 표기법으로 전환하는 것으로 알려져 있다.
      따라서 별표로 끝나는 매개변수 이름을 다른 용도로 사용하면
      상호운용성 문제가 발생할 가능성이 크다.

4.1.  확장을 사용해야 하는 경우

   [RFC2277]의 4.2절은 사람이 읽을 수 있는 텍스트를 포함하는
   프로토콜 요소가 언어 정보를 담을 수 있어야 한다고 요구한다. 따라서
   매개변수 값이 텍스트이며 그 언어가 알려져 있다면
   항상 ext-value 생성 규칙을 사용하는 것이 바람직하다.

   또한 매개변수 값에 US-ASCII 부호화 문자 집합에
   속하지 않는 문자를 담아야 하는 경우에도
   이 확장을 사용하는 것이 바람직하다([RFC0020]).
   유니코드 문자 집합의 일부로 제한되는 새로운
   매개변수를 정의하는 것은 허용될 수 없다는 점에 주의한다.

4.2.  오류 처리

   헤더 필드 명세는 동일한 이름의 매개변수를
   여러 개 허용하는지와 이를 어떻게 처리해야 하는지 정의해야 한다.
   이 명세는 확장 구문을 사용하는 매개변수를
   우선하도록 제안한다. 이를 통해 생성자는
   아직 확장 구문을 이해하지 못하는 수신자의 동작을 방해하지 않고
   두 형식을 모두 사용할 수 있다.






Reschke                      Standards Track                    [Page 8]

RFC 8187            Charset/Language Encoding in HTTP     September 2017


   예:

     foo: bar; title="EURO exchange rates";
               title*=utf-8''%e2%82%ac%20exchange%20rates

   이 경우 송신자는 레거시 수신자를 위해 ASCII 버전의 제목을 제공하면서
   이 명세를 이해하는 수신자를 위해 국제화된 버전도 포함한다.
   후자의 수신자는 당연히 이전 구문보다
   새로운 구문을 우선하는 것이 바람직하다.

5.  보안 고려사항

   이 문서에서 설명하는 형식은 비 ASCII 문자를 전송할 수 있으므로
   문자 "스푸핑"이 가능해진다.
   이 경우 표시된 값이 실제와 다른 것으로 보일 수 있다.

   또한 UTF-8 디코딩과 관련된
   알려진 공격 시나리오가 있다.

   두 주제에 대한 자세한 정보는 [RFC3629]의 10절을 참조한다.

   또한 이 문서에서 규정하는 확장은
   하나의 매개변수에 대해 여러 언어 버전을 전송할 수 있게 한다.
   같은 매개변수의 서로 다른 언어 버전이 동등하지 않다면
   이러한 사용은 스푸핑 공격을 허용할 수 있다.
   이 공격이 실제로 효과가 있는지는
   규정된 매개변수에 달려 있다.

6.  IANA 고려사항

   이 문서는 IANA의 어떠한 조치도 요구하지 않는다.

부록 A.  다음 명세에서의 변경: RFC 5987

   이 절은 [RFC5987]과 비교한 변경 사항을 요약한다:

   o  문서 제목을 "HTTP 헤더 필드 매개변수의
      문자 인코딩 및 언어 지정"으로 변경했다.

   o  필드 값의 비 ASCII 문자와 관련된 문제를 더 잘 설명하기 위해
      서론을 다시 작성했다.

   o  "ISO-8859-1" 인코딩을 지원해야 한다는 요구사항을 제거했다.

   o  이 문서는 더 이상 일반적인 "매개변수"의 ABNF를
      다시 정의하려고 하지 않는다(HTTP에는 실제로 일반적인
      매개변수 정의가 없다는 것이 밝혀졌다. 예를 들어
      공백 처리에 미묘한 차이가 있다).

   o  현재 구현의 오류 처리 결함에 관한 설명은
      더 이상 정확하지 않아 제거했다.

부록 B.  구현 보고서

   이 문서에서 정의하는 인코딩은 현재 네 가지
   서로 다른 HTTP 헤더 필드에서 사용된다:

   o  "Authentication-Control"([RFC8053]에서 정의),

   o  "Authorization"(HTTP 다이제스트 인증에 사용되며,
      [RFC7616]에서 정의),

   o  "Content-Disposition"([RFC6266]에서 정의), 그리고

   o  "Link"([RFC5988]에서 정의).

   이 인코딩은 1997년에
   [RFC2231]에서 정의한 인코딩의 프로파일/명확화이므로,
   [RFC5987]이 공개될 때 이미 많은 사용자 에이전트가 "Content-Disposition"에서의 사용을 지원했다.

   [RFC5987]이 공개된 이후 널리 사용되는 데스크톱 사용자
   에이전트 세 개가 이 인코딩에 대한 지원을 추가했다. 자세한 내용은
   <http://purl.org/NET/http/content-disposition-tests#encoding-
   2231-char>를 참조한다. 현재 모든 주요 데스크톱
   사용자 에이전트의 최신 버전이 이를 지원한다.

   Internet Explorer 9의 구현은
   ISO-8859-1 문자 인코딩을 지원하지 않는다는 점에 주의한다. 이번 문서 개정은
   UTF-8만으로 모든 코드 포인트를 표현할 수 있음을 인정하고
   ISO-8859-1 지원 요구사항을 제거한다.

   한편 "Link" 헤더 필드는 비교적 최근에
   [RFC5988]에서 규정되었다. 이 문서를 작성하는 시점에는
   Firefox(버전 15부터)를 제외한 어떤 사용자 에이전트도
   "title*" 매개변수를 지원하지 않았다.

   [RFC7616]의 3.4절은 HTTP 다이제스트 인증에 사용할
   "username*" 매개변수를 정의한다. 작성 시점에는
   이 확장을 구현한 사용자 에이전트가 없었다.
