'Basic' HTTP 인증 스킴

초록

이 문서는 자격증명을 사용자 ID/비밀번호 쌍으로 전송하며 Base64로 인코딩하는 "Basic" 하이퍼텍스트 전송 프로토콜(HTTP) 인증 스킴을 정의합니다.

1. 소개

이 문서는 사용자 ID/비밀번호 쌍을 Base64로 인코딩하여 전송하는 "Basic" 하이퍼텍스트 전송 프로토콜(HTTP) 인증 스킴을 정의합니다(HTTP 인증 스킴은 [RFC7235]에 정의되어 있습니다).

이 스킴은 사용자 ID와 비밀번호가 평문으로 네트워크를 통해 전송되기 때문에, TLS(Transport Layer Security, [RFC5246])와 같은 외부의 안전한 시스템과 함께 사용되지 않는 한 안전한 사용자 인증 방법으로 간주되지 않습니다.

"Basic" 스킴은 이전에 Section 2 of [RFC2617]에 정의되어 있었습니다. 이 문서는 정의를 갱신하고, 'charset' 인증 매개변수(Section 2.1)를 도입하여 국제화 문제도 다룹니다.

RFC 2617을 갱신하는 다른 문서로는 "Hypertext Transfer Protocol (HTTP/1.1): Authentication" ([RFC7235], 인증 프레임워크 정의), "HTTP Digest Access Authentication" ([RFC7616], "Digest" 인증 스킴 정의 갱신), 및 "HTTP Authentication-Info and Proxy-Authentication-Info Response Header Fields" ([RFC7615])가 있습니다. 이 네 문서를 합하면 RFC 2617은 폐기됩니다.

1.1. 용어 및 표기

이 문서에서 사용된 키워드 "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", 및 "OPTIONAL"은 [RFC2119]에 설명된 대로 해석됩니다.

"protection space"와 "realm" 용어는 RFC7235 섹션 2.2에 정의되어 있습니다.

"(character) repertoire" 및 "character encoding scheme" 용어는 RFC6365 섹션 2에 정의되어 있습니다.

2. 'Basic' 인증 스킴

Basic 인증 스킴은 클라이언트가 각 보호 공간("realm")에 대해 사용자 ID와 비밀번호로 자신을 인증해야 한다는 모델에 기반합니다. realm 값은 해당 서버에서 다른 realm과 단순 동등 비교만 가능한 자유 형식 문자열입니다. 서버는 요청된 리소스에 적용되는 보호 공간에 대해 사용자 ID와 비밀번호를 검증할 수 있는 경우에만 요청을 처리합니다.

Basic 인증 스킴은 인증 프레임워크를 다음과 같이 활용합니다.

챌린지에서는:

  • 스킴 이름은 "Basic"입니다.
  • 인증 매개변수 'realm'은 필수(REQUIRED)입니다 ([RFC7235], Section 2.2).
  • 인증 매개변수 'charset'은 선택적(OPTIONAL)입니다 (자세한 내용은 Section 2.1 참조).
  • 다른 인증 매개변수는 정의되어 있지 않습니다 — 알 수 없는 매개변수는 수신자가 무시해야(MUST) 하며, 새 매개변수는 이 명세를 개정해야만 정의될 수 있습니다.

또한 챌린지를 올바르게 파싱하는 복잡성에 대해서는 RFC7235 섹션 4.1을 참조하십시오.

스킴 및 매개변수 이름은 대소문자 구분 없이 비교됩니다.

자격증명에는 RFC7235 섹션 2.1에 정의된 "token68" 문법이 사용됩니다. 이 값은 아래에 정의된 대로 user-id와 password에 기초하여 계산됩니다.

인증 공간 내의 URI에 대한 요청 수신 시 자격증명이 없는 경우, 서버는 401 (Unauthorized) 상태 코드와 WWW-Authenticate 헤더 필드를 사용하여 챌린지를 응답할 수 있습니다([RFC7235], Section 3.1).

예를 들면:

HTTP/1.1 401 Unauthorized
Date: Mon, 04 Feb 2014 16:50:53 GMT
WWW-Authenticate: Basic realm="WallyWorld"

여기서 "WallyWorld"는 서버가 보호 공간을 식별하기 위해 할당한 문자열입니다.

프록시는 407 (Proxy Authentication Required) 상태 코드와 Proxy-Authenticate 헤더 필드를 사용하여 유사한 챌린지로 응답할 수 있습니다([RFC7235], Section 3.2).

권한을 얻기 위해 클라이언트는

  1. 사용자로부터 user-id와 password를 얻고,
  2. user-id, 단일 콜론(":"), password를 연결하여 user-pass를 구성하고,
  3. user-pass를 옥텟 시퀀스로 인코딩하고(아래의 문자 인코딩 스킴 논의를 참조),
  4. 이 옥텟 시퀀스를 Base64([RFC4648], Section 4)로 인코딩하여 US-ASCII 문자 시퀀스로 변환하여 basic-credentials를 얻습니다([RFC0020]).

이 인증 스킴의 원래 정의는 user-pass를 옥텟 시퀀스로 변환할 때 사용할 문자 인코딩 스킴을 명시하지 않았습니다. 실제로 대부분 구현체는 ISO-8859-1([ISO-8859-1]) 같은 로케일별 인코딩이나 UTF-8([RFC3629])을 선택했습니다. 이전과의 호환성 때문에 이 명세는 기본 인코딩을 US-ASCII과 호환되는 한(US-ASCII 문자를 단일 옥텟으로 매핑하는 경우) 미정의로 남깁니다.

user-id와 password에는 어떤 제어 문자도 포함되어서는 안 됩니다(MUST NOT) (자세한 내용은 RFC5234 Appendix B.1의 "CTL" 참조).

또한 user-id에 콜론 문자가 포함된 경우는 무효입니다. user-pass 문자열에서 첫 번째 콜론이 user-id와 password를 구분하기 때문입니다; 첫 번째 콜론 이후의 텍스트는 비밀번호의 일부로 취급됩니다. 따라서 콜론을 포함한 user-id는 user-pass 문자열에 인코딩할 수 없습니다.

많은 사용자 에이전트가 사용자가 입력한 user-id에 콜론이 포함되어 있는지 확인하지 않고 user-pass 문자열을 생성한다는 점을 유의하십시오; 수신자는 이 경우 사용자 이름 입력의 일부를 비밀번호의 일부로 처리할 것입니다.

사용자 에이전트가 user-id "Aladdin"과 비밀번호 "open sesame"을 보내려면 다음 헤더 필드를 사용합니다:

Authorization: Basic QWxhZGRpbjpvcGVuIHNlc2FtZQ==

2.1. 'charset' auth-param

챌린지에서 서버는 'charset' 인증 매개변수를 사용하여 사용자 에이전트가 "user-pass"(옥텟 시퀀스)를 생성할 때 사용하기를 기대하는 문자 인코딩 스킴을 표시할 수 있습니다. 이 정보는 순수히 권고적(advisory)입니다.

허용되는 유일한 값은 "UTF-8"이며, 대소문자 구분 없이 매치되어야 합니다(참조: [RFC2978], Section 2.3). 이는 서버가 문자 데이터를 Unicode 정규화 형식 C("NFC", RFC5198 Section 3)로 변환하고 UTF-8 문자 인코딩 스킴([RFC3629])을 사용하여 옥텟으로 인코딩할 것을 기대함을 나타냅니다.

user-id의 경우 수신자는 RFC7613 섹션 3.3에 정의된 "UsernameCasePreserved" 프로파일에 포함된 모든 문자를 지원해야 하며(MUST) 다만 콜론(" : ") 문자는 예외입니다.

password의 경우 수신자는 RFC7613 섹션 4.2에 정의된 "OpaqueString" 프로파일의 모든 문자를 지원해야 합니다(MUST).

다른 값들은 향후 사용을 위해 예약되어 있습니다.

참고: 'charset'은 챌린지에서만 정의됩니다. Basic 인증은 자격증명에 단일 토큰('token68' 문법)을 사용하므로 자격증명 문법 자체는 확장 가능하지 않습니다.

참고: 'charset'이라는 이름은 RFC2831 섹션 2.1.1과의 일관성을 위해 선택되었습니다. 사실 더 나은 이름은 'accept-charset'이었을 것이며, 이는 그것이 포함된 메시지 자체가 아니라 서버의 기대를 나타내기 때문입니다.

아래 예에서 서버는 "foo" realm에서 Basic 인증을 사용하며 UTF-8 문자 인코딩을 선호함을 표시합니다:

WWW-Authenticate: Basic realm="foo", charset="UTF-8"

매개변수 값은 토큰이거나 인용된 문자열일 수 있습니다; 이 경우 서버는 인용 문자열 표기법을 선택했습니다.

사용자 이름이 "test"이고 비밀번호가 유니코드 문자 U+00A3(파운드 기호)를 뒤에 붙인 "123" 문자열일 때, UTF-8 인코딩을 사용하면 user-pass는 다음과 같습니다:

't' 'e' 's' 't' ':' '1' '2' '3' pound
74  65  73  74  3A  31  32  33  C2  A3

이 옥텟 시퀀스를 Base64로 인코딩하면([RFC4648]) 다음과 같습니다:

dGVzdDoxMjPCow==

따라서 Authorization 헤더 필드는 다음과 같습니다:

Authorization: Basic dGVzdDoxMjPCow==

또는 프록시 인증의 경우:

Proxy-Authorization: Basic dGVzdDoxMjPCow==

2.2. 자격증명 재사용

인증된 요청의 절대 URI([RFC3986], Section 4.3)가 주어지면, 해당 요청의 인증 범위(authentication scope)는 경로 구성요소("hier_part", [RFC3986], Section 3)의 마지막 슬래시("/") 문자 이후의 모든 문자를 제거하여 얻습니다. 클라이언트는 인증된 요청의 realm 값이 지정하는 보호 공간 내에서 인증 범위의 접두사 일치(prefix-match)를 갖는 URI들도 동일한 보호 공간에 속한다고 가정해야(SHOULD) 합니다.

클라이언트는 해당 공간의 리소스에 대한 요청에서 서버로부터 추가 챌린지를 받지 않고도 해당 Authorization 헤더 필드를 선제적으로 전송할 수 있습니다(MAY). 마찬가지로, 클라이언트가 프록시에 요청을 보낼 때도 Proxy-Authorization 헤더 필드에서 user-id와 password를 프록시로부터 추가 챌린지 없이 재사용할 수 있습니다(MAY).

예를 들어, 다음과 같이 인증된 요청이 있다면:

http://example.com/docs/index.html

아래 URI들에 대한 요청은 알려진 자격증명을 사용할 수 있습니다:

http://example.com/docs/
http://example.com/docs/test.doc
http://example.com/docs/?page=1

반면 아래 URI들은 인증 범위 밖으로 간주됩니다:

http://example.com/other/
https://example.com/docs/

URI는 여러 인증 범위의 일부일 수 있다는 점에 유의하십시오(예: "http://example.com/" 및 "http://example.com/docs/"). 이 명세는 이들 중 어느 것이 더 높은 우선순위를 가져야 하는지 정의하지 않습니다.

3. 국제화 고려사항

US-ASCII 문자 집합을 벗어나는 문자를 포함한 user-id나 password는 통신 당사자 양측이 사용할 문자 인코딩 스킴에 합의하지 않으면 상호 운용성 문제가 발생합니다. 서버는 'charset' 매개변수(Section 2.1)를 사용하여 "UTF-8"을 선호한다고 표시함으로써 클라이언트가 해당 인코딩으로 전환할 가능성을 높일 수 있습니다.

'realm' 매개변수는 텍스트로 간주될 수 있는 데이터를 담지만, [RFC7235]는 비-US-ASCII 문자를 신뢰성 있게 전송하는 방법을 정의하지 않습니다. 이 문제는 해당 명세를 개정할 때 해결되어야 할 알려진 이슈입니다.

4. 보안 고려사항

Basic 인증 스킴은 안전한 사용자 인증 방법이 아니며, 전송되는 자격증명은 물리적 네트워크 상에서 평문으로 전송됩니다. HTTP는 Basic 인증에 일회용 비밀번호 등과 같은 향상 기능을 추가하는 것을 막지 않습니다.

Basic 인증의 가장 심각한 결함은 사용자 비밀번호가 물리적 네트워크를 통해 평문으로 전송된다는 점입니다. 많은 다른 인증 스킴은 이 문제를 해결합니다.

Basic 인증은 비밀번호를 평문으로 전송하므로, 민감하거나 가치 있는 정보를 보호하기 위해(예: HTTPS 없이) 사용해서는 안 됩니다(SHOULD NOT).

Basic 인증의 일반적인 사용 사례는 식별 목적입니다 — 예를 들어 서버의 정확한 사용 통계를 수집하기 위해 사용자가 user-id와 password를 제공하도록 요구하는 경우입니다. 이 경우 사용자가 스스로 비밀번호를 선택하게 허용하지 않고 서버가 사용자에게 user-id와 password를 발급한다면 위험이 적다고 생각할 수 있습니다. 그러나 사용자가 여러 비밀번호를 관리하기 어렵기 때문에 자주 동일한 비밀번호를 재사용하는 경향이 있어 위험이 발생합니다.

서버가 사용자가 자체 비밀번호를 선택하도록 허용하면 위협은 서버의 문서 무단 접근뿐 아니라 사용자가 동일한 비밀번호를 사용하여 보호하는 다른 시스템의 자원에 대한 무단 접근까지 포함합니다. 또한 서버의 비밀번호 데이터베이스에 저장된 많은 비밀번호가 다른 사이트의 비밀번호일 수 있습니다. 따라서 시스템 소유자나 관리자가 해당 정보를 안전하게 유지하지 않으면 모든 사용자가 타 사이트에 대한 무단 접근 위험에 노출될 수 있습니다. 이는 보안 및 개인정보 문제를 야기합니다(RFC6973 참조). 동일한 user-id/비밀번호 조합이 이메일이나 건강 포털 같은 다른 계정에 사용되는 경우 개인 정보가 노출될 수 있습니다.

Basic 인증은 위조 서버에 의한 스푸핑에도 취약합니다. 사용자가 자신이 인증된 정보를 가진 호스트에 연결하고 있다고 믿게끔 유도될 수 있고, 실제로는 악의적 서버에 연결되면 공격자는 비밀번호를 요청하여 저장한 뒤 오류를 가장할 수 있습니다. 서버 구현자는 이러한 위조를 방지해야 합니다; 특히 기존 연결의 메시지 프레이밍 제어를 가져올 수 있는 소프트웨어 구성요소는 주의해서 사용하거나 아예 사용하지 않아야 합니다(예: RFC3875의 NPH 스크립트 등).

Basic 인증을 구현하는 서버 및 프록시는 요청을 인증하기 위해 어떤 형태로든 사용자 비밀번호를 저장해야 합니다. 이러한 비밀번호는 비밀번호 데이터가 유출되더라도 쉽게 복원될 수 없도록 저장되어야 합니다. 사용자가 스스로 비밀번호를 설정할 수 있도록 허용되는 경우에는 특히 중요합니다. 사용자는 약한 비밀번호를 선택하고 인증 영역(realm) 전반에 걸쳐 재사용하는 경향이 알려져 있기 때문입니다. 우수한 비밀번호 해싱 기법에 대한 전체 논의는 이 문서의 범위를 벗어나지만, 서버 운영자는 비밀번호 데이터 유출 시 사용자에 대한 위험을 최소화하기 위해 노력해야 합니다. 예를 들어 서버는 사용자 비밀번호를 평문으로 저장하거나 솔트가 없는 다이제스트로 저장하는 것을 피해야 합니다. 최신 비밀번호 해싱 기법에 대한 자세한 논의는 "Password Hashing Competition" (<https://password-hashing.net>)을 참조하십시오.

UTF-8 문자 인코딩과 정규화 사용은 추가적인 보안 고려사항을 수반합니다; 자세한 내용은 RFC3629 섹션 10 및 RFC5198 섹션 6을 참조하십시오.

5. IANA 고려사항

IANA는 "Hypertext Transfer Protocol (HTTP) Authentication Scheme Registry"를 유지 관리합니다([RFC7235]) <http://www.iana.org/assignments/http-authschemes>.

"Basic" 인증 스킴의 항목은 이 명세를 참조하도록 업데이트되었습니다.

부록 A. RFC 2617에서의 변경사항

스킴 정의는 [RFC7235]와 같은 최신 명세와 일치하도록 다시 작성되었습니다.

새로운 인증 매개변수 'charset'이 추가되었습니다. 이것은 순수히 권고적이므로 기존 구현은 변경할 필요가 없으며, 추가 정보를 이용하고자 하는 경우에만 변경하면 됩니다.

부록 B. 'charset' 매개변수의 배포 고려사항

B.1. 사용자 에이전트

'charset'을 구현하지 않는 사용자 에이전트는 새로운 매개변수를 무시하고 이전과 동일하게 계속 작동합니다.

기본적으로 이미 UTF-8을 사용하는 사용자 에이전트는 정의상 'charset'을 구현한 것입니다.

다른 사용자 에이전트는 기본 동작을 유지하다가 새 매개변수를 보게 되면 UTF-8로 전환할 수 있습니다.

B.2. 서버

자격증명에서 비-US-ASCII 문자를 지원하지 않는 서버는 'charset'을 지원하기 위해 변경할 필요가 없습니다.

비-US-ASCII 문자를 지원해야 하지만 UTF-8 문자 인코딩을 사용할 수 없는 서버는 영향받지 않으며 이전과 동일하게 작동합니다.

비-US-ASCII 문자를 지원해야 하고 UTF-8을 사용할 수 있는 서버는 챌린지에 'charset' 매개변수를 지정하여 옵트인할 수 있습니다. 'charset'을 이해하는 클라이언트는 UTF-8을 사용하기 시작할 것이고, 그렇지 않은 클라이언트는 계속 기본 인코딩으로 자격증명을 보내거나 깨진 자격증명을 보내거나 전혀 보내지 않을 수 있습니다. 모든 클라이언트가 UTF-8을 지원하도록 업그레이드될 때까지 서버는 요청에서 UTF-8과 레거시 인코딩을 모두 보게 될 가능성이 큽니다. UTF-8로 처리하는 것이 실패할 경우(UTF-8 디코딩 실패나 user-id/password 불일치 등) 서버는 이전에 지원하던 레거시 인코딩으로 폴백을 시도할 수 있습니다. 단, 암묵적 재시도는 신중히 수행되어야 합니다; 일부 서브시스템은 반복된 로그인 실패를 자격증명 추측 공격으로 감지할 수 있습니다.

B.3. 기본 인코딩을 단순히 UTF-8로 전환하지 않는 이유

오늘날 일부 사이트는 ISO-8859-1([ISO-8859-1])과 같은 로컬 문자 인코딩을 기본값으로 사용하도록 되어 있고, 사용자 에이전트가 해당 인코딩을 사용하기를 기대합니다. 이러한 사이트에서 사용자 에이전트가 UTF-8로 전환하면 인증이 중단될 수 있습니다.

사이트는 User-Agent 헤더 필드를 검사하여(RFC7231, Section 5.5.3) 클라이언트가 어떤 문자 인코딩을 기대하는지 결정할 수 있습니다. 따라서 일부 사용자 에이전트에 대해서는 UTF-8을 지원하되 다른 사용자 에이전트에 대해서는 다른 인코딩을 기본으로 사용하는 사이트가 있을 수 있습니다. 이러한 후자의 그룹에 속한 사용자 에이전트는 다수의 서버가 항상 UTF-8을 사용하도록 업그레이드될 때까지 기존 동작을 계속해야 합니다.

감사의 글

이 명세는 이전에 RFC 2617에서 정의된 "Basic" HTTP 인증 스킴의 정의를 인계받았습니다. 우리는 해당 명세 작업에 기여한 John Franks, Phillip M. Hallam-Baker, Jeffery L. Hostetler, Scott D. Lawrence, Paul J. Leach, Ari Luotonen, 및 Lawrence C. Stewart에게 감사드립니다. 추가 감사의 글은 RFC2617 섹션 6을 참조하십시오.

user-pass에 사용되는 문자 인코딩 스킴과 관련된 국제화 문제는 2000년에 모질라 버그로 보고되었습니다 (참조: <https://bugzilla.mozilla.org/show_bug.cgi?id=41489> 및 더 최근의 <https://bugzilla.mozilla.org/show_bug.cgi?id=656213>). 이 문제를 새로운 auth-param으로 해결하자는 아이디어는 Andrew Clover의 것이었습니다.

이 개정에 대한 피드백을 준 HTTPAUTH 작업 그룹 구성원들과 리뷰어들(예: Stephen Farrell, Roy Fielding, Daniel Kahn Gillmor, Tony Hansen, Bjoern Hoehrmann, Kari Hurtta, Amos Jeffries, Benjamin Kaduk, Michael Koeller, Eric Lawrence, Barry Leiba, James Manger, Alexey Melnikov, Kathleen Moriarty, Juergen Schoenwaelder, Yaron Sheffer, Meral Shirazipour, Michael Sweet, 및 Martin Thomson)에게 감사드립니다.
