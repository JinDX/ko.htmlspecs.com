No-Vary-Search HTTP 캐싱 확장

초록

이 명세는 URI 쿼리 구성 요소가 캐싱에 미치는 방식을 변경하는 HTTP 캐싱 확장을 정의한다. 이 명세에서는 원본 서버가 쿼리 구성 요소의 특정 부분이 제공되는 응답에 의미상 영향을 주지 않으며 캐시 일치 여부를 판단할 때 무시할 수 있음을 캐시에 알릴 수 있도록 하는 "No-Vary-Search" 응답 헤더 필드를 도입한다.¶

이 문서에 관하여

이 참고 사항은 RFC로 게시되기 전에 제거된다.¶

이 초안의 최신 개정판은 https://httpwg.org/http-extensions/draft-ietf-httpbis-no-vary-search.html에서 확인할 수 있다. 이 문서의 상태 정보는 https://datatracker.ietf.org/doc/draft-ietf-httpbis-no-vary-search/에서 확인할 수 있다.¶

이 문서에 대한 논의는 HTTP 작업 그룹 메일링 리스트(mailto:ietf-http-wg@w3.org)에서 이루어지며, 그 보관 문서는 https://lists.w3.org/Archives/Public/ietf-http-wg/에 있다. 작업 그룹 정보는 https://httpwg.org/에서 확인할 수 있다.¶

이 초안의 소스와 이슈 추적기는 https://github.com/httpwg/http-extensions/labels/no-vary-search에서 확인할 수 있다.¶

1. 소개

HTTP 캐싱 [HTTP-CACHING]은 여러 캐시 키에서 일치하는 리소스를 재사용하는 것에 기반하며, 그중 가장 중요한 것은 제시된 대상 URI([HTTP]의 Section 7.1)입니다. 그러나 때때로 여러 URI가 같은 리소스를 나타낼 수 있습니다. 이로 인해 캐시가 항상 기대만큼 유용하지는 않게 됩니다. 캐시에 어떤 URI 아래의 응답이 들어 있지만, 그 응답이 다른 URI 아래에서 요청되면 캐시된 버전은 무시됩니다.¶

"No-Vary-Search" 응답 헤더 필드는 [HTTP-CACHING]의 제4절에 설명된 대로, 쿼리 구성 요소만 서로 다른 URI들이 동일한 리소스를 식별하는 경우에 이 일반적인 문제의 특정 하위 집합을 해결하는 캐싱 확장을 정의한다. 이를 통해 리소스는 쿼리 구성 요소의 일부 또는 전체가 제공되는 응답에 의미상 영향을 주지 않으므로 캐시 일치 여부를 판단할 때 무시할 수 있음을 선언할 수 있다. 이는 쿼리 구성 요소를 application/x-www-form-urlencoded 형식 [WHATWG-URL]을 사용하여 인코딩된 매개변수의 시퀀스로 해석함으로써 이루어진다. 예를 들어 쿼리 구성 요소 내 매개변수의 순서가 어떤 리소스가 식별되는지에 영향을 주지 않는 경우, 이는 다음을 사용하여 나타낸다.¶ 

No-Vary-Search: key-order
¶

특정 쿼리 매개변수(예: 분석용으로 무언가를 나타내는 것)가 제공되는 리소스에 의미적으로 영향을 주지 않는다면, 이는 다음을 사용하여 표시됩니다¶

No-Vary-Search: params=("utm_source" "utm_medium" "utm_campaign")
¶

그리고 리소스가 대신 허용 목록 기반 접근 방식을 원하여, 특정한 알려진 쿼리 매개변수만 제공되는 응답에 의미적으로 영향을 주는 경우에는 다음을 사용할 수 있습니다¶

No-Vary-Search: except=("productId")
¶

쿼리 구성 요소의 일부를 변경하여 고유한 캐시 키를 생성하고 더 새로운 응답을 강제로 가져오도록 하는 관행인 "캐시 버스팅"은 "No-Vary-Search" 응답 헤더 필드로 인해 효과가 없어질 수 있음에 유의한다.¶

3절에서는 [STRUCTURED-FIELDS] 프레임워크를 사용하여 새로운 "No-Vary-Search" 응답 헤더 필드를 정의한다. 4절과 5절 에서는 필드 값을 명세에서 표현할 수 있는 데이터 모델과 구조화 필드 파서의 원시 출력을 해당 데이터 모델로 구문 분석하는 절차를 설명한다. 6절에서는 헤더 필드의 영향을 받을 때 두 URL이 동등한지를 비교하는 핵심 알고리즘을 제시한다. 특히 이 알고리즘은 [WHATWG-URL]에 명시된 application/x-www-form-urlencoded 형식이 제공하는 쿼리 구성 요소의 키와 값 분해를 사용한다. (따라서 이 헤더 필드는 쿼리 구성 요소가 해당 형식을 따르지 않는 URL에는 유용하지 않다.) 마지막으로 7절에서는 이 새로운 동등성을 고려하도록 [HTTP-CACHING]의 4절을 확장하는 방법을 설명한다.¶

배포 관점에서 이 확장은 브라우저 캐시, 콘텐츠 전송 네트워크 및 포워드 프록시를 포함한 HTTP 캐시에 의해 구현된다. 원본 서버는 이러한 캐시에 지침을 제공하기 위해 "No-Vary-Search" 응답 헤더 필드를 전송한다. 이 확장을 구현하는 캐시는 대상 URI의 쿼리 구성 요소가 다르더라도 이전에 저장된 응답을 새 요청에 안전하게 재사용할 수 있는 시점을 판단하기 위해 이러한 지침을 사용한다.¶

2. 규약 및 정의

이 문서의 핵심 단어 "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", 및 "OPTIONAL"은 여기에 표시된 것처럼 모두 대문자로 나타날 때에만 BCP 14 [RFC2119] [RFC8174]에 설명된 대로 해석됩니다.¶

이 문서에서 "URI"와 "URL"이라는 용어는 문맥에 따라 서로 바꾸어 사용됩니다. "URI"는 [URI], [HTTP], 및 [HTTP-CACHING]의 문맥에서 사용되는 반면, "URL"은 [WHATWG-URL]에 지정된 알고리즘의 문맥에서 사용됩니다.¶

이 문서에서 "query parameters"라는 용어는 application/x-www-form-urlencoded 형식을 사용하여 URL의 query 구성 요소를 파싱한 결과로 생성되는 키와 값을 가리킨다 [WHATWG-URL].¶

이 문서는 WHATWG 및 W3C 사용에서 일반적인 일부 규약과 표기법도 채택하며, 특히 알고리즘과 관련된 경우가 그렇다. [WHATWG-INFRA], 그리고 특히 다음을 보라:¶

  • 리스트 리터럴 표기 « 1, 2, 3 »를 포함한 리스트의 정의.¶

  • code units로서의 표현을 포함한 문자열의 정의.¶

(사용되는 다른 개념은 인라인 참조를 사용하여 표시된다.)¶

3. HTTP header field 정의

"No-Vary-Search" 응답 헤더 필드는 구조화 필드이며 [STRUCTURED-FIELDS], 그 값은 반드시 사전이어야 한다([STRUCTURED-FIELDS]의 3.2절).¶

여기에는 다음 제약이 있다:¶

  • 존재하는 경우, key-order entry의 값은 MUST boolean이어야 한다(Section 3.3.6 of [STRUCTURED-FIELDS]).¶

  • 존재하는 경우, params entry의 값은 MUST 문자열의 inner list여야 한다(Section 3.1.1 of [STRUCTURED-FIELDS]).¶

  • 존재하는 경우, except entry의 값은 MUST 문자열의 inner list여야 한다(Section 3.1.1 of [STRUCTURED-FIELDS]).¶

  • params entry도 존재하는 경우 except entry는 MUST NOT 존재하면 안 된다.¶

dictionary는 key-order, params, except 중 하나가 아닌 키를 가진 entry들을 MAY 포함할 수 있지만, 그 의미는 이 명세에서 정의되지 않는다. 이 명세의 구현은 그러한 entry들을 무시한다(하지만 미래의 문서가 그러한 entry들에 의미를 부여할 수도 있다).¶

파싱 알고리즘은 Section 5.2에 정의되어 있다.¶

4. 데이터 모델

URL variation config는 다음으로 구성된다:¶

no-vary params

특수 값 wildcard 또는 문자열 리스트¶

vary params

특수 값 wildcard 또는 문자열 리스트¶

vary on key order

boolean¶

default URL variation config는 no-vary params가 빈 리스트이고, vary params가 wildcard이며, vary on key order가 true인 URL variation config이다.¶

obtain a URL variation config 알고리즘(Section 5.2)은 모든 URL variation config가 다음 제약을 따르도록 보장한다:¶

  • vary params는 no-vary params가 wildcard인 경우에만, 그리고 그 경우에 한해 리스트이다; 그리고¶

  • no-vary params는 vary params가 wildcard인 경우에만, 그리고 그 경우에 한해 리스트이다.¶

5. 파싱

5.1. URL variation config 파싱

value가 주어졌을 때 parse a URL variation config하려면:¶

  1. value가 null이면, default URL variation config를 반환한다.¶

  2. result를 새 URL variation config로 둔다.¶

  3. result의 vary on key order를 true로 설정한다.¶

  4. value["key-order"]가 존재하면:¶

    1. value["key-order"]가 boolean이 아니면, default URL variation config를 반환한다.¶

    2. result의 vary on key order를 value["key-order"]의 boolean 부정값으로 설정한다.¶

  5. value["params"]와 value["except"]가 둘 다 존재하거나 둘 다 존재하지 않으면, default URL variation config를 반환한다.¶

  6. value["params"]가 존재하면:¶

    1. value["params"]가 array가 아니면, default URL variation config를 반환한다.¶

    2. value["params"] 안의 어떤 item이라도 string이 아니면, default URL variation config를 반환한다.¶

    3. value["params"]의 각 item에 parse a key (Section 5.3)를 적용한 결과로 result의 no-vary params를 설정한다.¶

    4. result의 no-vary params 안의 어떤 item이라도 error이면, default URL variation config를 반환한다.¶

    5. result의 vary params를 wildcard로 설정한다.¶

  7. 그렇지 않고, value["except"]가 존재하면:¶

    1. value["except"]가 array가 아니면, default URL variation config를 반환한다.¶

    2. value["except"] 안의 어떤 item이라도 string이 아니면, default URL variation config를 반환한다.¶

    3. value["except"]의 각 item에 parse a key (Section 5.3)를 적용한 결과로 result의 vary params를 설정한다.¶

    4. result의 vary params 안의 어떤 item이라도 error이면, default URL variation config를 반환한다.¶

    5. result의 no-vary params를 wildcard로 설정한다.¶

  8. result를 반환한다.¶

일반적으로 이 알고리즘은 엄격하며, 인식하지 못하는 것을 발견할 때마다 default URL variation config를 반환하는 경향이 있다. 이는 default URL variation config 동작이 단지 더 적은 cache hit를 유발할 뿐이며, 이는 허용 가능한 fallback 동작이기 때문이다.¶

하지만 top level의 인식되지 않은 key들은 무시되며, 이는 이 명세를 미래에 확장하기 쉽게 하기 위한 것이다. 기존 client software의 오동작을 피하기 위해, 그러한 확장은 cached response가 match할 수 있는 request의 집합을 줄이기보다는 확장할 가능성이 높다.¶

이 알고리즘의 입력은 일반적으로 field_type "dictionary"를 사용하여 structured field(Section 4.2 of [STRUCTURED-FIELDS])를 파싱함으로써 얻어진다.¶

5.2. URL variation config 획득

HTTP response (Section 3.4 of [HTTP]) response가 주어졌을 때 obtain a URL variation config하려면:¶

  1. fieldValue를 response의 "No-Vary-Search" 응답 헤더 필드를 사전으로 구문 분석한 결과로 둔다([STRUCTURED-FIELDS]의 4.2절).¶

  2. fieldValue가 주어졌을 때 parse a URL variation config (Section 5.1)의 결과를 반환한다. ¶

5.2.1. 예제

다음은 여러 입력이 resulting no-vary params 및 vary params에 미치는 영향 측면에서 어떻게 파싱되는지를 보여준다:¶

Table 1
입력 결과
No-Vary-Search: key-order no-vary params: (empty list)
vary params: wildcard
vary on key order: false
No-Vary-Search: params=("a") no-vary params: « "a" »
vary params: wildcard
No-Vary-Search: except=("x") no-vary params: wildcard
vary params: « "x" »
No-Vary-Search: params=() no-vary params: (빈 리스트)
vary params: wildcard
No-Vary-Search: except=() no-vary params: wildcard
vary params: (빈 리스트)

다음 입력은 모두 invalid이며, default URL variation config가 반환되게 한다:¶

표 2
입력 설명
No-Vary-Search: key-order="not a boolean" key-order에는 문자열이 아니라 부울 값이 필요하다
No-Vary-Search: params="not an inner list" params에는 문자열이 아니라 내부 목록이 필요하다
No-Vary-Search: params=(not-a-string) params 항목은 문자열이어야 한다(토큰은 유효하지 않음)
No-Vary-Search: params=?0 params에는 부울 값이 아니라 내부 목록이 필요하다
No-Vary-Search: params=?1 params에는 부울 값이 아니라 내부 목록이 필요하다
No-Vary-Search: params=?1, except=("x") params와 except는 둘 다 존재할 수 없다
No-Vary-Search: params=("a"), except=("x") params와 except는 둘 다 존재할 수 없다
No-Vary-Search: params=(), except=() params와 except는 둘 다 존재할 수 없다
No-Vary-Search: except="not an inner list" except에는 문자열이 아니라 내부 목록이 필요하다
No-Vary-Search: except=(not-a-string) except 항목은 문자열이어야 한다(토큰은 유효하지 않음)
No-Vary-Search: except=?1 except에는 부울 값이 아니라 내부 목록이 필요하다

다음 입력은 유효하지만 다소 일반적이지 않다. 각 입력을 더 일반적인 형식과 함께 제시한다.¶

표 3
입력 일반적인 형식
No-Vary-Search: key-order=?1 No-Vary-Search: key-order
No-Vary-Search: except=("x"), key-order No-Vary-Search: key-order, except=("x")
No-Vary-Search: params=() (헤더 필드를 생략)
No-Vary-Search: key-order=?0 (헤더 필드를 생략)

5.3. key 파싱

ASCII string keyString이 주어졌을 때 parse a key하려면:¶

  1. keyBytes를 keyString의 isomorphic encoding [WHATWG-INFRA]으로 둔다.¶

  2. keyBytes 안의 모든 0x2B (+)를 0x20 (SP)로 바꾼다.¶

  3. keyBytesDecoded를 keyBytes의 percent-decoding [WHATWG-URL]으로 둔다.¶

  4. keyStringDecoded를 keyBytesDecoded의 UTF-8 decoding without BOM [WHATWG-ENCODING]으로 둔다.¶

  5. keyStringDecoded를 반환한다.¶

5.3.1. 예제

parse a key 알고리즘은 application/x-www-form-urlencoded 형식 [WHATWG-URL]이 (ASCII 문자로 제한되는) URI 안에서 키와 값의 전체 entry list를 인코딩할 수 있게 하는 방식과 유사하게, ASCII structured header field 형식에서 non-ASCII key string을 인코딩할 수 있게 한다. 예를 들어,¶ 

No-Vary-Search: params=("%C3%A9+%E6%B0%97")
¶

vary 매개변수가 « "é 気" »인 URL 변형 구성이 생성된다. 인코딩된 문자열의 "+" 문자는 공백(SP)으로 매핑된다는 점에 유의하라. 뒤의 예에서 설명하듯이, 동등성 검사 중의 정규화 과정으로 인해 다음과 같은 URI를 동등한 것으로 처리한다:¶

  • https://example.com/?é 気=1¶

  • https://example.com/?é+気=2¶

  • https://example.com/?%C3%A9%20気=3¶

  • https://example.com/?%C3%A9+%E6%B0%97=4¶

등등이 해당되며, 이는 이들 모두가 동일한 key "é 気"를 가지도록 parsed [WHATWG-URL] 되기 때문이다.¶

6. 비교

두 URL [WHATWG-URL] urlA와 urlB는, 주어진 URL variation config variationConfig에 대해 다음 알고리즘이 true를 반환하면 equivalent modulo variation config이다:¶

  1. urlA와 urlB의 scheme, username, password, host, port 또는 path가 다르면 false를 반환한다.¶

  2. variationConfig가 default URL variation config와 equivalent이면:¶

    1. urlA의 query가 urlB의 query와 같으면 true를 반환한다.¶

    2. false를 반환한다.¶

    이 경우, query에 대해 application/x-www-form-urlencoded parser [WHATWG-URL]를 실행한 후에는 동일해 보일 수도 있는 URL 쌍, 예컨대 https://example.com/a와 https://example.com/a?, 또는 https://example.com/foo?a=b&&&c와 https://example.com/foo?a=b&c=도 inequivalent로 취급된다.¶

  3. searchParamsA와 searchParamsB를 빈 리스트로 둔다.¶

  4. urlA의 query가 null이 아니면, searchParamsA를 urlA의 query에 대한 isomorphic encoding [WHATWG-INFRA]이 주어졌을 때 application/x-www-form-urlencoded parser [WHATWG-URL]를 실행한 결과로 설정한다.¶

  5. urlB의 query가 null이 아니면, searchParamsB를 urlB의 query에 대한 isomorphic encoding [WHATWG-INFRA]이 주어졌을 때 application/x-www-form-urlencoded parser [WHATWG-URL]를 실행한 결과로 설정한다.¶

  6. variationConfig의 no-vary params가 리스트이면:¶

    1. searchParamsA를 searchParamsA 안의 item pair 중에서 variationConfig의 no-vary params가 pair[0]을 포함하지 않는 것들만 담은 리스트로 설정한다.¶

    2. searchParamsB를 searchParamsB 안의 item pair 중에서 variationConfig의 no-vary params가 pair[0]을 포함하지 않는 것들만 담은 리스트로 설정한다.¶

  7. 그렇지 않고, variationConfig의 vary params가 리스트이면:¶

    1. searchParamsA를 searchParamsA 안의 item pair 중에서 variationConfig의 vary params가 pair[0]을 포함하는 것들만 담은 리스트로 설정한다.¶

    2. searchParamsB를 searchParamsB 안의 item pair 중에서 variationConfig의 vary params가 pair[0]을 포함하는 것들만 담은 리스트로 설정한다.¶

  8. variationConfig의 vary on key order가 false이면:¶

    1. keyLessThan을 두 pair (keyA, valueA) 및 (keyB, valueB)를 입력으로 받아 keyA가 code unit less than [WHATWG-INFRA] keyB인지 여부를 반환하는 알고리즘으로 둔다.¶

    2. searchParamsA를 keyLessThan을 사용하여 오름차순으로 sorting [WHATWG-INFRA]한 searchParamsA의 결과로 설정한다.¶

    3. searchParamsB를 keyLessThan을 사용하여 오름차순으로 sorting [WHATWG-INFRA]한 searchParamsB의 결과로 설정한다.¶

  9. searchParamsA의 size가 searchParamsB의 size와 같지 않으면 false를 반환한다.¶

  10. i를 0으로 둔다.¶

  11. i < searchParamsA의 size인 동안:¶

    1. searchParamsA[i][0]이 searchParamsB[i][0]과 같지 않으면 false를 반환한다.¶

    2. searchParamsA[i][1]이 searchParamsB[i][1]과 같지 않으면 false를 반환한다.¶

    3. i를 i + 1로 설정한다.¶

  12. true를 반환한다.¶

6.1. 예제

application/x-www-form-urlencoded parser가 query string을 canonicalize하는 방식 때문에, 명백히 equivalent해 보이지 않는 query string이 파싱 후에는 equivalent로 취급되는 경우가 있다.¶

따라서 예를 들어 "No-Vary-Search" 응답 헤더 필드에 No-Vary-Search: key-order와 같이 기본값이 아닌 값을 지정하면 다음과 같은 동등 관계가 성립한다.¶

표 4
첫 번째 Query 두 번째 Query 설명
null ? null query는 빈 문자열과 동일하게 파싱된다
?a=x ?%61=%78 파싱은 percent-decoding을 수행한다
?a=é ?a=%C3%A9 파싱은 percent-decoding을 수행한다
?a=%f6 ?a=%ef%bf%bd 두 값 모두 U+FFFD (�)로 파싱된다

7. 캐싱

캐시 [HTTP-CACHING]가 이 명세를 구현한다면, [HTTP-CACHING]의 Section 4에 있는 제시된 대상 URI 요구 사항:¶

제시된 대상 URI([HTTP]의 Section 7.1)와 저장된 응답의 대상 URI가 일치하고,¶

는 다음으로 대체됩니다.¶

제시된 대상 URI([HTTP]의 Section 7.1)와 저장된 응답의 대상 URI가 일치하거나 URL variation config를 모듈로 하여 동등하고,¶

캐시 구현은 다음과 같은 응답을 더 최근에 저장한 경우, target URI가 URL variation config를 모듈로 해서만 일치하는 저장된 응답을 재사용하지 않을 수 있습니다.¶

  • 쿼리를 제외한 대상 URI가 제시된 대상 URI와 같고,¶

  • "No-Vary-Search" 응답 헤더 필드에 비어 있지 않은 값이 있으며,¶

  • "No-Vary-Search" 응답 헤더 필드 값이 재사용 대상으로 고려 중인 저장된 응답의 값과 다르다.¶

일반적으로 캐시는 저장된 응답을 재사용할 의무가 없다. 그러나 위 내용은 성능 또는 기타 이유로 유리한 경우 캐시가 더 적은 수의 저장된 응답을 검색할 수 있도록 명시적으로 허용한다.¶

즉, 캐시는 주어진 경로명에 대해 둘 이상의 응답을 저장할 수 있으므로, 캐시된 모든 응답에 접근하지 않고도 "No-Vary-Search" 응답 헤더 필드 값을 효율적으로 조회할 방법이 필요하다. 이러한 캐시는 [HTTP-CACHING]의 4절에 있는 다른 조건을 확인하기 전에 저장된 응답을 효율적으로 식별하기 위해 다음과 같은 단계를 수행할 수 있다.¶

  1. exactMatch를 cache[presentedTargetURI]로 둔다. 재사용할 수 있는 저장된 응답이면 이를 반환한다.¶

  2. targetPath를 쿼리 매개변수를 제거한 presentedTargetURI로 둔다.¶

  3. lastNVS를 mostRecentNVS[targetPath]로 둔다. 존재하지 않으면 null을 반환한다.¶

  4. simplifiedURL을 lastNVS에 따라 presentedTargetURI를 단순화한 결과로 둔다(중요하지 않은 쿼리 매개변수를 제거하고, 키 순서를 무시해야 하는 경우 매개변수를 키를 기준으로 오름차순으로 정렬한다 [WHATWG-INFRA]).¶

  5. nvsMatch를 cache[simplifiedURL]로 둔다. 존재하지 않으면 null을 반환한다. (정확한 URL뿐만 아니라 이 값도 캐시에 저장할 때 기록되었다고 가정한다.)¶

  6. nvsMatch에서 variationConfig를 획득한다(5.2절).¶

  7. variationConfig가 주어졌을 때 nvsMatch의 대상 URI와 presentedTargetURI가 URL 변형 구성에 따라 동등하지 않으면(6절) null을 반환한다.¶

  8. nvsMatch가 재사용할 수 있는 저장된 응답이면 이를 반환한다. 그렇지 않으면 null을 반환한다.¶

캐시 구현의 효율성을 높이기 위해 서버는 시간이 지나면서 주어진 경로명에 대한 요청에 응답할 때 쿼리 구성 요소의 처리 방식을 업데이트해야 하는 경우가 아니라면 "No-Vary-Search" 응답 헤더 필드에 서로 다른 비어 있지 않은 값을 전송하지 않는 것이 좋다. 그렇게 하면 위와 같은 전략을 사용하는 캐시 구현이 원래 재사용할 수 있었던 일부 저장된 응답을 찾지 못하게 된다.¶

8. 보안 고려 사항

주의해야 할 주요 위험은 일치하지 않는 URL의 영향이다. 특히 이로 인해 사용자가 링크 위에 마우스를 올렸을 때 표시된 URL이나 URL 표시줄에 표시된 URL과 다른 URL에서 원래 가져온 응답을 보게 될 수 있다.¶

이 필드를 잘못 구성하면 캐시 오염이나 데이터 유출 위험이 심화될 수 있다. 매개변수를 무시함으로써 응답을 안전하게 재사용하는 데 필요한 서버 처리를 우회하게 되는 경우에는 해당 매개변수를 무시해서는 안 된다. 여기에는 권한 부여, 사용자 식별, 서명 검증, 사용자 동의, 라우팅, 감사, 철회 또는 기타 보안에 민감한 작업에 사용되는 매개변수가 포함된다.¶

그러나 그 영향은 쿼리 매개변수로 제한되므로 관련 보안 경계인 출처([ORIGIN])를 넘지 않는다. (웹 브라우저 보안 UI의 관점에서 본 호스트도 참조한다. [WHATWG-URL]) 실제로 출처는 이미 URL과 응답 본문을 표시하는 방식을 완전히 제어할 수 있으며, 여기에는 history.replaceState() 또는 서비스 워커와 같은 기술을 통한 클라이언트 측 제어도 포함된다.¶

9. 개인정보 보호 고려 사항

이 제안은 사용자 식별자를 전달하기 위해 query parameters를 자주 사용하는 탐색 추적이라는 개인정보 보호와 매우 관련이 큰 영역에 인접해 있습니다. 그러나 우리는 이 제안 자체에는 개인정보 보호 영향이 없다고 봅니다. 이는 기존 탐색 추적 완화나 현재 검토 중인 알려진 미래의 완화책을 방해하지 않습니다. 실제로 어떤 페이지가 URI에 사용자 식별자를 인코딩한다면, 이 제안이 제공하는 유일한 능력은 서버가 캐시를 우회하지 않고 캐시가 서버를 대신하게 하여 그러한 사용자 ID의 서버 처리를 방지함으로써 사용자 추적을 줄이는 것입니다. [NAV-TRACKING-MITIGATIONS]¶

그러나 사용자 신원 또는 비공개 상태와 관련된 매개변수를 잘못 무시하는 부정확한 구성은 한 사용자를 위한 캐시된 콘텐츠를 다른 사용자에게 노출할 수 있다. 이러한 실수는 표준 캐싱에서도 발생할 수 있지만, "No-Vary-Search" 응답 헤더 필드는 그러한 잘못된 구성의 가능성을 확대하므로 출처가 쿼리 매개변수를 정확하게 분류하는 것이 매우 중요하다.¶
