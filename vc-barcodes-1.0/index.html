초록

이 명세는 운전면허증(PDF417) 및 여행 문서(MRZ)에서 발견되는 것과 같은 데이터를 검증 가능한 자격 증명[VC-DATA-MODEL-2.0]을 사용하여 인코딩하는 메커니즘을 설명한다. 검증 가능한 자격 증명 표현은 150바이트 미만에 들어갈 만큼 충분히 압축되어 있으며 따라서 표준 인쇄 공정을 사용해 실물 카드에 인쇄되는 기존의 2차원 바코드와 통합될 수 있다.

                  1. 소개

                  운전면허증, 여권, 여행 자격과 같은 실물 자격 증명에는 문서에서 정보를 빠르게 읽는 데 사용할 수 있는 기계 판독 가능 데이터가 자주 포함된다. 이 정보는 PDF417 [ISO15438-2015], 기계 판독 구역(MRZ) [ICAO9303-3], 및 1차원 또는 2차원 "막대" 형식으로 구성된 기타 광학 스캔 가능 코드와 같은 형식으로 인코딩되며, 따라서 "바코드"라는 용어를 사용한다. 정보를 검증 가능한 자격 증명으로 인코딩한다는 것은 데이터가 변조 징후를 갖는다는 의미다. 널리 사용 가능한 바코드 생성 및 스캔 라이브러리 덕분에 누구나 이러한 바코드를 배포하고 사용하는 것이 상당히 간단하다.

                  따라서 이러한 바코드의 발급자가 바코드에 포함된 정보뿐 아니라 바코드를 생성한 주체를 보호할 수 있도록 하는 것이 유용하다.

                  검증 가능한 자격 증명 데이터 모델 v2.0 명세는 운전면허증이나 여행 문서에 있는 정보와 같은 자격 증명 정보를 표현하기 위한 전역 표준을 제공한다. 검증 가능한 자격 증명 데이터 무결성 1.0 명세는 자격 증명 정보를 보호하기 위한 전역 표준을 제공한다. 이 두 명세를 결합하면 자격 증명이 변조되는 것을 방지하고, 자격 증명의 작성 주체를 표현하며, 개인정보를 보호하는 방식으로 자격 증명의 현재 상태를 제공하는 수단을 얻을 수 있다. 그러나 이러한 데이터 형식은 광학 바코드로 표현하기에는 대체로 너무 크다.

                  링크드 데이터용 컴팩트 바이너리 객체 표현 v1.0 명세는 보호된 검증 가능한 자격 증명을 해당 정보를 광학 바코드로 표현하거나 광학 바코드에 내장하는 것이 가능해질 정도로 압축하는 수단을 제공한다.

                  이 명세는 운전면허증(PDF417)이나 여행 문서(MRZ)에서 볼 수 있는 것과 같은 광학 바코드 또는 기타 스캔 가능한 요소에 인코딩된 데이터를 검증 가능한 자격 증명 [VC-DATA-MODEL-2.0]을 사용하여 바코드의 대상에 관한 정보 또는 바코드 자체에 관한 정보를 표현함으로써 변조 징후가 드러나게 만드는 메커니즘을 설명한다. 다음으로 이 검증 가능한 자격 증명은 데이터 무결성 [VC-DATA-INTEGRITY]으로 보호되고, 이어서 CBOR-LD [CBOR-LD]를 사용해 압축된다.

                  검증 가능한 자격 증명을 사용하여 바코드의 내용을 보호하는 주요 메커니즘은 두 가지다:

                  • 검증 가능한 자격 증명을 포함하는 바코드는 현재 바코드가 없는 실물 문서(새 문서 포함)에 추가될 수 있다. 바코드 내부의 검증 가능한 자격 증명에는 문서의 데이터 일부 또는 전체가 포함될 수 있다. 이 사용 사례에서 바코드는 일반적으로 검증 가능한 자격 증명만 포함한다.
                  • 문서에 이미 바코드가 있는 경우, 보안을 강화하기 위해 해당 바코드를 보안이 향상된 검증 가능한 자격 증명을 포함하는 새 바코드로 교체할 수 있다. 이 시나리오에서 새롭게 보강된 바코드는 원래 바코드의 정보와 다른 정보에 대해 디지털 서명을 수행하는 새로 추가된 검증 가능한 자격 증명을 모두 포함할 것으로 예상된다.

                  두 사용 사례 모두 검증 가능한 자격 증명으로 보호되는 데이터에 대해 진위성, 무결성, 변조 저항성을 달성한다. 또한 필요한 사용 사례의 경우, 이러한 검증 가능한 자격 증명은 바코드별로 폐기(revoke)되거나 일시 중지(suspend)될 수 있다.

                  1.2 설계 목표

                  다음은 이 명세에 포함된 기술의 설계 목표입니다.

                  • 진위성: 검증에 성공한 검증 가능한 자격 증명 바코드는 명시된 발급 기관에서 생성되었음이 보장됩니다.
                  • 무결성: 검증에 성공한 검증 가능한 자격 증명 바코드가 있는 문서의 데이터는 해당 데이터가 바코드로 보호되는 한 수정되지 않았음이 보장됩니다.
                  • 실시간 상태: 검증 가능한 자격 증명 바코드를 검증하면 문서가 폐기되거나 정지되지 않았음을 증명하며, 이는 개인정보를 침해하는 신뢰할 수 있는 원본 데이터베이스로의 "전화 확인" 없이 수행됩니다.
                  • 단순성: 검증 가능한 자격 증명 바코드는 문서에 있는 기존의 광학 바코드(예: 운전면허증 뒷면의 PDF417)를 재사용하거나 쉽게 사용할 수 있는 형식(예: QR 코드)으로 새 바코드를 추가합니다.
                  • 적합성: 검증 가능한 자격 증명 바코드 기술 스택은 국제 표준 및 표준화 절차 중인 기술과 일치합니다.

                  2.1 OpticalBarcodeCredential

                  OpticalBarcodeCredential은 1. 작성자 정보, 2. 변조 방지, 3. 선택적으로 폐기 및 정지 상태를 제공하는 방식으로 광학 바코드의 내용을 보호하는 데 사용됩니다. 다시 말해, 자격 증명을 통해 광학 바코드를 누가 발급했는지, 처음 발급된 이후 광학 바코드가 변조되었는지, 그리고 광학 바코드의 발급자가 해당 문서가 여전히 유효하다고 보증하는지 여부를 알 수 있습니다. 이러한 기능은 물리적 문서에 상당한 사기 방지 보호를 제공합니다.

                  OpticalBarcodeCredential의 credentialSubject 유형은 검증 가능한 자격 증명 자체에 표현된 정보 외에도, 검증 가능한 자격 증명으로 보호되는 물리적 문서의 기계 판독 가능 데이터 종류를 식별합니다. 이 명세는 OpticalBarcodeCredential과 함께 사용되는 모든 credentialSubject 유형의 상위 클래스 역할을 하는 일반 유형 MachineReadableInformation을 정의합니다. 이 명세의 주요 부분에서는 하나의 구체적인 하위 클래스인 MachineReadableZone(섹션 2.1.1 MachineReadableZone 참조)을 정의하며, 이는 검증 가능한 자격 증명이 물리적 문서의 기계 판독 영역을 보호함을 나타냅니다. 부록에는 두 개의 추가 하위 클래스인 AamvaDriversLicenseScannableInformation(규범적인 부록 A. AAMVA 운전면허증 및 신분증 문서 참조)과 IsoDrivingLicenceMachineReadableInformation(정보 제공용 부록 B. ISO 준수 운전면허증 참조)이 정의되어 있습니다. 다른 명세에서는 출생증명서나 교육 증명서의 PDF417 바코드와 같은 다른 종류의 기계 판독 가능 데이터를 자격 증명이 보호한다는 것을 나타내는 추가 credentialSubject 유형을 정의할 수 있습니다(MAY).

                  이 명세 또는 다른 명세에서 정의되었는지와 관계없이 OpticalBarcodeCredential과 함께 사용되는 모든 credentialSubject 유형은 MachineReadableInformation의 하위 클래스로 정의되어야 합니다(MUST). MachineReadableInformation 값은 더 구체적인 하위 클래스 값과 함께 credentialSubject의 type 배열에 포함될 수 있습니다(MAY). 특정 하위 클래스를 인식하지 못하는 프로세서는 상위 클래스 값을 사용하여 credentialSubject가 검증 가능한 자격 증명으로 보호된 기계 판독 가능 데이터를 설명한다는 것을 판단할 수 있습니다.

                  이 명세 또는 다른 명세에서 정의되는 새로운 credentialSubject 유형은 섹션 3. 알고리즘의 알고리즘과 함께 사용하려면 다음 사항을 모두 정의해야 합니다(MUST).

                  • 해당 유형의 자격 증명이 보호하는 물리적 문서의 기계 판독 가능 광학 데이터 (예: PDF417 바코드, 기계 판독 영역)
                  • 구성 요소 추출 규칙, 즉 섹션 3.2.4.4 opticalDataBytes 생성의 알고리즘에서 사용하기 위해 광학 데이터의 보호된 구성 요소를 문자열 목록으로 추출하는 방법
                  • 추출된 구성 요소를 결정론적 목록으로 정렬하는 데 사용되는 순서 규칙 (유형에서 순서 규칙을 정의하지 않은 경우 섹션 3.2.4.4 opticalDataBytes 생성에 설명된 대로 유니코드 코드 포인트 순서를 사용)
                  • 광학 데이터의 구성 요소 중 일부만 디지털 서명되는 경우 protectedComponentIndex 속성의 사용 방법. 여기에는 비트 문자열의 길이, 모든 패딩 비트의 값 및 각 비트가 참조하는 결정론적 구성 요소 목록이 포함됩니다.
                  • 섹션 2.3 바코드로의 인코딩 및 바코드로부터의 디코딩에 설명된 대로, 해당 유형의 CBOR-LD 인코딩 자격 증명을 바코드에 삽입하는 데 사용되는 문자 인코딩

                  지역별 바코드 데이터 모델을 보호하기 위해 이러한 추가 유형을 정의하는 방법의 예제는 부록 A. AAMVA 운전면허증 및 신분증 문서에서 확인할 수 있습니다. 이 부록은 AAMVA 준수 운전면허증과 신분증의 PDF417 바코드에 검증 가능한 자격 증명 바코드를 추가하는 방법을 규범적으로 정의합니다.

                  OpticalBarcodeCredential로 보호되는 기계 판독 가능 데이터가 개별 구성 요소(예: PDF417 바코드의 개별 필드)로 구성되고 해당 구성 요소 중 일부만 디지털 서명되는 경우, credentialSubject는 protectedComponentIndex 속성을 사용하여 보호되는 구성 요소를 표현합니다. protectedComponentIndex의 값은 multibase-base64url로 인코딩된 비트 문자열입니다. 비트 문자열의 위치 i에 있는 각 비트는 연결된 credentialSubject 유형에 대해 정의된 결정론적 구성 요소 목록에서 인덱스 i에 있는 구성 요소에 대응합니다. 위치 i의 비트가 1이면 결정론적 구성 요소 목록의 위치 i에 있는 구성 요소가 디지털 서명으로 보호됩니다. 비트가 0이면 해당 구성 요소는 보호되지 않습니다. 구성 요소에 대응하지 않는 비트 문자열 끝의 모든 패딩 비트는 0으로 설정해야 합니다(MUST). 디지털 서명을 생성하고 검증할 때 protectedComponentIndex를 사용하는 방법에 대한 자세한 내용은 섹션 3.2.4.4 opticalDataBytes 생성을 참조하십시오.

                  2.1.1 MachineReadableZone

                  MachineReadableZone 유형의 credentialSubject는 검증 가능한 자격 증명이 물리적 문서의 기계 판독 영역(MRZ) [ICAO9303-3]을 보호함을 나타냅니다. MachineReadableZone은 MachineReadableInformation의 하위 클래스입니다. 기계 판독 영역의 모든 행이 보호되므로 이 유형에는 protectedComponentIndex 속성이 필요하지 않습니다.

                  구현자는 CBOR-LD로 인코딩된 MachineReadableZone 자격 증명을 QR 코드로 인코딩하기 전에 문자열 'VC1-'을 앞에 추가한 base45-multibase로 다시 인코딩해야 합니다(REQUIRED).

                  2.2 TerseBitstringStatusListEntry

                  TerseBitstringStatusListEntry는 비트 문자열 상태 목록 v1.0 명세에 정의된 BitstringStatusListEntry의 압축 표현입니다.

                  TerseBitstringStatusListEntry 유형의 객체에는 두 개의 추가 속성이 있어야 합니다(MUST).

                  • terseStatusListBaseUrl은 이 자격 증명과 연결된 상태 목록의 위치를 식별합니다. terseStatusListBaseUrl은 URL [URL]이어야 합니다(MUST).
                  • terseStatusListIndex는 위 URL에 있는 개별 상태를 지정합니다. terseStatusListIndex는 32비트 부호 없는 정수로 표현할 수 있어야 합니다(MUST).

                  TerseBitstringStatusListEntry를 처리하려면 섹션 3.2.3.1 TerseBitstringStatusListEntry에서 BitstringStatusListEntry로의 알고리즘을 적용하여 BitstringStatusListEntry로 변환한 다음, 비트 문자열 상태 목록 v1.0에 따라 처리합니다.

                  구현자는 개별 상태 목록의 길이에 해당하는 listLength 값을 설정해야 합니다. 그러면 32비트 terseStatusListIndex에 대해 상태 목록의 수는 listCount = 2^32 / listLength가 됩니다. TerseBitstringStatusListEntry에서 BitstringStatusListEntry로 변환하려면 listLength가 필요합니다. 일부 listLength 값은 이러한 상태 목록의 개인정보 보호 속성을 훼손할 수 있으므로 구현은 listLength = 2^26 및 listCount = 2^6을 사용해야 합니다(MUST).

                  2.3 바코드로의 인코딩 및 바코드로부터의 디코딩

                  이 명세의 자격 증명은 CBOR-LD를 사용하여 검증 가능한 자격 증명을 바이너리 형식으로 효율적으로 인코딩하지만, 바이너리 데이터를 표준 바코드 이미지 형식으로 직접 변환하는 것은 비효율적이거나 호환되지 않는 경우가 많습니다. 이를 위해 구현에 대한 문자 인코딩 요구 사항이 유형별로 제공되며, 일반적으로 대상 바코드 형식에 따라 달라집니다.

                  각 credentialSubject 유형은 해당 유형의 CBOR-LD 인코딩 자격 증명을 바코드에 배치하기 전에 문자 인코딩하는 방법을 지정해야 합니다. MachineReadableZone의 문자 인코딩 요구 사항은 섹션 2.1.1 MachineReadableZone에 제공됩니다. 다른 유형에 대한 요구 사항은 해당 유형을 정의하는 명세 또는 부록에 제공됩니다 (예: 부록 A. AAMVA 운전면허증 및 신분증 문서와 부록 B. ISO 준수 운전면허증).

                  3. 알고리즘

                  다음 절에서는 운전면허증 및 여행 문서와 같은 물리적 매체에 있는 바코드와 기계 판독 영역 등의 광학 정보를 보호하는 디지털 증명을 추가하고 검증하는 알고리즘을 설명합니다.

                  3.1 일반 알고리즘

                  이 절에는 검증 가능한 자격 증명의 인코딩 및 디코딩에 일반적으로 적용되는 알고리즘이 포함되어 있습니다.

                  3.1.1 VC를 QR 코드로 인코딩

                  다음 알고리즘은 검증 가능한 자격 증명을 QR 코드로 표현할 수 있는 텍스트 문자열로 인코딩하는 방법을 지정합니다. 필수 입력은 검증 가능한 자격 증명(맵 inputDocument)과 옵션 집합(맵 options)입니다. 출력은 인코딩된 검증 가능한 자격 증명(문자열) 또는 오류입니다. 이 알고리즘이 문자열을 인코딩할 때마다 UTF-8 인코딩을 사용해야 합니다(MUST).

                  1. typeTable을 options.typeTable의 값으로 설정합니다.
                  2. registryEntryId를 options.registryEntryId의 값으로 설정합니다.
                  3. inputDocument, typeTable 및 registryEntryId를 입력으로 전달하여 JSON-LD에서 CBOR-LD로의 인코딩 알고리즘을 실행한 결과를 cborldDocument로 설정합니다. 인코딩 오류가 발생하면 오류를 발생시켜야 합니다(MUST).
                  4. cborldDocument를 bytes로, 정수 45를 targetBase로, 0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZ $%*+-./:를 baseAlphabet으로 전달하여 Base 인코딩 알고리즘을 실행한 결과를 base45Value로 설정합니다.
                  5. 다음 값을 연결한 결과를 qrCodeText로 설정합니다. VC1-, R(base45용 Multibase 접두사), 그리고 base45Value.
                  6. qrCodeText를 인코딩된 검증 가능한 자격 증명으로 반환합니다. 이 값은 QR 코드 이미지로 인코딩할 텍스트로 모든 QR 코드 라이브러리에 제공할 수 있습니다.

                  3.1.2 QR 코드를 VC로 디코딩

                  다음 알고리즘은 QR 코드로 인코딩된 검증 가능한 자격 증명을 디코딩하는 방법을 지정합니다. 필수 입력은 텍스트 문자열 (문자열 inputDocument)과 옵션 집합(맵 options)입니다. 출력은 검증 가능한 자격 증명(맵) 또는 오류입니다. 이 알고리즘이 문자열을 인코딩할 때마다 UTF-8 인코딩을 사용해야 합니다(MUST).

                  1. inputDocument가 텍스트 VC1-R로 시작하는지 확인합니다. 그렇지 않으면 오류를 발생시켜야 합니다(MUST).
                  2. inputDocument에서 처음 다섯 문자(VC1-R)를 제거한 값을 base45Value로 설정합니다.
                  3. base45Value를 sourceEncoding으로, 정수 45를 sourceBase로, 0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZ $%*+-./:를 baseAlphabet으로 전달하여 Base 디코딩 알고리즘을 실행한 결과를 cborldDocument로 설정합니다.
                  4. cborldDocument를 입력으로 전달하여 CBOR-LD에서 JSON-LD로의 디코딩 알고리즘을 실행한 결과를 jsonldDocument로 설정합니다. 디코딩 오류가 발생하면 오류를 발생시켜야 합니다(MUST).
                  5. jsonldDocument를 디코딩된 검증 가능한 자격 증명으로 반환합니다.

                  3.2 OpticalBarcodeCredential 알고리즘

                  이 절에는 type이 OpticalBarcodeCredential인 검증 가능한 자격 증명의 인코딩 및 디코딩에 특화된 알고리즘이 포함되어 있습니다. 이는 일반적으로 문서의 기존 기계 판독 가능 정보에 검증 가능한 자격 증명을 추가하는 사용 사례에서 나타납니다.

                  3.2.1 OpticalBarcodeCredential 인코딩

                  1. opticalData를 보호할 광학 바코드의 데이터로 설정합니다.
                  2. issuerUrl을 발급자가 자격 증명 검증에 사용하려는 URL로 설정합니다.
                  3. unsignedCredential.issuer가 issuerUrl로 설정된 OpticalBarcodeCredential을 unsignedCredential로 설정합니다.
                  4. 자격 증명 상태가 필요한 경우:
                    1. statusListEntry를 발급자가 OpticalBarcodeCredential에 추가하려는 BitstringStatusListEntry (비트 문자열 상태 목록 v1.0 명세에 정의됨)로 설정합니다.
                    2. statusListEntry에 섹션 3.2.3.2 BitstringStatusListEntry에서 TerseBitstringStatusListEntry로의 알고리즘을 적용한 결과를 unsignedCredential.credentialStatus로 설정합니다.
                  5. opticalData와 unsignedCredential에 서명하기 위해 3.2.4.1 증명 추가 (ecdsa-xi-2023)의 알고리즘을 사용한 결과를 signedCredential로 설정합니다.
                  6. CBOR-LD [CBOR-LD]를 사용하여 signedCredential을 인코딩하고, 원하는 credentialSubject.type 값 및 사용 사례의 처리 규칙에 따라 opticalData의 지정된 영역에 추가합니다.

                  3.2.2 OpticalBarcodeCredential 디코딩

                  1. opticalData를 물리적 문서에서 스캔한 기계 판독 가능 데이터 (예: PDF417 또는 MRZ 데이터)로 설정합니다.
                  2. vcbPayload를 opticalData의 지정된 영역에서 추출한 검증 가능한 자격 증명 페이로드로 설정합니다.
                  3. 자격 증명 유형 및 바코드 형식과 연결된 문자 인코딩에서 vcbPayload를 디코딩한 결과를 cborldBytes로 설정하고, multibase 헤더가 있는 경우 제거합니다(섹션 2.3 바코드로의 인코딩 및 바코드로부터의 디코딩 참조).
                  4. 페이로드가 CBOR-LD로 압축된 경우 cborldBytes에 CBOR-LD 압축 해제 [CBOR-LD]를 적용한 결과인 OpticalBarcodeCredential을 credential로 설정합니다. 그렇지 않으면 cborldBytes로 표현된 OpticalBarcodeCredential을 credential로 설정합니다.
                  5. credential과 opticalData에 섹션 3.2.4.2 증명 검증 (ecdsa-xi-2023)의 알고리즘을 적용한 결과를 verificationResult로 설정합니다.
                  6. statusResult를 null로 설정합니다. credential.credentialStatus가 있는 경우:
                    1. credential에 섹션 3.2.3.1 TerseBitstringStatusListEntry에서 BitstringStatusListEntry로의 알고리즘을 적용한 결과를 statusListEntry로 설정합니다.
                    2. statusListEntry에 비트 문자열 상태 목록 v1.0: 검증 알고리즘을 적용한 결과를 statusResult로 설정합니다.
                  7. (verificationResult, statusResult)를 반환합니다.

                  3.2.3 상태 목록 항목 변환

                  이 절의 알고리즘은 TerseBitstringStatusListEntry와 BitstringStatusListEntry 간의 변환에 사용됩니다. 섹션 3.2.3.2 BitstringStatusListEntry에서 TerseBitstringStatusListEntry로의 알고리즘은 OpticalBarcodeCredential을 인코딩할 때 자격 증명에 서명하기 전에 BitstringStatusListEntry를 TerseBitstringStatusListEntry로 압축하는 데 사용됩니다. 섹션 3.2.3.1 TerseBitstringStatusListEntry에서 BitstringStatusListEntry로의 알고리즘은 반대 방향의 변환을 수행하며, 검증 과정에서 검증 가능한 자격 증명에 대한 검증이 수행된 후 사용됩니다.

                  3.2.3.1 TerseBitstringStatusListEntry에서 BitstringStatusListEntry로

                  검증 가능한 자격 증명 검증이 수행된 후, 이 알고리즘은 OpticalBarcodeCredential 검증 가능한 자격 증명(구조체 vc), vc와 연결된 BitstringStatusListCredential의 항목 수를 포함하는 정수 listLength, 그리고 문자열 statusPurpose (예: 'revocation', 'suspension'...)를 입력으로 받아 'BitstringStatusListEntry' 객체를 반환합니다.

                  1. result를 비어 있는 맵으로 설정합니다.
                  2. listIndex를 vc.credentialStatus.terseStatusListIndex/listLength를 다음으로 낮은 정수까지 내림한 값(즉, floor() 연산을 적용한 값)으로 설정합니다.
                  3. statusListIndex를 vc.credentialStatus.terseStatusListIndex % listLength로 설정합니다.
                  4. 다음 값을 연결한 결과를 result.statusListCredential로 설정합니다. vc.credentialStatus.terseStatusListBaseUrl, '/', statusPurpose, '/', listIndex.
                  5. result.type을 'BitstringStatusListEntry'로 설정합니다.
                  6. result.statusListIndex를 statusListIndex로 설정합니다.
                  7. result.statusPurpose를 statusPurpose로 설정합니다.
                  8. result를 반환합니다.

                  result는 비트 문자열 상태 목록 v1.0 명세의 검증 알고리즘에 대한 입력으로 사용할 수 있습니다.

                  3.2.3.2 BitstringStatusListEntry에서 TerseBitstringStatusListEntry로

                  이 알고리즘은 statusListCredential 값이 terseStatusListBaseUrl, '/', statusPurpose, '/', listIndex 형식의 URL일 것으로 예상되는 BitstringStatusListEntry(구조체 statusListEntry)와, 발급자가 게시하는 각 BitstringStatusListCredential의 항목 수를 포함하는 정수 listLength를 입력으로 받아 'TerseBitstringStatusListEntry' 객체를 반환합니다.

                  1. result를 비어 있는 맵으로 설정합니다.
                  2. listIndex를 statusListEntry.statusListCredential의 마지막 경로 세그먼트를 정수로 표현한 값으로 설정합니다.
                  3. terseStatusListBaseUrl을 statusListEntry.statusListCredential에서 마지막 두 경로 세그먼트(즉, '/', statusPurpose, '/', listIndex)를 제거한 값으로 설정합니다.
                  4. result.type을 'TerseBitstringStatusListEntry'로 설정합니다.
                  5. result.terseStatusListBaseUrl을 terseStatusListBaseUrl로 설정합니다.
                  6. result.terseStatusListIndex를 listIndex * listLength + statusListEntry.statusListIndex의 정수 표현으로 설정합니다.
                  7. result를 반환합니다.
                  참고: 상태 목적은 압축 항목에 포함되지 않습니다.

                  TerseBitstringStatusListEntry는 원래 BitstringStatusListEntry의 statusPurpose를 표현하지 않습니다. 대신 statusPurpose는 검증자가 섹션 3.2.3.1 TerseBitstringStatusListEntry에서 BitstringStatusListEntry로의 알고리즘에 대한 입력으로 제공합니다. 이 알고리즘은 검증 중에 BitstringStatusListEntry를 다시 구성합니다.

                  참고: 상태 목록은 선택 사항입니다.

                  모든 발급자가 자신의 검증 가능한 자격 증명에 대한 상태 목록 정보를 게시하는 것은 아니라는 점에 구현자는 유의하는 것이 좋습니다. 일부 발급자는 검증자가 상태 목록 자격 증명에 접근하도록 허용하기 전에 권한 부여를 요구할 수 있습니다.

                  3.2.4 ecdsa-xi-2023

                  ecdsa-xi-2023 암호 스위트는 실질적으로 ecdsa-rdfc-2019 알고리즘 [VC-DI-ECDSA]에 원래 광학 바코드 데이터와 같은 일부 "추가 정보"(xi)를 입력으로 받아 해당 데이터를 디지털 서명으로 보호되는 정보에 포함하는 단계가 추가된 것입니다. 이 절의 알고리즘은 이러한 서명을 생성하고 검증하는 방법을 자세히 설명합니다.

                  3.2.4.1 증명 추가 (ecdsa-xi-2023)

                  증명을 생성하려면 데이터 무결성 [VC-DATA-INTEGRITY] 명세의 섹션 4.1: 증명 추가에 있는 알고리즘을 실행해야 합니다(MUST). 해당 알고리즘에서 암호 스위트별 변환 알고리즘은 데이터 무결성 ECDSA 암호 스위트 v1.0의 변환(ecdsa-rdfc-2019) 절에 정의되어 있고, 해싱 알고리즘은 섹션 3.2.4.3 해싱 (ecdsa-xi-2023)에 정의되어 있으며, 증명 직렬화 알고리즘은 데이터 무결성 ECDSA 암호 스위트 v1.0의 증명 직렬화(ecdsa-rdfc-2019) 절에 정의되어 있습니다.

                  3.2.4.2 증명 검증 (ecdsa-xi-2023)

                  증명을 검증하려면 데이터 무결성 [VC-DATA-INTEGRITY] 명세의 섹션 4.2: 증명 검증에 있는 알고리즘을 실행해야 합니다(MUST). 해당 알고리즘에서 암호 스위트별 변환 알고리즘은 데이터 무결성 ECDSA 암호 스위트 v1.0의 변환(ecdsa-rdfc-2019) 절에 정의되어 있고, 해싱 알고리즘은 섹션 3.2.4.3 해싱(ecdsa-xi-2023)에 정의되어 있으며, 증명 검증 알고리즘은 데이터 무결성 ECDSA 암호 스위트 v1.0의 증명 검증(ecdsa-rdfc-2019) 절에 정의되어 있습니다.

                  3.2.4.3 해싱(ecdsa-xi-2023)

                  해싱 알고리즘은 아래에 설명된 광학 데이터 해싱이 추가된 데이터 무결성 ECDSA 암호 스위트 v1.0 명세의 해싱(ecdsa-rdfc-2019) 절에 정의된 알고리즘입니다. 구현은 기계 판독 가능 광학 데이터(PDF417 또는 MRZ 데이터)를 이 해싱 알고리즘에서 사용할 수 있도록 제공한다고 가정합니다.

                  이 알고리즘에 필요한 입력은 변환된 데이터 문서 (transformedDocument), 정규 증명 구성 (canonicalProofConfig) 및 광학 데이터 (opticalDataBytes)입니다. 출력으로 바이트 시퀀스로 표현된 하나의 해시 데이터 값이 생성됩니다.

                  해싱 알고리즘은 데이터 무결성 ECDSA 암호 스위트 v1.0의 해싱(ecdsa-rdfc-2019) 절에 정의된 알고리즘에서 3단계를 다음 두 단계로 대체한 것입니다.

                  1. opticalDataHash를 hashData에 적용한 것과 동일한 해시 알고리즘을 opticalDataBytes 값에 적용한 결과로 설정합니다.
                  2. hashData를 proofConfigHash(첫 번째 해시), transformedDocumentHash(두 번째 해시) 및 opticalDataHash(세 번째 해시)를 결합한 결과로 설정합니다.
                  3.2.4.4 opticalDataBytes 생성

                  이 절의 알고리즘은 디지털 서명이 생성되거나 검증되는 광학 데이터 (opticalDataBytes)를 생성합니다. 이 알고리즘은 모든 종류의 기계 판독 가능 광학 데이터에 일반적으로 적용됩니다. credentialSubject의 유형은 광학 데이터의 보호된 구성 요소를 추출하는 방법을 정의하며(아래의 유형별 구성 요소 추출 절 참조), 이 알고리즘은 해당 구성 요소를 정규화하고 해싱하기 전에 결정론적 목록으로 정렬합니다.

                  이 알고리즘에 필요한 입력은 기계 판독 가능 광학 데이터 (opticalData)와 자격 증명 주체(credentialSubject)입니다. 보호된 광학 데이터의 해싱된 정규 형식을 나타내는 하나의 값이 출력으로 생성됩니다.

                  1. credentialSubject 유형과 연결된 구성 요소 추출 규칙에 따라 opticalData의 보호된 구성 요소를 문자열 배열로 추출한 결과를 dataToCanonicalize로 설정합니다. 해당 유형에 정의되어 있는 경우 credentialSubject.protectedComponentIndex를 사용합니다. MachineReadableZone의 구성 요소 추출 규칙은 섹션 구성 요소 추출: MachineReadableZone에 제공됩니다. 다른 유형의 규칙은 해당 유형을 정의하는 명세 또는 부록에 제공됩니다(예: 부록 A.2 구성 요소 추출은 부록 A. AAMVA 운전면허증 및 신분증 문서에 정의된 유형에 적용되고, 부록 B.2 구성 요소 추출은 부록 B. ISO 준수 운전면허증에 설명된 유형에 적용됩니다).
                  2. credentialSubject 유형과 연결된 순서 규칙을 사용하여 dataToCanonicalize를 결정론적 목록으로 정렬한 다음, 배열에서 하나의 문자열을 생성하도록 결합 연산을 적용한 결과를 canonicalizedData로 설정합니다. credentialSubject 유형이 순서 규칙을 정의하지 않은 경우 dataToCanonicalize를 유니코드 코드 포인트 순서로 정렬합니다.
                  3. canonicalizedData를 해싱하고 결과를 반환합니다.
                  구성 요소 추출: MachineReadableZone

                  MachineReadableZone 유형의 credentialSubject에서 opticalData는 기계 판독 영역의 데이터이며, 보호된 구성 요소는 다음과 같이 추출됩니다. 이 유형의 순서 규칙은 자격 증명에 행이 나타나는 순서입니다.

                  1. dataToCanonicalize를 빈 배열로 설정합니다.
                  2. 자격 증명의 기계 판독 영역에 있는 각 행에 대해:
                    1. mrzLine을 해당 행의 데이터를 포함하는 문자열로 설정합니다.
                    2. mrzLine의 끝에 줄 바꿈 문자를 추가하고 mrzLine을 dataToCanonicalize에 추가합니다.
                  3. dataToCanonicalize를 반환합니다.
                  3.2.4.5 증명 구성(ecdsa-xi-2023)

                  증명 구성 알고리즘은 데이터 무결성 ECDSA 암호 스위트 v1.0의 증명 구성(ecdsa-rdfc-2019) 절에 정의된 알고리즘에서 4단계를 다음 단계로 대체한 것입니다.

                  1. options.type이 DataIntegrityProof로 설정되지 않았고 proofConfig.cryptosuite가 ecdsa-xi-2023으로 설정되지 않은 경우, INVALID_PROOF_CONFIGURATION 오류를 발생시켜야 합니다(MUST).

                  4. 위협 모델

                  이 절은 비규범적이다.

                  이 절에서는 보안, 개인정보 보호, 안전 및 상호운용성 고려 사항을 포함하여 이 명세의 일반적인 위협 모델을 자세히 설명한다. 아래의 각 위협은 함께 제공되는 검증 가능한 자격 증명 바코드 위협 모델 문서에 있는 설명, 대응, 영향을 받는 시스템 요소 및 STRIDE 분류를 포함한 전체 분석으로 연결된다. 이 문서에서는 모델링된 생태계, 데이터 흐름도 및 이해관계자도 설명한다. 이 모델은 디지털 서명이 물리적 문서의 다른 기계 판독 가능 데이터를 포괄하는 OpticalBarcodeCredential 흐름과, 일반 알고리즘을 통해 바코드로 인코딩되며 디지털 서명이 자체 주장만 포괄하는 일반적인 검증 가능한 자격 증명 모두를 다룬다.

                  4.1 대상 위협

                  1. 바코드 데이터 변조 보안 — 공격자가 발급 후 물리적 문서의 기계 판독 가능 데이터를 변경하여 생년월일, 만료일 또는 문서 번호와 같은 서명된 속성을 바꾼다.
                  2. 기계 판독 가능 정보가 없는 문서의 위조 보안 — 기계 판독 가능 정보 없이 발급된 문서는 사람이 직접 검사해야만 확인할 수 있으므로 위조와 변경을 암호학적으로 탐지할 수 없다. 바코드로 인코딩된 일반적인 검증 가능한 자격 증명은 발급자의 주장을 기계로 검증할 수 있게 한다.
                  3. 위조 바코드를 통한 발급자 스푸핑 보안 — 공격자가 OpticalBarcodeCredential을 조작하여 위조 문서에 인쇄함으로써 합법적인 발급 기관에서 발급한 것처럼 보이게 한다.
                  4. 취소되거나 정지된 문서의 수락 보안 — 공격자가 문서를 사용할 수 없게 만들어야 하는 상태 변경 이후에도 해당 문서를 계속 사용하며, 상태를 실시간으로 확인할 수 없는 검증자는 이 변경을 탐지할 수 없다.

                  4.2 구현 위협

                  1. 광학 데이터 복제 안전 보안 — 진본 문서에서 복사한 서명된 바코드가 사기성 문서에서도 증명 검증을 통과하며, 특히 서명된 속성이 대략적이고 생체 정보와 결합되지 않은 경우에 그러하다.
                  2. 서명되지 않은 필드 대체 안전 보안 — 공격자가 디지털 서명의 적용을 받지 않는 바코드 필드를 수정하여 사기 탐지에 서명되지 않은 데이터를 사용하는 검증자를 속인다.
                  3. 신뢰할 수 없는 검증 소프트웨어 보안 개인정보 보호 — 악의적이거나 검토되지 않은 검증 소프트웨어가 사기성 자격 증명을 유효하다고 거짓으로 보고하거나, 실패한 검사를 숨기거나, 문서에서 읽은 개인 데이터를 유출한다.
                  4. 서명된 범위와 서명되지 않은 범위의 표시 실패 안전 — 검증 소프트웨어가 각 자격 증명의 디지털 서명이 포괄하는 범위와 포괄하지 않는 범위를 표시하지 못한다. 일반적인 검증 가능한 자격 증명의 서명은 자체 주장만 포괄하고, OpticalBarcodeCredential의 서명은 선택된 광학 데이터만 포괄하므로, 서명되지 않았거나 일치하지 않는 문서 데이터가 서명된 데이터와 동일한 수준의 신뢰를 얻게 된다.
                  5. 검증자 신뢰 앵커 구성 오류 보안 — 지나치게 광범위하거나 오래되었거나 공격자가 제공한 신뢰 저장소로 인해 검증자가 제시된 문서 유형에 대한 권한이 없는 엔터티의 자격 증명을 수락한다.
                  6. 상태 서비스의 서비스 거부 보안 — 공격자가 상태 서비스에 접근할 수 없게 만들어 검증자가 문서의 취소 또는 정지 여부를 확인하지 못하게 한다.
                  7. 과도한 캐싱으로 인한 오래된 상태 보안 개인정보 보호 — 과도하게 캐시된 상태 목록으로 인해 캐시가 채워진 후 취소된 문서가 계속 수락될 수 있다.
                  8. 불충분한 보호 구성 요소 인덱스 보안 — 바코드 필드를 너무 적게 서명한 발급자는 검증에는 성공하지만 문서 데이터 대부분을 자유롭게 수정할 수 있는 자격 증명을 생성한다.
                  9. 자격 증명 주체 유형 혼동 보안 상호운용성 — 인식되지 않는 서드 파티 유형, 더 약하게 주장된 유형 또는 일반 상위 클래스 처리 등 잘못된 credentialSubject 하위 클래스에서 처리된 자격 증명은 유형별 추출, 인코딩 및 검증 규칙을 우회한다.

                  4.3 외부 위협

                  1. 물리적 매체 정보 유출 개인정보 보호 — 예를 들어 편의점의 고해상도 비디오카메라를 통해 문서 표면에서 바코드를 보유자가 모르는 사이에 캡처할 수 있으며, 디지털 제시 방식과 달리 바코드가 인코딩한 모든 정보가 유출된다.
                  2. 상태 목록 검색을 통한 상관관계 분석 개인정보 보호 — 상태 목록의 호스트가 검증자의 검색 요청을 관찰하여 문서가 언제 어디서 확인되는지에 대한 정보를 구성할 수 있다.
                  3. 강제 제시 및 과도한 공개 개인정보 보호 — 바코드를 제시하면 선택적 공개 메커니즘 없이 바코드에 포함된 모든 서명된 속성이 공개된다.
                  4. 검증자 간 보유자 연결 개인정보 보호 — 정적인 바코드 값은 검증자가 보유자의 개별 제시를 하나의 프로필로 연결할 수 있게 하는 영구적인 상관 식별자로 작용한다.

                  4.4 종속성 위협

                  1. 암호학적으로 유의미한 양자 컴퓨터에 의한 ECDSA 해독 보안 — 암호학적으로 유의미한 양자 컴퓨터가 수명이 긴 물리적 문서를 보호하는 ECDSA 서명을 위조하며, 이미 발급된 바코드도 소급하여 위조할 수 있다.
                  2. 악성 바코드 삽입을 통한 큐싱 보안 — VCB가 예상되는 위치에 제시되지만 상호작용을 가로채도록 조작된 바코드는 검증자의 처리 파이프라인에 있는 바코드 스캐너, JSON-LD/CBOR-LD 처리기, HTTP 클라이언트 또는 암호화 하드웨어와 소프트웨어를 공격한다.
                  3. 생체 정보 위조 보안 안전 — 개인의 이미지와 같이 쉽게 복제할 수 있는 생체 데이터가 생체 검사에서 거짓 양성을 발생시킨다.
                  4. 발급자 서명 키의 침해 보안 — 발급자의 비공개 서명 키를 획득한 공격자는 진짜 자격 증명과 구별할 수 없는 유효한 자격 증명을 무제한으로 발급할 수 있다.
                  5. 키 해석 및 키 관리 스푸핑 보안 — 발급자 키가 제공되는 위치를 제어하거나 리디렉션하는 공격자는 검증자가 공격자가 서명한 자격 증명을 진짜로 검증하도록 만든다.
                  6. 기수 인코딩 및 멀티베이스 헤더 혼동 상호운용성 보안 — 문서 제조자와 검증자 사이에서 유형별 문자 인코딩 가정이 일치하지 않으면 검증된 바이트와 서명된 바이트가 달라진다.

                  A. AAMVA 운전면허증 및 신분증 문서

                  이 부록에서는 MachineReadableInformation의 하위 클래스로 정의되며 AAMVA DL/ID 카드 설계 표준 [aamva-dl-id-card-design-standard]에 따라 발급된 운전면허증과 신분증의 PDF417 바코드 내용을 보호하는 데 사용되는 credentialSubject 유형인 AamvaDriversLicenseScannableInformation을 정의합니다. 이 유형은 섹션 2.1 OpticalBarcodeCredential에 규정된 새로운 credentialSubject 유형에 대한 요구 사항을 충족합니다. 이 부록은 특정 국가나 지역에서 발급되는 문서에 대해 이러한 유형을 정의하는 방법의 예제이기도 하며, 다른 명세에서도 다른 문서 유형에 대해 유사한 유형을 정의하는 것이 권장됩니다.

                  A.1 AamvaDriversLicenseScannableInformation

                  AamvaDriversLicenseScannableInformation 유형의 credentialSubject는 검증 가능한 자격 증명이 AAMVA 준수 운전면허증 또는 신분증 [aamva-dl-id-card-design-standard]의 PDF417 바코드 내용을 보호함을 나타냅니다.

                  AamvaDriversLicenseScannableInformation 객체에는 PDF417의 어떤 필드가 디지털 서명되는지에 관한 정보를 포함하는 필수 protectedComponentIndex 속성이 있습니다(REQUIRED). protectedComponentIndex는 3바이트/24비트 값이어야 하며(MUST), JSON-LD 자격 증명에서 총 5자가 되도록 multibase-base64url로 인코딩됩니다. AAMVA 준수 운전면허증 PDF417에는 22개의 필수 필드가 있으며 [aamva-dl-id-card-design-standard], protectedComponentIndex 값의 처음 22비트가 이러한 필드에 대응합니다. 각 AAMVA 필수 필드는 세 문자 요소 ID로 시작합니다(예: 문서 만료일의 DBA). 이 유형과 연결된 결정론적 구성 요소 목록은 이러한 22개 요소 ID를 유니코드 코드 포인트 순서로 정렬한 목록입니다(즉, ['DAC', 'DAD' ... 'DDG']). protectedComponentIndex의 위치 i에 있는 비트가 1이면 정렬된 요소 ID의 위치 i에 있는 AAMVA 필수 필드가 디지털 서명으로 보호됩니다. protectedComponentIndex의 마지막 두 비트는 패딩 비트이며 0이어야 합니다(MUST). 자세한 내용은 섹션 3.2.4.4 opticalDataBytes 생성을 참조하십시오.

                  구현자는 CBOR-LD로 인코딩된 AamvaDriversLicenseScannableInformation 자격 증명을 PDF417로 인코딩하기 전에 base64url로 문자 인코딩하는 것이 권장됩니다(RECOMMENDED). base로 인코딩된 VCB 데이터 앞에는 multibase 헤더를 추가할 수 있습니다(MAY). PDF417 필드 헤더 명세에는 multibase 헤더의 존재 여부가 표시될 것으로 예상됩니다.

                  A.2 구성 요소 추출

                  AamvaDriversLicenseScannableInformation 유형의 credentialSubject에서 opticalData는 PDF417 바코드의 데이터이며, 보호된 구성 요소는 다음과 같이 추출됩니다. 이 유형의 순서 규칙은 기본 유니코드 코드 포인트 순서입니다.

                  1. dataToCanonicalize를 빈 배열로 설정합니다.
                  2. credentialSubject.protectedComponentIndex를 multibase-base64url에서 바이너리로 디코딩하여 얻은 길이 24비트의 비트 문자열에서 처음 22비트를 bitfieldDecoded로 설정합니다.
                  3. fieldsAlphabetized를 이 유형의 결정론적 구성 요소 목록, 즉 유니코드 코드 포인트 순서로 정렬된 22개의 AAMVA 필수 PDF417 요소 ID [aamva-dl-id-card-design-standard]를 포함하는 배열(즉, ['DAC', 'DAD' ... 'DDG'])로 설정합니다.
                  4. bitfieldDecoded에서 값이 1인 각 비트에 대해:
                    1. fieldName 문자열을 fieldsAlphabetized[i]로 설정합니다. 여기서 i는 bitfieldDecoded에서 해당 비트의 인덱스입니다.
                    2. fieldData 문자열을 해당 필드 이름과 연결되어 PDF417에 포함될 데이터로 설정합니다.
                    3. fieldData를 fieldName의 끝에 연결하고, 줄 바꿈 문자 (\n, U+000A)를 끝에 연결한 다음 결과를 dataToCanonicalize에 추가합니다.
                  5. dataToCanonicalize를 반환합니다.

                  B. ISO 준수 운전면허증

                  이 절은 비규범적입니다.

                  이 부록에서는 MachineReadableInformation의 하위 클래스로 정의되며 ISO 준수 운전면허증(IDL) [ISO18013-2]의 기계 판독 가능 데이터를 보호하는 데 사용할 수 있는 credentialSubject 유형인 IsoDrivingLicenceMachineReadableInformation을 설명합니다. 이는 섹션 2.1 OpticalBarcodeCredential의 요구 사항을 충족하는 credentialSubject 유형을 IDL에 대해 정의할 수 있는 방법을 보여주며, 사용하기 전에 이 명세의 향후 개정판이나 다른 명세에서 개선될 것으로 예상됩니다.

                  B.1 IsoDrivingLicenceMachineReadableInformation

                  IsoDrivingLicenceMachineReadableInformation 유형의 credentialSubject는 검증 가능한 자격 증명이 ISO 준수 운전면허증(IDL)의 압축 인코딩된 기계 판독 가능 데이터, 예를 들어 운전면허증의 PDF417 바코드 내용을 보호함을 나타냅니다. 이 데이터는 [ISO18013-2]에 정의되어 있습니다. 기계 판독 가능 IDL 데이터는 [ISO18013-2]의 논리적 데이터 구조에 정의된 데이터 그룹(DG1부터 DG11까지)으로 구성되며, 이 명세에서는 이러한 데이터 그룹을 광학 데이터의 구성 요소로 사용합니다. IsoDrivingLicenceMachineReadableInformation은 MachineReadableInformation의 하위 클래스입니다.

                  IsoDrivingLicenceMachineReadableInformation 객체에는 어떤 데이터 그룹이 디지털 서명되는지에 관한 정보를 포함하는 필수 protectedComponentIndex 속성이 있습니다. protectedComponentIndex는 2바이트/16비트 값이며, JSON-LD 자격 증명에서 총 4자가 되도록 multibase-base64url로 인코딩됩니다. 이 유형과 연결된 결정론적 구성 요소 목록은 [ISO18013-2]에 정의된 데이터 그룹을 데이터 그룹 번호의 오름차순으로 정렬한 목록 (즉, ['DG1', 'DG2' ... 'DG11'])이며, protectedComponentIndex 값의 처음 11비트가 이러한 데이터 그룹에 대응합니다. protectedComponentIndex의 위치 i에 있는 비트가 1이면 결정론적 구성 요소 목록의 위치 i에 있는 데이터 그룹이 디지털 서명으로 보호됩니다. protectedComponentIndex의 나머지 비트는 패딩 비트이며 0으로 설정됩니다. 자세한 내용은 섹션 3.2.4.4 opticalDataBytes 생성을 참조하십시오.

                  구현자는 CBOR-LD로 인코딩된 IsoDrivingLicenceMachineReadableInformation 자격 증명을 PDF417로 인코딩하기 전에 base64url로 문자 인코딩할 것으로 예상됩니다. base로 인코딩된 VCB 데이터 앞에는 multibase 헤더를 추가할 수 있습니다. 인코딩된 VCB는 선택적이고 관할권별 데이터용인 데이터 그룹 11에 배치될 것으로 예상됩니다. VCB가 11개의 데이터 그룹 중 하나에 배치되는 경우 protectedComponentIndex의 해당 요소는 0으로 설정됩니다.

                  B.2 구성 요소 추출

                  IsoDrivingLicenceMachineReadableInformation 유형의 credentialSubject에서 opticalData는 운전면허증의 압축 인코딩된 기계 판독 가능 데이터 [ISO18013-2]이며, 보호된 구성 요소는 다음과 같이 추출됩니다. 이 유형의 순서 규칙은 데이터 그룹 번호의 오름차순입니다.

                  1. dataToCanonicalize를 빈 배열로 설정합니다.
                  2. credentialSubject.protectedComponentIndex를 multibase-base64url에서 바이너리로 디코딩하여 얻은 길이 16비트의 비트 문자열에서 처음 11비트를 bitfieldDecoded로 설정합니다.
                  3. dataGroupsOrdered를 이 유형의 결정론적 구성 요소 목록, 즉 [ISO18013-2]에 정의된 데이터 그룹 식별자를 데이터 그룹 번호의 오름차순으로 정렬한 배열 (즉, ['DG1', 'DG2' ... 'DG11'])로 설정합니다.
                  4. bitfieldDecoded에서 값이 1인 각 비트에 대해:
                    1. dataGroupName 문자열을 dataGroupsOrdered[i]로 설정합니다. 여기서 i는 bitfieldDecoded에서 해당 비트의 인덱스입니다.
                    2. dataGroupData 문자열을 opticalData에서 dataGroupName으로 식별되고 데이터 그룹 구분 문자로 구분된 데이터 그룹 내용의 base64url 인코딩으로 설정합니다.
                    3. dataGroupData를 dataGroupName의 끝에 연결하고, 줄 바꿈 문자(\n, U+000A)를 끝에 연결한 다음 결과를 dataToCanonicalize에 추가합니다.
                  5. dataToCanonicalize를 반환합니다.

                  C.3 구현 참고 사항

                  C.3.1 CBOR-LD

                  컨텍스트 용어에서 CBOR-LD 정수로의 맵을 생성할 때 일부 컨텍스트는 특정 객체 유형 아래에 중첩된 다른 컨텍스트를 포함한다는 점에 유의하십시오. 이러한 중첩 컨텍스트를 "유형 범위 컨텍스트"라고 하며, 데이터에서 연결된 유형이 사용될 때만 활성화됩니다. 컨텍스트의 용어에는 해당 컨텍스트가 활성화된 후에만 ID가 할당되므로 이는 용어 ID 할당에 중요합니다. 이 테스트 벡터에서 두 자격 증명이 동일한 컨텍스트를 사용하지만 운전면허증과 취업 허가 문서에 대해 생성된 맵이 서로 다른 이유가 바로 이것입니다.

                  또한 CBOR-LD에서는 연결된 값이 복수인 용어를 표현할 때 홀수를 사용한다는 점에 유의하십시오. 예를 들어 위의 CBOR-LD 용어-ID 및 ID-용어 맵에서 "type"은 156에 매핑되지만, VC에서 여러 유형이 표현되는 위치에서는 대신 157이 사용됩니다.
