초록

이 문서는 인터넷 클라이언트가 서버에서 제공하는 콘텐츠에 대해, 해당 콘텐츠가 준수하는 데이터 프로파일을 기반으로 어떻게 협상할 수 있는지 설명한다. 이는 미디어 유형이나 언어에 의한 협상과는 다르다. 프로파일은 반환되는 정보의 내용을 지정할 수 있으며, 이는 응답 서버가 요청된 리소스에 대해 보유한 정보의 하위 집합일 수 있고, 실무 공동체의 상호운용성 요구사항을 충족하기 위해 특정한 방식으로 구조화될 수 있다.

프로파일에 관한 DXWG 문서 개요

이 문서는 W3C Dataset Exchange Working Group(DXWG) 및 Internet Engineering Taskforce(IETF)가 편집한 프로파일 관련 문서 모음 중 하나이다. DXWG 문서는 다음과 같다.

  • [DX-PROF] - Profiles Vocabulary: 프로파일과 관련 리소스를 설명하는 RDF 어휘
  • [PROF-CONNEG] 이 문서, 프로파일을 사용해 인터넷 리소스 콘텐츠를 협상하는 방법에 대한 구체적인 지침
  • DXWG는 또한 [PROF-GUIDANCE] - Profile Guidance: 프로파일링에 대한 일반 권고사항과 지침도 제공할 계획이다.

IETF의 관할 아래 유지되는 다음 문서는 이 문서의 기술적 기반을 수립하지만 DXWG의 범위에는 포함되지 않는다.

  • [PROF-IETF] - Indicating, Discovering, Negotiating, and Writing Profiled Representations: 프로파일 기반 HTTP 콘텐츠 협상을 위한 HTTP 헤더를 정의하는 IETF Internet-Draft

        1. 소개

        이 섹션은 비규범적이다.

        인터넷 식별자를 역참조하여 전달되는 콘텐츠는 여러 방식으로 협상의 대상이 될 수 있다. HTTP 프로토콜 [RFC9110]을 사용할 때, 클라이언트는 하나 이상의 요청 헤더를 설정할 수 있다.

        • 서버가 제공할 수도 있고 제공하지 않을 수도 있는 선호 미디어 유형을 지정하는 Accept 헤더
        • 특정 콘텐츠 인코딩 시스템을 사용하도록 요청하는 Accept-Encoding 헤더
        • 선호 언어를 나타내는 Accept-Language 헤더

        그러나 클라이언트는 정보 모델, 즉 표준, 명세 또는 프로파일의 준수 여부를 기반으로 콘텐츠를 협상하는 정의된 방법을 갖고 있지 않았다. 이 문서는 그러한 기능을 어떻게 제공할 수 있는지 설명한다.

        리소스에 관한 온라인 정보가 하나 이상의 프로파일을 준수하는 경우, 여기에서 설명하는 방법은 클라이언트가 해당 프로파일 목록을 요청하고, 선호 순서에 따라 하나 이상의 프로파일에 맞는 콘텐츠를 요청할 수 있게 한다.

        예를 들어 카탈로그는 서로 다른 정보 모델을 준수하는 데이터셋 설명의 표현 선택지를 제공할 수 있다. 예컨대 [VOID], [VOCAB-DATA-CUBE] 및 [VOCAB-DCAT]일 수 있다. 더 나아가 [VOCAB-DCAT] 표현은 [DCAT-AP] 프로파일, [GeoDCAT-AP] 프로파일, 그리고 조직별 프로파일인 "MyOrgDCATProfile"도 준수할 수 있다. 이러한 더 좁은 프로파일은 자신들이 프로파일로 삼는 더 일반적인 명세를 넘어, 데이터셋 설명의 여러 요소를 추가로 제약한다. 이 데이터셋 설명의 가능한 표현에 대한 정보를 요청할 때, 데이터셋에 사용할 수 있는 프로파일 목록을 요청할 수도 있고, 예를 들어 [GeoDCAT-AP]와 같은 특정 프로파일을 준수하는 표현을 명시적으로 요청할 수도 있다. 프로파일이 요청되지 않았거나 지원되지 않는 프로파일이 요청된 경우, 서버는 서버가 지원하는 기본 프로파일을 준수하는 기본 콘텐츠를 반환한다.

        콘텐츠 협상 메커니즘을 선택할 때, 인터넷 클라이언트는 HTTP 프로토콜을 사용할 수 있지만 서버에 지시를 제공하기 위한 다른 방법도 사용할 수 있다. 가능한 메커니즘 중 하나는 URL 쿼리 문자열 인수(QSA)이다. QSA는 웹 브라우저에 요청을 수동으로 입력하는 경우처럼 HTTP를 통한 협상이 실용적이지 않은 상황에서 사람과 기계 모두에게 유용하다. 이 명세는 프로파일 기반 콘텐츠 협상의 추상 모델을 제공하고, 그 추상 모델을 준수하는 두 가지 특정 방법, 즉 HTTP와 QSA의 사용에 관한 지침을 제시한다.

        HTTP 헤더 및 URL QSA 방법은 추상 모델의 기능 프로파일로 정의된다. 이 명세는 이 두 기능 프로파일만 설명하지만, 구현자는 미래에 실현될 수 있는 환경을 포함한 다른 환경을 위해 추상 모델의 기능 프로파일을 구현하고자 할 것으로 예상된다.

        구현자는 자신이 정의하는 모든 기능 프로파일이 추상 모델의 기능을 구현하고 대체 표현 데이터 모델에 따라 대체 표현 정보를 제공할 수 있도록 해야 한다.

        리소스 표현이 프로파일을 어떻게 준수하는지, 그리고 프로파일과 명세가 서로 어떻게 관련되는지를 설명하는 것은 이 명세의 일부가 아니다. 이러한 질문의 일부 측면은 DXWG가 함께 작성한 Profiles Vocabulary [DX-PROF]에서 다룬다.

        2. 적합성

        비규범으로 표시된 섹션뿐 아니라, 이 명세의 모든 작성 지침, 도표, 예제 및 참고는 비규범적이다. 이 명세의 그 밖의 모든 내용은 규범적이다.

        이 문서에서 핵심어 MAY, MUST, MUST NOT, RECOMMENDED, SHOULD 및 SHOULD NOT은 여기에 표시된 것처럼 모두 대문자로 나타날 때에만 BCP 14 [RFC2119] [RFC8174]에 설명된 대로 해석되어야 한다.

        준수 목적상 이 문서의 규범 섹션은 3. 정의, 7. 추상 모델, 8. 기능 프로파일 및 10. 테스트 모음이다. 부록은 비규범적이다.

        참고

        리소스 표현의 콘텐츠가 준수할 수 있는 명세와 프로파일은 자체적인 적합성 개념을 포함하며, 이는 이 명세의 범위를 벗어난다.

        3. 정의

        명세

        비교의 기준, 즉 다른 것들을 평가할 수 있는 기준점.

        출처: DCMI Metadata Terms [DCTERMS]의 Standard 정의.

        데이터 명세

        주어진 맥락에서 사용되는 데이터의 내용과 구조를 정의하는, 사람 및/또는 기계가 처리할 수 있는 표현을 가진 명세.

        출처: DXWG의 논의.

        기능 명세

        주어진 맥락에서 애플리케이션의 동작을 정의하는, 사람 및/또는 기계가 처리할 수 있는 표현을 가진 명세.

        출처: DXWG의 논의.

        프로파일

        다른 명세의 사용에 대해 제약하거나, 확장하거나, 결합하거나, 지침 또는 설명을 제공하는 명세.

        프로파일의 대상이 되는 명세가 특수한 유형의 명세, 예를 들어 데이터 명세 또는 기능 명세라면, 그 프로파일도 같은 종류, 즉 데이터 프로파일 또는 기능 프로파일이 된다.

        이 Content Negotiation by Profile 명세는 데이터 프로파일에 대한 협상을 다루며, 이를 달성하는 여러 방식에 대한 기능 프로파일을 지정한다. 이 문서에서 "profile"이라는 용어가 대부분 나타날 때는 "data profile"을 의미한다.

        데이터 프로파일

        다른 데이터 명세의 사용에 대해 제약하거나, 확장하거나, 결합하거나, 지침 또는 설명을 제공하는 데이터 명세.

        이 정의에는 때때로 "application profiles", "metadata profiles" 또는 "metadata application profiles"라고 불리는 것들이 포함된다.

        출처: DXWG의 논의.

        기능 프로파일

        다른 기능 명세의 사용에 대해 제약하거나, 확장하거나, 결합하거나, 지침 또는 설명을 제공하는 기능 명세.

        출처: DXWG의 논의.

        클라이언트
        하나 이상의 HTTP 요청을 보내기 위해 서버에 연결을 설정하는 프로그램. [RFC9110]
        서버
        HTTP 요청을 처리하기 위해 연결을 수락하고 HTTP 응답을 보내는 프로그램. [RFC9110]
        리소스
        URI로 식별되는 개체. 익숙한 예로는 전자 문서, 이미지, 일관된 목적을 가진 정보 출처가 있다. [RFC3986]
        표현

        HTTP 통신에서 어떤 것의 현재 또는 원하는 상태에 대한 추상화. [RFC9110]

        이 명세에서 표현은 리소스의 표현이다.

        메타데이터
        리소스에 대해 제공되는 정보. [RFC3986]
        요청
        리소스에 관한 정보를 위해 클라이언트에서 서버로 인터넷을 통해 보내지는 메시지. [RFC9110]
        응답
        인터넷을 통해 서버에서 클라이언트로 전송되며, 요청에 응답하여 리소스에 관한 정보를 제공하는 메시지입니다. [RFC9110]
        토큰

        5. 동기

        이 섹션은 비규범적이다.

        많은 경우 단일 미디어 유형의 범위 안에서 리소스를 설명하는 여러 방법이 있다. 예를 들어 XML 문서는 application/xml 미디어 유형을 준수하면서도 여러 DTD 또는 XML 스키마 중 하나를 따를 수 있다. RDF 문서는 text/turtle, application/rdf+xml 등과 같은 미디어 유형 직렬화를 선택할 수 있으며, 콘텐츠의 정보 모델에 사용할 수 있는 많은 수의 어휘(클래스와 속성)를 가진다. 클라이언트가 리소스의 표현을 검색하기 위한 HTTP GET과 같은 인터넷 리소스 요청을 시작할 때, 클라이언트와 서버는 전송되는 리소스가 DTD, XML Schema, 어휘 또는 기타 표준, 명세 또는 프로파일에 따라 어떻게 구조화될 것인지에 대한 정보를 교환할 표준화된 방법을 가져야 한다. 비HTTP 콘텐츠 협상을 사용할 때는 쿼리 문자열 인수가 포함된 URI와 같은 방법이 이전에 구현된 바 있으며, 예로는 OAI-PMH [OAI-PMH] 및 OGC의 CSW [CSW] 프로토콜이 있다.

        이 문서는 프로파일 기반 콘텐츠 협상을 위한 추상적이고 기능 기반인 명세를 설명하며, 서로 다른 환경에서 이 명세를 구현하기 위한 HTTP 헤더 기능 프로파일과 두 가지 쿼리 문자열 인수 기반 기능 프로파일을 제공한다. 쿼리 문자열 방식은 Dataset Exchange Working Group의 헌장(2.3절)에서 요구하는 "대체 수단"(추상 명세의 두 번째 비HTTP 구현)을 제공할 뿐 아니라, 잠재적인 기능 프로파일 구현자가 자신의 구현을 위한 지침으로 삼을 수 있는 추상 명세의 기능 프로파일도 보여준다.

        이 추상 명세의 다른 쿼리 문자열 또는 REST 기반 기능 프로파일도 가능하다고 여겨지지만, 여기서는 지정하지 않는다. 일반적으로 리소스 표현의 대체 프로파일 목록과 프로파일에 따른 리소스 표현 검색을 지원하는 기존 API도, 이 문서의 기능 프로파일이 그러하듯 이 명세가 요구하는 기능을 구현함으로써 이 명세에 대한 적합성을 지원하고 입증할 수 있다.

        참고
        콘텐츠 협상 HTTP 헤더의 표준화는 IETF의 관할 사항이다. HTTP에서 프로파일을 표시하고 협상하기 위한 Internet Draft [PROF-IETF]의 첫 번째 제안이 제공되어 있지만 아직 IETF에 제출되지는 않았다. IETF 초안의 현재 버전(-00)은 이 문서와 병행되는 작업에서 완전히 다시 작성될 것으로 예상되며, 이 문단이 이 문서에서 제거될 때까지는 진행 중인 작업으로 보아야 한다.

        6.1 HTTP 헤더에서 프로파일 정보를 전달하기 위한 기존 표준

        6.1.1 Accept/Content Type을 profile 매개변수와 함께 사용하기

        HTTP Accept 및 Content-Type 헤더 필드 [RFC9110]는 클라이언트가 허용 가능한 미디어 유형(Accept)을 지정하고, 서버가 응답 본문의 미디어 유형(Content-Type)을 나타낼 수 있게 한다. 미디어 유형 등록은 선택적인 미디어 유형 매개변수 목록도 지정할 수 있다. 일부 미디어 유형 등록(예: application/ld+json)은 응답 본문이 준수하는 프로파일을 알리는 데 사용할 수 있는 "profile"이라는 미디어 유형 매개변수의 사용을 지정한 바 있다.

        예제 1: HTTP Accept 헤더를 'profile' 매개변수와 함께 사용하기 
        GET /resource/a HTTP/1.1
Accept: application/ld+json;q=0.9;profile="urn:example:profile-1", \
        application/ld+json;q=0.7;profile="urn:example:profile-2"

--

HTTP/1.1 200 OK
Content-Type: application/ld+json;profile="urn:example:profile-2"

        2018년에 DXWG 구성원들은 프랑스 리옹에서 열린 연례 포럼 TPAC에서 JSON-LD WG와 더 긴 논의를 진행했으며, Accept 및 Content-Type 헤더의 "profile” 매개변수는 JSON-LD의 "expanded"(http://www.w3.org/ns/json-ld#expanded) 또는 "flattened"(http://www.w3.org/ns/json-ld#flattened)와 같이 미디어 유형에 특화된 프로파일을 전달하는 것으로 보아야 한다는 결론을 내렸다. 미디어 유형과 독립적인 프로파일의 사용을 알리기 위해서는 HTTP 헤더 필드 Accept-Profile 및 Link: <...>; rel="profile"을 사용해야 한다.

        6.1.2 rel="profile"인 Link 헤더 사용하기(RFC 6906)

        HTTP Link 헤더 필드 [RFC8288]는 두 리소스 간의 관계를 지정함으로써 웹 리소스(Link Context)를 대상 리소스(Link Target)와 연결한다. 관계 유형 중 하나는 [RFC6906]에 정의된 "profile"이다. [RFC6906]은 프로파일을 정의하기를 "기본 미디어 유형 의미론을 변경하지 않으면서 리소스 표현을 처리하는 데 사용할 수 있는 추가 의미론 […]"이라고 하며, 구체적으로 "프로파일의 작성자와 사용자는 이를 미디어 유형 전반에서 사용할 수 있도록 하는 방식으로 정의하고 관리할 수 있다(MAY)"고 명시한다. 따라서 "profile" 관계는 허용 가능한 프로파일(요청) 및 콘텐츠(응답)에 관한 정보를 전달하는 적절한 방법처럼 보인다.

        예제 2: profile 매개변수가 있는 Link 헤더 사용하기 
        HEAD /resource/a HTTP/1.1
Accept: text/turtle;q=0.9,application/rdf+xml;q=0.5
Link: <http://example.com/profile/x>; rel="profile"

--

HTTP/1.1 200 OK
Content-Type: text/turtle
Link: <http://example.com/profile/x>; rel="profile"

        "profile" 관계는 서버가 응답 본문의 프로파일을 나타내는 데 사용할 수 있다. 그러나 요청에서 "profile" 관계를 사용해 품질 정보(q-value)를 전달할 가능성은 없다.

        6.1.3 Prefer/Preference-Applied 헤더 필드 사용하기(RFC 7240)

        HTTP Prefer 및 Preference-Applied 헤더 필드 [RFC7240]는 프로파일 선호도에 관한 정보를 전달하는 데 사용할 수 있다. 클라이언트는 Prefer 헤더를 사용하여 특정 프로파일을 준수하는 리소스 표현에 대한 선호를 서버에 알릴 수 있다. 서버가 응답에서 Preference-Applied 헤더 필드를 보내면, 클라이언트는 그 선호가 존중되었음을 알 수 있다.

        예제 3: profile 매개변수가 있는 Prefer 헤더 사용하기 
        GET /resource/a HTTP/1.1
Accept: text/turtle
Prefer: profile="urn:example:schema"

--

HTTP/1.1 200 OK
Content-Type: text/turtle
Preference-Applied: profile="urn:example:schema"

        이 접근 방식에는 두 가지 단점이 있다. 첫째, Link 헤더의 경우와 마찬가지로 요청 헤더에서 q-value를 사용할 가능성이 없다. 둘째, 클라이언트가 표시한 선호를 서버가 무시했다는 것을 서버가 나타낼 수 있는 유일한 방법은 Preference-Applied 헤더 필드를 보내지 않는 것이다. 그러나 클라이언트 입장에서는 Preference-Applied 헤더가 없을 때, 서버가 그 선호를 존중하지 않았기 때문인지, 아니면 서버가 Prefer 헤더를 이해하지 못했기 때문인지 명확하지 않다. 이는 Prefer: profile="" 헤더가 포함된 요청에 응답할 때 Link: rel=profile 헤더를 반드시 보내도록 함으로써 해결할 수 있다. 그러나 이 해결책은 클라이언트가 특정 프로파일 요청에 대한 응답을 찾기 위해 두 개의 서로 다른 헤더를 평가해야 하므로, 클라이언트 구현을 더 복잡하게 만들 것이다. 더 나아가 [RFC7240]은 구현자가 콘텐츠 협상을 위해 Prefer 헤더 메커니즘을 사용하지 말 것("SHOULD NOT")을 명시적으로 권고한다.

        6.2 Archival Resource Key(ARK)

        ARK(Archival Resource Key) [ARK]는 정보 객체의 지속적인 식별을 위한 식별자 체계이다. ARK 식별자는 "NAA[즉 Name Assigning Authority]가 명명한 객체로 들어가는 일종의 서비스 진입점을 만들기 위해 기본 ARK를 확장하는" 선택적 한정자를 포함할 수 있다. 한정자를 통해, 모든 NMA(Name Mapping Authority, ARK 해석을 제공하는 서비스 제공자)는 해당 객체의 변형에 대한 접근을 제공할 수 있다. 한정자 집합은 열려 있으며, 모든 ARK NAA 또는 NMA는 자신만의 한정자를 만들 수 있다. ARK 명세는 버전, 언어 및 형식을 한정자의 예로 열거하며(§2.5), 프로파일 이름도 특정 프로파일을 준수하는 정보 객체의 표현을 가리키는 한정자로 사용할 수 있다. 예를 들어 URI https://api.istex.fr/ark:/67375/6GQ-MLC8GRWC-5/는 ARK 67375/6GQ-MLC8GRWC-5로 식별되는 리소스에 대한 메타데이터의 XML 인코딩을 나열하며, 여기에는 "MODS", 즉 Library of Congress의 Metadata Object Description Schema를 포함한 여러 XML 어휘를 준수하는 인코딩이 포함된다.

        6.3 Linked Data API

        여러 Linked Data API 도구는 쿼리 문자열 인수(QSA)를 사용하여 URI로 식별되는 리소스의 서로 다른 표현에 대한 접근을 제공한다. 두 가지 예로는 영국 정부가 만든 Linked Data API 명세의 구현인 Epimorphics의 ELDA 도구와 CSIRO가 Python 프로그래밍 언어로 구현한 Linked Data API 구현인 pyLDAPI가 있다. 이 두 도구는 리소스 URI에 _view=alternates QSA를 추가하여 만든 URL을 역참조함으로써, 리소스에 사용할 수 있는 view와 format 목록을 제공한다. alternates라는 이름의 view는 모든 리소스에서 사용할 수 있는 특수한 view이며, 다른 모든 view를 나열한다.

        이 도구들이 view라고 부르는 것은 데이터 프로파일과 유사하며, format은 HTTP 미디어 유형과 유사하다.

        이러한 API는 특정 view, 특정 format, 또는 둘 중 하나가 지정되지 않았거나 유효하지 않은 경우 기본 view 또는 기본 format을 준수하는 리소스 표현에 직접 접근할 수 있게 한다. 예를 들어 pyLDAPI를 사용하면 주소 GAACT714845933의 표현에 사용할 수 있는 view와 format은 http://linked.data.gov.au/dataset/gnaf/address/GAACT714845933?_view=alternates를 역참조하여 확인할 수 있으며, Alternates View에 나열된 해당 주소의 "ISO19160" view를 RDF Turtle format으로 제공하는 것은 http://linked.data.gov.au/dataset/gnaf/address/GAACT714845933?_view=ISO19160&_format=text/turtle에서 사용할 수 있다.

        6.4 OAI-PMH

        Open Archives Initiative Protocol for Metadata Harvesting [OAI-PMH]는 "...메타데이터 수확을 기반으로 하는 애플리케이션 독립적인 상호운용성 프레임워크를 제공한다.". 이를 위해 OAI-PMH는 Data Providers의 클라이언트가 다음을 수행할 수 있도록 하는 쿼리 문자열 인수 기반 "Protocol Requests and Responses"를 지정한다. 즉, 저장소에서 사용할 수 있는 메타데이터 formats (이 문서에서 설명하는 데이터 프로파일과 유사함)를 검색하고 (ListMetadataFormats), 식별된 메타데이터 프로파일(metadataPrefix)에 따라 식별된 레코드의 메타데이터를 검색하며(GetRecord), 그 밖의 여러 저장소 조회 작업을 수행하고, 수정 날짜와 같은 매개변수로 필터링된 레코드 메타데이터 컬렉션을 수확할 수 있게 한다.

        OAI-PMH는 저장소의 모든 리소스 표현이 동일한 프로파일 집합(이것을 formats라고 부름)에 따라 사용할 수 있어야 한다고 요구한다. 이는 전적으로 XML 기반이므로, 프로파일은 모두 XML로 제시되어야 하며, 리소스의 XML 표현 콘텐츠는 레코드, 프로파일, 사용된 OAI-PMH 메서드, 요청 시간 및 기타 공통 메타데이터를 항상 식별하는 XML 봉투 안에 제시된다.

        6.5 Catalogue Service for the Web(CSW)

        [CSW]는 지리공간 커뮤니티가 전 세계적으로 사용하는 OGC 표준으로, 카탈로그 서비스에 대한 기계 실행 가능한 인터페이스를 구현하여 데이터셋, 지리공간 서비스([WMS], [WFS] 등)에 관한 메타데이터와 그 밖의 유형의 리소스에 대한 접근을 제공한다. 자유 텍스트 및 패싯 검색과 같은 공통 기능을 지원하는 것 외에도, CSW는 각각 outputSchema 및 outputFormat 쿼리 매개변수를 사용하여 표시되는 주어진 메타데이터 스키마 및 형식에 따른 메타데이터 검색을 지원한다. 일반적으로 지원되는 메타데이터 스키마는 [DC11] 및 [ISO-19115]이며, 기본 형식은 XML이다. 특정 CSW 인스턴스가 지원하는 메타데이터 스키마와 형식은 GetCapabilities 요청을 통해 반환되는 서비스 "capabilities" (서비스 인터페이스에 대한 기계 판독 가능한 설명)에 설명되어 있다.

        특히 CSW는 이론적으로 메타데이터 형식에 대한 HTTP 콘텐츠 협상을 지원하며, 명세는 이 정보가 HTTP Accept 헤더와 outputFormat 매개변수 양쪽에 모두 지정된 요청에 대한 충돌 해결 메커니즘을 정의한다 (OGC CSW 3.0 명세 - HTTP Protocol Binding의 6.2절 참조).

        7. 추상 모델

        이 섹션은 특정 환경에서의 어떤 구현과도 독립적인, 프로파일 기반 콘텐츠 협상을 위한 개념적, 즉 추상적인 모델을 설명한다.

        서로 다른 환경을 위한 이 추상 모델의 구현을 기능 프로파일이라고 한다. 유효한 기능 프로파일이 되려면 이들은 이러한 추상 모델 기능을 구현해야 한다(MUST). 이를 어떻게 수행하는지는 환경별로 달라진다.

        기능 프로파일은 자신만의 추가 기능으로 이 추상 모델을 확장할 수 있다(MAY). 다만 이러한 추가 사항은 여기서 정의된 기능을 무효화해서는 안 된다(MUST NOT).

        서로 다른 데이터 프로파일을 준수하는 리소스의 표현을 설명하기 위한 데이터 모델이 여기에 제시되어 있으며, 이 모델은 모든 기능 프로파일에서 사용되어야 한다(MUST). 데이터 모델이 어떻게 실현되는지는 구현자가 결정하도록 남겨 둔다. 구현된 데이터 모델의 적합성을 어떻게 입증하는지는 여기서 자세히 다루지 않으며, 다음 지침만 제공한다. 구현자는 자신의 대체 표현 데이터 모델 구현의 적합성을, 해당 모델의 환경별 실현과 이 명세에서 제공하는 모델의 구체적 실현, 예를 들어 OWL 온톨로지 표현 사이의 공개된 매핑을 제공함으로써 입증하는 것이 좋다(SHOULD).

        7.1 콘텐츠 협상 배경

        인터넷을 통한 모든 콘텐츠 협상은 클라이언트와 서버 사이에서 이루어진다. 전자는 요청을 통해 리소스 또는 리소스의 메타데이터 표현을 요청하고, 응답을 통해 요청한 표현을 받는다. 통신하는 특정 기계 쌍의 경우, 정보가 오가며 요청되는 과정에서 클라이언트와 서버의 역할이 서로 바뀔 수 있다.

        인터넷 리소스에는 클라이언트/서버 에이전트 쌍이 콘텐츠에 대해 협상할 수 있는 여러 측면이 있을 수 있다. 이러한 측면은 독립적으로 취급되어야 하므로, 프로파일에 의한 협상과 그 밖의 어떤 측면에 의한 협상을 포함하는 리소스의 콘텐츠 협상은 서로 영향을 주지 않는다.

        이 추상 모델에서는 클라이언트, 서버, 리소스, 메타데이터, 요청 또는 응답에 대해, 정의 섹션3. 정의에서 이미 제공된 세부 사항 외에는 어떤 구체적인 세부 사항도 가정하지 않는다.

        7.2 프로파일 식별

        데이터 프로파일을 준수하는 리소스의 표현을 요청하는 클라이언트는 리소스를 Uniform Resource Identifier(URI) [RFC3986]로 식별해야 하며(MUST), 프로파일은 URI 또는 토큰으로 식별해야 한다(MUST).

        프로파일 식별에 URI가 사용되는 경우, 이는 프로파일 설명으로 역참조되는 HTTP URI인 것이 좋다(SHOULD). 다른 종류의 URI, 예를 들어 URN도 사용할 수 있으며(MAY), 이들은 역참조 가능하지 않을 수 있다. 토큰이 사용되는 경우, 이는 요청/응답 메시지 쌍 안에서 데이터 프로파일을 명확하게 식별해야 한다(MUST). 서버는 토큰이 URI에 매핑될 수 있는 맥락을 선언해야 한다(MUST).

        7.3 요청 및 응답

        프로파일 기반 콘텐츠 협상과 관련하여 클라이언트가 서버에 할 수 있는 요청에는 두 가지 주요 유형이 있다. 이 명세를 따르는 프로파일을 통해 콘텐츠를 협상하려는 클라이언트는 이 두 요청 유형을 구현할 수 있어야 한다(MUST).

        1. 프로파일 목록
          클라이언트는 서버가 적합한 리소스 표현을 전달할 수 있는 데이터 프로파일들의 URI 목록을 요청한다.
        2. 프로파일별 리소스 가져오기
          클라이언트는 특정 프로파일을 준수하는, 요청된 리소스의 표현을 요청한다.

        이 명세를 따르는 서버는 각 요청에 대해 다음과 같은 각각의 응답으로 응답해야 한다(MUST).

        1. 프로파일 목록
          서버는 클라이언트에게, 자신이 적합한 리소스 표현을 전달할 수 있는 데이터 프로파일들의 URI 목록으로 응답한다.
        2. 프로파일별 리소스 가져오기
          서버는 클라이언트가 식별한 요청된 프로파일을 준수하는 리소스의 특정 데이터 프로파일로 응답하거나, 기본 데이터 프로파일로 응답한다.

        이러한 요청과 그 응답에 대한 더 자세한 설명은 다음에 제시된다.

        7.3.1 프로파일 목록

        클라이언트는 서버가 어떤 데이터 프로파일에 대해 리소스의 적합한 표현을 전달할 수 있는지 알고자 한다. 프로파일 목록은 특정 리소스 표현에 대한 요청이 이루어지기 전에 알려져 있을 수도 있고, 최초 요청이 이루어진 뒤에야 알려질 수도 있다.

        프로파일 목록 요청은 독립적인 요청이거나 다른 기능 프로파일 요청의 일부여야 한다(MUST).

        프로파일 목록 요청은 여러 형식 중 하나의 응답으로 이어질 수 있다(MAY). 다만 리소스의 표현이 준수하는 데이터 프로파일들은 URI 또는 토큰 중 하나로 명확하게 식별되어야 한다. 후자의 경우, 하나의 특정 클라이언트/서버 메시지 쌍 안에서 URI에 매핑 가능해야 한다(MUST).

        서버는 특정 데이터 프로파일을 지정하는 프로파일별 리소스 가져오기 요청이 제시되었을 때 전달할 수 없는 데이터 프로파일을 목록에 포함해서는 안 된다(MUST NOT).

        예제 4는 QSA 기능 프로파일을 준수하는 요청/응답 메시지 쌍을 보여주며, 여기서 요청은 특정 리소스에 대한 프로파일 목록 요청이다.

        예제 4: 단순 프로파일 목록 요청 및 응답 메시지(QSA 기능 프로파일) 
        # A request for all the profiles to which representations of resource a conform
GET /resource/a?_profile=alt HTTP/1.1

---

# The server returns a list of profiles both in its HTTP response header and also
# in the response body (HTML). Note that the action of returning the response message
# conforms to the QSA Functional Profile and this is indicated with the Link header
# combined with the "profile" relation
HTTP/1.1 200 OK
Content-Type: text/html
Link: <http://www.w3.org/ns/dx/connegp/profile/qsa>; rel="profile"
# This Link header indicates representations are available that conform to Profile X
# & Y and that the Profile X-conformant representations are available in HTML
# & XML Media Types.
Link:
  <http://example.org/resource/a?_profile=profile-x&_mediatype=text/html>;
          rel="canonical"; type="text/html";
          formats="http://otherexample.org/profile/x",
  <http://example.org/resource/a?_profile=profile-x&_mediatype=application/xml>;
          rel="alternate";
          type="application/xml";
          formats="http://otherexample.org/profile/x",
  <http://example.org/resource/a?_profile=profile-y&_mediatype=application/xml>;
          rel="alternate";
          type="application/xml";
          formats="http://otherexample.org/profile/y"

<!DOCTYPE html>
<html>
  <head>
    <meta charset="UTF-8">
    <title>Profiles for Resource A</title>
  </head>
  <body>
    <h1>Profiles available for Resource X</h1>
    <ul>
      <li><a href="?_profile=profile-x&_mediatype=text/html">X, in HTML</a></li>
      <li><a href="?_profile=profile-x&_mediatype=application/xml">X, in XML</a></li>
      <li><a href="?_profile=profile-y&_mediatype=application/xml">Y, in XML</a></li>
    </ul>
  </body>
</html>

        7.3.2 프로파일별 리소스 가져오기

        프로파일 기반 콘텐츠 협상의 가장 기본적인 요청은 클라이언트가 데이터 프로파일을 준수한다고 주장되는 리소스의 표현을 요청하는 것이다.

        프로파일별 리소스 가져오기 요청을 실행하는 클라이언트는 데이터 프로파일을 URI 또는 세션 내에서 URI에 명확하게 매핑되는 토큰으로 식별해야 한다(MUST).

        프로파일별 리소스 가져오기를 실행하는 클라이언트는 기능 프로파일별 순서 지정으로 선호도를 표현하여, 여러 데이터 프로파일 중 하나를 준수하는 리소스 표현을 요청할 수 있다(MAY).

        서버는 클라이언트 요청에 가장 잘 맞는 프로파일로 응답하려고 시도하는 것이 좋다(SHOULD). 서버가 가장 잘 맞는 프로파일을 결정하기 위해 따라야 하는 선호 순서는 다음과 같다(MUST). 정확히 일치하는 프로파일이 먼저이고, 그다음은 리소스 표현이 준수하는 다음으로 가장 구체적인 프로파일이다. 리소스 표현은 계층을 통해, 즉 추이적으로 더 일반적인 명세나 다른 프로파일을 준수할 수도 있음에 유의한다.

        [RFC9110]에 지정된 바와 같이, 프로파일, 미디어 유형 또는 다른 협상 차원의 선호도를 지정하는 요청에서 HEAD 메서드가 사용되는 경우, 응답은 본문이 비어 있어야 한다는 점(MUST)을 제외하고, 헤더와 상태 코드를 포함하여 GET 메서드의 응답과 같아야 한다. 응답 콘텐츠를 생성하는 동안에만 값이 결정되는 헤더는 생략될 수 있음(MAY)에 유의하는 것이 중요하다.

        서버가 다른 리소스로 리디렉션하는 경우, 클라이언트가 요청한 목록에서 선택된 프로파일을 표시해야 하며(MUST), 알려진 경우 리디렉션 요청(303 응답)에서 반환될 것으로 예상되는 더 구체적인 프로파일을 표시하는 것이 좋다(SHOULD).

        참고: 다른 리소스로 리디렉션
        프로파일별 리소스 가져오기 요청은 리소스의 표현에 대한 것이며, 프로파일을 준수하는 표현이 있는 리소스가 정보 리소스가 아닐 수도 있으므로, 서버의 응답이 다른 리소스로의 리디렉션 형태를 취할 수 있다는 점에 유의하는 것이 중요하다. 이는 이른바 'httpRange-14' 문제를 처리하기 위한 W3C의 권고에 따른 것이다. 리디렉션 응답의 예는 예제 6에 제시되어 있다.

        HTTP 헤더 기능 프로파일에 따라 Accept-Profile 및 Link: rel="profile" 헤더가 포함된 단순 요청/응답 메시지 쌍은 예제 5에 나와 있으며, 리디렉션이 있는 예는 예제 6에 나와 있다. 예제 7은 요청된 프로파일보다 더 좁은 프로파일 응답을 나타내는 HTTP 헤더 기능 프로파일 메시지 쌍을 보여준다.

        예제 5: 단순 프로파일별 리소스 가져오기 요청 및 응답(HTTP 헤더 기능 프로파일) 
        # A request for resource a according to Profile x is made
GET /resource/a HTTP/1.1
Accept-Profile: <http://example.org/profile/x>

---

# The server returns a representation of Resource a conforming with Profile x
HTTP/1.1 200 OK
Link: <http://example.org/profile/x>; rel="profile"

[response body]

        # A request for a non-information resource a according to Profile x is made
GET /resource/a HTTP/1.1
Accept-Profile: <http://example.org/profile/x>

---

# The server returns a 303 Redirect to another URI identifying an information
# resource that then returns the requested resource representation. The redirecting
# server indicates the profile to which the redirected to resource representation
# conforms
HTTP/1.1 303 See Other

Link: <http://example.org/profile/x>; rel="profile"

---

# The client now requests the indicated information resource. Note that the
# Accept-Profile header is no longer needed since the original response has
# catered for that in the redirect response
GET /info-resource/b HTTP/1.1

---

# The final server response with the information resource. Note that this
# response does not include the profile-indicating Link rel="profile" header
HTTP/1.1 200 OK

[response body]

        # A request for Resource A whose representation conforms
# to Profile X is made

GET /resource/a HTTP/1.1
Accept-Profile: <http://example.org/profile/x>
[more request headers]

# Resource a according to Profile Y which it knows is a

HTTP/1.1 200 OK
[other response headers]

        동일한 프로파일 계층 안에 있지 않은 둘 이상의 프로파일을 준수하는 리소스가 반환되는 경우 (즉, 리소스가 일련의 프로파일을 준수하지만 그중 일부는 독립적이며, 해당 집합의 다른 프로파일을 특수화한 프로파일이 아닌 경우), 서버는 각 독립 프로파일에 대한 적합성을 표시하는 것이 좋다(SHOULD).

        예를 들어 HTTP 헤더 기능 프로파일을 사용할 때, [GeoDCAT-AP]와 [STATDCAT-AP]를 모두 준수하는 서버의 응답에서, 어느 프로파일도 다른 프로파일을 프로파일링하지 않으므로 둘 모두에 충분한 단일 적합성 표시가 없다고 할 때 (둘 모두 [DCAT-AP]를 프로파일링한다는 점에 유의한다. [DX-PROF]의 DCAT-AP 계층 예제 참조), [GeoDCAT-AP]와 [STATDCAT-AP]에 대한 프로파일 URI를 사용하는 응답은 다음과 같을 수 있다.

        Link: <https://joinup.ec.europa.eu/release/geodcat-ap-v10>; rel="profile", <https://joinup.ec.europa.eu/release/statdcat-ap/101>; rel="profile"

        7.4 대체 표현 데이터 모델

        이 데이터 모델은 서로 다른 프로파일을 준수하는 리소스의 표현을 설명하는 데 사용되어야 한다(MUST).

        이 모델의 그래픽 개요는 그림 1에 제시되어 있다.

        서로 다른 프로파일을 준수하는 리소스의 대체 표현에 대한 설명은, 이 명세가 만들어진 애플리케이션 프로파일에 관련성이 있다고 판단되는 것에 따라, 이 모델을 구현하는 모델링 시스템에 따라 제시될 수 있다(MAY). 예를 들어 HTTP 애플리케이션 프로파일(8.2 Hypertext Transfer Protocol 헤더)은 [RFC9110]의 HTTP 명세 헤더 구조 제약 안의 텍스트로 제한되므로, 해당 환경에서 이 데이터 모델의 구문적 전달은 그 제약에 따라 구현되어야 한다.

        이 데이터 모델의 일부 구현에 대한 데이터 인스턴스의 적합성을 테스트하기 위한 도구는 10. 테스트 모음에 제시되어 있다. 예상되는 상황에서 사용하기 위한 이 데이터 모델의 구체적 구현 및 확장에 대한 제안은 A.4 대체 표현 데이터 모델 - 세부 사항에 제시되어 있다. 제안된 사용 예도 해당 부록에 제시되어 있다.

        7.5 구현 프로파일의 우선순위

        서비스는 HTTP, QSA 및 그 밖의 가능한 접근 방식을 포함하여 여러 기능 프로파일을 구현할 수 있다(MAY). 이러한 경우 클라이언트는 서로 다른 메커니즘을 통해 충돌하는 선택을 지정할 수 있다. 예를 들어 클라이언트가 기본 헤더를 보내면서도 특정 표현을 요청하는 일반적인 경우가 그렇다. 여기서 정의하는 우선순위는 어떤 메커니즘을 사용해야 하는지 결정한다(MUST).

        우선순위는 QSA가 HTTP보다 앞선다. 이는 URI가 리소스를 더 정확하게 가리킬수록, 그 요청과 함께 어떤 HTTP 헤더가 전송되었는지와 관계없이 에이전트가 바로 그 정확한 리소스를 요청하려는 의도를 가질 가능성이 더 높다는 근거에 따른 것이다.

        추상 모델의 다른 잠재적으로 충돌하는 기능 프로파일이 정의된다면, 우선순위를 설정해야 할 것이다. 이를 선언하는 방법에 대해서는 구체적인 메커니즘을 제안하지 않는다.

        8. 기능 프로파일

        8.1 이 명세의 기능 프로파일

        이 섹션은 서로 다른 시스템 환경을 위한 이 명세의 추상 모델에 대한 기능 프로파일을 정의한다. 다른 프로파일도 정의될 수 있으며, 추상 모델을 준수하는 모든 프로파일에 대한 적합성은 이 명세에 대한 적합성을 충족한다.

        이 명세는 두 환경, 즉 HTTP 헤더와 사람용 브라우저(URL 쿼리 문자열 인수)를 위한 추상 모델의 기능 프로파일을 제공한다.

        또한 Resource Representation Description (cnpr:rrd) 프로파일은 서버가 GetResource 요청에 대한 서버 응답이 어떤 프로파일(들)을 준수하는지 나타낼 것임을 선언하는 데 사용될 수 있다.

        사람용 브라우저 환경에 대해서는 서로 다른 사용 방식을 보여주기 위해 두 가지 기능 프로파일이 제시된다. 이 명세의 추가 기능 프로파일은 다른 환경을 위해서나, 이러한 환경 안의 제한된 시나리오를 위해서도 구현될 수 있으며(MAY), 구현자는 이 명세를 준수하는 추가 프로파일을 만들도록 권장된다.

        여기서 미리 정의된 이 명세의 기능 프로파일은 그림 2에 나열되어 있다. 이들에 대한 네임스페이스 접두사는 다음과 같다.

        • cnpr → http://www.w3.org/ns/dx/connegp/profile/

        위 기능 프로파일에 사용되는 네임스페이스 http://www.w3.org/ns/dx/connegp/profile/는 Dataset Exchange Working Group이 예약한 W3C 네임스페이스 http://www.w3.org/ns/dx/의 일부이며, 이 작업 그룹이 다루는 문제와 관련된 모든 네임스페이스 요구사항을 위해 마련된 것이다. /profile/ 경로 세그먼트는 현재 그림 2의 위 4개 인스턴스만 포함하는 프로파일 객체 등록부를 나타낸다.

        8.2 Hypertext Transfer Protocol 헤더

        Hypertext Transfer Protocol(HTTP) 헤더를 사용하는 추상 모델의 기능 프로파일을 여기서 제시한다. 이 구현은 HTTP 콘텐츠 협상을 기반으로 하며, 특정 방식으로 작성된 Link 헤더와 예정된 Internet-Draft [PROF-IETF]에서 정의될 새로운 HTTP 헤더 Accept-Profile을 사용한다.

        참고: POST/PUT은 범위 밖

        POST 및 PUT 메서드는 이 기능 프로파일의 범위 밖으로 간주된다. 이러한 HTTP 메서드가 제안된 추상 모델의 어떤 기능을 구현하게 될지는 명확하지 않다.

        요청 메시지 콘텐츠의 적합성을 전달하기 위해 POST 및 PUT 요청에 rel="profile"이 있는 Link 헤더를 지정할 수 있다.

        서버는 원하는 방식으로 자유롭게 협상을 구현할 수 있지만, User Agent가 Accept-Profile 헤더를 보내는 경우, 나열된 어떤 프로파일도 준수하지 않는 표현은 클라이언트가 해석할 수 없는 것으로 간주하는 것이 좋다(SHOULD). 이는 나열된 프로파일을 준수하지만 다른 차원에서 낮은 선호 점수를 가진 표현이, 다른 차원에서 더 높은 선호 점수를 가지지만 나열된 어떤 프로파일도 준수하지 않는 표현보다 더 선호되는 것으로 간주되는 것이 좋다는 뜻이다(SHOULD). Accept-Profile 헤더 선호가 주어지지 않은 경우, 프로파일 차원은 협상 목적상 무시되는 것이 좋다(SHOULD). 그럼에도 모든 경우에 서버의 응답은 자신이 그 표현이 준수한다고 알고 있는 모든 프로파일의 URI를 나열하는 rel="profile"이 있는 Link 헤더를 포함하는 것이 좋다(SHOULD).

        8.2.1 프로파일 목록

        서버가 특정 리소스에 대해 지원하는 프로파일 목록을 검색하는 선호 방식은 해당 리소스에 대해 GET 또는 HEAD 요청을 보내는 것이다. 어느 경우든, 프로파일 기반 콘텐츠 협상을 구현하는 서버는 그 리소스의 기본 표현과 모든 대체 표현에 관한 정보, 그리고 그 표현들이 준수하는 프로파일을 포함하는 HTTP Link 헤더를 반환하는 것이 좋다(SHOULD). 기본 표현, 즉 특정 표현이 요청되지 않았을 때 반환될 표현은 rel="canonical"로 식별하는 것이 좋고(SHOULD), 다른 표현은 rel="alternate"로 식별하는 것이 좋다.

        예로, 미디어 유형 application/xml, text/html 및 text/turtle로 사용할 수 있는 리소스 http://example.org/resource/a를 생각해 보자. text/html 표현에는 프로파일이 없는 반면, application/xml 및 text/turtle 표현은 모두 urn:example:profile:x 및 urn:example:profile:y 프로파일로 사용할 수 있다.

        Accept-Profile 헤더가 없는 요청이 기본적으로 urn:example:profile:x를 준수하는 콘텐츠를 전달한다고 가정하면, HTTP 요청/응답 쌍은 예제 8과 같을 수 있다.

        8.2.1.1 HTTP 대체 표현 데이터 모델 구현

        기능 프로파일 구현은 추상 모델의 기능을 구현하는 것에 더해, 대체 표현 데이터 모델에 따라 대체 표현 정보를 전달할 수 있도록 해야 한다. 이 HTTP 헤더 기능 프로파일에서 이를 수행하기 위해 선택된 메커니즘은 아래 설명된 [RFC8288]의 Link 헤더이다.

        HTTP Link는 [RFC8288]에 따르면 "두 리소스 간의 유형화된 연결이며" 다음으로 구성된다.

        • 링크 컨텍스트,
        • 링크 대상,
        • 링크 관계 유형, 그리고
        • 선택적으로 대상 속성.

        링크 컨텍스트는 Link 헤더가 전달되는 리소스이다. 관계 유형은 rel 속성 키 이름으로 주어지고, 링크 대상은 URI이며, 다른 선택적 대상 속성에는 profile 속성 키 이름으로 주어지는 profile이 포함될 수 있다.

        예제 9에서 링크 컨텍스트 resource/a 요청에 대해 반환된 Link 헤더의 첫 부분은 다음 구성요소를 가진다.

        • 링크 대상 - <http://example.org/resource/a.prof1.ttl>
        • 관계 유형 - rel="canonical"
        • 대상 속성 - type="text/turtle" 및 formats="urn:example:profile:x"

        이러한 Link HTTP 헤더 구성요소를 사용하여, 이 HTTP 헤더 기능 프로파일은 Alternate Profiles Data Model에 따라 리소스의 대체 데이터 프로파일을 전달할 수 있으며, 아래 그림 3은 헤더 구성요소를 데이터 모델의 OWL 온톨로지 표현에 매핑한다. 이 표현은 데이터 모델의 구체적이고 형식적인 실현이다. 이 매핑은 7. 추상 모델의 지시에 따라 제시된다. 그 지시는 "구현자는 자신의 대체 표현 데이터 모델 구현의 적합성을, 해당 모델의 환경별 실현과 이 명세에서 제공하는 모델의 구체적 실현, 예를 들어 OWL 온톨로지 표현 사이의 공개된 매핑을 제공함으로써 입증하는 것이 좋다(SHOULD)"는 것이다.

        8.2.1.2 토큰 매핑

        HTTP 서버가 클라이언트가 토큰을 통해 프로파일을 식별할 수 있게 하려는 경우, URI를 통한 프로파일 식별의 필수 요구사항에 더해, 서버는 지원하는 각 토큰이 어떤 프로파일 URI에 해당하는지 나타내는 것이 좋다(SHOULD). 이 명세의 HTTP 헤더 기능 프로파일을 구현할 때, 서버는 응답 안의 각 profile URI/token 쌍에 대해 Link 헤더([RFC8288])를 포함해야 한다(MUST). 각 Link 헤더는 "http://www.w3.org/ns/dx/prof/Profile"을 Link Target으로 사용해야 하며(MUST), 다음 Target Attribute를 포함해야 한다(MUST).

        대상 속성 대상 속성 값
        rel "type"
        token anchor 속성의 프로파일 URI에 매핑되는 토큰
        anchor token 속성의 토큰에 매핑되는 프로파일의 프로파일 URI

        # The profile URI in the "anchor" element is linked to the token "igsn-r1"

# Further, the relation "type" is used to inform
# that the anchor resource is of type "dcterms:Standard"

Link: <http://www.w3.org/ns/dx/prof/Profile>;
  rel="type";
  token="igsn-r1";
  anchor=<http://schema.igsn.org/description/1.0>

        8.2.2 프로파일별 리소스 가져오기

        특정 프로파일을 준수하는 리소스 표현 가져오기는 해당 리소스에 대해 HTTP GET 요청을 보내고 원하는 프로파일 URI를 Accept-Profile 헤더에 지정하여 수행한다.

        프로파일 기반 콘텐츠 협상을 구현하는 서버는 반환된 프로파일을 나타내는 rel="profile"이 있는 Link 헤더를 포함한 HTTP 응답 헤더로 응답해야 한다(MUST).

        요청과 응답의 URI는 모두 꺾쇠괄호 '<' 및 '>'로 둘러싸야 한다(MUST).

        허용 가능한 프로파일 URI의 범위를 제공할 수 있으며(MAY), 제공되는 경우 콤마로 구분하거나 별도의 Accept-Profile 헤더에 넣어야 한다(MUST).

        선호도는 클라이언트가 URI와 세미콜론 ';'으로 구분된 품질 표시자(q-value)를 순서 지정 메커니즘으로 사용하여 나타낼 수 있다(MAY). q-value가 있는 URI(이 경우 URN)의 예는 <urn:example:profile:x>;q=1.0,이며, 여기서 URI는 <urn:example:profile:x>이고 q-value는 q=1.0이다.

        예제 13은 리소스 /resource/a에 대한 단순 요청을 보여준다. 이 요청은 URI(이 예에서는 URN) urn:example:profile:x 및 urn:example:profile:y로 식별되는 프로파일에 따른 표현을 선호하며, 'q' 값은 첫 번째에 더 높은 선호가 있음을 나타낸다. 서버는 응답을 반환하고, rel="profile"이 있는 Link HTTP 헤더에 해당 식별자를 포함함으로써 urn:example:profile:x에 대한 적합성을 나타낸다.

        예제 13: HTTP 헤더를 사용하여 특정 프로파일을 준수하는 리소스 표현 요청 
        GET /resource/a HTTP/1.1
Accept: text/turtle;q=0.8, application/xml;q=0.5
Accept-Profile: <urn:example:profile:x>;q=1.0,<urn:example:profile:y>;q=0.6
[more request headers]

HTTP/1.1 200 OK

Link: <urn:example:profile:x>; rel="profile"

        8.3.1 QSA 기능 프로파일 설명

        HTTP 헤더 기능 프로파일의 프로파일 협상 방식은 완전 자동화된 프로파일 기반 콘텐츠 협상을 가능하게 하지만, 이 명세의 동기가 된 사용 사례에는 사람이 실행 가능한 협상도 포함되어 있었다. 또한 6. 관련 작업에서 설명한 것처럼, 이전 및 기존 시스템들은 이미 여러 수단을 통해 사람이 실행 가능한 프로파일 기반 콘텐츠 협상을 허용하고 있다.

        사람이 실행 가능한 프로파일 기반 콘텐츠 협상을 허용하고, 기존 시스템과 유사한 메커니즘이 이 명세의 추상 모델의 모든 측면을 어떻게 충족할 수 있는지 보여주기 위해, 이 섹션은 추상 모델의 쿼리 문자열 인수(QSA) 기능 프로파일을 보여준다. 이 기능 프로파일은 추상 모델의 모든 필수 기능을 지원한다는 점에서 HTTP 헤더 기능 프로파일과 기능적으로 동등하지만, HTTP 또는 다른 어떤 기능 프로파일과도 상호 배타적이지 않다. 이 명세의 구현은 여러 환경에서 또는 같은 환경 안에서 다른 방식으로 프로파일 기반 콘텐츠 협상 기능을 구현하기 위해 이 명세의 여러 기능 프로파일에 적합할 수 있다.

        독립적인 IETF 문서 [PROF-IETF]의 대상이기도 한 HTTP 헤더 기능 프로파일과 달리, QSA 기능 프로파일은 여기서 완전히 지정된다. 이 QSA 접근 방식의 두 형식이 제시된다. 첫 번째는 고정 키워드 "QSA Functional Profile"이고, 두 번째는 서버가 원하는 어떤 키워드든 구현할 수 있는 "QSA Alternate Keywords Functional Profile"이다. 이러한 다양한 기능 프로파일은 모두 8.1 이 명세의 기능 프로파일에서 식별된다.

        참고
        시스템이 이러한 기능 프로파일 중 하나 또는 여러 개에 적합함은 A.3 기능 프로파일에 대한 시스템 적합성 입증에 따라 입증될 수 있다. 이 명세에 설명된 기능 프로파일 중 하나 이상에 대한 적합성을 시스템, 예를 들어 서버가 반드시 나타내야 하는 것은 아니라는 점에 유의한다. 모든 시스템이 그렇게 하지는 않을 수 있기 때문이다. 시스템은 서비스 카탈로그의 주석 달린 항목과 같은 여러 방식으로 기능 프로파일에 대한 적합성을 보여줄 수도 있다.
        8.3.1.1 QSA URI 설명

        쿼리 문자열은 지정된 매개변수에 값을 할당하는 URL의 일부이다. QSA는 사람이 웹 브라우저 안에서, 그리고 다른 클라이언트/서버 상황에서 서버에 추가 정보를 전달하기 위해 흔히 사용된다. 쿼리 문자열 키/값 쌍은 물음표 기호 ?로 URI의 스킴, 권한 및 경로와 구분되며, 등호 기호 =로 연결된 키/값 쌍으로 이루어지고, 각 키/값 쌍은 앰퍼샌드 기호 &로 서로 구분된다. 이는 [RFC3986]에 따른 것이다.

        QSA를 사용해 프로파일 기반 콘텐츠 협상을 구현한 리소스 요청 URI의 예는 예제 14에 나와 있다.

        예제 14: QSA를 사용해 프로파일 기반 콘텐츠 협상을 구현한 리소스 요청 URI 예 
        http://example.com/path/to/resource/a?_profile=prof-01

        예제 14에서 리소스 표현에 대해 요청된 프로파일은 토큰 prof-01로 표시되며, 이 토큰은 쿼리 문자열 인수로 리소스의 URI에 추가되어야 한다(MUST). 이 명세의 7.3.1 프로파일 목록에서 허용한 바와 같이, 여기서는 프로파일, 즉 prof-01을 식별하기 위해 토큰이 사용되지만, 해당 토큰은 하나의 특정 클라이언트/서버 세션 안에서 URI에 매핑 가능해야 하며(MUST), 이를 위한 메커니즘은 아래에 설명되어 있다.

        이러한 URI에는 추가 QSA를 사용하거나 다른 기법(예: HTTP 헤더)을 사용하여 콘텐츠 협상의 추가 측면을 포함할 수 있지만(MAY), 포함하는 경우에도 프로파일 기반 콘텐츠 협상 요청의 동작을 변경해서는 안 된다(MUST NOT). 허용 가능한 포함을 보여주기 위해, 예제 14의 URI를 사용하는 클라이언트가 요청 콘텐츠를 Turtle [TURTLE] 명세에 따라 RDF로 직렬화하도록 선호를 나타내고자 한다면, Turtle에 대한 IANA 미디어 유형 목록의 토큰인 text/turtle을 사용하고, URI 작성 요구사항 [RFC3986]에 따라 예제 15와 같이 URI를 작성할 수 있다.

        예제 15: 프로파일 및 미디어 유형에 의한 콘텐츠 협상이 포함된 QSA URI 예 
        http://example.com/path/to/resource/a?_profile=prof-01&_mediatype=text/turtle
        참고: URL의 최대 길이
        쿼리 문자열 인수가 중요한 정보를 전달하기 위해 URI(또는 URL)를 사용하는 경우, 구현자는 URI/URL을 사용하는 QSA가 포함된 전체 요청 URI의 총 길이가 길이 제한을 초과하지 않도록 해야 한다. [RFC9110]의 §4.1은 발신자와 수신자가 최소 8,000 옥텟의 요청 라인을 지원할 것을 권고한다. 그러나 일부 클라이언트 및 서버 구현은 2,000자를 넘는 URL을 허용할 수 없다. 예를 들어 Sitemap 프로토콜은 URL 길이 제한이 2,048자이다. URL 길이와 관련된 문제에 대한 더 긴 논의는 stackoverflow의 이 질문을 참조한다.
        8.3.1.2 키 명명

        이 명세에는 쿼리 문자열 인수를 사용하는 사람 클라이언트가 사용할 수 있도록, QSA 키 명명 요구사항으로 구별되는 두 가지 서로 다른 기능 프로파일이 포함되어 있다. 두 프로파일은 "QSA Functional Profile"과 "QSA Alternate Keywords Functional Profile"이며, 전자는 후자의 프로파일이다. 이는 전자가 이 명세의 필수 기능을 달성하는 방법에 대해 더 엄격한 적합성 규칙("더 좁은" 규칙)을 포함하기 때문이다. 이러한 기능 프로파일은 8.1 이 명세의 기능 프로파일에서 식별되고 정의된다.

        "QSA Functional Profile"을 준수하려면, 프로파일 토큰 또는 URI를 나타내기 위해 QSA 키 _profile을 사용해야 하며(MUST), 리소스 표현의 미디어 유형을 나타내기 위해 키 _mediatype을 사용하는 것이 좋다(SHOULD).

        "QSA Alternate Keywords Functional Profile" 프로파일을 준수하는 경우, [RFC3986]의 명세 안에서 허용되는 어떤 키 값이든 원하는 프로파일을 나타내는 데 사용할 수 있다(MAY). 그러나 이 기능 프로파일을 준수하는 서버는 아래 8.3.4 QSA 키 탐색에서 자세히 설명한 것처럼, 사용되는 값을 클라이언트가 발견할 수 있게 하는 메커니즘도 제공해야 한다(MUST).

        8.3.2 프로파일 목록

        "QSA Functional Profile"에 대한 적합성을 위해, 클라이언트가 프로파일 목록 요청을 할 수 있도록 서버는 _profile QSA 키를 지원하는 것이 좋다(SHOULD). 이 요청에는 예약된 토큰 alt를 사용하는 것이 좋으며(SHOULD), 예를 들면 _profile=alt이다.

        "QSA Alternate Keywords Functional Profile"에 대한 적합성을 위해서는 _view=alternates와 같은 다른 키/값 쌍을 사용할 수 있지만(MAY), 이 경우 구현하는 서버는 8.3.4 QSA 키 탐색에 따라 그 키를 발견할 수단을 제공해야 한다(MUST).

        프로파일 목록 요청에 대한 서버의 응답은 해당 리소스의 표현을 지원하는 모든 프로파일 목록과, 선택적으로 그 표현에 대해 지원되는 미디어 유형도 제시하는 것이 좋다(SHOULD).

        서버는 HTTP 헤더 기능 프로파일에 따라(Link 헤더 사용) 응답의 HTTP 헤더에 대체 프로파일 정보를 표현하는 것이 좋으며(SHOULD), 리소스의 기본 프로파일 표현 대신 응답 본문에 그 정보를 표현할 수도 있다(MAY). 이 본문 콘텐츠 허용은 사람이 더 낮은 수준의 HTTP 정보를 볼 필요 없이 웹 브라우저에서 리소스에 대한 대체 프로파일 적합 표현 선택지를 쉽게 읽을 수 있게 하기 위한 것이다.

        서버가 HTTP 본문에 대체 프로파일 정보를 제공하는 경우, 서버는 아래 프로파일별 리소스 가져오기 기능에 사용되는 것과 동일한 미디어 유형 협상 방법을 사용하여 클라이언트가 응답의 특정 미디어 유형을 협상할 수 있도록 허용할 수 있다(MAY).

        리소스의 대체 프로파일 표현을 HTTP 헤더 콘텐츠뿐 아니라 JSON 형식의 HTTP 본문 콘텐츠로도 전달하도록 하는 예제 요청은 예제 16과 같을 수 있다.

        8.3.2.1 QSA 대체 표현 데이터 모델 구현

        QSA 기능 프로파일에 따라 이 명세를 구현하는 경우, 구현은 대체 표현 데이터 모델에 따라 대체 표현 정보를 전달해야 한다(MUST). HTTP 헤더 기능 프로파일에 따라 HTTP Link 헤더를 사용해 그렇게 할 수도 있고(MAY), 다른 접근 방식을 사용할 수도 있다(MAY).

        [RFC8288] (Web Linking)의 서론에서 언급한 것처럼, HTML 및 일부 다른 데이터 모델은 "잘 정의된 링크 개념"을 가지고 있으므로, QSA 구현자는 HTTP 본문 콘텐츠를 통해, 아마도 HTML 또는 다른 데이터 모델/형식으로 대체 표현 데이터 모델 정보의 전달을 구현할 수 있다(MAY). 이는 QSA 구현을 사용하는 사람 클라이언트 사용자가 웹 브라우저나 다운로드 가능한 파일 안에서 이를 볼 수 있게 해 도움을 줄 수 있다.

        8.3.2.2 토큰 매핑

        현재 미디어 유형에 의한 HTTP 콘텐츠 협상의 관례는 text/html 또는 application/ld+json과 같은 미디어 유형에 대해 토큰을 사용하며, 그 토큰은 IANA의 미디어 유형 목록에 등록되어 있다. 프로파일 기반 콘텐츠 협상 시스템 구현자는 미디어 유형 식별자에 대해 해당 목록의 토큰을 사용하고, 다른 콘텐츠 협상 차원 (언어 등)의 식별자에 대해서는 HTTP 콘텐츠 협상 모범 사례를 따르는 것이 좋다(SHOULD).

        참고: 미디어 유형에 대한 URI 사용
        IANA의 토큰을 기반으로 미디어 유형에 대한 URI를 만든 여러 이니셔티브가 존재하며, 예로 conneg.info가 있다. 이러한 URI는 미디어 유형을 나타내는 데 사용할 수 있다.

        프로파일의 중앙 등록부를 만들자는 제안은 없다. 이러한 저자들은 장기적으로 그것이 지속 가능하지 않다고 보는데, 이는 만들어질 프로파일 수가 많을 가능성이 있고, 프로파일이 대체로 커뮤니티별 성격을 가질 가능성이 크기 때문이다 (각 커뮤니티는 널리 관련되지는 않을 자신의 필요에 맞는 프로파일을 만들 것이다).

        7.2 프로파일 식별에 따라, 모든 프로파일은 URI로 식별되어야 한다(MUST). URI는 보편적으로 고유하므로 식별자 중복을 피하기 위한 등록이 필요하지 않기 때문이다. 그러나 이 명세의 두 QSA 기능 프로파일 중 하나를 준수하는 시스템은, 클라이언트/서버 상호작용 중 프로파일을 식별하기 위해 URI를 사용하는 대신, 등록되지 않았고 보편적으로 고유하지 않은 토큰을 사용하여 프로파일을 식별할 수 있다(MAY). 다만 그렇게 하는 경우, 클라이언트가 프로파일 토큰/URI 매핑을 발견할 수 있는 방법을 제공해야 한다(MUST).

        프로파일 URI에 대한 토큰을 클라이언트가 사용할 수 있게 하려는 QSA 서버는 8.2.1.2 토큰 매핑의 HTTP 헤더 기능 프로파일에 제공된 지침을 따르는 것이 좋다(SHOULD).

        8.3.2.3 리소스 URL

        QSA 기반 프로파일 협상이 이루어지는 리소스 URL은 어떤 QSA 기반 시스템에서도 다른 리소스 URI의 QSA 값 자체가 되지 않는 것이 좋다(SHOULD NOT). 이러한 메커니즘은 내부적으로 사용될 수 있고 레거시 시스템이 프로파일 협상에 사용하지만, 이러한 QSA 프로파일에 대한 적합성을 더 알아보기 쉽게 하기 위해 클라이언트에게는 숨기는 것이 가장 좋다. 예제 18은 이를 보여준다.

        예제 18: 리소스 URL 자체는 다른 URL의 매개변수가 되지 않는 것이 좋음 
        For the representation of Resource X, according to Profile Y, in Media Type Z:

Rather than:
GET /single/endpoint \
            ?resource=http://example.org/resource/X \
            &_profile=Y \
            &_mediatype=Z HTTP/1.1

Use:
GET /resource/X?_profile=Y&_mediatype=Z HTTP/1.1

        8.3.3 프로파일별 리소스 가져오기

        이 명세의 "QSA Functional Profile" 프로파일을 준수하려면, 서버는 클라이언트가 _profile 쿼리 문자열로 식별하는 프로파일에 따라 리소스를 요청할 수 있도록 허용해야 한다(MUST). 프로파일을 식별하는 데 토큰 또는 URI를 사용할 수 있으므로, 서버는 둘 중 하나를 수락해야 한다(MUST). 서버는 인코딩된 URI와 인코딩되지 않은 URI를 모두 수락할 수 있지만(MAY), 둘 중 하나만 수락할 수도 있다(MAY). URI는 꺾쇠괄호 '<' 및 '>'로 둘러싸야 한다(MUST).

        이 명세의 "QSA Alternate Keywords Functional Profile" 프로파일을 준수하려면, 서버는 클라이언트가 서버 구현자가 선택한 키로 식별하는 프로파일에 따라 리소스를 요청할 수 있도록 허용해야 하지만(MUST), 서버는 8.3.4 QSA 키 탐색에 따라 그 키를 발견할 수단도 제공해야 한다(MUST).

        프로파일별 리소스 가져오기를 구현하는 QSA 서버는 클라이언트가 여러 프로파일 중 하나에 따른 리소스 표현에 대한 선호를 나타낼 수 있도록 허용하는 것이 좋다(SHOULD). 이러한 요청은 프로파일을 식별하는 데 사용되는 QSA 키/값 쌍의 값 안에 프로파일 식별자(URI 또는 토큰)의 순서 있는 목록을 포함함으로써 프로파일 선호를 나타내야 한다(MUST). 예를 들어 리소스 표현에 대해 profile-z, 그다음 http://example.org/profile/y, 마지막으로 profile-x를 그 선호 순서대로 선호하는 클라이언트는 다음과 같이 요청할 수 있다.

        GET /resource/a?_profile=profile-z,<http://example.org/profile/y>,profile-x

        서버는 응답에 rel="profile"이 있는 Link HTTP 헤더를 포함하여 실제로 반환된 프로파일을 나타내야 하며(MUST), 다른 방식으로도 반환된 프로파일을 나타낼 수 있다(MAY). 서버는 이스케이프된 URI를 지원하는 것이 좋으며(SHOULD), 프로파일을 식별하는 이스케이프되지 않은 URI도 지원할 수 있고(MAY), 둘 다 지원할 수도 있다.

        리소스 표현에 대해 여러 미디어 유형 형식을 구현하는 서버는, 클라이언트가 그들에 대한 선호 순서를 유사한 방식으로 지정할 수 있도록 허용하는 것이 좋다(SHOULD).

        8.3.4 QSA 키 탐색

        이 기능은 이 명세의 "QSA Alternate Keywords Functional Profile" 프로파일에 대한 적합성을 주장하는 서버에만 관련된다.

        "QSA Alternate Keywords Functional Profile"에 대한 적합성을 주장하는 서버는 클라이언트가 "QSA Functional Profile"의 _profile 대신 사용되는 QSA 키와, 어떤 키/값 조합으로든 구현되어야 하는 _profile=alt에 해당하는 것을 발견할 수 있게 하는 방법을 구현해야 한다(MUST). 이를 통해 서버에 대한 지식이 거의 없는 클라이언트도 프로파일 목록 및 프로파일별 리소스 가져오기 요청을 만드는 방법을 발견할 수 있다.

        서버는 미디어 유형 및 기타 콘텐츠 협상 차원을 나타내는 데 사용되는 QSA 키도 클라이언트가 발견할 수 있도록 허용하는 것이 좋다(SHOULD).

        "QSA Alternate Keywords Functional Profile"이 지원되는 리소스에 대한 어떤 요청에 응답하는 서버도, HTTP 기능 프로파일에 따라 대체 프로파일 및 미디어 유형을 나타내는 HTTP 헤더를 포함하는 것이 좋다(SHOULD). 서버는 대신 또는 추가로 같은 정보를 나타내는 HTTP 본문 콘텐츠를 제공할 수 있다(MAY). 그렇게 하는 경우, 이러한 정보는 URI 요청에 대한 기본 응답, 즉 QSA 없이 이루어진 요청에 대한 응답에 존재하는 것이 좋다(SHOULD). 일련의 예제 요청은 예제 19에 제시되어 있다.

        예제 19: QSA 키 탐색을 위한 예제 요청 및 응답 
        # A client makes a request for Resource A not knowing if any Content
# Negotiation by Profile is supported. It supplies an Accept-Profile
# header just in case. For extra efficiency, the client could have
# made a HEAD request instead of a GET

GET /resource/a HTTP/1.1
Accept-Profile: <http://example.org/profile/x>

# The server does not understand the HTTP Get Resource By Profile
# request (doesn't support the HTTP Headers Functional Profile) but is
# able to supply an HTTP Link header indicating alternate resource
# representations. It can be seen from the Link header that keys other
# than _profile & _mediatype are in use - view & format - thus this is
# QSA Alt, not a QSA Functional Profile-conformant system

# The resource representations available conform to profile-x & profile-y.
# The profile-x-conformant representation is available in HTML & Turtle,
# the profile-y-conformant representation is available only in XML

HTTP/1.1 200 OK
Link:
  <http://example.org/resource/a?view=profile-x&format=text/html>;
          rel="canonical";
          type="text/html";
          formats="http://otherexample.org/profile/x",
  <http://example.org/resource/a?view=profile-x&format=text/turtle>;
          rel="alternate";
          type="text/turtle";
          formats="http://otherexample.org/profile/x",
  <http://example.org/resource/a?view=profile-y&format=application/xml>;
          rel="alternate";
          type="application/xml";
          formats="http://otherexample.org/profile/y"

# Note that here the server does not directly indicate the profile served
# (there is no Link header with rel="profile" present) but this can be inferred
# by the link header with rel="canonical"

        위 예제 19의 Link 헤더는 프로파일 목록 요청이 전달하는 모든 정보를 전달하지만, 웹 브라우저에서는 직접 보이지 않는다. 예제 16은 프로파일을 나열하는 동등한 Link 헤더와 HTTP 본문 정보를 포함하는 요청/응답 쌍을 보여주며, 후자는 브라우저에서 볼 수 있다. 그러나 이 요청을 작성하는 클라이언트는 서버의 기본 리소스 표현이 아니라 이 응답을 트리거하는 데 QSA 키/값 쌍 _profile=alt가 사용된다는 것을 알아야 한다.

        "QSA Alternate Keywords Functional Profile"을 준수할 때 프로파일 목록에 어떤 QSA 키/값 쌍이 사용되는지를 클라이언트에게 전달하기 위해, 서버는 위의 프로파일 목록 전달 방법을 따라, 리소스의 한 표현이 URI http://www.w3.org/ns/dx/conneg/altr로 식별되는 Alternate Profiles Data Model을 준수하는 것으로 제공된다는 점을 나타내는 것이 좋다(SHOULD). 이는 예제 20에서 보여주며, 이는 예제 19의 확장이다.

        예제 20: Alternate Profiles Data Model 적합 응답을 보여주는 이전 예제의 확장 
        GET /resource/a HTTP/1.1
Accept-Profile: <http://example.org/profile/x>

--

HTTP/1.1 200 OK
Link:
  <http://example.org/resource/a?view=profile-x&format=text/html>;
          rel="canonical";
          type="application/html";
          formats="http://otherexample.org/profile/x",
  <http://example.org/resource/a?view=profile-x&format=text/turtle>;
          rel="alternate";
          type="text/turtle";
          formats="http://otherexample.org/profile/x",
  <http://example.org/resource/a?view=profile-y&format=application/xml>;
          rel="alternate";
          type="application/xml";
          formats="http://otherexample.org/profile/y"
  <http://example.org/resource/a?view=altrep&format=application/ld+json>;
          rel="alternate";
          type="application/ld+json";
          formats="http://www.w3.org/ns/dx/connegp/altr"

[default response content]

        예제 20은 리소스 /resource/a에 대해 7.4 대체 표현 데이터 모델에서 정의된 Alternate Profiles Data Model을 식별하는 URI인 http://www.w3.org/ns/dx/connegp/altr 명세/프로파일을 준수하는 표현이 존재한다는 것을 보여준다.

        이 예제는 또한 QSA view=altrep를 사용하여 Alternate Profiles Data Model 적합 응답에 대한 요청을 작성할 수 있음을 보여준다. 따라서 http://example.org/resource/a?view=altrep를 역참조하면 /resource/a의 기본 표현이 아니라, 예제 20의 Link 헤더 콘텐츠와 동등한 콘텐츠도 산출하는 응답이 생성된다.

        9. Link 속성

        9.1 토큰

        Link 헤더 필드에서 사용될 때, token 속성은 클라이언트가 anchor 속성에 주어진 전체 프로파일 URI의 대안으로 사용할 수 있는(MAY) 토큰을 지정하는 데 사용된다.

        프로파일 URI의 대안으로 토큰을 사용하는 것은 기본적으로 현재 리소스 (즉, 현재 요청 URI로 식별되는 리소스)로 제한된다는 점에 유의해야 한다. 서버는 이에 대해 더 넓은 범위를 사용할 수 있지만(MAY), 서버 문서가 다른 수단을 통해 명시적으로 다른 지침을 제공하지 않는 한 클라이언트는 그것에 의존해서는 안 된다.

        profile 속성 값의 ABNF는 token / quoted-string이며, 여기서 "token"과 "quoted-string"은 [RFC9110]의 5.6절에 정의된 것과 같다. [RFC8288]의 3절에 정의된 link-param 값에 대한 규칙이 적용된다.

        예제 21: 프로파일 URI를 토큰에 연결하기 위해 Link 속성 "token" 사용

        14. 보안 및 개인정보 보호

        이 섹션은 비규범적이다.

        HTTP를 사용하여 협상하고 전송한다는 것은 해당 프로토콜과 관련된 모든 개인정보 보호 및 보안 문제가 프로파일 협상에도 관련됨을 의미한다. 예를 들어 사용자 에이전트, accept-headers, IP 주소 등과 같은 정보는 잠재적으로 식별 정보로 사용될 수 있으며, 특히 IP 주소는 지리적 위치와 기관 소속에 관한 정보를 추가한다. 또한 협상 과정의 시작 부분에서 허용 가능한 프로파일 목록을 제공하면 사용자 관심사에 관한 정보가 드러날 수 있으며, 이는 그러한 정보를 사용자 프로파일에 추가하는 데 사용될 수 있다.

        이러한 문제에 대한 더 완전한 관점은 이 산출물에 대한 개인정보 보호 및 보안 설문지를 참조한다.

        A.2 이 명세의 기능 프로파일에 대한 Profiles Vocabulary 설명

        이 명세에는 8.1 이 명세의 기능 프로파일에서 식별되고 말로 설명된 여러 개의 서로 다른 기능 프로파일이 포함되어 있다. 이 부록은 Profiles Vocabulary [DX-PROF]에 따라 이러한 기능 프로파일과 그들 사이의 관계에 대한 설명을 제시한다.

        코드 목록 1의 RDF(turtle 구문) 코드는 Content Negotiation by Profile을 dcterms:Standard로 정의하며, [DX-PROF]에서의 그 정의는 이 문서의 명세 정의와 일치한다. 이 문서는 동작을 설명하므로 이 명세는 기능 명세임에 유의한다. 그런 다음 그 4개의 프로파일은 일반적인 PROF 모델링에 따라 prof:Profiles라고 불린다. 이 4개의 기능 프로파일은 계층으로 제시되며, 프로파일은 표준을 직접 프로파일링하거나, QSA Functional Profile의 경우처럼 다시 표준을 프로파일링하는 다른 프로파일을 프로파일링한다. 이는 코드 목록 아래의 그림 4에도 그래픽으로 표시되어 있다.

        A.3 기능 프로파일에 대한 시스템 적합성 입증

        8.1 이 명세의 기능 프로파일에 제시된 이 명세의 기능 프로파일 식별과, 이 부록에서 Profiles Vocabulary [DX-PROF]를 사용해 설명된 그 관계를 통해, 시스템은 [DX-PROF] 메커니즘을 사용하여 이 명세 또는 그 기능 프로파일 중 어느 것에 대한 적합성도 보여줄 수 있다. 이는 [DCTERMS] 술어 dcterms:conformsTo를 사용하여 수행된다. 예를 들어 URI <http://example.org/system/a>로 식별되는 시스템이 URI <SPEC_OR_PROFILE_URI>로 식별되는 명세 또는 기능 프로파일에 적합하다고 주장하려면 다음과 같이 할 수 있다.

        <http://example.com/system/a> dcterms:conformsTo <SPEC_OR_PROFILE_URI> .

        <SPEC_OR_PROFILE_URI>는 이 명세의 URI인 https://www.w3.org/TR/dx-connegp/일 수 있지만, 가장 좋은 경우에는 8.1 이 명세의 기능 프로파일에 나열된 프로파일 URI 중 하나나 다른 기능 프로파일의 URI가 될 것이다. 기능 프로파일 URI는 명세 전체보다 범위가 더 좁기 때문에, 이를 인용하면 무엇에 적합한지 훨씬 더 명확하기 때문이다.

        여러 적합성 대상, 즉 이 명세나 그 기능 프로파일에 대한 적합성을 주장하려는 시스템은 dcterms:conformsTo를 여러 번 사용하여 그렇게 할 수 있다.

        코드 목록 2의 코드는 [VOCAB-DCAT-2]를 사용하여 문서화되고, 예제 49와 같은 그 예제의 일부를 차용한 가상의 웹 서비스를 보여준다. 여기에는 [VOCAB-DCAT-2] 및 [DX-PROF]에 따라 사용되는 술어 dcterms:conformsTo가 포함되어 있다. 여기서는 QSA Alternate Keywords Functional Profile 프로파일에 대한 적합성을 주장하며, 이는 8.1 이 명세의 기능 프로파일에 따라 식별된 URI http://www.w3.org/ns/dx/connegp/profile/qsa-alt로 표시된다.

        A.5 Content Negotiation by Profile에 대한 DCAT Distributions 지원 설명

        DCAT [VOCAB-DCAT-2] dcat:Dataset은 dcat:DataService를 통해 접근 가능할 수 있으며, 해당 서비스는 이 명세의 하나 이상의 기능 프로파일을 지원할 수 있다. 이 경우 코드 목록 5에 예시된 것처럼, 서비스가 관련 기능 프로파일을 참조할 때 술어 dcterms:conformsTo를 사용하여 지원을 선언하는 것이 좋다.

        DCAT 2는 데이터 서비스가 자신이 접근을 제공하는 데이터셋의 개별 데이터 항목을 식별자로 접근할 수 있게 하는지 지정하는 표준적 방법을 제공하지 않으므로, 이 예제는 전체로 배포되는 데이터셋과 관련된다는 점에 유의한다. 그럼에도 dcterms:conformsTo의 사용은 개별 항목에 접근하는 메커니즘을 선언하는 데이터 서비스에도 적용될 수 있다. 이 메커니즘은 dcat:endpointDescription을 통해 식별될 수 있다.
