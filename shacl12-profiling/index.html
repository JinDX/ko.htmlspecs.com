초록

이 문서는 SHACL 프로파일링을 정의합니다.

SHACL, 즉 Shapes Constraint Language는 RDF 그래프의 구조를 설명하기 위한 언어입니다. SHACL은 검증, 추론, 도메인 모델링, 다른 에이전트에 정보를 제공하기 위한 온톨로지 생성, 사용자 인터페이스 구축, 코드 생성, 데이터 통합과 같은 다양한 목적으로 사용될 수 있습니다.

SHACL 프로파일링은 SHACL의 프로파일과 SHACL을 사용한 프로파일링을 기술할 수 있게 하는 SHACL Shapes Constraint Language의 요소를 정의합니다. 이 문서의 범위는 SHACL Shapes를 포함하는 그래프를 비롯한 RDF 그래프의 프로파일링으로 한정됩니다.

이 명세는 Data Shapes 작업 그룹에서 발행합니다.

1. 소개

이 문서는 SHACL의 프로파일링과 SHACL을 사용한 RDF 그래프 프로파일링이라는 좁은 범위의 작업만 다루므로, 이에 필요한 어휘 요소만 정의합니다.

이 문서는 프로파일 어휘에서 정한 더 넓은 범위의 작업과 정의에 부합하고자 합니다.

1.1 SHACL 프로파일링이란 무엇인가?

정의상 SHACL은 RDF 데이터를 제약하므로, shapes graph에 따라 유효한 데이터는 data graph의 프로파일이 됩니다. shapes graph가 data graph의 모든 요소를 검증하면, 유효한 결과 데이터는 data graph의 "null" 프로파일이 됩니다. 이는 원래 data graph와 동일하다는 뜻입니다.

프로파일 어휘에서는 프로파일을 다음과 같이 정의합니다:

다른 표준의 사용을 제약, 확장, 결합하거나 그 사용에 관한 지침 또는 설명을 제공하는 표준

shapes graph를 "표준"으로 본다면, shapes graph에 따라 유효한 데이터가 검증된 data graph의 프로파일일 뿐 아니라, shapes graph 자체도 data graph에 사용된 데이터 모델의 프로파일 역할을 합니다.

이 문서에서는 최적의 프로파일링을 위해 SHACL 정보를 패키징하는 방법을 설명하고, 각 SHACL 명세에 대해 생성된 RDF 데이터를 패키징하는 예를 보여 줍니다.

2.3 그룹 식별 SHACL 요소

sh:ShapesGraph의 인스턴스를 사용하는 것이 좋습니다(SHOULD). 이를 통해 검증에 사용하는 SHACL 요소의 인스턴스를 그룹화합니다.

SHACL 요소는 다른 많은 RDF 정의 데이터와 마찬가지로 흔히 OWL 2 Web Ontology Language RDF-Based Semantics (Second Edition)의 owl:Ontology 클래스 인스턴스 안에 그룹화되어 왔습니다.

예를 들어, Open Geospatial Consortium의 공간 RDF 데이터용 GeoSPARQL 1.1 표준은 SHACL 검증기를 제공합니다. 이 검증기는 Turtle 파일 안에 27개의 sh:NodeShape 인스턴스와 비슷한 수의 sh:PropertyShape 인스턴스를 포함합니다. 이 파일에는 검증 리소스의 수정일, 사용 라이선스 등과 같은 메타데이터를 제시하는 owl:Ontology 인스턴스도 포함됩니다.

이 권고는 기존 관행을 대체하며, sh:ShapesGraph를 대신 사용할 것을 권고합니다. 이는 SHACL 1.2 Core에서 SHACL 요소를 그룹화하기 위해 특별히 정의한 클래스입니다.

NodeShapes와 Class 정의처럼 SHACL과 OWL 요소가 혼합되어 있다면 owl:Ontology를 계속 사용하는 것이 좋습니다(SHOULD).

2.4 요소 정의 표시

검증에 사용하는 SHACL 요소의 인스턴스는 SHOULD 요건으로 자신을 정의하는 sh:ShapesGraph 인스턴스를 rdfs:isDefinedBy 술어로 나타내는 것이 좋습니다.

SHACL 요소를 owl:Ontology 인스턴스로 식별한 그룹에 넣을 때는 RDF 파일에 요소와 온톨로지 인스턴스를 함께 담는 것이 일반적인 관행이었습니다. 이는 데이터 교환에는 합리적이지만, 교환한 파일을 RDF 데이터베이스에 저장하면 컨테이너 인스턴스와 그 안에서 정의한 SHACL 요소 사이의 연관이 사라질 수 있습니다. 명명된 그래프에 적재하면 그 그래프가 온톨로지와 SHACL 요소를 그룹화하여 연관을 유지할 수도 있습니다. 그러나 이는 비의미적 연관, 즉 그래프 안에서 직접 보이지 않는 연관입니다.

이 권고에 따르면 SHACL 요소의 작성자는 SHOULD 요건으로 해당 SHACL 요소가 정의된 그룹을 나타내는 것이 좋습니다. RDF에서 이를 주장하는 예는 다음과 같습니다:

ex:sg-M a sh:ShapesGraph ; . ex:shape-1 a sh:NodeShape ; rdfs:isDefinedBy ex:sg-M ; .
{ "@id": "ex:ont-M", "@type": "sh:ShapesGraph" }, { "@id": "ex:shape-1", "@type": "sh:NodeShape", "rdfs:isDefinedBy": { "@id": "ex:ont-M" } }
참고

2.5 Shapes와 Classes의 구문적 변형 절(SHACL 1.2 Core)에서는 property shapes를 공백 노드로 선언할 수 있지만, 그래프 간 재사용이 더 쉬워지므로 IRI로 선언하는 것이 바람직하다고 경고합니다. 이 절에 따라 shape에 관한 정보를 포함한다면 IRI를 사용하는 것이 좋습니다(SHOULD).

2.5 요소 사용 표시

sh:ShapesGraph 인스턴스가 SHACL 요소를 정의하지 않고 검증에 사용한다면, SHOULD 요건으로 해당 SHACL 요소를 rdfs:member 술어로 멤버임을 나타내는 것이 좋습니다.

SHACL 요소가 어떤 요소 그룹 안에서 사용되지만 그 그룹에서 정의된 것은 아니라면, 해당 그룹에서 정의된 것으로 표시하지 않는 것이 좋습니다(SHOULD NOT). 따라서 위 절의 권고는 관련이 없습니다. SHACL 요소를 정의한 곳이 아닌 그룹 안에서 재사용하는 것은 Linked Data 원칙 [LDP]에 따라 예상되고 권장되는 일입니다.

rdfs:member 술어를 사용하여 SHACL 요소가 자신을 정의하지 않은 그룹에 포함됨을 나타내는 예는 다음과 같습니다. 위 예처럼 rdfs:isDefinedBy를 사용하는 방법도 함께 보여 줍니다.

# 'Shapes Graph M' uses a Shape defined by 'Shapes Graph Other' ex:sg-M a sh:ShapesGraph ; rdfs:member ex:shape-1 ; . ex:sg-Other a sh:ShapesGraph ; . ex:shape-1 a sh:NodeShape ; rdfs:isDefinedBy ex:sg-Other ; .
{ "@id": "ex:shape-1", "@type": "sh:NodeShape", "rdfs:isDefinedBy": { "@id": "ex:ont-Other" } }, { "@id": "ex:ont-Other", "@type": "sh:ShapesGraph" }, { "@id": "ex:ont-M", "@type": "sh:ShapesGraph", "rdfs:member": { "@id": "ex:shape-1" } }

2.6 그룹 의존성 표시

sh:ShapesGraph 인스턴스를 사용하여 검증에 사용하는 SHACL 요소를 그룹화할 때는 SHOULD 요건으로 다른 SHACL 요소 그룹에 대한 의존성을 나타내는 것이 좋습니다. 이 그룹들은 sh:ShapesGraph 인스턴스로 식별하고 의존성은 owl:imports 술어로 나타냅니다.

SHACL 검증 도구에서는 RDF 데이터가 담긴 파일 같은 한 컬렉션의 SHACL 요소를 owl:imports 명령으로 다른 컬렉션에 가져오는 관행이 확립되어 있습니다. pySHACL [PYSH] 등 많은 SHACL 검증 엔진이 이를 수행합니다. 이 주장에서 특정 검증 엔진의 동작이 발생할 것으로 기대하지 않더라도, 한 컬렉션 또는 그룹에서 다른 것으로의 의존성을 나타내는 데 이 관행을 권고합니다. SHACL 데이터 관리에도 유용한 정보를 제공할 가능성이 있기 때문입니다.

owl:imports의 예는 아래 예와 같습니다.

# 'Shapes Graph N' imports 'Shapes Graph M' ex:sg-M a sh:ShapesGraph ; . ex:sg-N a sh:ShapesGraph ; owl:imports ex:sg-M ; .
{ "@id": "ex:ont-N", "@type": "owl:Ontology", "owl:imports": { "@id": "ex:ont-M" } }, { "@id": "ex:ont-M", "@type": "owl:Ontology" }

의존 대상의 버전을 매우 구체적으로 나타내려면, 아래 예처럼 owl:imports는 MAY 요건으로 sh:ShapesGraph의 특정 버전을 대상으로 삼을 수 있습니다. 해당 버전은 owl:versionIRI 술어로 나타냅니다.

# 'Shapes Graph N' imports 'Version 4.2 of Shapes Graph M' ex:sg-M a sh:ShapesGraph ; owl:versionIRI ex:sg-M-4.2 ; . ex:sg-N a sh:ShapesGraph ; owl:imports ex:sg-M-4.2 ; .

의존성 계산

한 shapes graph가 다른 shapes graph에 의존함은 SHOULD 요건으로 dcterms:requires 같은 술어로 나타내는 것이 좋습니다. 위 패키징 권고를 따르면 한 shapes graph의 다른 shapes graph에 대한 의존성을 MAY 요건으로 다음 규칙을 사용해 계산할 수 있습니다. 이 규칙들은 dcterms:requires를 사용합니다:

# dependency through element definition and reuse RULE { ?sg1 dcterms:requires ?sg2 . } WHERE { ?sg1 a sh:ShapesGraph ; rdfs:member ?shape ; . ?shape rdfs:isDefinedBy ?sg2 . ?sg2 a sh:ShapesGraph . FILTER (?sg1 != ?sg2) # exclude self-dependencies } # dependency through importing # rule linking means un-versioned importing only runs if versioned importing does not RULE { ?sg1 dcterms:requires ?sg2 . } WHERE { ?sg1 owl:imports ?sg2 . NOT { ?sg1 dcterms:requires ?sg2 . } } # versioned importing RULE { ?sg1 dcterms:requires ?sg2_v . } WHERE { ?sg1 owl:imports ?sg2 . ?sg2 owl:versionIRI ?sg2_v . } # transitive dependency RULE { ?sg1 dcterms:requires ?sg3 . } WHERE { ?sg1 dcterms:requires ?sg2 . ?sg2 dcterms:requires ?sg3 . FILTER (?sg1 != ?sg3) }

2.7 맥락과 함께 검증 결과 보존하기

results graph 요소의 결과를 보존할 때는 validation report의 맥락을 SHOULD 요건으로 SHACL 프로파일링 어휘의 요소를 사용하여 제공하는 것이 좋습니다.

앞으로도 이해할 수 있도록 results graph를 보존하려면 validation report에 맥락을 연결해야 할 수 있습니다. 알아 두어야 할 중요한 맥락으로는 검증의 입력인 data graph와 shapes graph, 검증 시점, 검증을 수행한 시스템의 세부 정보가 있습니다.

이러한 사건, 즉 검증에 관한 세부 정보는 PROV-O: The PROV Ontology에서 특성화하는 일반적인 사항입니다. PROV-O는 맥락을 보존하는 일반 모델인 출처 정보를 제공합니다. 여기서는 아래 SHACL 프로파일링 어휘에서 PROV-O의 기본 요소를 특수화합니다. 이 어휘는 SHACL 1.2 Core 어휘의 부분집합입니다.

그림 1의 출발점 도식에서 보듯 일반적인 PROV-O 출처 모델은 prov:Activity 인스턴스를 시간적 사건으로 봅니다. 이 사건은 prov:used로 사물을 사용하고 prov:generated로 사물을 생성하며, 사물은 prov:Entity 인스턴스입니다. 사건을 수행하는 사람, 조직 또는 시스템은 prov:wasAssociatedWith로 연결되는 prov:Agent 인스턴스입니다.

SHACL 검증 사건인 처리는 prov:Activity의 특수화된 형태인 sh:ValidationActivity로 표현됩니다. 프로세서 객체는 prov:Agent의 특수화된 형태인 sh:ValidationAgent로 표현됩니다.

SHACL 1.2 Core의 검증 절에서는 처리에 필요한 입력이 data graph인 sh:DataGraph와 shapes graph인 sh:ShapesGraph임을 명시합니다. 프로세서 구현은 추론 등에 쓰이는 추가 리소스도 지원할 수 있습니다. 또한 처리가 sh:ValidationReport 인스턴스를 생성한다고 정의합니다. 이들은 모두 prov:Entity의 특수화된 형태입니다.

sh:ValidationActivity는 적어도 data graph와 shapes graph를 입력으로 가져야 하며, 두 입력의 역할은 매우 다릅니다. 따라서 이를 나타내기 위해 prov:used의 두 특수화된 형태인 sh:usedDataGraph와 sh:usedShapesGRaph를 제공합니다.

아래 그림은 앞서 언급한 SHACL 요소를 PROV-O 속성으로 서로 연결하고, PROV-O의 그림 1에 따라 모양과 색을 지정하여 보여 줍니다.

위 모델링을 사용하면 아래 예처럼 "활동 중심" 및 "출력 연결" 형태의 처리를 모델링할 수 있습니다. 이를 통해 각각 시간성을 갖춘 출처 정보와 더 간단한 출처 정보를 표현할 수 있습니다.

# activity-centric ex:dg a sh:DataGraph ; . ex:sg a sh:DataGraph ; . ex:ag a sh:ValidationAgent ; . ex:vr a sh:ValidationReport ; . ex:ac a sh:ValidationActivity ; prov:wasAssociatedWith ex:ag ; prov:used ex:dg , # or sh:usedDataGraph ex:sg ; # or sh:usedShapesGraph prov:generated ex:vr ; .
{ "@id": "ex:dg", "@type": "sh:DataGraph" }, { "@id": "ex:ac", "@type": "sh:ValidationActivity", "prov:generated": { "@id": "ex:vr" }, "prov:used": [ { "@id": "ex:dg" }, { "@id": "ex:sg" } ], "prov:wasAssociatedWith": { "@id": "ex:ag" } }, { "@id": "ex:sg", "@type": "sh:DataGraph" }, { "@id": "ex:ag", "@type": "sh:ValidationAgent" }, { "@id": "ex:vr", "@type": "sh:ValidationReport" }
# output-linked ex:dg a sh:DataGraph ; . ex:sg a sh:DataGraph ; . ex:ag a sh:ValidationAgent ; . ex:vr a sh:ValidationReport ; prov:wasAttributedTo ex:ag ; prov:wasDerivedFrom ex:dg , ex:sg ; . # If the Validation Report indicates validity, with sh:conforms being true then, # as per the Rules in this vocab: ex:dg sh:conformsToShapesGraph ex:sg ; .

이 문서의 conforms to shapes graph 규칙을 사용하면 위의 "출력 연결" 예처럼 data graph와 shapes graph 사이에 직접적인 관계를 만들 수 있습니다.

3. SHACL 프로파일링

이 절에서는 SHACL 1.2 프로파일의 구성 방법을 설명하고, 그 예를 제시하며, 추가 프로파일을 만드는 방법을 안내한다.

이 명세 발행 시점에 알려진 SHACL 1.2 프로파일 목록과 커뮤니티가 관리하는 프로파일의 링크는 A. SHACL 프로파일 를 참조하세요.

3.1 SHACL 프로파일 정의

SHACL 프로파일은 SHOULD 요건에 따라 다음 어휘로 선언한다: 프로파일 어휘. 이 어휘를 사용한 SHACL 1.2 코어 프로파일 선언은 다음과 같다.

이 선언은 IRI <http://www.w3.org/ns/shacl/profile/core> 로 코어 프로파일을 식별하며, 인스턴스의 타입으로 다음을 지정한다: prof:Profile이고, SHACL 1.1 합집합 프로파일의 프로파일이며(자세한 내용은 A. SHACL 프로파일은 참조). 명세, 스키마, 검증기라는 세 가지 프로파일 자원을 갖는다.

SHACL을 검증하는 데 SHACL을 사용하므로( SHACL-SHACL), 여기서 스키마가 준수한다고 표시된 데이터 모델은 이 코어 프로파일 자체의 검증기이다.

프로파일 어휘의 용어로 설명하면, 위에서 연결한 각 명세의 온라인 문서는 함께 SHACL 1.2 프로파일을 구성하는 여러 리소스 중 하나일 뿐입니다. 문서는 "사람이 읽을 수 있는 형태로 프로파일 정의"라는 명세 리소스 역할을 맡고, 다른 리소스는 다른 역할을 맡습니다. SHACL 사용자에게 특히 중요한 것은 각 프로파일의 SHACL shapes graph로, "데이터의 프로파일 적합성을 확인하는 방법에 관한 지침 제공"이라는 검증 역할을 맡습니다. 여러 SHACL 1.2 프로파일은 다른 프로파일 리소스 역할을 맡는 추가 리소스를 제공할 수도 있습니다. 예를 들어 Core는 핵심 스키마인 SHACL 온톨로지를 제공하고, SHACL UI는 UI 위젯 어휘와 확장된 용어 어휘를 제공합니다.

참고

이러한 명세 프로파일이나 아래 정의한 Union 프로파일에 대해 RDF 데이터를 검증하려면, 해당 프로파일의 검증 리소스를 사용하세요. 이들은 SHACL-SHACL shapes graph로서 SHACL 1.2 개요의 SHACL-SHACL 부록에 나열되어 있습니다.

3.2 프로파일 만들기

어떤 기준으로든 SHACL 1.2 프로파일을 추가로 만들 수 있다. 예를 들어 특정 계산 복잡도로 제한된 형태 유형만 구현하는 SHACL 1.2 Core 프로파일을 만들 수 있다. 이는 OWL 2 Web Ontology Language Profiles (Second Edition)에 정의된 OWL 프로파일과 비슷하다. 이 경우 SHACL 패키징 절 에서 제시한 방법으로 SHACL 1.2 Core의 일부 요소만 포함하는 프로파일을 정의할 수 있다.

그 밖의 기준으로도 SHACL 요소 을 선택하거나 사용을 제한할 수 있다. 계산 복잡도 이외의 기준을 사용한 예는 A. SHACL 프로파일 의 예는 다양한 기준으로 만든 프로파일을 보여 줍니다.

SHACL 1.2 프로파일을 만들 때는 현재 알려진 SHACL 1.2 프로파일과 같은 방식으로 식별하고 제시하는 것이 중요합니다. 그래야 다른 사람도 이를 효과적으로 사용할 수 있습니다. SHACL 1.2 프로파일 작성자는 다음과 같이 하는 것이 좋습니다(SHOULD):

  1. IRI로 프로파일을 식별합니다
  2. 사용할 어휘는 프로파일 어휘
  3. 이 명세에서 정의한 알려진 SHACL 1.2 프로파일과 커뮤니티가 만든 프로파일을 바탕으로 프로파일을 정의한다
    • 를 참조하세요 3.3 알려진 SHACL 프로파일
  4. SHACL 사용자 커뮤니티와 프로파일을 공유합니다
    • 프로파일을 SHACL 리소스 저장소 에 제출하여 SHACL 커뮤니티의 알려진 프로파일에 포함되도록 한다.

3.3 알려진 SHACL 프로파일

이 명세 발행 시점에 알려진 위에 나열한 각 SHACL 1.2 명세의 SHACL 1.2 프로파일은 아래 A. SHACL 프로파일의 명세 프로파일에 제시합니다. 또한 모든 명세 프로파일을 결합한 Union 프로파일도 A. SHACL 프로파일.

SHACL의 다른 여러 프로파일을 만든 곳은 W3CData Shapes 작업 그룹은 여러 다른 SHACL 프로파일도 만들었으며, 이들도 A. SHACL 프로파일 에 나열되어 있습니다. 그러나 이 목록은 명세 기반, 계산 노력 기반(OWL 프로파일 [owl2-profiles]과 유사) 등 다양한 종류의 프로파일을 보여 주기 위한 것이며, SHACL 프로파일의 완전한 목록을 의도한 것은 아닙니다.

W3C SHACL 커뮤니티가 관리하는 SHACL 리소스 저장소를 SHACL 프로파일 정의를 모으는 중심 장소로 제안합니다.

4. SHACL을 사용한 프로파일링

이 절에서는 SHACL을 사용하여 RDF 리소스의 프로파일을 만드는 방법을 설명합니다.

프로파일 어휘의 일반 프로파일링 용어와 요소가, 5. SHACL 프로파일링 어휘에 정의된 더 특수한 SHACL 프로파일링 요소와 함께 사용됩니다.

4.1 소개

이 절은 비규범입니다.

SHACL은 2017년에 발표된 이후, W3C 온톨로지 같은 개방 세계 RDF 모델을 기반으로 애플리케이션에서 사용할 폐쇄 세계 RDF 데이터 모델을 만드는 데 널리 사용되었습니다.

대표적인 예로, Indigenous Data Network는 프로파일을 정의하여 schema.org라는 범용 RDF 어휘를 원주민 데이터 목록 작성 분야에서 사용하도록 제약합니다. IDN은 목록에 등록된 객체의 메타데이터가 해당 프로파일에 적합한지 테스트하는 SHACL 검증기를 제공합니다.

범용 또는 허용적인 모델을 제약하는 것 외에도, 자체 규칙에 따라 데이터를 검증하는 리소스를 제공하지 않는 명세에 대해 shapes graph를 정의할 수 있습니다. shapes graph가 원래 모델에 추가 규칙을 부과하지 않고 그 명세의 모든 규칙을 구현하려 한다면, 해당 모델의 null 프로파일을 만듭니다.

명세를 프로파일링하는 것 외에도, RDF 데이터셋에서 데이터를 추출하는 데 SHACL을 사용하면 그 데이터셋의 데이터 프로파일을 만듭니다.

다음 절들은 명세 프로파일링과 데이터 프로파일링을 설명하고 지침을 제공합니다.

4.2.3 프로파일 계층 구조

데이터가 SHACL로 정의한 프로파일과 그 프로파일의 대상 표준 모두에 적합한지 테스트해야 한다고 합시다. 그 표준 역시 SHACL로 정의되어 있거나 SHACL로 만든 검증 역할의 리소스를 제공한다면, 해당 프로파일과 표준 또는 그 검증기들을 합성한 shapes graph를 만들 수 있습니다.

여러 표준을 프로파일링하거나 다른 프로파일의 프로파일을 만드는 등 프로파일링 상황이 복잡할 때 이것이 중요할 것으로 예상됩니다. 표준과 프로파일에서 shapes graph를 자동으로 조립하는 것이 수동 조립보다 훨씬 나을 수 있기 때문입니다.

4.2.4 Null 프로파일 만들기

SHACL이 만들어지기 전에는 RDF 어휘의 복잡한 검증 규칙을 표현하는 간단하고 표준화된 방법이 없었다. 따라서 2017년 이전에 제정된 많은 RDF 표준은 사용자가 그 표준에 따라 데이터를 쉽게 검증하는 방법을 제공하지 않는다.

많은 RDF 어휘 표준은 OWL 공리로 모델 제약을 제시하지만, 이를 데이터 검증에 바로 쓰기는 어렵다. 다른 표준에는 편집자나 제3자가 제공하는 비공식 검증 도구가 있다. 예를 들어, PROV-O: The PROV Ontology 에는 prov-check가 있다. 이는 표준 편집자 중 한 명이 작성한 Python 패키지로, SPARQL 질의를 실행한다.

이제 SHACL을 사용하여 표준의 null 프로파일을 만들고, 그 공리와 암묵적 규칙의 상당수 또는 전부를 표준화된 데이터 검증 언어로 표현할 수 있다.

다음에 따른다: 프로파일 어휘 및 4.1 소개. 표준의 null 프로파일 은 원래 표준에 추가 규칙을 부과하지 않고 그 표준의 모든 규칙을 구현하려 하는 프로파일입니다.

SHACL 이외의 모델링 방식이나 규칙 시스템으로도 표준의 null 프로파일을 만들 수 있지만, 여기서는 SHACL의 사용만 다룬다.

검증기가 없는 표준은 보통 검증 가능한 형태로 규칙을 나열하지 않으므로, 표준의 null 프로파일을 만드는 보편적이고 정밀한 방법은 없다. 하지만 유용한 방법은 여럿 알려져 있다. 흔한 방법 하나는 기존 도구를 사용해 OWL 규칙을 SHACL로 변환하는 것이다. 예를 들면 소프트웨어 패키지 또는 제품에 내장된 기능이 있다. 또한 클래스나 속성의 정의 또는 다른 주석에서 의도한 용도를 자연어로 설명하는 경우가 많다. 예를 들어, Data Catalog Vocabulary (DCAT) - Version 3의 dcat:Role 클래스 사용 참고에는 “한정된 귀속 관계에서 개체에 대한 에이전트의 역할을 지정하는 데 사용한다”라고 쓰여 있다.

다음 절을 참조한다: B. Null 프로파일 예제 에는 표준의 null 프로파일 예와 그 작성 방법에 관한 설명이 있다.

5.7 규칙: conforms to shapes graph

"conforms to shapes graph" 규칙은 data graph가 shapes graph에 적합함을 나타낼 수 있게 하는 추론 규칙입니다. 이를 위해서는 Validation Report가 있어야 하며, 이 보고서는 검증에 data graph와 shapes graph를 사용했고 sh:conforms 속성이 true를 나타내야 합니다.

이 추론 규칙은 sh:conforms 속성 값을 테스트해야 하므로 OWL 속성 체인 공리로 표현할 수 없습니다. 따라서 여기서는 SPARQL 1.2 Query Language 규칙과 SPARQL 1.2 RL 규칙의 두 형태로 제시합니다.

CONSTRUCT { ?dg sh:conformsToShapesGraph ?sg } WHERE { ?va sh:usedDataGraph ?dg ; sh:usedShapesGraph ?sg ; prov:generated ?vr ; . ?vr sh:conforms true . }
RULE { ?dg sh:conformsToShapesGraph ?sg } WHERE { ?va sh:usedDataGraph ?dg ; sh:usedShapesGraph ?sg ; prov:generated ?vr ; . ?vr sh:conforms true . }

5.8 규칙: conforms to standard

"conforms to standard" 규칙은 data graph가 표준에 적합함을 나타낼 수 있게 하는 추론 규칙입니다. 이를 위해서는 data graph가 shapes graph에 적합해야 하며, 해당 shapes graph는 그 표준의 프로파일이어야 합니다. 이 추론을 통해 데이터가 표준의 프로파일 및 표준 자체에 적합하다는 정적인 주장을 할 수 있습니다. 이는 이러한 대상에 대한 적합성을 알아야 하지만 지속적으로 검증할 수는 없는 데이터에 유용합니다.

이 추론 규칙은 여기서 SPARQL 1.2 Query Language 규칙과 SPARQL 1.2 RL 규칙의 두 형태로 제시합니다.

CONSTRUCT { ?x dcterms:conformsTo ?z } WHERE { ?x sh:conformsToShapesGraph ?y . ?y prof:isProfileOf ?z . }
RULE { ?x dcterms:conformsTo ?z } WHERE { ?x sh:conformsToShapesGraph ?y . ?y prof:isProfileOf ?z . }
참고

이 규칙의 결과는 프로파일 어휘의 속성 체인 공리 dcterms:conformsTo owl:propertyChainAxiom ( dcterms:conformsTo prof:isProfileOf )가 적합성 주장을 프로파일 계층 구조의 상위로 전파할 수 있게도 합니다.

A.2.3 재귀 제약 금지 프로파일

이 프로파일은 SHACL shape 정의에 대한 구조적 검증 규칙을 수립하며, 재귀 제약 작성을 명시적으로 금지합니다. 핵심 SHACL 명세는 구조적 재귀를 허용하지만, 구현마다 재귀 정의를 다르게 평가할 수 있음을 인정합니다. 이러한 차이는 프로세서가 순환 데이터 그래프를 만났을 때 비결정적 동작이나 무한 검증 루프로 이어지는 경우가 많습니다. 모든 준수 프로세서에서 예측 가능하고 일관된 검증 결과를 보장하기 위해, 이 프로파일은 자기 참조 shape, 상호 의존 shape, 재귀 트리 구조 등 허용되지 않는 구체적인 shape 작성 패턴을 정의합니다.

재귀 제약의 정의

SHACL shapes graph SG가 비재귀 제약 프로파일에 적합한 것은 다음과 동치입니다: 그 shape 참조 그래프(아래 정의)가 비순환입니다.

R(SG)를 다음과 같은 방향 그래프라고 합시다:

  • 각 노드는 SG의 형태이다(다음에 해당하는 RDF 노드): sh:Shape, sh:NodeShape, sh:PropertyShape또는
  • 인 RDF 노드, 또는 아래 정의에 따라 shape를 나타내는 위치에 사용된 RDF 노드입니다. R(SG) 에 방향 간선 s → t가 존재하는 것은 SG에서 shape s 가 shape t 를 SHACL 속성을 통해 참조할 때입니다. 이 속성의 값은 shape를 직접 식별하거나 shape 참조를 포함하는 RDF 리스트를 식별합니다.

shapes graph가 이 프로파일에 적합한지 판정하기 위해, 구현은 MUST 요건으로 shape 참조 그래프를 구성하고 순환 여부를 확인할 때 다음 각 속성과 리스트 구문을 shape 참조 관계로 취급해야 합니다:

  • sh:node
  • sh:property (참조된 property shape로 향하는 간선)
  • sh:qualifiedValueShape
  • , sh:and, sh:or의 리스트 멤버 sh:xone
  • sh:not
  • sh:memberShape
  • sh:reifierShape
  • sh:someValue

shapes graph가 s → ⋯ → s 형태의 순환을 하나라도 포함하면 이 프로파일을 위반합니다. 다음도 여기에 포함됩니다:

  • 직접 자기 참조 (shape가 자신을 참조), 그리고
  • 간접 자기 참조 (shape가 다른 shape를 참조하고, 그 참조를 따라가면 결국 원래 shape를 참조)

C. 보안 고려 사항

이 절은 비규범입니다.

대부분의 RDF 기반 기술과 마찬가지로, SHACL 프로세서는 다양한 출처에서 조립된 그래프에 대해 동작할 수 있습니다. 일부 애플리케이션은 열린 "linked data"("LD") 아키텍처를 가지며 조직의 신뢰 네트워크 밖에 있는 출처에서 RDF triples를 동적으로 조립할 수 있습니다. RDF는 누구나 어떤 리소스에 대해서도 문장을 추가할 수 있도록 하므로, triples는 shape 정의 또는 data graph 내 노드의 원래 의도된 의미를 수정하여 오해의 소지가 있는 결과로 이어질 수 있습니다. 이에 대한 보호(및 다음 시나리오에 대한 보호)는 신뢰할 수 있고 검증된 RDF 출처만 사용하고, owl:imports 및 sh:shapesGraph를 통해 그래프가 동적으로 추가될 가능성을 제거함으로써 달성할 수 있습니다.

다른 표준의 프로파일을 만들 때, 작성자는 자신의 제약이 그 표준의 규칙을 위반하지 않는지 확인해야 합니다. 제약이 규칙을 위반하는데도 우연히 또는 의도적으로 표준의 규칙은 사용하지 않고 프로파일의 규칙만으로 데이터 유효성을 검사한다면, 데이터가 유효하다고 잘못 판정될 수 있습니다. 이로 인해 데이터가 우발적으로 공개되거나 사용되어 보안 문제가 발생할 수 있습니다.

D. 개인정보 보호 고려 사항

이 절은 비규범입니다.

영구 저장한 검증 결과에는 데이터 그래프, shapes graph, 검증 에이전트 및 검증이 이루어진 시점이 식별될 수 있다. 게시자는 이 정보가 개인정보나 기밀 정보를 드러내는지 살펴보고, 공유하기 전에 적절한 접근 제어를 적용해야 한다.
