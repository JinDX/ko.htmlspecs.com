초록

이 문서는 SHACL 프로파일링을 정의합니다.

SHACL, 즉 Shapes Constraint Language는 RDF 그래프의 구조를 설명하기 위한 언어입니다. SHACL은 검증, 추론, 도메인 모델링, 다른 에이전트에 정보를 제공하기 위한 온톨로지 생성, 사용자 인터페이스 구축, 코드 생성, 데이터 통합과 같은 다양한 목적으로 사용될 수 있습니다.

SHACL 프로파일링은 SHACL의 프로파일과 SHACL을 사용한 프로파일링을 허용하기 위해 만들어진 SHACL Shapes Constraint Language의 요소를 정의합니다. 이 문서의 범위는 SHACL Shapes를 포함하는 그래프를 포함하여 RDF 그래프의 프로파일링으로 제한됩니다.

이 명세는 Data Shapes Working Group에서 발행했습니다.

이 정의에서는 영어 단어의 핵심 의미가 유지됩니다. 데이터 객체의 요약 또는 데이터 객체로부터의 추출은 그것의 윤곽일 수 있기 때문입니다. 예를 들어 3D 공간 객체의 2D 표현, 또는 많은 부분을 가진 데이터셋의 통계적 요약이 이에 해당합니다.

정의상 SHACL은 RDF 데이터를 제약합니다. 따라서 shapes graph에 따라 유효한 모든 데이터는 data graph의 프로파일이 됩니다. shapes graph가 data graph의 모든 요소를 검증한다면, 그 결과로 나온 유효한 데이터는 해당 data graph의 "null" 프로파일이 됩니다. 이는 원래 데이터 그래프와 동일하다는 뜻입니다.

The Profiles Vocabulary는 specification의 맥락에서 profile을 다음과 같이 정의합니다.

2.2 권고 사항 요약

위에 표시된 유스 케이스에 대한 해결책은 sh:ShapesGraph의 인스턴스를 사용하여 SHACL 요소를 그룹화하는 것과 같은 잘 정립된 관행을 바탕으로 다음 권고 사항으로 이어집니다.

  1. sh:ShapesGraph의 인스턴스는 SHACL 요소의 인스턴스를 그룹화하는 데 사용되어야 합니다(SHOULD)
  2. SHACL 요소의 인스턴스는 이를 정의하는 sh:ShapesGraph의 인스턴스를 rdfs:isDefinedBy 술어로 표시해야 합니다(SHOULD)
  3. SHACL 요소를 사용하지만 이를 정의하지 않는 sh:ShapesGraph의 인스턴스는 rdfs:member 술어로 해당 SHACL 요소를 멤버로 표시해야 합니다(SHOULD)
  4. SHACL 요소를 그룹화하는 데 사용되는 sh:ShapesGraph의 인스턴스는 sh:ShapesGraph의 인스턴스를 사용하여 식별된 다른 SHACL 요소 그룹에 대한 의존성을 owl:imports 술어로 표시해야 합니다(SHOULD)

다음 하위 절에서는 이러한 각 권고 사항을 자세히 설명합니다.

2.3 SHACL 요소 그룹 식별

sh:ShapesGraph의 인스턴스는 SHACL 요소의 인스턴스를 그룹화하는 데 사용되어야 합니다(SHOULD).

SHACL 요소는 다른 많은 RDF 정의 데이터와 마찬가지로 흔히 OWL 2 Web Ontology Language RDF-Based Semantics (Second Edition)의 owl:Ontology 클래스 인스턴스 안에 그룹화되어 왔습니다.

예를 들어, Open Geospatial Consortium의 공간 RDF 데이터를 위한 GeoSPARQL 1.1 표준은 Turtle 파일 안에 27개의 sh:NodeShape 인스턴스와 비슷한 수의 sh:PropertyShape 인스턴스를 포함하는 SHACL 검증기를 제공합니다. 이 파일에는 검증 리소스의 수정일, 사용 라이선스 등과 같은 메타데이터를 제시하는 owl:Ontology의 인스턴스도 포함됩니다.

이 권고 사항은 그러한 관행을 대체하며, owl:Ontology의 특수화된 하위 클래스인 sh:ShapesGraph를 사용하여 SHACL 요소를 그룹화할 것을 권고합니다. 이는 모호한 그룹화 객체를 피하기 위한 것입니다.

2.4 요소 정의 표시

SHACL 요소의 인스턴스는 이를 정의하는 sh:ShapesGraph의 인스턴스를 rdfs:isDefinedBy 술어로 표시해야 합니다(SHOULD).

sh:ShapesGraph 인스턴스를 사용하여 식별되는 그룹에 SHACL 요소를 넣을 때의 일반적인 관행은 단순히 요소와 온톨로지 인스턴스를 RDF 파일 안에 포함하는 것이었습니다. 이는 데이터 교환에는 합리적이지만, 교환된 파일이 RDF 데이터베이스에 저장될 때 sh:ShapesGraph 인스턴스와 그 안에 정의된 SHACL 요소 사이의 연관이 사라질 수 있습니다. named graph로 로드되는 경우, 온톨로지와 SHACL 요소를 그룹화하는 named graph를 통해 연관이 유지될 수도 있지만, 이는 비의미론적 연관, 즉 그래프에서 직접 보이지 않는 연관입니다.

이 권고 사항은 SHACL 요소의 작성자가 해당 SHACL 요소가 정의된 그룹을 표시해야 한다고 제안합니다(SHOULD). RDF에서 이러한 주장의 예는 다음과 같습니다.

ex:ont-M a sh:ShapesGraph ; . ex:shape-1 a sh:NodeShape ; rdfs:isDefinedBy ex:ont-M ; .
참고

SHACL 1.2 Core의 2.5 Syntactic Variations of Shapes and Classes 절에서는 property shapes를 blank nodes로 선언할 수 있지만, 그래프 간 더 나은 재사용을 가능하게 하므로 이를 IRIs로 선언하는 것이 바람직하다는 경고가 제시됩니다. 이 절에 따른 shapes에 관한 정보를 포함하는 경우, IRIs를 사용해야 합니다(SHOULD).

2.5 요소 사용 표시

SHACL 요소를 사용하지만 이를 정의하지 않는 sh:ShapesGraph의 인스턴스는 rdfs:member 술어로 해당 SHACL 요소를 멤버로 표시해야 합니다(SHOULD)

SHACL 요소가 요소 그룹 안에서 사용되지만 그 그룹에 의해 정의되지 않는 경우, 해당 그룹에 의해 정의된 것으로 표시해서는 안 되므로(SHOULD NOT) 위 절의 권고 사항은 관련이 없습니다. Linked Data 원칙 [LDP]에 따라, 이를 정의하지 않는 그룹 안에서 SHACL 요소를 재사용하는 것은 예상되고 권장됩니다.

SHACL 요소가 이를 정의하지 않는 그룹에 포함됨을 나타내기 위해 rdfs:member 술어를 사용하는 예와, 위 예에서처럼 rdfs:isDefinedBy를 사용하는 예는 다음과 같습니다.

# 'Ontology M'은 'Ontology Other'가 정의한 Shape를 사용합니다 ex:ont-M a sh:ShapesGraph ; rdfs:member ex:shape-1 ; . ex:ont-Other a sh:ShapesGraph ; . ex:shape-1 a sh:NodeShape ; rdfs:isDefinedBy ex:ont-Other ; .

2.6 그룹 의존성 표시

SHACL 요소를 그룹화하는 데 사용되는 sh:ShapesGraph의 인스턴스는 sh:ShapesGraph의 인스턴스를 사용하여 식별된 다른 SHACL 요소 그룹에 대한 의존성을 owl:imports 술어로 표시해야 합니다(SHOULD).

SHACL 검증 도구에서는 RDF 데이터를 포함하는 파일과 같은 한 컬렉션에서 다른 컬렉션으로 owl:imports 지시를 통해 SHACL 요소를 가져오는 것이 확립된 관행입니다. pySHACL [PYSH]과 같은 많은 SHACL 검증 엔진이 이를 수행하며, 이 관행은 특정 검증 엔진의 동작이 해당 주장으로부터 발생할 것으로 기대되지 않더라도 한 컬렉션/그룹에서 다른 컬렉션/그룹으로의 의존성을 나타내는 데 권장됩니다. 이는 SHACL 데이터 관리에도 유용한 정보가 될 가능성이 높습니다.

owl:imports의 예는 아래 예와 같습니다.

# 'Ontology N'은 'Ontology M'을 가져옵니다 ex:ont-M a owl:Ontology ; . ex:ont-N a owl:Ontology ; owl:imports ex:ont-M ; .

3. SHACL의 프로파일링

이 절에서는 SHACL 1.2의 기존 프로파일이 어떻게 만들어지는지 설명하고, 몇 가지 예를 제시하며, 더 많은 SHACL 프로파일을 만드는 방법을 나타냅니다.

이 명세의 발행 시점에 알려진 SHACL 프로파일 목록과 커뮤니티에서 관리하는 프로파일에 대한 링크는 부속서 A를 참조하세요.

3.1 SHACL 프로파일 정의

SHACL의 프로파일은 The Profiles Vocabulary를 사용하여 선언해야 합니다. SHACL 1.2의 Core 프로파일 선언은 다음과 같습니다.

# Core profile 선언 <http://www.w3.org/ns/shacl/profile/core> a prof:Profile ; prof:isProfileOf <https://www.w3.org/TR/shacl/> ; prof:hasResource <https://www.w3.org/TR/shacl12-core/> , <http://www.w3.org/ns/shacl-shacl/core> ; . # Core specification <https://www.w3.org/TR/shacl12-core/> a prof:ResourceDescriptor ; prof:hasRole role:Specification ; dcterms:format "text/html" ; dcterms:conformsTo <http://www.w3.org/TR/html5/> ; prof:hasArtifact <https://www.w3.org/TR/shacl12-core/> ; . # Core validator <http://www.w3.org/ns/shacl-shacl/core> a prof:ResourceDescriptor ; prof:hasRole role:Validation ; dcterms:format "text/turtle" ; dcterms:conformsTo <https://www.w3.org/TR/shacl/> ; prof:hasArtifact <http://www.w3.org/ns/shacl-shacl/core> ; .

이 선언은 Core 프로파일을 IRI <http://www.w3.org/ns/shacl/profile/core>로 식별하고, 그것이 prof:Profile의 인스턴스이며, 2015년의 원래 SHACL 발행물의 프로파일이고, 두 개의 프로파일 리소스, 즉 명세와 검증기를 가진다는 것을 나타냅니다.

The Profiles Vocabulary의 용어를 사용해 설명하면, 위에 링크된 각 명세의 온라인 문서 형태는 SHACL 1.2의 프로파일을 함께 구성하는 많은 리소스 중 하나일 뿐입니다. 이 문서는 Specification — "사람이 읽을 수 있는 형식으로 프로파일을 정의" — 의 리소스 역할을 수행하며, 다른 리소스들은 다른 역할을 수행합니다. SHACL 사용자에게 특히 관심 있는 것은 각 프로파일의 SHACL shapes graph로, 이는 Validation — "데이터가 프로파일에 적합한지 검증하는 방법에 대한 지침 제공" — 의 역할을 수행합니다. SHACL 1.2의 다양한 프로파일은 다른 프로파일 리소스 역할을 가진 추가 리소스를 제공할 수 있습니다.

shapes graph 검증 리소스는 SHACL 1.2 Overview의 SHACL-SHACL 부록에 제공됩니다.

참고

이러한 Specification Profiles 또는 아래에 정의된 Union Profile 중 하나에 대해 RDF 데이터를 검증하려면 SHACL 1.2 Overview의 SHACL-SHACL 부록에 나열된 SHACL-SHACL shapes graphs를 사용하세요.

SHACL 패키징을 사용하여 프로파일에서 지원할 SHACL 요소를 선택하는 방법을 설명합니다.

  2. 이 명세에서 정의한 SHACL 1.2의 프로파일로 해당 프로파일을 정의합니다
    • 부록 A를 참조하세요
  3. SHACL 사용자 커뮤니티와 프로파일을 공유합니다

4.1.1 프로파일링 상황의 특성화

이슈 617: [PROF] 유스 케이스: SKOS 프로파일 ProfilesUCR

이슈 764: 데이터의 SHACL 프로파일링을 위한 유스 케이스: 다중 모델 상호운용성 ProfilesUCR
이 UC가 여기에서 답변되었습니까?

SHACL은 데이터가 알려진 Specification과 일치하는지 테스트하는 데 자주 사용됩니다. 그러한 테스트에 사용되는 SHACL이 해당 명세의 규칙 이외의 어떤 규칙도 구현하지 않는다면, SHACL shapes graph는 그 명세의 null profile을 만듭니다.

Shapes Graph가 명세에 있는 규칙보다 더 많거나 다른 규칙을 구현한다면, 이는 그 명세의 (non-null) profile을 테스트하는 것입니다.

Shapes Graph SG1이 specification S1을 프로파일링하고 있다면, The Profiles Vocabulary의 특성화에 따라 다음과 같습니다.

<SG1> a prof:Profile ; prof:isProfileOf <S1> ; .

그러나 SG1은 Validation의 역할도 수행하므로, 이 상황에 대한 더 완전한 The Profiles Vocabulary 특성화는 다음과 같습니다.

<SG1> a prof:Profile ; prof:isProfileOf <S1> ; prof:hasResource [ prof:hasArtifact <SG1> ; prof:hasRole role:validation ; ] ; .

이는 The Profiles Vocabulary의 예상치 못한 사용입니다. 여기서는 프로파일이, 하나의 프로파일 리소스가 모든 역할을 수행하는 대신, 보통 프로파일의 일부 또는 그 리소스 중 하나가 수행하는 역할도 수행하고 있습니다. 그러나 이는 정당하며, 공통 프로파일링 리소스 역할인 검증을 수행하는 리소스를 개념적 프로파일이 나타낼 수 있게 하려는 PROF의 목표를 여전히 달성합니다.

프로파일 리소스가 SHACL 1.2 Core를 사용하며 Turtle로 제공됨을 나타내려면, 다음도 특성화에 추가할 수 있습니다.

<SG1> a prof:Profile ; prof:isProfileOf <S1> ; prof:hasResource [ prof:hasArtifact <S1> ; prof:hasRole role:validation ; dcterms:conformsTo <https://www.w3.org/TR/shacl12-core/> ; dcterms:format "text/turtle" ; ] ; .

SG1이 프로파일의 요구 사항에 대한 규범적 표현으로도 간주되는 경우, 예를 들어 그 요구 사항을 담은 별도의 자연어 문서와 대비된다면, prof:hasRole 값 role:constraints도 해당 리소스에 적용될 수 있습니다.

4.3 프로파일 부분 역할

SHACL은 RDF 데이터에 대한 제약과 추론 규칙을 구현할 수 있는 언어입니다. 이 두 가지는 프로파일 설계자가 하고자 할 수 있는 일의 전체가 아닙니다. 예를 들어, 프로파일이 왜 그리고 어떻게 만들어졌는지에 대한 문서를 포함하거나, 확장된 스키마 안에 새로운 모델 요소(클래스, 술어 등)를 제공하고 싶을 수 있습니다.

SHACL은 가능한 모든 프로파일 부분에 사용할 수 없으므로, 프로파일 설계자는 프로파일의 전체 부분 집합과 이들 간의 관계를 설정하는 방법에 대한 지침을 위해 SHACL 명세군 밖의 명세를 살펴볼 필요가 있습니다. 이를 위해 The Profiles Vocabulary가 사용될 것으로 예상됩니다.

The Profiles Vocabulary의 Resource Role Instances 어휘를 참조하면, SHACL 그래프가 프로파일 안에서 Validation 역할을 수행할 수 있으며, SHACL이 OWL이 Classes와 Properties를 선언하는 것과 마찬가지로 Node 및 Property Shapes를 선언할 수 있으므로 어쩌면 Specification 역할도 수행할 수 있음이 분명해 보입니다.

SHACL shapes는 자연스럽게 모델과 데이터를 제약하므로, 프로파일이 어떤 것 — 표준 또는 다른 프로파일 — 을 어떻게 제약하는지를 나타내는 데 사용된다면 Constraints의 역할을 수행할 수 있습니다.

SHACL Rules가 한 모델에서 다른 모델로 데이터를 변환하도록 구현되는 경우, SHACL shapes는 Mapping 역할도 수행할 수 있습니다.

4.4 프로파일 계층 구조

프로파일 계층 구조는 하나의 프로파일이 다른 프로파일의 특수화가 되어, 더 구체적인 프로파일이 더 넓은 프로파일로부터 제약을 상속하는 체인을 형성하는 배열입니다. The Profiles Vocabulary의 규칙에 따라, C가 B의 프로파일이고 B가 A의 프로파일이라면, C에 적합하려는 데이터는 B와 A에도 적합한 경우에만 유효할 수 있습니다.

프로파일에 대한 데이터의 적합성을 확인한다는 것은 Validation 역할을 가진 프로파일 리소스로 데이터를 테스트한다는 뜻입니다.

4.5 Null 프로파일 만들기

SHACL을 사용하여 만들어진 명세의 null profile은, SHACL을 사용하여 해당 명세의 규칙 중 일부, 그리고 아마도 전부를 구현하지만 SHACL에서 그 밖의 어떤 규칙도 구현하지 않는 그 명세의 프로파일입니다.

SHACL을 사용하여 명세의 null profile을 만드는 주된 목적은 SHACL 검증을 통해 해당 명세에 대한 적합성 테스트를 가능하게 하는 것입니다. 이러한 목적이 존재하는 이유는 많은 RDF 데이터 모델이 모델 명세, 예를 들어 OWL 모델 또는 모델에 관한 자연어 문서만을 가지고 있지만, SHACL 검증기와 같은 데이터 검증 메커니즘을 제공하지 않기 때문입니다. 이러한 모델의 예로는 Data Catalog Vocabulary (DCAT) - Version 3, Schema.org, The RDF Data Cube Vocabulary, 그리고 많은 W3C 표준이 있습니다.

참고

명세의 null profile은 SHACL 이외의 메커니즘을 사용하여 만들 수도 있지만, 여기서는 SHACL의 사용에만 초점을 맞춥니다.

null profile로 작동하는 RDF 데이터용 비-SHACL 검증기의 예는 W3C의 Constraints of the PROV Data Model입니다. 이는 PROV-O: The PROV Ontology에 따라 공식화된 provenance 데이터에 적용되는 제약 목록을 제공합니다. Constraints of the PROV Data Model은 PROV-O: The PROV Ontology 및 개념적 PROV-DM: The PROV Data Model에 명시되거나 암시된 제약 외에는 어떤 제약도 구현하지 않습니다. 그러나 시간적 엔티티의 순서 지정과 같이 모델이 명시적으로 모델링하지는 않지만 올바른 사용에 필요한 사항에 대한 테스트는 포함합니다. 이러한 제약의 구현은 SPARQL 질의를 실행하는 Python 스크립트로 만들어졌으며, 이를 통해 RDF 데이터 검증이 가능합니다.

명세의 null profile을 만드는 데 보편적이고 정밀한 방법론을 제시할 수는 없습니다. 그 작업의 본질상 명세의 규칙이 부정확하게 정의되어 있을 수 있으며, 따라서 이를 정밀한 SHACL로 특성화하는 데 사용되는 방법도 부정확한 규칙 정의가 달라지는 것과 마찬가지로 달라질 것이기 때문입니다.

다른 명세의 null profile 예는 B. Null Profile Examples를 참조하세요.

CONSTRUCT { ?x sh:conformsTo ?z } WHERE { ?x sh:validationReport ?y . ?y sh:usedShapesGraph ?z ; sh:conforms true ; . }

C. 보안 및 개인정보 보호 고려사항

이 절은 비규범입니다.

대부분의 RDF 기반 기술과 마찬가지로, SHACL 프로세서는 다양한 출처에서 조립된 그래프에 대해 동작할 수 있습니다. 일부 애플리케이션은 열린 "linked data"("LD") 아키텍처를 가지며 조직의 신뢰 네트워크 밖에 있는 출처에서 RDF triples를 동적으로 조립할 수 있습니다. RDF는 누구나 어떤 리소스에 대해서도 문장을 추가할 수 있도록 하므로, triples는 shape 정의 또는 data graph 내 노드의 원래 의도된 의미를 수정하여 오해의 소지가 있는 결과로 이어질 수 있습니다. 이에 대한 보호(및 다음 시나리오에 대한 보호)는 신뢰할 수 있고 검증된 RDF 출처만 사용하고, owl:imports 및 sh:shapesGraph를 통해 그래프가 동적으로 추가될 가능성을 제거함으로써 달성할 수 있습니다.

다른 명세의 프로파일을 만들 때, 프로파일 작성자는 자신의 제약이 해당 명세의 규칙을 위반하지 않도록 해야 합니다. 만약 어떤 제약이 이를 위반하고, 우연히 또는 설계상 데이터 유효성 검사를 위해 명세의 규칙이 아니라 프로파일의 규칙만 사용된다면, 데이터가 잘못 유효한 것으로 계산될 수 있습니다. 이는 우발적인 데이터 공개 또는 사용으로 이어져 잠재적으로 보안 문제를 일으킬 수 있습니다.
