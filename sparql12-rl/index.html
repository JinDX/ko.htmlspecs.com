1. 소개

이 문서는 SPARQL-RL을 소개합니다. 이는 선언적 규칙을 통해 기존 RDF 데이터에서 새로운 RDF 트리플을 도출하는 메커니즘입니다. 이 문서는 규칙 기반 추론의 구문과 의미론을 정의합니다.

SPARQL-RL 구현은 추론 및 질의 연산 중 하나 또는 둘 다를 제공합니다. 추론 연산은 주어진 기본 그래프에 규칙을 적용하고 기본 그래프에 나타나지 않는, 규칙 평가를 통해 도출된 RDF 트리플을 포함하는 추론 그래프를 생성합니다. 추론 그래프와 기본 그래프를 결합하는 것은 선택 사항이며 사용자에게 맡겨집니다. 질의 연산은 주어진 목표 패턴이 규칙을 사용하여 기본 그래프에서 도출될 수 있는지, 그리고 어떻게 도출되는지를 결정합니다.

SPARQL-RL은 규칙의 헤드에 있는 트리플 템플릿에서 사용할 수 있는 빈 노드를 포함하여 새로운 RDF 용어를 생성할 수 있습니다.

SPARQL-RL은 실패에 의한 부정도 지원하며, 이는 규칙이 평가되는 순서에 따라 서로 다른 추론 그래프를 초래할 수 있습니다. 이를 방지하기 위해 규칙은 규칙 간의 순서를 설정하는 계층화 기법을 사용하여 평가되며, 항상 동일한 추론 그래프가 생성되도록 합니다.

문맥이 명확한 경우 SPARQL-RL을 SRL이라고 부를 수 있습니다.

3. SPARQL-RL 개요

이 절은 비규범적입니다.

SPARQL-RL은 기본 그래프와 규칙 집합이 주어지면 새로운 트리플을 추론합니다. 평가의 출력은 기본 그래프에 나타나지 않는 도출된 트리플을 포함하는 추론 그래프입니다.

각 규칙에는 본문이라고 하는 패턴과 헤드라고 하는 결과 템플릿이 있습니다. 규칙은 본문이 결합된 기본 그래프 및 이 시점까지의 실행에서 추론된 모든 트리플과 일치하도록 본문의 변수 값을 찾아 실행됩니다. 그런 다음 이 값은 규칙 헤드의 트리플 템플릿을 인스턴스화하여 새로운 추론 트리플을 생성하는 데 사용됩니다.

규칙은 더 이상 트리플이 추론되지 않을 때까지 실행되며, 새롭게 추론된 트리플을 사용할 수 있게 됨에 따라 규칙은 두 번 이상 실행될 수 있습니다.

SPARQL-RL 실행은 새로운 빈 노드를 포함하여 새로운 RDF 용어를 생성하거나 패턴의 부재를 검사할 때 규칙 실행 순서가 서로 다른 결과를 초래하지 않도록 정의됩니다. 즉, 규칙 실행 순서와 관계없이 동일한 추론 그래프가 생성됩니다.

SPARQL-RL에는 SPARQL 1.2 질의 언어에서 영감을 받은 사람이 이해하기 쉬운 구문이 있습니다. 규칙 집합 평가는 SPARQL과 유사한 요소를 포함하지만, 규칙 실행 순서와 관계없이 동일한 추론 그래프가 생성되도록 세부 사항에는 차이가 있습니다.

이 절의 예제에서는 소프트웨어 구성 요소와 그 종속성을 설명합니다. 프런트엔드는 애플리케이션 서버를 호출하고, 애플리케이션 서버는 알려진 취약점이 있는 데이터베이스를 질의합니다.

3.1 트리플 패턴

하나의 트리플 패턴은 트리플 데이터와 매칭되어 변수에 값을 부여합니다. 패턴에는 세 요소가 있으며, 각각 RDF 용어, 변수, 또는 다음과 같은 패턴입니다. 트리플 용어에 변수가 포함된 패턴입니다.

이 첫 번째 예제에서는 기본 그래프와 규칙 집합에 다음 데이터가 있습니다.

예제 1: 기본 예제 
:frontend :callsService :app .
:app      :queriesDatabase :db .
:db       :hasVulnerability :vuln1 .
RULE { ?x :dependsOn ?y } WHERE { ?x :callsService ?y }
RULE { ?x :dependsOn ?y } WHERE { ?x :queriesDatabase ?y }
:frontend :dependsOn :app .
:app      :dependsOn :db .

위 규칙을 데이터에 적용하면 다음과 같은 결론을 도출합니다. :frontend는 :app에 의존하고, :app는 :db에 의존하며, 이는 의존성의 종류와 무관합니다.

그런 다음 의존하는 규칙을 추가하여 :exposedTo 관계를 도출할 수 있습니다. 이 규칙은 다른 규칙이 생성한 :dependsOn 트리플에 의존합니다. (아래 4.3 규칙 의존성도 참조하세요):

예제 2: 추론된 트리플에 대한 의존 
:frontend :callsService :app .
:app      :queriesDatabase :db .
:db       :hasVulnerability :vuln1 .
RULE { ?x :dependsOn ?y } WHERE { ?x :callsService ?y }
RULE { ?x :dependsOn ?y } WHERE { ?x :queriesDatabase ?y }
RULE { ?x :exposedTo ?v } WHERE { ?x :dependsOn ?y . ?y :hasVulnerability ?v }
:app      :exposedTo :vuln1 .
:frontend :dependsOn :app .
:app      :dependsOn :db .

3.2 재귀

이전 절의 :exposedTo 규칙은 직접적인 의존성에만 도달합니다. :frontend는 :db에 직접 의존하지 않으므로 :frontend에 대한 :exposedTo 트리플은 추론되지 않습니다. 길이에 관계없이 의존성 사슬을 따라 노출을 전파하기 위해, 해당 규칙을 두 규칙으로 대체합니다. 구성 요소는 자신이 가진 취약점에 노출되며, 구성 요소는 직접적인 의존 대상이 노출된 모든 취약점에도 노출됩니다.

예제 3: 규칙 재귀 
:frontend :callsService :app .
:app      :queriesDatabase :db .
:db       :hasVulnerability :vuln1 .
RULE { ?x :dependsOn ?y } WHERE { ?x :callsService ?y }
RULE { ?x :dependsOn ?y } WHERE { ?x :queriesDatabase ?y }
RULE { ?x :exposedTo ?v } WHERE { ?x :hasVulnerability ?v }
RULE { ?x :exposedTo ?v } WHERE { ?x :dependsOn ?y . ?y :exposedTo ?v }
:db       :exposedTo :vuln1 .
:app      :exposedTo :vuln1 .
:frontend :exposedTo :vuln1 .
:frontend :dependsOn :app .
:app      :dependsOn :db .

이전 예제와 비교하면 다음이 추가됩니다. :db :exposedTo :vuln1 — 데이터베이스가 자신의 취약점에 노출됩니다 — 및 :frontend :exposedTo :vuln1: 노출은 사슬을 통해 :frontend에 도달하며, 그 의존성 사슬의 길이와는 무관합니다.

이 마지막 규칙은 재귀 규칙입니다. 규칙의 본문이 규칙의 머리부에 의존합니다.

3.3 필터링

규칙 본문에서 표현식을 사용하여 변수의 값을 제한할 수 있습니다. 이 제한은 본문을 매칭할 때 적용됩니다. 예를 들어 각 취약점의 심각도가 주어지면, 심각한 취약점에 노출된 구성 요소에 상태를 부여할 수 있습니다.

예제 4: 필터링 
:app1 :exposedTo :vuln1 .
:app2 :exposedTo :vuln2 .
:vuln1 :severity 9.1 .
:vuln2 :severity 4.3 .
RULE { ?x :status :criticallyExposed }
WHERE {
    ?x :exposedTo ?v .
    ?v :severity ?s .
    FILTER(?s >= 9.0)
}
:app1 :status :criticallyExposed .

FILTER는 표현식을 평가하며, 현재 변수 바인딩 집합을 표현식이 참으로 평가되면 유지하고, 표현식이 거짓으로 평가되면 현재 변수 바인딩 집합을 버립니다. 이는 다음과 동일합니다. FILTER 연산(SPARQL) 또한 SPARQL-RL은 SPARQL과 동일한 함수 및 연산자를 다수 제공합니다.

3.4 부정

부정은 매칭되지 않아야 하는 패턴을 지정하는 데 사용됩니다. 이를 "실패에 의한 부정"이라고 합니다.

부정 요소를 평가하기 위해 규칙 집합 평가 알고리즘은 해당 패턴과 매칭되는 트리플을 생성할 수 있는 모든 규칙이 부정 요소의 평가 전에 완료되도록 보장합니다. 이를 계층화라고 하며, 부정이 기반으로 삼는 대상에 데이터에서 비롯되든 다른 규칙에서 비롯되든 관련된 모든 가능한 트리플이 포함되도록 보장합니다. 부정을 포함하는 규칙은 이러한 트리플을 생성하는 규칙에 의존한다고 합니다. (아래 4.3 규칙 의존성을 참조하세요).

예제 5: 실패에 의한 부정 
:app rdf:type :Component ;
    :status :criticallyExposed .

:logger rdf:type :Component .
RULE { ?x :status :safeToDeploy }
WHERE {
    ?x rdf:type :Component .
    NOT { ?x :status :criticallyExposed }
}
:logger :status :safeToDeploy .

3.5 할당 및 RDF 용어 생성

할당을 통해 규칙은 표현식의 결과를 변수에 할당할 수 있습니다. 이는 규칙 본문에서 이루어지며, 새로운 RDF 용어를 생성하는 데 사용할 수 있습니다. 이때 데이터를 기반으로 합니다.

예제 6: 할당 
RULE { ?v :riskScore ?r }
WHERE {
    ?v :severity ?s .
    ?v :exploitLikelihood ?p .
    SET ( ?r := ?s * ?p )
}

규칙 머리부에 빈 노드를 사용할 수 있으며, 각각 새로운 빈 노드를 생성합니다. 이는 규칙 평가가 트리플을 생성할 때마다 이루어집니다.

예제 7: 규칙 머리부의 빈 노드 
RULE { [] rdf:type :Notification ; :concerns ?x }
WHERE { ?x :status :criticallyExposed }

규칙에 포함되는 할당, 빈 노드를 생성하는 규칙에서 평가하는 규칙 머리부, 그리고 템플릿이 있는 규칙에서 포함하는 트리플 용어에 포함된 변수 가 있는 경우, 해당 규칙은 단일 실행 규칙입니다. 이러한 규칙은 자신이 의존하는 데이터를 생성할 수 있는 모든 규칙 이후에 실행되며, 자신이 생성하는 데이터에 의존하는 모든 규칙 이전에 실행됩니다.

이 조건은 이러한 규칙이 자기 자신으로 되돌아가 반복하여 무한한 수의 RDF 용어를 생성하지 않도록 보장합니다.

참고

상수인 RDF 용어가 규칙 머리부에 있더라도 해당 규칙이 단일 실행 규칙이 되는 것은 아니며, 해당 용어가 기본 그래프에 나타나지 않아도 마찬가지입니다. 규칙은 매번 동일한 용어를 평가 시 제공하므로, 유한한 수의 용어만 추가할 수 있습니다.

표현식을 평가할 때 할당에서 오류가 발생하면, 현재 해 매핑은 다음에 의해 거부됩니다. 할당.

3.7 규칙 집합 가져오기

SPARQL-RL 규칙 집합은 다른 규칙 집합을 통합할 수 있으며, 이를 위해 해당 URL을 규칙 집합 가져오기에 포함합니다. 이를 통해 규칙을 규칙 집합 간에 공유되는 라이브러리로 구조화할 수 있습니다.

규칙 집합의 IMPORTS 문은 어떤 규칙이든 규칙 집합 내에서 평가되기 전에 처리됩니다. 가져오기 단계에서 가져온 규칙 집합에 자체 가져오기가 있으면, 이들도 재귀적으로 처리됩니다. 규칙 집합을 처리하는 동안 IMPORTS 문을 순회하면 순환 가져오기를 만날 수 있습니다. 규칙 집합은 한 번만 가져옵니다. 가져오기 문 그래프의 순환은 무한 루프를 유발하지 않습니다.

규칙 집합 가져오기 지원은 다음에서 선택 사항입니다. SPARQL-RL 처리기. 자세한 내용은 4.5 처리: 가져오기를 참조하세요.

3.8 데이터 블록

데이터 블록은 규칙 집합 평가에 RDF 트리플을 직접 제공합니다. 데이터 블록의 트리플은 추론 그래프에 추가되며, 규칙 본문에서 매칭에 사용할 수 있습니다.

예를 들어 규칙 집합은 알려진 사실을 포함하여 제공될 수 있으며, 이 사실은 데이터에서 도출되지 않고 직접 단언됩니다.

예제 8: 규칙 집합에 데이터 포함 
DATA {
    # 버전 2.0.0 및 이전 버전에는 알려진 취약점이 있으며
    # 심각하게 노출된 것으로 간주합니다.
    :appV2 rdf:type :Component ;
           :version "2.0.0" ;
           :status :criticallyExposed .
}
참고

데이터 블록은 본문이 비어 있는 규칙과 동등합니다. 그 트리플은 어떠한 규칙도 평가되지 않은 상태에서 추론 그래프의 일부가 됩니다.

3.9 기본 데이터 매칭

규칙 집합 평가 중에는 원래의 대상에만 패턴 매칭을 수행해야 할 수 있습니다. 기본 그래프가 그 대상이며, 추론된 트리플은 대상이 아닙니다.

기본값 설정이 이에 해당하는 예입니다. 규칙은 기본 그래프에 이미 값이 있는지 검사해야 하며, 값이 없으면 규칙은 기본값을 계산할 수 있습니다.

예제 9: NOT을 사용하는 기본 데이터 
:A :distanceMiles 5 .
:A :distanceKilometers 8 .
:B :distanceMiles 10 .
RULE  { ?x :distanceKilometers ?kilometers }
WHERE {
    ?x :distanceMiles ?miles .
    NOT DATA { ?x :distanceKilometers ?km }
    SET ( ?kilometers := xsd:integer(?miles *  1.60934))
}
:B :distanceKilometers 16 .

NOT DATA를 사용하면 규칙 본문의 다른 부분에서 추론된 트리플을 매칭할 수 있습니다. 또한 전체 규칙 본문 매칭을 다음 대상으로 수행할 수도 있습니다. 기본 그래프를 대상으로, WHERE DATA를 사용합니다. 그러면 이러한 규칙은 기본 그래프의 매칭에만 의존합니다.

예제 10: WHERE를 사용하는 기본 데이터 
RULE  { ?x :distanceKilometers ?kilometers }
WHERE DATA {
    ?x :distanceMiles ?miles .
    NOT { ?x :distanceKilometers ?km }
    SET ( ?kilometers := xsd:integer(?miles *  1.60934))
}
참고

이 절의 매칭 대상은 기본 그래프입니다. 여기에는 다음에 의해 추가된 트리플이 포함되지 않습니다. 규칙 집합 평가가 다음에서 추가한 트리플입니다. 규칙 집합의 DATA 블록 (3.8 데이터 블록).

3.10 규칙 집합 평가

규칙은 다음으로 구성됩니다. 규칙 집합. 규칙 집합과 데이터 그래프(즉, 기본 그래프)는 평가의 입력입니다. 출력은 그래프이며, 다음과 같이 부릅니다. 추론 그래프, 이는 평가 과정에서 생성된 트리플의 집합으로, 다음에 나타나지 않는 트리플로 이루어집니다. 기본 그래프.

평가 중에 한 규칙을 기반으로 추론된 트리플은 다른 규칙의 매칭에 사용할 수 있습니다. 규칙 집합 평가는 다음 시점까지 진행됩니다. 더 이상 트리플을 추론할 수 없는 시점이며, 이때 입력은 규칙 집합과 기본 그래프입니다.

평가는 다음 단계로 시작됩니다. 규칙 집합을 준비합니다. 이는 규칙 자체를 평가하기 전에 수행됩니다.

  1. 지원되는 경우, 입력 규칙 집합의 가져오기를 해석하여 모든 규칙을 포함하는 규칙 집합을 구성합니다. 가져온 모든 규칙 집합의 규칙이 포함됩니다. 처리기는 가져오기 중 하나라도 수용할 수 없으면 오류를 알립니다. 이는 해당 처리기를 기준으로 합니다(4.5 가져오기 처리).
  2. 각 규칙이 올바른 형식의 규칙인지 확인합니다.
  3. 다음을 계산합니다. 의존성 그래프.
  4. 하나의 계층화를 계산합니다. (4.4 계층화) 이를 통해 부정 요소 및 단일 실행 규칙이 일관되고, 예측 가능한 결과를 생성하도록 합니다. 계층화에는 다음의 검사가 포함됩니다. 의존성을 검사하며, 이는 규칙 간의 의존성입니다. (4.3.1 의존성 그래프).

하나의 규칙 집합이 준비되면, 평가는 각각의 계층을 계층화에서 순서대로 가져와, 해당 계층의 규칙을 완료될 때까지 평가하고, 그런 다음 다음 계층으로 이동하는 방식으로 진행됩니다. 규칙 실행으로 트리플이 추론되면, 해당 트리플은 즉시 다른 규칙이 실행될 때 사용할 수 있게 됩니다.

4.3 규칙 종속성

규칙 R1은 규칙 R2에 의존하며, 이는 두 번째 규칙의 출력이 첫 번째 규칙의 본문 평가에 영향을 미치는 경우입니다. 즉, R2의 머리부에는 하나의 트리플 템플릿이 있으며, 이 템플릿은 다음과 매칭되는 트리플을 생성할 수 있습니다. 하나의 트리플 패턴으로서 R1의 본문에 있으며, 이는 트리플 패턴 요소이거나, 다음의 내부에 있습니다. 부정 요소 또는 집계 패턴.

의존성에는 두 종류가 있습니다: 닫힌 의존성 및 열린 의존성. 닫힌 의존성은 규칙 R2가 규칙 R1이 실행되기 전에 가능한 모든 출력을 생성했음을 보장합니다. 규칙 의존성이 닫혀 있지 않으면 열린 의존성입니다. 이는 첫 번째 규칙 R1이 실행될 수 있게 하며, 그동안 규칙 R2는 추가 트리플을 생성하기 위해 다시 실행될 수 있고, 이에 따라 R1이 R2의 새 트리플로 재평가될 수 있습니다.

플래그 .evaldata가 false로 설정된 규칙은 기본 그래프를 사용하여 매칭하며, 해당 규칙에는 의존성이 없습니다.

이 첫 번째 예제에서 첫 번째 규칙은 열린 의존성을 가집니다. 그 대상은 두 번째 규칙입니다.

예제 11: 열린 의존성 
RULE { ?x :exposedTo ?v } WHERE { ?x :dependsOn ?y . ?y :hasVulnerability ?v }
RULE { ?x :dependsOn ?y } WHERE { ?x :callsService ?y }

이 두 번째 예제에서 첫 번째 규칙은 닫힌 의존성을 가집니다. 그 대상은 두 번째 규칙입니다. 트리플 패턴 ?x :status :criticallyExposed는 다음의 내부에 나타납니다. 부정 요소로서 첫 번째 규칙에 속하며, 다음과 매칭됩니다. 트리플 템플릿으로서 두 번째 규칙의 머리부에 있습니다. 첫 번째 규칙은 두 번째 규칙이 가능한 모든 출력을 생성할 때까지 평가할 수 없습니다.

예제 12: 닫힌 의존성 
RULE { ?x :status :safeToDeploy }
WHERE { ?x rdf:type :Component . NOT { ?x :status :criticallyExposed } }

RULE { ?x :status :criticallyExposed } WHERE { ?x :exposedTo ?v }

규칙 R1이 의존하는 대상은 규칙 R2이며, 이는 R1.evaldata가 true이고 어떤 트리플 패턴이 R1의 본문에 있을 때, 그것이 트리플 패턴 요소이든, 다음의 내부에 있든, 부정 요소 neg로서 neg.evaldata가 true인 경우, 또는 집계 패턴 내부에 있든, 의존하는 대상이 트리플 템플릿이며, 이 템플릿이 R2의 머리부에 있는 경우입니다.

닫힌 의존성

하나의 규칙 의존성이 규칙 R1에서 규칙 R2로 향할 때, 이는 닫힌 의존성이며, 다음 조건 중 하나라도 성립하는 경우입니다:

  • 하나의 트리플 패턴이 부정 요소 내부에 나타나며, R1의 해당 부정 요소의 플래그 .evaldata가 true이고, 매칭되는 트리플 템플릿이 규칙 머리부에 있으며, 이는 R2의 머리부입니다.
  • 규칙 R1이 의존하는 대상이 규칙 R2이고 R1이 단일 실행 규칙입니다.
열린 의존성

하나의 규칙 의존성이 규칙 R1에서 규칙 R2로 향할 때, 이는 열린 의존성이며, 해당 의존성이 닫힌 의존성이 아닌 경우입니다.

트리플 템플릿은 트리플 템플릿의 변수에 대한 값이 존재하여 템플릿의 변수를 값으로 대체했을 때 트리플 T2가 되고, T2가 T1과 같으면 RDF 트리플 T1을 생성할 수 있습니다.

마찬가지로, 트리플 패턴과 일치하는 트리플 T1은 해당 패턴의 변수에 할당할 값들이 존재하는 경우입니다. 트리플 패턴의 변수를 해당 값으로 치환할 때에는 빈 노드를 변수로 취급하는 경우도 포함되며, 패턴에서 치환한 결과 트리플 T2가 생성되고, 이 T2와 동일한 T1이어야 합니다.

트리플 템플릿 또는 트리플 패턴에서 변수가 두 번 이상 사용되면, 대체할 때 동일한 RDF 용어가 사용됩니다.

트리플 패턴에서 변수를 RDF 용어로 대체하는 것은 트리플 용어 내부의 변수를 대체하는 것도 포함합니다.

4.3.1 종속성 그래프

규칙 간의 종속성은 종속성 그래프라고 하는 방향 그래프로 표현됩니다. 그래프의 정점은 규칙 집합의 규칙이며, 간선에는 종속성이 열린 종속성인지 닫힌 종속성인지에 따라 open 또는 closed라는 레이블이 지정됩니다.

종속성 그래프
규칙 집합의 종속성 그래프는 각 정점이 규칙 집합의 규칙이고, R1이 R2에 의존하면 규칙 R1에서 규칙 R2로 향하는 간선이 존재하는 방향 그래프입니다. 간선에는 종속성이 열린 종속성인지 닫힌 종속성인지에 따라 open 또는 closed라는 레이블이 지정됩니다.
전이적 규칙 종속성
종속성 그래프에서 R1에서 R2로 가는 경로가 존재하면 규칙 R1은 규칙 R2에 대해 전이적 종속성을 가집니다.
재귀적 규칙 종속성

종속성 그래프에 R이 관여하는 순환 경로가 있으면 규칙 R은 재귀적 종속성을 가집니다.

참고

종속성 그래프는 기본 그래프의 영향을 받지 않습니다.

4.3.2 종속성 그래프 알고리즘

다음 알고리즘은 종속성 그래프를 규칙 집합에서 구성하는 한 가지 가능한 방법을 제시합니다. 적합성은 이 절차의 사용 여부가 아니라 종속성 그래프의 정의를 충족하는 종속성 그래프를 생성하는지 여부에 달려 있습니다. 

define mergeLabel(oldLabel, newLabel):
    # 닫힌 의존성이 열린 의존성보다 우선합니다.
    if oldLabel == "open" and newLabel == "open":
        the result is "open"
    else:
        the result is "closed"
    endif
enddefine

# 출력 -- 규칙 정점과 레이블이 지정된 간선으로 이루어진 의존성 그래프입니다.
define buildDependencyGraph(ruleSet):
    # edgeLabelMap은 (R1, R2)를 "open" 또는 "closed"에 매핑합니다
    let edgeLabelMap be a map from pair (rule, rule) to label

    foreach rule R1 in ruleSet.rules:
        let bodyDependencies = {}

        if R1.evaldata then:
            # 규칙의 각 트리플 패턴 TP를 "open" 또는 "closed"가 필요한 것으로 분류합니다
            # 이는 부정 요소 또는 집계
            # 패턴 내부에 있는지 여부에 따라 결정됩니다.
            foreach rule element RBE in R1.body:
                if RBE is a triple pattern element of triple pattern TP:
                    let item be a pair (TP, "open")
                    add item to bodyDependencies
                else if RBE is a filter element:
                    # 아무 작업도 수행하지 않습니다
                else if RBE is a negation element:
                    if RBE.evaldata then:
                        foreach triple pattern TP in RBE.inner:
                            let item be a pair (TP, "closed")
                            add item to bodyDependencies
                        endfor
                    endif
                else if RBE is an assignment element:
                    # 아무 작업도 수행하지 않습니다
                else if RBE is an aggregation element:
                    foreach triple pattern TP in RBE.pattern:
                        let item be a pair (TP, "closed")
                        add item to bodyDependencies
                    endfor
                endif
            endfor
        endif

        foreach pair (triple pattern TP, depLabel) in bodyDependencies:
            if R1 is a run-once rule:
              set depLabel to "closed"
            endif
            # 이 트리플 패턴 요소 또는 부정 요소의 의존성을 찾습니다.
            foreach rule R2 in ruleSet.rules:
                foreach triple template TT in R2.head:
                    if triple pattern TP matches triple template TT:
                        let key = (R1, R2)
                        if edgeLabelMap contains key:
                            let oldLabel = edgeLabelMap.get(key)
                            let merged = mergeLabel(oldLabel, depLabel)
                            edgeLabelMap.set(key, merged)
                        else:
                            edgeLabelMap.set(key, depLabel)
                        endif
                    endif
                endfor
            endfor
        endfor
    endfor

    let DP = { }
    foreach entry ((R1, R2), label) in edgeLabelMap:
        add an edge (R1 -> R2) labeled with label to DP
    endfor

    the result is DP
enddefine

4.4 계층화

계층화는 하나의 규칙 집합을 순서가 있는 시퀀스로 분할하는 과정이며, 이 시퀀스는 계층화 계층으로 구성됩니다(다른 명칭은 "strata"이며, 단수형은 "stratum"입니다). 더 낮은 계층의 규칙은 더 높은 계층의 규칙보다 먼저 평가됩니다.

계층화는 다음 사이의 의존성에 제약을 부과합니다. 규칙. 이를 통해 부정 요소, 집계 요소, 및 단일 실행 규칙이 오직 앞선(더 낮은) 계층과 기본 그래프를 사용하여 계산된 결과에만 의존하도록 보장합니다. 이는 단일하고, 명확하게 정의되며, 유한한 평가 결과를 보장합니다. 규칙 집합을 주어진 기본 그래프에 대해 평가한 결과입니다.

참고

계층화 과정은 평가와 관련된 다른 결정을 내리는 데에도 사용할 수 있습니다. 이 문서는 필요한 조건을 설명합니다. 일관된 평가를 위한 조건이며, 계층화를 구성하는 가능한 방법 하나를 제시합니다. 구현은 조건을 충족해야 하며, 호환되는 동작을 얻으려면 여기에 설명된 조건을 충족해야 하지만, 제시된 그대로 알고리즘을 구현할 필요는 없습니다.

계층화 계층

하나의 계층화 계층 SL은 쌍으로, 서로소인 집합들로 구성되며, 규칙의 집합 (SL.once, SL.general)입니다. SL.once는 정확히 해당 계층의 단일 실행 규칙으로 이루어집니다; 이러한 규칙은 각각 평가되며, 정확히 한 번, 다음의 평가가 시작될 때 평가됩니다. 계층화 계층. SL.general은 해당 계층의 나머지 규칙 집합이며, 이 규칙들은 새 트리플이 더 이상 추론되지 않을 때까지 반복해서 평가됩니다.

계층화

하나의 계층화가 어떤 규칙 집합에 대한 것일 때, 이는 계층화 계층의 시퀀스입니다. 어떤 규칙 집합의 각 규칙은 정확히 하나의 집합에 나타나며, 이 집합은 해당 계층화 계층 중 하나에 속합니다.

해당 계층화 계층이 속한 계층화에서는 번호를 부여하며, 0부터 시작합니다. 계층 번호가 어떤 규칙의 것일 때, 이는 번호로서 해당 계층화 계층이 그 규칙을 포함합니다. 더 작은 계층 번호를 가진 규칙은 더 낮은 계층에 있습니다; 더 큰 계층 번호를 가진 규칙은 더 높은 계층에 있습니다.

규칙 R1에서 규칙 R2로 향하는 모든 간선에 대해, 의존성 그래프가 속한 규칙 집합에서:

  • 간선의 레이블이 closed이면, 계층 번호를 가진 R1의 해당 번호는 다음보다 엄격히 큽니다. 계층 번호로서 R2의 번호입니다.
  • 간선의 레이블이 open이면, 계층 번호를 가진 R1의 해당 번호는 다음보다 크거나 같습니다. 계층 번호로서 R2의 번호입니다.
참고

하나의 규칙 집합은 둘 이상의 계층화를 가질 수 있습니다. 구현은 어떤 계층화든 사용할 수 있으며, 해당 규칙 집합의 계층화이면 됩니다.

4.4.1 계층화 조건

계층화는 다음 조건이 충족되는 경우에만 정의됩니다. 규칙 집합이 이 조건을 충족하지 않으면 이 명세는 그러한 규칙 집합의 평가 결과를 정의하지 않습니다.

계층화 조건
계층화 조건은 규칙 집합의 종속성 그래프에서 닫힌 종속성이 관여하는 재귀적 종속성이 없어야 한다고 요구합니다.
참고

계층화 조건은 계층화가 존재하기 위한 정확한 조건입니다. 규칙 집합의 종속성 그래프의 순환 경로 중 어느 것도 닫힌 종속성을 포함하지 않는 경우에만 규칙 집합의 계층화를 형성할 수 있습니다.

4.4.2 계층화 알고리즘

다음 알고리즘은 규칙 집합만을 기반으로 하는 한 가지 가능한 계층화를 제시합니다. 

define stratification(ruleSet):

    let DP = Dependency graph for the rule set.
    let stratumMap be a map from rule to integer

    # 종속성 그래프는 계층화 조건을 충족해야 합니다.
    # 무한 계층화 검사는 계층화 조건 위반에
    # 대비하기 위한 보호 장치입니다.
    let limit = num rules + 1
    let maxStratum = 0

    # stratumMap을 초기화합니다.
    foreach rule in ruleSet.rules:
        stratumMap.set(rule, 0)
    endfor

    boolean changed = true
    while changed:
        changed = false
        foreach edge E in DP:
            # 레이블이 있는 pRule에서 qRule로 향하는 간선입니다.
            let pRule = source of edge
            let qRule = destination of the edge
            let label = edge label

            if label == "open":
                if stratumMap.get(pRule) < stratumMap.get(qRule):
                    stratumMap.set(pRule, stratumMap.get(qRule))
                    changed = true
                endif
            endif
            if label == "closed":
                if stratumMap.get(pRule) <= stratumMap.get(qRule):
                    let xStratum = 1 + stratumMap.get(qRule)
                    if xStratum > limit:
                        # 계층화 요구 사항을 위반했습니다.
                        error "Stratification error"
                    endif
                    stratumMap.set(pRule, xStratum)
                    maxStratum = max(maxStratum, xStratum)
                    changed = true
                endif
            endif
        endfor
    endwhile

    # 결과 맵을 초기화합니다.
    let stratumRules be a map from integer to rules.
    foreach i = 0 to maxStratum
        stratumRules.set(i, {})
    endfor

    # stratumMap에서 동일한 레벨 번호를 가진 규칙을 모읍니다.
    foreach rule R in map stratumMap:
        let stratumNum = stratumMap.get(R)
        add R to stratumRules.get(stratumNum)
    endfor

    # 각 레벨을 once와 general로 분할합니다.
    let stratumLevels be a sequence of pairs of sets of rules.
    for i = 0 to maxStratum:
        let rules = stratumRules.get(i)
        let once = { R in rules | R is a run-once rule }
        let general = rules \ once
        stratumLevels.set(i, pair(once, general))
    endfor

    the result is stratumLevels
enddefine
참고

계층화 조건의 결과로, 한 번 실행되는 규칙이 평가되고 나면 해당 규칙의 결과를 결정하는 데 사용된 데이터는 이후 평가 중 변경되지 않습니다.

완전한 규칙 집합에 종속성 분석과 계층화를 단계별로 적용하고 이어서 평가까지 수행하는 내용은 6.6 실제 예제에 나와 있습니다.

4.5 가져오기 처리

웹에서 문서를 읽는 작업에는 보안상 영향이 있습니다. 규칙 집합 가져오기 지원 여부는 SPARQL-RL 처리기에서 선택 사항입니다. 또한 구현은 부분적으로 지원할 수 있으며, 예를 들어 일부 규칙 집합의 가져오기만 지원하고 다른 규칙 집합은 지원하지 않거나, 검증된 사본에서만 가져오도록 할 수도 있습니다.

가져오기 처리에는 다음 조건이 적용됩니다.

  • 규칙 집합 가져오기를 지원하지 않는 구현은 반드시 해당 규칙 집합에 IMPORTS 문이 포함되어 있으면 이를 거부하고 오류를 알려야 합니다.
  • 부분적인 지원을 제공하는 구현은 반드시 지원하지 않는 가져오기를 발견하면 오류를 알려야 합니다.
  • 구현은 반드시 가져오기 대상 문서를 해석할 수 없거나, 해당 문서가 구문상 유효하지 않은 경우 오류를 알려야 합니다.
  • 처리기는 반드시 규칙 집합을 한 번만 가져와야 하며, 이는 무한 루프를 방지하기 위한 것입니다. IMPORTS 문을 처리할 때 적용됩니다.

하나의 해결된 규칙 집합은 다른 규칙 집합에서 가져오기에 언급된 모든 규칙 집합을 재귀적으로 읽어 생성되며, 이 가져오기는 해당 다른 규칙 집합에 속합니다.

5. SPARQL-RL과 SPARQL의 관계

이 절은 비규범적입니다.

SRL과 SPARQL은 밀접한 관계가 있습니다. SRL은 호환되도록 설계되었으며, 그 대상은 SPARQL이고, SRL의 많은 구문은 다음에서 가져오거나 영감을 받았습니다. SPARQL 패턴 매칭입니다. 그러나 몇 가지 차이점이 있습니다.

SRL에서 RULE 변수는 사용 전에 항상 바인딩되며, 이는 FILTER 또는 SET의 표현식에서 사용되든, 트리플 템플릿에서 사용되든 마찬가지입니다. 이 템플릿은 규칙 머리부에 속합니다. SPARQL CONSTRUCT 질의 및 INSERT 업데이트는 변수가 CONSTRUCT 또는 INSERT 템플릿에 나타나지만 WHERE 절에서 값이 주어지지 않으면 부분적인 결과를 생성합니다.

  • 올바른 형식성 조건은 다음을 보장합니다. 변수가 적어도 하나의 트리플 패턴 요소에 나타나거나, 또는 할당 변수로 나타나며, 이는 다음에서 사용되기 전이어야 합니다. 필터 요소 또는 할당 요소로서, 해당 규칙 본문 내에 있습니다.
  • SRL의 SET 형식과 SPARQL의 BIND 형식은 서로 다른 오류 처리 동작을 가집니다. SET에서 발생한 오류는 현재 해를 필터링하여 제외하지만, BIND는 현재 해의 변수를 설정하지 않은 채 해당 해를 전달합니다. SET(?var := expr)는 다음과 동일합니다. SPARQL에서 BIND(expr AS ?var) 뒤에 FILTER(BOUND(?var))를 사용하는 것입니다.
  • 규칙 본문의 WHERE 절 구문에는 UNION 또는 OPTIONAL 구문이 포함되지 않습니다. 이러한 SPARQL 요소는 바인딩되지 않은 변수를 초래할 수 있습니다. UNION 또는 OPTIONAL의 효과는 다음을 사용하여 얻을 수 있습니다. 올바른 형식의 규칙.

그 밖의 차이점은 다음과 같습니다:

  • NOT 구문은 내부 본문을 트리플 패턴과 필터로 제한하며, 중첩 패턴을 허용하지 않습니다. NOT은 규칙 본문에서 작성된 위치에서 필터로 실행되며, 이는 SPARQL FILTER NOT EXISTS와 다릅니다.
  • 속성 경로 구문은 / 및 ^를 사용하는 경로만 지원합니다. 이들은 트리플 패턴으로 확장할 수 있습니다. 임의 길이 연산자인 * 및 +는 허용하지 않습니다. 임의 길이 경로는 SPARQL-RL에서 표현할 수 있으며, 더 일반적인 접근 방식인 재귀를 사용합니다.
  • 일부 함수는 SRL 구문에 포함되지 않습니다. 여기에는 COALESCE나 BOUND가 없습니다. 해시 함수도 없습니다. 또한 RAND도 없는데, 이는 매번 호출될 때 서로 다른 결과를 반환하기 때문입니다.

  • BNODE를 사용하면 호출할 때마다 서로 다른 빈 노드가 생성됩니다. 규칙 집합 평가의 결과로 생성되는 추론 그래프는 그래프 동형입니다.

  • UUID 및 STRUUID를 사용하여 고유 식별자를 생성할 수 있습니다. 규칙은 이렇게 생성된 식별자를 검사하지 않는 것이 좋으며, 오직 트리플을 생성하는 데만 사용해야 합니다.

입력: 기본 그래프라고 하는 그래프 G와 규칙 집합 RS.
출력: 추론된 트리플의 RDF 그래프 GI

6.1 평가 정의

해 매핑
하나의 해 매핑 μ는 부분 함수입니다. μ : V → T, 여기서 V는 모든 변수의 집합이며, T는 모든 RDF 용어의 집합입니다. μ의 정의역은 dom(μ)로 나타내며, 이는 부분집합으로서 V 중 μ가 정의되는 원소로 구성됩니다. 용어 해는 다음을 의미함이 명확할 때 사용할 수 있습니다. 해 매핑. 다음 조건을 만족하는 해 매핑을 μ0로 표기합니다. dom(μ0)가 공집합입니다.
치환 함수

치환 함수, 또는 간단히 치환은, 다음 함수입니다. subst(μ, 트리플 패턴) 이 함수는 트리플 패턴을 반환하며, 해당 트리플 패턴에서 변수 var가 다음에 속하면, dom(μ), 그 변수의 각 출현은 RDF 용어로 대체되며, 이는 해 매핑이 var에 대해 제공하는 용어입니다. 결과 트리플 패턴에 변수가 없으면, 이는 하나의 RDF 트리플입니다.

함수 subst(μ, 트리플 템플릿) 도 유사하게 정의됩니다. 변수의 각 출현은 트리플 템플릿에서 다음으로 대체됩니다. RDF 용어로서, 해 매핑이 var에 대해 제공하는 용어입니다.

템플릿 인스턴스 함수
템플릿 인스턴스 함수는 다음 함수입니다. replaceBlankNodes(list of 트리플 템플릿) 이 함수는 다음의 목록을 반환합니다. 트리플 템플릿이며, 각각의 빈 노드가 인수에서 새로운 빈 노드로 대체됩니다. 동일한 빈 노드가 여러 번 나타나면 동일한 새 빈 노드로 대체됩니다.
평가 그래프
하나의 평가 그래프는 RDF 그래프이며, 다음을 결합합니다. 기본 그래프 및 규칙 집합 평가 중에 생성된 모든 트리플입니다.
그래프 매칭
하나의 그래프 매칭은 다음 방법을 찾습니다. 트리플 패턴을 다음의 트리플에 매핑하는 방법입니다. RDF 그래프.

G를 RDF 그래프라고 하고, TP를 트리플 패턴이라고 합니다. 함수 graphMatch(G, TP)는 가능한 모든 해의 집합을 반환하며, 이 해들은 트리플 패턴에 적용될 때 다음에 속하는 트리플을 생성합니다. 그래프 G.

G를 RDF 그래프, TP를 트리플 패턴이라고 하고, V를 TP에 나타나는 변수의 집합이라고 합니다. 

graphMatch(G, TP) = { μ | dom(μ) = V and subst(μ, TP) is a triple in G }
해 호환성
두 해 S1과 S2는 호환되며, 이는 변수의 값이 일치하는 경우입니다. 두 해에 공통으로 있는 변수에 대해 일치해야 합니다.

S1과 S2를 해라고 합니다. 

compatible(μ1, μ2) = true
                      if forall v in dom(μ1) intersection dom(μ2)
                          μ1(v) = μ2(v)
compatible(μ1, μ2) = false otherwise
해 시퀀스
하나의 해 시퀀스는 해의 다중집합입니다. 시퀀스에는 정의된 순서가 없습니다. 이는 순서 없는 목록과 동등하며 중복을 포함할 수 있습니다.
해 병합
두 해가 호환되면, 두 해의 병합은 하나의 해이며, 각 해의 변수를 다음에 매핑합니다. RDF 용어로서, 두 해 중 어느 한쪽에서 가져온 용어입니다.
μ1, μ2를 해 매핑이라고 하고, S1과 S2를 해 시퀀스라고 합니다. 
merge(μ1, μ2) = μ such that
                    μ(v) = μ1(v) if v in dom(μ1)
                    μ(v) = μ2(v) otherwise
merge(S1, S2) = { μ |
                    μ1 in S1, μ2 in S2
                    and compatible(μ1, μ2)
                    μ = merge(μ1, μ2) }
참고

merge(μ1, μ2)의 정의역은 domain(μ1) ∪ domain(μ2)입니다.

두 해에 공통 변수가 없으면 두 해는 호환되며, 두 해의 병합은 다음의 합집합입니다. μ1 및 μ2.

유효 불리언 값
함수 EBV(x)는 유효 불리언 값을 반환하며, 그 대상은 RDF 용어입니다.

빈 노드는 다음 내에서 변수로 취급됩니다. 트리플 패턴으로서 규칙 본문에 속하며, 각 빈 노드를 변수로 대체하되 이 변수는 해당 규칙에서 사용되지 않는 변수입니다. 여기에는 다음 내부의 빈 노드를 대체하는 것도 포함됩니다. 트리플 용어. 동일한 빈 노드가 나타나는 각 위치에는 동일한 변수를 사용하고, 서로 다른 각각의 빈 노드에는 서로 다른 변수를 사용합니다.

define evalRuleElements(B, SEQ, G, GD):
    where
        B is a sequence of rule elements
        SEQ is a solution sequence
        G and GD are RDF graphs

    foreach rule element rElt in B:

        if rElt is a triple pattern element TP:
            X = graphMatch(G, TP)
            SEQ1 = {}
            foreach μ1 in X:
                foreach μ2 in SEQ:
                    if compatible(μ1, μ2):
                      μ3 = merge(μ1, μ2)
                      add μ3 to SEQ1
                    endif
                endfor
            endfor
        endif

        if rElt is a filter element F:
            SEQ1 = {}
            foreach solution μ in SEQ:
                let x = evalFunction(F.expr, μ)
                if x is not an error and EBV(x) is true:
                    add μ to SEQ1
                endif
            endfor
        endif

        if rElt is a negation element N:
            SEQ1 = {}
            foreach solution μ in SEQ:
                S = sequence{ μ }
                if N.evaldata:
                    NEG = evalRuleElements(N.inner, S, G, GD)
                else:
                    NEG = evalRuleElements(N.inner, S, GD, GD)
                endif
                if NEG is empty:
                    add μ to SEQ1
                endif
            endfor
        endif

        if rElt is an assignment element A:
            SEQ1 = {}
            foreach solution μ in SEQ:
                let x = evalFunction(A.expr, μ)
                if x is not an error:
                    # 매핑 A.var -> x를 해 μ에 추가합니다
                    let μ2 be a solution mapping μ ∪ { (A.var, x) }
                    add μ2 to SEQ1
                else:
                    # 오류: 해 μ를 버립니다
                endif
            endfor
        endif

        ## COUNT(*)는 어떻게 처리하나요?
        if rElt is an aggregation element AGG:
            let SEQX = evalRuleElements(AGG.pattern, SEQ, G, GD)
            let KGRP = empty map of solution mappings to solution sequences
            # 해 매핑을 그룹에 배정합니다.
            foreach solution μx in SEQX:
                let μk be μx restricted to AGG.grouping
                if KGRP[μk] is defined:
                    Add μx to the solution sequence KGRP[μk]
                else:
                    KGRP[μk] = solution sequence of one element μx
                endif
            endfor
            # 각 그룹에 대해 집계 함수를 계산하고
            # 그리고 그룹 키와 다음을 포함하는 해 매핑을 생성합니다.
            # 집계 할당의 결과입니다.
            let SEQ1 be an empty solution sequence
            foreach key K of map KGRP:

                let Z be an empty solution mapping
                foreach aggregation function F in AGG.assignments:
                    let V = calculate F.function(X)
                    add solution mapping (F.var, V) to Z
                endfor
                Z = merge(Z, K)
                add Z to SEQ1
            endfor
        endif
        SEQ = SEQ1
    endfor

    return SEQ

define evalRule(R, G, GD):
    where
        R is a well-formed rule
        G and GD are RDF graphs
    let B be R.body
        treating 빈 노드를 변수로.

    # 어떤 변수도 매핑하지 않는 해 하나로 이루어진 해 시퀀스입니다.
    let SEQ0: Solution sequence = { μ0 }

    if R.evaldata:
        let SEQ = evalRuleElements(B, SEQ0, G, GD)
    else:
        let SEQ = evalRuleElements(B, SEQ0, GD, GD)
    endif

    # 규칙 머리부를 평가합니다
    let OUT = empty set
    foreach μ in SEQ:
        let S = {}
        # 각 빈 노드를 새로운 빈 노드로 대체한 규칙 머리부입니다
        let HT = replaceBlankNodes(R.head)
        foreach triple template TT in HT
            let triple = subst(μ, TT)
            Add triple to S
        endfor
        OUT = OUT ∪ S
    endfor
    return OUT
enddefine

OUT에는 다음에도 존재하는 트리플이 포함될 수 있습니다. 기본 그래프.

6.5 규칙 집합 평가

하나의 규칙 집합을 평가하는 것은 해당 규칙 집합의 각 계층을 실행하는 것으로 정의되며, 각 계층은 해당 규칙 집합의 계층화에 속하고, 다음 계층으로 이동하기 전에 순서대로 완전히 실행되어야 합니다. 계층은 이러한 순서에 따라 실행됩니다. 하나의 계층은 먼저 해당 계층의 각 일회 실행 규칙을 평가한 다음, 해당 계층의 일반 규칙을 새로운 트리플이 더 이상 생성되지 않을 때까지 반복해서 평가합니다. 

let G0 be the input base graph
let RS be the rule set
let D be the graph of all DATA triples in RS

Apply stratification to RS

let LS be the sequence of layers after stratification

# 추론 그래프
let GI = { t ∈ D | t ∉ G0 }

# 평가 그래프 및 데이터 블록
let GE = G0 ∪ D

foreach stratum ST in LS:
    foreach rule R in ST.once:
        let X = evalRule(R, GE, G0)
        let Y = { t ∈ X | t ∉ GE }
        GI = GI ∪ Y
        GE = GE ∪ Y
    endfor

    let finished = false
    while ! finished:
        finished = true
        foreach rule R in ST.general:
            let X = evalRule(R, GE, G0)
            let Y = { t ∈ X | t ∉ GE }
            if Y is not empty:
                finished = false
                GI = GI ∪ Y
                GE = GE ∪ Y
            endif
        endfor
    endwhile
endfor
the result is GI

6.6 실제 예제

이 절은 비규범적입니다.

이 절에서는 완전한 규칙 집합의 평가 과정을 단계별로 살펴봅니다. 즉, 규칙 종속성을 결정하고 (4.3 규칙 종속성), 계층화를 계산하고 (4.4 계층화), 각 계층을 차례로 평가하여 추론 그래프를 생성합니다 (6.5 규칙 집합 평가).

이 예제에서는 소프트웨어 구성 요소와 그 종속성을 설명합니다. 프런트엔드는 애플리케이션 서버에 의존하고, 애플리케이션 서버는 데이터베이스와 로깅 라이브러리에 의존합니다. 데이터베이스에는 알려진 취약점이 있습니다. 규칙은 종속성 체인을 따라 취약점에 대한 노출을 전파하고, 심각한 취약점에 노출된 구성 요소에 :criticallyExposed 상태를 부여하고, 심각하지 않은 구성 요소에 :safeToDeploy 상태를 부여하며, 심각하게 노출된 각 구성 요소에 대한 알림을 생성합니다. (실제로 취약점이 구성 요소에 영향을 미치는지 여부는 배포된 버전에 따라 달라집니다. 이 예제에서는 버전을 생략하고 취약점을 직접 명시합니다.) 간결성을 위해 기본 그래프에서는 3.1 트리플 패턴에서처럼 더 구체적인 관계에서 도출하는 대신 :dependsOn 트리플을 직접 명시합니다.

예제 13: 실제 예제: 데이터와 규칙 
:frontend rdf:type :Component ;
          :dependsOn :app .
:app      rdf:type :Component ;
          :dependsOn :db ;
          :dependsOn :logger .
:db       rdf:type :Component ;
          :hasVulnerability :vuln1 .
:logger   rdf:type :Component .
:vuln1    :severity 9.1 .
# R1
RULE { ?x :exposedTo ?v } WHERE { ?x :hasVulnerability ?v }

# R2
RULE { ?x :exposedTo ?v } WHERE { ?x :dependsOn ?y . ?y :exposedTo ?v }

# R3
RULE { ?x :status :criticallyExposed }
WHERE { ?x :exposedTo ?v . ?v :severity ?s . FILTER(?s >= 9.0) }

# R4
RULE { ?x :status :safeToDeploy }
WHERE { ?x rdf:type :Component . NOT { ?x :status :criticallyExposed } }

# R5
RULE { [] rdf:type :Notification ; :concerns ?x }
WHERE { ?x :status :criticallyExposed }

규칙은 주석에서 R1부터 R5까지의 레이블이 지정되어 있으며, 이 절의 나머지 부분에서는 이러한 레이블로 참조됩니다. 이 규칙들은 3.2 재귀부터 3.5 할당 및 RDF 용어 생성까지에서 소개한 규칙입니다. 규칙 집합에는 IMPORTS가 없으므로 가져오기 처리를 거쳐도 변경되지 않으며, DATA 블록도 없으므로 평가는 기본 그래프만으로 시작됩니다.

6.6.1 종속성 결정

어떤 규칙이 어떤 규칙에 의존하는지 결정하기 위해 각 규칙 본문의 각 트리플 패턴을 모든 규칙 헤드의 트리플 템플릿과 비교합니다 (4.3 규칙 종속성).

  • R1의 본문은 단일 트리플 패턴 ?x :hasVulnerability ?v입니다. 어떤 규칙 헤드에도 술어가 :hasVulnerability인 트리플을 생성할 수 있는 트리플 템플릿이 없으므로, 이 패턴은 데이터에만 매칭될 수 있습니다. R1에는 종속성이 없습니다.
  • R2의 본문에는 두 개의 트리플 패턴이 있습니다. ?x :dependsOn ?y는 어떤 규칙 헤드와도 매칭되지 않으므로 데이터에만 매칭됩니다. ?y :exposedTo ?v는 R1의 헤드 템플릿 ?x :exposedTo ?v과 매칭되고, R2 자체의 헤드와도 매칭됩니다. 두 출현 모두 트리플 패턴 요소이며 (부정 요소 안에 나타나지 않고, R2도 한 번 실행되는 규칙이 아닙니다), 따라서 R2는 R1에 대해 열린 종속성을 가지며 자신에 대해서도 열린 종속성을 가집니다. R2가 자신에게 의존하므로 R2는 재귀 규칙입니다.
  • R3의 본문에서 패턴 ?x :exposedTo ?v는 R1과 R2의 헤드와 매칭되므로 R3는 각각에 대해 열린 종속성을 가집니다. 패턴 ?v :severity ?s는 어떤 규칙 헤드와도 매칭되지 않습니다.
  • R4의 본문에서 패턴 ?x rdf:type :Component는 어떤 규칙 헤드와도 매칭되지 않습니다. 술어가 rdf:type인 유일한 헤드 템플릿은 R5에 있으며, 그 목적어 :Notification은 :Component와 다른 RDF 용어이므로 생성된 어떤 트리플도 매칭될 수 없습니다. 패턴 ?x :status :criticallyExposed은 부정 요소 NOT { ?x :status :criticallyExposed } 안에 나타나며 R3의 헤드 템플릿과 매칭됩니다. 패턴이 부정 요소에 나타나므로 R4는 R3에 대해 닫힌 종속성을 가집니다.
  • R5의 본문에서 패턴 ?x :status :criticallyExposed은 R3의 헤드와 매칭됩니다. R5의 헤드에는 빈 노드가 있으므로, 이 패턴이 일반적인 트리플 패턴 요소임에도 불구하고 R3에 대한 종속성은 닫힌 종속성입니다. 어떤 규칙 본문의 패턴도 R5의 헤드 템플릿과 매칭되지 않으므로 어떤 규칙도 R5에 의존하지 않습니다.

따라서 종속성 그래프에는 5개의 정점과 6개의 간선이 있습니다.

  • R2 → R1 (열림)
  • R2 → R2 (열림)
  • R3 → R1 (열림)
  • R3 → R2 (열림)
  • R4 → R3 (닫힘)
  • R5 → R3 (닫힘)

R4와 R5는 R1 또는 R2에 직접적으로 의존하지 않지만, 각각 R3을 통해 두 규칙 모두에 대한 전이적 종속성을 가집니다.

그래프의 유일한 순환은 자기 자신을 향하는 간선 R2 → R2이며, 이는 열린 종속성입니다. 어떤 순환에도 닫힌 종속성이 포함되지 않으므로 계층화 조건이 충족되며 규칙 집합에는 잘 정의된 결과가 있습니다.

6.6.2 계층화 계산

계층화 알고리즘에 따라 모든 규칙은 계층 0에서 시작합니다. 그런 다음 아무것도 변경되지 않을 때까지 간선을 반복해서 검사합니다.

  • 열린 간선은 출발 규칙이 대상과 같은 계층 또는 더 높은 계층에 있어야 함을 요구합니다. 네 개의 열린 간선은 모든 규칙이 계층 0에 있는 상태에서 이미 이 조건을 충족하므로 아무런 변경도 일으키지 않습니다.
  • 닫힌 간선은 대상 규칙이 먼저 완료될 때까지 실행되어야 하므로 출발 규칙이 대상보다 엄격히 높은 계층에 있어야 합니다. 간선 R4 → R3 (닫힘)는 R4와 R3가 모두 계층 0에 있으므로 R4를 계층 1로 이동시킵니다. 마찬가지로 간선 R5 → R3 (닫힘)는 R5를 계층 1로 이동시킵니다.

간선을 한 번 더 순회해도 변경되는 내용이 없으므로 계층이 확정됩니다. 그런 다음 각 계층은 한 번 실행되는 규칙과 일반 규칙으로 나뉩니다. R5는 헤드에 빈 노드가 있으므로 한 번 실행되는 규칙입니다. 규칙 집합의 다른 규칙 중 한 번 실행되는 규칙은 없습니다. 계층화는 다음과 같습니다.

  • 계층 0: 일반 R1, R2, R3; 한 번 실행되는 규칙 없음
  • 계층 1: 한 번 실행되는 R5; 일반 R4

이 순서는 더 높은 계층에 있는 규칙의 의도를 반영합니다. 구성 요소를 배포해도 안전한지, 그리고 어떤 구성 요소에 알림이 필요한지는 모든 :status :criticallyExposed 트리플이 도출된 후에만 결정할 수 있습니다. 이 트리플을 도출하는 규칙 R3는 바로 아래 계층에서, 자신에게 데이터를 제공하는 규칙 R1 및 R2와 함께 완료됩니다.

6.6.3 계층 평가

평가는 6.5 규칙 집합 평가의 알고리즘을 따릅니다. 평가 그래프 GE는 기본 그래프로 시작하고 추론 그래프 GI는 비어 있는 상태로 시작합니다. 각 계층은 순서대로 완료될 때까지 평가됩니다. 계층의 규칙은 패스 단위로 평가되며, 한 패스에서 새로운 트리플이 생성되지 않을 때까지 패스를 반복합니다. 알고리즘은 한 패스 내에서 계층의 규칙이 평가되는 순서를 정하지 않습니다. 이 실행 과정에서는 R1, R2, R3 순서를 사용합니다. 다른 순서는 동일한 추론 결과를 서로 다른 수의 패스에 분산시킬 수 있지만, 계층 0이 완료될 때까지 실행되므로 동일한 최종 그래프를 생성합니다.

이 규칙 집합에는 DATA 블록이 없으므로 평가의 모든 시점에서 GE는 G0와 GI를 더한 것입니다. 따라서 실행 과정에서는 GI만 추적하며, 평가가 진행됨에 따른 상태와 각 새 트리플을 생성한 규칙을 표시합니다.

계층 0, 첫 번째 패스.

  • R1: 본문이 :db :hasVulnerability :vuln1과 매칭되어 ?x = :db와 ?v = :vuln1이 바인딩됩니다. 헤드는 :db :exposedTo :vuln1을 생성합니다. 이 트리플은 GE에 없으므로 GE와 GI에 추가됩니다.
  • R2: 본문은 ?x :dependsOn ?y와 ?y :exposedTo ?v를 조인합니다. 이제 GE에는 :db :exposedTo :vuln1이 있으므로 조인에서 하나의 솔루션이 나옵니다. ?x = :app, ?y = :db, ?v = :vuln1입니다 (:app :dependsOn :db에서 도출됩니다). 헤드는 :app :exposedTo :vuln1을 생성하며, 이는 새 항목이므로 추가됩니다. 아직 :frontend에 대한 솔루션은 없습니다. 이 R2 평가가 시작될 때는 :app :exposedTo :vuln1이 GE에 없었기 때문입니다.
  • R3: 이제 ?x :exposedTo ?v는 :db와 :app에 대해 매칭됩니다. :vuln1 :severity 9.1과 조인하고 FILTER(?s >= 9.0)을 적용하면 두 솔루션이 모두 유지됩니다. 헤드는 :db :status :criticallyExposed와 :app :status :criticallyExposed를 생성하며, 둘 다 새 항목입니다. 
# 계층 0의 첫 번째 패스 후 GI
:db  :exposedTo :vuln1 .                    # 새 항목 (R1)
:app :exposedTo :vuln1 .                    # 새 항목 (R2)
:db  :status :criticallyExposed .           # 새 항목 (R3)
:app :status :criticallyExposed .           # 새 항목 (R3)

새 트리플이 생성되었으므로 계층 0의 평가는 다음 패스로 계속됩니다.

계층 0, 두 번째 패스.

  • R1: 이전과 동일하게 매칭됩니다. :db :exposedTo :vuln1은 이미 GE에 있으므로 새로 생성되는 항목이 없습니다.
  • R2: 이제 조인에서는 ?x = :frontend, ?y = :app, ?v = :vuln1도 나오며, 새 트리플 :frontend :exposedTo :vuln1을 생성합니다. 노출이 종속성 체인을 따라 두 단계를 이동하는 데 두 번의 패스가 필요했습니다.
  • R3: 새 트리플 :frontend :status :criticallyExposed을 생성합니다. 
# 계층 0의 두 번째 패스 후 GI
:db       :exposedTo :vuln1 .
:app      :exposedTo :vuln1 .
:frontend :exposedTo :vuln1 .               # 새 항목 (R2)
:db       :status :criticallyExposed .
:app      :status :criticallyExposed .
:frontend :status :criticallyExposed .      # 새 항목 (R3)

계층 0, 세 번째 패스. 이제 모든 규칙의 모든 솔루션은 이미 GE에 있는 트리플만 생성합니다. GI는 변경되지 않습니다. 새로운 트리플이 없으므로 계층 0이 완료됩니다. 즉, 도출할 수 있는 모든 :exposedTo 트리플과 모든 :status :criticallyExposed 트리플이 도출되었습니다.

계층 1, 한 번 실행되는 규칙. 이 계층의 한 번 실행되는 규칙이 먼저 평가되며, 각각 정확히 한 번 평가됩니다.

  • R5: 본문은 세 개의 :status :criticallyExposed 트리플과 매칭되어 ?x = :db, ?x = :app, ?x = :frontend 솔루션을 제공합니다. 각 솔루션에 대해 헤드를 인스턴스화하면 새로운 빈 노드가 생성되어 솔루션마다 두 개의 트리플이 생성되며, 이들은 심각하게 노출된 각 구성 요소에 대한 알림입니다. 이후 이 계층의 일반 규칙이 반복해서 평가되더라도 R5는 다시 평가되지 않습니다.

계층 1, 일반 규칙의 첫 번째 패스.

  • R4: 패턴 ?x rdf:type :Component는 :frontend, :app, :db, :logger와 매칭됩니다. (방금 R5가 생성한 rdf:type :Notification 트리플과는 매칭되지 않습니다.) 부정 요소 NOT { ?x :status :criticallyExposed }는 :frontend, :app, :db에 대한 솔루션을 거부합니다. GE가 각각에 대한 :status :criticallyExposed 트리플을 포함하기 때문입니다. ?x = :logger 솔루션만 남으며, 새로운 트리플 :logger :status :safeToDeploy을 생성합니다. 
# 계층 1 후 GI
:db       :exposedTo :vuln1 .
:app      :exposedTo :vuln1 .
:frontend :exposedTo :vuln1 .
:db       :status :criticallyExposed .
:app      :status :criticallyExposed .
:frontend :status :criticallyExposed .
_:n1      rdf:type :Notification .          # 새 항목 (R5)
_:n1      :concerns :db .                   # 새 항목 (R5)
_:n2      rdf:type :Notification .          # 새 항목 (R5)
_:n2      :concerns :app .                  # 새 항목 (R5)
_:n3      rdf:type :Notification .          # 새 항목 (R5)
_:n3      :concerns :frontend .             # 새 항목 (R5)
:logger   :status :safeToDeploy .           # 새 항목 (R4)

계층 1, 일반 규칙의 두 번째 패스. 새로운 트리플이 없습니다. 평가가 완료되며, 위에 표시된 GI가 결과 추론 그래프입니다.

이러한 결과를 신뢰할 수 있게 하는 것은 계층화입니다. :frontend :status :criticallyExposed이 도출되기 전인 계층 0의 첫 번째 패스 중에 평가되었다면 R4는 :frontend :status :safeToDeploy이라고 잘못 결론 내렸을 것이며, R5는 :db와 :app에 대한 알림은 생성했지만 :frontend에 대해서는 생성하지 않았을 것입니다. 두 규칙 모두 계층 1까지 지연하면 완전한 :status :criticallyExposed 트리플 집합을 볼 수 있으므로, 각 계층 내에서 규칙이 평가되는 순서는 최종 결과에 영향을 미치지 않습니다.

7. SPARQL-RL 문법

SPARQL-RL 문서는 UTF-8 [RFC3629]로 인코딩되고 RuleSet 생성 규칙으로 시작하며 7.6 문법에 정의된 추가 제약 조건을 준수하는 RDF 문자열입니다. U+0000에서 U+D7FF까지와 U+E000에서 U+10FFFF까지의 범위에 있는 유니코드 스칼라 값만 허용됩니다. 여기에는 U+D800에서 U+DFFF까지의 범위인 서로게이트 코드 포인트가 제외됩니다.

7.1 버전 선언

버전 레이블은 SPARQL-RL의 구문 및 의미론 적합성을 식별하는 문자열입니다.

버전 레이블
버전 레이블
"1.2"

버전 선언은 문서의 앞부분에서 SHOULD 이루어져야 합니다.

하나의 SPARQL-RL 문서에 여러 개의 VERSION 지시문이 나타날 수 있습니다. 각 지시문은 해당 지시문 뒤의 문서 부분에 적용되며, 다른 지시문을 만나거나 문서의 끝에 도달할 때까지 적용됩니다.

버전 레이블은 미디어 유형의 version 매개변수를 통해 지정할 수도 있습니다. 현재 VERSION 지시문이 없는 경우 미디어 유형의 일부로 지정된 버전을 고려합니다.

7.2 공백

공백 (생성 규칙 WS)은 그렇지 않으면 하나의 터미널로 잘못 인식될 두 터미널을 구분하는 데 사용됩니다. 아래에서 대문자로 표기된 규칙 이름은 공백이 중요한 위치를 나타내며, 이러한 규칙들은 SPARQL-RL 파서를 구성하기 위한 터미널의 한 가지 선택이 됩니다.

생성 규칙 String에서는 공백이 중요합니다.

7.3 주석

주석은 IRIREF, STRING_LITERAL1, STRING_LITERAL2, STRING_LITERAL_LONG1 또는 STRING_LITERAL_LONG2 외부에 있는 #로 시작하며, 줄의 끝( LF 또는 CR로 표시됨)까지 계속됩니다. 주석 마커 뒤에 줄의 끝이 없으면 파일의 끝까지 계속됩니다. 주석은 공백으로 취급됩니다.

7.4 IRI 참조

상대 IRI 참조는 통합 자원 식별자(URI): 일반 구문 [RFC3986]에 따라 기준 IRI를 사용하여 제5.2절의 기본 알고리즘만으로 해석됩니다. 구문 기반 정규화나 스킴 기반 정규화 (RFC3986의 제6.2.2절 및 제6.2.3절에 설명됨)는 수행되지 않습니다. IRI 참조에서 추가로 허용되는 문자는 국제화 자원 식별자 (IRI) [RFC3987] 제6.5절에 따라 URI 참조에서 예약되지 않은 문자를 처리하는 것과 동일한 방식으로 처리됩니다.

BASE 지시문은 [RFC3986] 제5.1.1절, "콘텐츠에 포함된 기준 URI"에 따라 상대 IRI 참조를 해석하는 데 사용되는 기준 IRI를 정의합니다. 제5.1.2절, "캡슐화 엔티티의 기준 URI"는 범위 내 기준 IRI가 xml:base 지시문이 있는 SOAP 봉투 또는 Content-Location 헤더가 있는 MIME 멀티파트 문서와 같은 캡슐화 문서에서 유래할 수 있는 방법을 정의합니다. 5.1.3, 검색 URI의 기준 "URI"에서 식별되는 "검색 URI"는 특정 SPARQL-RL 문서를 가져온 URL입니다. 위의 어느 것도 기준 URI를 지정하지 않으면 기본 기준 URI(제5.1.4절, "기본 기준 URI")가 사용됩니다. 각 BASE 지시문은 이전 기준 URI를 기준으로 새로운 범위 내 기준 URI를 설정합니다.

7.5 이스케이프 시퀀스

SPARQL-RL 문서에서는 세 가지 형태의 이스케이프가 사용됩니다.

  • 숫자 이스케이프 시퀀스는 유니코드 코드 포인트의 값을 나타냅니다.

    숫자 이스케이프 시퀀스는 유니코드 서로게이트의 범위인 U+D800에서 U+DFFF까지의 코드 포인트 값을 생성해서는 MUST NOT 됩니다.

    이스케이프 시퀀스 유니코드 코드 포인트
    \u hex hex hex hex 네 개의 16진수 숫자를 최상위 자릿수에서 최하위 자릿수 순으로 해석하여 인코딩된 값에 해당하는, U+0000에서 U+D7FF까지 및 U+E000에서 U+FFFF까지의 범위에 있는 유니코드 코드 포인트입니다.
    \U hex hex hex hex hex hex hex hex 여덟 개의 16진수 숫자를 최상위 자릿수에서 최하위 자릿수 순으로 해석하여 인코딩된 값에 해당하는, U+0000에서 U+D7FF까지 및 U+E000에서 U+10FFFF까지의 범위에 있는 유니코드 코드 포인트입니다.

    여기서 hex는 16진수 문자입니다.

    HEX ::= [0-9] | [A-F] | [a-f]

  • 문자열 이스케이프 시퀀스는 문자열 리터럴에서 전통적으로 이스케이프되는 문자를 나타냅니다.

    이스케이프 시퀀스 유니코드 코드 포인트
    \t U+0009
    \b U+0008
    \n U+000A
    \r U+000D
    \f U+000C
    \" U+0022
    \' U+0027
    \\ U+005C

  • 예약 문자 이스케이프 시퀀스는 \ 뒤에 ~.-!$&'()*+,;=/?#@%_ 문자 중 하나가 오는 형식이며, \의 오른쪽에 있는 문자를 나타냅니다.

A. SPARQL-RL에서 SPARQL로의 변환

이슈 1303: SRL: 다음 변환을 보여 주는 알고리즘 제공: SRL에서 SPARQL 질의로 SPARQL-RL

SPARQL-RL을 SPARQL 질의로 변환하는 과정을 보여 주는 알고리즘을 제공합니다.

B. 가져오기 알고리즘 예제

이 절은 규범적이지 않습니다.

다음 알고리즘은 참조된 모든 문서를 재귀적으로 방문하여 IMPORTS 문을 해석하는 한 가지 방법을 보여 줍니다.

두 규칙 집합 RS1과 RS2의 규칙 집합 병합은 다음과 같이 정의되는 규칙 집합 MR을 생성합니다. 

let RS be a rule set
let V = {}
if RS has a location:
    V = { location of RS }
endif

define ruleSetMerge(rule set RS1, rule set RS2):
    let MR be a rule set
    MR.rules = RS1.rules ∪ RS2.rules
    MR.data = rdf_merge(RS1.data, RS2.data)
    MR.imports = {}
    the result is MR
enddefine

define imports(rule set RS):
    let RS2 be a rule set formed from RS.rules and RS.data
    foreach URL x in RS.imports:
        if x ∉ V:
            V = V ∪ { x }
            read rule set RS3 from URL x
            RS2 = ruleSetMerge(RS2, imports(RS3))
        endif
    endfor
    the result is RS2
enddefine

result is imports(RS)

여기서 rdf_merge는 RDF 병합 연산입니다.

D. 보안 고려 사항

이 절은 규범적이지 않습니다.

SPARQL-RL 문서에는 다른 SPARQL-RL 문서를 참조하고 그 내용을 현재 문서로 가져오는 IMPORTS 문이 포함될 수 있습니다. 가져온 문서 자체에도 IMPORTS 문이 포함되어 있다면, 해당 문서들도 가져옵니다.

규칙 집합을 모듈화하는 데 유용하지만, IMPORTS 문을 사용하면 보안 위험이 발생할 수 있습니다. 이러한 위험에는 규칙 집합이 악의적이거나 우발적으로 평가 과정에서 과도한 계산을 유발하는 경우와, HTTP 요청이 가로채져 오래된 사본을 포함한 다른 문서가 반환되는 경우 등이 있으며, 이에 국한되지는 않습니다.

SPARQL-RL 규칙 집합을 RDF 그래프에 적용하면 상당한 계산량과 메모리 사용량이 발생할 수 있으며, 이를 악용하여 서비스 거부를 유발할 수 있습니다. 애플리케이션은 SPARQL-RL 규칙 집합을 적용함으로써 발생할 수 있는 계산량과 메모리 사용량을 제한하도록 주의해야 합니다.

SPARQL-RL 구문은 UTF-8 [RFC3629]로 인코딩되며, 문자열 데이터에서 이스케이프되지 않은 제어 문자를 사용할 수 있습니다. 이 규격에서는 이러한 내용을 최종 사용자에게 직접 노출하지 않지만, 사용자 에이전트를 통해 표시될 수 있으며, 이러한 문자로 인해 표시된 텍스트가 오해를 불러일으킬 수 있습니다.

SPARQL-RL은 임의의 애플리케이션 데이터를 처리하고 생성하는 데 사용할 수 있으며, 보안 고려 사항은 사용 영역에 따라 달라집니다. 텍스트에 적용할 수 있는 보안 도구와 프로토콜 (예: PGP 암호화, 체크섬 검증, 비밀번호로 보호된 압축)도 SPARQL-RL 문서에 사용할 수 있습니다. SPARQL-RL 규칙 집합 평가 결과에 포함된 정보의 민감도를 반영하도록 보안 및 개인정보 보호 프로토콜을 적용해야 합니다.

SPARQL-RL의 보안 고려 사항에는 RDF 데이터와 다음과 같은 형식의 보안 고려 사항도 포함됩니다. RDF Turtle.

E. 개인정보 보호 고려 사항

이 절은 규범적이지 않습니다.

SPARQL-RL 문서에는 추가적인 애플리케이션 데이터가 포함될 수 있으며, 여기에는 개인 식별 정보(PII)를 표현한 내용이나 민감한 것으로 간주될 수 있는 기타 정보가 포함될 수 있습니다. 이러한 정보가 포함된 규칙 집합을 게시하는 작성자는 해당 정보를 게시할 필요성과 용도를 신중하게 고려하고, 데이터가 사용되거나 잠재적으로 공개될 것으로 예상되는 지역에 적용되는 규정(예: GDPR, CCPA, 기타 규정)도 고려해야 하며, 특히 데이터 접근에 승인 조치가 필요한지 검토하는 것이 좋습니다.
