초록

   이 명세는 JSON Web Signature(JWS), JSON Web Encryption
   (JWE) 및 JSON Web Key(JWK) 명세와 함께 사용할 암호화 알고리즘과

   IANA 레지스트리를 정의합니다.

1.  소개

   이 명세는 JSON Web Signature(JWS) [JWS], JSON Web
   Encryption(JWE) [JWE] 및 JSON Web Key(JWK) [JWK] 명세와 함께
   사용할 암호화 알고리즘과 식별자를 등록합니다. 또한 이러한 식별자를 위한 여러
   IANA 레지스트리를 정의합니다. 이들 모든 명세는 JSON 기반
   [RFC7159] 데이터 구조를 사용합니다. 이
   명세는 또한 이러한 알고리즘과 키 유형에
   특화된 의미와 연산을 설명합니다.

   알고리즘과 식별자를 JWS, JWE 및 JWK 명세 자체가 아니라
   여기에 등록하는 것은 시간이 지남에 따라 필수, 권고,
   선택 사항 및 사용 중단 알고리즘 집합이 변경되더라도 해당 명세들을
   변경하지 않고 유지할 수 있도록 하기 위한 것입니다. 또한 이를 통해
   이 문서를 변경하지 않고 JWS, JWE 및 JWK 명세를 변경할 수
   있습니다.

   이 명세에서 정의하는 이름은 결과 표현을 간결하게 만드는 것이
   핵심 목표이므로 짧습니다.

   UTF8(STRING)은 STRING의 UTF-8 [RFC3629] 표현의 옥텟을

   ASCII(STRING)은 STRING의 ASCII [RFC20] 표현의 옥텟을
   나타내며, 여기서 STRING은 0개 이상의 ASCII
   문자 시퀀스입니다.

   두 값 A와 B의 연결은 A || B로 나타냅니다.

2.  용어

   "JSON Web Signature (JWS)", "Base64url Encoding", "Header
   Parameter", "JOSE Header", "JWS Payload", "JWS Protected Header",
   "JWS Signature", "JWS Signing Input" 및 "Unsecured JWS"라는 용어는
   JWS 명세 [JWS]에서 정의합니다.

   "JSON Web Encryption (JWE)", "Additional Authenticated Data
   (AAD)", "Authentication Tag", "Content Encryption Key (CEK)", "Direct
   Encryption", "Direct Key Agreement", "JWE Authentication Tag", "JWE
   Ciphertext", "JWE Encrypted Key", "JWE Initialization Vector", "JWE
   Protected Header", "Key Agreement with Key Wrapping", "Key
   Encryption", "Key Management Mode" 및 "Key Wrapping"이라는 용어는
   JWE 명세 [JWE]에서 정의합니다.

   "JSON Web Key (JWK)" 및 "JWK Set"이라는 용어는 JWK
   명세 [JWK]에서 정의합니다.

   "Ciphertext", "Digital Signature", "Initialization Vector",
   "Message Authentication Code (MAC)" 및 "Plaintext"라는 용어는
   "인터넷 보안 용어집, 버전 2" [RFC4949]에서 정의합니다.

3.2.  SHA-2 함수를 사용하는 HMAC

   해시 기반 메시지 인증 코드(HMAC)를 사용하면 비밀값과
   암호화 해시 함수를 사용하여 MAC을 생성할 수 있습니다. 이를 통해
   MAC을 생성한 주체가 MAC 키를 보유하고 있었음을
   입증할 수 있습니다. HMAC을 구현하고 검증하는 알고리즘은
   RFC 2104 [RFC2104]에 제공됩니다.

   이 알고리즘에는 해시 출력과 동일한 크기(예: "HS256"의 경우
   256비트) 이상의 키를 반드시 사용해야 합니다. (이
   요구 사항은 NIST SP 800-117 [NIST.800-107]의 섹션 5.3.4(HMAC
   키의 보안 효과)에 근거하며, 여기서는
   유효 보안 강도가 키의 보안 강도와
   내부 해시 값 크기의 두 배 중 작은 값이라고 명시합니다.)

   HMAC SHA-256 MAC은 RFC 2104에 따라 생성되며, SHA-256을
   해시 알고리즘 "H"로, JWS Signing Input을 "text" 값으로,
   공유 키를 사용합니다. HMAC 출력 값이 JWS
   Signature입니다.

   다음 "alg"(알고리즘) 헤더 매개변수 값은
   JWS Signature가 해당 알고리즘을 사용하여 계산된
   HMAC 값임을 나타내는 데 사용합니다.

                +-------------------+--------------------+
                | "alg" 매개변수 값 | MAC 알고리즘       |
                +-------------------+--------------------+
                | HS256             | SHA-256 사용 HMAC  |
                | HS384             | SHA-384 사용 HMAC  |
                | HS512             | SHA-512 사용 HMAC  |
                +-------------------+--------------------+

   JWS용 HMAC SHA-256 MAC은 RFC 2104에 따라 HMAC
   값을 계산하여 검증합니다. SHA-256을 해시 알고리즘 "H"로 사용하고,
   수신한 JWS Signing Input을 "text" 값으로 사용하며,
   공유 키를 사용합니다. 그런 다음 계산된 HMAC 값을
   수신한 인코딩된 JWS Signature 값을 base64url 디코딩한 결과와 비교합니다.
   타이밍 공격을 방지하기 위해 계산된 HMAC 값과 JWS Signature 값의
   비교는 반드시 상수 시간 방식으로 수행해야 합니다.
   또는 계산된 HMAC 값을 base64url 인코딩하여
   수신한 인코딩된 JWS Signature 값과 비교할 수 있습니다(역시
   상수 시간 방식). 이 비교는 인코딩되지 않은 값을
   비교하는 것과 동일한 결과를 생성합니다. 두 경우 모두 값이 일치하면
   HMAC이 검증된 것입니다.

3.3.  RSASSA-PKCS1-v1_5를 사용하는 디지털 서명

   정의된 RSASSA-PKCS1-v1_5 디지털 서명 알고리즘
   (일반적으로 PKCS #1으로 알려짐)을 SHA-2 [SHS] 해시 함수와 함께

   이러한 알고리즘에는 2048비트 이상의 키를 반드시 사용해야 합니다.

   RSASSA-PKCS1-v1_5 SHA-256 디지털 서명은 다음과 같이
   생성합니다. 원하는 개인 키와 SHA-256 해시 함수를 사용하여
   RSASSA-PKCS1-v1_5-SIGN으로 JWS Signing Input의 디지털 서명을
   생성합니다. 이것이 JWS Signature 값입니다.

   다음 "alg"(알고리즘) 헤더 매개변수 값은
   JWS Signature가 해당 알고리즘을 사용하여 계산된 디지털 서명
   값임을 나타내는 데 사용합니다.

          +-------------------+---------------------------------+
          | "alg" 매개변수 값 | 디지털 서명 알고리즘             |
          +-------------------+---------------------------------+
          | RS256             | SHA-256 사용 RSASSA-PKCS1-v1_5 |
          | RS384             | SHA-384 사용 RSASSA-PKCS1-v1_5 |
          | RS512             | SHA-512 사용 RSASSA-PKCS1-v1_5 |
          +-------------------+---------------------------------+

   다음과 같이 검증합니다. JWS Signing Input, JWS
   Signature 및 서명자가 사용한 개인 키에 대응하는 공개 키를
   SHA-256을 해시 함수로 사용하는
   RSASSA-PKCS1-v1_5-VERIFY 알고리즘에 전달합니다.

   RSASSA-PKCS1-v1_5 SHA-384 및 RSASSA-
   PKCS1-v1_5 SHA-512 알고리즘을 사용한 서명과 검증은

3.4.  ECDSA를 사용하는 디지털 서명

   타원 곡선 디지털 서명 알고리즘(ECDSA) [DSS]은
   타원 곡선 암호화를 사용할 수 있게 하며, 이는 더 짧은 키 크기를
   사용하면서 RSA 암호화와 동등한 보안을 제공하고
   많은 연산에서 더 빠른 처리 속도를 제공할 수 있습니다. 즉,
   ECDSA 디지털 서명은 동등한 강도의 RSA 디지털 서명보다
   길이 측면에서 상당히 작습니다.

   이 명세는 P-256 곡선과 SHA-256 암호화 해시 함수를 사용하는 ECDSA,
   P-384 곡선과 SHA-384 해시 함수를 사용하는 ECDSA,
   P-521 곡선과 SHA-512 해시 함수를 사용하는 ECDSA를 정의합니다.
   P-256, P-384 및 P-521 곡선은
   [DSS]에 정의되어 있습니다.

   ECDSA P-256 SHA-256 디지털 서명은 다음과 같이 생성합니다.

   1.  원하는 개인 키로 ECDSA P-256 SHA-256을 사용하여
       JWS Signing Input의 디지털 서명을 생성합니다. 출력은
       (R, S) 쌍이며, R과 S는 256비트 부호 없는 정수입니다.

   2.  R과 S를 빅 엔디언 순서의 옥텟 시퀀스로 변환하며, 각
       배열의 길이는 32옥텟이어야 합니다. 값에 포함된 선행 0
       옥텟을 생략하기 위해 옥텟 시퀀스 표현을
       단축해서는 안 됩니다.

   3.  두 옥텟 시퀀스를 R, 그다음 S 순서로 연결합니다.
       (많은 ECDSA 구현은 이 연결 결과를
       출력으로 직접 생성한다는 점에 유의하십시오.)

   4.  결과로 얻은 64옥텟 시퀀스가 JWS Signature 값입니다.

   다음 "alg"(알고리즘) 헤더 매개변수 값은
   JWS Signature가 해당 알고리즘을 사용하여 계산된 디지털 서명
   값임을 나타내는 데 사용합니다.

           | ES384             | P-384 및 SHA-384 사용 ECDSA  |

3.6.  "none" 알고리즘 사용

   무결성 보호를 제공하지 않는 JWS도 생성할 수 있습니다.
   이러한 JWS를 비보안 JWS라고 합니다. 비보안 JWS는
   "alg" 값 "none"을 사용하며 다른 JWS와 동일한 형식이지만,
   JWS Signature 값으로 빈 옥텟 시퀀스를 반드시 사용해야 합니다.
   수신자는 JWS Signature 값이 빈 옥텟 시퀀스인지
   반드시 확인해야 합니다.

   비보안 JWS를 지원하는 구현은 애플리케이션이
   특정 객체에 무결성 보호가 없어도 허용된다고 지정하지 않는 한
   그러한 객체를 유효한 것으로 받아들여서는 안 됩니다.
   구현은 기본적으로 비보안 JWS를 받아들여서는 안 됩니다.
   다운그레이드 공격을 완화하기 위해 애플리케이션은
   전역 수준에서 비보안 JWS의 수락을 신호해서는 안 되며,
   객체별로 수락 여부를 신호하는 것이 좋습니다. 이 알고리즘 사용과 관련된
   보안 고려 사항은 섹션 8.5를 참조하십시오.

   JWE Encrypted Key가 해당 알고리즘을 사용하여

4.6.2.  ECDH 키 합의를 위한 키 파생

   키 파생은 [NIST.800-56A]의 섹션 5.8.1에 정의된
   Concat KDF를 사용하여 수행하며, Digest Method는 SHA-256입니다.
   Concat KDF 매개변수는 다음과 같이 설정합니다.

  Z

   keydatalen
      원하는 출력 키의 비트 수로 설정합니다.
      "ECDH-ES"의 경우 "enc" 알고리즘에서 사용하는 키의 길이입니다.
      "ECDH-ES+A128KW", "ECDH-ES+A192KW" 및 "ECDH-ES+A256KW"의 경우
      각각 128, 192 및 256입니다.

      Data는 "alg"(알고리즘) 헤더 매개변수 값의 ASCII 표현에 대한
      옥텟으로 설정합니다.

      빈 옥텟 시퀀스로 설정합니다.

   PartyVInfo
      PartyVInfo 값은 Datalen || Data 형식이며, Data는
      0개 이상의 옥텟으로 이루어진 가변 길이 문자열이고 Datalen은
      Data의 길이(옥텟 단위)를 나타내는 고정 길이의
      빅 엔디언 32비트 카운터입니다. "apv"(agreement PartyVInfo) 헤더
      매개변수가 있으면 Data는 "apv" 값을 base64url
      디코딩한 결과로 설정하고 Datalen은 Data의 옥텟 수로
      설정합니다. 그렇지 않으면 Datalen은 0으로, Data는
      빈 옥텟 시퀀스로 설정합니다.

   SuppPubInfo
      keydatalen을 32비트 빅 엔디언 정수로 표현한 값으로
      설정합니다.

   SuppPrivInfo
      빈 옥텟 시퀀스로 설정합니다.

   애플리케이션은 해당 애플리케이션에서 "apu" 및 "apv" 헤더
   매개변수를 어떻게 사용할지 지정해야 합니다. "apu"와 "apv" 값은
   사용되는 경우 서로 달라야 합니다. [NIST.800-56A]를 준수하려는 애플리케이션은
   해당 문서의 요구 사항을 충족하는 값을 제공해야 하며,
   예를 들어 생성자와 소비자를 식별하는 값을 사용할 수 있습니다.
   또는 애플리케이션은 "Diffie-Hellman Key Agreement Method" [RFC2631]와
   유사한 방식으로 키 파생을 수행할 수 있습니다.
   이 경우 "apu" 매개변수는 생략하거나 임의의 512비트 값
   (RFC 2631의 Ephemeral-Static 모드에서 PartyAInfo와 유사한 값)을
   나타낼 수 있으며, "apv" 매개변수는 존재하지 않는 것이 좋습니다.

   이 방법을 사용하는 키 합의 계산의 예시는
   부록 C를 참조하십시오.

4.8.  PBES2를 사용한 키 암호화

   이 절에서는 먼저 [RFC2898]의 섹션 6.2에 지정된
   PBES2 방식을 사용하여 사용자가 제공한 비밀번호로부터 키 암호화 키를
   파생한 다음, 파생된 키로 JWE CEK를 암호화함으로써
   JWE CEK에 비밀번호 기반 암호화를 수행하는 구체적인 방법을 정의합니다.

   이러한 알고리즘은 PBKDF2 키 파생의 의사난수 함수(PRF)로
   HMAC SHA-2 알고리즘을 사용하며, 암호화 방식에는 AES Key Wrap
   [RFC3394]을 사용합니다. PBES2 비밀번호 입력은
   옥텟 시퀀스입니다. 사용할 비밀번호가 옥텟 시퀀스가 아니라
   텍스트 문자열로 표현되는 경우 해당 텍스트 문자열의 UTF-8 인코딩을
   옥텟 시퀀스로 반드시 사용해야 합니다. 솔트 매개변수는 아래의
   "p2s" 정의에 지정된 대로 "p2s"(PBES2 salt input) 헤더 매개변수 값과
   "alg"(알고리즘) 헤더 매개변수 값으로부터 반드시 계산해야 합니다.
   반복 횟수 매개변수는 "p2c"(PBES2 count) 헤더 매개변수 값으로
   반드시 제공해야 합니다. 각 알고리즘은 각각 HMAC SHA-256,
   HMAC SHA-384 및 HMAC SHA-512를 PRF로 사용하고 128비트,
   192비트 및 256비트 AES Key Wrap 키를 사용합니다.
   파생 키 길이는 각각 16, 24 및 32옥텟입니다.

   다음 "alg"(알고리즘) 헤더 매개변수 값은
   JWE Encrypted Key가 해당 비밀번호 기반 암호화
   알고리즘의 결과를 해당 키 래핑 알고리즘용 키 암호화 키로
   사용하여 CEK를 암호화한 결과임을 나타내는 데 사용합니다.

   +--------------------+----------------------------------------------+
   | "alg" 매개변수 값  | 키 관리 알고리즘                             |
   +--------------------+----------------------------------------------+
   | PBES2-HS256+A128KW | HMAC SHA-256 및 "A128KW" 래핑을 사용하는    |
   |                    | PBES2                                        |
   | PBES2-HS384+A192KW | HMAC SHA-384 및 "A192KW" 래핑을 사용하는    |
   |                    | PBES2                                        |
   | PBES2-HS512+A256KW | HMAC SHA-512 및 "A256KW" 래핑을 사용하는    |
   |                    | PBES2                                        |
   +--------------------+----------------------------------------------+

   "PBES2-HS256+A128KW"를 사용하는 키 암호화 계산의 예시는
   JWK 명세 [JWK]의 부록 C를 참조하십시오.

   정의합니다. 첫 번째는 128비트 CBC 키와 HMAC SHA-256을,
   두 번째는 192비트 CBC 키와 HMAC SHA-384를, 세 번째는
   256비트 CBC 키와 HMAC SHA-512를 사용합니다. 이러한 알고리즘의
   테스트 사례는 부록 B에서 확인할 수 있습니다.

5.2.2.1.  AES_CBC_HMAC_SHA2 암호화

   인증된 암호화 알고리즘은 네 개의 옥텟 문자열을 입력으로
   받습니다. 비밀 키 K, 평문 P, Additional Authenticated Data
   A 및 Initialization Vector IV입니다. 인증된 암호문
   값 E와 Authentication Tag 값 T가 출력으로 제공됩니다.
   평문의 데이터는 암호화되고 인증되며,
   Additional Authenticated Data는 인증되지만 암호화되지는 않습니다.

   암호화 과정은 다음과 같거나 이와 동등한 단계 집합을
   사용합니다.

   1.  보조 키 MAC_KEY 및 ENC_KEY는 입력 키 K로부터
       다음과 같이 생성합니다. 이 두 키는 각각 옥텟
       문자열입니다.

          MAC_KEY는 K의 처음 MAC_KEY_LEN개 옥텟으로
          순서대로 구성됩니다.
          ENC_KEY는 K의 마지막 ENC_KEY_LEN개 옥텟으로
          순서대로 구성됩니다.





Jones                        표준 트랙                        [페이지 23]

 RFC 7518                JSON 웹 알고리즘(JWA)               2015년 5월


       입력 키 K의 옥텟 수는 반드시
       MAC_KEY_LEN과 ENC_KEY_LEN의 합이어야 합니다. 이러한 매개변수의 값은
       섹션 5.2.3부터 5.2.5까지의 인증된 암호화 알고리즘에서
       지정합니다. MAC 키가 입력 키 K에서 암호화 키보다
       앞에 온다는 점에 유의하십시오. 이는 식별자
       "AES_CBC_HMAC_SHA2"의 알고리즘 이름 순서와 반대입니다.

   2.  사용되는 IV는 암호에서 사용하기 위해 무작위 또는
       의사무작위로 생성한 128비트 값입니다.

   3.  ENC_KEY를 키로, IV를 사용하여 PKCS #7 패딩을 적용한
       CBC 방식으로 평문을 암호화합니다. 이 단계의 암호문 출력을
       E라고 나타냅니다.

   4.  옥텟 문자열 AL은 Additional Authenticated Data A의
       비트 수를 64비트 부호 없는 빅 엔디언 정수로
       표현한 값과 같습니다.

   5.  다음 데이터에 순서대로 HMAC [RFC2104]을 적용하여
       메시지 Authentication Tag T를 계산합니다.

          Additional Authenticated Data A,
          Initialization Vector IV,
          이전 단계에서 계산한 암호문 E, 그리고
          위에서 정의한 옥텟 문자열 AL.

       문자열 MAC_KEY를 MAC 키로 사용합니다. 이 단계에서 계산된
       MAC 출력을 M이라고 나타냅니다. M의 처음 T_LEN개 옥텟을
       T로 사용합니다.

   6.  암호문 E와 Authentication Tag T를 인증된 암호화의
       출력으로 반환합니다.

   암호화 과정은 다음과 같이 나타낼 수 있습니다. 여기서 K, P, A,
   IV 및 E는 각각 키, 평문, Additional Authenticated Data,
   Initialization Vector 및 암호문을 나타냅니다.

      MAC_KEY = K의 처음 MAC_KEY_LEN개 옥텟,
      ENC_KEY = K의 마지막 ENC_KEY_LEN개 옥텟,
      E = CBC-PKCS7-ENC(ENC_KEY, P),
      M = MAC(MAC_KEY, A || IV || E || AL),
      T = M의 처음 T_LEN개 옥텟.

5.2.2.2.  AES_CBC_HMAC_SHA2 복호화

   인증된 복호화 연산에는 위에서 정의한 K, A, IV, E 및 T의
   다섯 가지 입력이 있습니다. 출력은 하나뿐이며, 평문 값 P 또는
   입력이 인증되지 않았음을 나타내는 특수 기호 FAIL입니다.
   인증된 복호화 알고리즘은 다음과 같거나 이와 동등한
   단계 집합을 사용합니다.

   1.  보조 키 MAC_KEY와 ENC_KEY를 섹션 5.2.2.1의
       1단계와 동일하게 입력 키 K로부터 생성합니다.

   2.  A와 E의 무결성과 진위를
       섹션 5.2.2.1의 5단계와 동일한 입력으로 HMAC을 계산하여
       확인합니다. 이전 단계의 값 T를
       HMAC 출력의 처음 MAC_KEY 길이 비트와 비교합니다.
       이 값들이 동일하면 A와 E가 유효한 것으로 간주하고
       처리를 계속합니다. 그렇지 않으면 MAC 검증에 사용한 모든
       데이터를 폐기하고 인증된 복호화 연산은
       실패했음을 나타내는 값을 반환한 뒤 연산을 중단합니다.
       (단, 타이밍 공격 방지와 관련된 보안 고려 사항은 [JWE]의
       섹션 11.5를 참조하십시오.)

   3.  값 E를 복호화하고 PKCS #7 패딩을 검사한 후
       제거합니다. 값 IV를 Initialization Vector로 사용합니다.
       값 ENC_KEY를 복호화 키로 사용합니다.

   4.  평문 값을 반환합니다.

5.2.3.  AES_128_CBC_HMAC_SHA_256

   이 알고리즘은 위의 일반
   AES_CBC_HMAC_SHA2 알고리즘을 구체화한 인스턴스입니다.
   메시지 인증을 제공하기 위해 SHA-256 해시 함수 [SHS]와 함께
   HMAC 메시지 인증 코드 [RFC2104]를 사용하며,
   HMAC 출력은 [RFC4868]에 정의된 HMAC-SHA-256-128 알고리즘에 대응하도록

      ENC_KEY_LEN은 16옥텟입니다.
      MAC_KEY_LEN은 16옥텟입니다.
      HMAC에는 SHA-256 해시 알고리즘을 사용합니다.
      HMAC-SHA-256 출력은 마지막 16옥텟을 제거하여
      T_LEN=16옥텟으로 잘라냅니다.

   적절한 제목(예: "알고리즘 등록 요청:

   거부할 경우 설명과, 해당되는 경우 요청을 성공시키기 위한
   제안을 포함해야 합니다.

7.1.  JSON 웹 서명 및 암호화 알고리즘 레지스트리

   이 명세는 JWS 및 JWE의 "alg"(알고리즘) 및 "enc"(암호화 알고리즘)
   헤더 매개변수 값을 위한 IANA "JSON Web Signature and
   Encryption Algorithms" 레지스트리를 설정합니다.
   이 레지스트리는 알고리즘 이름, 알고리즘 설명,
   알고리즘 사용 위치, 구현 요구 사항,
   변경 제어자 및 해당 알고리즘을 정의하는 명세에 대한 참조를
   기록합니다. 사용 위치 집합이 서로 겹치지 않는 경우
   동일한 알고리즘 이름을 여러 번 등록할 수 있습니다.

   서로 다른 길이의 키를 사용하는 알고리즘의 여러 변형을
   등록하고 각 키 길이를 고정해야 하는 경우
   (예: 키 파생 함수로 생성되기 때문에)
   알고리즘 이름에 키 길이를 포함하는 것이 좋습니다.
   이렇게 하면 JSON 텍스트를 읽는 사람이 보안 결정을
   더 쉽게 내릴 수 있습니다.

   지정 전문가는 등록하려는 알고리즘이 현재
   암호학적으로 신뢰할 수 있다고 간주되거나
   Deprecated 또는 Prohibited로 등록되는지를 합리적으로
   충분히 검토하는 것이 좋습니다.

7.1.1.  등록 템플릿

   알고리즘 이름:
      요청된 이름(예: "HS256")입니다. 이 이름은 대소문자를 구분하는
      ASCII 문자열입니다. 지정 전문가가 예외를 허용할 충분한
      이유가 있다고 명시하지 않는 한, 대소문자를 구분하지 않고
      비교했을 때 다른 등록된 이름과 일치해서는 안 됩니다.

   알고리즘 설명:
      알고리즘에 대한 간략한 설명입니다(예: "SHA-256을 사용하는 HMAC").

   알고리즘 사용 위치:
      알고리즘의 사용 위치입니다. 알고리즘을 JWS 또는 JWE와 함께
      사용하는 경우 "alg" 또는 "enc" 값 중 하나 이상이어야 합니다.
      알고리즘 식별자가 JWK "alg" 멤버 값으로 사용되지만 JWS 또는
      JWE와 함께 사용되지 않는 경우 "JWK" 값을 사용합니다. 예를 들어
      인증되지 않은 암호화 알고리즘이 이에 해당할 수 있습니다.
      지정 전문가의 승인을 받아 다른 값을 사용할 수도 있습니다.

   JOSE 구현 요구 사항:
      JWS 및 JWE의 알고리즘 구현 요구 사항이며,
      필수, 권고, 선택 사항, 사용 중단 또는 금지 중 하나여야 합니다.
      선택적으로 단어 뒤에 "+" 또는 "-"를 붙일 수 있습니다.
      "+"는 향후 명세 버전에서 요구 수준이 높아질 가능성이
      있음을 나타냅니다. "-"는 향후 명세 버전에서 요구 수준이
      낮아질 가능성이 있음을 나타냅니다. 인증되지 않은 암호화
      알고리즘이나 JWS 또는 JWE 알고리즘으로 직접 사용하기에
      부적합한 다른 알고리즘에 등록되는 모든 식별자는
      "금지"로 등록해야 합니다.

   변경 제어자:
      표준 트랙 RFC의 경우 "IESG"를 기재합니다. 그 외의 경우에는
      책임 당사자의 이름을 기재합니다. 기타 세부 정보(예: 우편
      주소, 이메일 주소, 홈페이지 URI)도 포함할 수 있습니다.

7.3.1.  등록 템플릿

   압축 알고리즘 값:
      요청된 이름(예: "DEF")입니다. 이 명세의 핵심 목표는
      결과 표현을 간결하게 만드는 것이므로, 충분한 이유가
      없는 한 이름은 8자를 넘지 않도록 짧게 하는 것이 권고됩니다.
      이 이름은 대소문자를 구분합니다. 지정 전문가가 예외를
      허용할 충분한 이유가 있다고 명시하지 않는 한, 대소문자를
      구분하지 않고 비교했을 때 다른 등록된 이름과 일치해서는 안 됩니다.

   압축 알고리즘 설명:
      압축 알고리즘에 대한 간략한 설명입니다(예: "DEFLATE").

   변경 제어자:
      표준 트랙 RFC의 경우 "IESG"를 기재합니다. 그 외의 경우에는
      책임 당사자의 이름을 기재합니다. 기타 세부 정보(예: 우편 주소,
      이메일 주소, 홈페이지 URI)도 포함할 수 있습니다.

   명세 문서:
      매개변수를 지정하는 문서에 대한 참조이며,
      가능하면 문서 사본을 가져오는 데 사용할 수 있는 URI도

8.1.  암호화 민첩성

   구현자는 암호화 알고리즘이 시간이 지남에 따라 약해진다는 점을
   인지해야 합니다. 새로운 암호 분석 기법이 개발되고 컴퓨팅
   성능이 향상됨에 따라 특정 암호화 알고리즘을 깨는 데 필요한
   작업량은 감소합니다. 따라서 구현자와 배포 환경은
   지원되고 사용되는 알고리즘 집합이 시간에 따라 변경되는 것에
   대비해야 합니다. 따라서 암호화 알고리즘 구현은 모듈식이어야 하며,
   새로운 알고리즘을 쉽게 추가할 수 있어야 합니다.

8.2.  키 수명

   많은 알고리즘에는 키 수명 및/또는 키를 사용할 수 있는
   횟수와 관련된 보안 고려 사항이 있습니다. 이러한 보안 고려 사항은
   해당 알고리즘을 JOSE 데이터 구조와 함께 사용할 때도 계속
   적용됩니다. 키 수명에 대한 구체적인 지침은 NIST SP 800-57
   [NIST.800-57]을 참조하십시오.

8.3.  RSAES-PKCS1-v1_5 보안 고려 사항

   RFC 3447의 섹션 8 [RFC3447]에서는 새 애플리케이션에
   RSASSA-PKCS1-v1_5를 채택하지 말고 대신 RSASSA-PSS로
   전환할 것을 명시적으로 요구하지만, 이 명세에는 상호 운용성
   이유로 RSASSA-PKCS1-v1_5가 포함되어 있습니다. 이는
   널리 구현되어 있기 때문입니다.

   RSAES-PKCS1-v1_5와 함께 사용하는 키는
   RFC 3447의 섹션 7.2에 있는 제약 조건을 따라야 합니다. 또한
   "RSA 암호 시스템에 대한 20년간의 공격" [Boneh99]의 섹션 3에
   설명된 것처럼 공개 키 지수 값이 낮은 키를 사용해서는 안 됩니다.

8.4.  AES GCM 보안 고려 사항

   AES GCM과 함께 사용하는 키는 [NIST.800-38D]의 섹션 8.3에 있는
   제약 조건을 따라야 하며, 여기에는 "주어진 키를 사용하는
   인증된 암호화 함수의 모든 IV 길이와 모든 인스턴스를 포함하여
   인증된 암호화 함수의 총 호출 횟수는 2^32를 초과해서는 안 된다"고
   명시되어 있습니다. 이 규칙에 따라 AES GCM은 동일한 키 값을
   2^32회를 초과하여 사용해서는 안 됩니다.

   동일한 AES GCM 키와 함께 같은 IV 값을 여러 번 사용해서는
   절대로 안 됩니다. 이를 방지하는 한 가지 방법은 키와 함께
   카운터를 저장하고 사용할 때마다 증가시키는 것입니다.
   이 카운터는 위의 2^32 한도를 초과하지 않도록 하는 데도
   사용할 수 있습니다.

   이 보안 고려 사항은 복합 AES-CBC HMAC SHA-2 또는
   AES Key Wrap 알고리즘에는 적용되지 않습니다.

8.5.  비보안 JWS 보안 고려 사항

   비보안 JWS("alg" 값 "none"을 사용하는 JWS)는 무결성
   보호를 제공하지 않습니다. 따라서 페이로드가 디지털 서명이나
   MAC 값 이외의 수단으로 보호되는 상황 또는 보호할 필요가 없는
   상황에서만 사용해야 합니다.

   비보안 JWS를 기본적으로 허용하지 않도록 하는 한 가지 예는
   가상의 JWS 소프트웨어 라이브러리의 "verify" 메서드가
   "none"이 허용 가능한 "alg" 값인지 나타내는 Boolean
   "acceptUnsecured" 매개변수를 갖도록 하는 것입니다. 또 다른 예로,
   "verify" 메서드는 애플리케이션이 허용하는 알고리즘 목록을
   매개변수로 받을 수 있으며, 해당 목록에 "none"이 없으면
   비보안 JWS 값을 거부할 수 있습니다.

   다음 예시는 비보안 JWS를 전역 수준에서 허용하지 않아야 하는
   이유를 보여줍니다. 애플리케이션이 두 채널,
   (1) HTTP 및 (2) 클라이언트 인증을 사용하는 HTTPS를 통해
   JWS를 허용한다고 가정합니다. HTTP를 통해 수신한 객체에는
   JWS Signature를 요구하지만 HTTPS에서는 비보안 JWS를 허용합니다.
   애플리케이션이 "none"을 허용한다고 전역적으로 표시한다면
   공격자는 HTTP를 통해 비보안 JWS를 제공하면서도 해당 객체를
   성공적으로 검증되게 할 수 있습니다. 대신 애플리케이션은
   HTTPS를 통해 수신한 각 객체에 대해 "none" 허용을 표시해야
   하지만(예: 위의 첫 번째 가상 JWS 소프트웨어 라이브러리에서
   "acceptUnsecured"를 "true"로 설정), HTTP를 통해 수신한
   각 객체에 대해서는 그렇게 해서는 안 됩니다.

8.8.  비밀번호 고려 사항

   비밀번호는 여러 공격에 취약합니다. 이러한 한계 중 일부를
   완화하기 위해 이 문서는 사용자가 제공한 비밀번호에서
   암호화 키를 파생하는 데 RFC
   2898 [RFC2898]의 원칙을 적용합니다.

   그러나 비밀번호의 강도는 여전히 상당한 영향을 미칩니다.
   높은 엔트로피를 가진 비밀번호는 사전 공격에 대한 저항력이 더 높습니다.
   [NIST.800-63-2]에는 비밀번호 엔트로피를 추정하기 위한 지침이
   포함되어 있으며, 이는 애플리케이션과 사용자가 더 강한
   비밀번호를 생성하는 데 도움이 될 수 있습니다.

   이상적인 비밀번호는 파생 키 길이와 같거나 그보다 긴
   비밀번호입니다. 그러나 특정 알고리즘별 크기를 초과하는
   비밀번호는 먼저 해시되며, 이로 인해 공격자의 유효 검색 공간이
   해시 알고리즘 길이로 줄어듭니다. "PBES2-HS256+A128KW"에
   사용하는 비밀번호는 16옥텟보다 짧지 않고 128옥텟보다
   길지 않도록 하는 것이 권고되며, "PBES2-HS512+A256KW"에
   사용하는 비밀번호는 32옥텟보다 짧지 않고 128옥텟보다
   길지 않도록 하는 것이 권고됩니다.

   그럼에도 비밀번호 기반 암호화를 어디에서 어떻게 사용할지
   주의해야 합니다. 반복 횟수가 너무 작으면 이러한 알고리즘은
   여전히 사전 기반 공격에 취약할 수 있습니다. 이는 특히
   파일 시스템에 저장된 보호 데이터처럼 공격자가 보호를 우회하려는
   시도를 무제한으로 수행할 수 있는 데이터를 보호하는 데 이러한
   알고리즘을 사용하는 경우 특히 문제가 됩니다.

   합의된 키를 생성합니다.

   JSON 콘텐츠의 서명 및 암호화를 위한 해결 방법은 이전에
   "Magic Signatures" [MagicSignatures], "JSON Simple Sign
   1.0" [JSS], "Canvas Applications" [CanvasApp], "JSON Simple
   Encryption" [JSE] 및 "JavaScript Message Security Format" [JSMS]에서

   "Authenticated Encryption with AES-CBC and HMAC-SHA"

   John Foley가 작성한 [AEAD-CBC-SHA]의 테스트 사례를 기반으로 합니다.

   기반이 된 "Using JavaScript Object Notation (JSON) Web
   Encryption (JWE) for Protecting JSON Web Key (JWK) Objects"
   [JWE-JWK]을 작성했습니다.
