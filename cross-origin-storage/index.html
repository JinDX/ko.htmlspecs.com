초록

교차 출처 저장소(Cross-Origin Storage, COS)는 웹 애플리케이션이 AI 모델, WebAssembly 모듈, 널리 사용되는 JavaScript 라이브러리 등의 대용량 파일을 서로 다른 출처 간에 저장하고 검색할 수 있도록 하는 콘텐츠 주소 지정 가능 캐시이다. 파일은 URL이 아니라 암호학적 해시로 식별되므로, 한 출처에서 한 번 가져온 바이트 단위로 동일한 리소스를 사용자 에이전트가 허용하는 다른 모든 출처에서 두 번째 다운로드 없이 재사용할 수 있다. 캐시의 존재 여부를 사용자가 방문한 사이트를 추론하는 데 이용하지 못하도록, 파일의 교차 출처 공개는 k-익명성 방식의 인기도 기준을 충족하는 해시로 제한된다.

1. 소개

이 절은 비규범적입니다.

저장소는 일반적으로 사용자의 보안과 개인정보를 보호하기 위해 출처별로 분할됩니다. 이는 올바른 기본값이지만, 매우 크고 널리 사용되며 공개적으로 배포되는 일부 리소스 — AI 모델, WebAssembly 모듈, JavaScript 라이브러리, 게임 엔진, 대형 웹 글꼴 — 에는 적합하지 않습니다. 이러한 리소스는 어떤 사이트에서 요청하더라도 바이트 단위로 완전히 동일한 파일입니다. 서로 관련이 없는 두 출처가 각각 동일한 8 GB 모델에 의존하는 경우, 출처별로 분할된 저장소는 사용자가 해당 모델을 두 번 다운로드하고 보관하도록 강제하므로 사용자의 대역폭, 저장 공간, 배터리뿐만 아니라 네트워크 전체에도 낭비가 됩니다.

Cross-Origin Storage(COS)는 URL이 아니라 암호학적 해시를 키로 사용하는 콘텐츠 주소 지정 가능 캐시로, 사용자 에이전트가 이러한 리소스의 저장된 단일 사본을 사용에 동의한 여러 출처 간에 공유할 수 있게 합니다. COS에 리소스를 저장하는 것은 항상 저장 출처가 명시적으로 동의하여 수행하는 작업이며, 사용자 에이전트는 원래 해당 리소스를 읽을 수 있도록 허용되는 출처에 대해서도 리소스의 존재 확인을 제공하지 않을 수 있습니다. § 8 개인정보 보호 및 보안 고려사항을 참조하십시오.

이 명세의 진입점은 requestFileHandle() 메서드이며, crossOriginStorage를 통해 노출됩니다. 

const hash = {
  algorithm: 'SHA-256',
  value: '8f434346648f6b96df89dda901c5176b10a6d83961dd3c1ac88b59b2dc327aa4',
};
try {
  const handle = await navigator.crossOriginStorage.requestFileHandle(hash);
  const file = await handle.getFile();
  // 파일로 무언가를 수행합니다.
} catch (err) {
  if (err.name === 'NotFoundError') {
    // Cross-Origin Storage에 (공개 가능한 상태로) 존재하지 않으므로, 대신 네트워크에서 가져옵니다.
  }
}

이 명세는 File System Standard [FS]의 FileSystemFileHandle, FileSystemWritableFileStream 및 관련 기반 구조를 재사용하되, 단일 출처의 비공개 또는 사용자가 볼 수 있는 파일 시스템이 아니라 전용 교차 출처 공유 파일 시스템을 대상으로 합니다.

이 명세는 명령형 JavaScript API만 정의합니다. 관련 제안에서는 동일한 기반 캐시를 다른 호스트 명세에 통합합니다 — link 및 script의 HTML crossoriginstorage 속성, crossOriginStorage JavaScript import 속성, CSS cross-origin-storage() <request-url-modifier>, 그리고 fetch()의 crossOriginStorage RequestInit 옵션이며, 각각 자체 호스트 명세에서 정의됩니다. § 9 다른 명세와의 통합을 참조하십시오.

2. 개념

2.1. 해시

COS 해시는 다음 항목을 가진 구조체입니다.

algorithm

[WEBCRYPTO]에서 인식하는 해시 알고리즘의 이름을 나타내는 문자열입니다. 예를 들어 "SHA-256"입니다.

value

algorithm이 생성한 다이제스트를 소문자 16진수로 인코딩한 문자열입니다. "SHA-256"의 경우 길이는 64자입니다.

algorithm dictionary 멤버는 일반 DOMString으로 형식이 지정되며, HashAlgorithmIdentifier로 지정되지 않습니다. 그 값의 범위가 정확히 [WEBCRYPTO]의 해시 알고리즘에서 허용되는 이름 집합과 같더라도 마찬가지입니다. HashAlgorithmIdentifier는 (object or DOMString)입니다 — 추가로 object도 허용하며, 이는 [WEBCRYPTO]에 의해 Algorithm 형태의 dictionary로 정규화되므로, 호출자는 이를 필요로 하는 알고리즘에 추가 매개변수를 전달할 수 있습니다 (예: {name: "HMAC", hash: "SHA-256"}). 해시 알고리즘은 이러한 매개변수를 받지 않으며, algorithm은 단일 작업에서 한 번 소비되는 것이 아니라 콘텐츠 주소 지정 가능 키의 일부로 저장되고, 비교되며, 왕복 변환되고, 이 명세의 모든 예에서는 단순 문자열을 사용합니다. 여기서 임의 객체를 허용해도 기능은 추가되지 않으면서 동등성과 직렬화를 불필요하게 복잡하게 만들 뿐입니다. 따라서 DOMString이 이 필드에 더 좁고 더 올바른 형식입니다.

두 COS 해시 값은 각 algorithm 값이 ASCII 대소문자 구분 없는 일치이고 각 value 값이 정확히 같은 경우 동일합니다.

참고: 대소문자가 규범적으로 제한되지 않는 algorithm과 달리, value는 이미 규범적으로 소문자여야 하므로(위 참조), 이를 비교할 때는 ASCII 대소문자 구분 없는 비교가 아니라 일반 문자열 비교를 사용합니다.

콘텐츠 주소 지정 가능 저장소는 그 항목을 URL이나 이름이 아니라 COS 해시의 동등성으로 키 지정하는 저장소입니다. 즉, 바이트가 동일하고 동일한 해시 알고리즘을 사용하는 두 파일은 몇 개의 출처에서 저장했는지 또는 몇 개의 URL에서 가져왔는지와 관계없이 동일한 항목입니다.

2.2. COS 항목

각 사용자 에이전트에는 하나의 COS 레지스트리가 있으며, 이는 COS 해시 값에서 COS 항목 구조체로의 맵이며, Cross-Origin Storage를 사용하는 모든 출처에서 공유됩니다. COS 항목에는 다음 항목이 있습니다.

hash

COS 해시입니다.

bytes

Null이거나, hash의 algorithm으로 계산한 다이제스트가 hash의 value와 같은 바이트 시퀀스입니다. 작성자가 검증 및 저장을 완료할 때까지는 Null입니다.

state

"pending" 또는 "written"입니다. 항목은 "pending"으로 시작하며, bytes가 처음 설정될 때 정확히 한 번 "written"이 됩니다.

보류 중인 작성자 수

초깃값이 0인 음이 아닌 정수로, 아직 완료되지 않은 작성자 — 즉 생성 요청 완료에서 반환된 FileSystemFileHandle 핸들 중 그 종료 쓰기가 아직 완료되지 않은 것 — 의 수를 셉니다. 검증 및 저장에서 실패한 쓰기를 안전하게 정리할 수 있는지를 결정하는 데만 사용됩니다. § 3.3 파일 생성 및 쓰기를 참조하십시오.

origins

출처의 목록으로, 공개 해시 목록과 독립적으로 명시적 교차 출처 읽기 액세스가 부여된 출처를 포함합니다. 처음에는 비어 있습니다. 오직 증가할 뿐이며 절대 줄어들지 않습니다. 이는 항목을 읽을 수 있는 대상을 결정하는 세 가지 독립적이고 가산적인 권한 부여 중 하나이며, 나머지 두 가지는 해당 항목의 저장 출처(해당 출처와 동일 사이트인 출처와 함께 항상 읽을 수 있음)와 전역적으로 공개 가능 여부입니다.

전역적으로 공개 가능

초깃값이 false인 불리언으로, 항목이 전역 ("*") 가용성을 요청하여 작성되었는지를 기록합니다. true이면 해당 항목은 요청이 § 8.3 가용성 게이팅을 통과한 모든 출처에서 읽을 수 있습니다 — 즉, 해당 출처의 hash가 PHL에 있고 GREASE 적용으로 억제되지 않는 경우입니다. 오직 설정될 뿐이며 절대 해제되지 않습니다.

참고: 이는 origins 내부의 센티널 값이 아니라 별도의 항목이므로, 이후 전역 가용성 요청은 기존의 명시적 origins 목록을 대체하는 대신 그 위에 "*" 권한을 추가합니다. 둘을 하나의 필드로 합친다면, 바이트를 제공한 작성자가 목록 범위의 항목을 "*" 범위의 항목으로 바꿀 수 있고 — § 8.3 가용성 게이팅은 "*" 권한에는 적용되지만 명시적 origins 목록에는 적용되지 않으므로 — 이전에는 목록을 통해 항목을 읽을 수 있던 출처가 hash가 PHL에 없을 때마다 "NotFoundError"를 받기 시작하게 됩니다. 권한을 서로 독립적으로 유지하면 모든 가시성 변경이 엄격하게 가산적으로 이루어지며, 이는 업그레이드할 수 있지만 절대 다운그레이드할 수 없음이라는 요구사항과 일치합니다.

저장 출처

각각 이 항목의 바이트 쓰기를 적어도 한 번 성공적으로 완료한 출처의 집합입니다. 페이지를 다시 불러와도 유지되며 시간이 지나면서 증가합니다. § 5.2 축출에 설명된 경우를 제외하고는 절대 줄어들지 않습니다. 저장 출처에 포함된 출처는 origins 또는 항목의 hash가 공개 해시 목록 (PHL)에 있는지와 관계없이 항상 requestFileHandle()을 통해 항목에 대한 핸들을 얻을 수 있습니다. § 3.4.1 원래 저장자의 액세스를 참조하십시오.

사용자 에이전트에는 연관된 Cross-Origin Storage 큐가 있으며, 이는 새 병렬 큐를 시작한 결과입니다. COS 레지스트리에 대한 모든 작업은 이 큐에 대기열에 추가되어야 하며, 그러면 해당 작업은 대기열에 추가된 순서대로 실행되고 서로 끼어들지 않습니다.

2.3. 공개 해시 목록

Cross-Origin Storage에 특정 해시가 존재하는지 확인하는 행위 자체가 사용자의 탐색 기록에 관한 정보를 유출할 수 있습니다(§ 8.2 교차 사이트 프로빙 참조). 이는 특히 전역 권한에 대한 위험입니다 — 항목의 명시적 origins 목록과 모든 항목이 가지는 동일 사이트 기본 권한은 이미 저장 출처의 명시적 선택에 의해 공개 범위가 제한되어 있지만, 항목을 전역적으로 공개 가능하게 만들면 잠재적으로 웹상의 모든 출처에 노출됩니다. 이 특정 위험을 제한하기 위해, 전역적으로 공개 가능한 리소스는 해당 권한을 통해 그 저장 출처 밖의 출처에 공개되려면 해시가 추가적인 독립 게이트를 통과해야 합니다. 즉, 벤더 중립적이고 구현 정의인 COS 해시 값의 허용 목록인 공개 해시 목록 (PHL)에 속해야 합니다. 해시는 k-익명성 방식의 인기 기준 — 예를 들어 바이트가 동일한 상태로 일정 최소 수의 독립된 출처에 나타나는 것 — 을 충족한 경우에만 공개 해시 목록에 추가되므로, 공유 캐시에 해당 해시가 존재하는지 확인하더라도 특정 개별 사용자에 관한 정보를 제공하지 않습니다.

COS 해시 hash는 hash가 사용자 에이전트의 현재 공개 해시 목록 스냅샷의 항목과 동일하면 공개 해시 목록에 있음 상태입니다.

공개 해시 목록의 검색 프로토콜, 업데이트 주기, 데이터 형식, 인기 임계값 및 거버넌스는 이 명세의 부속 산출물로 자세히 설계되며, [URL] Standard의 공개 접미사 목록이 규범적 문구가 아니라 부속 데이터 파일인 방식과 유사합니다 — 이 저장소의 공개 해시 목록 설명 문서를 참조하십시오. 해당 설계는 공개 접미사 목록의 여러 벤더 간 롤링 릴리스 선례를 모델로 WHATWG의 거버넌스를 제안하며, 독립적으로 검증된 보편성을 기준으로 하는 추가 기준 — 위에서 설명한 k-익명성 방식의 기준을 구체화한 것으로, 해시를 추가하는 과정의 일부로 오프라인에서 한 번 적용되며 사용자 에이전트가 각 쿼리마다 반복하는 검사가 아님 — 을 제안합니다. 이 내용 중 어느 것도 아직 이 제안 밖에서는 확립되지 않았습니다. 목록 자체의 초기 비규범적 코드 프로토타입은 이 저장소의 public-hash-list/implementation/에 유지되고 있습니다 — 이는 실용적인 임시 위치이며, 전용 다중 벤더 저장소가 PHL 설명 문서에서 설명하는 최종 거버넌스 목표로 남아 있습니다. 이 명세는 특정 검색 메커니즘이나 거버넌스 모델이 아니라 해시가 PHL에 있는지 여부에만 의존하므로, 해당 설계가 어떻게 발전하더라도 올바르게 유지됩니다.

3. CrossOriginStorageManager 인터페이스

[Exposed=(Window,Worker), SecureContext]
interface CrossOriginStorageManager {
  Promise<FileSystemFileHandle> requestFileHandle(
      CrossOriginStorageRequestFileHandleHash hash,
      optional CrossOriginStorageRequestFileHandleOptions options = {});
};

dictionary CrossOriginStorageRequestFileHandleHash {
  required DOMString value;
  required DOMString algorithm;
};

dictionary CrossOriginStorageRequestFileHandleOptions {
  boolean create = false;
  (DOMString or sequence<DOMString>) origins;
};

interface mixin NavigatorCrossOriginStorage {
  [SameObject, SecureContext] readonly attribute CrossOriginStorageManager crossOriginStorage;
};
Navigator includes NavigatorCrossOriginStorage;
WorkerNavigator includes NavigatorCrossOriginStorage;

각 Navigator 및 WorkerNavigator 객체에는 연관된 CrossOriginStorageManager 객체가 있습니다. crossOriginStorage getter 단계는 this에 연관된 CrossOriginStorageManager를 반환하는 것입니다.

각 CrossOriginStorageManager 객체에는 연관된 출처가 있으며, 객체가 생성될 때 this의 관련 설정 객체의 출처로 설정됩니다.

참고: 스크립트 자체에 관한 어떤 정보가 아니라 관련 설정 객체에서 출처를 가져오는 것은 워커에 대해 명확히 설명할 가치가 있는 결과를 가져옵니다. blob: URL에서 생성된 워커는 이를 생성한 컨텍스트의 출처를 가지므로, 해당 출처의 Cross-Origin Storage 뷰를 정확히 공유합니다. 즉, 이러한 워커가 작성한 것은 이를 생성한 페이지가 다시 읽을 수 있고, 페이지가 저장한 것은 워커가 읽을 수 있습니다. blob: URL은 자체적인 출처가 아니며, 이를 취소해도 워커가 해당 뷰에서 분리되지 않습니다. 반면 data: URL에서 생성된 워커는 불투명 출처를 가집니다. 이 명세는 현재 호출하는 출처가 불투명한 경우 requestFileHandle()이 무엇을 하는지 정의하지 않습니다. 불투명 출처에 관한 COS 요청 검증 규칙은 호출자가 지정하는 출처를 규율하는 것이지, 호출자가 요청을 보내는 출처를 규율하는 것이 아닙니다. 불투명 출처에는 저장 출처나 동일 사이트 비교의 키로 사용할 안정적인 식별자가 없으므로, 여기에 의미 있게 부여할 수 있는 것이 없습니다.

3.1. requestFileHandle() 메서드

handle = await navigator . crossOriginStorage . requestFileHandle(hash)

hash로 식별되는 파일이 Cross-Origin Storage에 존재하며 호출 출처에 공개할 수 있는 경우 해당 파일의 핸들을 반환합니다. 그렇지 않으면 "NotFoundError" DOMException으로 거부됩니다. "NotFoundError"는 파일이 Cross-Origin Storage에 물리적으로 존재하지 않는다는 것을 증명하지 않습니다. § 8.3 가용성 게이팅을 참조하십시오. 호출자는 이를 "대신 네트워크에서 가져오십시오."로 취급할 수 있습니다.

handle = await navigator . crossOriginStorage . requestFileHandle(hash, { create: true })

hash로 식별되는 파일을 Cross-Origin Storage에 쓰는 데 사용할 수 있는 핸들을 반환하며, 아직 항목이 존재하지 않으면 새 항목을 생성하고, 기본적으로 동일 사이트 출처로 제한합니다. 호출자는 항목이 이미 존재했는지 여부와 관계없이 핸들의 createWritable() 메서드를 통해 완전한 파일 내용을 작성해야 합니다. 사용자 에이전트는 그 시점에 작성된 바이트의 해시가 hash와 일치하는지 검증하며, 그렇지 않으면 "DataError" DOMException으로 거부합니다. 이 요구사항은 출처가 생성 요청을 사용하여 hash가 이미 존재했는지를 알아내는 오라클로 사용하는 것을 방지합니다.

handle = await navigator . crossOriginStorage . requestFileHandle(hash, { create: true, origins: "*" })

위와 같으며, 추가로 작성이 완료되면 hash에 대한 요청이 § 8.3 가용성 게이팅을 통과하는 모든 출처에 항목을 공개할 수 있게 합니다.

handle = await navigator . crossOriginStorage . requestFileHandle(hash, { create: true, origins: ["https://a.example", "https://b.example"] })

위와 같으며, 공개를 정확히 나열된 출처로 제한합니다(호출 출처 및 이미 저장 출처에 있는 모든 출처에 추가하여).

requestFileHandle(hash, options) 메서드의 단계는 다음과 같습니다.

  1. result를 새 promise로 둡니다.

  2. realm을 this의 관련 Realm으로 둡니다.

  3. global을 this의 관련 전역 객체로 둡니다.

  4. origin을 this에 연관된 출처로 둡니다.

  5. global이 주어졌을 때 Cross-Origin Storage 권한 확인을 실행한 결과가 false이면 다음을 수행합니다.

    1. global이 주어졌을 때 DOM 조작 작업 소스에서 전역 작업을 대기열에 추가하여 result를 "NotAllowedError" DOMException으로 거부합니다.

    2. result를 반환합니다.

  6. validationFailure를 hash와 options이 주어졌을 때 COS 요청 검증을 실행한 결과로 둡니다.

  7. validationFailure가 null이 아니면 다음을 수행합니다.

    1. global이 주어졌을 때 DOM 조작 작업 소스에서 전역 작업을 대기열에 추가하여 result를 validationFailure로 거부합니다.

    2. result를 반환합니다.

  8. 다음 단계를 Cross-Origin Storage 큐에 대기열에 추가합니다.

    1. options["create"]가 true이면 다음을 수행합니다.

      1. result, hash, options, global, 그리고 realm이 주어졌을 때 생성 요청 완료를 실행합니다.

    2. 그렇지 않으면 다음을 수행합니다.

      1. result, hash, origin, global, 그리고 realm이 주어졌을 때 읽기 요청 완료를 실행합니다.

  9. result를 반환합니다.

CrossOriginStorageRequestFileHandleHash hash 및 CrossOriginStorageRequestFileHandleOptions options이 주어졌을 때 COS 요청을 검증하려면, null 또는 TypeError를 반환합니다.

  1. hash["algorithm"]이 [WEBCRYPTO]에서 인식하는 해시 알고리즘 이름이 아니면 새 TypeError를 반환합니다.

  2. hash["value"]가 hash["algorithm"]이 "SHA-256"과 ASCII 대소문자를 구분하지 않고 일치할 때 정규 표현식 /^[0-9a-f]{64}$/과 일치하지 않으면 새 TypeError를 반환합니다.

    참고: 향후 해시 알고리즘은 다른 예상 다이제스트 길이를 정의할 수 있습니다. 이 명세는 예제 전반의 사용과 일치하도록 "SHA-256"만 규범적으로 제한합니다.

  3. options["origins"]가 존재하고 "*"가 아니면 다음을 수행합니다.

    1. candidates를 options["origins"]로 두며, 단일 문자열은 하나의 항목을 가진 목록으로 취급합니다.

    2. candidates의 크기가 사용자 에이전트의 최대 출처 목록 길이보다 크면 새 TypeError를 반환합니다.

    3. candidates의 각 candidate에 대해 다음을 수행합니다.

      1. candidate에 대해 기본 URL 파서를 실행한 결과가 실패이거나, 파싱된 URL의 출처가 불투명 출처이면 새 TypeError를 반환합니다.

  4. null을 반환합니다.

3.2. 파일 읽기

promise result, COS 해시 hash, 출처 origin, 전역 객체 global, 그리고 Realm realm이 주어졌을 때 읽기 요청을 완료하려면 다음을 수행합니다.

  1. entry를 COS 레지스트리에서 hash가 hash와 동일한 COS 항목이 있으면 해당 항목으로, 그렇지 않으면 null로 둡니다.

  2. entry가 null이 아니고 entry의 state가 "pending"이면 다음을 수행합니다.

    1. global이 주어졌을 때 DOM 조작 작업 소스에서 전역 작업을 대기열에 추가하여 result를 "NotAllowedError" DOMException으로 거부합니다.

    2. 반환합니다.

    참고: 쓰기가 진행 중인 해시는 의도적으로 존재하지 않는 해시처럼 동작하지 않습니다. 이는 호출자가 진행 중인 쓰기를 진짜 캐시 미스로 잘못 판단하여, 오직 해당 파일을 쓰기 위한 목적으로 매우 큰 파일을 중복하여 동시에 다운로드하기 시작하지 않도록 하기 위한 것입니다. § 3.3 파일 생성 및 쓰기를 참조하십시오.

  3. disclosableEntry를 entry와 origin이 주어졌을 때 가용성 게이팅 적용을 실행한 결과로 둡니다.

  4. disclosableEntry가 null이면 다음을 수행합니다.

    1. global이 주어졌을 때 DOM 조작 작업 소스에서 전역 작업을 대기열에 추가하여 result를 "NotFoundError" DOMException으로 거부합니다.

    2. 반환합니다.

  5. handle을 realm에서 Cross-Origin Storage 파일 시스템 내의 disclosableEntry를 가리키는 locator를 가진 새 FileSystemFileHandle을 생성한 결과로 둡니다 [FS].

  6. handle의 COS 출처를 origin으로 설정합니다.

  7. handle의 읽기 가능을 true로 설정합니다.

    참고: 이 핸들은 이미 가용성 게이팅 적용을 통과했으므로 호출 출처는 해당 항목의 바이트를 받을 권한이 있습니다.

  8. global이 주어졌을 때 DOM 조작 작업 소스에서 전역 작업을 대기열에 추가하여 result를 handle로 이행합니다.

COS 항목 또는 null인 entry와 출처 origin이 주어졌을 때 COS 공개를 결정하려면 COS 항목 또는 null을 반환합니다.

  1. entry가 null이면 null을 반환합니다.

  2. 단언: entry의 state는 "written"입니다.

  3. origin이 entry의 저장 출처에 있으면 entry를 반환합니다.

    참고: 원래 저장자와 직접 해당 항목을 성공적으로 작성한 모든 출처는 언제든 이를 다시 읽을 수 있습니다. § 3.4.1 원래 저장자의 액세스를 참조하십시오.

  4. origin이 entry의 저장 출처 중 어떤 항목과 동일 사이트이면 entry를 반환합니다.

    참고: 모든 항목이 가지는 동일 사이트 기본값 — origins 옵션이 없는 쓰기가 요청하는 권한 — 은 이후에 추가된 origins 목록이나 전역적으로 공개 가능 권한과 관계없이 항상 유지됩니다. 아래의 공개 해시 목록 게이트보다 먼저 확인되므로, 동일 사이트 출처는 해당 항목의 hash가 PHL에 있는지 여부와 관계없이 항목을 읽습니다. 여기서 동일 사이트는 하나의 신뢰 단위이므로, § 8.2 교차 사이트 프로빙이 보호하는 사이트 경계를 넘어 어떤 정보도 공개하지 않습니다.

  5. origin의 직렬화가 entry의 origins의 항목이면 entry를 반환합니다.

    참고: 명시적 origins 목록에 있는 출처는 해당 항목이 PHL에 있을 필요 없이 항목을 읽습니다. 저장 출처는 해당 출처를 명시함으로써 제한된 공개 결정을 내렸으며 (§ 3.4 리소스 가시성 업그레이드 및 § 7 Cross-Origin-Storage-Allow-Origin 헤더 참조), 그 위에 별도의 전역적 보편성을 요구하면 일반적인 제한 공유가 흔히 독점 리소스인 것에 대한 관련 없는 공개 큐레이션에 의존하게 됩니다. 이를 전역적으로 공개 가능 게이트보다 먼저 확인하는 것은 이후의 전역 가용성 쓰기가 목록에 있는 출처의 액세스를 취소하지 않도록 합니다. § 8.2 교차 사이트 프로빙을 참조하십시오.

  6. entry의 전역적으로 공개 가능이 true이면 다음을 수행합니다.

    1. entry의 hash가 PHL에 있지 않으면 null을 반환합니다.

      참고: 공개 해시 목록 게이트는 전역 권한에만 적용됩니다 — 공개가 그렇지 않으면 웹의 모든 출처에 도달할 수 있는 유일한 경우입니다. 항목이 전역적으로 공개 가능하지만 그 hash가 PHL에 있지 않으면, 이 권한만으로 자격을 얻는 출처에는 공개되지 않습니다. 저장 출처, 그와 동일 사이트인 집합 또는 명시적 origins 목록에도 나타나는 출처는 이미 위에서 반환되었습니다.

    2. entry를 반환합니다.

  7. null을 반환합니다.

COS 항목 또는 null인 entry와 출처 origin이 주어졌을 때 가용성 게이팅을 적용하려면 COS 항목 또는 null을 반환합니다.

  1. disclosable을 entry와 origin이 주어졌을 때 COS 공개 결정을 실행한 결과로 둡니다.

  2. disclosable이 null이면 null을 반환합니다.

  3. origin이 disclosable의 저장 출처에 있으면 disclosable을 반환합니다.

  4. 사용자 에이전트가 이 요청에 GREASE 적용을 하기로 선택하면 null을 반환합니다.

  5. disclosable을 반환합니다.

3.3. 파일 생성 및 쓰기

생성 요청 완료에 의해 생성된 FileSystemFileHandle에는 연관된 요청된 출처가 있으며, 이는 핸들을 통해 성공적으로 쓰기가 완료되면 검증 및 저장이 항목의 origins를 업그레이드하려고 시도할 값입니다.

COS 항목을 가리키는 모든 FileSystemFileHandle에는 또한 이를 얻은 출처인 연관된 COS 출처와, 해당 특정 핸들을 통해 getFile()이 항목의 바이트를 공개할 수 있는지를 규율하는 연관된 읽기 가능 불리언이 있습니다. 이미 가용성 게이팅을 통과한 읽기 요청 완료에서 반환된 핸들의 경우 true이고, 동일한 핸들에 대해 검증 및 저장이 성공하기 전까지는 생성 요청 완료에서 반환된 핸들의 경우 false입니다.

참고: 이는 의도적으로 항목이 아니라 핸들의 속성입니다. 생성 요청은 항목이 이미 존재하며 이미 "written"인지 여부와 관계없이 핸들을 반환하므로(생성 요청 완료 참조), 항목별 규칙을 사용하면 어떤 출처든 requestFileHandle()을 create: true로 호출하여 자신이 한 번도 작성하지 않은 항목을 즉시 읽고, origins, PHL 구성원 여부 또는 GREASE 적용을 충족하지 않고도 그 내용을 알아낼 수 있게 됩니다. 이 명세의 모든 공개 제어는 읽기 경로에 적용되므로, 항목별 게이팅은 생성 요청이 그 모든 제어를 우회할 수 있게 합니다. 호출자에게 먼저 올바른 바이트를 제공하도록 요구하면 생성으로 얻은 핸들을 통한 성공적인 읽기는 호출자가 이미 가지고 있지 않은 어떤 정보도 공개하지 않습니다.

promise result, COS 해시 hash, CrossOriginStorageRequestFileHandleOptions options, 전역 객체 global, 그리고 Realm realm이 주어졌을 때 생성 요청을 완료하려면 다음을 수행합니다.

  1. requestedOrigins를 options["origins"]이 주어졌을 때 요청된 출처 정규화를 실행한 결과로 둡니다.

  2. requestedOrigins가 목록이면 다음을 수행합니다.

    1. ceiling을 global이 주어졌을 때 COS 범위 상한 얻기를 실행한 결과로 둡니다.

    2. ceiling이 포함하지 않는 각 출처를 requestedOrigins에서 제거합니다.

      참고: 이는 COS 범위 상한과의 교집합으로, § 7 Cross-Origin-Storage-Allow-Origin 헤더에서 설명합니다. 공개하는 출처의 Cross-Origin-Storage-Allow-Origin 헤더가 승인하지 않은 수신자는 쓰기를 실패시키는 대신 제거되며, 이는 리소스 가시성 업그레이드에서 길이 제한을 초과하는 업그레이드가 초과분을 제거하는 방식과 일치합니다. 사용자 에이전트는 제거된 각 출처를 명시하는 콘솔 경고를 기록할 것으로 예상됩니다.

    3. requestedOrigins가 비어 있으면 requestedOrigins를 null로 설정합니다.

      참고: 모든 구성원이 제거된 목록은 승인된 교차 출처 수신자가 없는 쓰기가 되므로, 엄격히 더 좁은 빈 목록(동일 사이트 읽기 사용자조차 제외함)이 아니라 동일 사이트 기본값으로 되돌아갑니다. 바이트는 여전히 저장되며, 승인되지 않은 공개만 보류됩니다.

  3. entry를 COS 레지스트리에서 hash가 hash와 동일한 COS 항목이 있으면 해당 항목으로, 그렇지 않으면 null로 둡니다.

  4. entry가 null이면 다음을 수행합니다.

    1. entry를 hash가 hash, bytes가 null, state가 "pending", origins가 빈 목록, 전역적으로 공개 가능이 false, 그리고 저장 출처가 빈 집합인 새 COS 항목으로 설정합니다.

    2. COS 레지스트리[hash]를 entry로 설정합니다.

    참고: 새 항목은 명시적인 origins 권한 없이 시작하며 전역적으로 공개 가능하지 않습니다. 바이트가 작성되고 검증되면 requestedOrigins가 아래에서 검증 및 저장에 의해 리소스 가시성 업그레이드를 통해 적용되며, 이는 기존 항목을 찾은 요청과 정확히 같습니다. 이 때문에 생성 요청은 가시성을 확장하기 전에 전체 바이트를 제공해야 합니다(§ 3.4 리소스 가시성 업그레이드 참조).

  5. entry의 보류 중인 작성자 수를 1 증가시킵니다.

    참고: 이는 호출자가 handle에서 createWritable()을 한 번도 호출하지 않거나, 그 결과 스트림을 한 번도 닫지 않더라도 handle을 미완료 작성자로 추적합니다. 이러한 버려진 핸들은 entry에 영구적으로 계산되며, 이는 이 메커니즘이 존재하기 전에도 버려진 진행 중 쓰기가 entry를 영구적으로 "pending" 상태에 두었던 것과 같습니다. 검증 및 저장을 참조하십시오.

  6. handle을 realm에서 Cross-Origin Storage 파일 시스템 내의 entry를 가리키는 locator를 가진 새 FileSystemFileHandle을 생성한 결과로 둡니다 [FS].

  7. handle의 COS 출처를 global의 관련 설정 객체의 출처로 설정합니다.

  8. handle의 요청된 출처를 requestedOrigins로 설정합니다.

  9. handle의 읽기 가능을 false로 설정합니다.

    참고: handle은 entry가 이미 존재했는지 여부 및 이미 "written"인지 여부와 관계없이 반환됩니다. 호출자는 여전히 handle을 통해 완전한 파일 바이트를 제공해야 하므로, 쓰기를 사용하여 이전 존재 여부를 감지할 수 없고(§ 8.2 교차 사이트 프로빙 참조), 더 허용적인 origins 값에 대한 요청도 승인되기 전에 검증될 수 있습니다. § 3.4 리소스 가시성 업그레이드를 참조하십시오.

  10. global이 주어졌을 때 DOM 조작 작업 소스에서 전역 작업을 대기열에 추가하여 result를 handle로 이행합니다.

(DOMString or sequence<DOMString>) 또는 undefined인 origins가 주어졌을 때 요청된 출처를 정규화하려면 "*", 목록 형태의 출처, 또는 null을 반환합니다.

  1. origins가 존재하지 않으면 null을 반환합니다.

  2. origins가 "*"이면 "*"를 반환합니다.

  3. list를 « »로 둡니다.

  4. origins의 각 candidate에 대해 다음을 수행합니다(단일 문자열은 하나의 항목을 가진 목록으로 취급합니다).

    1. candidateOrigin을 candidate에 기본 URL 파서를 실행한 결과인 출처로 둡니다.

      참고: COS 요청 검증은 이미 각 candidate가 불투명하지 않은 출처로 파싱됨을 확인했습니다.

    2. list에 candidateOrigin이 포함되어 있지 않으면, candidateOrigin을 list에 추가합니다.

  5. list를 반환합니다.

참고: 기존 항목에 나중에 병합할 때만 중복을 제거하는 대신 여기에서 중복을 제거하면, 항목이 처음 생성되는 순간부터 origins에 중복이 없게 되어 이후의 모든 복제본도 중복 없이 유지됩니다.

COS 항목을 가리키는 locator를 가진 핸들에서 createWritable()을 호출하여 얻은 FileSystemWritableFileStream이 닫히면 [FS], 사용자 에이전트는 해당 닫기 작업의 promise가 이행되기 전에 아래의 검증 및 저장 단계를 실행해야 합니다.

참고: 이는 닫기가 어떻게 트리거되었는지와 관계없이 적용됩니다 — 명시적인 close() 호출이든, 소스의 끝에 도달하여 기본적으로 대상도 닫는 pipeTo() 호출이든 마찬가지입니다. [STREAMS]는 스트림이 닫힌 상태가 되는 시점에 두 경우를 구분하지 않으며, 이 알고리즘도 마찬가지입니다.

닫힌 스트림의 핸들이 가리키는 COS 항목 entry, 완전히 작성된 바이트 시퀀스 bytes, 그리고 닫기 작업의 관련 설정 객체의 출처 origin이 주어졌을 때 검증 및 저장 단계는 다음과 같습니다.

  1. computedValue를 entry의 algorithm으로 명명된 알고리즘을 사용하여 [WEBCRYPTO]에 따라 계산한 bytes의 소문자 16진수 다이제스트로 둡니다.

  2. computedValue가 entry의 value와 정확히 같지 않으면 다음을 수행합니다.

    1. 닫기 작업의 promise를 "DataError" DOMException으로 거부합니다.

    2. 다음 단계를 Cross-Origin Storage 큐에 대기열에 추가합니다.

      1. entry의 보류 중인 작성자 수를 1 감소시킵니다.

      2. entry의 state가 "pending"이고 entry의 보류 중인 작성자 수가 0이면 entry의 hash를 COS 레지스트리에서 제거합니다.

        참고: 이 단계는 실패한 쓰기가 영구적으로 도달할 수 없는 "pending" 항목을 남기는 대신 스스로 정리하도록 합니다. 동일한 해시에 대한 이후의 requestFileHandle() 호출은 다른 작성자가 더 이상 미완료 상태가 아니면 항목을 전혀 보지 못하고 일반적인 "NotFoundError"를 받으며, 무기한 "NotAllowedError"를 받지 않습니다. 이 수는 동일한 해시에 대해 다른 작성자가 동시에 진행 중인 항목을 삭제하는 것을 방지합니다(예를 들어 두 탭이 모두 해시가 없음을 확인하고 독립적으로 쓰기를 시작한 경우). 그 작성자가 여전히 미완료 상태이거나 이미 성공했다면, 수가 아직 0에 도달하지 않았거나 entry의 state가 더 이상 "pending"이 아니므로 이 단계는 아무 작업도 하지 않습니다. 이미 "written"인 항목은 이후에 얼마나 많은 작성자가 이를 요청하고 실패하는지와 관계없이 이 방식으로 제거될 수 없습니다. 한 번도 성공적으로 작성되지 않은 항목만 대상이 됩니다.

    3. 이 단계를 중단합니다.

  3. 다음 단계를 Cross-Origin Storage 큐에 대기열에 추가합니다.

    1. entry의 bytes를 bytes로 설정합니다.

    2. entry의 state를 "written"으로 설정합니다.

    3. 아직 존재하지 않는 경우 origin을 entry의 저장 출처에 추가합니다.

    4. entry의 보류 중인 작성자 수를 1 감소시킵니다.

    5. entry와 핸들의 요청된 출처가 주어졌을 때 리소스 가시성 업그레이드를 실행합니다.

    6. 핸들의 읽기 가능을 true로 설정합니다.

      참고: 이 핸들만 읽을 수 있게 됩니다. 아직 쓰기가 수행되지 않은 다른 생성 요청에서 얻은 동일 항목의 다른 핸들은 계속 읽을 수 없습니다.

COS 항목을 가리키는 FileSystemFileHandle에서 호출된 createWritable()은 keepExistingData의 값과 관계없이, 그리고 가리키는 항목의 state와 관계없이 내용이 빈 상태로 시작하는 FileSystemWritableFileStream을 생성해야 합니다.

참고: [FS]는 그 외의 경우 keepExistingData를 기존 파일의 내용으로 스트림을 초기화하는 것으로 정의합니다. 여기서 이를 준수하면 호출자가 자신이 한 번도 보유하지 않은 바이트의 저장 출처가 될 수 있습니다. 생성 요청은 항목이 이미 존재하는지 여부와 관계없이 핸들을 반환하므로, 호출자는 다른 출처가 저장한 해시에 대한 writable을 열고 아무것도 작성하지 않은 채 닫은 다음 그대로 이어받은 바이트가 요청된 값으로 해시되도록 할 수 있습니다. 그렇게 되면 origins, 공개 해시 목록, 그리고 GREASE 적용을 전혀 확인하지 않고도 읽기 액세스가 부여됩니다 — 각각은 허용된 두 작업을 결합하여 만든 가용성 게이팅 우회입니다. 이는 검증 및 저장이 모든 생성 요청에서 완전한 내용을 요구하는 것과 같은 이유입니다.

참고: 따라서 아무런 쓰기 없이 닫힌 writable은 빈 바이트 시퀀스를 가지며, 호출자가 원하는 어떤 항목에서도 요청된 값으로 해시되지 않으므로 검증 및 저장은 다른 모든 불일치와 마찬가지로 "DataError" DOMException으로 거부합니다. 대신 해당 경우에 저장소 또는 I/O 실패를 보고하는 구현은 관련 없는 오류 뒤에 검증 결과를 숨기게 됩니다.

File System Standard [FS]는 아직 종속 명세가 FileSystemWritableFileStream의 닫기 단계에 추가적인 쓰기별 검증을 연결할 수 있는 확장 지점을 정의하지 않습니다. 그러한 훅이 존재하기 전까지 이 절에서는 필요한 동작을 직접 설명합니다. 향후 개정에서는 [FS]와 정식으로 통합될 것으로 예상됩니다.

3.4. 리소스 가시성 업그레이드

COS 항목의 가시성은 업그레이드할 수 있지만 절대 다운그레이드할 수 없습니다.

COS 항목 entry와 "*", 목록 형태의 출처, 또는 null인 requestedOrigins가 주어졌을 때 리소스 가시성을 업그레이드하려면 다음을 수행합니다.

  1. requestedOrigins가 null이면 반환합니다.

    참고: origins를 생략하면 동일 사이트 가용성만 요청하며, 모든 항목에는 이미 이것이 있으므로(COS 공개 결정 참조), 추가할 것이 없습니다.

  2. requestedOrigins가 "*"이면 다음을 수행합니다.

    1. entry의 전역적으로 공개 가능을 true로 설정합니다.

    2. 반환합니다.

    참고: 이는 전역 권한을 추가하는 것이며, entry의 origins에는 영향을 주지 않습니다. 이미 명시적인 origins 목록이 있던 항목은 이를 유지하므로, 해당 목록의 모든 출처는 항목이 전역적으로 공개 가능해진 이후에도 PHL과 무관한 액세스를 유지합니다. 이것이 두 권한을 별도로 저장하는 핵심적인 이유입니다. 전역적으로 공개 가능을 참조하십시오.

  3. requestedOrigins의 각 candidateOrigin에 대해 다음을 수행합니다.

    1. entry의 origins가 candidateOrigin을 포함하면 계속합니다.

    2. entry의 origins의 크기가 사용자 에이전트의 최대 출처 목록 길이와 같으면 중단합니다.

      참고: 나머지 candidateOrigin 값은 이 업그레이드를 실패시키는 대신 조용히 제외됩니다 — 쓰기 자체는 이미 성공했기 때문입니다 — 하지만 사용자 에이전트는 항목의 origins 목록이 한도에 도달했다는 콘솔 경고를 기록할 것으로 예상됩니다.

    3. candidateOrigin을 entry의 origins에 추가합니다.

참고: 업그레이드는 origins에 추가하거나 전역적으로 공개 가능을 true로 설정하기만 하며, 어느 권한도 제거되거나 축소되지 않습니다. 목록을 요청한 작성자는 아직 전역적으로 공개 가능하지 않은 항목을 확장하는 것과 마찬가지로 이미 전역적으로 공개 가능한 항목도 확장합니다 — 새로 나열된 출처는 "*" 권한이 계속 유효한 동안에도 PHL과 무관한 액세스를 얻습니다 — 두 권한은 순서 관계가 아니라 서로 독립적이기 때문입니다.

참고: 원래 저장자뿐 아니라 새로운 사이트도, 항목의 origins를 확장할 수 있습니다. 단, 해당 항목의 hash로 해시되는 바이트도 함께 제공해야 합니다. 이는 의도된 동작입니다. 해시에 맞는 올바른 바이트를 이미 보유한 모든 사이트는 구조상 해당 해시가 무엇을 나타내는지에 관해 원래 저장자와 동일한 권위를 갖습니다.

3.4.1. 원래 저장자의 액세스

COS 항목의 쓰기를 성공적으로 완료한 출처 — 즉, 해당 항목의 저장 출처에 있는 모든 출처 — 는 이후 언제든 requestFileHandle()을 통해 해당 항목의 핸들을 얻을 수 있으며, 항목의 origins 값이나 그 hash가 PHL에 있는지 여부와 무관합니다. 이는 출처가 자신이 저장한 것에 항상 액세스할 수 있는 Cache API의 모델을 따릅니다.

4. Cross-Origin Storage 파일 시스템

Cross-Origin Storage 파일 시스템은 파일 시스템 루트이며, 어떤 출처의 버킷 파일 시스템이나 로컬 파일 시스템 액세스 루트와도 구별되고, 그 항목은 COS 레지스트리의 COS 항목과 일대일로 대응합니다.

Cross-Origin Storage 파일 시스템은 [FS]의 일반적인 호출별 권한 확인 모델을 사용하지 않습니다. 여기에서 얻은 모든 FileSystemFileHandle은 스크립트에 반환되기 전에 이미 § 3.2 파일 읽기 또는 § 3.3 파일 생성 및 쓰기에 의해 완전히 승인되었으므로, 이러한 핸들에서 getFile() 또는 createWritable()을 호출해도 추가 권한 프롬프트가 발생하지 않습니다.

따라서 이러한 핸들의 queryPermission() 및 requestPermission()은 프롬프트가 나타날 수 없으므로 절대로 "prompt"를 보고해서는 안 됩니다. 생성 요청으로 얻지 않은 핸들에서 쓰기 모드에 대해서는 "denied"를, 그 외에는 "granted"를 보고해야 합니다.

참고: 쓰기는 핸들이 실제로 보유하지 않을 수 있는 유일한 기능입니다. 생성 요청만 쓰기가 가능한 핸들을 생성하므로, 다른 핸들의 쓰기 모드에 "granted"를 보고하면 createWritable()이 거부할 기능을 가지고 있다고 주장하게 됩니다. 읽기는 "granted"로 유지됩니다. 읽을 수 있는 핸들을 가진 호출자는 이를 통해 읽을 수 있기 때문입니다. 요청해도 어느 결과도 바꿀 수 없습니다. 표시할 프롬프트도 없고 권한 부여를 기록할 상태도 없기 때문입니다.

읽기 가능이 false인 COS 항목을 가리키는 FileSystemFileHandle에서 getFile()을 호출하면 "NotAllowedError" DOMException으로 거부해야 합니다. 이는 서로 다른 두 경우를 다룹니다.

  • 항목이 아직 "pending"인 생성 요청의 핸들입니다. 동일한 해시에 대한 동시 requestFileHandle() 호출이 거부되는 것과 같은 이유입니다(§ 3.2 파일 읽기 참조). 호출자는 아직 검증되지 않은 자리 표시자를 파일의 실제 내용인 것처럼 관찰할 수 없어야 합니다.

  • 다른 출처가 이미 작성한 항목에 대한 생성 요청의 핸들입니다. 해당 항목의 state는 "written"이지만, 이 호출자는 바이트를 제공하지 않았으며 가용성 게이팅도 통과하지 않았으므로, 해당 항목에 관해 아무것도 알아서는 안 됩니다 — 존재 여부도 포함됩니다.

핸들의 읽기 가능이 true가 되면, 그 핸들에서 호출된 getFile()은 그 내용이 가리키는 항목의 bytes인 File을 반환합니다. 이는 [FS]가 해당 바이트를 바이너리 데이터로 가지는 파일 항목에 대해 이미 정의하는 동작과 정확히 같습니다.

COS 항목을 가리키는 FileSystemFileHandle에는 단일 문자열, 즉 항목의 COS 해시의 value를 포함하는 목록을 경로로 가지며, 루트가 Cross-Origin Storage 파일 시스템인 파일 시스템 locator가 있습니다.

참고: [FS]는 name을 핸들의 locator 경로의 마지막 경로 구성요소로 정의하므로, 이는 name을 임의로 선택하도록 두지 않고 확정합니다. 즉, 해시입니다. 항목에는 자체 이름이 없고 해시만이 유일한 식별자이므로, 이를 보고하면 빈 문자열이 버릴 정보를 보존할 수 있습니다.

항목에는 이름도 포함 디렉터리도 없으므로, [FS]의 구조적 표면 대부분에는 작용할 대상이 없습니다. 예외는 식별성이며, 이는 콘텐츠 주소 지정 항목이 언제나 답할 수 있는 유일한 질문입니다. COS 레지스트리는 각 COS 해시마다 최대 하나의 COS 항목을 보유하므로, 두 핸들은 그 해시가 같은 경우에만 정확히 동일한 항목을 가리킵니다.

COS 항목을 가리키는 FileSystemFileHandle에서, 마찬가지로 COS 항목을 가리키며 동일한 출처가 얻은 인수를 사용해 isSameEntry()을 호출한 경우, 두 핸들의 COS 해시 항목이 같으면 true를, 그렇지 않으면 false를 반환해야 합니다.

참고: 이를 거부하면 사용자 에이전트가 이미 보유한 정보를 버리게 됩니다.

호출하는 출처가 얻지 않은 인수나, Cross-Origin Storage 파일 시스템이 아닌 파일 시스템을 가리키는 인수로 isSameEntry()을 호출하면 거부해야 합니다.

참고: 이 경우 false를 반환하면 두 핸들이 서로 다른 항목을 가리킨다고 단언하게 되며, 이는 호출 출처가 검사할 권한이 없는 핸들에 관한 주장입니다. 거부하는 것은 단지 비교할 수 없었다는 것만 나타냅니다.

COS 항목을 가리키는 FileSystemFileHandle에서 호출된 move() 및 remove()은 "NotAllowedError" DOMException으로 거부해야 하며, 항목을 변경하지 않아야 합니다.

참고: 항목은 그 저장 출처의 모든 출처가 공유하므로, 제거를 허용하면 한 사이트가 다른 사이트가 의존하는 데이터를 파괴할 수 있습니다. 삭제는 축출과 사용자의 자체 저장소 제어에 속합니다. 항목은 COS 해시로 이름이 정해지고 포함 디렉터리가 없으므로, 이름 변경이나 부모 변경에는 작용할 대상이 없습니다.

참고: 작성 시점에는 두 메서드 모두 [FS]나 File System Access API에 정의되어 있지 않으므로 (WICG/file-system-access#214), 오류 이름은 [FS]가 항목 삭제를 위해 정의하는 작업인 removeEntry()을 따릅니다. 즉, 읽기-쓰기 액세스가 허용되지 않은 경우 액세스 결과의 오류 이름으로 거부합니다. 여기서는 존재하지 않음이 아니라 거부됨으로 해석하는 것이 정확합니다 — 작업 자체는 의미가 있으며 거부되는 것입니다.

createSyncAccessHandle()에는 여기서 별도 규칙이 필요하지 않습니다. 그 단계는 핸들이 버킷 파일 시스템에 있지 않을 때마다 "InvalidStateError" DOMException으로 거부하며, Cross-Origin Storage 파일 시스템은 어떤 출처의 파일 시스템과도 구별되는 파일 시스템 루트이므로, [FS]가 이미 거부 여부와 오류 이름을 모두 결정합니다.

참고: 이는 이 명세가 독립적으로 보더라도 원하는 결과입니다. FileSystemSyncAccessHandle은 호출자에게 쓰기 가능한 파일 디스크립터를 제공하며, 그러면 호출자는 항목의 bytes를 해당 바이트가 저장된 기준인 COS 해시와 일치하지 않게 변경할 수 있고, 해당 항목을 공개할 수 있는 다른 모든 출처도 같은 바이트를 읽게 됩니다.

4.1. 핸들 전송

FileSystemFileHandle은 직렬화 가능한 객체이므로 [FS], COS 항목을 가리키는 핸들은 다른 환경 설정 객체에 전달할 수 있습니다. 예를 들어 postMessage(message, options)을 사용할 수 있습니다. 이는 requestFileHandle()과 더불어 이러한 핸들을 얻는 두 번째 방법이므로, 여기에서도 제약을 둡니다.

직렬화 단계에서, COS 항목을 가리키는 FileSystemFileHandle에 value와 serialized가 주어지면 다음을 추가로 수행합니다.

  1. serialized.[[COSOrigin]]을 value의 COS 출처로 설정합니다.

  2. serialized.[[COSMayRead]]를 value의 읽기 가능으로 설정합니다.

역직렬화 단계에서 serialized, value 및 realm이 주어지면 다음을 추가로 수행합니다.

  1. serialized.[[COSOrigin]]이 realm의 환경 설정 객체의 출처와 동일 출처가 아니면 "DataCloneError" DOMException을 던집니다.

  2. value의 COS 출처를 serialized.[[COSOrigin]]으로 설정합니다.

  3. value의 읽기 가능을 serialized.[[COSMayRead]]로 설정합니다.

참고: 동일 출처 검사가 없다면, 전송은 이 명세의 모든 공개 제어를 한 번에 무력화합니다. 읽기 가능이 true인 핸들은 이미 이를 요청한 출처에 대해 가용성 게이팅 적용을 통과했습니다. 이를 다른 출처에 게시하면 해당 출처에 대해 origins, PHL 구성원 여부 또는 GREASE 적용을 한 번도 평가하지 않고 해당 항목의 바이트를 넘겨주게 됩니다. 이는 File System Standard의 기존 핸들 처리 방식과 일치하며, 핸들도 마찬가지로 동일 출처 수신자에게만 유용합니다.

참고: 읽기 가능은 다시 계산되는 대신 핸들과 함께 전달되므로, 아직 쓰기가 수행되지 않은 생성 요청 핸들은 전송 후에도 읽을 수 없는 상태로 유지되고, 읽기 요청 핸들은 다시 게이팅되지 않고도 읽을 수 있는 상태를 유지합니다. 도착 시 다시 게이팅하는 것은 더 나쁜 결과를 낳습니다. 호출자가 같은 핸들을 전송하여 가용성을 반복해서 탐지할 수 있게 되기 때문입니다.

5. 저장소 관리

5.1. 저장소 제한

사용자 에이전트는 단일 출처가 다른 출처의 항목을 축출하려는 목적으로 캐시를 가득 채우는 것을 방지하기 위해, 성공적인 쓰기를 통해 COS 레지스트리에 하나의 출처가 기여할 수 있는 총 바이트 수에 제한을 두어야 합니다. 구체적인 제한은 구현 정의입니다. 출처의 쓰기가 해당 제한을 초과하는 경우, 사용자 에이전트는 "QuotaExceededError" DOMException으로 쓰기를 거부해야 하며 콘솔에 경고를 기록하는 것이 좋습니다.

참고: 항목은 콘텐츠 주소 지정 가능하므로, 하나의 출처가 동일한 해시 아래 동일한 바이트를 반복해서 쓰더라도 최초의 성공적인 쓰기 이후 추가 할당량을 소비하지 않습니다. § 2.2 COS 항목을 참조하십시오.

사용자 에이전트에는 또한 구현 정의인 최대 출처 목록 길이가 있으며, 이는 하나의 origins 목록에 포함할 수 있는 출처 수의 상한을 정하는 양의 정수입니다. 이는 목록이 처음 제공될 때(COS 요청 검증 참조)와 나중에 기존 항목에 병합될 때(리소스 가시성 업그레이드 참조) 모두 적용되므로, 단일 호출이나 시간이 지나며 여러 호출이 누적된 효과 어느 쪽도 항목의 origins를 무제한으로 증가시킬 수 없습니다. 메모리 사용량에 상한을 두는 것 외에도, 이는 출처 목록이 "*"의 선언되지 않은 대체 수단으로 사용되는 것을 방지합니다. § 8.2 교차 사이트 프로빙을 참조하십시오.

이 제한을 초과하는 것은 두 위치에서 서로 다르게 처리됩니다. 두 호출은 작업의 매우 다른 시점에 발생하기 때문입니다.

  • COS 요청 검증에서는 파일이 가져와지거나 해시되거나 쓰이기 전에 제한을 확인합니다. 제한을 초과한 호출자는 즉시 "TypeError"를 받고 그 외에는 아무 일도 일어나지 않습니다 — 다른 잘못된 origins 값과 동일하게 처리됩니다.

  • 리소스 가시성 업그레이드에서는 서로 독립적인 여러 쓰기 호출에서 요청된 출처가 누적된 결과로만 제한에 도달할 수 있으며, 서로 관련 없는 출처들이 오랜 기간에 걸쳐 이를 발생시킬 수도 있습니다. 또한 이 호출의 바이트가 이미 해시되고 검증되어 영구적으로 저장된 이후에만 제한을 확인합니다. 그 시점에서 쓰기를 거부하면 관련 없는 관리상 제한 때문에 성공적으로 검증까지 끝난 — 그리고 잠재적으로 매우 큰 — 쓰기를 폐기하게 되며, 이를 어느 한 호출자의 실수로 돌릴 수도 없습니다. 따라서 쓰기는 그대로 성공하게 두고, 용량을 초과한 출처만 origins에서 제외하며 콘솔 경고를 표시합니다. 이는 기존의 더 허용적인 범위에서 더 제한적인 범위로의 요청 처리와 같습니다. 즉, 완전히 이행할 수 없는 출처 요청은 이를 전달한 쓰기를 실패시키는 대신 조용히 상한에 맞춰 제한됩니다. 이 명세의 다른 부분에 있는 § 8.3 가용성 게이팅과 일관되게, 호출자는 자신이 요청한 출처가 실제로 추가되었는지를 사후에 신뢰성 있게 확인할 방법이 없습니다. 이후 해당 출처에서 requestFileHandle()을 호출하더라도 출처가 추가된 상태에서 실패할 수 있습니다 — 예를 들어 GREASE 적용 때문일 수 있습니다 — 따라서 그 결과도 어느 방향의 확인으로도 해석해서는 안 됩니다.

5.2. 축출

이 절은 비규범적입니다.

저장소 압박이 있는 경우, 사용자 에이전트는 COS 레지스트리에서 항목을 축출할 수 있습니다. 예를 들어 각 항목에 가장 최근에 액세스한 저장 출처 전반에 최소 최근 사용 정책을 사용할 수 있습니다. 사용자 에이전트는 사용자가 저장된 파일, 각 파일에 액세스한 출처를 확인하고 항목을 수동으로 삭제하거나 모든 Cross-Origin Storage 데이터를 지울 수 있는 설정 UI를 제공할 것으로 예상됩니다.

사용자가 출처의 사이트 데이터를 지우면 사용자 에이전트는 해당 출처가 포함된 모든 저장 출처 집합에서 해당 출처를 제거하는 것이 좋습니다. 이 제거 후 COS 항목의 저장 출처가 비어 있으면 사용자 에이전트는 해당 항목을 삭제 대상으로 고려할 수 있습니다.

5.3. 수동으로 추가된 항목

이 절은 비규범적입니다.

위에서 설명한 설정 UI를 통해 사용자가 디스크에 이미 가지고 있는 파일을 직접 Cross-Origin Storage에 추가할 수 있습니다 — 예를 들어 웹사이트와 무관하게 독립적으로 다운로드한 AI 모델입니다 — 이 경우 어떤 스크립트도 requestFileHandle()을 호출하지 않습니다. 이러한 항목에는 쓰기를 귀속할 요청 출처가 없으므로, 명령형 API만으로는 답할 수 없는 두 가지 질문이 생깁니다.

  • § 3.4.1 원래 저장자의 액세스를 위한 원래 저장자는 누구입니까? 아무도 아닙니다. 항목의 저장 출처는 쓰기를 수행한 출처를 포함하는 대신 빈 상태로 시작합니다. 따라서 어떤 출처도 다른 모든 요청 출처에 적용되는 일반적인 가용성 게이팅 및 origins 검사에서 면제되지 않습니다 — 실제로 바이트를 작성한 출처가 없으므로 이것이 올바른 결과입니다.

  • 이러한 항목도 origins를 생략한 일반적인 쓰기처럼 동일 사이트에만 제한해야 합니까? 아닙니다. "동일 사이트"는 요청 출처를 기준으로 할 때만 의미가 있으며, 수동 추가에는 그러한 출처가 없으므로 "동일 사이트"가 의미할 사이트 자체가 없습니다. 사용자 에이전트는 대신 이러한 항목을 전역적으로 공개 가능하게 만들 것으로 예상되며, 명시적인 origins 목록은 비워 둡니다. 파일을 수동으로 시드하는 것은 사용자가 아직 방문하지 않은 사이트가 이미 디스크에 있는 파일을 재사용하도록 하는 데 목적이 있으며, 다른 출처가 실제로 이를 발견할 수 있어야 그 목적을 달성하기 때문입니다. 사용자 에이전트의 설정 UI는 사용자가 더 좁은 범위를 선택할 수 있도록 추가로 지원할 수 있습니다.

이 방식으로 추가된 후에는 state가 "written"인 항목은 그 외의 면에서 웹사이트가 requestFileHandle()을 통해 작성한 항목과 구별되지 않습니다. 동일한 가용성 게이팅 및 가시성 업그레이드 규칙이 같은 권한을 가진 다른 항목과 정확히 동일하게 적용됩니다 — 항목이 전역적으로 공개 가능한 상태가 되는 경우 PHL에 있음 검사도 포함됩니다. 이는 수동 추가의 기본값이지만 가능한 유일한 결과는 아닙니다.

5.4. 출처 메타데이터

이 절은 비규범적입니다.

COS 항목은 그 바이트가 어디에서 왔는지에 관한 정보를 의도적으로 전혀 기록하지 않습니다. 식별자는 hash뿐입니다. 동일한 바이트는 얼마나 많은 출처가 저장했는지 또는 몇 개의 URL에서 가져왔는지와 관계없이 동일한 항목입니다(§ 2.2 COS 항목 참조). URL은 항목 자체가 아니라 한 작성자의 가져오기에 속하는 속성이므로, 여러 출처가 작성한 항목에 하나를 선택하는 비자의적인 방법은 없습니다. URL은 바이트처럼 검증할 수 없으며(§ 8.1 리소스 무결성 참조), 경로나 쿼리 문자열은 특정 문서, 계정 또는 세션을 나타낼 수 있으므로 저장 출처의 거친 출처 값보다 사용자의 탐색에 관한 정보를 훨씬 더 많이 담고 있습니다. 따라서 이를 항목에 기록하면 origins와 § 8.3 가용성 게이팅이 부과하기 위해 존재하는 공개 제한을 우회하여 고엔트로피 신호가 전달됩니다.

그럼에도 이를 원하는 동기는 실제로 존재합니다. § 5.2 축출에서 설명한 설정 UI에서 수 기가바이트 크기의 파일을 보는 사용자와 requestFileHandle() 호출이 왜 실패했는지 디버깅하는 개발자는 모두 파일이 어디에서 왔는지 알고 싶어 합니다. 사용자 에이전트는 항목과 함께 구현 비공개 출처 기록을 유지하여 이를 제공할 수 있습니다 — 예를 들어 각 저장 출처가 바이트를 가져온 URL과 그 시각입니다 — 단, 해당 기록은 항목의 일부가 아니라 사용자 에이전트 상태로 취급되어야 합니다.

  • 이는 절대로 스크립트에 노출되지 않습니다. 이 명세의 어떤 것도 이를 공개하지 않으며, 나중에 추가되는 어떤 것도 공개해서는 안 됩니다. requestFileHandle()도, 그것이 반환하는 FileSystemFileHandle도 이러한 기록이 존재하는지 여부는 물론 그 내용까지 드러내서는 안 됩니다. 특히 요청하는 출처는 자신이 생성하지 않은 기록을 관찰할 수 없어야 합니다.

  • 이는 신뢰할 수 있는 비웹 표면을 통해서만 표시됩니다. 사용자 에이전트 자체의 설정 및 저장소 검사 UI, 개발자 도구, 그리고 사용자 에이전트에 확장 플랫폼이 있는 경우에는 탐색 기록을 노출하는 다른 API와 동일한 수준에서 명시적으로 사용자가 부여한 권한 뒤에 있는 확장 API를 통해서만 표시됩니다. 고려 중인 확장 표면은 이 저장소의 브라우저 확장 통합 지점 설명 문서를 참조하십시오.

  • 이는 검증되지 않으며, 그렇게 표시됩니다. 그 안의 URL은 바이트를 작성한 출처의 주장이지 해당 바이트에 대한 증명이 아닙니다 — 콘텐츠를 보장하는 것은 hash뿐입니다(§ 8.1 리소스 무결성 참조). 두 출처가 동일한 항목에 서로 다른 URL을 기록할 수 있으며, 어느 쪽이든 부정확하거나 의도적으로 오해를 유도할 수 있습니다.

  • 이는 항목 및 귀속된 출처와 수명을 공유합니다. 항목이 축출되거나 삭제되면 폐기되고, 한 출처에 귀속된 부분은 사용자가 해당 출처의 사이트 데이터를 지우는 경우를 포함하여 그 출처가 저장 출처에서 제거되면 폐기됩니다(§ 5.2 축출 참조).

이러한 기록은 콘텐츠에 보이지 않으므로, 사용자 에이전트가 이를 유지하는지 여부와 얼마나 많이 유지하는지는 전적으로 구현에 맡겨집니다. 이 명세의 어떤 것도 이에 의존하지 않으며, 사이트는 그 존재 여부를 감지할 수 없습니다.

6. 권한 정책 통합

이 명세는 문자열 "cross-origin-storage"로 식별되는 정책 제어 기능 [permissions-policy]을 정의합니다. 기본 허용 목록은 self입니다.

[permissions-policy]은 Document에 대해 사용이 허용됨을 정의하지만, CrossOriginStorageManager는 자체 Document가 없는 WorkerGlobalScope에도 노출됩니다. 따라서 검사는 호출하는 전역 객체를 대상으로 기술됩니다. 워커 전역 객체는 이를 소유하는 Document들로 전이적으로 해석되며, 그 모든 문서가 해당 기능을 허용해야 합니다.

전역 객체 global이 주어졌을 때 Cross-Origin Storage 권한을 확인하려면 불리언을 반환합니다.

  1. global이 Window 객체이면 다음을 수행합니다.

    1. document를 global의 연관된 Document로 둡니다.

    2. document가 null이면 false를 반환합니다.

    3. document가 "cross-origin-storage" 정책 제어 기능을 사용하도록 허용되지 않았으면 false를 반환합니다.

    4. true를 반환합니다.

  2. global이 WorkerGlobalScope 객체이면 다음을 수행합니다.

    1. owners를 global의 소유자 집합으로 둡니다.

    2. owners가 비어 있으면 false를 반환합니다.

    3. owners의 각 owner에 대해 다음을 수행합니다.

      1. owner가 Document이고 owner가 "cross-origin-storage" 정책 제어 기능을 사용하도록 허용되지 않았으면 false를 반환합니다.

      2. owner가 WorkerGlobalScope 객체이고 owner가 주어졌을 때 Cross-Origin Storage 권한 확인을 실행한 결과가 false이면 false를 반환합니다.

    4. true를 반환합니다.

  3. false를 반환합니다.

이 알고리즘이 false를 반환하는 전역 객체에서 수행된 모든 requestFileHandle() 호출은 해시 검증, 레지스트리 조회 또는 쓰기가 발생하기 전에 "NotAllowedError" DOMException으로 거부됩니다.

참고: 소유자 집합을 통해 해석하는 것은 이 기능이 이름뿐인 옵트아웃이 되지 않도록 하는 장치입니다. blob: URL에서 생성된 워커는 이를 생성한 페이지의 출처에서 실행되며 해당 페이지의 Cross-Origin Storage 뷰를 정확히 공유하므로(§ 3 CrossOriginStorageManager 인터페이스 참조), 전역 객체 자체의 Document만 참조하는 검사는 모든 워커에서 자명하게 충족되며, 호출을 new Worker(URL.createObjectURL(&hellip;))로 옮기기만 해도 다른 어떤 사항도 변경하지 않고 cross-origin-storage=() 정책을 우회할 수 있게 됩니다.

참고: ServiceWorkerGlobalScope의 소유자 집합은 비어 있으므로 이 알고리즘은 그곳에서 false를 반환합니다. 이는 [HTML]의 누락이 아니라 구조적인 결과입니다. 소유자 집합은 활성 상태 관계로, 워커가 생성될 때 채워지고 해당 워커가 여전히 적극적으로 필요한지를 결정할 때 참조되며, 서비스 워커에는 의도적으로 어떤 Document와도 이러한 관계가 없습니다. 등록은 지속되며, 사용자 에이전트는 페이지가 시작하는 대신 이벤트에 응답하여 전역 객체를 시작하고, 서비스 워커 클라이언트가 전혀 없어도 실행될 수 있습니다. 따라서 register()를 호출한 클라이언트는 등록 시점에는 알 수 있지만, 전역 객체가 실행될 때에는 일반적으로 이미 사라져 있으며, 하나의 실행 중인 서비스 워커는 서로 정책이 일치하지 않을 수도 있는 여러 클라이언트에 서비스를 제공합니다.

참고: 서비스 워커를 지원하려면 소유자를 순회하는 방식이 아니라 캡처된 정책이 필요하며, 이는 이 명세가 아니라 [permissions-policy] 및 [service-workers]에서 다룰 작업입니다. 이 명세가 선호하는 형태는 서비스 워커의 정책을 자체 스크립트 응답에 있는 Permissions-Policy 헤더에서 도출하는 것입니다. 이는 정책 컨테이너가 이미 해당 응답의 CSP를 전달하는 방식과 같으며, 출처의 제어 아래에 계속 남고 등록 시점에 고정되는 대신 모든 업데이트 확인에서 다시 평가됩니다. 반대로 등록한 클라이언트의 정책을 스냅샷으로 저장하면 옵트아웃이 오래된 상태로 남게 됩니다. 헤더에서 기능을 제거하더라도 등록이 우연히 업데이트될 때까지 적용되지 않기 때문입니다. 이러한 모델이 존재하기 전까지는 실패 시 닫는 방식이 옵트아웃을 우회하는 데 사용할 수 없는 유일한 답입니다.

참고: SharedWorkerGlobalScope의 소유자 집합은 서로 다른 정책을 가진 여러 Document를 포함할 수 있으며, 워커의 수명 동안 소유자를 얻거나 잃습니다. 모든 소유자가 기능을 허용하도록 요구하면 한 소유자가 이를 허용하지 않을 경우 전체 공유 워커에서 Cross-Origin Storage가 비활성화되며, 그 결과는 두 requestFileHandle() 호출 사이에서도 바뀔 수 있습니다. 반대로 허용하는 소유자 하나만 요구하면, 기능을 허용하는 어떤 문서든 기능을 허용하지 않는 문서를 대신하여 다시 활성화할 수 있게 됩니다.

7. Cross-Origin-Storage-Allow-Origin 헤더

origins 목록이 비어 있지 않은 COS 항목은 쓰기 출처가 제어하지 않는 출처에 공개할 수 있지만, 해당 목록은 스크립트(origins를 통해) 또는 마크업으로 선언되며, 스크립트 또는 마크업 삽입에 성공한 공격자는 어느 쪽이든 설정할 수 있습니다. 이 선언을 삽입된 콘텐츠가 아니라 공개되는 바이트를 가진 출처의 운영자에게 귀속할 수 있도록 하기 위해, 이 명세는 그러한 선언이 지정할 수 있는 출처의 범위를 제한하는 응답 헤더를 정의합니다.

Cross-Origin-Storage-Allow-Origin 응답 헤더는 COS 범위 상한을 전달합니다. 이는 공개 환경에서 수행되는 requestFileHandle() 쓰기 또는 해당 환경으로 로드하는 호스트 통합이 동일 사이트가 아닌 origins 목록에서 지정할 수 있는 출처의 집합입니다. 선언된 목록은 그대로 적용되지 않으며, 상한과 교집합을 취합니다 (생성 요청 완료 참조). 따라서 상한은 선언을 좁힐 수만 있으며, 넓히거나 새로 만들 수는 없습니다.

참고: 이 헤더는 목록 형식에만 적용됩니다. 동일 사이트 기본값은 교차 출처 수신자를 지정하지 않으므로 승인이 필요하지 않으며, "*" 형식은 읽기 경로에서 공개 해시 목록에 대한 가용성 게이팅의 적용을 받습니다. 사용자별 비밀 값은 이 검사를 절대 통과할 수 없으므로 쓰기 시점의 상한도 필요하지 않습니다. "*"에 헤더를 요구하면 공개 해시 목록이 이미 막지 않는 어떤 것도 추가로 막지 못하면서, 설정이 필요 없는 전역 공유 사례만 깨뜨리게 됩니다.

헤더 목록 headers가 주어졌을 때 COS 범위 상한을 파싱하려면 집합 형태의 출처를 반환합니다.

  1. value를 headers에서 "Cross-Origin-Storage-Allow-Origin"을 가져오고, 디코딩하고, 분할한 결과로 둡니다.

  2. value가 null이면 빈 집합을 반환합니다.

  3. ceiling을 빈 집합으로 둡니다.

  4. value의 각 token에 대해 다음을 수행합니다.

    1. token에서 선행 및 후행 ASCII 공백을 제거합니다.

    2. token이 빈 문자열이면 계속합니다.

    3. origin을 token에 기본 URL 파서를 실행한 결과인 출처로 둡니다.

    4. origin이 실패이거나 불투명 출처이면 빈 집합을 반환합니다.

      참고: 여기에는 출처로 파싱되지 않는 "*"인 token도 포함됩니다. Cross-Origin-Storage-Allow-Origin 헤더는 유한한 구체적 출처 집합만 열거할 수 있습니다. "*"는 허용되는 값이 아닙니다. "모든 출처"를 상한으로 허용하면 삽입된 콘텐츠가 원하는 수신자를 무엇이든 선언할 수 있게 되어 헤더의 전체 목적을 무력화하기 때문입니다. 제한 없는 공개는 "*" origins 형식을 통해서만 가능하며, 이 형식은 공개 해시 목록의 게이팅을 받고 이 헤더를 전혀 참조하지 않습니다. 잘못된 형식이거나 "*"를 포함하는 헤더는 존재하지 않는 헤더와 정확히 마찬가지로 아무것도 승인하지 않습니다. 실패 시 닫힙니다.

    5. origin을 ceiling에 추가합니다.

  5. ceiling을 반환합니다.

참고: 가져오고, 디코딩하고, 분할은 U+002C (,)에서 분할하므로 헤더 값의 출처는 쉼표로 구분되며, 이는 Timing-Allow-Origin [RESOURCE-TIMING] 및 목록 값을 갖는 HTTP 응답 헤더의 일반적인 규칙과 일치합니다. 반면 형제인 crossoriginstorage HTML 콘텐츠 속성은 호스트 구문에 맞추기 위해 공백으로 구분됩니다. 두 형식 모두 동일한 출처 집합으로 해석됩니다.

전역 객체 global이 주어졌을 때 COS 범위 상한을 얻으려면 집합 형태의 출처를 반환합니다.

  1. global이 Window 객체이면 다음을 수행합니다.

    1. document를 global의 연관된 Document로 둡니다.

    2. document가 null이면 빈 집합을 반환합니다.

    3. document의 COS 범위 상한을 반환합니다.

  2. global이 WorkerGlobalScope 객체이면 다음을 수행합니다.

    1. owners를 global의 소유자 집합으로 둡니다.

    2. owners가 비어 있으면 빈 집합을 반환합니다.

    3. ceiling을 null로 둡니다.

    4. owners의 각 owner에 대해 다음을 수행합니다.

      1. ownerCeiling을 빈 집합으로 둡니다.

      2. owner가 Document이면 ownerCeiling을 owner의 COS 범위 상한으로 설정합니다.

      3. 그렇지 않고 owner가 WorkerGlobalScope 객체이면 ownerCeiling을 owner가 주어졌을 때 COS 범위 상한 얻기를 실행한 결과로 설정합니다.

      4. ceiling이 null이면 ceiling을 ownerCeiling로 설정하고, 그렇지 않으면 ceiling을 ceiling과 ownerCeiling의 교집합으로 설정합니다.

    5. ceiling을 반환합니다.

  3. 빈 집합을 반환합니다.

모든 Document에는 COS 범위 상한이 있으며, 이는 집합 형태의 출처입니다. 이 값은 문서가 생성될 때 그 문서를 만드는 데 사용된 응답의 헤더 목록이 주어졌을 때 COS 범위 상한 파싱을 실행한 결과로 설정됩니다.

참고: 워커의 소유자 집합 전체에 대해 교집합을 취하는 것은 Cross-Origin Storage 권한 확인과 대응합니다. 어떤 출처가 워커의 상한에 포함되려면 모든 소유 Document가 전이적으로 해당 출처를 승인해야 합니다. blob: 워커는 이를 생성한 페이지의 출처와 Cross-Origin Storage 뷰를 정확히 공유하므로(§ 3 CrossOriginStorageManager 인터페이스 참조), 워커 자체만 참조하는 상한은 모든 워커에서 비어 있게 되고, 목록 범위 쓰기를 new Worker(URL.createObjectURL(&hellip;))로 옮기면 페이지의 승인을 유지하는 대신 수신자가 제거됩니다. 소유자들의 상한을 교집합으로 취하면 어느 한 소유자도 상한을 넓힐 수 없게 하면서 이를 유지합니다.

Document의 COS 범위 상한을 해당 응답에서 채우고, 각 호스트 통합에 대해 저장되는 바이트가 나온 응답에서 동등한 상한을 설정하려면, [permissions-policy] 및 [CSP]이 응답 처리 시점에 채워지는 것과 마찬가지로 호스트 명세에 훅이 필요합니다. 이러한 훅이 존재하기 전까지 이 절에서는 필요한 동작을 직접 설명합니다. 향후 개정에서는 § 3.3 파일 생성 및 쓰기에서 언급한 [FS] 훅과 함께 이를 정식으로 통합할 것으로 예상됩니다.

8. 개인정보 보호 및 보안 고려사항

이 절은 RFC 2119 키워드를 사용하는 부분을 제외하고 비규범적입니다. 저장소의 보안 및 개인정보 보호 설문지도 참조하십시오.

8.1. 리소스 무결성

모든 COS 항목은 암호학적 해시를 키로 사용하며, 그 바이트는 해당 해시에 대해 검증됩니다(§ 3.3 파일 생성 및 쓰기 참조). 따라서 사이트는 requestFileHandle()을 통해 얻은 파일의 바이트가 hash를 직접 가져왔을 때 얻었을 바이트와 정확히 동일하다고 확신할 수 있습니다. 개발자는 Cross-Origin Storage의 내용을 열거하거나, 해시를 이미 알지 못한 상태에서 파일에 액세스할 수 없습니다.

COS 해시는 비밀이 아닙니다. 이는 콘텐츠 식별자로서, 파일을 이미 보유한 사람이라면 누구나 쉽게 계산할 수 있으며, 이 명세가 대상으로 하는 널리 배포되는 종류의 리소스에서는 일반적으로 공개된 정보입니다. 예를 들어 모델이나 라이브러리의 릴리스와 함께 게시될 수 있습니다. 따라서 해시를 아는 것으로 항목을 조회할 수는 있지만, capability URL이나 bearer token과 달리 해시 자체는 액세스 권한을 부여하지 않습니다. 조회 성공 여부는 해시가 우연히 공개되지 않은 채 남아 있었는지가 아니라 전적으로 origins 및 § 8.3 가용성 게이팅에 의해 결정됩니다. 개발자는 공개되지 않은 해시를 액세스 제어 메커니즘으로 취급해서는 안 됩니다. 특정 파일에 관심이 있는 공격자는 그 해시를 추측할 필요 없이 파일 자체만 얻으면 됩니다(§ 8.2 교차 사이트 프로빙 참조).

8.2. 교차 사이트 프로빙

리소스가 소수의 사이트에서만 사용되는 경우, 공격자가 해당 리소스가 Cross-Origin Storage에 존재한다는 사실을 알아낼 수 있으면 사용자가 그 사이트들 중 하나를 방문했을 가능성이 높다고 추론할 수 있습니다. requestFileHandle()이 존재 여부를 알아내는 메커니즘이므로 각 호출은 사실상 하나의 프로브입니다. 이 명세의 두 가지 독립적인 메커니즘이 프로브가 알아낼 수 있는 정보를 제한합니다.

  • origins(§ 3.4 리소스 가시성 업그레이드 참조)를 사용하면 저장 출처가 공개 대상을 선택한 출처 집합으로 제한할 수 있으므로, 독점적이거나 인기가 낮은 리소스는 전역적으로 전혀 프로빙할 수 없게 할 수 있습니다.

  • § 8.3 가용성 게이팅은 추가로, 요청 출처가 저장 출처 밖에 있는 경우 해시가 PHL에 있지 않으면 "*" 범위 리소스의 공개를 보류합니다. 따라서 origins: "*"로 저장된 리소스가 웹의 모든 출처에서 자동으로 프로빙 가능해지지는 않습니다. 이 게이트는 "*" 범위 항목에만 적용됩니다. 목록 및 동일 사이트 범위 항목의 경우 저장 출처가 이미 해당 공개 범위를 명시적으로 제한했으므로 첫 번째 항목의 제한이 유일한 게이트입니다.

첫 번째 항목은 "선택한 출처 집합"이 웹보다 의미 있게 작게 유지되는 경우에만 성립합니다. origins의 형태 자체는 호출자가 매우 많은 수의 출처를 열거하는 것을 막지 않습니다. 예를 들어 공개된 상위 사이트 순위에서 구성한 목록은 "*"만이 요구하는 의도적이고 명시적인 옵트인을 우회하면서 기능적으로 전역 공개에 가까워질 수 있습니다. 최대 출처 목록 길이(§ 5.1 저장소 제한 참조)가 이를 제한합니다. 실제 다중 속성 사용 사례(공통 제어 아래의 소수 관련 출처)를 수용하기에는 충분하지만 "모든 출처"를 의미 있게 근사하기에는 턱없이 작은 제한을 두면, 제한된 출처 형식의 origins가 "*"의 선언되지 않은 대체 수단으로 사용되는 것을 방지할 수 있습니다.

사용자 에이전트는 추가로 단일 출처에서 반복되는 requestFileHandle() 호출의 속도를 제한하거나 다른 방식으로 스로틀링하는 것이 좋으며, 프로빙되는 해시가 PHL에 있는지 여부와 관계없이 기기 내 휴리스틱(예를 들어 사용자별로 생성된 것으로 보이는 해시에 대한 요청 패턴 탐지)을 적용하여 프로빙 시도를 식별하고 차단할 수 있습니다.

§ 9 다른 명세와의 통합에 있는 호스트 통합 중 하나가 수행하는 조회도 페이지에 오류를 노출하지 않더라도 동일하게 하나의 프로브입니다. 사이트는 자체 서버가 폴백 요청을 받았는지를 관찰할 수 있고, 이는 여기서 "찾을 수 없음" 결과가 전달하는 것과 동일한 1비트 정보를 전달합니다. 이러한 조회는 이 명세의 게이트가 허용하지 않는 어떤 정보도 공개하지 않으며, 해당 게이트는 그대로 적용됩니다. 그러나 속도 제한은 이러한 표면에서의 조회가 requestFileHandle() 호출과 함께 계산되는 경우에만 효과가 있습니다. 스크립트 가능한 통합도 마찬가지로 쉽게 루프에서 조회를 발생시킬 수 있기 때문입니다.

8.3. 가용성 게이팅

저장 출처 밖의 출처에서 수행된 requestFileHandle() 읽기가 성공하는지는 항상 요청 출처가 항목을 읽도록 허용되는지에 달려 있으며, 이는 origins가 규율합니다. "*" 범위 항목에는 두 번째 독립적인 질문도 적용됩니다. 즉, 사용자 에이전트가 항목이 존재한다는 사실 자체를 공개할 의향이 있는지이며, 이는 PHL 구성원 여부 및 GREASE 적용이 규율합니다. 이러한 항목에서는 두 조건을 모두 충족해야 합니다. 목록 또는 동일 사이트 범위 항목에서는 첫 번째 질문만 적용되지만, GREASE 적용은 여전히 origins가 원래 허용했을 공개를 억제할 수 있습니다. 규범적 알고리즘은 § 3.2 파일 읽기를 참조하십시오. 따라서 "NotFoundError"는 리소스가 존재하지 않는다는 증거가 아닙니다. 리소스가 존재하지 않을 수도 있고, 요청 출처가 범위 밖일 수도 있으며, "*" 범위 리소스의 해시가 아직 또는 영원히 PHL에 없을 수도 있고, GREASE 적용이 실제 양성 결과를 억제했을 수도 있습니다. 개발자는 "NotFoundError"를 "네트워크로 폴백하십시오."보다 더 구체적인 의미로 취급해서는 안 됩니다.

참고: "*" 범위 항목의 공개는 현재 컨텍스트에서 서드파티 쿠키를 설정하거나 읽을 수 있는 요청 출처로 추가 제한됩니다. 해당 항목은 PHL 구성원 여부와 관계없이, 서드파티 쿠키를 사용할 수 없는 출처에는 공개되지 않습니다. 이는 PHL 구성원 여부만으로는 막을 수 없는 허점을 닫습니다. 공격자는 각각은 평범하고 개별적으로 PHL 자격을 갖춘 리소스 중 어떤 부분집합을 쓸지 선택함으로써 교차 사이트 식별자를 만들 수 있으며, 그 결과 발생하는 프로브가 일반적인 추적 쿠키보다 더 많은 정보를 제공하는지를 결정하는 요소는 서드파티 쿠키의 가용성입니다.

8.4. GREASE 적용

사용자 에이전트는 GREASE 적용(무작위 확장을 생성하고 확장성을 유지하기)을 적용할 수 있습니다. 즉, § 8.3 가용성 게이팅이 원래 공개를 허용하는 경우에도 때때로 공개 가능한 항목이 없는 것처럼 응답할 수 있습니다. 이는 사이트가 실제 부재와 개인정보 보호를 위한 거짓 음성을 구별하기 어렵게 만드는 노이즈를 추가하며, UA 클라이언트 힌트에서 적용하는 기법과 유사합니다.

GREASE 적용을 사용하는 사용자 에이전트는 해당 항목의 크기에 비례하여 합리적으로 적용해야 합니다. 작은 항목은 네트워크 가져오기로 폴백하는 비용이 낮으므로 가끔 발생하는 거짓 음성이 합리적인 개인정보 보호 절충안이 됩니다. 사용자 에이전트는 항목의 크기 때문에 불필요한 재다운로드가 그에 따른 개인정보 보호 이익에 비해 명백히 불균형해지는 항목에는 GREASE 적용을 해서는 안 됩니다. 예를 들어 기가바이트 규모의 AI 모델 가중치에서는 거짓 음성이 값싼 재다운로드가 아니라 전체 파일의 관찰 가능하고 비용이 큰 재다운로드를 강제하기 때문입니다.

8.5. 핑거프린팅

공격자가 Cross-Origin Storage 프로빙에서 추출할 수 있는 정보는 프로빙한 리소스가 얼마나 인기 있는지에 의해 제한됩니다. 일반적인 AI 모델이나 널리 사용되는 JavaScript 라이브러리처럼 매우 인기 있는 리소스를 사용자가 가지고 있다는 사실을 알아내더라도, 사용자가 이를 사용하는 (매우 많을 수도 있는) 사이트 중 하나를 방문했다는 사실만 드러납니다. 반면 희귀하거나 고유한 리소스를 사용자가 가지고 있다는 사실은 훨씬 더 많은 정보를 제공합니다. 사용자 에이전트는 해시가 의도적으로 사용자별로 고유하게 만들어진 것으로 보이는 리소스를 탐지하기 위해 기기 내 휴리스틱을 적용하고(예를 들어 하나의 사이트에서만 작성된 적이 있는 해시 또는 비정상적으로 자주 요청되는 해시), 명목상의 PHL 상태와 관계없이 이러한 패턴을 프로빙 시도로 취급할 것으로 예상됩니다.

9. 다른 명세와의 통합

이 절은 비규범적입니다.

여기에서 정의한 COS 레지스트리는 requestFileHandle()을 직접 거치지 않고도 네 가지 호스트 통합에서 접근할 수 있습니다. 각 통합은 이 문서가 아니라 자체 호스트 명세에서 정의됩니다. 이 명세는 해당 통합이 기반으로 삼을 것으로 예상되는 공통 기반 개념(COS 해시, COS 항목, 가용성 게이팅, 그리고 공개 해시 목록)만 정의합니다.

  • HTML: 이미 integrity [SRI]를 가진 link 및 script 요소의 crossoriginstorage 속성으로, whatwg/html#12770에서 WHATWG에 제안되었습니다.

  • JavaScript: Import Attributes 제안을 기반으로 하며 integrity와 함께 사용할 수 있는 호스트 정의 crossOriginStorage import 속성으로, whatwg/html#12771에서 WHATWG에 제안되었습니다.

  • CSS: integrity()와 함께 사용할 수 있는 cross-origin-storage() <request-url-modifier>로, w3c/csswg-drafts#14056에서 CSS Working Group에 제안되었습니다.

  • Fetch: integrity [FETCH]와 함께 사용할 수 있는 crossOriginStorage RequestInit 옵션으로, whatwg/fetch#1954에서 WHATWG에 제안되었습니다. 세 가지 선언적 형식과 달리 이 형식에는 호스트 정의 destination이 없으므로, COS 레지스트리에서 제공된 Response가 MIME 유형, 상태 및 기타 메타데이터를 어떻게 보고할지는 해당 명세의 미해결 문제입니다. COS 항목은 바이트만 저장합니다.

설명을 위해서만, 다음은 동일한 전역 공유 리소스를 네 가지 형식 각각을 통해 Cross-Origin Storage에 옵트인한 예입니다.

<script src="popular-library.js" integrity="sha256-abc123..." crossoriginstorage="*"></script>

import data from "popular-resource.ext" with {
  integrity: "sha256-abc123...",
  crossOriginStorage: "*",
};

@font-face {
  font-family: "Popular Font";
  src: url("popular-font.woff2" integrity("sha256-abc123...") cross-origin-storage(*));
}

const response = await fetch("popular-resource.ext", {
  integrity: "sha256-abc123...",
  crossOriginStorage: "*",
});

이 코드 조각은 설명을 위한 것일 뿐입니다. 이 구문 중 어떤 것도 이 명세에서 정의되지 않으며, 제한된, "*"가 아닌 origins 값을 어떻게 표기하는지를 포함하여 각 형식의 권위 있는 문법은 이 문서가 아니라 해당 호스트 명세에 속합니다. 표기 방식은 의도적으로 다릅니다. RequestInit 멤버는 origins와 정확히 일치하도록 sequence<DOMString>을 받을 수 있지만, 속성 값, import 속성 값 및 CSS 수정자 인수에는 텍스트만 넣을 수 있습니다.

네 가지 형식 모두 먼저 COS 레지스트리에서 일치하고 공개 가능한 항목을 확인한 후 네트워크 가져오기로 폴백하고, 성공적으로 가져와 무결성 검증을 통과한 리소스를 다른 출처가 재사용할 수 있도록 COS 레지스트리에 저장하는 처리 모델을 공유할 것으로 예상됩니다. 이는 requestFileHandle()이 수행하는 것과 정확히 같습니다. 이러한 통합에 관한 논의는 이 저장소의 이슈 트래커가 아니라 해당 통합을 포함할 호스트 명세의 트래커에서 이루어져야 합니다.
