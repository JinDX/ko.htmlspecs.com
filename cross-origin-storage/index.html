개요

교차 출처 저장소(COS)는 웹 애플리케이션이 파일을 저장하고 가져올 수 있는 콘텐츠 주소 지정 방식의 캐시입니다. AI 모델, WebAssembly 모듈, 매우 널리 쓰이는 JavaScript 라이브러리 같은 대용량 파일을 서로 다른 출처에 걸쳐 사용할 수 있습니다. 파일은 URL 대신 암호학적 해시로 식별되므로 바이트 단위로 동일한 리소스를 한 출처에서 한 번 가져오면 사용자 에이전트가 허용하는 다른 모든 출처에서 재사용할 수 있어 다시 다운로드할 필요가 없습니다. 기본적으로 동일 사이트의 출처에서 파일을 읽을 수 있습니다. 작성자는 출처 몇 개를 추가로 지정하거나 모든 출처와 공유할 수 있습니다. 모든 출처와의 공유는 k-익명성과 유사한 방식의 인기도 기준을 충족하는 해시에만 적용됩니다. 교차 사이트 조회에 대한 사이트별 예산과 사이트별 쓰기 한도는 각 사이트가 다른 사이트에서 저장한 내용에 관해 알아낼 수 있는 정보의 범위를 제한합니다.

1. 소개

이 절은 비규범적입니다.

저장소는 일반적으로 사용자의 보안과 개인정보를 보호하기 위해 출처별로 분할됩니다. 이는 적절한 기본 동작이지만, 크기가 매우 크고 널리 쓰이며 공개적으로 배포되는 일부 리소스(AI 모델, WebAssembly 모듈, JavaScript 라이브러리, 게임 엔진, 대용량 웹 글꼴)에는 적합하지 않습니다. 이러한 리소스는 어느 사이트에서 요청하든 바이트 단위까지 동일한 파일입니다. 서로 관련 없는 두 출처가 각각 동일한 8 GB 모델에 의존하면, 출처별로 분할된 저장소에서는 사용자가 그 모델을 두 번 다운로드하고 보관해야 합니다. 이는 사용자의 대역폭과 저장 공간, 배터리를 낭비하고 네트워크 전체에도 부담을 줍니다.

교차 출처 저장소(COS)는 내용 주소 지정 방식의 캐시입니다. 암호학적 해시를 URL 대신 키로 사용하므로, 사용자 에이전트는 이러한 리소스의 저장된 사본 하나를 사용을 선택한 여러 출처에서 공유할 수 있습니다. COS에 리소스를 저장하려면 언제나 저장하는 출처가 이를 명시적으로 선택해야 합니다. 사용자 에이전트는 리소스를 읽을 권한이 있는 출처에도 그 존재를 확인해 주지 않을 수 있습니다. § 8 개인정보 보호 및 보안 고려 사항을 참조하세요.

이 명세의 진입점은 getFileHandle() 메서드이며, 이를 노출하는 속성은 crossOriginStorage입니다: 

const hash = {
  algorithm: 'SHA-256',
  value: '8f434346648f6b96df89dda901c5176b10a6d83961dd3c1ac88b59b2dc327aa4',
};
try {
  const handle = await navigator.crossOriginStorage.getFileHandle(hash);
  const file = await handle.getFile();
  // 파일을 사용해 작업을 수행합니다.
} catch (err) {
  if (err.name === 'NotFoundError') {
    // 교차 출처 저장소에 없거나 존재를 공개할 수 없으므로 네트워크에서 가져옵니다.
  }
}

이 명세는 FileSystemFileHandle, FileSystemWritableFileStream, 그리고 이와 관련된 파일 시스템 표준의 기반 구조를 재사용합니다 [FS]. 적용 범위는 전용 파일 시스템으로, 출처 간에 공유되며 각 출처의 비공개 파일 시스템이나 사용자에게 보이는 파일 시스템과 구분됩니다.

이 명세는 명령형 JavaScript API와 더불어 호스트 통합의 기반이 되는 공통 저장 단계를 정의합니다. 관련 제안들은 동일한 기반 캐시를 다른 호스트 명세에 통합합니다. HTML의 crossoriginstorage 속성은 link 및 script에 적용되며, 그 밖에 crossOriginStorage JavaScript 가져오기 속성, CSS의 cross-origin-storage() <request-url-modifier>, 그리고 crossOriginStorage RequestInit 옵션이 fetch()에 사용됩니다. 각 통합은 해당 호스트 명세에 정의되어 있습니다. § 9 다른 명세와의 통합을 참조하세요.

2. 개념

2.1. 해시

COS 해시는 구조체이며 다음 항목을 가집니다:

algorithm

이 문자열은 해시 알고리즘의 이름을 나타냅니다. [WEBCRYPTO]에서 인정하는 이름 중 "SHA-1"은 제외되며, 한 예로 "SHA-256"이 있습니다.

value

이 문자열은 다이제스트를 소문자 16진수로 인코딩한 값이며, 다이제스트는 algorithm으로 생성합니다. "SHA-256"의 경우 길이는 64자입니다.

algorithm 딕셔너리 멤버의 타입은 단순 DOMString입니다. 이 멤버가 가질 수 있는 값의 집합은 [WEBCRYPTO]의 해시 알고리즘이 허용하는 이름의 집합과 정확히 일치합니다. HashAlgorithmIdentifier의 타입은 (object or DOMString)이며, 이 중 object 분기는 [WEBCRYPTO]에 따라 Algorithm 형태의 딕셔너리로 정규화되므로 호출자는 추가 매개변수가 필요한 알고리즘에 이를 전달할 수 있습니다(예: {name: "HMAC", hash: "SHA-256"}). 해시 알고리즘은 이러한 매개변수를 받지 않습니다. algorithm은 저장, 비교 및 왕복 변환 시 모두 내용 주소 지정 방식의 키에 포함되며, 이 명세의 모든 예에서는 단순 문자열을 사용합니다. 여기서 임의의 객체를 허용하면 기능이 늘어나지 않으면서 동등성 비교와 직렬화만 불필요하게 복잡해집니다. 따라서 DOMString이 이 필드에 더 좁고 정확한 타입입니다.

두 COS 해시 값이 같다는 것은 두 해시의 algorithm 값이 ASCII 대소문자를 구분하지 않고 일치하며, value 값이 정확히 일치한다는 뜻입니다.

참고: value는 이미 소문자로 규정되어 있으므로(위 참조), 비교할 때는 일반적인 문자열 비교를 사용합니다. algorithm에는 규범적으로 정해진 대소문자 표기가 없으므로 ASCII 대소문자를 구분하지 않고 비교합니다.

내용 주소 지정 방식의 저장소에서는 항목의 키가 같은지를 판단하는 기준으로 동등성을 사용하며, 그 비교 대상은 COS 해시입니다. 두 파일의 바이트와 해시 알고리즘이 같으면 두 파일은 같은 항목입니다. 몇 개의 출처가 이를 저장했는지, 몇 개의 URL에서 가져왔는지는 관계없습니다.

2.2. COS 항목

COS 파티션은 환경 설정 객체 settings에 대해 다음과 같이 구합니다. 사이트 구하기를 settings의 최상위 출처에 적용한 결과입니다. settings가 자사 COS 컨텍스트인지는 사이트 구하기를 settings의 출처에 적용한 결과로 판단합니다. 그 결과와 동일 사이트여야 하는 대상은 해당 객체의 COS 파티션입니다.

COS 공유 레코드는 하나의 구조체이며 다음 항목을 가집니다. origin은 출처이며, partition은 COS 파티션으로서 해당 레코드를 추가한 쓰기 작업의 파티션입니다. first-party는 불리언으로, 해당 쓰기 작업의 실행 환경이 자사 COS 컨텍스트였는지를 기록합니다. 레코드는 읽기 작업의 COS 파티션이 동일 사이트 조건을 충족할 때 적용되며, 비교 대상은 레코드의 partition입니다. COS 공개 여부 결정을 참조하세요.

각 사용자 에이전트에는 단 하나의 COS 레지스트리가 있습니다. 이는 맵으로, 각 COS 해시 값을 COS 항목 구조체에 대응시키며, 교차 출처 저장소를 사용하는 모든 출처가 공유합니다. COS 항목에는 다음 항목이 있습니다:

hash

COS 해시입니다.

bytes

이 바이트 시퀀스의 다이제스트를 계산할 때는 hash의 algorithm을 사용하며, 계산 결과는 hash의 value와 같습니다.

참고: 항목이 COS 레지스트리에 추가되려면 작성자가 이 바이트를 제공하고 사용자 에이전트가 이를 검증해야 합니다. 검증 및 저장을 참조하세요. 요청되었지만 완료되지 않은 쓰기 작업은 레지스트리에 전혀 나타나지 않습니다. 따라서 진행 중인 쓰기 작업은 읽기 경로에서 쓰기 작업이 없는 경우와 구별할 수 없습니다. § 8.3 진행 중인 쓰기를 참조하세요.

origins

이 목록은 COS 공유 레코드로 구성되며, 명시적으로 교차 출처 읽기 권한을 부여합니다. 이 권한은 공개 해시 목록과 독립적입니다. 각 레코드는 동일 사이트 관계에 있는 모든 출처에 적용되며, 비교 대상은 레코드의 origin입니다. 따라서 https://a.example을 명시하면 https://www.a.example도 허용됩니다. 레코드의 first-party가 참이면 해당 레코드는 자사 COS 컨텍스트에서 읽는 주체에도 최상위 사이트와 관계없이 적용됩니다. 목록은 처음에는 비어 있으며 이후에는 확장되기만 합니다. 이는 누가 항목을 읽을 수 있는지를 결정하는 세 가지 독립적이고 누적되는 범위 중 하나입니다. 나머지 두 가지는 해당 항목의 저장 출처(항상 읽을 수 있으며, 다른 출처도 이들과 동일 사이트이면 항상 읽을 수 있음)와 전역 공개 가능입니다.

참고: 따라서 하나의 출처를 지정하는 것은 그 출처의 전체 사이트를 신뢰한다는 뜻입니다. 작성자가 지정한 출처의 사이트에서 작성자가 신뢰하지 않는 콘텐츠를 호스팅하는 경우(예: 공개 접미사 목록에서 빠진 호스팅 도메인), 해당 콘텐츠 전체에 항목이 공개됩니다.

참고: 쓰기 작업의 origins에 명시적으로 빈 목록을 지정하면 (origins: []) 허용 범위는 origins를 생략한 쓰기 작업과 정확히 같습니다. 즉, 항목의 저장 출처 및 이들과 동일 사이트인 출처가 허용됩니다. 이는 모든 항목에 적용되는 기본 범위입니다(COS 공개 여부 결정 참조). 상한을 적용하면 빈 목록이 null이 되므로, 두 쓰기 작업은 생성 요청 완료의 나머지 단계를 같은 상태에서 실행합니다. 명시적인 목록은 수신 대상을 추가하기만 하며, 작성자 자신의 사이트에서 항목을 읽지 못하게 하는 일은 없습니다.

전역 공개 가능

이 불리언은 초깃값이 거짓이며, 항목을 쓸 때 요청한 가용성 범위가 전역("*")이고 해당 요청이 COS 사용자 활성화 조건을 통과했는지를 기록합니다. 값이 참이면 요청이 § 8.4 가용성 제한을 통과하는 모든 출처에서 항목을 읽을 수 있습니다. 즉, 요청한 hash가 PHL에 포함되고, 사이트 간 조회 예산이 해당 요청을 허용하며, GREASE가 해당 요청을 억제하지 않아야 합니다. 일단 설정되면 계속 참으로 유지됩니다.

참고: 이는 별도의 항목으로 origins와 구분됩니다. 따라서 나중에 전역 가용성을 요청하더라도 전역 범위는 기존의 명시적인 origins 목록에 더해집니다. 이 둘을 하나의 필드로 합치면 바이트를 제공한 작성자가 목록 범위의 항목을 "*" 범위의 항목으로 바꿀 수 있습니다. § 8.4 가용성 제한은 전역 범위에만 적용되므로, 이전에는 목록을 통해 항목을 읽을 수 있었던 출처도 그때부터 "NotFoundError"를 받게 됩니다. 이는 hash가 다음 조건을 충족하지 않을 때마다 발생합니다. 바로 PHL에 포함되어야 한다는 조건입니다. 각 범위를 독립적으로 유지하면 공개 범위는 변경될 때마다 확장되기만 합니다. 이는 확장은 가능하지만 축소는 불가능하다는 원칙이 요구하는 동작입니다.

저장 출처

이 집합은 COS 공유 레코드로 구성되며, 각 출처와 COS 파티션 쌍당 레코드가 하나씩 있습니다. 해당 파티션에서 그 출처가 이 항목의 바이트를 적어도 한 번 성공적으로 기록한 경우에 해당합니다. 레코드의 first-party 값은 관여하지 않습니다. 이 집합은 페이지를 다시 로드해도 유지되며 시간이 지날수록 커집니다. § 5.2 퇴거에 설명된 경우에만 줄어듭니다. 레코드의 origin은 언제든지 해당 항목의 핸들을 얻을 수 있습니다. 이때 getFileHandle()을 레코드의 partition에서 사용하며, 이는 origins 값이나 항목의 hash가 공개 해시 목록(PHL)에 포함되는지 여부와 무관합니다. § 3.5.2 원래 저장한 출처의 접근을 참조하세요.

참고: 최상위 사이트를 공유 레코드의 키로 사용하면 삽입된 프레임이 볼 수 있는 교차 출처 저장소의 범위가 저장소 분할에 따라 다른 저장소에서 볼 수 있는 범위와 같아집니다. 이 키가 없으면 여러 사이트에 삽입된 프레임이 한 사이트에서 작은 파일을 쓴 후 다른 사이트에서 저장 출처 자격으로 해당 파일을 다시 읽어 공개 해시 목록, GREASE 적용, 그리고 사이트 간 조회 예산을 우회할 수 있습니다. 이는 제3자 쿠키와 같은 효과를 냅니다. 최상위 쓰기 작업에도 키를 사용하므로 추적자가 최상위 사이트 방문 시 한 번 기록한 뒤 곳곳에 삽입된 프레임에서 다시 읽을 수는 없습니다. origins 레코드가 자사 COS 컨텍스트에서 만들어졌다면 자사 컨텍스트에서는 어느 최상위 사이트에서나 적용되므로 최상위 사이트 간 제한적 공유도 계속 작동합니다. 이러한 레코드가 다른 최상위 사이트에서의 조회에 응답하면 작성자의 최상위 사이트에서 저장한 내용이 공개되므로, 사이트 간 조회 예산에 이 조회가 산입됩니다(가용성 제한 적용 참조). 전역 공개 가능에는 키를 사용하지 않습니다. 공개 해시 목록, GREASE 적용, 그리고 사이트 간 조회 예산이 이미 이를 통제하기 때문입니다.

사용자 에이전트에는 연결된 교차 출처 저장소 큐가 있으며, 이는 새 병렬 큐 시작의 결과입니다. COS 레지스트리에 대한 모든 연산은 큐에 넣기를 통해 이 큐에 추가해야 합니다. 따라서 각 연산은 큐에 들어간 순서대로 실행되며 실행 도중 서로 뒤섞이지 않습니다.

2.3. 공개 해시 목록

교차 출처 저장소에 해시가 존재한다고 확인해 주는 것만으로도 사용자의 방문 기록에 관한 정보가 유출될 수 있습니다(§ 8.2 사이트 간 탐색 참조). 이는 전역 범위에만 해당하는 위험입니다. 항목에 명시한 origins 목록과 모든 항목에 적용되는 동일 사이트 기본 범위에서는 저장 출처가 명시적으로 선택한 범위로 공개가 이미 제한됩니다. 반면 항목을 전역 공개 가능으로 설정하면 웹상의 모든 출처에 노출될 수 있습니다. 이러한 위험을 제한하기 위해 전역 공개 가능 리소스를 전역 범위를 통해 해당 리소스의 저장 출처 이외의 출처에 공개하려면 해시가 별도의 독립적인 조건을 충족해야 합니다. 즉, 공개 해시 목록 (PHL)에 포함되어야 합니다. 이 목록은 특정 공급업체에 종속되지 않는 구현 정의 허용 목록으로, COS 해시 값으로 구성됩니다. 해시는 k-익명성과 유사한 보급도 기준을 충족한 후에만 공개 해시 목록에 추가됩니다(예: 일정 수 이상의 독립적인 출처에서 바이트가 동일하게 나타나는 경우). 따라서 공유 캐시에 해당 해시가 존재한다고 확인해도 개별 사용자에 관해 드러나는 정보는 거의 없습니다.

COS 해시 hash가 공개 해시 목록에 포함된다는 것은 hash와 같은 항목이 사용자 에이전트의 현재 공개 해시 목록 스냅샷에 있다는 뜻입니다.

공개 해시 목록의 조회 프로토콜, 갱신 주기, 데이터 형식, 보급도 임곗값 및 관리 체계는 이 명세의 부속 자료에서 상세히 설계합니다. 이는 공개 접미사 목록의 취지를 따른 것입니다. 공개 접미사 목록은 [URL] 표준의 부속 데이터 파일입니다. 공개 해시 목록 설명서는 이 저장소에서 확인할 수 있습니다. 이 설계는 여러 공급업체가 참여하는 공개 접미사 목록을 모델로 삼아 WHATWG가 목록을 관리하고, 지속적으로 배포해 온 선례를 따르며, 널리 쓰인다는 사실이 독립적으로 확인되는지를 등재 기준으로 삼자고 제안합니다. 이는 위에서 설명한 k-익명성 방식의 기준을 구체화한 것입니다. 이 기준은 오프라인에서 단 한 번, 해시 등재 절차의 일부로 적용하므로 사용자 에이전트가 조회할 때마다 다시 적용하지 않습니다. 이 내용은 아직 이 제안 밖에서 확립되지 않았습니다. 목록 자체의 초기 비규범적 코드 프로토타입은 현재 이 저장소의 다음 경로에 있습니다. public-hash-list/implementation/. 여러 공급업체가 참여하는 전용 저장소를 두는 것은 여전히 PHL 설명서에 기술된 관리 체계의 목표입니다. 이 명세는 해시가 PHL에 포함되는지 여부에만 의존하므로, 목록의 조회 방식이나 관리 모델 또는 그 밖의 설계가 어떻게 발전하든 유효합니다.

3. CrossOriginStorageManager 인터페이스

[Exposed=(Window,Worker), SecureContext]
interface CrossOriginStorageManager {
  Promise<FileSystemFileHandle> getFileHandle(
      CrossOriginStorageGetFileHandleHash hash,
      optional CrossOriginStorageGetFileHandleOptions options = {});
};

dictionary CrossOriginStorageGetFileHandleHash {
  required DOMString value;
  required DOMString algorithm;
};

dictionary CrossOriginStorageGetFileHandleOptions {
  boolean create = false;
  (DOMString or sequence<DOMString>) origins;
};

interface mixin NavigatorCrossOriginStorage {
  [Exposed=(Window,Worker), SameObject, SecureContext]
  readonly attribute CrossOriginStorageManager crossOriginStorage;
};
Navigator includes NavigatorCrossOriginStorage;
WorkerNavigator includes NavigatorCrossOriginStorage;

각 Navigator 및 WorkerNavigator 객체에는 연결된 CrossOriginStorageManager 객체가 있습니다. crossOriginStorage 게터의 단계에서 반환하는 값은 this에 연결된 CrossOriginStorageManager입니다.

각 CrossOriginStorageManager 객체에는 연결된 출처가 있으며, 그 값은 this의 관련 설정 객체의 출처로 설정됩니다. 또한 연결된 파티션의 값은 COS 파티션으로 설정되며, 이는 this의 관련 설정 객체에 속한 파티션입니다. 두 값은 모두 객체를 생성할 때 설정됩니다.

참고: 출처를 관련 설정 객체에서 가져오고 스크립트 자체의 특성에는 의존하지 않는다는 점은 워커에서 특히 중요합니다. blob: URL로 생성한 워커의 출처는 해당 워커를 생성한 컨텍스트의 출처이므로, 그 출처와 정확히 같은 교차 출처 저장소 내용을 볼 수 있습니다. 워커가 기록한 내용은 워커를 생성한 페이지에서 다시 읽을 수 있고, 페이지가 저장한 내용은 워커에서 읽을 수 있습니다. blob: URL 자체가 별개의 출처인 것은 아니며, 이 URL을 폐기해도 워커에서 볼 수 있는 내용은 달라지지 않습니다. data: URL로 생성한 워커의 출처는 불투명한 출처입니다. 이 명세는 현재 getFileHandle()이 호출하는 출처가 불투명할 때 어떻게 동작하는지 정의하지 않습니다. COS 요청 검증의 출처 규칙은 호출자가 지정하는 출처에만 적용됩니다. 불투명한 출처에는 저장 출처의 키 또는 동일 사이트 비교의 기준으로 삼을 안정적인 식별자가 없으므로, 해당 출처에 권한을 부여해도 의미가 없습니다.

3.1. getFileHandle() 메서드

handle = await navigator . crossOriginStorage . getFileHandle(hash)

hash로 식별되는 파일의 핸들을 반환합니다. 파일이 존재하고 공개할 수 있어야 하는데, 이때 파일은 교차 출처 저장소에 있고 호출 출처에 공개할 수 있어야 합니다. 그렇지 않으면 "NotFoundError" DOMException으로 거부됩니다. "NotFoundError"는 해당 파일이 교차 출처 저장소에 물리적으로 없다는 증거가 아닙니다. § 8.4 가용성 제한을 참조하세요. 호출자는 이를 "대신 네트워크에서 이 파일을 가져오라"는 의미로 처리할 수 있습니다.

handle = await navigator . crossOriginStorage . getFileHandle(hash, { create: true })

hash로 식별되는 파일을 쓸 수 있는 핸들을 반환합니다. 파일을 쓸 위치는 교차 출처 저장소이며, 항목이 아직 없으면 새로 생성합니다. 기본 공개 범위는 동일 사이트의 출처로 제한됩니다. 호출자는 파일 내용 전체를 핸들의 createWritable() 메서드로 써야 합니다. 이는 항목이 이미 존재했는지와 무관합니다. 이때 사용자 에이전트는 기록한 바이트의 해시가 hash인지 검증하며, 일치하지 않으면 "DataError" DOMException으로 거부합니다. 이 요구 사항은 출처가 생성 요청을 통해 hash가 이미 있었는지 알아내는 일을 방지합니다.

handle = await navigator . crossOriginStorage . getFileHandle(hash, { create: true, origins: "*" })

위와 같으며, 추가로 항목을 쓴 후에는 어느 출처든 해당 출처의 hash 요청이 § 8.4 가용성 제한을 통과하면 그 출처에 항목을 공개할 수 있습니다.

handle = await navigator . crossOriginStorage . getFileHandle(hash, { create: true, origins: ["https://a.example", "https://b.example"] })

위와 같으며, 공개 범위는 열거된 출처 및 그 각각과 동일 사이트인 출처로 제한됩니다(호출 출처와 이미 저장 출처에 포함된 모든 출처 및 이들과 동일 사이트인 출처도 포함합니다).

getFileHandle(hash, options) 메서드의 단계는 다음과 같습니다.

  1. result를 새 프로미스로 설정합니다.

  2. realm을 this의 관련 렐름으로 설정합니다.

  3. global을 this의 관련 전역 객체로 설정합니다.

  4. origin을 this에 연결된 출처로 설정합니다.

  5. partition을 this의 파티션으로 설정합니다.

  6. 교차 출처 저장소 권한 확인에 global을 전달하여 실행한 결과가 false이면 다음을 수행합니다.

    1. 전역 작업을 큐에 추가합니다. 이때 DOM 조작 작업 소스와 global을 사용합니다. 이 작업이 거부할 프로미스는 result이며 거부 사유는 "NotAllowedError" DOMException입니다.

    2. result를 반환합니다.

  7. validationFailure를 COS 요청 검증에 hash와 options를 전달하여 실행한 결과로 설정합니다.

  8. validationFailure가 null이 아니면 다음을 수행합니다.

    1. 전역 작업을 큐에 추가합니다. 이때 DOM 조작 작업 소스와 global을 사용합니다. 이 작업이 거부할 프로미스는 result이며 거부 사유는 validationFailure입니다.

    2. result를 반환합니다.

  9. 다음 단계를 큐에 추가합니다. 이때 사용하는 큐는 교차 출처 저장소 큐입니다.

    1. options["create"]가 true이면 다음을 수행합니다.

      1. 생성 요청 완료를 실행합니다. 인수는 result, hash, options, global, realm입니다.

    2. 그렇지 않으면 다음을 수행합니다.

      1. 읽기 요청 완료를 실행합니다. 인수는 result, hash, origin, partition, global, realm입니다.

  10. result를 반환합니다.

COS 요청 검증에서는 주어진 CrossOriginStorageGetFileHandleHash hash 및 CrossOriginStorageGetFileHandleOptions options를 바탕으로 null 또는 TypeError를 반환합니다.

  1. hash["algorithm"]가 해시 알고리즘의 이름으로서 [WEBCRYPTO]에서 인식하는 이름이 아니거나, ASCII 대소문자를 구분하지 않고 비교했을 때 "SHA-1"과 일치하면, 새로운 TypeError를 반환합니다.

    참고: SHA-1에는 충돌 저항성이 없습니다. COS 항목을 식별하는 키로는 해당 항목의 COS 해시만 사용하므로, SHA-1 충돌이 발생하면 한 출처의 바이트가 다른 출처의 읽기 요청에 반환될 수 있습니다. 이는 다른 출처가 요청한 바이트가 서로 달라도 다이제스트가 같은 경우입니다.

  2. hash["value"]가 다음 정규 표현식 /^[0-9a-f]{64}$/과 일치하지 않고 hash["algorithm"]가 ASCII 대소문자를 구분하지 않고 비교했을 때 "SHA-256"과 일치하면, 새로운 TypeError를 반환합니다.

    참고: 향후 해시 알고리즘에서는 예상 다이제스트 길이를 다르게 정의할 수 있습니다. 이 명세는 "SHA-256"에 대해서만 규범적 제약을 두며, 이는 모든 예제에서 이 알고리즘을 사용하는 것과 일치합니다.

  3. options["origins"]가 존재하고 그 값이 "*"가 아니면 다음을 수행합니다.

    1. candidates를 options["origins"]로 설정하고, 단일 문자열은 항목이 하나인 목록으로 취급합니다.

    2. candidates의 크기가 사용자 에이전트의 최대 출처 목록 길이보다 크면 새로운 TypeError를 반환합니다.

      참고: 이 상한은 candidates로 전달된 원래 목록에 적용되며, 파싱이나 중복 제거에 앞서 적용됩니다(요청된 출처 정규화 참조). 따라서 URL 파싱 횟수도 호출당 제한됩니다. 항목 수가 최대 출처 목록 길이보다 하나 많은 목록은 같은 출처만 반복하더라도 거부됩니다. 정규화하면 단일 출처가 되더라도 마찬가지입니다.

    3. 각 candidate에 대해 다음을 수행합니다. 순회할 목록은 candidates입니다.

      1. url을 기본 URL 파서를 실행한 결과로 설정합니다. 입력은 candidate입니다.

      2. url이 실패이면 새로운 TypeError를 반환합니다.

        참고: origins를 생략하거나 인수로 빈 목록을 전달하는 경우에만 동일 사이트 기본 범위를 요청합니다. 빈 문자열은 목록으로 취급되며, 그 유일한 후보는 파싱에 실패하므로 다른 유효하지 않은 출처와 마찬가지로 거부됩니다. 한편 선언적 통합에서 동일 사이트를 뜻하는 빈 값은( § 9 다른 명세와의 통합 참조) 해당 텍스트 구문의 특성이며 각 호스트 명세에서 정의합니다.

      3. url의 스킴이 "http"도 "https"도 아니거나, url의 출처가 잠재적으로 신뢰할 수 있는 출처가 아니면, 새로운 TypeError를 반환합니다.

        참고: 목록에 넣을 의미가 있는 출처는 직접 getFileHandle()을 호출할 수 있는 출처뿐입니다. API는 보안 컨텍스트에서만 노출되므로 https: 출처와 루프백 http: 출처(예: http://localhost)는 허용되며, 다른 호스트의 http: 출처, ws:, wss:, ftp: 및 출처가 불투명한 모든 스킴은 거부됩니다. 여기에는 chrome-extension:과 같은 확장 스킴도 포함됩니다.

  4. null을 반환합니다.

3.2. 파일 읽기

읽기 요청 완료 절차에는 프로미스 result, COS 해시 hash, 출처 origin, 사이트 partition, 전역 객체 global, 렐름 realm이 주어집니다. 단계는 다음과 같습니다.

  1. entry를 다음 조건에 맞는 COS 항목으로 설정합니다. 이 항목은 COS 레지스트리에 있으며, 항목의 hash와 같아야 할 값은 hash입니다. 해당 항목이 없으면 null로 설정합니다.

    참고: 다른 작성자가 요청했지만 아직 완료하지 않은 쓰기 작업은 COS 레지스트리에 없으므로, 해당 해시에 대해 entry는 null이며 이 알고리즘은 어느 출처도 기록한 적 없는 해시를 처리할 때와 똑같이 진행됩니다. 이 명세가 허용하는 모든 공개 여부는 아래의 가용성 제한 적용에서 결정합니다. 그보다 앞서 응답할 수 있는 분기는 없습니다. § 8.3 진행 중인 쓰기를 참조하세요.

  2. disclosableEntry를 가용성 제한 적용의 실행 결과로 설정합니다. 인수는 entry, origin, partition입니다.

  3. disclosableEntry가 null이면 다음을 수행합니다.

    1. 전역 작업을 큐에 추가합니다. 이때 DOM 조작 작업 소스와 global을 사용합니다. 이 작업이 거부할 프로미스는 result이며 거부 사유는 "NotFoundError" DOMException입니다.

    2. 반환합니다.

  4. handle을 새 FileSystemFileHandle 생성 [FS]의 결과로 설정합니다. 핸들의 위치 지정자가 가리키는 것은 disclosableEntry의 hash이며, 그 위치는 교차 출처 저장소 파일 시스템 안입니다. 핸들을 생성하는 렐름은 realm입니다.

  5. handle의 COS 해시를 disclosableEntry의 hash로 설정합니다.

  6. handle의 COS 출처를 origin으로 설정합니다.

  7. handle의 읽기 가능 여부를 true로 설정합니다.

    참고: 이 핸들은 이미 가용성 제한 적용 절차를 통과했으므로, 호출한 출처에는 해당 항목의 바이트를 읽을 권한이 있습니다.

  8. 전역 작업을 큐에 추가합니다. 이때 DOM 조작 작업 소스와 global을 사용합니다. 이 작업이 결정할 프로미스는 result이며, 그 값은 handle입니다.

COS 공개 여부 결정 절차에는 COS 항목 또는 null인 entry, 출처 origin, 사이트 partition이 주어지며, 다음과 같이 COS 항목 또는 null을 반환합니다.

  1. entry가 null이면 null을 반환합니다.

    참고: COS 레지스트리의 항목은 언제나 쓰기와 검증이 끝난 상태이므로 이 알고리즘에서 고려해야 할 부분 기록 상태는 없습니다. 어떤 해시에 대한 유일한 쓰기 작업이 아직 진행 중이면 그 해시는 레지스트리에 없고 이 알고리즘에는 null로 전달됩니다. 이는 어느 출처도 기록한 적 없는 해시와 같습니다. § 8.3 진행 중인 쓰기를 참조하세요.

  2. firstParty는 다음과 같이 설정합니다. 사이트 구하기를 origin에 적용한 결과가 동일 사이트 관계를 partition과 이루면 true로, 그렇지 않으면 false로 설정합니다.

  3. entry의 저장 출처가 포함하는 COS 공유 레코드 중에서 다음 두 조건을 충족하는 레코드가 있는지 확인합니다. 레코드의 origin이 동일 사이트 관계를 origin과 이루고, 레코드의 partition이 동일 사이트 관계를 partition과 이루면 entry를 반환합니다.

    참고: 원래 저장한 출처와 직접 해당 항목 쓰기에 성공한 모든 출처는 쓰기를 수행한 최상위 사이트에서 언제나 해당 항목을 다시 읽을 수 있습니다. § 3.5.2 원래 저장한 출처의 접근을 참조하세요.

    참고: 모든 항목에 적용되는 동일 사이트 기본 범위(쓰기 시 별도의 origins 옵션 없이 요청하는 접근 범위)는 항상 유지됩니다. 이는 어떤 origins 목록이나 전역 범위를 나중에 추가하더라도 마찬가지입니다. 이 범위를 아래의 공개 해시 목록 조건보다 먼저 검사하므로, 동일 사이트의 출처는 항목을 읽을 수 있습니다. 항목의 hash가 PHL에 포함되는지는 관계없습니다. 여기서 동일 사이트는 하나의 신뢰 단위이므로, 이렇게 해도 사이트 경계를 넘어 공개되는 정보는 없습니다. 이 경계는 § 8.2 사이트 간 탐색에서 보호하는 경계입니다.

  4. entry의 origins가 포함하는 COS 공유 레코드 중에서 다음 조건을 충족하는 레코드가 있는지 확인합니다. 레코드의 origin이 동일 사이트 관계를 origin과 이루어야 하며, 추가로 레코드의 partition이 동일 사이트 관계를 partition과 이루거나, 레코드의 first-party와 firstParty가 모두 true여야 합니다. 그런 레코드가 있으면 entry를 반환합니다.

    참고: 명시적인 origins 목록에 있는 출처나 그중 하나와 동일 사이트인 출처는 항목을 읽을 수 있으며, 해당 항목이 PHL에 포함될 필요는 없습니다. 목록에 있는 각 출처에서 해당 사이트 전체로 범위를 넓히는 것은 위의 동일 사이트 기본 범위와 일치합니다. 동일 사이트의 출처들은 하나의 신뢰 단위이므로, 사이트의 출처 하나를 지정하면 모두를 지정한 셈입니다. 저장 출처는 공개 범위를 한정하기 위해 해당 출처를 지정했습니다(§ 3.5 리소스 공개 범위 확대 및 § 7 Cross-Origin-Storage-Allow-Origin 헤더 참조). 여기에 별도로 전역적인 보급 수준까지 요구하면 일반적인 제한 공유가 그와 무관한 공개 선별 절차에 의존하게 되며, 그 대상은 독점 리소스인 경우가 많습니다. 이 조건을 먼저 검사하고 그 뒤에 전역 공개 가능 조건을 검사해야 나중에 전역 가용성을 요청하는 쓰기 작업을 수행하더라도 목록에 있는 출처의 접근 권한이 취소되지 않습니다. § 8.2 사이트 간 탐색을 참조하세요.

  5. entry의 전역 공개 가능이 true이면 다음을 수행합니다.

    1. entry의 hash가 PHL에 포함되지 않으면 null을 반환합니다.

      참고: 공개 해시 목록 조건은 전역 범위에만 적용됩니다. 이 조건이 없을 때 웹상의 어떤 출처에든 공개될 수 있는 경우는 전역 범위뿐입니다. 항목이 전역 공개 가능하더라도 그 hash가 PHL에 포함되지 않으면 이 범위를 통해서만 자격을 얻는 출처에는 공개되지 않습니다. 출처가 그 밖에도 다음 중 하나에 해당한다면, 즉 저장 출처, 명시적인 origins 목록 또는 이들 중 하나와 동일 사이트인 출처 집합에 속한다면 위 단계에서 이미 항목을 반환했습니다.

    2. 사용자 에이전트가 이 요청에 GREASE 적용을 선택하면 null을 반환합니다.

      참고: GREASE 역시 전역 범위에만 적용됩니다. 위에서 검사한 레코드는 이 단계에 도달하지 않습니다. 저장 출처와 그 출처와 동일 사이트인 출처들은 하나의 신뢰 단위이며, 명시적인 origins 목록에 있는 출처는 작성자가 의도적으로 지정했고 그 작성자의 Cross-Origin-Storage-Allow-Origin 헤더가 허용한 출처입니다. 이 허용 범위에는 해당 출처와 동일 사이트인 출처도 포함됩니다.

    3. entry를 반환합니다.

  6. null을 반환합니다.

가용성 제한 적용 절차에는 COS 항목 또는 null인 entry, 출처 origin, 사이트 partition이 주어지며, 다음과 같이 COS 항목 또는 null을 반환합니다.

  1. 다음 두 조건을 모두 충족하는지 확인합니다. 예산 차감 대상에서 제외되는지 판정하는 절차에 entry, origin, partition을 주어 실행한 결과가 false이고, 사이트 간 조회 예산 차감 절차에 partition을 주어 실행한 결과도 false이면 null을 반환합니다.

    참고: 예산 초과로 거부된 조회는 null을 반환하며, 읽기 요청 완료 절차는 이를 동일한 "NotFoundError" DOMException으로 바꿉니다. 항목을 찾지 못했을 때와 결과도 소요 시간도 같습니다. 차감 대상인 조회는 항목을 찾았는지와 관계없이 예산에서 차감합니다. 항목을 찾지 못한 경우에도 찾은 경우만큼 많은 정보가 드러나기 때문입니다.

  2. COS 공개 여부 결정 절차에 entry, origin, partition을 주어 실행한 결과를 반환합니다.

3.2.1. 사이트 간 조회 예산

모든 사이트에는 사이트 간 조회 예산이 있습니다. 이 예산은 구조체이며, 다음 항목을 가집니다. count는 음이 아닌 정수이며 초깃값은 0입니다. 기간 시작 시점은 시점 또는 null이며 초깃값은 null입니다. 이 예산은 사용자가 방문 중인 최상위 사이트에 속하므로, 한 페이지의 모든 프레임과 그 프레임들이 불러오는 모든 출처는 같은 예산을 사용합니다.

사용자 에이전트에는 구현에서 정의하는 최대 사이트 간 조회 횟수가 있습니다. 이는 작은 양의 정수입니다. 또한 구현에서 정의하는 조회 기간이 있으며, 이는 시간의 길이입니다.

참고: 조회 예산을 약 8~16회로 설정하고 조회 기간을 일주일 정도로 잡으면, 추적기가 한 기간에 얻는 정보량은 사이트 간 식별자에 필요한 약 32비트에 크게 못 미치면서도 사이트에는 실제로 사용하는 공유 파일을 조회할 기회가 충분히 남습니다.

사용자 에이전트는 각 사이트의 사이트 간 조회 예산을 페이지가 다시 로드되어도 유지하고, 사용자의 모든 최상위 탐색 가능 객체에 걸쳐 유지해야 합니다. 따라서 페이지를 새로 고치거나 새 탭에서 열어도 예산이 초기화되지 않습니다. 사용자 에이전트는 사이트의 예산을 초기 상태로 되돌려야 합니다. 이는 사용자가 해당 사이트의 데이터를 사용자 에이전트 자체 설정이나 저장소 인터페이스를 통해 삭제할 때 적용됩니다. 사이트가 직접 유발할 수 있는 동작에 대한 응답으로 예산을 초기화해서는 안 됩니다. Clear-Site-Data 응답 헤더가 그 예입니다.

조회가 예산 차감 대상에서 제외되는지 판정하려면 다음 입력을 사용합니다. COS 항목 또는 null인 entry, 출처 origin, 그리고 사이트 partition입니다.

  1. entry가 null이면 false를 반환합니다.

  2. entry의 저장 출처가 포함하는 COS 공유 레코드 중에서 origin이 동일 사이트 관계를 origin과 이루고, partition이 동일 사이트 관계를 partition과 이루는 레코드가 있으면 true를 반환합니다.

  3. entry의 origins가 포함하는 COS 공유 레코드 중에서 origin이 동일 사이트 관계를 origin과 이루고, partition이 동일 사이트 관계를 partition과 이루는 레코드가 있으면 true를 반환합니다.

  4. false를 반환합니다.

참고: 이러한 조회에는 공유 레코드를 사용하여 응답합니다. 이 레코드는 읽는 주체 자신의 최상위 사이트에서 작성되었으므로 다른 사이트가 저장한 내용은 전혀 드러나지 않습니다. 그 밖의 모든 조회는 예산에서 차감합니다. 일치하는 항목이 없는 조회, 전역 범위를 통해 응답한 조회, 그리고 first-party origins 레코드를 사용하여 응답한 조회 중 그 레코드가 다른 최상위 사이트에서 작성된 경우도 포함됩니다.

사이트 간 조회 예산 차감에서는 주어진 사이트 partition에 대해 다음과 같이 불리언을 반환합니다.

  1. budget을 partition의 사이트 간 조회 예산으로 설정합니다.

  2. now를 사용자 에이전트가 세션 간에 유지하는 시계의 현재 시각으로 설정합니다.

  3. budget의 기간 시작 시점이 null이 아니고 now가 그 시점으로부터 적어도 조회 기간만큼 지난 시점이라면, budget의 count를 0으로 설정하고 기간 시작 시점을 null로 설정합니다.

  4. budget의 count가 사용자 에이전트의 최대 사이트 간 조회 횟수 이상이면 false를 반환합니다.

  5. budget의 기간 시작 시점이 null이면, 그 값으로 now를 설정합니다.

  6. budget의 count를 1 증가시킵니다.

  7. true를 반환합니다.

어떤 호스트 통합 기능을 통한 조회든 가용성 제한 적용 단계에 도달하는 방식은 getFileHandle() 호출과 같으므로 동일한 조건으로 예산에서 차감합니다. 예산에는 이들 조회가 모두 함께 집계됩니다.

3.3. 파일 생성 및 쓰기

FileSystemFileHandle이 생성 요청 완료를 통해 생성되면 이 핸들에는 연결된 요청된 출처가 있습니다. 이는 검증 및 저장 단계에서 확대를 시도할 때 항목의 origins에 적용하려는 값으로, 핸들을 통한 쓰기가 성공하면 이러한 확대를 시도합니다.

모든 FileSystemFileHandle 중 교차 출처 저장소 파일 시스템을 가리키는 핸들에는 연결된 COS 해시도 있습니다. 이는 핸들이 가리키는 COS 해시입니다. 또한 핸들에 연결된 COS 출처는 이 핸들을 얻은 출처입니다. 마지막으로 핸들에 연결된 읽기 가능 여부 불리언은 getFile()이 해당 핸들을 통해 그 핸들이 가리키는 항목의 바이트를 공개할 수 있는지 결정합니다. 이 값이 true로 설정되는 경우는 읽기 요청 완료에서 핸들을 반환할 때입니다. 이 핸들은 이미 가용성 제한을 통과했습니다. 반면 생성 요청 완료에서 반환한 핸들에서는 검증 및 저장이 바로 그 핸들에 대해 성공할 때까지 이 값이 false입니다.

참고: 핸들이 가리키는 것은 COS 해시이며, COS 항목이 아닙니다. 생성 요청 완료는 해당 해시에 대한 항목이 COS 레지스트리에 없고 앞으로도 생기지 않을 수 있는 경우에도 핸들을 반환합니다. 따라서 핸들이 참조할 항목은 검증 및 저장이 항목을 생성해야 비로소 존재합니다.

참고: 이 속성은 의도적으로 개별 핸들에 둡니다. 생성 요청은 해당 해시의 항목이 이미 존재하는지와 관계없이 핸들을 반환합니다( 생성 요청 완료 참조). 따라서 항목별로 규칙을 적용하면 어느 출처든 getFileHandle()을 다음 인수, 즉 create: true로 호출한 직후 자신이 한 번도 쓰지 않은 항목을 읽을 수 있게 됩니다. 그러면 origins, PHL 포함 여부 또는 GREASE 적용 조건을 충족하지 않고도 그 내용을 알 수 있습니다. 이 명세의 모든 공개 제어는 읽기 경로에 적용되므로, 항목별로 제한하면 생성 요청이 이러한 제어를 모두 우회할 수 있습니다. 호출자가 먼저 올바른 바이트를 제공하도록 요구하면 생성 요청으로 얻은 핸들을 통해 읽기에 성공하더라도 호출자가 이미 가지고 있던 것 외에는 아무것도 드러나지 않습니다.

생성 요청 완료 절차에는 프로미스 result, COS 해시 hash, CrossOriginStorageGetFileHandleOptions options, 전역 객체 global, 그리고 렐름 realm이 주어집니다. 단계는 다음과 같습니다.

  1. requestedOrigins를 요청된 출처 정규화를 실행한 결과로 설정합니다. 입력은 options["origins"]입니다.

  2. requestedOrigins가 목록이면, requestedOrigins를 다음 알고리즘의 실행 결과로 설정합니다. COS 범위 상한 적용을 실행할 때 requestedOrigins와 다음 알고리즘의 실행 결과를 전달합니다. COS 범위 상한 구하기에 전달하는 입력은 global입니다.

  3. handle을 새 FileSystemFileHandle 생성 [FS]의 결과로 설정합니다. 이 핸들의 위치 지정자가 가리키는 대상은 hash이며, 그 위치는 교차 출처 저장소 파일 시스템 안입니다. 핸들을 생성할 렐름은 realm입니다.

  4. handle의 COS 해시를 hash로 설정합니다.

  5. handle의 COS 출처를 global의 관련 설정 객체의 출처로 설정합니다.

  6. handle의 요청된 출처를 requestedOrigins로 설정합니다.

  7. handle의 읽기 가능 여부를 false로 설정합니다.

    참고: 이 알고리즘은 COS 레지스트리를 조회하거나 수정하지 않습니다. 그 이유는 결과가 hash의 기존 저장 여부와 무관해야 하기 때문입니다. 그렇지 않으면 생성 요청 자체가 항목이 이미 존재했는지를 드러냅니다(§ 8.2 사이트 간 탐색 참조). 따라서 handle은 정확히 같은 조건으로 반환됩니다. 항목이 이미 존재하든, 한 번도 기록되지 않았든, 다른 작성자가 지금 기록 중이든 마찬가지이며, 이 호출자가 바이트를 제공할 때까지 핸들에는 읽기 권한이 없습니다.

    참고: 여기서는 아무것도 등록하지 않으므로 호출자가 핸들을 요청한 후 이를 버려서 한 번도 createWritable()을 호출하지 않거나 그 결과로 생성된 스트림을 끝내 닫지 않으면, 레지스트리는 요청 전의 상태를 그대로 유지합니다. 다른 출처에서는 요청이 발생했는지 관찰할 수 없으며, 이후 읽기를 차단하는 자리표시자 상태에 해시를 고정할 수도 없습니다. § 8.3 진행 중인 쓰기를 참조하세요.

    참고: requestedOrigins를 적용하는 것은 검증 및 저장뿐입니다. 이때 리소스 공개 범위 확대를 실행하는 시점은 바이트의 쓰기와 검증이 끝난 후입니다. 따라서 생성 요청으로 공개 범위를 넓히려면 먼저 모든 바이트를 제공해야 합니다. § 3.5 리소스 공개 범위 확대를 참조하세요.

  8. 전역 작업을 큐에 추가합니다. 이때 DOM 조작 작업 소스와 global을 사용합니다. 이 작업이 결정할 프로미스는 result이며, 그 값은 handle입니다.

요청된 출처 정규화는 (DOMString or sequence<DOMString>) 또는 undefined인 origins를 받아 "*", 목록(각 항목은 출처) 또는 null을 반환합니다.

  1. origins가 존재하지 않으면 null을 반환합니다.

  2. origins가 "*"이면 "*"를 반환합니다.

  3. list를 « »로 설정합니다.

  4. 각 candidate에 대해 origins를 순회합니다(단일 문자열은 목록으로 취급하며, 이때 항목은 하나입니다).

    1. candidateOrigin을 다음 출처로 설정합니다. 이 출처는 기본 URL 파서를 candidate에 실행하여 얻은 URL의 출처입니다.

      참고: COS 요청 검증 단계에서 각 candidate의 파싱 결과가 http: 또는 https: URL이고 그 출처가 잠재적으로 신뢰할 수 있는 출처임을 이미 확인했습니다.

    2. list가 포함하는 항목에 candidateOrigin이 없으면, 끝에 추가할 값으로 candidateOrigin을 사용하여 list에 추가합니다.

  5. list를 반환합니다.

참고: 이후 기존 항목에 병합하기에 앞서 여기서 중복을 제거하면 origins에는 항목이 처음 생성되는 순간부터 중복이 없으므로, 이후 이를 복제한 결과에도 중복이 없습니다.

다음 FileSystemWritableFileStream이 닫히는 경우를 고려합니다. 이 스트림은 createWritable()을 핸들에서 호출하여 얻으며, 해당 핸들의 위치 지정자는 교차 출처 저장소 파일 시스템을 가리킵니다 [FS]. 이때 사용자 에이전트는 아래의 검증 및 저장 단계를 해당 핸들에 대해 실행해야 하며, 이는 닫기 연산의 프로미스가 이행되기 전이어야 합니다.

참고: 이는 닫기가 어떤 방식으로 시작되었는지와 관계없이 적용됩니다. 명시적인 close() 호출일 수도 있고, pipeTo() 호출이 소스의 끝에 도달한 경우일 수도 있습니다. 후자의 경우 기본적으로 대상도 닫힙니다. [STREAMS]는 스트림이 닫히는 시점에 두 경우를 구분하지 않으며, 이 알고리즘도 마찬가지입니다.

검증 및 저장 단계에는 다음 입력이 주어집니다. 먼저 FileSystemFileHandle인 handle이며, 이 핸들의 스트림은 닫혔습니다. 나머지 입력은 기록된 전체 바이트 시퀀스 bytes와 닫기 연산의 관련 설정 객체 settings입니다. 단계는 다음과 같습니다.

  1. origin을 settings의 출처로 설정합니다.

  2. partition을 COS 파티션으로 설정합니다. 이 파티션은 settings의 것입니다.

  3. firstParty를 settings가 자사 COS 컨텍스트이면 true로, 그렇지 않으면 false로 설정합니다.

  4. hash를 handle의 COS 해시로 설정합니다.

  5. computedValue를 bytes의 소문자 16진수 다이제스트로 설정합니다. 이 값을 계산할 때 사용하는 알고리즘은 hash의 algorithm이 지정하며, 계산은 [WEBCRYPTO]를 따릅니다.

  6. computedValue가 hash의 value와 정확히 같지 않으면 다음을 수행합니다.

    1. 거부할 대상은 닫기 연산의 프로미스이며, 거부 사유는 "DataError" DOMException입니다.

    2. 이 단계를 중단합니다.

    참고: 쓰기가 실패하면 정리할 것이 없습니다. 생성 요청 완료 단계에서는 항목을 등록하지 않으므로, 검증된 바이트를 생성하지 못한 쓰기는 COS 레지스트리에 영향을 주지 않습니다. 이후에 getFileHandle()을 같은 해시로 호출하면 동일한 "NotFoundError"를 받습니다. 쓰기를 시도한 적이 없어도 받았을 오류입니다. 어떤 출처가 이미 기록한 항목도 마찬가지로 영향을 받지 않습니다. 이 알고리즘은 바이트와 공유 레코드를 추가하기만 합니다.

  7. 다음 단계를 큐에 추가합니다. 이때 사용하는 큐는 교차 출처 저장소 큐입니다.

    1. entry를 다음 조건에 맞는 COS 항목으로 설정합니다. COS 레지스트리에서 hash가 같은 항목을 찾되, 비교할 값은 hash입니다. 그런 항목이 없으면 null로 설정합니다.

    2. 다음 둘 중 하나가 성립하면 아래 단계를 수행합니다. COS 저장 한도 확인을 entry, origin 및 bytes의 길이로 실행한 결과가 false이거나, COS 쓰기 사용량 부과를 entry, origin, partition 및 bytes의 길이로 실행한 결과가 false인 경우입니다.

      1. 전역 작업을 큐에 추가합니다. 작업 소스로는 DOM 조작 작업 소스를, 전역 객체로는 settings의 전역 객체를 사용합니다. 이 작업이 거부할 대상은 닫기 연산의 프로미스이며, 거부 사유는 "QuotaExceededError" DOMException입니다.

      2. 이 단계를 중단합니다.

    3. entry가 null이면 다음을 수행합니다.

      1. entry를 새 COS 항목으로 설정합니다. 그 hash는 hash이고, bytes는 bytes이며, origins는 빈 목록이고, 전역 공개 가능은 false이며, 저장 출처는 빈 집합입니다.

      2. 설정할 대상은 COS 레지스트리[hash]이고, 값은 entry입니다.

      참고: 이 단계는 이 명세에서 항목을 추가하는 유일한 단계입니다. 항목은 COS 레지스트리에 추가되며, 이 단계는 bytes가 검증된 후에만 실행됩니다. 검증 기준은 hash입니다. 두 작성자가 모두 해당 해시가 없음을 확인하고 동시에 쓰기를 수행하면 각각 이 단계에 도달합니다. 둘 중 어느 쪽이든 두 번째로 큐에 들어간 쪽은 첫 번째가 만든 항목을 발견하고 아래 단계에서 자신의 출처와 레코드만 추가합니다. 양쪽의 바이트는 같은 해시값을 가지므로 한 번만 저장하면 됩니다.

    4. 추가할 COS 공유 레코드는 그 origin이 origin이고, partition이 partition이며, first-party가 firstParty인 레코드입니다. 이를 entry의 저장 출처에 추가하되, 동등한 레코드가 이미 있으면 추가하지 않습니다.

    5. 리소스 공개 범위 확대를 실행합니다. 인수는 entry, handle의 요청된 출처, partition, firstParty 및 settings의 전역 객체입니다.

    6. handle의 읽기 가능 여부를 true로 설정합니다.

      참고: 읽을 수 있게 되는 것은 이 핸들 하나뿐입니다. 같은 해시에 대해 다른 핸들을 얻었더라도, 그 핸들이 별도의 생성 요청에서 반환되었고 그 핸들로 쓰기를 수행한 적이 없다면 여전히 읽을 수 없습니다.

createWritable()을 호출할 때 대상인 FileSystemFileHandle이 가리키는 곳이 교차 출처 저장소 파일 시스템이면, 생성해야 하는 것은 FileSystemWritableFileStream이며, 그 내용은 처음에 비어 있어야 합니다. 이는 keepExistingData의 값과 무관하며, 대상 COS 해시에 해당하는 항목이 COS 레지스트리에 있는지와도 무관합니다.

참고: [FS]에서는 일반적으로 keepExistingData가 기존 파일의 내용으로 스트림을 초기화하도록 정의합니다. 여기서도 이를 적용하면 호출자가 보유한 적이 없는 바이트의 저장 출처가 될 수 있습니다. 생성 요청은 해당 항목이 이미 존재하는지와 무관하게 핸들을 반환합니다. 따라서 항목이 이미 존재한다면 다른 출처가 저장한 해시의 쓰기 가능 스트림을 열었을 때, 그 스트림에 아무것도 쓰지 않고 닫더라도 이월된 바이트의 해시가 요청한 값과 일치할 수 있습니다. 그러면 읽기 접근이 허용되면서도 origins, 공개 해시 목록 및 GREASE 적용은 전혀 참조되지 않습니다. 이는 가용성 제한을 우회하는 것으로, 개별적으로 허용되는 두 연산을 조합할 때 생기는 문제입니다. 같은 이유로 검증 및 저장은 생성 요청마다 전체 내용을 요구합니다.

참고: 따라서 아무것도 쓰지 않고 닫은 쓰기 가능 스트림에는 빈 바이트 시퀀스가 들어 있습니다. 이 시퀀스의 해시값은 호출자가 원하는 항목의 요청된 값과 일치하지 않으므로 검증 및 저장은 프로미스를 거부하며, 거부 사유는 "DataError" DOMException입니다. 이는 다른 모든 불일치를 처리하는 방식과 같습니다. 구현이 이 경우에 저장소 또는 I/O 오류를 대신 보고하면 검증 결과가 관련 없는 오류에 가려집니다.

파일 시스템 표준 [FS]에는 아직 이 표준에 의존하는 명세가 쓰기별 검증을 추가할 수 있는 확장점이 없습니다. 검증을 추가할 위치는 FileSystemWritableFileStream의 닫기 단계입니다. 그러한 확장점이 마련될 때까지는 이 절에서 필요한 동작을 직접 설명합니다. 향후 개정판에서는 [FS]와 정식으로 통합할 예정입니다.

3.4. 가져온 리소스 저장

§ 9 다른 명세와의 통합에 열거된 호스트 통합 기능은 가져온 리소스를 저장할 때 다음 인터페이스를 거치지 않습니다. FileSystemFileHandle입니다. 각 호스트 명세에서는 가져온 바이트가 해당 통합 기능에서 요구하는 무결성 검사를 통과하면 다음 알고리즘을 실행할 것으로 기대됩니다.

가져온 리소스를 교차 출처 저장소에 저장하는 절차에는 응답 response, 바이트 시퀀스 bytes, COS 해시 hash, "*" 또는 목록(각 항목은 문자열) 또는 null인 origins, 그리고 환경 설정 객체 settings가 주어집니다. 단계는 다음과 같습니다.

  1. 교차 출처 저장소 권한 확인에 settings의 전역 객체를 전달하여 실행한 결과가 false이면 반환합니다.

  2. options의 값은 «[ "origins" → origins ]»로 설정하되, 이는 origins가 null이 아닐 때이며, 그렇지 않으면 «[ ]»로 설정합니다.

  3. COS 요청 검증에 hash와 options를 전달하여 실행한 결과가 null이 아니면 반환합니다.

  4. computedValue를 bytes의 소문자 16진수 다이제스트로 설정합니다. 이 값을 계산할 때 사용하는 알고리즘은 hash의 algorithm이 지정하며, 계산은 [WEBCRYPTO]를 따릅니다.

  5. computedValue가 hash의 value와 정확히 같지 않으면 반환합니다.

    참고: 통합 기능 자체의 무결성 메타데이터에는 여러 다이제스트가 나열될 수 있으며, 그중 하나만 일치해도 무결성 검사를 통과합니다. 이 단계에서는 항목의 키가 바로 이 바이트들로 계산한 해시인지 확인합니다.

  6. requestedOrigins를 요청된 출처 정규화를 실행한 결과로 설정합니다. 입력은 options["origins"]입니다.

  7. requestedOrigins가 목록이면 다음을 수행합니다.

    1. internalResponse의 값은 response의 내부 응답으로 설정하되, 이는 response가 필터링된 응답일 때입니다. response 자체를 사용하는 경우는 그 밖의 경우입니다.

    2. requestedOrigins를 COS 범위 상한 적용을 실행한 결과로 설정합니다. 인수는 requestedOrigins와 COS 범위 상한 파싱의 실행 결과입니다. 파싱할 대상은 internalResponse의 헤더 목록입니다.

    참고: 상한은 가져온 리소스 자체의 응답에서 가져오므로, 바이트를 제공하는 서버가 그 바이트를 어느 출처에 공개할 수 있는지 결정합니다. 리소스를 로드하는 Document의 COS 범위 상한은 관여하지 않습니다. 문서 운영자는 해당 리소스를 통제하지 않으며, 문서 운영자가 수신 대상을 승인할 수 있다면 어떤 사이트든 다른 사이트의 리소스를 자신이 선택한 출처와 공유할 수 있다고 선언할 수 있기 때문입니다. 사용자 에이전트는 내부 응답에서 헤더를 읽으므로 불투명한 필터링된 응답에서도 이 절차가 작동하며, 헤더는 페이지에 노출되지 않습니다.

  8. origin을 settings의 출처로 설정합니다.

  9. partition을 COS 파티션으로 설정합니다. 이 파티션은 settings의 것입니다.

  10. firstParty를 settings가 자사 COS 컨텍스트이면 true로, 그렇지 않으면 false로 설정합니다.

  11. 다음 단계를 큐에 추가합니다. 이때 사용하는 큐는 교차 출처 저장소 큐입니다.

    1. entry를 다음 조건에 맞는 COS 항목으로 설정합니다. COS 레지스트리에서 hash가 같은 항목을 찾되, 비교할 값은 hash입니다. 그런 항목이 없으면 null로 설정합니다.

    2. COS 저장 한도 확인을 entry, origin 및 bytes의 길이로 실행한 결과가 false이거나, COS 쓰기 사용량 부과를 entry, origin, partition 및 bytes의 길이로 실행한 결과가 false이면 이 단계를 중단합니다.

    3. entry가 null이면 다음을 수행합니다.

      1. entry를 새 COS 항목으로 설정합니다. 그 hash는 hash이고, bytes는 bytes이며, origins는 빈 목록이고, 전역 공개 가능은 false이며, 저장 출처는 빈 집합입니다.

      2. 설정할 대상은 COS 레지스트리[hash]이고, 값은 entry입니다.

      참고: 검증 및 저장과 마찬가지로, 항목은 bytes가 검증된 후에만 생성됩니다. 검증 기준은 hash이며, 이 검증은 통합 기능의 integrity 검사에서 이미 수행했습니다. getFileHandle()을 사용해 같은 해시에 대해 쓰기를 진행 중인 작성자는 영향을 받지 않습니다. 이 작성자에게는 레지스트리 상태가 없으며, 자체 검증 및 저장은 정상적으로 완료됩니다. 이때 해당 항목을 찾아 자신의 출처와 공유 레코드를 그 항목에 추가합니다.

    4. 추가할 COS 공유 레코드는 그 origin이 origin이고, partition이 partition이며, first-party가 firstParty인 레코드입니다. 이를 entry의 저장 출처에 추가하되, 동등한 레코드가 이미 있으면 추가하지 않습니다.

    5. 리소스 공개 범위 확대를 실행합니다. 인수는 entry, requestedOrigins, partition, firstParty 및 settings의 전역 객체입니다.

참고: 검증 및 저장과 마찬가지로, 저장하려면 언제나 전체 바이트가 필요합니다. 해당 해시의 항목이 이미 존재할 때도 마찬가지이므로, 저장 작업은 항목이 이미 존재했는지를 드러내지 않습니다. 통합 기능이 네트워크에서 가져오기에 앞서 수행하는 조회는 읽기이므로 가용성 제한과 § 8.2 사이트 간 탐색의 탐색 관련 고려 사항이 적용됩니다.

3.5. 리소스 공개 범위 확대

COS 항목의 공개 범위는 확대할 수 있지만 축소할 수는 없습니다.

리소스 공개 범위 확대 절차에는 COS 항목 entry, "*" 또는 목록(각 항목은 출처) 또는 null인 requestedOrigins, 사이트 partition, 불리언 firstParty, 그리고 전역 객체 global이 주어집니다. 단계는 다음과 같습니다.

  1. requestedOrigins가 null이면 반환합니다.

    참고: origins를 생략하면 동일 사이트에서만 사용할 수 있도록 요청합니다. 모든 항목에 이미 이 범위가 적용되므로(COS 공개 여부 결정 참조) 추가할 것이 없습니다.

  2. requestedOrigins가 "*"이면 다음을 수행합니다.

    1. entry의 hash가 PHL에 포함되지 않으면, 사용자 에이전트는 콘솔에 경고를 기록하거나 개발자 도구에 문제를 보고할 것으로 기대됩니다. 경고나 보고에는 해당 항목을 읽을 수 있는 출처가 동일 사이트의 출처와 해당 항목의 origins 목록에 있는 출처뿐이라고 명시합니다.

      참고: 쓰기 자체는 성공하므로, 메시지가 없으면 개발자는 전역 범위가 적용되지 않았음을 알 방법이 없습니다. § 8.5 개발자 지침을 참조하세요.

    2. entry의 전역 공개 가능이 true이면 반환합니다.

    3. global이 COS 사용자 활성화 상태이면, entry의 전역 공개 가능을 true로 설정합니다.

    4. 그렇지 않으면 추가할 값은 entry이며, 이를 partition의 전역 공개 대기 항목에 추가합니다.

    5. 반환합니다.

    참고: 이 단계에서는 전역 범위를 추가하며, entry의 origins는 수정하지 않습니다. 항목에 이미 명시적인 origins 목록이 있으면 그 목록이 유지됩니다. 따라서 모든 출처는 해당 목록에 있는 한 PHL과 무관한 접근 권한을 유지하며, 이는 항목이 전역 공개 가능이 된 후에도 마찬가지입니다. 이것이 두 범위를 별도로 저장하는 주된 이유입니다. 전역 공개 가능을 참조하세요.

  3. 각 candidateOrigin에 대해 다음을 수행합니다. 순회할 목록은 requestedOrigins입니다.

    1. record를 다음 COS 공유 레코드로 설정합니다. 그 origin은 candidateOrigin이고, partition은 partition이며, first-party는 firstParty입니다.

    2. entry의 origins가 포함하는 레코드 중 record와 동등한 레코드가 있으면 다음 반복으로 넘어갑니다.

    3. entry의 origins의 크기가 사용자 에이전트의 최대 출처 목록 길이와 같으면 반복을 중단합니다.

      참고: 남은 candidateOrigin 값은 이번 확대에서 별도 오류 없이 제외됩니다. 쓰기 자체는 이미 성공했기 때문이며, 사용자 에이전트는 콘솔에 해당 항목의 출처 목록이 최대 길이에 도달했다는 경고를 기록할 것으로 기대됩니다.

    4. 끝에 추가할 값은 record이며, 이를 entry의 origins에 추가합니다.

참고: 공개 범위를 확대할 때는 origins에 추가하거나 전역 공개 가능을 true로 설정하기만 합니다. 작성자가 목록을 요청하면 이미 전역 공개 가능인 항목의 공개 범위도 그렇지 않은 항목과 같은 방식으로 넓어집니다. 두 범위가 서로 독립적이기 때문입니다. 새로 목록에 추가된 출처는 PHL과 무관한 접근 권한을 얻으며, 전역 범위도 계속 적용됩니다.

참고: 원래 저장한 사이트 이외의 사이트를 포함하여 어느 사이트든 항목의 origins를 확대할 수 있습니다. 단, 해당 사이트도 해시값이 항목의 hash와 일치하는 바이트를 제공해야 합니다. 이는 의도한 동작입니다. 특정 해시에 맞는 바이트를 이미 보유한 사이트라면, 설계상 그 해시가 어떤 바이트를 가리키는지에 관해서는 원래 저장한 사이트와 동등한 권한을 갖습니다.

3.5.1. 사용자 활성화 조건

COS 사용자 활성화 조건은 쓰기 작업의 전역 범위 적용을 보류합니다. 이는 사용자가 쓰기가 수행된 사이트의 페이지와 상호작용할 때까지입니다. 쓰기를 수행한 페이지는 항목을 즉시 읽을 수 있습니다. 이때 사용하는 것은 해당 페이지의 저장 출처 레코드입니다. 동일 사이트의 출처 및 명시적인 origins 목록에 있는 출처도 마찬가지입니다. 이 목록은 작성자가 자신의 Cross-Origin-Storage-Allow-Origin 헤더로 승인했으며, 이들 출처도 항목을 즉시 읽을 수 있습니다.

모든 사이트에는 전역 공개 대기 항목이 있습니다. 이는 집합으로, COS 항목으로 구성되며 처음에는 비어 있습니다.

사용자 에이전트가 활성화 알림을 Window window에 대해 실행할 때마다 [HTML], 다음 단계를 큐에 추가해야 합니다. 이때 사용하는 큐는 교차 출처 저장소 큐입니다.

  1. partition을 COS 파티션으로 설정합니다. 이 파티션은 window의 관련 설정 객체의 것입니다.

  2. 각 entry에 대해 partition의 전역 공개 대기 항목을 순회하며, entry의 전역 공개 가능을 true로 설정합니다.

  3. 비우기를 partition의 전역 공개 대기 항목에 수행합니다.

참고: 다른 사이트가 팝업으로 연 페이지가 몇 초 만에 닫히거나 일련의 과정에서 연달아 다시 로드되면 사용자 활성화를 받지 못하므로, 그 페이지가 기록한 파일은 다른 사이트에 보이지 않습니다. 이 쓰기 작업의 결과가 전역 공개 가능해지는 시점은 사용자가 해당 사이트의 페이지와 실제로 상호작용할 때이며, 같은 방문 중일 수도 있고 이후 방문 중일 수도 있습니다. 퇴거된 항목은 모든 전역 공개 대기 항목 집합에서도 제거됩니다.

전역 객체 global이 COS 사용자 활성화 상태인 조건은 다음과 같습니다. global이 Window 객체이고 이 객체에 지속적 활성화가 있거나, global이 DedicatedWorkerGlobalScope 객체이고 해당 객체의 소유자 중 하나의 관련 전역 객체가 COS 사용자 활성화 상태입니다.

참고: 전용 워커는 자신을 소유한 페이지를 대신하여 동작하므로 해당 페이지의 활성화 상태를 따릅니다. 이는 교차 출처 저장소 권한 확인에서 해당 페이지의 정책을 따르는 것과 같습니다. 공유 워커의 소유자는 생기기도 하고 사라지기도 하므로, 공유 워커의 전역 범위 쓰기 작업은 동일한 최상위 사이트의 페이지에서 다음 활성화가 일어날 때까지 기다립니다.

3.5.2. 원래 저장한 출처의 접근

어떤 출처가 성공적으로 쓰기를 완료한 COS 항목이 있으면(즉, 해당 출처가 레코드의 origin이고 그 레코드가 항목의 저장 출처에 있으면), 그 출처는 언제든지 이후에 해당 항목의 핸들을 얻을 수 있습니다. 이때 getFileHandle()을 호출하는 곳은 동일한 최상위 사이트이며, 이는 항목의 origins 값이나 항목의 hash가 PHL에 포함되는지와 무관합니다. 이는 Cache API의 모델과 같습니다. 이 모델에서는 출처가 자신이 저장한 내용에 언제나 접근할 수 있으며, 저장소 분할 시 Cache API에도 최상위 사이트를 키로 사용합니다. 다른 최상위 사이트에서는 해당 출처도 여느 출처와 같은 조건으로 항목을 읽습니다.

4. 교차 출처 저장소 파일 시스템

교차 출처 저장소 파일 시스템은 파일 시스템 루트로, 어느 출처의 버킷 파일 시스템이나 로컬 파일 시스템 접근 루트와도 구별됩니다. 그 항목은 각각 COS 레지스트리의 COS 항목과 일대일로 대응합니다.

교차 출처 저장소 파일 시스템은 [FS]의 일반적인 호출별 권한 검사 모델을 사용하지 않습니다. 모든 FileSystemFileHandle은 이 파일 시스템에서 얻을 때 필요한 권한을 이미 § 3.2 파일 읽기 또는 § 3.3 파일 생성 및 쓰기에 따라 스크립트에 반환되기 전에 모두 부여받으므로, getFile() 또는 createWritable()을 이러한 핸들에서 호출해도 추가 권한 요청 창이 표시되지 않습니다.

따라서 이러한 핸들의 queryPermission()과 requestPermission()은 다음 값을 보고해서는 안 됩니다. "prompt". 권한 요청 창이 나타날 수 없기 때문입니다. 쓰기 모드에서는 "denied"를 보고해야 하는데, 이는 해당 핸들을 생성 요청으로 얻지 않은 경우에 해당합니다. 그 밖에는 "granted"를 보고해야 합니다.

createWritable()을 다음과 같은 FileSystemFileHandle에서 호출하는 경우를 고려합니다. 핸들이 교차 출처 저장소 파일 시스템을 가리키고, 이 핸들을 얻은 경로가 생성 요청이 아니라면, 호출은 "NotAllowedError" DOMException으로 거부되어야 하며, 이때 FileSystemWritableFileStream을 생성해서는 안 됩니다.

참고: 쓰기는 핸들에 실제로 없을 수 있는 유일한 기능입니다. 생성 요청으로만 쓰기 가능한 핸들을 얻을 수 있으므로, 다른 핸들의 쓰기 모드에 "granted"를 보고하면 마치 쓰기 기능을 갖춘 것처럼 보이지만 createWritable()은 이를 거부합니다. 읽기 상태는 계속 "granted"입니다. 읽기 가능한 핸들을 가진 호출자는 이를 통해 읽을 수 있기 때문입니다. 권한을 요청해도 두 응답 중 어느 것도 바꿀 수 없습니다. 표시할 권한 요청 창도 없고 권한을 기록할 상태도 없기 때문입니다.

다음 조건에서 getFile()을 호출하면, 해당 FileSystemFileHandle이 가리키는 대상이 교차 출처 저장소 파일 시스템이고 핸들의 읽기 가능 여부가 false일 때 호출을 거부해야 합니다. 이때 오류는 "NotAllowedError" DOMException입니다. 여기에는 서로 다른 두 경우가 해당합니다.

  • 생성 요청으로 얻은 핸들로서, 이를 통한 쓰기가 아직 이루어지지 않았고, 핸들이 가리키는 해시에 해당하는 항목이 COS 레지스트리에 없는 경우입니다. 반환할 검증된 바이트가 없으며, 호출자가 자신이 끝내지 않은 쓰기를 마치 파일의 실제 내용인 것처럼 관찰할 수 있어서는 안 됩니다.

  • 어떤 다른 출처가 이미 쓴 해시에 대해 생성 요청으로 얻은 핸들인 경우입니다. 검증된 바이트는 존재하지만, 이 호출자는 그 바이트를 제공하지도 않았고 가용성 제한을 통과하지도 않았으므로 해당 항목에 관해 아무것도 알 수 없어야 합니다. 심지어 항목의 존재 여부조차도 알 수 없어야 합니다.

참고: 두 경우 모두 동일하게 거부되므로 어떠한 정보도 공개되지 않습니다. 따라서 "NotAllowedError"는 읽기 경로에서 의도적으로 피하는 오류이지만 여기서는 안전합니다. 이 핸들은 호출자가 자신의 생성 요청으로 얻은 것이며, 다른 어느 출처에서도 핸들을 역직렬화할 수 없기 때문입니다(§ 4.1 핸들 전달 참조). 그러므로 응답은 출처 경계를 넘지 않으며, 레지스트리의 내용에 관계없이 일정합니다. 반면 § 8.3 진행 중인 쓰기에서는 읽기 경로가 구별 가능한 오류를 반환했다면 정보가 그 경계를 넘었을 것입니다.

핸들의 읽기 가능 여부가 true이면, getFile()을 그 핸들에서 호출할 때 반환되는 것은 File이며, 그 내용은 핸들이 가리키는 항목의 bytes입니다. 이는 정확히 [FS]가 이미 정의한 파일 항목의 동작으로, 이때 항목의 이진 데이터는 해당 바이트입니다.

FileSystemFileHandle이 가리키는 대상이 교차 출처 저장소 파일 시스템이면, 이 핸들에는 파일 시스템 로케이터가 있으며, 그 경로는 다음과 같은 목록입니다. 이 목록에는 단 하나의 문자열이 들어 있으며, 그 문자열은 핸들의 COS 해시의 value입니다. 로케이터의 루트는 교차 출처 저장소 파일 시스템입니다.

참고: [FS]에서는 name을 핸들의 로케이터가 가진 경로의 마지막 구성 요소로 정의하므로, 이로써 name도 정해집니다. 그 값은 해시입니다. 항목 자체에는 이름이 없고 해시만이 항목을 식별하므로, 해시를 보고하면 빈 문자열을 반환할 때 사라질 정보가 전달됩니다.

항목에는 이름도 이를 포함하는 디렉터리도 없으므로, [FS]에서 정의하는 구조 관련 기능 대부분에는 적용할 대상이 없습니다. 예외는 동일성입니다. 내용으로 주소를 지정하는 항목에서는 동일한 항목인지 언제나 판정할 수 있습니다. COS 레지스트리에서 하나의 COS 항목만이 각 COS 해시에 대응할 수 있으므로, 두 핸들은 해시가 같을 때, 그리고 그때에만 같은 항목을 가리킵니다.

isSameEntry()을 다음과 같은 FileSystemFileHandle에서 호출하는 경우, 핸들이 가리키는 대상이 교차 출처 저장소 파일 시스템이고, 인수 역시 이를 가리키며 두 핸들을 얻은 곳이 같은 출처라면, true를 반환해야 하는 조건은 두 핸들의 COS 해시 항목이 같다는 것입니다. 그 밖에는 false를 반환해야 합니다.

참고: 이 비교를 거부하면 사용자 에이전트가 이미 보유한 정보를 버리게 됩니다.

isSameEntry()을 다음과 같은 FileSystemFileHandle에서 호출하는 경우, 핸들이 가리키는 대상이 교차 출처 저장소 파일 시스템이고, 인수를 호출 측 출처가 얻지 않았거나 인수가 가리키는 파일 시스템이 교차 출처 저장소 파일 시스템과 다르면, 호출은 다음 오류로 거부되어야 합니다. "NotAllowedError" DOMException입니다. 다른 파일 시스템을 가리키는 핸들, 예를 들어 getDirectory()가 반환하는 핸들은 [FS]에서 정한 동작을 유지합니다. 이는 인수로 FileSystemFileHandle을 전달하고 이 인수가 교차 출처 저장소 파일 시스템을 가리킬 때에도 마찬가지입니다.

참고: 이 경우 false를 반환하면 두 핸들이 서로 다른 항목을 가리킨다고 단정하게 됩니다. 이는 호출 측 출처가 검사할 권한이 없는 핸들에 관한 단정입니다. 거부는 단지 비교할 수 없었음을 나타냅니다.

move()와 remove()를 다음과 같은 FileSystemFileHandle에서 호출할 때, 그 대상이 교차 출처 저장소 파일 시스템이면 호출은 "NotAllowedError" DOMException으로 거부되어야 하며, 핸들이 가리키는 항목을 변경해서는 안 됩니다.

참고: 항목은 그 저장 출처에 속한 모든 출처가 공유하므로, 제거를 허용하면 한 사이트가 다른 사이트에서 의존하는 데이터를 파괴할 수 있습니다. 삭제는 퇴거와 사용자 자신의 저장소 제어 기능이 담당합니다. 이름이나 상위 디렉터리 변경에는 적용할 대상이 없습니다. 항목의 이름은 COS 해시로 정해지며, 항목을 포함하는 디렉터리는 없기 때문입니다.

참고: 작성 시점에는 두 메서드 중 어느 것도 [FS]나 파일 시스템 접근 API에 정의되어 있지 않으므로 (WICG/file-system-access#214), 오류 이름은 removeEntry()을 따릅니다. 이 연산은 [FS]가 항목 삭제를 위해 정의한 것으로, 읽기·쓰기 접근이 허가되지 않으면 접근 결과의 오류 이름으로 거부됩니다. 여기서도 거부가 정확한 동작입니다. 연산 자체는 의미가 있지만 수행이 허용되지 않기 때문입니다.

createSyncAccessHandle()에는 별도 규칙이 필요하지 않습니다. 이 메서드의 단계에서는 "InvalidStateError" DOMException으로 거부하도록 정하고 있으며, 이는 핸들이 버킷 파일 시스템에 속하지 않는 모든 경우에 해당합니다. 또한 교차 출처 저장소 파일 시스템은 파일 시스템 루트로서 어느 출처의 루트와도 구별되므로, [FS]가 이미 거부 여부와 오류 이름을 모두 정하고 있습니다.

참고: 이 명세만 따로 고려해도 같은 결과가 바람직합니다. FileSystemSyncAccessHandle은 호출자에게 쓰기 가능한 파일 디스크립터를 제공하므로, 호출자가 항목의 bytes를 해당 바이트에 대응하는 COS 해시는 그대로 둔 채 변경할 수 있습니다. 항목을 공개할 수 있는 다른 모든 출처도 바로 그 바이트를 읽습니다.

4.1. 핸들 전달

FileSystemFileHandle은 직렬화 가능한 객체입니다 [FS]. 따라서 COS 항목을 가리키는 핸들을 다른 환경 설정 객체에 전달할 수 있습니다. 예를 들어 postMessage(message, options)을 사용할 수 있습니다. 이는 이러한 핸들을 얻는 두 번째 방법으로, getFileHandle()과 함께 이 절에서 제약을 받습니다.

다음 직렬화 단계는 FileSystemFileHandle에 적용되며, 그 핸들이 가리키는 대상이 교차 출처 저장소 파일 시스템이고 value와 serialized가 주어지면 다음을 추가로 수행합니다.

  1. serialized.[[COSHash]]를 value의 COS 해시로 설정합니다.

  2. serialized.[[COSOrigin]]을 value의 COS 출처로 설정합니다.

  3. serialized.[[COSMayRead]]를 value의 읽기 가능 여부로 설정합니다.

다음 역직렬화 단계에서는 serialized, value, realm이 주어지면 다음을 추가로 수행합니다.

  1. serialized.[[COSOrigin]]과 동일한 출처인지 비교할 대상은 realm의 환경 설정 객체의 출처입니다. 동일한 출처가 아니면 "DataCloneError" DOMException을 던집니다.

  2. value의 COS 해시를 serialized.[[COSHash]]로 설정합니다.

  3. value의 COS 출처를 serialized.[[COSOrigin]]으로 설정합니다.

  4. value의 읽기 가능 여부를 serialized.[[COSMayRead]]로 설정합니다.

참고: 동일 출처 검사가 없으면 핸들 전달만으로 이 명세의 모든 공개 제어가 무력화됩니다. 핸들의 읽기 가능 여부가 true이면 이미 가용성 제한 적용을 해당 핸들을 요청한 출처에 대해 통과한 것입니다. 이를 다른 출처로 보내면, 그 출처에 대해 origins, PHL 포함 여부 또는 GREASE 적용을 평가하지 않고도 항목의 바이트를 넘기게 됩니다. 이는 파일 시스템 표준이 기존 핸들을 다루는 방식과 일치합니다. 기존 핸들도 동일 출처의 수신자만 사용할 수 있습니다.

참고: 읽기 가능 여부는 핸들과 함께 전달되므로, 생성 요청으로 얻었고 아직 쓰기에 사용하지 않은 핸들은 전달 후에도 읽을 수 없으며, 읽기 요청으로 얻은 핸들은 제한을 다시 적용하지 않아도 계속 읽을 수 있습니다. 수신 시 제한을 다시 적용하면 호출자가 같은 핸들을 전달하는 것만으로 가용성을 반복해서 탐색할 수 있습니다.

참고: 원본 핸들로 쓰기 전에 복제한 핸들은 계속 읽을 수 없습니다. 이를 보유한 측은 getFileHandle()을 호출하되 옵션 create를 생략하여, 읽기 가능한 핸들을 얻을 수 있습니다. 이때에는 원래 저장한 출처의 접근이 적용됩니다.

5. 저장소 관리

5.1. 저장 한도

사용자 에이전트는 하나의 출처가 COS 레지스트리에 성공한 쓰기를 통해 저장할 수 있는 총 바이트 수를 제한해야 합니다. 이는 단일 출처가 다른 출처의 항목을 퇴거시키려고 캐시를 가득 채우지 못하게 하기 위함입니다. 구체적인 한도는 구현에 따라 정해집니다.

COS 저장 한도 검사에는 COS 항목 또는 null인 entry, 출처 origin, 음이 아닌 정수 length가 주어지며, 다음과 같이 불리언을 반환합니다.

  1. entry가 null이 아니고 그 저장 출처가 포함하는 COS 공유 레코드 중 origin이 origin인 것이 있으면 true를 반환합니다.

    참고: 항목은 내용 주소 지정 방식을 사용하므로, 이 출처가 이미 저장한 바이트를 다시 써도 보유량이 늘어나지 않습니다.

  2. held는 다음 길이의 합으로 둡니다. 합산할 값은 bytes의 길이이며, 대상은 모든 COS 항목 중 COS 레지스트리에 있으면서 그 저장 출처가 다음을 포함하는 항목입니다. COS 공유 레코드 중 origin이 origin인 레코드입니다.

  3. held와 length의 합이 origin의 저장 한도를 초과하면 콘솔에 경고를 기록하고 false를 반환합니다.

  4. true를 반환합니다.

저장 한도는 한 출처가 한 시점에 보유하는 양을 제한하므로, 여러 출처를 불러오는 페이지에는 그 수만큼의 한도가 주어집니다. 따라서 사용자 에이전트는 COS 쓰기 한도도 각 사이트별로 유지하고, 해당 사이트를 COS 파티션으로 삼아 수행한 쓰기를 어느 출처나 프레임에서 수행했는지에 관계없이 집계해야 합니다. 이 한도에는 구현에 따라 정해지는 최대 쓰기 횟수와 최대 바이트 수가 구현에 따라 정해지는 시간 구간별로 있으며, 이 한도를 지속적으로 보관하고 초기화하는 조건은 사이트 간 조회 예산과 같습니다.

COS 쓰기 사용량 부과에는 COS 항목 또는 null인 entry, 출처 origin, 사이트 partition, 음이 아닌 정수 length가 주어지며, 다음과 같이 불리언을 반환합니다.

  1. entry가 null이 아니고 그 저장 출처가 포함하는 COS 공유 레코드 중 origin이 origin이고 partition이 partition인 것이 있으면 true를 반환합니다.

    참고: 이 출처가 이미 이 최상위 사이트에서 저장한 바이트를 써도 보유량이 늘지 않으므로, 출처별 저장 한도에서와 마찬가지로 사용량을 부과하지 않습니다. 부과 여부는 오직 이 출처 자체의 이전 쓰기에만 달려 있으므로, 다른 출처가 저장한 내용에 관해서는 아무것도 공개하지 않습니다.

  2. 쓰기를 한 번 더 수행하거나 length바이트를 더 쓰면 partition의 COS 쓰기 한도를 현재 구간에서 초과하게 되는 경우, 콘솔에 경고를 기록하고 false를 반환합니다.

  3. 쓰기 1회와 length바이트를 partition의 COS 쓰기 한도에 산입합니다.

  4. true를 반환합니다.

참고: 쓰기 사용량은 바이트를 검증한 뒤 부과합니다. 다른 출처가 또는 다른 최상위 사이트에서 이 출처가 이미 해당 해시를 저장했는지와 관계없이 부과량이 같으므로, 이 한도는 다른 사이트가 저장한 내용을 드러내지 않습니다. 두 한도는 사용 양상을 구분합니다. 사이트에서 하나의 대규모 AI 모델을 저장하면 바이트 한도는 소모하지만 횟수는 거의 소모하지 않는 반면, 추적기가 식별자를 인코딩하려고 작은 표식 파일을 수십 개 저장하면 횟수 한도를 금세 소진합니다.

사용자 에이전트에는 또한 구현에 따라 정해지는 최대 출처 목록 길이가 있습니다. 이는 하나의 목록에 들어갈 수 있는 출처 수의 상한을 정하는 양의 정수로, 하나의 origins 목록에 적용됩니다. 이 제한은 목록이 처음 제공될 때(COS 요청 유효성 검사 참조)와 이후 목록을 기존 항목에 병합할 때 모두 적용되므로( 리소스 공개 범위 확대 참조), 단 한 번의 호출로도, 여러 번에 걸친 호출의 누적 효과로도 항목의 origins를 무한히 늘릴 수 없습니다. 이는 메모리 사용량을 제한할 뿐만 아니라 출처의 목록이 명시적으로 선언하지 않은 "*"의 대용으로 쓰이는 것도 방지합니다. § 8.2 사이트 간 탐색을 참조하세요.

이 한도를 초과하는 경우는 두 곳에서 서로 다르게 처리됩니다. 한 작업 안에서 두 호출이 일어나는 시점이 크게 다르기 때문입니다.

  • COS 요청 유효성 검사에서는 파일을 가져오거나 해시를 계산하거나 쓰기 전에 한도를 검사합니다. 한도를 초과한 호출자는 즉시 "TypeError"를 받으며 그 밖의 동작은 일어나지 않습니다. 이는 형식이 잘못된 다른 origins 값과 같은 처리입니다.

  • 리소스 공개 범위 확대에서는 오직 여러 요청이 누적된 결과로만 한도에 도달할 수 있습니다. 서로 독립적인 여러 쓰기 호출에서 출처를 요청하고, 심지어 서로 무관한 출처가 오랜 기간에 걸쳐 요청할 수도 있습니다. 한도 검사는 이번 호출의 바이트에 대해 이미 해시 계산, 검증, 영구 저장이 끝난 뒤에야 이루어집니다. 이때 쓰기를 거부하면 성공적으로 검증까지 끝난, 어쩌면 매우 큰 쓰기를 별개의 기록 관리 한도 때문에 버리게 되며, 이를 어느 한 호출자의 잘못으로 돌릴 수도 없습니다. 따라서 쓰기는 성공하도록 두고, 한도를 넘는 출처만 origins에서 제외하며 콘솔에 경고를 기록합니다. 이는 기존의 허용 범위를 더 좁히는 요청에 대한 처리와 같습니다. 출처 요청을 모두 받아들일 수 없으면 별도 통지 없이 범위를 제한하고, 그 요청을 포함한 쓰기는 그대로 성공합니다. 이 명세의 다른 곳에 나오는 § 8.4 가용성 제한과 마찬가지로, 이 경우에도 호출자가 요청한 출처의 실제 추가 여부를 나중에 확실히 확인할 방법은 없습니다. 이후 getFileHandle()을 해당 출처에서 호출해도, 출처가 추가되었는데도 실패할 수 있습니다(예를 들어 항목이 퇴거되었거나 읽는 측 사이트가 사이트 간 조회 예산을 소진한 경우). 따라서 호출 결과를 어느 쪽으로든 확증으로 해석해서는 안 됩니다.

5.2. 퇴거

이 절은 비규범적입니다.

저장 공간이 부족하면 사용자 에이전트는 항목을 COS 레지스트리에서 퇴거시킬 수 있습니다. 예를 들어 각 항목에 가장 최근에 접근한 저장 출처를 대상으로 가장 오래 사용되지 않은 항목부터 퇴거시키는 정책을 적용할 수 있습니다. 사용자 에이전트는 설정 UI를 제공하여 사용자가 저장된 파일과 각 파일에 접근한 출처를 확인하고, 직접 항목을 삭제하거나 교차 출처 저장소의 모든 데이터를 지울 수 있도록 하는 것이 기대됩니다.

사용자가 한 출처의 사이트 데이터를 지우면, 사용자 에이전트는 공유 레코드 중 origin이 해당 출처인 것을 모든 저장 출처 집합에서 제거하는 것이 좋습니다. 제거한 뒤 COS 항목의 저장 출처가 비어 있으면, 사용자 에이전트는 해당 항목을 삭제 대상으로 고려할 수 있습니다.

5.3. 파생 산출물

사용자 에이전트는 파생 산출물을 보관할 수 있습니다. 이는 bytes를 하나 이상의 COS 항목에서 얻어 계산한 뒤 재사용하려고 보관하는 데이터로, 컴파일된 WebAssembly 모듈, GPU 파이프라인 또는 컴파일된 ML 그래프 등이 있습니다. 파생 산출물에는 다음 항목이 있습니다.

sources

비어 있지 않은 목록으로, COS 해시 값을 담습니다. 이 값들은 산출물 계산에 바이트를 제공한 항목을 나타냅니다.

페이지가 선택한 입력

결과에 영향을 주며 스크립트가 자유롭게 설정할 수 있는 그 밖의 모든 입력입니다. 컴파일 옵션, 그 자체가 소스가 아닌 코드나 그래프 구조, 상수 또는 연산자 옵션 등이 이에 해당합니다. 비어 있을 수 있습니다.

producers

하나의 집합으로, 여기에 속하는 사이트는 COS 파티션 중 사용자 에이전트가 해당 산출물을 계산한 파티션입니다.

사용자 에이전트는 파생 산출물의 키를 해당 산출물의 sources, 페이지가 선택한 입력, 그리고 구현에 따라 정해지는 사용자 에이전트와 장치의 속성에서 도출합니다. 사용자 에이전트는 스크립트가 키를 선택하거나 읽도록 허용해서는 안 되며, 파생 산출물의 내용을 스크립트에 노출해서도 안 됩니다.

파생 산출물은 반드시 그 키에만 의존해야 합니다. 산출물을 계산하게 한 콘텐츠를 실행한 결과에서 파생된 데이터를 포함해서는 안 됩니다.

참고: 그렇지 않으면 자주 실행되는 코드를 최적화하는 컴파일러가 산출물을 생성한 페이지에서 어떤 함수를 실행했는지 기록하게 되며, 산출물을 재사용하면 그 실행 프로파일이 다른 사이트에 공개됩니다.

사용자 에이전트는 파생 산출물을 어떤 COS 파티션에서 재사용하려 할 때, 그 파티션이 산출물의 producers에 속하지 않고 사이트의 콘텐츠가 키 이외의 경로로 산출물에 영향을 줄 수 있다면 재사용해서는 안 됩니다.

참고: 사이트 콘텐츠를 실행하는 프로세스에서 컴파일한 코드는 해당 프로세스가 침해되면 그 콘텐츠에 의해 변경될 수 있습니다. 이를 다른 최상위 사이트에서 재사용하면 한 사이트가 다른 사이트의 프로세스에서 코드를 실행할 수 있게 됩니다.

사용자 에이전트는 파생 산출물을 제거해야 합니다. 이는 해당 산출물의 sources 중 하나라도 COS 레지스트리에서 제거할 때 적용됩니다. 사용자가 한 사이트의 데이터를 지우면, 사용자 에이전트는 그 사이트를 모든 producers 집합에서 제거하는 것이 좋으며, 산출물의 producers가 그 결과 비게 되면 해당 산출물을 삭제할 수 있습니다.

파생 산출물 재사용 여부 결정에는 파생 산출물 artifact, 사이트 partition, 그리고 목록 obtained가 주어집니다. 이 목록은 COS 해시 값의 목록으로, 그에 해당하는 바이트는 요청 측 컨텍스트가 COS 레지스트리에서 읽어 제공한 것입니다. 다음과 같이 불리언을 반환합니다.

  1. artifact의 producers가 포함하는 사이트 중 동일 사이트 관계가 partition과 성립하는 것이 있으면 true를 반환합니다.

    참고: 이는 사용자 에이전트가 이미 수행하는 사이트별 캐싱입니다.

  2. obtained가 다음을 모두 포함하지 않으면, 즉 모든 항목이 포함되어 있지 않으면, 이때 대상이 되는 것은 artifact의 sources이며, false를 반환합니다.

    참고: 읽기는 이미 가용성 제한 적용을 거쳤으며, 이 과정에서 사이트 간 조회 예산을 차감합니다. 다른 곳에서 얻은 바이트를 허용하면 페이지는 두 검사 중 어느 것도 거치지 않고 계산에 걸리는 시간만으로 항목이 존재하는지 알 수 있게 됩니다.

  3. artifact의 페이지가 선택한 입력이 비어 있으면 true를 반환합니다.

  4. 다음 사이트 간 조회 사용량 부과를 partition에 대해 수행한 결과가 true이면 true를 반환합니다.

  5. false를 반환합니다.

파생 산출물 재사용 여부 결정이 false를 반환하면, 사용자 에이전트는 산출물이 없었던 것처럼 새로 계산한 뒤, 요청 측의 COS 파티션을 산출물의 producers에 추가해야 합니다. 따라서 재사용이 거부된 경우와 산출물을 찾지 못한 경우를 구별할 수 없습니다. § 8.7 파생 산출물 타이밍을 참조하세요.

어떤 입력이 소스이고 어떤 입력을 페이지가 선택하는지는 호스트 명세에서 정의합니다.

  • WebAssembly: WebAssembly.compileStreaming() 또는 WebAssembly.instantiateStreaming()으로 모듈을 컴파일할 때 사용한 File을 교차 출처 저장소에서 읽었다면 해당 항목이 그 모듈의 소스입니다. 기본값과 다른 컴파일 옵션은 페이지가 선택한 입력입니다.

  • WebGPU: 셰이더 코드를 COS 항목에서 읽었다면 그 코드는 소스입니다. 그 밖의 셰이더 코드, 파이프라인에서 재정의할 수 있는 상수, 파이프라인 레이아웃은 페이지가 선택합니다. gpuweb/gpuweb#11110을 참조하세요.

  • WebNN: COS 항목에서 읽은 상수는 소스입니다. 그래프 구조, 연산자 옵션, 그 밖의 상수는 페이지가 선택합니다. webmachinelearning/webnn#971을 참조하세요.

WebGPU와 WebNN에는 입력의 COS 유래 정보를 컴파일러에 전달하는 호스트 통합이 필요합니다.

5.4. 수동으로 추가한 항목

이 절은 비규범적입니다.

앞에서 설명한 설정 UI는 사용자가 디스크에 이미 보유한 파일을 직접 교차 출처 저장소에 추가할 수 있게 할 수 있습니다(예를 들어 웹사이트와 무관하게 다운로드한 AI 모델). 이때 어떤 스크립트도 getFileHandle()을 호출할 필요가 없습니다. 이러한 항목에는 쓰기를 귀속시킬 요청 측 출처가 없으므로, 다음 두 가지 의문이 생깁니다. 이 두 가지에는 명령형 API만으로 답할 수 없습니다.

  • 원래 저장한 출처는 어디인가요? 여기서 말하는 출처는 § 3.5.2 원래 저장한 출처의 접근에서의 출처입니다. 해당하는 출처는 없습니다. 항목의 저장 출처는 처음에 비어 있습니다. 따라서 어느 출처도 일반적인 가용성 제한과 origins 검사에서 면제되지 않으며, 다른 모든 요청 출처와 같은 검사를 받습니다. 바이트를 실제로 쓴 출처가 없으므로 이는 올바른 결과입니다.

  • 이러한 항목도 다음 옵션을 생략한 일반적인 쓰기처럼 동일 사이트에서만 접근하도록 제한해야 하나요? origins가 그 옵션입니다. 그렇지 않습니다. "동일 사이트"는 요청 측 출처를 기준으로 할 때만 의미가 있는데, 수동 추가에는 그런 출처가 없으므로 "동일 사이트"의 기준이 될 사이트도 없습니다. 사용자 에이전트는 이러한 항목을 전역 공개 가능 상태로 두고, 명시적 origins 목록은 비워 두는 것이 기대됩니다. 수동으로 파일을 미리 넣어 두는 것은 다른 출처가 실제로 그 파일을 발견할 수 있어야 목적을 달성하기 때문입니다(사용자가 아직 방문하지 않은 사이트에서 사용자의 디스크에 이미 있는 파일을 재사용하는 것). 사용자 에이전트의 설정 UI는 사용자가 더 좁은 범위를 선택할 수 있게 할 수도 있습니다.

이렇게 추가한 항목은 그 밖의 면에서 웹사이트가 getFileHandle()로 쓴 항목과 구별되지 않습니다. 동일한 가용성 제한 및 공개 범위 확대 규칙이 같은 공유 레코드를 가진 다른 모든 항목과 똑같이 적용됩니다. 여기에는 PHL 포함 여부 검사도 포함되며, 항목이 최종적으로 전역 공개 가능 상태이면 언제나 적용됩니다. 수동 추가 시 기본값이 바로 이 상태입니다.

5.5. 유래 메타데이터

이 절은 비규범적입니다.

COS 항목은 의도적으로 바이트를 어디서 가져왔는지 기록하지 않습니다. 항목을 식별하는 것은 hash뿐입니다. 바이트가 같으면 몇 개의 출처가 그 바이트를 저장했는지, 몇 개의 URL에서 가져왔는지에 관계없이 같은 항목입니다(§ 2.2 COS 항목 참조). URL은 한 쓰기 주체가 수행한 가져오기의 속성이므로, 여러 출처가 쓴 항목에 대해 하나의 URL을 선택하는 데에는 임의적이지 않은 기준이 없습니다. 또한 URL은 바이트처럼 검증할 수도 없으며(§ 8.1 리소스 무결성 참조), 사용자가 방문한 곳에 관해 대략적인 출처 값보다 훨씬 많은 정보를 담고 있습니다. 저장 출처에 있는 값과 달리, URL의 경로나 쿼리 문자열은 특정 문서, 계정 또는 세션을 식별할 수 있기 때문입니다. 따라서 URL을 항목에 기록하면 엔트로피가 높은 신호가 origins와 § 8.4 가용성 제한에서 부과하는 공개 제한을 우회하게 됩니다.

그렇지만 이 정보가 필요한 실제 이유도 있습니다. 수 기가바이트짜리 파일을 § 5.2 퇴거에서 설명한 설정 UI로 살펴보는 사용자도, getFileHandle()이 파일을 찾지 못한 이유를 디버깅하는 개발자도 파일을 어디서 가져왔는지 알고 싶을 수 있습니다. 사용자 에이전트는 항목과 함께 구현 내부에서만 사용하는 유래 레코드를 유지하여 이를 지원할 수 있습니다(예를 들어 각 저장 출처가 해당 바이트를 가져온 URL과 시점). 단, 레코드는 다음과 같이 항목 외부에 보관하는 사용자 에이전트의 상태로 취급해야 합니다.

  • 레코드는 스크립트에 절대 노출되지 않습니다. 이 명세의 어떤 기능도 이를 공개하지 않으며, 나중에 추가되는 기능도 공개하지 않는 것이 좋습니다. getFileHandle()도, 그 메서드가 반환하는 FileSystemFileHandle도 레코드의 내용은 물론이고 존재 여부조차 드러내지 않는 것이 좋습니다. 특히 요청 측 출처는 자신이 직접 생성하지 않은 레코드를 관찰할 수 있어서는 안 됩니다.

  • 레코드는 웹에서 접근할 수 없는 신뢰된 인터페이스를 통해서만 표시됩니다. 사용자 에이전트 자체의 설정 및 저장소 검사 UI, 개발자 도구, 그리고 사용자 에이전트에 확장 기능 플랫폼이 있다면 사용자가 명시적으로 부여한 권한이 필요한 확장 기능 API가 이에 해당합니다. 방문 기록을 노출하는 다른 API와 동일한 권한 기준을 적용합니다. 고려 중인 확장 기능 인터페이스는 브라우저 확장 기능 통합 지점 해설서를 이 저장소에서 참조하세요.

  • 레코드는 검증되지 않았으며, 그렇게 표시됩니다. 레코드의 URL은 바이트를 쓴 출처가 주장하는 값입니다. 오직 hash만이 내용을 보장합니다(§ 8.1 리소스 무결성 참조). 두 출처가 같은 항목에 대해 서로 다른 URL을 기록할 수 있으며, 둘 중 어느 쪽이든 부정확하거나 의도적으로 오해를 유발할 수 있습니다.

  • 레코드는 항목 및 레코드가 귀속된 출처와 수명을 공유합니다. 항목이 퇴거되거나 삭제되면 레코드를 폐기하고, 특정 출처에 귀속된 부분은 해당 출처의 공유 레코드를 저장 출처에서 제거할 때 폐기합니다. 여기에는 사용자가 해당 출처의 사이트 데이터를 지우는 경우도 포함됩니다(§ 5.2 퇴거 참조).

이 레코드는 콘텐츠에서 볼 수 없으므로, 사용자 에이전트가 레코드를 보관할지, 어느 정도까지 보관할지는 전적으로 구현에 맡깁니다. 이 명세의 어떤 동작도 이 레코드에 의존하지 않으며, 사이트는 레코드의 유무를 감지할 수 없습니다.

6. 권한 정책과의 통합

이 명세에서는 정책 제어 기능 [permissions-policy]을 정의하며, 이를 식별하는 것은 문자열 "cross-origin-storage"입니다. 이 기능의 기본 허용 목록은 self입니다. 워커용 권한 정책 [WORKERS-PERMISSIONS-POLICY]에 따르면, 이 기능은 서비스 워커에서 활성화할 수 없습니다.

이 절에서는 워커용 권한 정책 [WORKERS-PERMISSIONS-POLICY]이 마치 이미 [permissions-policy] 및 [HTML]의 일부인 것처럼 이를 사용합니다. 이 제안은 해설서이며, 워커 정책이나 SharedWorker의 allow 옵션, 또는 이 절에서 언급하는 "서비스 워커에서 활성화할 수 있음" 불리언을 정의한 명세는 없습니다. 작성 시점에 Chromium은 공유 워커에 해당하는 부분을 플래그 (PermissionsPolicyForSharedWorkers) 뒤에서 구현하며, 이를 기본 제공하는 엔진은 없습니다. 해당 동작이 명세화되면 이 절에서는 그 동작을 직접 기술하는 대신 해당 훅을 호출하는 것이 좋습니다.

[permissions-policy]에서는 사용 허용 여부를 Document에 대해 정의합니다. 그러나 CrossOriginStorageManager는 WorkerGlobalScope에도 노출되며, 여기에는 자체 Document가 없습니다. 따라서 검사는 호출 측 전역 객체를 기준으로 기술하며, [WORKERS-PERMISSIONS-POLICY]를 따릅니다. 전용 워커가 상속하는 정책은 Document 중 직간접적으로 해당 워커를 소유하는 문서의 정책이고, 공유 워커는 자체 정책을 가지며, 서비스 워커는 이 기능을 활성화할 수 없습니다.

교차 출처 저장소 권한 검사에는 전역 객체 global이 주어지며, 다음과 같이 불리언을 반환합니다.

  1. global이 Window 객체이면 다음을 수행합니다.

    1. document를 global의 연결된 Document로 둡니다.

    2. document가 null이면 false를 반환합니다.

    3. document에 사용이 허용되는지 검사할 대상은 "cross-origin-storage" 정책 제어 기능입니다. 사용이 허용되지 않으면 false를 반환합니다.

    4. true를 반환합니다.

  2. global이 DedicatedWorkerGlobalScope 객체이면 다음을 수행합니다.

    1. owners를 global의 소유자 집합으로 둡니다.

    2. owners가 비어 있으면 false를 반환합니다.

    3. 각각의 owner에 대해 owners에서 다음을 수행합니다.

      1. owner가 Document이고, owner에 사용이 허용되는지 검사할 때 "cross-origin-storage" 정책 제어 기능의 사용이 허용되지 않으면 false를 반환합니다.

      2. owner가 WorkerGlobalScope 객체이고 교차 출처 저장소 권한 검사를 owner에 대해 수행한 결과가 false이면 false를 반환합니다.

    4. true를 반환합니다.

  3. global이 SharedWorkerGlobalScope 객체이면, 다음 조건에서 true를 반환합니다. "cross-origin-storage"가 global의 권한 정책 [WORKERS-PERMISSIONS-POLICY]에서 활성화되어 있어야 하며, 그 밖에는 false를 반환합니다.

    참고: 이 정책에는 생성자가 allow 멤버를 통해 위임한 기능만 들어갑니다. 이 멤버는 SharedWorker 생성자 옵션에 있으며, 위임한 기능 중 워커 스크립트 자체의 Permissions-Policy 응답 헤더가 비활성화한 기능은 제외됩니다. 이러한 기능을 위임할 수 없는 컨텍스트는, 예를 들어 자체 정책이 교차 출처 저장소를 비활성화한 컨텍스트는 연결하지 못하므로, 워커가 실행되는 동안 정책은 바뀔 수 없습니다.

  4. false를 반환합니다.

    참고: 여기에는 ServiceWorkerGlobalScope가 포함됩니다. 여기서는 "cross-origin-storage"를 활성화할 수 없습니다 [WORKERS-PERMISSIONS-POLICY].

어떤 전역 객체에 대해 이 알고리즘이 false를 반환하면, 그 객체에서 이루어지는 모든 getFileHandle() 호출은 다음 오류로 거부됩니다. "NotAllowedError" DOMException이며, 이는 해시 유효성 검사, 레지스트리 조회 또는 쓰기가 일어나기 전입니다.

참고: 소유자 집합을 따라 권한을 판정해야 기능을 끄는 정책이 이름뿐인 설정에 그치지 않습니다. blob: URL에서 생성한 워커는 이를 생성한 페이지의 출처에서 실행되며 페이지와 정확히 같은 교차 출처 저장소를 봅니다( § 3 CrossOriginStorageManager 인터페이스 참조). 따라서 전역 객체 자체의 Document만 참조하는 검사는 모든 워커에서 검사 대상 없이 통과하게 되며, 호출을 new Worker(URL.createObjectURL(&hellip;)) 안으로 옮기기만 해도 cross-origin-storage=() 정책이 그 밖의 조건이 모두 같은데도 적용되지 않게 됩니다.

참고: 서비스 워커는 교차 출처 저장소를 사용할 수 없습니다. 그 이유는 "cross-origin-storage"가 서비스 워커에서 활성화할 수 있는 기능이 아니기 때문입니다 [WORKERS-PERMISSIONS-POLICY]. 이는 모든 정책 제어 기능의 기본값이며, 교차 출처 저장소도 이를 따릅니다. 서비스 워커의 등록은 지속적으로 보관되며, 사용자 에이전트는 이벤트에 응답하여 워커를 시작합니다. 실행 중인 서비스 워커 하나가 정책이 서로 다를 수 있는 여러 클라이언트를 담당하므로, 단 하나의 Document를 골라 그 정책을 참조할 수 없습니다. API 자체는 이곳에도 노출되므로, 호출은 "NotAllowedError"로 거부됩니다. 이는 이 알고리즘이 거부하는 다른 호출과 같습니다. 또한 explainers-by-googlers/workers-permissions-policy#4를 참조하세요.

참고: SharedWorkerGlobalScope의 소유자 집합에는 여러 Document가 서로 다른 정책을 가진 채 속할 수 있으며, 워커가 살아 있는 동안 소유자가 추가되거나 제거됩니다. 생성 시 고정되는 워커 자체의 정책을 참조하면, 두 번의 getFileHandle() 호출 사이에 판정이 달라지지 않습니다. 이를 이용해 비활성화 정책을 피할 수도 없습니다. 자체 정책으로 교차 출처 저장소를 비활성화한 문서는 그 기능을 위임할 수 없으므로, 그 기능이 있는 공유 워커를 생성할 수도, 그런 워커에 연결할 수도 없습니다.

7. Cross-Origin-Storage-Allow-Origin 헤더

COS 항목의 origins 목록이 비어 있지 않으면 해당 항목은 쓰기 측 출처가 제어하지 않는 출처에도 공개될 수 있습니다. 그런데 그 목록은 스크립트에서 다음 옵션을 통해 선언하거나( origins) 마크업에서 선언합니다. 두 경우 모두 공격자가 스크립트나 마크업 주입에 성공했다면 설정할 수 있습니다. 공개되는 바이트를 제공한 출처의 운영자에게 이 선언을 결부시키되 주입된 콘텐츠가 위조할 수 없는 형식을 사용하기 위해, 이 명세는 선언에서 지정할 수 있는 출처를 제한하는 응답 헤더를 정의합니다.

Cross-Origin-Storage-Allow-Origin 응답 헤더는 COS 범위 상한을 전달합니다. 이는 집합으로, 그 안의 출처는 쓰기가 동일 사이트 이외의 대상을 위한 origins 목록에 지정할 수 있는 출처입니다. 바이트를 제공하는 측에서 헤더를 보내므로, 공개되는 바이트의 근거가 되는 응답에서 다음과 같이 헤더를 읽습니다.

  • getFileHandle()을 사용하는 쓰기에서는 바이트를 스크립트가 생성할 수 있어, 바이트 자체를 가져온 응답이 없을 수 있습니다. 이때 헤더를 읽는 응답은 호출 측 전역 객체의 Document를 생성하는 데 사용한 응답이고, 워커의 경우에는 다음 Document의 응답입니다. 즉, 직접 또는 다른 워커를 거쳐 해당 워커를 생성한 문서입니다( COS 범위 상한 얻기 참조).

  • 호스트 통합의 경우에는 응답 중 저장할 바이트가 들어 있는, 가져온 리소스의 응답을 사용합니다 (가져온 리소스를 교차 출처 저장소에 저장 참조). 이는 리소스를 제공하는 서버의 응답이며, 이 서버가 반드시 Document, 즉 리소스를 불러오는 문서의 서버일 필요는 없습니다.

선언된 목록은 교집합을 상한과 취하므로( COS 범위 상한 적용 참조), 상한은 선언의 범위를 좁힐 수만 있습니다.

참고: 헤더는 바이트를 제공하는 측이 부여하는 권한입니다. 헤더가 지정한 출처, 즉 나중에 읽게 될 출처에는 의사를 묻지 않으며, 그 출처도 아무것도 보내지 않습니다. 목록에 있는 출처는 나중에 getFileHandle()을 호출하여 다른 읽기 주체와 마찬가지로 해당 COS 해시를 요청할 때에만 참여합니다. 이는 Access-Control-Allow-Origin [FETCH]과 반대 방향입니다. 그 경우에는 리소스를 보유한 서버가 특정 출처의 읽기를 허용합니다. 여기서는 바이트를 제공하는 측이 나중에 교차 출처 저장소에서 누가 그 바이트를 읽을 수 있는지 제한합니다. 쓰기 측 페이지에 주입된 콘텐츠는 제공자의 응답 헤더를 설정할 수 없으므로 그 범위를 넓힐 수 없습니다.

참고: 이 헤더는 목록 형식에만 적용됩니다. 동일 사이트 기본값은 다른 출처의 수신자를 별도로 지정하지 않으므로 권한 부여가 필요하지 않습니다. "*" 형식은 읽기 경로에서 가용성 제한을 적용하여 공개 해시 목록을 검사하며, 사용자별 비밀은 이 검사를 통과할 수 없으므로 쓰기 시점의 상한도 필요하지 않습니다. "*"에 헤더를 요구하면 공개 해시 목록이 이미 차단하는 것 외에는 더 차단하지 못하면서, 설정 없이 전역으로 공유하는 사용 방식만 깨뜨리게 됩니다.

COS 범위 상한 파싱에는 헤더 목록 headers가 주어지며, 반환하는 것은 집합입니다. 그 원소는 다음과 같이 구한 출처입니다.

  1. value를 다음 가져오기, 디코딩 및 분할의 결과로 둡니다. 대상은 headers의 "Cross-Origin-Storage-Allow-Origin"입니다.

  2. value가 null이면 빈 집합을 반환합니다.

  3. ceiling을 빈 집합으로 둡니다.

  4. 각각의 token에 대해 value에서 다음을 수행합니다.

    1. 앞뒤의 ASCII 공백 제거를 token에 적용합니다.

    2. token이 빈 문자열이면 다음 반복으로 넘어갑니다.

    3. url을 기본 URL 파서를 token에 대해 실행한 결과로 둡니다.

    4. url이 실패이거나, url의 스킴이 "http"도 "https"도 아니거나, url의 출처가 잠재적으로 신뢰할 수 있는 출처가 아니면, 빈 집합을 반환합니다.

      참고: 여기에는 token이 "*"인 경우도 포함됩니다. 이 값은 출처로 파싱되지 않습니다. Cross-Origin-Storage-Allow-Origin 헤더에는 유한한 수의 구체적인 출처만 열거할 수 있습니다. "*"는 허용되는 값이 아닙니다. "모든 출처"를 상한으로 삼으면 그 결과 주입된 콘텐츠가 원하는 수신자를 마음대로 선언할 수 있어 헤더의 목적 자체가 무력화되기 때문입니다. 제한 없는 공개는 "*" origins 형식으로만 가능하며, 이 경우에는 공개 해시 목록을 기준으로 제한을 적용하고 이 헤더는 참조하지 않습니다. 형식이 잘못되었거나 "*"를 포함한 헤더는 헤더가 없는 경우와 똑같이 아무것도 허용하지 않습니다. 실패하면 차단됩니다.

    5. 추가할 값은 url의 출처이며, 이를 ceiling에 추가합니다.

  5. ceiling을 반환합니다.

참고: 가져오기, 디코딩 및 분할은 U+002C (,)를 기준으로 분할하므로, 헤더 값에 포함된 출처는 쉼표로 구분합니다. 이는 Timing-Allow-Origin [RESOURCE-TIMING] 및 목록 값을 갖는 HTTP 응답 헤더의 일반적인 관례와 일치합니다. 반면 대응하는 crossoriginstorage HTML 콘텐츠 속성은 호스트 문법에 맞게 공백을 구분자로 사용합니다. 둘 다 동일한 출처 집합으로 해석됩니다.

COS 범위 상한 얻기에는 전역 객체 global이 주어지며, 반환하는 것은 집합입니다. 그 원소는 다음과 같이 구한 출처입니다.

  1. global이 Window 객체이면 다음을 수행합니다.

    1. document를 global의 연결된 Document로 둡니다.

    2. document가 null이면 빈 집합을 반환합니다.

    3. document의 COS 범위 상한을 반환합니다.

  2. global이 WorkerGlobalScope 객체이면 global의 COS 범위 상한을 반환합니다.

  3. 빈 집합을 반환합니다.

COS 범위 상한 적용에는 목록으로 주어지는 출처 requestedOrigins와 집합으로 주어지는 출처 ceiling이 입력되며, 다음과 같이 목록 형태의 출처 또는 null을 반환합니다.

  1. 제거를 requestedOrigins에 적용합니다. 제거할 출처는 ceiling이 포함하지 않는 모든 출처입니다.

    참고: 수신자가 COS 범위 상한에 없으면 제외되지만 쓰기는 그대로 성공합니다. 이는 길이 제한을 넘기는 확대 요청에서 초과분을 제외하는 리소스 공개 범위 확대의 처리와 같습니다. 사용자 에이전트는 콘솔에 경고를 기록하면서 제외된 각각의 출처를 명시하는 것이 기대됩니다.

  2. requestedOrigins가 비어 있으면 null을 반환합니다.

    참고: 목록의 모든 원소가 제외되면 쓰기에 대해 허가된 교차 출처 수신자가 없으므로 동일 사이트 기본값을 적용합니다. 바이트는 여전히 저장되며, 허가되지 않은 공개만 보류됩니다.

  3. requestedOrigins를 반환합니다.

모든 Document에는 COS 범위 상한이 있습니다. 이는 집합으로, 그 원소는 출처이며, 문서를 생성할 때 COS 범위 상한 파싱을 실행한 결과로 설정합니다. 이때 전달하는 헤더 목록은 응답 중 해당 문서를 생성하는 데 사용한 응답의 것입니다.

모든 WorkerGlobalScope에는 COS 범위 상한이 있습니다. 이는 집합으로, 그 원소는 출처이며, 워커를 생성하는 워커 실행 시 다음 결과로 설정합니다. COS 범위 상한 얻기에 전달하는 전역 객체는 outside settings의 전역 객체이며, 이 설정은 워커 실행에 주어진 것입니다. 전용 워커의 경우 해당 워커를 생성한 전역 객체입니다. 공유 워커의 경우에는 SharedWorker 생성자를 호출하여 워커를 만든 전역 객체입니다. 나중에 실행 중인 워커에 연결하는 컨텍스트는 그 상한을 변경하지 않습니다.

참고: 워커는 자신을 생성한 측의 상한을 사용하며, 자체 스크립트의 응답에서 상한을 가져오지 않습니다. blob: 워커는 자신을 생성한 페이지의 출처를 공유하고 그 페이지와 정확히 같은 교차 출처 저장소를 보며 (§ 3 CrossOriginStorageManager 인터페이스 참조), 그 응답에는 헤더가 없습니다. 따라서 워커 자체에서 상한을 읽으면 모든 blob: 워커의 상한이 비게 되며, 목록 범위 쓰기를 new Worker(URL.createObjectURL(&hellip;)) 안으로 옮기는 것만으로 해당 페이지가 허가한 수신자가 제외됩니다. 생성 시 상한을 고정하는 방식은 교차 출처 저장소 권한 검사와 같습니다. 여기서는 공유 워커의 정책에 생성자가 위임한 기능만 포함되므로, 두 번의 getFileHandle() 호출 사이에 어떤 컨텍스트가 연결하거나 연결을 끊더라도 판정이 달라지지 않습니다. 공유 워커에 연결할 수 있는 컨텍스트는 모두 워커와 같은 출처를 가지므로, 나중에 더 좁은 상한으로 연결하는 컨텍스트도 생성자의 상한을 허가한 동일한 운영자가 운영합니다.

Document의 COS 범위 상한을 해당 문서의 응답에서 채우려면 다음과 같이 [HTML]의 문서 생성 단계에 훅이 필요합니다. 이는 [permissions-policy] 및 [CSP]의 값을 응답 처리 시점에 채우는 방식과 같습니다. 이 훅이 생길 때까지는 이 절에서 필요한 동작을 직접 기술합니다. 향후 개정에서는 다음 [FS] 훅과 함께 정식으로 통합할 예정입니다(§ 3.3 파일 생성 및 쓰기 참조). WorkerGlobalScope의 COS 범위 상한에도 동일한 종류의 훅이 워커 실행에 필요합니다. 호스트 통합에는 이러한 훅이 필요하지 않습니다. 호스트 통합은 가져온 응답을 가져온 리소스를 교차 출처 저장소에 저장에 전달하며, 이 단계에서는 해당 응답에서 상한을 읽습니다.

8. 개인정보 보호 및 보안 고려 사항

이 절은 RFC 2119 키워드를 사용한 부분을 제외하면 비규범적입니다. 또한 보안 및 개인정보 보호 질문지를 이 저장소에서 참조하세요.

저장소의 개인정보 보호 분석에서는 이러한 고려 사항이 다루는 공격과 각 완화책으로 대응할 수 있는 범위를 설명합니다.

8.1. 리소스 무결성

모든 COS 항목은 암호학적 해시를 키로 사용하며, 바이트도 그 해시와 대조하여 검증합니다( § 3.3 파일 생성 및 쓰기 참조). 따라서 사이트는 다음 메서드를 통해 얻은 파일, 즉 getFileHandle()로 얻은 파일의 바이트가 직접 가져왔을 때 얻었을 바이트와 정확히 같음을 hash를 기준으로 확신할 수 있습니다. 개발자는 교차 출처 저장소의 내용을 열거하거나 해시를 미리 알지 못하는 파일에 접근할 수 없습니다.

COS 해시는 비밀이 아닙니다. 이는 콘텐츠 식별자이며, 파일을 이미 가진 사람이라면 누구나 손쉽게 계산할 수 있습니다. 이 명세가 대상으로 하는 널리 배포되는 리소스의 경우 보통 공개적으로 알려져 있으며, 모델이나 라이브러리를 출시할 때 함께 공개하는 경우도 많습니다. 따라서 해시를 알면 항목을 조회할 수 있지만, 해시만으로는 접근 권한이 생기지 않습니다. 조회의 성공 여부는 전적으로 origins와 § 8.4 가용성 제한에 의해 결정됩니다. 개발자는 공개되지 않은 해시를 접근 제어 수단으로 취급해서는 안 됩니다. 특정 파일에 관심이 있는 공격자는 해시를 추측할 필요 없이 파일 자체만 얻으면 됩니다(§ 8.2 사이트 간 탐색 참조).

8.2. 사이트 간 탐색

리소스를 사용하는 사이트가 소수에 불과하다면, 공격자는 해당 리소스가 교차 출처 저장소에 있음을 알았을 때 사용자가 그중 한 사이트를 방문했을 가능성이 크다고 추론할 수 있습니다. getFileHandle()은 존재 여부를 알아내는 수단이므로, 호출 한 번은 사실상 탐색 한 번에 해당합니다. 이 명세에서는 탐색으로 알 수 있는 정보를 세 가지 방식으로 제한합니다.

  • origins( § 3.5 리소스 공개 범위 확대 참조)를 사용하면 저장 측 출처가 선택한 출처 집합과 그 출처들과 동일 사이트인 출처로 공개를 제한할 수 있습니다. 따라서 독점 리소스나 사용 빈도가 낮은 리소스를 굳이 전역에서 탐색할 수 있게 할 필요가 없습니다.

  • § 8.4 가용성 제한은 추가로 "*" 범위의 리소스에 대해 요청 측 출처가 해당 리소스의 저장 출처에 없으면, 해시가 PHL에 포함된 경우에만 공개를 허용합니다. 따라서 리소스를 저장할 때 origins: "*"를 지정해도 웹상의 모든 출처가 자동으로 그 리소스를 탐색할 수 있게 되지는 않습니다. 이 제한은 "*" 범위의 항목에만 적용됩니다. 목록 또는 동일 사이트 범위의 항목에는 첫 번째 항목의 제한만 적용됩니다. 저장 측 출처가 이미 이들 항목의 공개 범위를 명시적으로 제한했기 때문입니다.

  • 사이트 간 조회 예산은 최상위 사이트가 한 조회 구간에 수행할 수 있는 탐색 횟수를 제한하므로, 개별적으로는 흔한 파일들의 특정 조합을 마음대로 검사할 수 없습니다.

첫 번째 항목은 "선택한 출처 집합"의 범위가 웹 전체보다 충분히 작을 때에만 성립합니다. origins의 형식 자체에는 호출자가 매우 많은 출처를 열거하는 것을 막는 제약이 없습니다(예를 들어 공개된 인기 사이트 순위로 목록을 작성할 수 있습니다). 이는 기능적으로 전역 공개에 가까우면서도 "*"만이 요구하는 의도적이고 명시적인 동의를 거치지 않게 됩니다. 최대 출처 목록 길이( § 5.1 저장 한도 참조)가 이를 제한합니다. 실제로 여러 서비스를 함께 운영하는 사용 사례 (동일한 운영 주체가 제어하는 소수의 관련 출처)는 수용하되, "모든 출처"에 의미 있게 근접하기에는 턱없이 작게 한도를 정하면 origins의 제한된 출처 형식이 명시적으로 선언하지 않은 "*"의 대용으로 쓰이는 것을 막을 수 있습니다.

참고: § 9 다른 명세와의 통합에 나오는 호스트 통합을 통한 조회도 페이지에 오류를 표시하지는 않지만 마찬가지로 탐색입니다. 사이트는 자체 서버가 대체 요청을 받았는지 관찰할 수 있으며, 이는 "NotFoundError"가 전달하는 것과 같은 1비트입니다. 따라서 같은 제한을 적용하며, 사이트 간 조회 예산에도 이를 getFileHandle() 호출과 함께 집계합니다. 스크립트로 제어할 수 있는 통합도 반복문에서 똑같이 쉽게 조회를 수행할 수 있기 때문입니다.

8.3. 진행 중인 쓰기

요청되었지만 완료되지 않은 쓰기는 어떤 출처에서도 한 번도 쓰지 않은 해시와 구별할 수 없어야 합니다. 이 명세의 구조가 이를 보장합니다. COS 항목을 COS 레지스트리에 추가하는 것은 검증 및 저장 또는 가져온 리소스를 교차 출처 저장소에 저장뿐이며, 두 경우 모두 바이트 전체를 해시와 대조하여 검증한 뒤에만 추가합니다. 생성 요청 완료는 레지스트리를 읽지도 쓰지도 않습니다. 따라서 읽기로 관찰할 수 있는 자리표시자 상태가 없으며, 읽기 경로에는 가용성 제한 적용보다 먼저 응답할 수 있는 분기도 없습니다.

이와 달리 생성 요청 시 자리표시자를 등록하고 동시에 이루어지는 읽기를 구별 가능한 오류로 거부한다면, 호출자는 어떤 출처가 바로 지금 특정 해시를 쓰고 있음을 알 수 있습니다. 이 1비트는 사소해 보이지만 그렇지 않습니다. 다음과 같이 이용할 수 있기 때문입니다.

  • 항목에 어떠한 접근 권한도 없는 출처를 포함하여 모든 출처가 알 수 있습니다. 자리표시자는 공유 레코드를 갖지 않으며, 읽기에 대한 응답은 가용성 제한 적용 전에 이루어지기 때문입니다.

  • 어떤 해시에 대해서든 알 수 있습니다. PHL에 포함되어 있지 않고 앞으로도 포함될 수 없는 해시도 해당하므로, 공격자가 사용자별 값에서 파생된 해시를 이용할 수 있습니다(§ 8.8 핑거프린팅 참조).

  • GREASE 적용을 거치지 않습니다. 이는 공개 여부가 제한 단계에 도달한 경우에만 적용되므로 해당 비트에는 잡음이 없습니다.

  • 바이트를 전혀 제공하지 않아도 되므로 출처별 저장 한도도, 해당 COS 쓰기 한도도, § 5.2 퇴거도 한 출처가 만들어 낼 수 있는 이러한 비트의 수를 제한하지 못합니다.

따라서 두 사이트에 삽입된 추적기는 첫 번째 사이트에서 임의 길이의 식별자를 만들고 두 번째 사이트에서 이를 다시 읽을 수 있습니다. 저장 공간을 소모하지 않으면서 origins, 공개 해시 목록, GREASE 적용을 모두 우회하는 셈입니다. 자리표시자는 서비스 거부의 원인이 될 수도 있습니다. 실제로 널리 쓰이는 리소스의 해시가 자리표시자에 묶이면 다른 모든 출처가 해당 리소스를 읽지 못하는 상태가 자리표시자가 남아 있는 동안 계속될 수 있습니다.

참고: 이 설계로 잃는 것은 한 호출자가 다른 호출자가 이미 대용량 파일을 다운로드하고 있음을 알아내어 중복 다운로드를 피하는 기능입니다. 이는 실제 비용이며, 이 명세의 이전 초안에서 이 경우에 구별 가능한 오류를 사용했던 이유이기도 합니다. 이 기능이 가장 필요한 단일 출처 내에서는 웹 잠금, BroadcastChannel 또는 공유 워커를 사용해 이 기능을 되살릴 수 있으며, 이들 수단 중 어느 것도 출처 경계를 넘어 정보를 공개하지 않습니다. 출처 간의 절감 효과는 대체로 이론적입니다. 서로 무관한 두 출처가 같은 순간에 동일한 해시를 두고 경합해야 하고, 두 출처 모두 아직 쓰지 않은 항목은 어차피 PHL에 포함되기 전까지 상대방에게 공개할 수 없기 때문입니다.

참고: "NotAllowedError"는 여전히 getFile()을 다음과 같은 핸들에서 호출할 때의 응답입니다. 생성 요청으로 얻었지만 아직 쓰기에 사용하지 않은 핸들입니다(§ 4 교차 출처 저장소 파일 시스템 참조). 이 응답은 레지스트리의 내용에 관계없이 일정하며 요청한 출처에만 전달됩니다. 핸들은 출처 간에 역직렬화할 수 없으므로(§ 4.1 핸들 전달 참조), 이 응답은 정보 전달 경로가 되지 않습니다.

8.4. 가용성 제한

getFileHandle()을 통한 읽기를 요청한 출처가 저장 출처에 없다면, 성공 여부는 언제나 요청 측 출처가 항목을 읽도록 허가되었는지에 달려 있습니다. 이를 결정하는 것은 origins입니다. "*" 범위의 항목에는 이와 독립적인 두 번째 조건도 적용됩니다. 바로 사용자 에이전트가 항목이 존재한다는 사실 자체를 공개할 것인지이며, 이는 PHL 포함 여부와 GREASE 적용에 따라 결정됩니다. 이러한 항목은 두 조건을 모두 충족해야 하며, 목록 또는 동일 사이트 범위의 항목에는 첫 번째 조건만 적용됩니다. 규범적 알고리즘은 § 3.2 파일 읽기를 참조하세요. 따라서 "NotFoundError"가 발생했다고 해서 리소스가 없다는 증거가 되지는 않습니다. 실제로 리소스가 없거나, 요청 측 출처가 범위 밖에 있거나, "*" 범위 리소스의 해시가 아직 PHL에 없거나 앞으로도 포함될 수 없거나, 또는 여전히 COS 사용자 활성화 조건을 기다리고 있거나, 요청 측 최상위 사이트가 이미 사이트 간 조회 예산을 소진했거나, GREASE 적용이 참양성 결과를 억제했다는 뜻일 수 있습니다. 개발자는 "NotFoundError"를 단순히 "네트워크에서 가져오기로 전환하라"는 것보다 더 구체적인 의미로 해석해서는 안 됩니다.

참고: 공개 해시 목록만으로는 전역 범위를 제한하지 못합니다. 개별 리소스가 각각 PHL 등재 요건을 충족하더라도 그중 어느 부분집합이 저장되었는지가 사이트 간 식별자가 될 수 있기 때문입니다. 사이트 간 조회 예산, COS 사용자 활성화 조건, 그리고 COS 쓰기 한도가 이를 제한합니다. 이들 중 어느 것도 사용자의 서드 파티 쿠키 설정에 의존하지 않습니다.

참고: 사이트 간 조회 예산에서 조회 사용량을 부과하지 않는 것은 읽는 측 자신의 최상위 사이트에서 작성한 공유 레코드를 통해 응답하는 경우뿐입니다( 사용량이 부과되지 않는 조회인지 판정 참조). 이는 저장 출처 레코드 또는 origins 레코드 중 그 partition이 동일 사이트 관계에 있는 것으로, 비교 대상은 읽는 측의 COS 파티션입니다. 그 밖의 모든 조회는 항목을 찾았는지에 관계없이 집계합니다. 여기에는 다른 최상위 사이트에서 작성한 first-party origins 레코드를 통해 응답하는 조회도 포함됩니다. Cross-Origin-Storage-Allow-Origin 헤더는 주입된 콘텐츠가 그런 읽기 주체를 지정하지 못하게 합니다. 쓰기 측 사이트의 운영자는 여전히 어떤 출처든 지정할 수 있으므로, 사용량을 부과하지 않으면 협력하는 두 사이트에서 한쪽이 표식 파일을 만들 때 목록에 상대방을 지정하여 서로 다른 방문 사이에도 길이 제한 없이 식별자가 전달될 수 있습니다. 조회가 예산 초과로 거부되면 "NotFoundError" DOMException으로 거부되며, 이는 항목을 찾지 못했을 때와 정확히 같습니다. COS 사용자 활성화 조건은 GREASE 적용과 마찬가지로, 오직 전역 범위를 통해서만 자격을 얻는 출처에 적용됩니다. 저장 출처, 명시적 origins 목록에 있는 출처, 그리고 두 종류 중 하나와 동일 사이트인 출처는 COS 공개 여부 결정이 항목을 반환하는 즉시 읽을 수 있습니다.

8.5. 개발자 지침

일부 정보 유출은 정보가 유출되는 사이트에 공격자가 없어도 발생합니다. 로그인한 사용자에게만 파일을 저장하는 사이트나 사용자마다 다른 바이트를 저장하는 사이트는 그 파일을 조회할 수 있는 모든 사이트에 해당 상태를 공개하게 되며, 자체 원격 측정 데이터에는 이 사실이 나타나지 않습니다. 사용자 에이전트는 개발자가 쓰기를 수행하는 시점에 그 쓰기로 무엇이 노출되는지 콘솔 경고 또는 개발자 도구로 알리는 것이 기대됩니다. 메시지를 표시할 만한 경우는 다음과 같습니다.

  • "*"를 요청한 쓰기에서 해시가 PHL에 포함되어 있지 않아 동일 사이트 범위가 유지되는 경우( 리소스 공개 범위 확대 참조).

  • origins 목록이 COS 범위 상한에 따라 일부 잘렸거나( COS 범위 상한 적용 참조), 최대 출처 목록 길이에 도달한 경우.

  • 출처별 저장 한도 또는 COS 쓰기 한도에 의해 쓰기가 거부된 경우.

8.6. GREASE 적용

사용자 에이전트는 GREASE 적용(무작위 확장을 생성하고 확장성을 유지하는 기법)을 사용할 수 있습니다. 이는 때때로 공개 가능한 항목이 없는 것처럼 응답하는 것으로, § 8.4 가용성 제한이 원래는 공개를 허용하는 경우에도 그렇게 합니다. 이를 통해 잡음을 더함으로써, 사이트가 실제 부재와 개인정보 보호를 위한 거짓 음성을 구별하기가 어려워집니다. 이는 사용자 에이전트 클라이언트 힌트에 사용되는 기법과 유사합니다.

GREASE 적용은 오직 전역 범위를 통해서만 자격을 얻는 출처에 적용됩니다. 이는 공개 해시 목록이 제한하는 경우와 같습니다(COS 공개 여부 결정 참조). 사용자 에이전트는 이를 저장 출처나 명시적 origins 목록에 있는 출처, 또는 두 종류 중 하나와 동일 사이트인 출처에 적용해서는 안 됩니다.

GREASE를 적용하는 사용자 에이전트는 해당 항목의 크기에 비례하여 판단해야 합니다. 항목이 작아 네트워크에서 다시 가져오는 비용이 낮다면 간헐적인 거짓 음성은 개인정보 보호를 위해 감수할 만한 비용입니다. 사용자 에이전트는 항목이 너무 커서 불필요한 재다운로드 비용이 그에 따른 개인정보 보호 효과에 비해 명백히 과도한 경우 (예를 들어 기가바이트 규모의 AI 모델 가중치)에는 GREASE를 적용해서는 안 됩니다. 이런 경우 거짓 음성으로 인해 전체 데이터를 다시 다운로드해야 하며, 이는 관찰 가능하고 비용도 크기 때문입니다. 사이트 간 조회 예산은 이러한 항목의 조회 횟수를 제한하며, GREASE 적용 여부를 알아내려고 같은 조회를 반복할 때마다 사용량을 부과합니다.

8.7. 파생 산출물 타이밍

파생 산출물을 재사용하는 것은 새로 계산하는 것보다 빠르므로 관찰할 수 있습니다. 산출물에 페이지가 선택한 입력이 없으면, 공개되는 정보는 다음 값을 제공한 읽기에서 이미 드러난 정보뿐입니다. 바로 해당 산출물의 sources입니다. 페이지가 선택한 입력에는 식별자가 담길 수 있습니다. 서로 협력하는 사이트의 스크립트가 선택한 특이한 연산자 옵션과 다른 사이트에서 관찰되는 계산 시간의 차이가 식별 정보를 드러낼 수 있습니다. 이와 같은 재사용을 매번 사이트 간 조회 예산에 산입하면, 공개되는 정보는 조회를 통해 이미 공개되는 범위로 제한됩니다.

8.8. 핑거프린팅

공격자가 교차 출처 저장소를 탐색하여 얻을 수 있는 정보는 탐색 대상 리소스가 얼마나 널리 쓰이는지에 따라 제한됩니다. 사용자가 흔한 AI 모델이나 널리 쓰이는 JavaScript 라이브러리처럼 매우 대중적인 리소스를 보유했다는 사실은, 사용자가 그 리소스를 쓰는 수많은 사이트 중 하나를 방문했다는 정도만 드러냅니다. 드물거나 고유한 리소스를 보유했다는 사실은 훨씬 많은 정보를 드러냅니다.

드물거나 사용자마다 다른 해시는 PHL에 포함되지 않으므로, 다른 사이트는 오직 origins 목록 중 쓰기 측 운영자가 허가한 목록을 통해서만 이를 읽을 수 있습니다. 또한 사이트 간 조회 예산은 다른 최상위 사이트에서 이루어진 이러한 읽기에 사용량을 부과합니다. 남는 위험은 사람이 직접 선별하는 AI 모델 부문을 통해 등재된 특수 용도의 모델처럼, PHL에 있지만 보유한 장치가 적은 해시입니다. 이 경우 단 한 번의 조회로 특정인을 가리킬 수 있으며, 한 번의 조회로 충분한 공격은 조회 예산으로 제한할 수 없습니다. PHL 등재는 공개를 허가할 뿐이므로, 사용자 에이전트는 언제든지 그러한 항목을 자체 스냅숏에서 제외하거나 사람이 선별한 부문 전체를 생략할 수 있습니다. 사용자 에이전트는 장치 내 휴리스틱을 적용하여 탐색 패턴을 감지하고 차단할 수도 있습니다.

9. 다른 명세와의 통합

이 절은 비규범적입니다.

여기서 정의한 COS 레지스트리에는 네 가지 호스트 통합을 통해서도 접근할 수 있으며, 이때 getFileHandle()을 직접 거칠 필요가 없습니다. 각 통합은 해당 호스트 명세에서 정의합니다. 이 명세는 공통으로 사용하는 기본 개념(COS 해시, COS 항목, 가용성 제한 및 공개 해시 목록)과 가져온 리소스를 교차 출처 저장소에 저장 단계를 정의하며, 이러한 통합은 이를 기반으로 할 것으로 기대됩니다.

  • HTML: crossoriginstorage 속성을 link 및 script 요소에 사용하는 방식으로, 해당 요소에는 이미 integrity [SRI]가 있어야 합니다. WHATWG에 제안된 이슈는 whatwg/html#12770입니다.

  • JavaScript: 호스트가 정의한 crossOriginStorage 가져오기 속성으로, 함께 사용할 수 있는 속성은 integrity입니다. 이는 가져오기 속성 제안을 기반으로 하며, WHATWG에 제안된 이슈는 whatwg/html#12771입니다.

  • CSS: cross-origin-storage() <request-url-modifier>로, integrity()와 함께 사용할 수 있습니다. CSS 작업 그룹에 제안된 이슈는 w3c/csswg-drafts#14056입니다.

  • Fetch: crossOriginStorage라는 RequestInit 옵션으로, 함께 사용할 수 있는 옵션은 integrity [FETCH]입니다. WHATWG에 제안된 이슈는 whatwg/fetch#1954입니다. 이 방식에는 호스트가 정의한 목적지가 없으며, COS 항목은 bytes만 저장하므로, 해당 명세에서 Response를 정의합니다. 이 응답은 COS 레지스트리에서 제공됩니다. 예상되는 형태는 성공 응답으로, 상태는 200, 상태 메시지는 OK이며, 본문은 bytes의 스트림입니다. Content-Type 헤더는 해당 호출자가 선언한 MIME 유형이며, 네트워크에서 가져오지 않았으므로 다른 헤더는 없습니다. 이 옵션에는 GET 메서드가 요구될 것으로 예상됩니다. 항목을 찾으면 요청을 전송하지 않고 응답하는데, 이는 요청 본문도 부수 효과도 없는 메서드에만 안전하기 때문입니다. 따라서 Request 생성자는 TypeError를 다른 모든 메서드에 대해 던지게 됩니다.

다음은 동일한 전역 공유 리소스에 대해 교차 출처 저장소 사용을 명시하는 네 가지 형식을 각각 보여 주는 예시입니다.

<script src="popular-library.js" integrity="sha256-abc123..." crossoriginstorage="*"></script>

import data from "popular-resource.ext" with {
  integrity: "sha256-abc123...",
  crossOriginStorage: "*",
};

@font-face {
  font-family: "Popular Font";
  src: url("popular-font.woff2" integrity("sha256-abc123...") cross-origin-storage(*));
}

const response = await fetch("popular-resource.ext", {
  integrity: "sha256-abc123...",
  crossOriginStorage: "*",
});

이 코드 조각들은 예시일 뿐입니다. 이 명세는 이러한 구문을 정의하지 않습니다. 제한된 출처 목록을 표기하는 방법을 포함하여 각 형식의 정식 문법은 해당 호스트 명세에서 정합니다. 표기가 의도적으로 다른 이유는 RequestInit 멤버가 sequence<DOMString>을 받을 수 있어 origins와 정확히 일치하는 반면, 속성값과 가져오기 속성값, CSS 수정자 인수는 텍스트만 담을 수 있기 때문입니다.

네 형식 모두 다음 처리 모델을 공유할 것으로 예상됩니다. 우선 COS 레지스트리에서 일치하고 공개 가능한 항목을 찾아보고, 없으면 네트워크에서 가져오며, 성공적으로 가져와 무결성이 검증된 리소스를 COS 레지스트리에 저장하여 다른 출처가 재사용할 수 있게 합니다. 이는 getFileHandle()의 동작과 정확히 같습니다. 저장 단계는 가져온 리소스를 교차 출처 저장소에 저장이며, 각 통합은 이 단계를 가져온 응답에 대해 수행합니다. 따라서 제한된 출처 값은 해당 리소스 응답의 Cross-Origin-Storage-Allow-Origin 헤더에 의해 제한되며, 이 헤더는 바이트를 제공하는 서버가 보냅니다(§ 7 Cross-Origin-Storage-Allow-Origin 헤더 참조). 이러한 통합에 관한 논의는 각 통합을 포함할 호스트 명세의 이슈 추적기에서 진행하며, 이 저장소의 이슈 추적기에서 진행하지 않습니다.

9.1. 리소스 타이밍

위 통합 중 하나가 COS 레지스트리에서 제공한 리소스도 리소스 타이밍 [RESOURCE-TIMING]에는 가져온 다른 리소스와 마찬가지로 보고됩니다. 이때 응답은 일치하는 항목을 찾아 제공한 것이므로, 그 캐시 상태는 "local"로 설정될 것으로 예상됩니다. 네트워크에서 가져오지 않았기 때문입니다. 또한 타이밍 허용 검사 통과 플래그는 설정될 것으로 예상됩니다. 관여한 서버 중 타이밍 정보를 보호해야 할 서버가 없기 때문입니다. 그리고 응답의 본문 정보의 인코딩된 크기와 디코딩된 크기는 bytes의 길이로 설정될 것으로 예상됩니다. 이는 Cache API가 저장한 응답을 처리하는 방식과 같습니다 [SERVICE-WORKERS]. 통합은 "cross-origin-storage"를 전달 유형으로 지정하여 리소스 타이밍 기록에 전달할 것으로 예상됩니다. 그 결과 항목의 deliveryType의 값은 "cross-origin-storage"이고, transferSize는 0이며, encodedBodySize는 저장된 리소스의 크기입니다.

참고: 일치하는 항목을 찾았는지는 이미 타이밍과 서버에 요청이 도착하지 않았다는 사실을 통해 관찰할 수 있으므로, 이로 인해 § 8.4 가용성 제한에서 이미 다루는 범위를 넘어서는 정보가 공개되지는 않습니다.

deliveryType에 값을 하나 더 추가할 것을 제안합니다.

  Promise<FileSystemFileHandle> getFileHandle(
      CrossOriginStorageGetFileHandleHash hash,
      optional CrossOriginStorageGetFileHandleOptions options = {});

  boolean create = false;

이슈 색인

가져오기 프로토콜, 갱신 주기, 데이터 형식, 보급도 기준값, 운영 체계를 비롯한 공개 해시 목록의 세부 설계는 이 명세에 딸린 별도 자료에 기술되어 있습니다. 이는 공개 접미사 목록이 [URL] 표준에 딸린 데이터 파일인 것과 같은 취지입니다. 공개 해시 목록 해설서를 이 저장소에서 참조하세요. 이 설계는 WHATWG가 운영을 맡는 방안을 제안합니다. 이는 공개 접미사 목록에서 여러 공급업체가 공동으로 수시로 릴리스해 온 선례를 따르며, 등재 기준은 널리 쓰인다는 사실이 독립적으로 확인되었는지에 둡니다. 이는 앞서 설명한 k-익명성 방식의 기준을 구체화한 것으로, 오프라인에서 한 번만 해시 등재 절차의 일부로 적용하므로 사용자 에이전트가 조회할 때마다 반복하지 않습니다. 이러한 사항은 아직 이 제안 밖에서 확립되지 않았습니다. 목록 자체의 초기 비규범적 코드 프로토타입은 현재 이 저장소의 다음 위치에 있습니다. public-hash-list/implementation/. 여러 공급업체가 공동으로 관리하는 전용 저장소는 여전히 PHL 해설서에서 제시하는 운영 목표입니다. 이 명세는 해시가 PHL에 포함되었는지에만 의존하므로, 앞으로 목록을 가져오는 방식이나 운영 모델, 그 밖의 설계가 어떻게 바뀌어도 유효합니다. ↵
파일 시스템 표준 [FS]에는 아직 이 표준에 의존하는 명세가 쓰기별 추가 검증을 FileSystemWritableFileStream의 닫기 단계에 연결할 수 있는 확장 지점이 정의되어 있지 않습니다. 이러한 훅이 생길 때까지 이 절에서 필요한 동작을 직접 설명하며, 향후 개정에서는 [FS]와 정식으로 통합할 예정입니다. ↵
이 절에서는 워커용 권한 정책 [WORKERS-PERMISSIONS-POLICY]이 마치 이미 [permissions-policy] 및 [HTML]의 일부인 것처럼 이를 사용합니다. 이 제안은 해설서이며, 워커 정책이나 SharedWorker의 allow 옵션, 또는 이 절에서 언급하는 "서비스 워커에서 활성화할 수 있음" 불리언을 정의한 명세는 없습니다. 작성 시점에 Chromium은 공유 워커에 해당하는 부분을 플래그 (PermissionsPolicyForSharedWorkers) 뒤에서 구현하며, 이를 기본 제공하는 엔진은 없습니다. 해당 동작이 명세화되면 이 절에서는 그 동작을 직접 기술하는 대신 해당 훅을 호출하는 것이 좋습니다. ↵
Document의 COS 범위 상한을 해당 문서의 응답에서 채우려면, [HTML]의 문서 생성 단계에 훅이 필요합니다. 이는 [permissions-policy] 및 [CSP]의 값을 응답 처리 시점에 채우는 방식과 같습니다. 이 훅이 생길 때까지는 이 절에서 필요한 동작을 직접 기술합니다. 향후 개정에서는 이를 다음 [FS] 훅과 함께 정식으로 통합할 예정입니다(§ 3.3 파일 생성 및 쓰기 참조). WorkerGlobalScope의 COS 범위 상한에도 같은 종류의 훅이 워커 실행에 필요합니다. 호스트 통합에는 이러한 훅이 필요하지 않습니다. 호스트 통합은 가져온 응답을 가져온 리소스를 교차 출처 저장소에 저장에 전달하며, 이 단계에서는 해당 응답에서 상한을 읽습니다. ↵
