초록

교차 출처 저장소(Cross-Origin Storage, COS)는 웹 애플리케이션이 AI 모델, WebAssembly 모듈, 널리 사용되는 JavaScript 라이브러리 등의 대용량 파일을 서로 다른 출처 간에 저장하고 검색할 수 있도록 하는 콘텐츠 주소 지정 가능 캐시이다. 파일은 URL이 아니라 암호학적 해시로 식별되므로, 한 출처에서 한 번 가져온 바이트 단위로 동일한 리소스를 사용자 에이전트가 허용하는 다른 모든 출처에서 두 번째 다운로드 없이 재사용할 수 있다. 캐시의 존재 여부를 사용자가 방문한 사이트를 추론하는 데 이용하지 못하도록, 파일의 교차 출처 공개는 k-익명성 방식의 인기도 기준을 충족하는 해시로 제한된다.

1. 소개

이 절은 비규범적입니다.

스토리지는 일반적으로 사용자의 보안과 개인정보를 보호하기 위해 오리진별로 분할됩니다. 이는 올바른 기본값이지만, 매우 크고 널리 사용되며 공개적으로 배포되는 일부 리소스에는 적합하지 않습니다. 이러한 리소스(AI 모델, WebAssembly 모듈, JavaScript 라이브러리, 게임 엔진 및 대형 웹 글꼴)는 어떤 사이트가 요청하더라도 바이트 단위로 동일한 파일입니다. 서로 관련 없는 두 오리진이 각각 동일한 8 GB 모델에 의존하는 경우, 오리진별로 분할된 스토리지는 사용자가 해당 모델을 두 번 다운로드하고 보관하도록 하므로 사용자의 대역폭, 스토리지, 배터리뿐 아니라 전체 네트워크에도 낭비가 됩니다.

Cross-Origin Storage(COS)는 URL이 아니라 암호학적 해시를 키로 사용하는 콘텐츠 주소 지정 가능 캐시로, 사용자 에이전트가 이러한 리소스를 사용하는 데 동의한 오리진들 사이에서 저장된 단일 사본을 공유할 수 있도록 합니다. COS에 리소스를 저장하는 것은 항상 저장 오리진의 명시적인 옵트인 동작이며, 사용자 에이전트는 그렇지 않았다면 읽기가 허용될 오리진에 대해서도 리소스의 존재 확인을 보류할 수 있습니다. § 8 개인정보 보호 및 보안 고려 사항을 참조하십시오.

이 명세의 진입점은 getFileHandle() 메서드이며, crossOriginStorage를 통해 노출됩니다: 

const hash = {
  algorithm: 'SHA-256',
  value: '8f434346648f6b96df89dda901c5176b10a6d83961dd3c1ac88b59b2dc327aa4',
};
try {
  const handle = await navigator.crossOriginStorage.getFileHandle(hash);
  const file = await handle.getFile();
  // 파일로 무언가를 수행합니다.
} catch (err) {
  if (err.name === 'NotFoundError') {
    // Cross-Origin Storage에 (공개 가능한 상태로) 존재하지 않습니다. 대신 네트워크에서 가져옵니다.
  }
}

이 명세는 FileSystemFileHandle, FileSystemWritableFileStream, 및 관련 File System Standard [FS]의 인프라를 재사용하며, 이는 전용 파일 시스템으로 범위가 한정되고 오리진 간에 공유되며 어떤 오리진의 비공개 또는 사용자에게 표시되는 파일 시스템과도 분리됩니다.

이 명세는 명령형 JavaScript API와 호스트 통합이 기반으로 삼는 공유 저장 단계를 정의합니다. 관련 제안은 동일한 기반 캐시를 다른 호스트 명세에 통합합니다. HTML의 link 및 script에 대한 crossoriginstorage 속성, crossOriginStorage JavaScript import 속성, CSS cross-origin-storage() <request-url-modifier>, 그리고 fetch()의 crossOriginStorage RequestInit 옵션입니다. 각각은 자체 호스트 명세에서 정의됩니다. § 9 다른 명세와의 통합을 참조하십시오.

2. 개념

2.1. 해시

COS 해시는 다음 구조체이며 다음 항목을 가집니다:

algorithm

문자열로, [WEBCRYPTO]에서 인식하는 해시 알고리즘의 이름입니다. 예: "SHA-256".

value

문자열로, algorithm이 생성한 다이제스트를 소문자 16진수로 인코딩한 값입니다. "SHA-256"의 경우 길이는 64자입니다.

algorithm 사전 멤버의 타입은 일반 DOMString입니다. 그 값 공간이 정확히 [WEBCRYPTO]의 해시 알고리즘이 허용하는 이름의 집합임에도 그렇습니다. HashAlgorithmIdentifier 는 (object or DOMString)이며, 그 object 분기는 [WEBCRYPTO]에 의해 Algorithm 형태의 사전으로 정규화되어, 호출자가 필요한 알고리즘에 추가 매개변수를 전달할 수 있게 합니다(예: {name: "HMAC", hash: "SHA-256"}). 해시 알고리즘은 이러한 매개변수를 사용하지 않으며, algorithm은 콘텐츠 주소 지정 가능 키의 일부로 저장되고 비교되며 왕복 처리되고, 이 명세의 예에서 모든 사용은 단순 문자열입니다. 여기에서 임의 객체를 허용하면 기능은 추가되지 않으면서 동등성 및 직렬화만 불필요하게 복잡해집니다. 따라서 DOMString이 이 필드에 더 좁고 더 올바른 타입입니다.

두 COS 해시 값은 동일합니다. 각각의 algorithm 값이 ASCII 대소문자를 구분하지 않고 일치하며, 각각의 value 값이 정확히 동일한 경우입니다.

참고: value는 이미 규범적으로 소문자이므로(위 참조), 이를 비교하는 것은 단순한 문자열 비교입니다. algorithm에는 규범적인 대소문자 규칙이 없으므로 ASCII 대소문자를 구분하지 않고 비교합니다.

콘텐츠 주소 지정 가능 저장소란 그 항목이 동등성을 기준으로 COS 해시를 키로 사용하는 저장소입니다. 즉, 동일한 바이트와 동일한 해시 알고리즘을 가진 두 파일은 몇 개의 오리진이 저장했는지 또는 몇 개의 URL에서 가져왔는지와 관계없이 동일한 항목입니다.

2.2. COS 항목

각 사용자 에이전트에는 단일 COS 레지스트리가 있으며, 이는 맵으로서 COS 해시 값을 COS 항목 구조체에 매핑하며, Cross-Origin Storage를 사용하는 모든 오리진이 공유합니다. COS 항목에는 다음 항목이 있습니다:

hash

COS 해시.

bytes

바이트 시퀀스로, hash의 algorithm으로 계산한 다이제스트가 hash의 value와 같습니다.

참고: 항목은 작성자가 이 바이트를 제공하고 사용자 에이전트가 이를 검증한 후에만 COS 레지스트리에 추가됩니다. 검증 및 저장을 참조하십시오. 요청되었지만 완료되지 않은 쓰기는 레지스트리에 전혀 표현되지 않으며, 이 때문에 진행 중인 쓰기는 읽기 경로에서 존재하지 않는 것과 구별되지 않습니다. § 8.3 진행 중인 쓰기를 참조하십시오.

origins

명시적인 교차 오리진 읽기 접근 권한을 부여받은 오리진의 목록으로, 공개 해시 목록과는 독립적입니다. 이 권한은 목록의 항목과 동일 사이트인 모든 오리진으로 확장되므로 목록에 https://a.example을 지정하면 https://www.a.example도 허용됩니다. 처음에는 비어 있으며, 이후에는 증가하기만 합니다. 이는 항목을 누가 읽을 수 있는지 결정하는 서로 독립적이며 가산적인 세 가지 권한 중 하나이며, 나머지 두 가지는 저장 오리진(항상 읽을 수 있으며, 해당 오리진과 동일 사이트인 오리진도 포함)과 전역적으로 공개 가능 상태입니다.

참고: origins 가 명시적인 빈 목록 (origins: [])인 쓰기는 origins 를 생략한 쓰기와 정확히 같은 권한을 부여합니다. 즉, 항목의 저장 오리진과 그 오리진들과 동일 사이트인 오리진이라는 모든 항목의 기본 권한입니다 (COS 공개 여부 결정 참조). 상한 적용은 빈 목록을 null로 바꾸므로, 두 쓰기는 나머지 생성 요청 완료 과정에 동일한 상태로 도달합니다. 명시적인 목록은 수신자를 추가하기만 하며, 작성자 자신의 사이트에서 항목을 숨기지는 않습니다.

전역적으로 공개 가능

처음에는 false인 불리언으로, 항목이 전역("*") 가용성을 요청하여 작성되었는지를 기록합니다. true이면, 해당 항목은 요청이 § 8.4 가용성 게이팅을 통과하는 모든 오리진에서 읽을 수 있습니다. 즉, 해당 hash가 PHL에 있고 GREASE 처리가 이를 억제하지 않는 경우입니다. 한 번 설정되면 계속 true로 유지됩니다.

참고: 이는 항목인 origins와는 별개이므로, 이후의 전역 가용성 요청은 기존의 명시적 origins 목록에 "*" 권한을 추가합니다. 둘을 하나의 필드로 합친다면, 바이트를 제공한 작성자가 목록 범위 항목을 "*" 범위 항목으로 바꿀 수 있습니다. § 8.4 가용성 게이팅은 "*" 권한에만 적용되므로, 이전에 목록을 통해 항목을 읽을 수 있었던 오리진은 이후 "NotFoundError"를 hash가 PHL에 있지 않을 때마다 받게 됩니다. 두 권한을 독립적으로 유지하면 모든 가시성 변경이 엄격하게 추가만 이루어지며, 이는 업그레이드할 수 있지만 절대로 다운그레이드할 수 없음이 요구하는 바입니다.

저장 오리진

각각 이 항목의 바이트 쓰기를 한 번 이상 성공적으로 완료한 오리진의 집합입니다. 페이지 로드 사이에도 유지되고 시간이 지나며 증가하며, § 5.2 축출에 설명된 경우를 제외하면 줄어들지 않습니다. 저장 오리진에 속한 오리진은 항상 getFileHandle()를 통해 해당 항목의 핸들을 얻을 수 있으며, origins 또는 항목의 hash가 공개 해시 목록 (PHL)에 있는지와 무관합니다. § 3.5.1 원래 저장자의 접근을 참조하십시오.

사용자 에이전트에는 연결된 Cross-Origin Storage 큐가 있으며, 이는 새 병렬 큐 시작의 결과입니다. COS 레지스트리에 대한 모든 작업은 이 큐에 큐에 추가되어야 하므로 큐에 추가된 순서대로 실행되며 서로 끼어들지 않습니다.

2.3. 공개 해시 목록

해시가 Cross-Origin Storage에 존재하는지 확인하는 행위 자체가 사용자의 탐색 기록에 관한 정보를 유출할 수 있습니다(§ 8.2 교차 사이트 탐색 참조). 이는 특히 전역 권한에서 위험합니다. 항목의 명시적 origins 목록과 모든 항목이 가지는 동일 사이트 기본 권한은 이미 저장 오리진의 명시적 선택에 의해 공개 범위가 제한되어 있는 반면, 항목을 전역적으로 공개 가능하게 만들면 잠재적으로 웹의 모든 오리진에 노출됩니다. 이러한 특정 위험을 제한하기 위해, 전역적으로 공개 가능한 리소스는 그 권한을 통해 해당 저장 오리진 외부의 오리진에 공개되려면 그 해시가 추가적인 독립 게이트를 통과해야 합니다. 즉, 공개 해시 목록 (PHL)이라는 공급업체 중립적이고 구현 정의된 COS 해시 값의 허용 목록에 포함되어야 합니다. 해시는 k-익명성 형태의 인기도 기준(예: 일정 최소 개수의 독립 오리진에서 바이트 단위로 동일하게 나타나는 경우)을 통과한 후에만 공개 해시 목록에 추가되므로, 공유 캐시에 존재하는지 확인해도 특정 사용자에 관한 정보가 되지 않습니다.

COS 해시 hash는 사용자 에이전트의 현재 공개 해시 목록 스냅샷의 항목과 동일하다면 공개 해시 목록에 있습니다.

공개 해시 목록의 검색 프로토콜, 업데이트 주기, 데이터 형식, 인기도 임계값 및 거버넌스는 이 명세의 동반 산출물로 상세하게 설계되며, [URL] 표준의 동반 데이터 파일인 공개 접미사 목록과 유사한 방식입니다. 이 저장소의 공개 해시 목록 설명서를 참조하십시오. 해당 설계는 Public Suffix List의 공급업체 간 롤링 릴리스 선례를 모델로 한 WHATWG 거버넌스와, 독립적으로 확인된 보편성을 기준으로 하는 등록 조건을 제안합니다. 이는 위에서 설명한 k-익명성 형태 기준의 구체적인 사례로, 해시가 등록될 때 오프라인에서 한 번 적용되므로 사용자 에이전트가 쿼리마다 이를 반복하지 않습니다. 이 내용 중 어느 것도 아직 이 제안 외부에서 확립되지 않았습니다. 목록 자체의 초기 비규범적 코드 프로토타입은 현재 이 저장소의 public-hash-list/implementation/에 있으며, 전용 공급업체 간 저장소가 PHL 설명서에 기술된 거버넌스 목표로 남아 있습니다. 이 명세는 해시가 PHL에 있는지에만 의존하므로 목록의 검색 메커니즘, 거버넌스 모델 또는 나머지 설계가 어떻게 발전하더라도 올바르게 유지됩니다.

3. CrossOriginStorageManager 인터페이스

[Exposed=(Window,Worker), SecureContext]
interface CrossOriginStorageManager {
  Promise<FileSystemFileHandle> getFileHandle(
      CrossOriginStorageGetFileHandleHash hash,
      optional CrossOriginStorageGetFileHandleOptions options = {});
};

dictionary CrossOriginStorageGetFileHandleHash {
  required DOMString value;
  required DOMString algorithm;
};

dictionary CrossOriginStorageGetFileHandleOptions {
  boolean create = false;
  (DOMString or sequence<DOMString>) origins;
};

interface mixin NavigatorCrossOriginStorage {
  [SameObject, SecureContext] readonly attribute CrossOriginStorageManager crossOriginStorage;
};
Navigator includes NavigatorCrossOriginStorage;
WorkerNavigator includes NavigatorCrossOriginStorage;

각 Navigator 및 WorkerNavigator 객체에는 연결된 CrossOriginStorageManager 객체가 있습니다. crossOriginStorage getter 단계는 this에 연결된 CrossOriginStorageManager를 반환하는 것입니다.

각 CrossOriginStorageManager 객체에는 연결된 오리진이 있으며, 객체가 생성될 때 this의 관련 설정 객체의 오리진으로 설정됩니다.

참고: 스크립트 자체에 관한 어떤 사항과도 무관하게 관련 설정 객체에서 오리진을 가져오는 것은 워커에 대해 명시할 가치가 있는 결과를 가집니다. blob: URL에서 생성된 워커는 이를 생성한 컨텍스트의 오리진을 가지므로 해당 오리진의 Cross-Origin Storage 뷰를 정확히 공유합니다. 즉, 그러한 워커가 쓴 것은 생성한 페이지에서 다시 읽을 수 있고, 페이지가 저장한 것은 워커가 읽을 수 있습니다. blob: URL은 자체 오리진이 아니며, 이를 취소해도 워커가 해당 뷰에서 분리되지 않습니다. data: URL에서 생성된 워커는 불투명 오리진을 가집니다. 이 명세는 현재 getFileHandle()가 호출하는 오리진이 불투명한 경우 무엇을 하는지 정의하지 않습니다. 불투명 오리진 규칙은 COS 요청 검증에서 호출자가 지정하는 오리진에만 적용됩니다. 불투명 오리진에는 저장 오리진 또는 동일 사이트 비교의 키로 사용할 안정적인 식별자가 없으므로 부여할 수 있는 의미 있는 권한이 없습니다.

3.1. getFileHandle() 메서드

handle = await navigator . crossOriginStorage . getFileHandle(hash)

hash로 식별되는 파일이 Cross-Origin Storage에 존재하고 호출 오리진에 공개 가능한 경우 해당 파일의 핸들을 반환합니다. 그렇지 않으면 "NotFoundError" DOMException으로 거부합니다. "NotFoundError"는 파일이 Cross-Origin Storage에 물리적으로 존재하지 않음을 증명하지 않습니다. § 8.4 가용성 게이팅을 참조하십시오. 호출자는 이를 "대신 네트워크에서 가져오십시오."로 처리할 수 있습니다.

handle = await navigator . crossOriginStorage . getFileHandle(hash, { create: true })

hash로 식별되는 파일을 Cross-Origin Storage에 쓸 수 있는 핸들을 반환하며, 아직 항목이 없으면 새 항목을 생성하고 기본적으로 동일 사이트 오리진으로 제한합니다. 호출자는 항목이 이미 존재했는지와 관계없이 핸들의 createWritable() 메서드를 통해 전체 파일 내용을 써야 합니다. 사용자 에이전트는 그 시점에 작성된 바이트가 hash로 해시되는지 검증하며, 그렇지 않으면 "DataError" DOMException으로 거부합니다. 이 요구사항은 오리진이 생성 요청을 hash가 이미 존재했는지를 알아내는 오라클로 사용하는 것을 방지합니다.

handle = await navigator . crossOriginStorage . getFileHandle(hash, { create: true, origins: "*" })

위와 같으며, 추가로 작성된 후에는 hash에 대한 요청이 § 8.4 가용성 게이팅을 통과하는 모든 오리진에 항목을 공개할 수 있게 합니다.

handle = await navigator . crossOriginStorage . getFileHandle(hash, { create: true, origins: ["https://a.example", "https://b.example"] })

위와 같으며, 공개를 나열된 오리진과 각각과 동일 사이트인 오리진으로 제한합니다(호출 오리진, 이미 저장 오리진에 있는 모든 오리진 및 이들과 동일 사이트인 오리진도 추가로 포함됩니다).

getFileHandle(hash, options) 메서드의 단계는 다음과 같습니다:

  1. result를 새 프로미스로 설정합니다.

  2. realm을 this의 관련 Realm으로 설정합니다.

  3. global을 this의 관련 전역 객체로 설정합니다.

  4. origin을 this에 연결된 오리진으로 설정합니다.

  5. global을 인수로 Cross-Origin Storage 권한 확인을 실행한 결과가 false이면 다음을 수행합니다:

    1. global을 인수로 전역 태스크를 큐에 추가하여 DOM 조작 태스크 소스에서 result를 "NotAllowedError" DOMException으로 거부하도록 합니다.

    2. result를 반환합니다.

  6. validationFailure를 hash와 options을 인수로 COS 요청 검증을 실행한 결과로 설정합니다.

  7. validationFailure가 null이 아니면:

    1. global을 인수로 전역 태스크를 큐에 추가하여 DOM 조작 태스크 소스에서 result를 validationFailure로 거부하도록 합니다.

    2. result를 반환합니다.

  8. 다음 단계를 큐에 추가하여 Cross-Origin Storage 큐에서 실행합니다:

    1. options["create"] 가 true이면:

      1. result, hash, options, global, 그리고 realm을 인수로 생성 요청 완료를 실행합니다.

    2. 그렇지 않으면:

      1. result, hash, origin, global, 그리고 realm을 인수로 읽기 요청 완료를 실행합니다.

  9. result를 반환합니다.

CrossOriginStorageGetFileHandleHash hash 와 CrossOriginStorageGetFileHandleOptions options을 인수로 COS 요청을 검증하려면 null 또는 TypeError를 반환합니다:

  1. hash["algorithm"] 이 [WEBCRYPTO]에서 인식하는 해시 알고리즘 이름이 아니면 새 TypeError를 반환합니다.

  2. hash["value"] 가 정규 표현식 /^[0-9a-f]{64}$/과 일치하지 않고 hash["algorithm"] 이 "SHA-256"과 ASCII 대소문자를 구분하지 않는 일치라면 새 TypeError를 반환합니다.

    참고: 향후 해시 알고리즘은 서로 다른 예상 다이제스트 길이를 정의할 수 있습니다. 이 명세는 전체 예에서의 사용과 일치하도록 "SHA-256"만 규범적으로 제한합니다.

  3. options["origins"] 가 존재하고 "*"가 아니라면:

    1. candidates를 options["origins"]로 설정하고, 단일 문자열은 하나의 항목을 가진 목록으로 취급합니다.

    2. candidates의 크기가 사용자 에이전트의 최대 origins 목록 길이보다 크면 새 TypeError를 반환합니다.

    3. candidates의 각 candidate에 대해 반복합니다:

      1. candidate에 기본 URL 파서를 실행한 결과가 실패이거나, 파싱된 URL의 오리진이 불투명 오리진이면 새 TypeError를 반환합니다.

  4. null을 반환합니다.

3.2. 파일 읽기

프로미스 result, COS 해시 hash, 오리진 origin, 전역 객체 global, 그리고 Realm realm을 인수로 읽기 요청을 완료하려면:

  1. entry를 COS 레지스트리에서 hash가 hash와 동일한 COS 항목으로 설정합니다. 없으면 null로 설정합니다.

    참고: 다른 작성자가 요청했지만 아직 완료하지 않은 쓰기는 COS 레지스트리에 없으므로, 그러한 해시에 대해 entry는 null이며 이 알고리즘은 어떤 오리진도 해당 해시를 작성한 적이 없는 경우와 정확히 동일하게 진행됩니다. 이 명세가 허용하는 모든 공개는 아래의 가용성 게이팅 적용에서 결정되며, 그 전에 응답할 수 있는 분기는 없습니다. § 8.3 진행 중인 쓰기를 참조하십시오.

  2. disclosableEntry를 entry와 origin을 인수로 가용성 게이팅 적용을 실행한 결과로 설정합니다.

  3. disclosableEntry가 null이면:

    1. global을 인수로 전역 태스크를 큐에 추가하여 DOM 조작 태스크 소스에서 result를 "NotFoundError" DOMException으로 거부하도록 합니다.

    2. 반환합니다.

  4. handle을 realm에서 disclosableEntry의 hash를 Cross-Origin Storage 파일 시스템 내에서 지정하는 로케이터를 가진 새 FileSystemFileHandle 생성 [FS]의 결과로 설정합니다.

  5. handle의 COS 해시를 disclosableEntry의 hash로 설정합니다.

  6. handle의 COS 오리진을 origin으로 설정합니다.

  7. handle의 읽기 가능을 true로 설정합니다.

    참고: 이 핸들은 이미 가용성 게이팅 적용을 통과했으므로 호출 오리진은 해당 항목의 바이트를 읽을 권한이 있습니다.

  8. global을 인수로 전역 태스크를 큐에 추가하여 DOM 조작 태스크 소스에서 result를 handle로 해결하도록 합니다.

COS 항목 또는 null인 entry와 오리진 origin을 인수로 COS 공개 여부를 결정하려면 COS 항목 또는 null을 반환합니다:

  1. entry가 null이면 null을 반환합니다.

    참고: COS 레지스트리의 항목은 항상 작성되고 검증된 것이므로 이 알고리즘에서 고려할 절반만 작성된 상태는 없습니다. 유일한 쓰기가 아직 진행 중인 해시는 레지스트리에 없으며 어떤 오리진도 작성한 적 없는 해시와 동일하게 null로 이 알고리즘에 전달됩니다. § 8.3 진행 중인 쓰기를 참조하십시오.

  2. origin이 entry의 저장 오리진에 있으면 entry를 반환합니다.

    참고: 원래 저장자와 자신이 해당 항목을 성공적으로 작성한 모든 오리진은 언제든지 다시 읽을 수 있습니다. § 3.5.1 원래 저장자의 접근을 참조하십시오.

  3. origin이 entry의 저장 오리진 중 어떤 항목과 동일 사이트이면 entry를 반환합니다.

    참고: 모든 항목이 가지는 동일 사이트 기본 권한 (origins 옵션 없이 쓰기를 수행할 때 요청되는 권한)은 이후 추가된 origins 목록 또는 전역적으로 공개 가능 권한과 관계없이 항상 유지됩니다. 이것은 아래의 공개 해시 목록 게이트보다 먼저 확인되므로, 동일 사이트 오리진은 항목의 hash가 PHL에 있는지 여부와 무관하게 읽을 수 있습니다. 여기에서 동일 사이트는 하나의 신뢰 단위이므로 이는 § 8.2 교차 사이트 탐색이 보호하는 사이트 경계를 넘어 아무것도 공개하지 않습니다.

  4. origin이 entry의 origins 중 어떤 항목과 동일 사이트이면 entry를 반환합니다.

    참고: 명시적 origins 목록의 오리진이나 그중 하나와 동일 사이트인 오리진은 항목이 PHL에 있을 필요 없이 읽을 수 있습니다. 각 나열된 오리진을 해당 사이트로 확장하는 것은 위의 동일 사이트 기본 권한을 그대로 반영합니다. 동일 사이트 오리진은 하나의 신뢰 단위이므로 사이트의 한 오리진을 지정하면 모두를 지정한 것입니다. 저장 오리진은 이를 지정함으로써 제한된 공개 결정을 내렸으며(§ 3.5 리소스 가시성 업그레이드 및 § 7 Cross-Origin-Storage-Allow-Origin 헤더 참조), 그 위에 별도의 전역적 보편성을 요구하면 일반적인 제한 공유가 흔히 독점적인 리소스에 대한 관계없는 공개 큐레이션에 의존하게 됩니다. 이를 전역적으로 공개 가능 게이트보다 먼저 확인하는 것이 이후의 전역 가용성 쓰기가 나열된 오리진의 접근을 취소하지 않도록 보장합니다. § 8.2 교차 사이트 탐색을 참조하십시오.

  5. entry의 전역적으로 공개 가능 값이 true이면:

    1. entry의 hash가 PHL에 있지 않으면 null을 반환합니다.

      참고: 공개 해시 목록 게이트는 전역 권한에만 적용되며, 이는 그렇지 않으면 웹의 모든 오리진까지 공개될 수 있는 유일한 경우입니다. 전역적으로 공개 가능하지만 hash가 PHL에 있지 않은 항목은 이 권한만으로 자격을 얻는 오리진에는 공개되지 않습니다. 하지만 저장 오리진, 명시적 origins 목록 또는 이 둘 중 하나의 동일 사이트 집합에도 속하는 오리진은 이미 위에서 반환되었습니다.

    2. 사용자 에이전트가 이 요청에 GREASE 처리를 적용하기로 선택하면 null을 반환합니다.

    3. entry를 반환합니다.

  6. null을 반환합니다.

3.3. 파일 생성 및 쓰기

생성 요청 완료에 의해 생성된 FileSystemFileHandle 에는 연결된 요청된 오리진이 있습니다. 이는 핸들에 성공적으로 쓰기가 완료된 후 검증 및 저장이 항목의 origins를 업그레이드하려고 시도할 값입니다.

Cross-Origin Storage 파일 시스템을 지정하는 모든 FileSystemFileHandle 에는 또한 연결된 COS 해시, 즉 그것이 지정하는 COS 해시와 연결된 COS 오리진, 즉 이를 얻은 오리진, 그리고 연결된 읽기 가능 불리언이 있으며, 이는 getFile()이 해당 특정 핸들을 통해 지정된 항목의 바이트를 공개할 수 있는지 결정합니다. 읽기 요청 완료가 반환한 핸들에서는 true이며, 이 핸들은 이미 가용성 게이팅을 통과했습니다. 반면 생성 요청 완료가 반환한 핸들에서는 동일한 핸들에 대해 검증 및 저장이 성공할 때까지 false입니다.

참고: 핸들은 COS 해시를 지정하며, COS 항목을 지정하는 것은 아닙니다. 생성 요청 완료는 COS 레지스트리에 항목이 없는 해시에 대한 핸들을 반환하며, 해당 해시는 영원히 항목을 갖지 않을 수도 있으므로 검증 및 저장이 항목을 생성하기 전까지 참조할 항목 자체가 없습니다.

참고: 이는 의도적으로 각 핸들의 속성입니다. 생성 요청은 해시에 대한 항목이 이미 존재하는지 여부와 관계없이 핸들을 반환하므로(생성 요청 완료 참조), 항목별 규칙을 사용하면 모든 오리진이 getFileHandle()을 create: true로 호출하고 이미 존재하는 항목을 즉시 읽어, origins, PHL 포함 여부, 또는 GREASE 처리를 충족하지 않고도 그 내용을 알아낼 수 있습니다. 이 명세의 모든 공개 제어는 읽기 경로에서 적용되므로 항목별 게이팅은 생성 요청이 그 모든 제어를 우회하게 합니다. 호출자에게 먼저 올바른 바이트 전체를 제공하도록 요구하면 생성으로 얻은 핸들을 통한 성공적인 읽기는 호출자가 이미 가지고 있지 않은 어떤 정보도 공개하지 않습니다.

프로미스 result, COS 해시 hash, CrossOriginStorageGetFileHandleOptions options, 전역 객체 global, 그리고 Realm realm을 인수로 생성 요청을 완료하려면:

  1. requestedOrigins를 options["origins"]을 인수로 요청된 오리진 정규화를 실행한 결과로 설정합니다.

  2. requestedOrigins가 목록이면, requestedOrigins를 requestedOrigins와 global을 인수로 COS 범위 상한 가져오기를 실행한 결과를 인수로 COS 범위 상한 적용을 실행한 결과로 설정합니다.

  3. handle을 realm에서 hash를 Cross-Origin Storage 파일 시스템 내에서 지정하는 로케이터를 가진 새 FileSystemFileHandle 생성 [FS]의 결과로 설정합니다.

  4. handle의 COS 해시를 hash로 설정합니다.

  5. handle의 COS 오리진을 global의 관련 설정 객체의 오리진으로 설정합니다.

  6. handle의 요청된 오리진을 requestedOrigins로 설정합니다.

  7. handle의 읽기 가능을 false로 설정합니다.

    참고: 이 알고리즘은 COS 레지스트리를 조회하지 않으며 수정하지도 않습니다. 그렇게 할 수 없습니다. 그 결과는 hash가 이미 저장되어 있는지와 무관해야 합니다. 그렇지 않으면 생성 요청 자체가 이전 존재 여부를 공개하게 됩니다(§ 8.2 교차 사이트 탐색 참조). 따라서 handle은 항목이 존재하든, 한 번도 작성된 적 없든, 다른 누군가가 지금 작성 중이든 정확히 동일한 조건으로 반환되며 이 호출자가 바이트를 제공하기 전까지 읽기 접근 권한을 갖지 않습니다.

    참고: 여기에는 아무것도 등록되지 않으므로, 핸들을 요청한 뒤 이를 포기하고 createWritable()을 호출하지 않거나 결과 스트림을 닫지 않는 호출자는 레지스트리를 발견한 그대로 남겨 둡니다. 다른 어떤 오리진도 해당 요청이 발생했다는 것을 관찰할 수 없으며, 어떤 해시도 이후 읽기를 억제하는 플레이스홀더 상태에 고정될 수 없습니다. § 8.3 진행 중인 쓰기를 참조하십시오.

    참고: requestedOrigins은 바이트가 작성되고 검증된 후 리소스 가시성 업그레이드를 통해 검증 및 저장에 의해서만 적용됩니다. 이것이 생성 요청이 가시성을 넓히기 전에 전체 바이트를 제공하도록 만드는 방식입니다. § 3.5 리소스 가시성 업그레이드를 참조하십시오.

  8. global을 인수로 전역 태스크를 큐에 추가하여 DOM 조작 태스크 소스에서 result를 handle로 해결하도록 합니다.

(DOMString or sequence<DOMString>) 또는 undefined인 origins을 인수로 요청된 오리진을 정규화하려면 "*", 목록 형태의 오리진, 또는 null을 반환합니다:

  1. origins이 존재하지 않으면 null을 반환합니다.

  2. origins이 "*"이면 "*"를 반환합니다.

  3. list를 « »로 설정합니다.

  4. origins의 각 candidate에 대해 반복합니다(단일 문자열은 하나의 항목을 가진 목록으로 취급합니다):

    1. candidateOrigin을 candidate에 기본 URL 파서를 실행한 결과인 오리진으로 설정합니다.

      참고: COS 요청 검증에서 이미 각 candidate가 불투명하지 않은 오리진으로 파싱됨을 확인했습니다.

참고: 이후 기존 항목에 병합하기 전에 여기에서 중복을 제거하면 origins가 항목이 처음 생성되는 순간부터 중복 없이 유지되므로 이후의 모든 복제도 중복 없이 유지됩니다.

Cross-Origin Storage 파일 시스템을 지정하는 핸들에서 createWritable()을 호출하여 얻은 FileSystemWritableFileStream이 [FS]에 따라 닫히면 사용자 에이전트는 해당 닫기 작업의 프로미스가 이행되기 전에 해당 핸들을 인수로 아래의 검증 및 저장 단계를 실행해야 합니다.

참고: 이는 닫기가 어떻게 트리거되었는지와 관계없이 적용됩니다. 명시적 close() 호출이거나, 소스의 끝에 도달하여 기본적으로 대상도 닫는 pipeTo() 호출일 수 있습니다. [STREAMS]는 스트림이 닫힌 상태가 되는 시점에 둘을 구별하지 않으며 이 알고리즘도 마찬가지입니다.

스트림이 닫힌 FileSystemFileHandle handle, 작성된 전체 바이트 시퀀스 bytes, 그리고 닫기 작업의 관련 설정 객체의 오리진 origin을 인수로 하는 검증 및 저장 단계는 다음과 같습니다:

  1. hash를 handle의 COS 해시로 설정합니다.

  2. computedValue를 bytes의 소문자 16진수 다이제스트로 설정하며, hash의 algorithm이 지정한 알고리즘을 사용하여 [WEBCRYPTO]에 따라 계산합니다.

  3. computedValue가 hash의 value와 정확히 같지 않으면:

    1. 닫기 작업의 프로미스를 "DataError" DOMException으로 거부합니다.

    2. 이 단계를 중단합니다.

    참고: 실패한 쓰기에는 정리할 것이 없습니다. 생성 요청 완료는 항목을 등록하지 않았으므로, 검증된 바이트를 생성하지 못한 쓰기는 COS 레지스트리를 그대로 두며, 이후 동일한 해시에 대한 getFileHandle() 호출은 쓰기를 전혀 시도하지 않았을 때와 동일한 "NotFoundError"를 받습니다. 어떤 오리진이 이미 작성한 항목도 마찬가지로 영향을 받지 않습니다. 이 알고리즘은 바이트와 권한을 추가하기만 합니다.

  4. 다음 단계를 큐에 추가하여 Cross-Origin Storage 큐에서 실행합니다:

    1. entry를 COS 레지스트리에서 hash가 hash와 동일한 COS 항목으로 설정합니다. 없으면 null로 설정합니다.

    2. entry가 null이면:

      1. entry를 새 COS 항목으로 설정합니다. 이 항목의 hash는 hash, bytes는 bytes, origins는 빈 목록, 전역적으로 공개 가능은 false, 그리고 저장 오리진은 빈 집합입니다.

      2. 설정하여 COS 레지스트리[hash]를 entry로 만듭니다.

      참고: 이는 이 명세에서 COS 레지스트리에 항목을 추가하는 유일한 단계이며, bytes가 hash에 대해 검증된 후에만 실행됩니다. 두 작성자가 모두 해시가 없음을 확인하고 동시에 쓰면 각각 여기 도달하며, 두 번째로 큐에 추가된 작성자는 첫 번째 작성자가 생성한 항목을 발견하고 자신의 오리진과 아래 권한만 추가합니다. 두 작성자의 바이트는 동일한 값으로 해시되므로 한 번만 저장해도 충분합니다.

    3. origin이 아직 없다면 entry의 저장 오리진에 추가합니다.

    4. entry와 handle의 요청된 오리진을 인수로 리소스 가시성 업그레이드를 실행합니다.

    5. handle의 읽기 가능을 true로 설정합니다.

      참고: 이 핸들만 읽을 수 있게 됩니다. 아직 쓰기를 완료하지 않은 다른 생성 요청으로 얻은 동일 해시의 다른 핸들은 계속 읽을 수 없습니다.

Cross-Origin Storage 파일 시스템을 지정하는 FileSystemFileHandle에서 호출한 createWritable()은 FileSystemWritableFileStream을 생성해야 하며, 그 내용은 keepExistingData의 값과 지정된 COS 해시에 COS 레지스트리 항목이 존재하는지 여부와 관계없이 비어 있는 상태로 시작해야 합니다.

참고: [FS]는 원래 keepExistingData가 기존 파일의 내용을 스트림에 초기값으로 넣도록 정의합니다. 여기에서 이를 따르도록 하면 호출자가 자신이 소유한 적 없는 바이트의 저장 오리진이 될 수 있습니다. 생성 요청은 항목이 이미 존재하는지와 관계없이 핸들을 반환하므로, 호출자가 다른 오리진이 저장한 해시에 대해 쓰기 가능 스트림을 열고 아무것도 쓰지 않은 채 닫아도 이어받은 바이트가 요청한 값으로 해시될 수 있습니다. 그러면 origins, 공개 해시 목록 및 GREASE 처리를 전혀 확인하지 않고 읽기 접근 권한을 얻게 됩니다. 이는 개별적으로 허용된 두 작업으로 만든 가용성 게이팅 우회입니다. 모든 생성 요청에서 검증 및 저장이 전체 내용을 요구하는 것도 같은 이유입니다.

참고: 아무것도 쓰지 않고 닫힌 쓰기 가능 스트림에는 빈 바이트 시퀀스가 들어 있으며, 이는 호출자가 원하는 어떤 항목의 요청 값으로도 해시되지 않으므로 검증 및 저장은 "DataError" DOMException으로 다른 불일치와 동일하게 거부합니다. 구현이 대신 스토리지 또는 I/O 실패를 보고한다면 검증 결과를 관계없는 오류 뒤에 숨기게 됩니다.

File System Standard [FS]에는 아직 종속 명세가 FileSystemWritableFileStream의 닫기 단계에 쓰기별 추가 검증을 연결할 확장 지점이 정의되어 있지 않습니다. 이러한 훅이 존재할 때까지 이 절에서는 필요한 동작을 직접 설명합니다. 향후 개정에서는 [FS]와 정식으로 통합할 것으로 예상됩니다.

3.4. 가져온 리소스 저장

§ 9 다른 명세와의 통합에 나열된 호스트 통합은 FileSystemFileHandle을 거치지 않고 가져온 리소스를 저장합니다. 해당 호스트 명세는 가져온 바이트가 통합에서 요구하는 무결성 검사를 통과하면 다음 알고리즘을 실행할 것으로 예상됩니다.

응답 response, 바이트 시퀀스 bytes, COS 해시 hash, "*", 목록 형태의 문자열, 또는 null인 origins, 그리고 환경 설정 객체 settings을 인수로 가져온 리소스를 Cross-Origin Storage에 저장하려면:

  1. settings의 전역 객체를 인수로 Cross-Origin Storage 권한 확인을 실행한 결과가 false이면 반환합니다.

  2. origins이 null이 아니면 options를 «[ "origins" → origins ]»로, 그렇지 않으면 «[ ]»로 설정합니다.

  3. hash와 options을 인수로 COS 요청 검증을 실행한 결과가 null이 아니면 반환합니다.

  4. computedValue를 bytes의 소문자 16진수 다이제스트로 설정하며, hash의 algorithm이 지정한 알고리즘을 사용하여 [WEBCRYPTO]에 따라 계산합니다.

  5. computedValue가 hash의 value와 정확히 같지 않으면 반환합니다.

    참고: 통합 자체의 무결성 메타데이터에는 여러 다이제스트가 나열될 수 있으며, 그중 하나와 일치하면 무결성 검사를 만족합니다. 이 단계는 항목의 키가 이 정확한 바이트가 생성하는 해시인지 확인합니다.

  6. requestedOrigins를 options["origins"]을 인수로 요청된 오리진 정규화를 실행한 결과로 설정합니다.

  7. requestedOrigins가 목록이면:

    1. response가 필터링된 응답이면 internalResponse를 response의 내부 응답으로, 그렇지 않으면 response로 설정합니다.

    2. requestedOrigins를 requestedOrigins와 internalResponse의 헤더 목록을 인수로 COS 범위 상한 파싱을 실행한 결과를 인수로 COS 범위 상한 적용을 실행한 결과로 설정합니다.

    참고: 상한은 가져온 리소스 자체의 응답에서 오므로 바이트를 제공하는 서버가 어떤 오리진에 공개할 수 있는지 결정합니다. 로드하는 Document의 COS 범위 상한은 관여하지 않습니다. 그 운영자는 리소스를 제어하지 않으며 수신자를 승인할 수 있게 하면 어떤 사이트든 다른 사이트의 자산을 자신이 선택한 오리진과 공유 가능하다고 선언할 수 있기 때문입니다. 사용자 에이전트는 내부 응답에서 헤더를 읽으므로 불투명한 필터링된 응답에서도 동작하며 헤더는 페이지에 노출되지 않습니다.

  8. origin을 settings의 오리진으로 설정합니다.

  9. 다음 단계를 큐에 추가하여 Cross-Origin Storage 큐에서 실행합니다:

    1. entry를 COS 레지스트리에서 hash가 hash와 동일한 COS 항목으로 설정합니다. 없으면 null로 설정합니다.

    2. entry가 null이면:

      1. entry를 새 COS 항목으로 설정합니다. 이 항목의 hash는 hash, bytes는 bytes, origins는 빈 목록, 전역적으로 공개 가능은 false, 그리고 저장 오리진은 빈 집합입니다.

      2. 설정하여 COS 레지스트리[hash]를 entry로 만듭니다.

      참고: 검증 및 저장과 마찬가지로, 항목은 bytes가 hash에 대해 검증된 후에만 생성되며, 통합의 integrity 검사가 이를 이미 수행했습니다. 동일한 해시에 대한 getFileHandle() 작성자가 아직 진행 중이어도 영향을 받지 않습니다. 해당 작성자는 레지스트리 상태를 보유하지 않으며 자신의 검증 및 저장은 정상적으로 완료되어 이 항목을 찾고 자신의 오리진과 권한을 추가합니다.

    3. origin이 아직 없다면 entry의 저장 오리진에 추가합니다.

    4. entry와 requestedOrigins을 인수로 리소스 가시성 업그레이드를 실행합니다.

참고: 검증 및 저장과 마찬가지로 저장은 항목이 이미 "written" 상태인 경우에도 항상 전체 바이트를 요구하므로 이전 존재 여부에 관한 아무것도 공개하지 않습니다. 네트워크 가져오기 전 통합의 조회는 읽기이며 가용성 게이팅과 § 8.2 교차 사이트 탐색의 탐색 고려 사항의 적용을 받습니다.

3.5. 리소스 가시성 업그레이드

COS 항목의 가시성은 업그레이드할 수 있지만 다운그레이드할 수 없습니다.

COS 항목 entry와 "*", 목록 형태의 오리진, 또는 null인 requestedOrigins을 인수로 리소스 가시성을 업그레이드하려면:

  1. requestedOrigins가 null이면 반환합니다.

    참고: origins를 생략하면 모든 항목이 이미 가지고 있는 동일 사이트 가용성만 요청하므로(COS 공개 여부 결정 참조) 추가할 것이 없습니다.

  2. requestedOrigins이 "*"이면:

    1. entry의 전역적으로 공개 가능을 true로 설정합니다.

    2. 반환합니다.

    참고: 이는 전역 권한을 추가하며 entry의 origins에는 영향을 주지 않습니다. 이미 명시적인 origins 목록을 가지고 있던 항목은 이를 유지하므로 그 목록의 모든 오리진은 항목이 전역적으로 공개 가능해진 이후에도 PHL과 무관한 접근 권한을 유지합니다. 이것이 두 권한을 별도로 저장하는 핵심 이유입니다. 전역적으로 공개 가능을 참조하십시오.

  3. requestedOrigins의 각 candidateOrigin에 대해 반복합니다:

    1. entry의 origins가 candidateOrigin을 포함하면 계속합니다.

    2. entry의 origins의 크기가 사용자 에이전트의 최대 origins 목록 길이와 같으면 중단합니다.

      참고: 남아 있는 candidateOrigin 값은 이 업그레이드에서 조용히 삭제됩니다. 쓰기 자체는 이미 성공했으며 사용자 에이전트는 항목의 origins 목록이 최대 용량이라는 콘솔 경고를 기록할 것으로 예상됩니다.

    3. candidateOrigin을 entry의 origins에 추가합니다.

참고: 업그레이드는 origins에 추가하거나 전역적으로 공개 가능을 true로 설정하기만 합니다. 목록을 요청하는 작성자는 이미 전역적으로 공개 가능한 항목도 그렇지 않은 항목과 동일하게 넓힙니다. 두 권한이 독립적이므로 새로 나열된 오리진은 "*" 권한이 계속 적용되는 동안에도 PHL과 무관한 접근 권한을 얻습니다.

참고: 원래 저장자가 아닌 사이트를 포함한 모든 사이트는 항목의 origins를 넓힐 수 있습니다. 단, 항목의 hash로 해시되는 바이트도 제공해야 합니다. 이는 의도된 동작입니다. 어떤 사이트든 해당 해시에 맞는 올바른 바이트를 이미 보유하고 있다면, 구조상 그 해시가 무엇을 의미하는지에 대해 원래 저장자만큼 권위가 있습니다.

3.5.1. 원래 저장자의 접근

COS 항목을 성공적으로 작성한 오리진, 즉 항목의 저장 오리진에 있는 모든 오리진은 이후 언제든 getFileHandle()을 통해 해당 항목의 핸들을 얻을 수 있으며, 항목의 origins 값 및 hash가 PHL에 있는지 여부와 무관합니다. 이는 오리진이 자신이 저장한 것에 항상 접근할 수 있는 Cache API의 모델을 따릅니다.

4. Cross-Origin Storage 파일 시스템

Cross-Origin Storage 파일 시스템은 어떤 오리진의 버킷 파일 시스템 또는 로컬 파일 시스템 접근 루트와 구별되는 파일 시스템 루트이며, 그 항목은 COS 레지스트리의 COS 항목 항목과 일대일로 대응합니다.

Cross-Origin Storage 파일 시스템은 [FS]의 일반적인 호출별 권한 확인 모델을 사용하지 않습니다. 여기에서 얻은 모든 FileSystemFileHandle은 스크립트에 반환되기 전에 이미 § 3.2 파일 읽기 또는 § 3.3 파일 생성 및 쓰기에 의해 완전히 승인되었으므로 그러한 핸들에서 getFile() 또는 createWritable()을 호출해도 추가 권한 프롬프트가 발생하지 않습니다.

따라서 이러한 핸들의 queryPermission()과 requestPermission()은 프롬프트가 나타날 수 없으므로 "prompt"를 보고해서는 안 됩니다. 생성 요청으로 얻지 않은 핸들의 쓰기 모드에 대해서는 "denied"를 보고해야 하며, 그 외에는 "granted"를 보고해야 합니다.

참고: 쓰기는 핸들이 실제로 갖지 않을 수 있는 유일한 기능입니다. 생성 요청만 쓰기가 가능한 핸들을 생성하므로 다른 핸들의 쓰기 모드에 "granted"를 보고하면 createWritable()이 거부할 기능이 있다고 주장하게 됩니다. 읽기는 "granted"로 유지됩니다. 읽기 가능한 핸들을 보유한 호출자는 이를 통해 읽을 수 있기 때문입니다. 요청한다고 해서 어느 응답도 바뀌지 않습니다. 표시할 프롬프트도 없고 권한을 기록할 상태도 없기 때문입니다.

읽기 가능이 false인 Cross-Origin Storage 파일 시스템을 지정하는 FileSystemFileHandle에서 getFile()을 호출하면 "NotAllowedError" DOMException으로 거부해야 합니다. 이는 서로 다른 두 경우를 포함합니다:

  • 아직 쓰기가 완료되지 않은 생성 요청의 핸들로, 해당 핸들이 지정하는 해시에 COS 레지스트리 항목이 없습니다. 반환할 검증된 바이트가 없으며 호출자가 자신의 미완료 쓰기를 파일의 실제 내용인 것처럼 관찰할 수 있어서는 안 됩니다.

  • 어떤 다른 오리진이 이미 작성한 해시에 대한 생성 요청의 핸들입니다. 검증된 바이트는 존재하지만 이 호출자는 이를 제공하지 않았고 가용성 게이팅도 통과하지 않았으므로 항목에 대해 아무것도 알아서는 안 되며, 존재 여부조차 알아서는 안 됩니다.

참고: 두 경우의 거부는 동일하므로 아무것도 공개하지 않습니다. 이것이 읽기 경로에서는 의도적으로 피하는 "NotAllowedError"가 여기에서는 안전한 이유입니다. 이 핸들은 호출자 자신이 자신의 생성 요청으로 얻은 것이며 다른 오리진에서 역직렬화할 수 없습니다(§ 4.1 핸들 전송 참조). 따라서 응답은 오리진 경계를 넘지 않으며 레지스트리 내용과 관계없이 일정합니다. 반면 § 8.3 진행 중인 쓰기에서는 읽기 경로의 구별 가능한 오류가 그 경계를 넘게 됩니다.

핸들의 읽기 가능이 true가 되면 해당 핸들에서 호출한 getFile()은 지정된 항목의 bytes를 내용으로 하는 File을 반환합니다. 이는 [FS]가 이미 해당 바이트를 바이너리 데이터로 가지는 파일 항목에 대해 정의하는 동작과 정확히 같습니다.

Cross-Origin Storage 파일 시스템을 지정하는 FileSystemFileHandle에는 파일 시스템 로케이터가 있으며, 그 경로는 하나의 문자열을 포함하는 목록입니다. 이 문자열은 해당 핸들의 COS 해시의 value이며, 루트는 Cross-Origin Storage 파일 시스템입니다.

참고: [FS]는 name을 핸들의 로케이터 경로의 마지막 구성 요소로 정의하므로 name도 결정됩니다. 즉, 해시입니다. 항목에는 자체 이름이 없고 해시가 유일한 식별자이므로 이를 보고하는 것은 빈 문자열에서 사라질 정보를 보존합니다.

항목에는 이름도 포함 디렉터리도 없으므로 [FS]의 구조적 표면 대부분은 수행할 작업이 없습니다. 예외는 동일성으로, 콘텐츠 주소 지정 항목이 항상 답할 수 있는 유일한 질문입니다. COS 레지스트리는 COS 해시당 최대 하나의 COS 항목을 보유하므로, 두 핸들은 그 해시가 동일할 때 정확히 같은 항목을 지정합니다.

Cross-Origin Storage 파일 시스템을 지정하는 FileSystemFileHandle에서 isSameEntry()을 호출할 때, 인수 역시 이를 지정하며 동일한 오리진에서 얻었다면 두 핸들의 COS 해시 항목이 동일한 경우 true를, 그렇지 않으면 false를 반환해야 합니다.

참고: 이를 거부하면 사용자 에이전트가 이미 보유한 정보를 버리게 됩니다.

isSameEntry()이 호출 오리진이 얻지 않은 인수나, Cross-Origin Storage 파일 시스템 외의 파일 시스템을 지정하는 인수와 함께 호출되면 거부해야 합니다.

참고: 이 경우 false를 반환하면 두 핸들이 서로 다른 항목을 지정한다고 단언하게 되며, 이는 호출 오리진이 조사할 권한이 없는 핸들에 관한 주장입니다. 거부는 단지 비교할 수 없었음을 의미합니다.

Cross-Origin Storage 파일 시스템을 지정하는 FileSystemFileHandle에서 호출된 move()와 remove()는 "NotAllowedError" DOMException으로 거부해야 하며 지정된 항목을 변경하지 않아야 합니다.

참고: 항목은 해당 저장 오리진의 모든 오리진에서 공유되므로 삭제를 허용하면 한 사이트가 다른 사이트가 의존하는 데이터를 파괴할 수 있습니다. 삭제는 축출과 사용자의 자체 스토리지 제어에 맡겨집니다. 이름 변경이나 부모 변경은 수행할 대상이 없습니다. 항목은 COS 해시로 이름이 정해지고 포함 디렉터리가 없기 때문입니다.

참고: 작성 시점에는 두 메서드 모두 [FS] 또는 File System Access API에서 정의되지 않았으므로 (WICG/file-system-access#214), 오류 이름은 [FS]가 항목 삭제에 대해 정의한 removeEntry()을 따릅니다. 읽기/쓰기 접근이 허용되지 않으면 접근 결과의 오류 이름으로 거부합니다. 여기에서 거부하는 것이 정확한 동작입니다. 해당 작업은 의미가 있지만 허용되지 않습니다.

createSyncAccessHandle()에는 여기에서 별도 규칙이 필요하지 않습니다. 그 단계는 핸들이 버킷 파일 시스템에 있지 않을 때마다 "InvalidStateError" DOMException으로 거부하며, Cross-Origin Storage 파일 시스템은 어떤 오리진의 파일 시스템과도 구별되는 파일 시스템 루트이므로 [FS]가 이미 거부 여부와 그 이름을 모두 결정합니다.

참고: 이는 이 명세가 독립적으로 원할 결과이기도 합니다. FileSystemSyncAccessHandle은 호출자에게 쓰기 가능한 파일 디스크립터를 제공하며, 이는 항목의 bytes를 저장 기준인 COS 해시와 일치하지 않도록 변경할 수 있게 하고, 해당 항목이 공개 가능한 다른 모든 오리진이 그 동일한 바이트를 읽게 만듭니다.

4.1. 핸들 전송

FileSystemFileHandle은 직렬화 가능 객체 [FS]이므로 COS 항목을 지정하는 핸들은 다른 환경 설정 객체로 전달할 수 있습니다. 예를 들어 postMessage(message, options)를 사용할 수 있습니다. 이는 getFileHandle() 외에 이러한 핸들을 얻는 두 번째 방법이므로 여기에서도 제한됩니다.

직렬화 단계에서 FileSystemFileHandle이 Cross-Origin Storage 파일 시스템을 지정하고 value와 serialized가 주어지면 추가로:

  1. serialized.[[COSHash]]를 value의 COS 해시로 설정합니다.

  2. serialized.[[COSOrigin]]을 value의 COS 오리진으로 설정합니다.

  3. serialized.[[COSMayRead]]를 value의 읽기 가능으로 설정합니다.

serialized, value 및 realm이 주어진 역직렬화 단계에서 추가로:

  1. serialized.[[COSOrigin]]이 realm의 환경 설정 객체의 오리진과 동일 오리진이 아니면 "DataCloneError" DOMException을 던집니다.

  2. value의 COS 해시를 serialized.[[COSHash]]로 설정합니다.

  3. value의 COS 오리진을 serialized.[[COSOrigin]]으로 설정합니다.

  4. value의 읽기 가능을 serialized.[[COSMayRead]]로 설정합니다.

참고: 동일 오리진 검사가 없으면 전송이 이 명세의 모든 공개 제어를 한 번에 무력화합니다. 읽기 가능이 true인 핸들은 이미 가용성 게이팅 적용을 이를 요청한 오리진에 대해 통과했습니다. 이를 다른 오리진에 게시하면 해당 오리진에 origins, PHL 포함 여부 또는 GREASE 처리가 평가되지 않은 채 항목의 바이트를 넘겨주게 됩니다. 이는 핸들이 마찬가지로 동일 오리진 수신자에게만 유용한 File System Standard의 기존 처리와 일치합니다.

참고: 읽기 가능은 핸들과 함께 이동하므로 쓰기가 완료되지 않은 생성 요청 핸들은 전송 후에도 읽을 수 없고, 읽기 요청 핸들은 다시 게이팅하지 않아도 읽을 수 있습니다. 도착 시 다시 게이팅하면 호출자가 동일한 핸들을 전송하여 가용성을 반복적으로 탐색할 수 있습니다.

5. 스토리지 관리

5.1. 스토리지 제한

사용자 에이전트는 단일 오리진이 다른 오리진의 항목을 축출하려는 목적으로 캐시를 가득 채우는 것을 방지하기 위해 성공적인 쓰기를 통해 오리진이 COS 레지스트리에 기여할 수 있는 총 바이트 수를 제한해야 합니다. 구체적인 제한은 구현 정의입니다. 오리진의 쓰기가 해당 제한을 초과하면 사용자 에이전트는 그 쓰기를 "QuotaExceededError" DOMException으로 거부해야 하며 콘솔에 경고를 기록해야 합니다.

참고: 항목은 콘텐츠 주소 지정 가능하므로 오리진이 동일한 바이트를 동일한 해시로 반복해서 써도 첫 성공적인 쓰기를 넘어 추가 할당량을 소비하지 않습니다. § 2.2 COS 항목을 참조하십시오.

사용자 에이전트에는 또한 구현 정의된 최대 origins 목록 길이가 있으며, 단일 origins 목록에 포함될 수 있는 오리진의 수를 제한하는 양의 정수입니다. 이 제한은 목록이 처음 제공될 때(COS 요청 검증 참조)와 이후 기존 항목에 병합될 때(리소스 가시성 업그레이드 참조) 모두 적용되므로 단일 호출이나 시간에 따른 많은 호출의 누적 효과 어느 쪽도 항목의 origins를 무한정 증가시킬 수 없습니다. 메모리 사용을 제한하는 것 외에도 이는 오리진의 목록을 "*"의 선언되지 않은 대체물로 사용하지 못하게 합니다. § 8.2 교차 사이트 탐색을 참조하십시오.

이 제한을 초과하는 경우는 두 위치에서 서로 다르게 처리됩니다. 두 호출이 작업의 매우 다른 시점에서 발생하기 때문입니다:

  • COS 요청 검증에서는 파일을 가져오거나 해시하거나 쓰기 전에 제한을 확인합니다. 이를 초과하는 호출자는 즉시 "TypeError"를 받으며 다른 작업은 일어나지 않습니다. 이는 다른 잘못된 형식의 origins 값과 동일한 처리입니다.

  • 리소스 가시성 업그레이드에서 이 제한은 오랜 기간 서로 무관한 오리진이 수행한 별개의 독립적 쓰기 호출에 걸쳐 요청된 오리진의 누적 효과에 의해서만 도달할 수 있으며, 이 호출의 바이트가 이미 해시되고 검증되고 영구 저장된 후에야 확인됩니다. 그 시점에 쓰기를 거부하면 관계없는 장부상의 제한 때문에 성공적이고 이미 검증되었으며 잠재적으로 매우 큰 쓰기를 폐기하게 되고 단일 호출자의 실수로 돌릴 수도 없습니다. 따라서 쓰기는 성공하도록 두고 용량을 초과하는 오리진만 origins에서 삭제하며 콘솔 경고를 기록합니다. 이는 기존의 더 허용적인 범위에서 더 제한적인 범위로의 요청 처리와 같습니다. 완전히 이행할 수 없는 오리진 요청은 조용히 제한되고 이를 실은 쓰기는 계속 성공합니다. 이 명세의 다른 부분의 § 8.4 가용성 게이팅과 일관되게 호출자는 요청한 오리진이 실제로 추가되었는지 사후에 신뢰성 있게 확인할 방법이 없습니다. 해당 오리진으로 후속 getFileHandle() 호출을 해도 오리진이 추가된 경우에도 실패할 수 있으므로(예: 항목이 축출되었거나 사용자 에이전트가 요청을 제한한 경우), 그 결과를 어느 쪽이든 확인으로 해석해서는 안 됩니다.

5.2. 축출

이 절은 비규범적입니다.

스토리지 압박이 있는 경우 사용자 에이전트는 COS 레지스트리에서 항목을 축출할 수 있습니다. 예를 들어 각 항목에 가장 최근 접근한 저장 오리진을 기준으로 최소 최근 사용 정책을 사용할 수 있습니다. 사용자 에이전트는 사용자가 저장된 파일, 각 파일에 접근한 오리진을 확인하고 항목을 직접 삭제하거나 모든 Cross-Origin Storage 데이터를 지울 수 있는 설정 UI를 제공할 것으로 예상됩니다.

사용자가 오리진의 사이트 데이터를 지우면 사용자 에이전트는 그 오리진이 나타나는 모든 저장 오리진 집합에서 해당 오리진을 제거해야 합니다. 제거 후 COS 항목의 저장 오리진이 비어 있으면 사용자 에이전트는 해당 항목의 삭제를 고려할 수 있습니다.

5.3. 수동으로 추가된 항목

이 절은 비규범적입니다.

위에서 설명한 설정 UI는 사용자가 디스크에 이미 가지고 있는 파일을 스크립트가 getFileHandle()을 호출하지 않아도 Cross-Origin Storage에 직접 추가할 수 있게 할 수 있습니다(예: 웹사이트와 무관하게 다운로드한 AI 모델). 이러한 항목에는 쓰기를 귀속시킬 요청 오리진이 없으므로 명령형 API만으로는 답할 수 없는 두 가지 질문이 생깁니다:

  • § 3.5.1 원래 저장자의 접근에서 말하는 원래 저장자는 누구입니까? 아무도 아닙니다. 항목의 저장 오리진은 빈 상태로 시작합니다. 따라서 어떤 오리진도 다른 요청 오리진이 적용받는 일반적인 가용성 게이팅 및 origins 검사에서 면제되지 않습니다. 실제로 바이트를 작성한 오리진이 없으므로 이것이 올바른 결과입니다.

  • origins를 생략한 일반적인 쓰기처럼 이러한 항목도 동일 사이트 전용으로 제한해야 합니까? 아닙니다. "동일 사이트"는 요청 오리진에 대해서만 의미가 있으며 수동 추가에는 요청 오리진이 없으므로 "동일 사이트"의 기준이 될 사이트가 없습니다. 사용자 에이전트는 이러한 항목을 전역적으로 공개 가능하게 만들고, 명시적 origins 목록은 비워 둘 것으로 예상됩니다. 수동으로 파일을 미리 저장하는 것은 사용자가 아직 방문하지 않은 사이트도 이미 디스크에 있는 파일을 재사용할 수 있게 하는 것이 목적이며 다른 오리진이 실제로 이를 발견할 수 있어야만 그 목적을 달성할 수 있기 때문입니다. 사용자 에이전트의 설정 UI는 추가로 사용자가 더 좁은 범위를 선택하도록 할 수 있습니다.

이 방식으로 추가된 항목은 이후에는 웹사이트가 getFileHandle()을 통해 작성한 항목과 구별되지 않습니다. 동일한 가용성 게이팅 및 가시성 업그레이드 규칙이 동일한 권한을 가진 다른 항목과 정확히 동일하게 적용됩니다. 여기에는 수동 추가의 기본값처럼 항목이 전역적으로 공개 가능해질 때마다 PHL에 있는지 확인하는 것도 포함됩니다.

5.4. 출처 메타데이터

이 절은 비규범적입니다.

COS 항목은 의도적으로 해당 바이트가 어디에서 왔는지에 관한 아무 정보도 기록하지 않습니다. 식별자는 hash뿐입니다. 동일한 바이트는 몇 개의 오리진이 저장했거나 몇 개의 URL에서 가져왔는지와 관계없이 동일한 항목입니다 (§ 2.2 COS 항목 참조). URL은 한 작성자의 가져오기에 속하는 속성이므로 여러 오리진이 작성한 항목에서 하나를 선택할 비자의적인 방법이 없습니다. URL은 바이트처럼 검증할 수 없으며(§ 8.1 리소스 무결성 참조), 경로나 쿼리 문자열이 특정 문서, 계정 또는 세션을 가리킬 수 있으므로 저장 오리진의 거친 오리진 값보다 사용자의 탐색에 대해 훨씬 많은 정보를 전달합니다. 따라서 이를 항목에 기록하면 origins와 § 8.4 가용성 게이팅이 부과하려는 공개 제한을 우회하여 높은 엔트로피 신호가 전달됩니다.

그럼에도 이를 원하는 동기는 실제로 존재합니다. § 5.2 축출에서 설명한 설정 UI에서 수 기가바이트 파일을 보는 사용자와 getFileHandle() 호출이 실패한 이유를 디버깅하는 개발자 모두 파일이 어디에서 왔는지 알고 싶을 수 있습니다. 사용자 에이전트는 항목과 함께 구현 비공개 출처 기록 (예: 각 저장 오리진이 바이트를 가져온 URL과 시점)을 보관하여 이를 제공할 수 있습니다. 단, 해당 기록은 항목 외부에 보관되는 사용자 에이전트 상태로 취급해야 합니다:

  • 스크립트에는 절대 노출되지 않습니다. 이 명세의 어떤 것도 이를 공개하지 않으며 이후 추가되는 것도 그래서는 안 됩니다. getFileHandle()도 이것이 반환하는 FileSystemFileHandle도 이러한 기록이 존재하는지 여부는 물론 그 내용도 공개해서는 안 됩니다. 특히 요청 오리진이 자신이 생성하지 않은 기록을 관찰할 수 있어서는 안 됩니다.

  • 신뢰할 수 있는 비웹 표면을 통해서만 표시됩니다. 즉 사용자 에이전트 자체의 설정 및 스토리지 검사 UI, 개발자 도구, 그리고 사용자 에이전트에 확장 플랫폼이 있는 경우 명시적으로 사용자가 부여한 권한 뒤에 있는 확장 API이며, 탐색 기록을 노출하는 다른 API와 동일하게 취급됩니다. 검토 중인 확장 표면은 이 저장소의 브라우저 확장 통합 지점 설명서를 참조하십시오.

  • 검증되지 않은 정보이며 그렇게 표시됩니다. 그 안의 URL은 바이트를 작성한 오리진의 주장입니다. 콘텐츠를 보장하는 것은 hash뿐입니다(§ 8.1 리소스 무결성 참조). 두 오리진은 동일한 항목에 대해 서로 다른 URL을 기록할 수 있으며 그중 하나 또는 둘 모두가 부정확하거나 의도적으로 오해를 유도할 수 있습니다.

  • 항목 및 해당 기록이 귀속되는 오리진과 수명을 공유합니다. 항목이 축출되거나 삭제되면 기록도 삭제되며, 오리진에 귀속되는 부분은 해당 오리진이 저장 오리진에서 제거될 때 삭제됩니다. 여기에는 사용자가 해당 오리진의 사이트 데이터를 지우는 경우도 포함됩니다(§ 5.2 축출 참조).

이러한 기록은 콘텐츠에 보이지 않으므로 사용자 에이전트가 이를 보관하는지, 그리고 얼마나 많이 보관하는지는 전적으로 구현에 맡겨집니다. 이 명세의 어떤 것도 이에 의존하지 않으며 사이트는 그 존재 여부를 감지할 수 없습니다.

6. Permissions Policy 통합

이 명세는 "cross-origin-storage" 문자열로 식별되는 정책 제어 기능 [permissions-policy]을 정의합니다. 기본 허용 목록은 self입니다.

[permissions-policy]은 Document에 대해 사용 허용됨을 정의하지만 CrossOriginStorageManager는 자체 Document가 없는 WorkerGlobalScope에도 노출됩니다. 따라서 검사는 호출 전역 객체에 대해 정의됩니다. 워커 전역은 전이적으로 이를 소유하는 Document로 해석되며 그 모두가 해당 기능을 허용해야 합니다.

전역 객체 global을 인수로 Cross-Origin Storage 권한을 확인하려면 불리언을 반환합니다:

  1. global이 Window 객체이면:

    1. document를 global의 연결된 Document로 설정합니다.

    2. document가 null이면 false를 반환합니다.

    3. document가 "cross-origin-storage" 정책 제어 기능을 사용하도록 허용되지 않았다면 false를 반환합니다.

    4. true를 반환합니다.

  2. global이 WorkerGlobalScope 객체이면:

    1. owners를 global의 소유자 집합으로 설정합니다.

    2. owners가 비어 있으면 false를 반환합니다.

    3. owners의 각 owner에 대해 반복합니다:

      1. owner가 Document이고 "cross-origin-storage" 정책 제어 기능을 사용하도록 허용되지 않았다면 false를 반환합니다.

      2. owner가 WorkerGlobalScope 객체이고 owner을 인수로 Cross-Origin Storage 권한 확인을 실행한 결과가 false이면 false를 반환합니다.

    4. true를 반환합니다.

  3. false를 반환합니다.

이 알고리즘이 false를 반환하는 전역 객체에서 수행된 모든 getFileHandle() 호출은 해시 검증, 레지스트리 조회 또는 쓰기가 발생하기 전에 "NotAllowedError" DOMException으로 거부됩니다.

참고: 소유자 집합을 통해 해석하는 것이 기능이 이름뿐인 옵트아웃이 되는 것을 방지합니다. blob: URL에서 생성된 워커는 이를 생성한 페이지의 오리진에서 실행되고 해당 페이지의 Cross-Origin Storage 뷰를 정확히 공유하므로 (§ 3 CrossOriginStorageManager 인터페이스 참조) 전역 자체의 Document만 확인하는 검사는 모든 워커에서 무조건 충족되며 호출을 new Worker(URL.createObjectURL(&hellip;))로 옮기기만 해도 그 외에는 아무것도 변경하지 않고 cross-origin-storage=() 정책을 우회할 수 있습니다.

참고: ServiceWorkerGlobalScope의 소유자 집합은 비어 있으므로 이 알고리즘은 그곳에서 false를 반환합니다. 이는 소유자 집합의 정의에서 따릅니다. 즉 워커가 생성될 때 채워지고 해당 워커가 계속 적극적으로 필요한지 결정할 때 사용되는 활성 관계입니다. 서비스 워커는 의도적으로 어떤 Document와도 이러한 관계를 갖지 않습니다. 등록은 지속되며 사용자 에이전트가 이벤트에 응답하여 전역을 시작하고 서비스 워커 클라이언트가 전혀 없어도 실행될 수 있기 때문입니다. register()를 호출한 클라이언트는 등록 시점에는 알 수 있지만 전역이 실행될 때는 보통 이미 사라져 있으며 하나의 실행 중인 서비스 워커가 정책이 서로 다를 수 있는 여러 클라이언트를 서비스합니다.

참고: 서비스 워커를 포함하려면 캡처된 정책이 필요하며 이 작업은 [permissions-policy] 및 [service-workers]의 영역입니다. 이 명세가 선호하는 형태는 서비스 워커 자체 스크립트 응답의 Permissions-Policy 헤더에서 서비스 워커 정책을 도출하는 것입니다. 정책 컨테이너가 이미 해당 응답의 CSP를 보유하는 방식과 같으며, 오리진의 제어 아래에 유지되고 모든 업데이트 검사 때 다시 평가됩니다. 등록 클라이언트의 정책을 스냅샷으로 저장하면 옵트아웃이 오래된 상태로 남습니다. 헤더에서 기능을 제거해도 등록이 우연히 업데이트될 때까지 적용되지 않기 때문입니다. 이러한 모델이 존재할 때까지는 닫힌 상태로 실패하는 것이 옵트아웃을 우회하는 데 사용할 수 없는 유일한 답입니다.

참고: SharedWorkerGlobalScope의 소유자 집합은 서로 다른 정책을 가진 여러 Document를 보유할 수 있으며 워커의 수명 동안 소유자가 추가되고 제거됩니다. 모든 소유자가 기능을 허용하도록 요구하면 이를 허용하지 않는 한 소유자가 전체 공유 워커에서 Cross-Origin Storage를 비활성화하며, 두 getFileHandle() 호출 사이에서도 답이 바뀔 수 있습니다. 반대로 허용적인 소유자 하나만 요구하면 기능을 허용하는 어떤 문서든 이를 허용하지 않는 문서를 대신해 다시 활성화할 수 있습니다.

7. Cross-Origin-Storage-Allow-Origin 헤더

COS 항목의 origins 목록이 비어 있지 않으면 작성 오리진이 제어하지 않는 오리진에 공개할 수 있지만, 해당 목록은 스크립트(origins)나 마크업에서 선언되며, 스크립트 또는 마크업 삽입에 성공한 공격자는 어느 쪽도 설정할 수 있습니다. 이 선언을 공개되는 바이트를 가진 오리진 운영자에게 결부시키고 삽입된 콘텐츠가 위조할 수 없는 형태로 만들기 위해 이 명세는 이러한 선언이 지정할 수 있는 오리진을 제한하는 응답 헤더를 정의합니다.

Cross-Origin-Storage-Allow-Origin 응답 헤더는 COS 범위 상한, 즉 쓰기가 동일 사이트가 아닌 origins 목록에 지정할 수 있는 오리진의 집합을 전달합니다. 바이트를 제공하는 쪽이 헤더를 보내므로 공개되는 바이트 뒤의 응답에서 읽습니다:

  • getFileHandle() 쓰기의 경우 바이트가 스크립트에서 생성되어 자체적인 원본 응답이 없을 수 있으므로 호출 전역 객체의 Document를 생성하는 데 사용된 응답, 또는 워커의 경우 이를 소유하는 Document들의 응답입니다 (COS 범위 상한 가져오기 참조).

  • 호스트 통합의 경우 저장되는 바이트를 가진 가져온 리소스의 응답입니다 (가져온 리소스를 Cross-Origin Storage에 저장 참조). 이는 리소스의 서버이며 이를 로드하는 Document의 서버와 다를 수 있습니다.

선언된 목록은 상한과 교집합을 취하므로(COS 범위 상한 적용 참조) 상한은 선언을 좁힐 수만 있습니다.

참고: 헤더는 바이트를 제공하는 쪽의 승인입니다. 헤더가 지정하는 오리진, 즉 최종 독자는 협의되지 않으며 아무것도 보내지 않습니다. 나열된 오리진은 나중에 다른 독자와 마찬가지로 COS 해시에 대해 getFileHandle()을 호출할 때만 참여합니다. 이는 리소스를 보유한 서버가 특정 오리진의 읽기를 허용하는 Access-Control-Allow-Origin [FETCH]와 반대 방향으로 동작합니다. 여기에서는 바이트 공급자가 나중에 Cross-Origin Storage에서 누가 이를 읽을 수 있는지를 제한하며 쓰기 페이지의 삽입된 콘텐츠는 공급자의 응답 헤더를 설정할 수 없으므로 그 제한을 확장할 수 없습니다.

참고: 헤더는 목록 형태에만 적용됩니다. 동일 사이트 기본값은 교차 오리진 수신자를 지정하지 않으므로 승인이 필요 없고 "*" 형태는 읽기 경로에서 공개 해시 목록에 대한 가용성 게이팅의 적용을 받습니다. 사용자별 비밀값은 이를 통과할 수 없으므로 쓰기 시점 상한도 필요 없습니다. "*"에도 헤더를 요구하면 공개 해시 목록이 이미 차단하지 않는 것을 추가로 차단하지 않으면서 구성 없는 전역 공유 사례를 깨뜨립니다.

헤더 목록 headers를 인수로 COS 범위 상한을 파싱하려면 집합 형태의 오리진을 반환합니다:

  1. value를 headers에서 "Cross-Origin-Storage-Allow-Origin"을 가져오고, 디코딩하고, 분할한 결과로 설정합니다.

  2. value가 null이면 빈 집합을 반환합니다.

  3. ceiling을 빈 집합으로 설정합니다.

  4. value의 각 token에 대해 반복합니다:

    1. token에서 앞뒤 ASCII 공백을 제거합니다.

    2. token이 빈 문자열이면 계속합니다.

    3. origin을 token에 기본 URL 파서를 실행한 결과인 오리진으로 설정합니다.

    4. origin이 실패이거나 불투명 오리진이면 빈 집합을 반환합니다.

      참고: 여기에는 오리진으로 파싱되지 않는 "*" token도 포함됩니다. Cross-Origin-Storage-Allow-Origin 헤더는 유한한 구체적 오리진 집합만 열거할 수 있습니다. "*"는 허용되는 값이 아닙니다. "모든 오리진"이라는 상한은 삽입된 콘텐츠가 원하는 어떤 수신자든 선언할 수 있게 하여 헤더의 전체 목적을 무력화하기 때문입니다. 무제한 공개는 "*" origins 형태를 통해서만 가능하며, 이는 공개 해시 목록에 의해 게이팅되고 이 헤더를 절대 조회하지 않습니다. 잘못된 형식이거나 "*"를 포함한 헤더는 없는 헤더와 정확히 동일하게 아무것도 승인하지 않으며 실패는 닫힌 상태로 처리됩니다.

    5. origin을 ceiling에 추가합니다.

  5. ceiling을 반환합니다.

참고: 가져오고, 디코딩하고, 분할은 U+002C (,)에서 분할하므로 헤더 값의 오리진은 쉼표로 구분됩니다. 이는 Timing-Allow-Origin [RESOURCE-TIMING] 및 목록 값을 가진 HTTP 응답 헤더의 일반적인 관례와 일치합니다. 반면 형제인 crossoriginstorage HTML 콘텐츠 속성은 호스트 구문에 맞추기 위해 공백으로 구분됩니다. 둘 다 동일한 오리진 집합으로 해석됩니다.

전역 객체 global을 인수로 COS 범위 상한을 가져오려면 집합 형태의 오리진을 반환합니다:

  1. global이 Window 객체이면:

    1. document를 global의 연결된 Document로 설정합니다.

    2. document가 null이면 빈 집합을 반환합니다.

    3. document의 COS 범위 상한을 반환합니다.

  2. global이 WorkerGlobalScope 객체이면:

    1. owners를 global의 소유자 집합으로 설정합니다.

    2. owners가 비어 있으면 빈 집합을 반환합니다.

    3. ceiling을 null로 설정합니다.

    4. owners의 각 owner에 대해 반복합니다:

      1. ownerCeiling을 빈 집합으로 설정합니다.

      2. owner가 Document이면 ownerCeiling을 owner의 COS 범위 상한으로 설정합니다.

      3. 그렇지 않고 owner가 WorkerGlobalScope 객체이면 ownerCeiling을 owner을 인수로 COS 범위 상한 가져오기를 실행한 결과로 설정합니다.

      4. ceiling이 null이면 ceiling을 ownerCeiling로 설정하고, 그렇지 않으면 ceiling을 ceiling과 ownerCeiling의 교집합으로 설정합니다.

    5. ceiling을 반환합니다.

  3. 빈 집합을 반환합니다.

오리진의 목록 requestedOrigins과 오리진의 집합 ceiling을 인수로 COS 범위 상한을 적용하려면 목록 형태의 오리진 또는 null을 반환합니다:

  1. ceiling이 포함하지 않는 각 오리진을 requestedOrigins에서 제거합니다.

    참고: COS 범위 상한에 없는 수신자는 삭제되며 쓰기는 계속 성공합니다. 이는 리소스 가시성 업그레이드에서 길이 제한을 초과한 업그레이드의 초과분을 삭제하는 방식과 같습니다. 사용자 에이전트는 삭제된 각 오리진을 명시하는 콘솔 경고를 기록할 것으로 예상됩니다.

  2. requestedOrigins이 비어 있으면 null을 반환합니다.

    참고: 모든 멤버가 삭제된 목록은 쓰기에 승인된 교차 오리진 수신자가 없도록 하므로 동일 사이트 기본값으로 되돌아갑니다. 바이트는 계속 저장되며 승인되지 않은 공개만 보류됩니다.

  3. requestedOrigins을 반환합니다.

모든 Document에는 COS 범위 상한이 있으며, 이는 집합 형태의 오리진입니다. 문서가 생성될 때 해당 문서를 생성하는 데 사용된 응답의 헤더 목록을 인수로 COS 범위 상한 파싱을 실행한 결과로 설정됩니다.

참고: 워커의 소유자 집합 전체의 교집합을 취하는 것은 Cross-Origin Storage 권한 확인을 반영합니다. 오리진은 전이적으로 모든 소유 Document가 승인했을 때만 워커의 상한에 포함됩니다. blob: 워커는 생성 페이지의 오리진과 Cross-Origin Storage 뷰를 정확히 공유하므로 (§ 3 CrossOriginStorageManager 인터페이스 참조), 워커 자체만 확인하는 상한은 모든 워커에서 비어 있게 되고 목록 범위 쓰기를 new Worker(URL.createObjectURL(&hellip;))로 옮기면 페이지가 승인한 수신자가 제거됩니다. 소유자의 상한 교집합을 취하면 단일 소유자가 이를 넓힐 수 없도록 하면서 해당 승인을 보존합니다.

Document의 COS 범위 상한을 해당 응답에서 채우려면 [HTML]의 문서 생성 단계에 훅이 필요합니다. 이는 [permissions-policy] 및 [CSP]가 응답 처리 시점에 채워지는 방식과 같습니다. 그러한 훅이 존재할 때까지 이 절은 필요한 동작을 직접 설명합니다. 향후 개정에서는 [FS] 훅과 함께 정식으로 통합할 것으로 예상됩니다. 해당 훅은 § 3.3 파일 생성 및 쓰기에 언급되어 있습니다. 호스트 통합에는 이러한 훅이 필요하지 않습니다. 호스트 통합은 가져온 응답을 가져온 리소스를 Cross-Origin Storage에 저장으로 전달하며, 이 알고리즘이 그 응답에서 상한을 읽습니다.

8. 개인정보 보호 및 보안 고려 사항

이 절은 RFC 2119 키워드를 사용하는 부분을 제외하면 비규범적입니다. 저장소의 보안 및 개인정보 보호 설문지도 참조하십시오.

8.1. 리소스 무결성

모든 COS 항목은 암호학적 해시를 키로 사용하고 그 바이트가 해당 해시에 대해 검증됩니다 (§ 3.3 파일 생성 및 쓰기 참조). 따라서 사이트는 getFileHandle()을 통해 얻은 파일이 hash 자체를 가져왔을 때 얻었을 바이트와 정확히 동일하다고 확신할 수 있습니다. 개발자는 Cross-Origin Storage의 내용을 열거하거나 해시를 이미 알지 못한 채 파일에 접근할 수 없습니다.

COS 해시는 비밀이 아닙니다. 이는 콘텐츠 식별자로서 파일을 이미 가진 사람이라면 누구나 쉽게 계산할 수 있으며, 이 명세가 대상으로 하는 널리 배포되는 리소스의 경우 흔히 모델이나 라이브러리 릴리스와 함께 공개됩니다. 따라서 해시를 아는 것으로 항목을 조회할 수 있지만 그 자체로 접근 권한을 부여하지 않습니다. 조회 성공 여부는 전적으로 origins와 § 8.4 가용성 게이팅에 의해 결정됩니다. 개발자는 공개되지 않은 해시를 접근 제어 메커니즘으로 취급해서는 안 됩니다. 특정 파일에 관심 있는 공격자는 해시를 추측할 필요 없이 파일 자체만 얻으면 됩니다(§ 8.2 교차 사이트 탐색 참조).

8.2. 교차 사이트 탐색

리소스가 소수의 사이트에서만 사용된다면 공격자는 해당 리소스가 Cross-Origin Storage에 존재한다는 사실을 알아내어 사용자가 그 사이트 중 하나를 방문했을 가능성이 높다고 추론할 수 있습니다. getFileHandle()이 존재 여부를 알아내는 메커니즘이므로 각 호출은 사실상 탐색입니다. 이 명세의 서로 독립적인 두 메커니즘은 탐색이 알아낼 수 있는 내용을 제한합니다:

  • origins (§ 3.5 리소스 가시성 업그레이드 참조)는 저장 오리진이 공개를 선택한 오리진 집합과 그와 동일 사이트인 오리진으로 제한할 수 있게 하므로, 독점적이거나 인기도가 낮은 리소스는 전역적으로 탐색 가능할 필요가 없습니다.

  • § 8.4 가용성 게이팅은 추가로 "*" 범위 리소스가 그 저장 오리진 외부의 요청 오리진에 공개되는 것을 해시가 PHL에 있지 않으면 보류합니다. 따라서 origins: "*"로 저장된 리소스가 웹의 모든 오리진에서 자동으로 탐색 가능해지지 않습니다. 이 게이트는 "*" 범위 항목에만 적용됩니다. 목록 및 동일 사이트 범위 항목에서는 저장 오리진이 이미 공개 범위를 명시적으로 제한했으므로 첫 번째 항목의 제한만 유일한 게이트입니다.

첫 번째 항목은 "선택된 오리진 집합"이 웹 전체보다 의미 있게 작게 유지될 때만 성립합니다. origins의 형태 자체는 호출자가 매우 많은 오리진을 열거하는 것을 막지 않습니다(예: 공개 상위 사이트 순위에서 구성한 목록). 이는 "*"만이 요구하는 의도적이고 명시적인 옵트인을 우회하면서 기능적으로 전역 공개에 근접하게 됩니다. 최대 origins 목록 길이 (§ 5.1 스토리지 제한 참조)가 이를 제한합니다. 실제 다중 속성 사용 사례(공통 제어 아래 있는 몇 개의 관련 오리진)를 수용할 만큼 충분히 크지만 "모든 오리진"에 의미 있게 근접하는 것에는 훨씬 못 미치는 제한은 제한된 오리진 형태의 origins를 "*"의 선언되지 않은 대체물로 사용할 수 없게 합니다.

사용자 에이전트는 단일 오리진에서 반복되는 getFileHandle() 호출에 추가로 속도 제한 또는 다른 형태의 제한을 적용해야 하며, 장치 내 휴리스틱(예: 사용자별로 생성된 것처럼 보이는 해시에 대한 요청 패턴 감지)을 적용하여 탐색 시도를 식별하고 차단할 수 있습니다. 탐색 대상 해시가 PHL에 있는지 여부와는 무관합니다.

§ 9 다른 명세와의 통합의 호스트 통합 중 하나가 수행하는 조회도 동일하게 탐색입니다. 페이지에 오류가 나타나지 않더라도 사이트는 자체 서버가 대체 요청을 받았는지 관찰할 수 있으며, 이는 여기의 "찾을 수 없음" 결과와 동일한 단일 비트를 전달합니다. 이러한 조회는 이 명세의 게이트가 허용하지 않는 것을 공개하지 않으며 해당 게이트는 그대로 적용됩니다. 하지만 속도 제한은 이러한 표면의 조회도 getFileHandle() 호출과 함께 계산될 때만 효과적입니다. 스크립트 가능한 통합도 마찬가지로 루프에서 쉽게 호출할 수 있기 때문입니다.

8.3. 진행 중인 쓰기

요청되었지만 완료되지 않은 쓰기는 모든 오리진에서 한 번도 작성되지 않은 해시와 구별할 수 없어야 합니다. 이 명세는 이를 구조적으로 달성합니다. COS 항목은 COS 레지스트리에 검증 및 저장 또는 가져온 리소스를 Cross-Origin Storage에 저장에 의해서만 추가되며, 두 경우 모두 전체 바이트가 해시에 대해 검증된 후에만 추가됩니다. 생성 요청 완료는 레지스트리를 읽지도 쓰지도 않습니다. 따라서 읽기가 관찰할 수 있는 플레이스홀더 상태가 없으며 읽기 경로에서 가용성 게이팅 적용 전에 응답할 수 있는 분기도 없습니다.

대안으로 생성 요청 시 플레이스홀더를 등록하고 동시 읽기에 구별 가능한 오류를 반환한다면 호출자가 어떤 오리진이 지금 특정 해시를 작성하고 있음을 알아낼 수 있습니다. 그 단일 비트는 작게 들리지만 그렇지 않습니다. 이는 다음과 같이 이용될 수 있습니다:

  • 항목에 어떤 종류의 권한도 없는 오리진을 포함한 모든 오리진에서 가능합니다. 플레이스홀더에는 권한이 없고 읽기는 COS 공개 여부 결정이 실행되기 전에 응답되기 때문입니다.

  • PHL에 있지 않고 앞으로도 포함될 수 없는 해시를 포함하여 모든 해시에서 가능합니다. 따라서 공격자는 사용자별 값에서 파생된 해시를 사용할 수 있으며 이는 정확히 § 8.6 핑거프린팅이 탐지하려는 패턴입니다.

  • 공개가 게이팅 단계에 도달한 경우에만 적용되는 GREASE 처리 없이 가능하므로 해당 비트에는 노이즈가 없습니다.

  • 바이트를 제공하지 않아도 가능하므로 오리진별 스토리지 제한도 § 5.2 축출도 오리진이 생성할 수 있는 이러한 비트의 수를 제한하지 못합니다.

따라서 두 사이트에 삽입된 추적기는 첫 번째 사이트에서 임의 너비의 식별자를 만들고 두 번째 사이트에서 스토리지 비용 없이 다시 읽어 origins, 공개 해시 목록, GREASE 처리를 모두 우회할 수 있습니다. 플레이스홀더는 서비스 거부 벡터도 됩니다. 실제로 인기 있는 리소스의 해시를 고정하면 플레이스홀더가 유지되는 동안 다른 모든 오리진의 읽기를 억제할 수 있습니다.

참고: 이 설계의 비용은 한 호출자가 다른 호출자가 이미 큰 파일을 다운로드 중임을 발견하여 중복 다운로드 시작을 피할 수 없다는 점입니다. 이는 실제 비용이며 이전 초안에서 여기에서 구별 가능한 오류를 사용했던 이유입니다. 가장 중요한 경우인 단일 오리진 내에서는 Web Locks, BroadcastChannel, 또는 공유 워커를 사용하여 회복할 수 있으며, 이들 중 어느 것도 오리진 경계를 넘어 정보를 공개하지 않습니다. 오리진 간에서는 절약 효과가 대체로 이론적입니다. 서로 관련 없는 두 오리진이 동일한 순간에 동일한 해시에 대해 경쟁해야 하고 어느 쪽도 아직 작성하지 않은 항목은 PHL에 포함될 때까지 다른 쪽에 공개할 수 없기 때문입니다.

참고: "NotAllowedError"는 쓰기를 완료하지 않은 생성으로 얻은 핸들에서 getFile()을 호출할 때의 응답으로 유지됩니다(§ 4 Cross-Origin Storage 파일 시스템 참조). 이 응답은 레지스트리와 관계없이 일정하며 요청을 한 오리진에만 도달합니다. 핸들은 교차 오리진으로 역직렬화할 수 없기 때문입니다(§ 4.1 핸들 전송 참조). 따라서 이는 채널이 아닙니다.

8.4. 가용성 게이팅

저장 오리진 외부의 오리진에서 getFileHandle() 읽기가 성공할지는 항상 요청 오리진이 항목을 읽도록 허용되었는지에 달려 있으며 이는 origins에 의해 결정됩니다. "*" 범위 항목에서는 두 번째 독립적인 질문도 적용됩니다. 사용자 에이전트가 항목이 존재한다는 사실 자체를 공개할 의향이 있는지이며 이는 PHL 포함 여부와 GREASE 처리에 의해 결정됩니다. 이러한 항목에서는 두 조건이 모두 충족되어야 하며, 목록 또는 동일 사이트 범위 항목에서는 첫 번째 질문만 적용됩니다. 규범적 알고리즘은 § 3.2 파일 읽기를 참조하십시오. 따라서 "NotFoundError"는 리소스가 없다는 증거가 아닙니다. 리소스가 존재하지 않거나, 요청 오리진이 범위 밖이거나, "*" 범위 리소스의 해시가 아직 또는 영원히 PHL에 없거나, GREASE 처리가 실제 양성을 억제한 것일 수 있습니다. 개발자는 "NotFoundError"를 "네트워크로 대체합니다."보다 더 구체적인 의미로 취급해서는 안 됩니다.

참고: 서드파티 쿠키를 지원하는 사용자 에이전트에서는 "*" 권한이 추적기에게 사용자의 사이트 간 방문을 연결하는 능력을 서드파티 쿠키보다 더 크게 제공하지 않습니다. PHL만으로는 이를 제한하지 못합니다. 공격자는 어떤 하위 집합을 작성할지 선택하여 개별적으로 PHL 자격이 있는 리소스로 교차 사이트 식별자를 구성할 수 있습니다. 서드파티 쿠키를 차단하는 사용자 에이전트도 교차 사이트 공개를 제한한다면 "*" 권한을 제공할 수 있습니다. 예를 들어 최상위 사이트를 키로 사용하고 페이지의 모든 프레임이 공유하는 소규모 교차 사이트 조회 예산, 일정 시간 동안 새로고침 사이에도 유지되는 카운트, 사용자의 제스처 이후에만 작성된 항목 공유 등을 사용할 수 있습니다. README의 개인정보 보호 고려 사항에서 이러한 완화책을 설명합니다.

8.5. GREASE 처리

사용자 에이전트는 GREASE 처리(무작위 확장 생성 및 확장성 유지)를 적용할 수 있습니다. 즉, § 8.4 가용성 게이팅이 원래 공개를 허용하는 경우에도 공개 가능한 항목이 없는 것처럼 가끔 응답합니다. 이는 사이트가 실제 부재와 개인정보 보호를 위한 거짓 음성을 구별하기 어렵게 하는 노이즈를 추가하며 UA Client Hints가 적용하는 기법과 유사합니다.

GREASE 처리는 전역적으로 공개 가능 권한만으로 자격을 얻는 오리진에만 적용됩니다. 이는 공개 해시 목록이 게이트하는 동일한 경우입니다(COS 공개 여부 결정 참조). 사용자 에이전트는 이를 저장 오리진, 명시적 origins 목록의 오리진, 또는 이 둘 중 하나와 동일 사이트인 오리진에 적용해서는 안 됩니다.

GREASE 처리를 적용하는 사용자 에이전트는 해당 항목의 크기에 비례하는 판단을 해야 합니다. 작은 항목의 경우 네트워크 가져오기로 대체하는 비용이 낮으므로 가끔 발생하는 거짓 음성은 합리적인 개인정보 보호 절충입니다. 사용자 에이전트는 크기 때문에 불필요한 재다운로드가 그에 따른 개인정보 보호 이점에 비해 명백히 지나치게 큰 항목 (예: 기가바이트 규모의 AI 모델 가중치)에 GREASE 처리를 적용해서는 안 됩니다. 그러한 경우 거짓 음성은 전체 관찰 가능하고 비용이 큰 재다운로드를 강제하기 때문입니다.

8.6. 핑거프린팅

공격자가 Cross-Origin Storage를 탐색하여 추출할 수 있는 정보는 탐색 대상 리소스의 인기도에 의해 제한됩니다. 일반적인 AI 모델이나 널리 사용되는 JavaScript 라이브러리처럼 매우 인기 있는 리소스를 사용자가 보유하고 있음을 알아도 사용자가 이를 사용하는 많은 사이트 중 하나를 방문했다는 사실만 드러납니다. 희귀하거나 고유한 리소스를 사용자가 보유하고 있음을 알아내는 것은 훨씬 더 많은 정보를 제공합니다. 사용자 에이전트는 해시가 사용자별로 의도적으로 고유해 보이는 리소스 (예: 단일 사이트에서만 작성되었거나 비정상적으로 자주 요청되는 해시)를 감지하는 장치 내 휴리스틱을 적용하고 명목상의 PHL 상태와 관계없이 이러한 패턴을 탐색 시도로 취급할 것으로 예상됩니다.

9. 다른 명세와의 통합

이 절은 비규범적입니다.

여기에서 정의한 COS 레지스트리는 getFileHandle()을 직접 거치지 않고도 네 가지 호스트 통합에서 접근할 수 있습니다. 각 통합은 자체 호스트 명세에서 정의됩니다. 이 명세는 공유 기반 개념(COS 해시, COS 항목, 가용성 게이팅 및 공개 해시 목록)과 이러한 통합이 기반으로 삼을 가져온 리소스를 Cross-Origin Storage에 저장 단계를 정의합니다.

  • HTML: 이미 integrity [SRI]를 가진 link 및 script 요소의 crossoriginstorage 속성으로, WHATWG에 whatwg/html#12770에서 제안되었습니다.

  • JavaScript: integrity와 함께 사용할 수 있는 호스트 정의 crossOriginStorage import 속성으로 Import Attributes 제안을 기반으로 하며 WHATWG에 whatwg/html#12771에서 제안되었습니다.

  • CSS: integrity()와 함께 사용할 수 있는 cross-origin-storage() <request-url-modifier>이며 CSS Working Group에 w3c/csswg-drafts#14056에서 제안되었습니다.

  • Fetch: integrity [FETCH]와 함께 사용할 수 있는 crossOriginStorage RequestInit 옵션으로 WHATWG에 whatwg/fetch#1954에서 제안되었습니다. 이 경우 호스트 정의 대상이 없으므로 COS 레지스트리에서 제공된 Response가 MIME 타입, 상태 및 기타 메타데이터를 어떻게 보고할지는 해당 명세의 열린 문제입니다. COS 항목은 bytes만 저장합니다.

설명을 위해 동일한 전역 공유 리소스를 네 가지 형태 각각으로 Cross-Origin Storage에 옵트인한 예는 다음과 같습니다:

<script src="popular-library.js" integrity="sha256-abc123..." crossoriginstorage="*"></script>

import data from "popular-resource.ext" with {
  integrity: "sha256-abc123...",
  crossOriginStorage: "*",
};

@font-face {
  font-family: "Popular Font";
  src: url("popular-font.woff2" integrity("sha256-abc123...") cross-origin-storage(*));
}

const response = await fetch("popular-resource.ext", {
  integrity: "sha256-abc123...",
  crossOriginStorage: "*",
});

이 코드 조각은 설명용일 뿐입니다. 이 구문 중 어느 것도 이 명세에서 정의하지 않습니다. 제한된 origins 목록을 어떻게 표기하는지를 포함하여 각 형태의 권위 있는 문법은 자체 호스트 명세에 속합니다. 표기는 의도적으로 다릅니다. RequestInit 멤버는 origins와 정확히 일치하는 sequence<DOMString>을 받을 수 있지만, 속성 값, import 속성 값 및 CSS 수정자 인수에는 텍스트만 담을 수 있습니다.

네 형태 모두 네트워크 가져오기로 대체하기 전에 일치하고 공개 가능한 항목이 있는지 COS 레지스트리를 먼저 확인하고, 성공적으로 가져오고 무결성이 검증된 리소스를 다른 오리진이 재사용할 수 있도록 COS 레지스트리에 저장하는 처리 모델을 공유할 것으로 예상됩니다. 이는 getFileHandle()과 정확히 동일합니다. 저장 단계는 가져온 리소스를 Cross-Origin Storage에 저장이며 각 통합은 가져온 응답과 함께 이를 실행합니다. 따라서 제한된 origins 값은 바이트를 제공하는 서버가 보낸 해당 리소스 응답의 Cross-Origin-Storage-Allow-Origin 헤더로 제한됩니다(§ 7 Cross-Origin-Storage-Allow-Origin 헤더 참조). 이러한 통합에 대한 논의는 이 저장소의 이슈 트래커가 아니라 이를 수용할 호스트 명세의 트래커에 속합니다.
