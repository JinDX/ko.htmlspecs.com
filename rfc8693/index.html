1. 소개

보안 토큰은 이기종 환경 또는 서로 다른 보안 도메인 간에 신원 및 보안 정보를 공유할 수 있도록 하는 정보의 집합입니다. 보안 토큰의 예로는 JSON 웹 토큰 (JWT) [JWT] 및 보안 어설션 마크업 언어 (SAML) 2.0 어설션 [OASIS.saml-core-2.0-os]이 있습니다. 보안 토큰은 일반적으로 무결성을 보장하기 위해 서명되며, 경우에 따라 기밀성을 보장하기 위해 암호화되기도 합니다. 보안 토큰은 [RFC7521]에서와 같이 어설션으로 설명되기도 합니다.¶

보안 토큰 서비스(STS)는 자신에게 제공된 보안 토큰을 검증하고 이에 대한 응답으로 새 보안 토큰을 발급할 수 있는 서비스로서, 이를 통해 클라이언트는 이기종 환경 또는 서로 다른 보안 도메인의 리소스에 적합한 액세스 자격 증명을 얻을 수 있습니다. 웹 서비스 클라이언트는 토큰 교환을 위해 STS와 상호 작용하는 프로토콜로 WS-Trust [WS-Trust]를 사용해 왔습니다. WS-Trust가 XML과 SOAP을 사용하는 반면, 현대적인 웹 개발의 추세는 RESTful(Representational State Transfer) 패턴과 JSON을 지향해 왔습니다. OAuth 2.0 권한 부여 프레임워크 [RFC6749] 및 OAuth 2.0 전달자 토큰 [RFC6750]은 서드 파티 애플리케이션의 HTTP 및 RESTful 리소스에 대한 액세스를 승인하는 널리 사용되는 표준으로 자리 잡았습니다. 일반적인 OAuth 2.0 상호 작용에는 리소스 소유자 권한 부여의 어떤 표현을 액세스 토큰으로 교환하는 과정이 포함되며, 이는 실제로 매우 유용한 패턴임이 입증되었습니다. 그러나 그 입력과 출력은 보안 토큰 교환 프레임워크를 완전히 수용하기에는 다소 지나치게 제한적입니다.¶

이 사양은 OAuth 2.0을 확장하여 클라이언트가 STS 역할을 하는 권한 부여 서버로부터 보안 토큰을 요청하고 획득할 수 있도록 하는 프로토콜을 정의합니다. OAuth 2.0과 마찬가지로 이 사양은 클라이언트 개발자의 단순성을 중시하며 현대적인 개발 환경에서 거의 보편적으로 제공되는 HTTP 클라이언트와 JSON 파서만을 필요로 합니다. 이 사양에서 정의하는 STS 프로토콜 자체는 RESTful이 아니지만(STS는 REST 접근 방식에 특히 적합하지 않습니다), RESTful 시스템을 사용하는 데 익숙한 개발자에게 친숙한 통신 패턴과 데이터 형식을 활용합니다.¶

토큰 교환 요청을 위한 새로운 권한 부여 유형과 토큰 엔드포인트에 대한 이러한 요청에 관련된 특정 매개변수를 이 사양에서 정의합니다. 토큰 교환 응답은 토큰 엔드포인트에서 반환되는 일반적인 OAuth 2.0 응답이며, 클라이언트에 정보를 제공하기 위해 여기에서 정의된 몇 가지 추가 매개변수가 포함됩니다.¶

토큰 교환을 요청하는 엔터티는 토큰 교환 상호 작용의 맥락에서 클라이언트로 간주됩니다. 그러나 그렇다고 해서 이 프로파일의 사용이 전통적인 OAuth 클라이언트로 제한되는 것은 아닙니다. 예를 들어 OAuth 리소스 서버는 보호된 리소스 요청에서 수신한 액세스 토큰을 백엔드 서비스 호출에 포함하기에 적합한 새 토큰으로 교환하기 위해 토큰 교환 중에 클라이언트 역할을 맡을 수 있습니다. 새 토큰은 다운스트림 서비스를 대상으로 범위가 더 좁게 지정된 액세스 토큰일 수도 있고 완전히 다른 종류의 토큰일 수도 있습니다.¶

이 사양의 범위는 OAuth 2.0을 활용하는 STS 방식의 토큰 교환을 위한 기본 요청 및 응답 프로토콜의 정의로 제한됩니다. 위임 의미를 표현할 수 있도록 몇 가지 새로운 JWT 클레임이 정의되지만, 토큰 자체의 구체적인 구문, 의미 및 보안 특성 (권한 부여 서버에 제시되는 토큰과 클라이언트가 획득하는 토큰 모두)은 명시적으로 이 사양의 범위를 벗어나며, 구현이 배포될 수 있는 신뢰 모델에는 어떠한 요구 사항도 부과하지 않습니다. 추가 프로파일에서는 당사자의 구체적인 성격과 관련 신뢰에 관한 보다 상세한 요구 사항을 제공할 수 있으며, 예를 들어 토큰의 서명 및/또는 암호화가 필요한지 또는 소유 증명 방식의 토큰이 요구되거나 발급되는지 등을 규정할 수 있습니다. 그러나 이러한 세부 사항은 개별 배포의 특정 요구 사항에 따라 결정되는 정책인 경우가 많으며, 그에 따라 구성되거나 구현됩니다.¶

획득한 보안 토큰은 여러 맥락에서 사용될 수 있으며, 그 구체적인 내용 역시 이 사양의 범위를 벗어납니다.¶

1.1. 위임과 가장의 의미

STS의 일반적인 사용 사례 중 하나는(앞 절에서 언급한 것처럼) 리소스 서버 A가 요청 사용자 B를 대신하여 백엔드 서비스 C를 호출할 수 있도록 하는 것입니다. 로컬 사이트 정책 및 권한 부여 인프라에 따라, A가 자신의 자격 증명을 사용하여 C에 액세스하면서 A가 B를 대신하여 행동하고 있음을 나타내는 어떤 형태의 주석("위임")을 함께 제공하거나, A가 C에 대한 제한된 액세스 자격 증명을 부여받되 계속해서 B를 권한이 부여된 엔터티로 식별하도록 하는 것("가장")이 바람직할 수 있습니다. 위임과 가장은 여러 참여자가 관련된 다른 시나리오에서도 유용한 개념이 될 수 있습니다.¶

보안 주체 A가 보안 주체 B를 가장하면 A에는 정의된 특정 권한 맥락 내에서 B가 가진 모든 권한이 부여되며, 해당 맥락에서는 B와 구별할 수 없습니다. 따라서 보안 주체 A가 보안 주체 B를 가장하는 경우, 그러한 토큰을 수신하는 모든 엔터티의 관점에서는 실제로 B와 상호 작용하는 것입니다. 신원 시스템의 일부 구성원이 가장이 이루어지고 있음을 인지할 수 있는 것은 사실이지만, 이는 요구 사항이 아닙니다. 모든 의도와 목적상 A가 B를 가장할 때 A는 토큰에 의해 승인된 권한의 맥락에서 B입니다. A가 B를 가장할 수 있는 능력은 토큰의 내용이나 대역 외 메커니즘을 통해 범위 또는 시간으로 제한되거나, 일회성 사용 제한이 적용될 수도 있습니다.¶

위임의 의미는 두 개념이 밀접하게 관련되어 있기는 하지만 가장의 의미와는 다릅니다. 위임 의미에서 보안 주체 A는 여전히 B와 구분되는 자신의 신원을 가지며, B가 일부 권한을 A에게 위임했을 수 있지만 모든 행동은 B를 대리하는 A가 수행하는 것으로 명시적으로 이해됩니다. 어떤 의미에서 A는 B의 대리인입니다.¶

위임과 가장이 모든 상황을 포괄하는 것은 아닙니다. 예를 들어 보안 주체가 직접 자신을 대신하여 행동하는 경우에는 위임도 가장도 적용되지 않습니다. 그러나 이들은 토큰 교환에서 더 일반적으로 적용되는 의미이므로 이 사양에서는 보다 직접적으로 다룹니다.¶

위임 의미는 일반적으로 토큰의 주된 주체와 해당 주체가 자신의 일부 권한을 위임한 행위자 모두에 관한 정보를 토큰에 포함하여 표현합니다. 이러한 토큰은 여러 주체에 관한 정보로 구성되어 있기 때문에 복합 토큰이라고도 합니다. 일반적으로 요청에서 subject_token은 토큰이 요청되는 대상이 되는 당사자의 신원을 나타내는 반면, actor_token은 발급된 토큰의 액세스 권한을 위임받는 당사자의 신원을 나타냅니다. 권한 부여 서버가 발급하는 복합 토큰에는 두 당사자에 관한 정보가 모두 포함됩니다. 복합 토큰을 발급할지 여부와 발급 시점은 권한 부여 서버와 적용 가능한 정책 및 구성의 재량에 따릅니다.¶

복합 토큰을 표현하는 구체적인 방식과 심지어 그러한 토큰을 발급할지 여부는 구현의 세부 사항과 토큰 종류에 따라 달라집니다. JWT가 아닌 복합 토큰의 표현은 이 사양의 범위를 벗어납니다. 그러나 actor_token 요청 매개변수는 원하는 행위자에 관한 정보를 제공하는 수단을 제공하며, JWT act 클레임은 위임 체인을 표현할 수 있습니다.¶

1.2. 요구 사항 표기법 및 규칙

이 문서에서 핵심어 "반드시", "해서는 안 됩니다", "필수입니다", "하여야 합니다", "하여서는 안 됩니다", "하는 것이 좋습니다", "하지 않는 것이 좋습니다", "권장됩니다", "권장되지 않습니다", "할 수 있습니다" 및 "선택 사항입니다"는 여기에서 보인 것처럼 모두 대문자로 나타나는 경우에만 BCP 14 [RFC2119] [RFC8174]에 설명된 대로 해석해야 합니다.¶

1.3. 용어

이 사양에서는 OAuth 2.0 [RFC6749]에서 정의된 "액세스 토큰 유형", "권한 부여 서버", "클라이언트", "클라이언트 식별자", "리소스 서버", "토큰 엔드포인트", "토큰 요청" 및 "토큰 응답" 이라는 용어와 JSON 웹 토큰(JWT) [JWT]에서 정의된 "Base64url 인코딩", "클레임" 및 "JWT 클레임 집합"이라는 용어를 사용합니다.¶

2. 토큰 교환 요청 및 응답

2.1. 요청

클라이언트는 권한 부여 서버의 토큰 엔드포인트에 4.5절의 [RFC6749]에서 정의된 확장 권한 부여 유형 메커니즘을 사용하여 토큰 요청을 보내 보안 토큰을 요청합니다.¶

권한 부여 서버에 대한 클라이언트 인증은 OAuth 2.0에서 제공하는 일반적인 메커니즘을 사용하여 수행합니다. 2.3.1절의 [RFC6749]에서는 클라이언트의 비밀번호 기반 인증을 정의하지만, 클라이언트 인증은 확장 가능하며 다른 메커니즘도 사용할 수 있습니다. 예를 들어 [RFC7523]에서는 전달자 JSON 웹 토큰(JWT) [JWT]을 사용한 클라이언트 인증을 정의합니다. 지원되는 클라이언트 인증 방법과 인증되지 않았거나 식별되지 않은 클라이언트를 허용할지 여부는 권한 부여 서버의 재량에 따른 배포 결정 사항입니다. 클라이언트 인증을 생략하면 손상된 토큰을 소유한 누구든지 STS를 통해 해당 토큰을 다른 토큰으로 활용할 수 있다는 점에 유의하십시오. 따라서 클라이언트 인증을 통해 STS는 어떤 엔터티가 다른 엔터티를 가장하거나 다른 엔터티로부터 위임을 받을 수 있는지 추가적인 권한 부여 검사를 수행할 수 있습니다.¶

클라이언트는 HTTP POST 메서드를 사용하여 확장 권한 부여 유형으로 토큰 엔드포인트에 토큰 교환 요청을 보냅니다. 다음 매개변수는 HTTP 요청 엔터티 본문에 application/x-www-form-urlencoded 형식과 UTF-8 문자 인코딩을 사용하여 포함되며, 이는 부록 B 의 [RFC6749]에 설명되어 있습니다.¶

grant_type
필수입니다. 값 urn:ietf:params:oauth:grant-type:token-exchange는 토큰 교환이 수행되고 있음을 나타냅니다.¶
resource
선택 사항입니다. 클라이언트가 요청된 보안 토큰을 사용하려는 대상 서비스 또는 리소스를 나타내는 URI입니다. 이를 통해 권한 부여 서버는 대상에 적합한 정책을 적용할 수 있으며, 예를 들어 발급할 토큰의 유형과 내용을 결정하거나 토큰을 어떻게 암호화할지 여부를 결정할 수 있습니다. 많은 경우 클라이언트는 상호 작용하는 시스템의 논리적 구성을 알지 못하며 토큰을 사용하려는 서비스의 URI만 알고 있습니다. resource 매개변수를 사용하면 클라이언트는 권한 부여 서버에 발급된 토큰을 사용할 위치를, 일반적으로 https URL로 제공하여 해당 리소스에 액세스할 때 사용될 것과 동일한 형식으로 토큰 교환 요청에 지정할 수 있습니다. 권한 부여 서버는 일반적으로 리소스 URI 값에서 적절한 정책으로 매핑할 수 있습니다. resource 매개변수의 값은 반드시 4.3절의 [RFC3986]에 규정된 절대 URI여야 하며, 쿼리 구성 요소를 포함할 수 있지만 프래그먼트 구성 요소는 포함해서는 안 됩니다. 여러 resource 매개변수를 사용하여 발급된 토큰이 나열된 여러 리소스에서 사용되도록 의도되었음을 나타낼 수 있습니다. resource 매개변수에 대한 추가 배경 정보 및 사용 방법은 [OAUTH-RESOURCE]를 참조하십시오.¶
audience
선택 사항입니다. 클라이언트가 요청된 보안 토큰을 사용하려는 대상 서비스의 논리적 이름입니다. 이는 resource 매개변수와 유사한 목적을 제공하지만 클라이언트가 대상 서비스의 논리적 이름을 제공합니다. 이 이름을 해석하려면 값이 클라이언트와 권한 부여 서버 모두가 이해하는 것이어야 합니다. OAuth 클라이언트 식별자, SAML 엔터티 식별자 [OASIS.saml-core-2.0-os] 및 OpenID Connect 발급자 식별자 [OpenID.Core]는 audience 매개변수 값으로 사용할 수 있는 항목의 예입니다. 그러나 특정 권한 부여 서버에서 사용하는 audience 값은 의도된 유형의 값으로 올바르게 해석되도록 해당 서버 내에서 고유해야 합니다. 여러 audience 매개변수를 사용하여 발급된 토큰이 나열된 여러 대상에서 사용되도록 의도되었음을 나타낼 수 있습니다. audience 및 resource 매개변수를 함께 사용하여 논리적 이름과 리소스 URI가 혼합된 여러 대상 서비스를 나타낼 수 있습니다.¶
scope
선택 사항입니다. 3.3절의 [RFC6749]에서 정의된, 공백으로 구분되고 대소문자를 구분하는 문자열 목록으로, 클라이언트가 토큰이 사용될 서비스 또는 리소스의 맥락에서 요청된 보안 토큰의 원하는 범위를 지정할 수 있게 합니다. 범위의 값과 관련 의미는 서비스별로 다르며 관련 서비스 문서에 설명되어야 합니다.¶
requested_token_type
선택 사항입니다. 요청된 보안 토큰 유형을 나타내는 3절에 설명된 식별자입니다. 요청된 유형을 지정하지 않으면 발급되는 토큰 유형은 권한 부여 서버의 재량에 따르며 resource 또는 audience 매개변수로 나타낸 서비스 또는 리소스의 요구 사항에 대한 지식에 따라 결정될 수 있습니다.¶
subject_token
필수입니다. 요청이 대신 이루어지는 당사자의 신원을 나타내는 보안 토큰입니다. 일반적으로 이 토큰의 주체는 요청에 대한 응답으로 발급되는 보안 토큰의 주체가 됩니다.¶
subject_token_type
필수입니다. subject_token 매개변수에 있는 보안 토큰의 유형을 나타내는 3절에 설명된 식별자입니다.¶
actor_token
선택 사항입니다. 행동하는 당사자의 신원을 나타내는 보안 토큰입니다. 일반적으로 이는 요청된 보안 토큰을 사용하고 주체를 대신하여 행동할 권한이 부여된 당사자입니다.¶
actor_token_type
actor_token 매개변수에 있는 보안 토큰의 유형을 나타내는 3절에 설명된 식별자입니다. 요청에 actor_token 매개변수가 있는 경우 필수이지만, 그렇지 않은 경우 포함해서는 안 됩니다.¶

요청을 처리할 때 권한 부여 서버는 표시된 토큰 유형에 적합한 검증 절차를 반드시 수행해야 하며, 행위자 토큰이 있는 경우에는 표시된 해당 토큰 유형에 대해서도 적절한 검증 절차를 수행해야 합니다. 특정 토큰의 유효성 기준과 세부 사항은 이 문서의 범위를 벗어나며 각 토큰 유형 및 그 내용에 따라 달라집니다.¶

일회성 사용 또는 토큰 유형에 특정한 다른 의미가 없는 경우 토큰 교환을 수행하는 행위는 주체 토큰이나 행위자 토큰의 유효성에 아무런 영향을 미치지 않습니다. 또한 교환은 일회성 이벤트이며 입력 토큰과 출력 토큰 사이에 긴밀한 연결을 만들지 않으므로, 예를 들어 출력 토큰의 만료 시간이 입력 토큰의 만료 시간에 영향을 받을 수 있더라도 입력 토큰의 갱신 또는 연장이 출력 토큰의 속성에 반영되지는 않습니다. 토큰 취소 이벤트를 전파하는 것이 여전히 적절하거나 바람직할 수 있습니다. 그러나 그렇게 하는 것은 STS 프로토콜의 일반적인 속성이 아니며 특정 구현, 토큰 유형 또는 배포에 따라 달라집니다.¶

2.1.1. 리소스, 대상 및 범위 간의 관계

토큰을 요청할 때 클라이언트는 audience 및 resource 매개변수를 통해 해당 토큰을 사용하려는 원하는 대상 서비스를 나타낼 수 있으며 scope 매개변수를 사용하여 요청된 토큰의 원하는 범위도 나타낼 수 있습니다. 이러한 요청은 클라이언트가 요청된 범위를 가지며 요청된 모든 대상 서비스에서 사용할 수 있는 토큰을 요청한다는 의미입니다. 실질적으로 토큰의 요청된 액세스 권한은 모든 대상 서비스에 있는 모든 범위의 데카르트 곱입니다.¶

권한 부여 서버는 어떤 토큰 요청이든 이행할 의사가 없거나 이행할 수 없을 수 있지만, 매우 광범위한 액세스 권한을 요청할 때 이행할 수 없는 요청이 될 가능성은 상당히 높습니다. 따라서 배포 환경에서 시스템 간 관계에 대한 구체적인 지식이 없는 경우, 클라이언트는 요청하는 액세스의 범위, 특히 대상 서비스의 수를 신중하게 결정해야 합니다. 권한 부여 서버는 2.2.2절에서 정의된 invalid_target 오류 코드를 사용하여 클라이언트에게 동시에 너무 많은 대상 서비스에 대한 액세스를 요청했음을 알릴 수 있습니다.¶

2.2. 응답

권한 부여 서버는 5절의 [RFC6749]에 규정된 대로 토큰 엔드포인트의 일반적인 OAuth 2.0 응답으로 토큰 교환 요청에 응답합니다. 추가적인 세부 사항과 설명은 다음 하위 절에서 제공합니다.¶

2.2.1. 성공 응답

요청이 유효하고 권한 부여 서버의 모든 정책 및 기타 기준을 충족하면, [RFC8259]에 규정된 "application/json" 미디어 유형과 HTTP 200 상태 코드를 사용하여 다음 매개변수를 HTTP 응답의 엔터티 본문에 추가함으로써 성공적인 토큰 응답을 구성합니다. 매개변수는 각 매개변수를 최상위 수준에 추가하여 JavaScript Object Notation(JSON) 구조로 직렬화합니다. 매개변수 이름과 문자열 값은 JSON 문자열로 포함합니다. 숫자 값은 JSON 숫자로 포함합니다. 매개변수의 순서는 중요하지 않으며 달라질 수 있습니다.¶

access_token
필수입니다. 토큰 교환 요청에 대한 응답으로 권한 부여 서버가 발급한 보안 토큰입니다. 5.1절의 [RFC6749]에 있는 access_token 매개변수를 여기에서 요청된 토큰을 전달하는 데 사용하며, 이를 통해 이 토큰 교환 프로토콜은 기존 OAuth 2.0 요청 및 토큰 엔드포인트용으로 정의된 응답 구조를 사용할 수 있습니다. access_token 식별자는 역사적인 이유로 사용되며 발급된 토큰이 반드시 OAuth 액세스 토큰일 필요는 없습니다.¶
issued_token_type
필수입니다. 발급된 보안 토큰의 표현을 나타내는 3절에 설명된 식별자입니다.¶
token_type
필수입니다. 발급된 액세스 토큰을 사용하는 방법을 지정하는 대소문자를 구분하지 않는 값으로, 7.1절의 [RFC6749]에 규정되어 있습니다. 이 값은 보호된 리소스에 액세스하기 위해 액세스 토큰을 활용하는 방법에 관한 정보를 클라이언트에 제공합니다. 예를 들어 Bearer 값은 [RFC6750]에 규정된 대로 발급된 보안 토큰이 전달자 토큰이며 클라이언트가 토큰 자체의 내용 이외에 자격에 대한 추가 증명 없이 그대로 제시할 수 있음을 나타냅니다. 이 매개변수의 의미는 issued_token_type 매개변수의 의미와 다르다는 점에 유의하십시오. 후자는 발급된 보안 토큰의 표현을 선언합니다. "토큰 유형"이라는 용어는 일반적으로 보안 토큰의 구조적 또는 구문적 표현을 의미하는 데 사용되며, 이 사양의 모든 *_token_type 매개변수에서도 그러합니다. 발급된 토큰이 액세스 토큰이 아니거나 액세스 토큰으로 사용할 수 없는 경우 token_type 값 N_A를 사용하여 OAuth 2.0 token_type 식별자가 해당 맥락에 적용되지 않음을 나타냅니다.¶
expires_in
권장됩니다. 권한 부여 서버에서 발급한 토큰의 유효 기간을 초 단위로 나타냅니다. 클라이언트는 토큰의 내용을 검사할 의향이나 능력이 없는 경우가 많으며, 이 매개변수는 토큰이 얼마나 오랫동안 유효할 것으로 예상할 수 있는지에 대해 토큰 유형에 구애받지 않는 일관된 표시를 제공합니다. 예를 들어 값 1800은 응답이 생성된 시점으로부터 30분 후에 토큰이 만료됨을 나타냅니다.¶
scope
발급된 보안 토큰의 범위가 클라이언트가 요청한 범위와 동일한 경우 선택 사항입니다. 그렇지 않은 경우 필수입니다.¶
refresh_token
선택 사항입니다. 하나의 임시 자격 증명(subject_token)을 다른 맥락에서 사용할 다른 임시 자격 증명(발급된 토큰)으로 교환하는 경우 일반적으로 새로 고침 토큰은 발급되지 않습니다. 토큰 교환 클라이언트가 원래 자격 증명이 더 이상 유효하지 않은 경우에도 리소스에 액세스할 수 있어야 하는 경우에는 새로 고침 토큰을 발급할 수 있습니다 (예: 사용자 부재 또는 더 이상 사용자가 클라이언트와 활성 세션을 유지하지 않는 오프라인 시나리오). 이 사양의 프로파일 또는 배포에서는 클라이언트가 어떤 조건에서 urn:ietf:params:oauth:grant-type:token-exchange 권한 부여 유형 요청에 대한 응답으로 새로 고침 토큰을 기대할 수 있는지 명확히 문서화해야 합니다.¶

2.2.2. 오류 응답

요청 자체가 유효하지 않거나 subject_token 또는 actor_token 중 하나가 어떤 이유로든 유효하지 않거나 정책에 따라 허용되지 않는 경우, 권한 부여 서버는 반드시 5.2절의 [RFC6749]에 규정된 대로 오류 응답을 구성해야 합니다. error 매개변수의 값은 반드시 invalid_request 오류 코드여야 합니다.¶

권한 부여 서버가 resource 또는 audience 매개변수로 표시된 대상 서비스에 토큰을 발급할 의사가 없거나 발급할 수 없는 경우, 오류 응답에서 invalid_target 오류 코드를 사용하는 것이 좋습니다.¶

권한 부여 서버는 5.2절의 [RFC6749]에서 설명한 error_description을 사용하여 오류의 이유에 관한 추가 정보를 포함할 수 있습니다.¶

필요한 경우 다른 오류 코드도 사용할 수 있습니다.¶

2.3. 토큰 교환 예시

다음 예시는 OAuth 리소스 서버가 교환 중에 클라이언트 역할을 맡는 가상의 토큰 교환을 보여 줍니다. 이 서버는 보호된 리소스 요청에서 받은 액세스 토큰을 새 토큰으로 교환하여 백엔드 서비스를 호출하는 데 사용합니다 (예시의 추가 줄 바꿈과 들여쓰기는 표시 목적일 뿐입니다).¶

그림 1은 리소스 서버가 Authorization 헤더에 OAuth 액세스 토큰이 포함된 보호된 리소스 요청을 수신하는 모습을 보여 주며, 이는 2.1절의 [RFC6750]에 규정되어 있습니다.¶

그림 2에서 리소스 서버는 토큰 교환을 위한 클라이언트 역할을 맡으며, 요청에 포함된 액세스 토큰은 그림 1에서 2.1절에 규정된 요청을 사용하여 권한 부여 서버로 전송됩니다. subject_token 매개변수의 값은 액세스 토큰을 전달하며, subject_token_type 매개변수의 값은 그것이 OAuth 2.0 액세스 토큰임을 나타냅니다. 클라이언트 역할을 하는 리소스 서버는 자신의 식별자와 비밀 값을 사용하여 HTTP Basic 인증 체계를 통해 권한 부여 서버에 인증합니다. resource 매개변수는 발급된 토큰이 사용될 백엔드 서비스 <https://backend.example.com/api>의 위치를 나타냅니다.¶

권한 부여 서버는 클라이언트 자격 증명과 토큰 교환 요청에 제시된 subject_token을 검증합니다. resource 매개변수로부터 권한 부여 서버는 요청에 적용할 적절한 정책을 결정할 수 있으며 <https://backend.example.com>에서 사용하기에 적합한 토큰을 발급합니다. 그림 3에 표시된 응답의 access_token 매개변수에는 새 토큰이 포함되며, 이 토큰은 자체적으로 1분 동안 유효한 전달자 OAuth 액세스 토큰입니다. 이 토큰은 우연히 JWT이지만, 그 구조와 형식은 클라이언트에 불투명하므로 issued_token_type은 그것이 액세스 토큰이라는 사실만 나타냅니다.¶

그런 다음 리소스 서버는 새로 획득한 액세스 토큰을 사용하여 그림 4에 나타낸 것처럼 백엔드 서버에 요청할 수 있습니다.¶

추가 예시는 부록 A에서 확인할 수 있습니다.¶

3. 토큰 유형 식별자

이 사양의 여러 매개변수에서는 해당 토큰을 설명하기 위한 값으로 식별자를 사용합니다. 구체적으로 요청의 requested_token_type, subject_token_type 및 actor_token_type 매개변수와 응답의 issued_token_type 멤버가 이에 해당합니다. 토큰 유형 식별자는 URI입니다. 토큰 교환은 다른 당사자가 발급한 토큰과 해당 권한 부여 서버에서 발급한 토큰 모두를 대상으로 작동할 수 있습니다. 전자의 경우 토큰 유형 식별자는 권한 부여 서버가 토큰을 파싱할 수 있도록 구문(예: JWT 또는 SAML 2.0)을 나타내고, 후자의 경우에는 해당 권한 부여 서버가 무엇을 위해 이를 발급했는지(예: access_token 또는 refresh_token)를 나타냅니다.¶

이 사양에서는 다음 토큰 유형 식별자를 정의합니다. 다른 토큰 유형을 나타내기 위해 다른 URI를 사용할 수 있습니다.¶

urn:ietf:params:oauth:token-type:access_token
토큰이 해당 권한 부여 서버에서 발급한 OAuth 2.0 액세스 토큰임을 나타냅니다.¶
urn:ietf:params:oauth:token-type:refresh_token
토큰이 해당 권한 부여 서버에서 발급한 OAuth 2.0 새로 고침 토큰임을 나타냅니다.¶
urn:ietf:params:oauth:token-type:id_token
토큰이 [OpenID.Core]의 2절에서 정의된 ID 토큰임을 나타냅니다.¶
urn:ietf:params:oauth:token-type:saml1
토큰이 base64url로 인코딩된 SAML 1.1 [OASIS.saml-core-1.1] 어설션임을 나타냅니다.¶
urn:ietf:params:oauth:token-type:saml2
토큰이 base64url로 인코딩된 SAML 2.0 [OASIS.saml-core-2.0-os] 어설션임을 나타냅니다.¶

urn:ietf:params:oauth:token-type:jwt 값은 9절의 [JWT]에서 정의되며, 토큰이 JWT임을 나타냅니다.¶

액세스 토큰과 JWT의 차이는 미묘합니다. 액세스 토큰은 위임된 권한 부여 결정을 나타내는 반면, JWT는 토큰 형식입니다. 액세스 토큰은 JWT 형식일 수 있지만 반드시 그럴 필요는 없습니다. 또한 JWT가 액세스 토큰일 수도 있지만 모든 JWT가 액세스 토큰인 것은 아닙니다. 이 사양에서 urn:ietf:params:oauth:token-type:access_token은 해당 권한 부여 서버에서 발급한 일반적인 OAuth 액세스 토큰이며, 클라이언트에는 불투명하고 해당 권한 부여 서버에서 획득한 다른 액세스 토큰과 동일한 방식으로 사용할 수 있음을 나타내는 것을 의도합니다. (이 토큰이 JWT일 수도 있지만 클라이언트는 그 사실을 알지 못하며 알 필요도 없습니다.) 반면 urn:ietf:params:oauth:token-type:jwt는 JWT가 구체적으로 요청되거나 전송되고 있음을 나타내기 위한 것입니다(예를 들어 [RFC7523]에서 지원하는 것처럼 JWT가 권한 부여 승인을 나타내는 값으로 사용되어 다른 권한 부여 서버에서 액세스 토큰을 획득하는 교차 도메인 사용 사례일 수 있습니다).¶

본질적으로 바이너리인 토큰의 경우, 이를 전달하는 데 사용되는 URI는 HTTP 및 OAuth에서 사용하기에 적합한 base64 또는 기타 인코딩의 의미와 연결되어야 한다는 점에 유의하십시오.¶

4. JSON 웹 토큰 클레임 및 검사 응답 매개변수

토큰 내에서 위임을 표현하는 메커니즘뿐만 아니라 위임 또는 가장에 대한 권한 부여를 표현하는 메커니즘을 정의해 두는 것이 유용합니다. 여기에서 설명하는 토큰 교환 프로토콜은 모든 유형의 토큰과 함께 사용할 수 있지만, 이 절에서는 이러한 의미를 JWT 및 OAuth 2.0 토큰 검사 [RFC7662] 응답에서 구체적으로 표현하기 위한 클레임을 정의합니다. 다른 유형의 토큰에 대해서도 유사한 정의가 가능하지만 이 사양의 범위를 벗어납니다.¶

여기에서 정의하지 않았지만 예시와 설명에서 사용하는 클레임인 iss, sub, exp 등은 [JWT]에서 정의된다는 점에 유의하십시오.¶

4.1. "act" (행위자) 클레임

act (행위자) 클레임은 JWT 내에서 위임이 이루어졌음을 표현하고 권한이 위임된 행동 당사자를 식별하는 수단을 제공합니다. act 클레임 값은 JSON 객체이며, JSON 객체의 멤버는 행위자를 식별하는 클레임입니다. act 클레임을 구성하는 클레임은 행위자를 식별하고 경우에 따라 행위자에 관한 추가 정보를 제공합니다. 예를 들어, 두 클레임 iss와 sub의 조합이 행위자를 고유하게 식별하는 데 필요할 수 있습니다.¶

그러나 act 클레임 내의 클레임은 행위자의 신원에만 관련되며, 최상위 클레임과 같은 방식으로 이를 포함하는 JWT의 유효성과는 관련이 없습니다. 따라서 신원과 관련되지 않은 클레임(예: exp, nbf, 및 aud)은 act 클레임 내에서 사용될 때 의미가 없으므로 사용하지 않습니다.¶

그림 5는 JWT 클레임 집합 내의 act (행위자) 클레임을 보여 줍니다. 토큰 자체의 클레임은 user@example.com에 관한 것이며, act 클레임은 admin@example.com이 현재 행위자임을 나타냅니다.¶

하나의 act 클레임을 다른 act 클레임 안에 중첩하여 위임 체인을 표현할 수 있습니다. 가장 바깥쪽 act 클레임은 현재 행위자를 나타내며, 중첩된 act 클레임은 이전 행위자를 나타냅니다. 가장 오래된 행위자가 가장 깊게 중첩됩니다. 중첩된 act 클레임은 현재 행위자에 도달하기 전에 수행된 여러 위임 단계를 통해 초기 요청과 주체를 연결하는 이력 추적 정보 역할을 합니다. 이러한 의미에서 현재 행위자는 전체 권한 부여/위임 이력을 포함하는 것으로 간주되며, 이는 자연스럽게 여기에서 설명한 중첩 구조로 이어집니다.¶

액세스 제어 정책을 적용할 목적으로, 토큰의 소비자는 반드시 토큰의 최상위 클레임과 act 클레임에 의해 현재 행위자로 식별된 당사자만 고려해야 합니다. 중첩된 act 클레임에 의해 식별된 이전 행위자는 정보 제공용일 뿐이며 액세스 제어 결정에서 고려해서는 안 됩니다.¶

그림 6의 다음 예시는 JWT 클레임 집합 내에 중첩된 act (행위자) 클레임을 보여 줍니다. 토큰 자체의 클레임은 user@example.com에 관한 것이며, act 클레임은 시스템 <https://service16.example.com>이 현재 행위자이고 <https://service77.example.com>이 이전 행위자였음을 나타냅니다. 이러한 토큰은 service16이 service77의 호출에서 토큰을 수신하고, 권한 부여 서버가 새로 발급되는 토큰에 해당 상황을 기록하면서 service26을 호출하기에 적합한 토큰으로 이를 교환한 결과로 생성될 수 있습니다.¶

OAuth 토큰 검사 응답의 최상위 멤버로 포함되는 경우 act는 같은 이름의 클레임과 동일한 의미와 형식을 가집니다.¶

4.2. "scope" (범위) 클레임

scope 클레임의 값은 토큰과 연관된 범위를 공백으로 구분한 목록을 포함하는 JSON 문자열이며, 그 형식은 3.3절의 [RFC6749]에 설명되어 있습니다.¶

그림 7은 JWT 클레임 집합 내의 scope 클레임을 보여 줍니다.¶

OAuth 2.0 토큰 검사 [RFC7662]에서는 이미 토큰과 연관된 범위를 전달하기 위한 scope 매개변수를 정의합니다.¶

4.3. "client_id" (클라이언트 식별자) 클레임

client_id 클레임은 토큰을 요청한 OAuth 2.0 [RFC6749] 클라이언트의 클라이언트 식별자를 전달합니다.¶

그림 8의 다음 예시는 식별자가 "s6BhdRkqt3"인 OAuth 2.0 클라이언트를 나타내는 JWT 클레임 집합 내의 client_id 클레임을 보여 줍니다.¶

OAuth 2.0 토큰 검사 [RFC7662]에서는 이미 client_id 매개변수를 토큰을 요청한 OAuth 2.0 클라이언트의 클라이언트 식별자로 정의합니다.¶

4.4. "may_act" (권한이 부여된 행위자) 클레임

may_act 클레임은 한 당사자가 행위자가 되어 다른 당사자를 대신하여 행동할 권한이 부여되었음을 나타냅니다. 예를 들어 토큰 교환 요청에서 subject_token이 토큰 엔드포인트에 제시될 때 이 클레임을 사용할 수 있으며, 주체 토큰의 may_act 클레임은 권한 부여 서버가 클라이언트(또는 actor_token에서 식별된 당사자)가 요청된 위임 또는 가장을 수행할 권한이 있는지 결정하는 데 사용할 수 있습니다. 클레임 값은 JSON 객체이며, JSON 객체의 멤버는 해당 클레임을 포함하는 JWT에 의해 식별된 당사자를 대신하여 행동할 자격이 있다고 선언된 당사자를 식별하는 클레임입니다. may_act 클레임을 구성하는 클레임은 권한이 부여된 행위자를 식별하고 경우에 따라 추가 정보를 제공합니다. 예를 들어 두 클레임 iss 및 sub의 조합은 권한이 부여된 행위자를 고유하게 식별하는 데 필요한 경우가 있으며, email 클레임은 해당 당사자에 관한 추가적인 유용한 정보를 제공하는 데 사용할 수 있습니다.¶

그러나 may_act 클레임 내의 클레임은 해당 당사자의 신원에만 관련되며, 최상위 클레임과 같은 방식으로 이를 포함하는 JWT의 유효성과는 관련이 없습니다. 따라서 exp, nbf 및 aud와 같은 클레임은 may_act 클레임 내에서 사용될 때 의미가 없으므로 사용하지 않습니다.¶

그림 9는 JWT 클레임 집합 내의 may_act 클레임을 보여 줍니다. 토큰 자체의 클레임은 user@example.com에 관한 것이며, may_act 클레임은 admin@example.com이 user@example.com을 대신하여 행동할 권한이 있음을 나타냅니다.¶

OAuth 토큰 검사 응답의 최상위 멤버로 포함되는 경우, may_act는 같은 이름의 클레임과 동일한 의미와 형식을 가집니다.¶

5. 보안 고려 사항

10절의 [RFC6749], 즉 OAuth 2.0 권한 부여 프레임워크의 보안 고려 사항에 있는 많은 지침이 여기에도 적용됩니다. 또한 [RFC6819]에서는 OAuth에 대한 추가적인 보안 고려 사항을 제공하며, [OAUTH-SECURITY]에서는 OAuth 2.0이 처음 게시된 이후의 배포 경험과 새롭게 등장한 위협을 바탕으로 보안 지침을 업데이트했습니다.¶

[JWT]에서 논의하는 일반적인 모든 보안 문제, 특히 URI 비교 및 인식되지 않은 값 처리와 관련된 문제도 여기에서 동일하게 적용됩니다.¶

또한 위임과 가장은 각각 고유한 보안 문제를 발생시킵니다. 한 보안 주체에게 다른 보안 주체의 권한이 위임될 때마다 악용 가능성이 문제가 됩니다. 이러한 악용 가능성을 완화하기 위해 scope 클레임을 사용하는 것이 (제한된 토큰 수명과 같은 다른 일반적인 제약 조건과 함께) 권장됩니다. 이는 위임된 권한을 행사할 수 있는 맥락을 제한하기 때문입니다.¶

6. 개인정보 보호 고려 사항

여기에서 설명한 기능의 맥락에서 사용되는 토큰에는 개인정보 보호에 민감한 정보가 포함될 수 있으며, 이러한 정보가 의도하지 않은 당사자에게 공개되는 것을 방지하기 위해 반드시 전송 계층 보안 (TLS)과 같은 암호화된 채널을 통해서만 전송해야 합니다. 특정 정보가 클라이언트에 공개되는 것을 방지하는 것이 바람직한 경우 토큰은 의도된 수신자를 대상으로 반드시 암호화해야 합니다. 배포에서는 필요한 데이터의 최소량을 결정하고 발급된 토큰에는 그러한 정보만 포함하는 것이 좋습니다. 경우에 따라 데이터 최소화에는 익명 또는 가명 사용자만 표현하는 것이 포함될 수 있습니다.¶

A.1.1. 토큰 교환 요청

앞선 요청의 subject_token은 JWT이며, 디코딩된 JWT 클레임 집합은 여기에 표시되어 있습니다. 이 JWT는 특정 시간 범위 내에 권한 부여 서버에서 사용하도록 되어 있습니다. JWT의 주체(bdc@example.net)는 새 토큰을 대신 요청하는 대상이 되는 당사자입니다.¶

A.1.3. 토큰 교환 응답

아래 표시된 토큰 교환 응답의 access_token 매개변수에는 클라이언트가 요청한 새 토큰이 포함되어 있습니다. 응답의 다른 매개변수는 이 토큰이 한 시간 후 만료되는 전달자 액세스 토큰임을 나타냅니다.¶

A.1.4. 발급된 토큰 클레임

발급된 토큰의 디코딩된 JWT 클레임 집합은 아래에 표시되어 있습니다. 새 JWT는 권한 부여 서버에서 발급되며 논리적 이름 urn:example:cooperation-context으로 알려진 시스템 엔터티가 만료되기 전 언제든 사용할 수 있도록 되어 있습니다. JWT의 주체(sub)는 요청을 수행하는 데 사용한 토큰의 주체와 동일하며, 이를 통해 클라이언트는 실질적으로 해당 토큰을 사용하여 논리적 이름 urn:example:cooperation-context으로 알려진 시스템 엔터티에서 그 주체를 가장할 수 있습니다.¶

A.2. 위임 토큰 교환 예시

A.2.1. 토큰 교환 요청

다음 토큰 교환 요청에서 클라이언트는 토큰을 요청하면서 subject_token과 actor_token을 모두 제공합니다. 클라이언트는 권한 부여 서버에 논리적 이름이 urn:example:cooperation-context인 대상 서비스에서 사용할 토큰이 필요하다고 알립니다. 권한 부여 서버의 정책에 따라 발급되는 토큰은 복합 토큰이어야 합니다.¶

A.2.2. 주체 토큰 클레임

앞선 요청의 subject_token은 JWT이며, 디코딩된 JWT 클레임 집합은 여기에 표시되어 있습니다. 이 JWT는 특정 만료 시간 전에 권한 부여 서버에서 사용하도록 되어 있습니다. JWT의 주체 (user@example.net)는 새 토큰을 대신 요청하는 대상이 되는 당사자입니다.¶

A.2.3. 행위자 토큰 클레임

앞선 요청의 actor_token은 JWT이며, 디코딩된 JWT 클레임 집합은 여기에 표시되어 있습니다. 이 JWT 역시 특정 만료 시간 전에 권한 부여 서버에서 사용하도록 되어 있습니다. JWT의 주체 (admin@example.net)는 요청 중인 보안 토큰을 사용할 행위자입니다.¶

A.2.4. 토큰 교환 응답

아래 표시된 토큰 교환 응답의 access_token 매개변수에는 클라이언트가 요청한 새 토큰이 포함되어 있습니다. 응답의 다른 매개변수는 이 토큰이 한 시간 후 만료되는 JWT이며, 발급된 토큰이 액세스 토큰이 아니므로 액세스 토큰 유형이 적용되지 않음을 나타냅니다.¶

A.2.5. 발급된 토큰 클레임

발급된 토큰의 디코딩된 JWT 클레임 집합은 아래에 표시되어 있습니다. 새 JWT는 권한 부여 서버에서 발급되며 논리적 이름 urn:example:cooperation-context으로 알려진 시스템 엔터티가 만료되기 전 언제든 사용할 수 있도록 되어 있습니다. JWT의 주체(sub)는 요청을 수행하는 데 사용한 subject_token의 주체와 동일합니다. JWT의 행위자(act)는 요청을 수행하는 데 사용한 actor_token의 주체와 동일합니다. 이는 위임을 나타내며, admin@example.net을 user@example.net을 대신하여 행동할 권한을 위임받은 현재 행위자로 식별합니다.¶
