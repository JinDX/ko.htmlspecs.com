초록

이 문서는 SHACL 규칙을 정의합니다.

SHACL, 즉 Shapes Constraint Language는 RDF 그래프의 구조를 설명하기 위한 언어입니다. SHACL은 검증, 추론, 도메인 모델링, 다른 에이전트에 정보를 제공하기 위한 온톨로지 생성, 사용자 인터페이스 구축, 코드 생성, 데이터 통합 등 다양한 목적으로 사용될 수 있습니다.

SHACL 규칙은 규칙 집합과 기본 데이터 그래프의 조합으로부터 새로운 RDF 데이터를 생성하여 추론을 제공합니다. 규칙은 RDF 또는 Shape Rules Language(SRL)로 표현될 수 있습니다.

이 명세는 Data Shapes 워킹 그룹에서 발행합니다.

1. 소개

이 문서는 선언적 규칙을 통해 기존 RDF 데이터에서 새로운 RDF 트리플을 도출하는 메커니즘인 SHACL 1.2의 추론 규칙을 소개합니다. 이 문서는 규칙 기반 추론의 구문과 의미론을 정의합니다.

SHACL Rules의 구현은 두 가지 작업을 제공합니다. infer 작업은 주어진 기본 그래프에 규칙을 적용하고 규칙 실행으로 도출된 RDF 트리플을 포함하는 추론 그래프를 생성합니다. 추론 그래프를 기본 그래프와 결합하는 것은 선택 사항이며 사용자에게 맡겨집니다. query 작업은 주어진 목표 패턴이 규칙을 사용하여 기본 그래프로부터 도출될 수 있는지를 판정합니다.

SHACL Rules는 규칙의 머리부에 있는 트리플 템플릿에서 사용할 수 있는 빈 노드를 포함하여 새로운 RDF 용어의 사용을 허용합니다.

SHACL Rules는 또한 실패로서의 부정과 같은 구조를 지원하며, 이러한 구조는 규칙이 실행되는 순서에 따라 서로 다른 추론 그래프로 이어질 수 있습니다. 이를 피하기 위해 규칙은 계층화 기법을 사용하여 평가되며, 이는 규칙 간에 단일한 암묵적 순서를 설정하여 항상 동일한 추론 그래프가 생성되도록 보장합니다.

3. SHACL 규칙

이 절은 비규범입니다.

SHACL 규칙은 기본 그래프와 규칙 집합이 주어졌을 때 새로운 트리플을 추론합니다. 평가의 출력은 기본 그래프에 나타나지 않는 도출된 트리플을 포함하는 추론 그래프입니다.

각 규칙은 본문이라고 하는 패턴과, 머리부라고 하는 결과 템플릿을 가집니다. 규칙은 본문 안의 변수 값들을 찾아 실행되며, 이때 본문은 결합된 기본 그래프 및 지금까지의 실행에서 나온 모든 추론 트리플과 일치해야 합니다. 그런 다음 이러한 값은 규칙 머리부의 트리플 템플릿을 인스턴스화하는 데 사용되어 새로운 추론 트리플을 생성합니다.

규칙은 더 이상 트리플이 추론되지 않을 때까지 실행되며, 새로운 추론 트리플을 사용할 수 있게 되면 규칙이 두 번 이상 실행될 수 있습니다.

SHACL Rules 실행은 새로운 빈 노드를 포함한 새로운 RDF 용어를 만들 때나 패턴의 부재를 테스트할 때, 규칙 실행 순서가 서로 다른 결과를 초래하지 않도록 정의됩니다. 즉, 규칙 실행 순서와 관계없이 동일한 추론 그래프가 생성됩니다.

SPARQL-RL은 SPARQL 1.2 쿼리 언어에서 영감을 받은 사용자 친화적인 구문을 사용합니다. 규칙 집합 평가에는 SPARQL과 유사한 요소가 포함되지만, 규칙 실행 순서와 관계없이 동일한 추론 그래프가 생성되도록 하기 위해 세부 사항에는 차이가 있습니다.

3.1 기본 패턴

이 절의 예제에서는 소프트웨어 구성 요소와 그 종속성을 설명한다. 프런트엔드는 애플리케이션 서버를 호출하고, 애플리케이션 서버는 알려진 취약점이 있는 데이터베이스를 조회한다.

이 첫 번째 예제에는 다음 데이터 그래프와 규칙 집합이 있습니다:

예제 1: 기본 예제 
:frontend :callsService :app .
:app      :queriesDatabase :db .
:db       :hasVulnerability :vuln1 .
RULE { ?x :dependsOn ?y } WHERE { ?x :callsService ?y }
RULE { ?x :dependsOn ?y } WHERE { ?x :queriesDatabase ?y }
:frontend :dependsOn :app .
:app      :dependsOn :db .

위 규칙을 데이터에 적용하면, :frontend가 :app에 종속되고, :app이 종속성의 종류와 관계없이 :db에 종속된다는 결론을 내린다.

그런 다음 다른 규칙이 생성한 :dependsOn 트리플에 종속되는 규칙을 추가하여 :exposedTo 관계를 도출할 수 있다(아래의 4.3 규칙 종속성도 참조):

예제 2: 추론된 트리플에 종속 
:frontend :callsService :app .
:app      :queriesDatabase :db .
:db       :hasVulnerability :vuln1 .
RULE { ?x :dependsOn ?y } WHERE { ?x :callsService ?y }
RULE { ?x :dependsOn ?y } WHERE { ?x :queriesDatabase ?y }
RULE { ?x :exposedTo ?v } WHERE { ?x :dependsOn ?y . ?y :hasVulnerability ?v }
:app      :exposedTo :vuln1 .
:frontend :dependsOn :app .
:app      :dependsOn :db .

3.2 재귀

이전 절의 :exposedTo 규칙은 직접적인 종속성에만 도달한다. :frontend는 :db에 직접 종속되지 않으므로, :frontend에 대한 :exposedTo 트리플은 추론되지 않는다. 임의 길이의 종속성 체인을 따라 노출을 전파하기 위해 해당 규칙을 두 규칙으로 대체한다. 구성 요소는 자신이 가진 취약점에 노출되며, 구성 요소는 직접 종속 대상이 노출된 모든 취약점에 노출된다.

예제 3: 규칙 재귀 
:frontend :callsService :app .
:app      :queriesDatabase :db .
:db       :hasVulnerability :vuln1 .
RULE { ?x :dependsOn ?y } WHERE { ?x :callsService ?y }
RULE { ?x :dependsOn ?y } WHERE { ?x :queriesDatabase ?y }
RULE { ?x :exposedTo ?v } WHERE { ?x :hasVulnerability ?v }
RULE { ?x :exposedTo ?v } WHERE { ?x :dependsOn ?y . ?y :exposedTo ?v }
:db       :exposedTo :vuln1 .
:app      :exposedTo :vuln1 .
:frontend :exposedTo :vuln1 .
:frontend :dependsOn :app .
:app      :dependsOn :db .

이전 예제와 비교하면 여기에는 :db :exposedTo :vuln1이 추가된다. 즉, 데이터베이스는 자체 취약점에 노출된다. 또한 :frontend :exposedTo :vuln1도 추가된다. 체인의 길이에 관계없이 노출이 종속성 체인을 통해 :frontend에 도달한다.

이 마지막 규칙은 재귀 규칙이다. 규칙의 본문이 규칙의 머리부에 종속된다.

3.3 필터링

규칙 본문의 표현식을 사용하여 본문을 일치시키는 과정에서 변수의 값을 제한할 수 있다. 예를 들어 각 취약점의 심각도가 주어지면, 심각한 취약점에 노출된 구성 요소에 상태를 부여할 수 있다.

예제 4: 필터링 
:app1 :exposedTo :vuln1 .
:app2 :exposedTo :vuln2 .
:vuln1 :severity 9.1 .
:vuln2 :severity 4.3 .
RULE { ?x :status :criticallyExposed }
WHERE {
    ?x :exposedTo ?v .
    ?v :severity ?s .
    FILTER(?s >= 9.0)
}
:app1 :status :criticallyExposed .

FILTER는 표현식을 평가하고 표현식이 참으로 평가되면 현재 변수 바인딩 집합을 유지하며, 표현식이 거짓으로 평가되면 현재 변수 바인딩 집합을 폐기한다. 이는 SPARQL의 FILTER 연산과 동일하며, SHACL 규칙은 SPARQL과 동일한 함수 및 연산자를 다수 제공한다.

3.4 부정

부정은 일치해서는 안 되는 패턴을 지정할 수 있게 한다. 이를 "실패로서의 부정"이라고 한다.

부정 요소를 평가하기 위해 규칙 평가 알고리즘은 부정 요소의 패턴과 일치하는 트리플을 생성할 수 있는 모든 규칙이 완료되었는지 확인한다. 이를 계층화라고 하며, 부정이 데이터에서 온 것이든 부정 요소에서 온 것이든 관련된 모든 가능한 트리플을 기반으로 하도록 보장한다. 부정을 포함하는 규칙은 이러한 트리플을 생성하는 규칙에 _종속_된다고 한다(아래의 4.3 규칙 종속성 참조).

예제 5: 실패로서의 부정 
:app rdf:type :Component ;
:status :criticallyExposed .

:logger rdf:type :Component .
RULE { ?x :status :safeToDeploy }
WHERE {
    ?x rdf:type :Component .
    NOT { ?x :status :criticallyExposed }
}
:logger :status :safeToDeploy .

3.5 할당 및 RDF 용어 생성

할당을 사용하면 규칙 본문에서 표현식의 결과를 변수에 할당할 수 있다. 이를 사용하여 데이터를 기반으로 새로운 RDF 용어를 생성할 수 있다.

예제 6: 할당 
RULE { ?v :riskScore ?r }
WHERE {
    ?v :severity ?s .
    ?v :exploitLikelihood ?p .
    SET ( ?r := ?s * ?p )
}

규칙 머리부에서 빈 노드를 사용할 수 있으며, 각 빈 노드는 규칙 평가에서 트리플이 생성될 때마다 새로운 빈 노드를 생성한다.

예제 7: 규칙 머리부의 빈 노드 
RULE { [] rdf:type :Notification ; :concerns ?x }
WHERE { ?x :status :criticallyExposed }

할당이 포함된 규칙과 규칙 머리부에서 빈 노드를 생성하는 규칙은 일회 실행 규칙이다. 이러한 규칙은 자신이 종속되는 데이터를 생성할 수 있는 모든 규칙이 실행된 후, 그리고 자신이 생성하는 데이터에 종속되는 모든 규칙이 실행되기 전에 실행된다. 규칙 머리부에 빈 노드가 포함된 규칙도 새로운 RDF 용어를 생성하며 일회 실행 규칙이다.

이 조건은 이러한 규칙이 자기 자신으로 되돌아가 반복되어 무제한으로 많은 RDF 용어를 생성하지 않도록 보장한다.

할당에서 표현식을 평가할 때 오류가 발생하면, 현재 해 매핑은 해당 할당에 의해 거부된다.

3.6 규칙 집합 가져오기

SHACL 규칙 집합은 해당 규칙 집합의 규칙 집합 가져오기에 다른 규칙 집합의 URL을 포함하여 해당 규칙 집합을 통합할 수 있다. 이를 통해 규칙을 여러 규칙 집합 간에 공유되는 라이브러리로 구성할 수 있다.

규칙 집합의 IMPORTS 문은 규칙 집합의 규칙이 평가되기 전에 처리된다. 가져오기 단계에서 가져온 규칙 집합에 자체 가져오기가 있는 경우 해당 가져오기도 재귀적으로 처리된다. 규칙 집합을 처리하는 동안 IMPORTS 문을 순회하면 순환 가져오기가 발생할 수 있다. 규칙 집합은 한 번만 가져온다. 가져오기 문 그래프의 순환으로 인해 무한 루프가 발생하지 않는다.

규칙 집합 가져오기 지원은 SRL 프로세서에서 선택 사항이다. 자세한 내용은 4.5 가져오기 처리를 참조한다.

3.7 데이터 블록

데이터 블록을 사용하면 RDF 트리플을 규칙 집합 평가에 직접 간결하게 제공할 수 있다. 데이터 블록의 트리플은 추론 그래프에 추가되며 규칙 본문에서 일치시키는 데 사용할 수 있다.

예를 들어 규칙 집합에는 데이터에서 도출하는 대신 알려진 사실을 직접 명시하여 포함할 수 있다.

예제 8: 규칙 집합에 데이터 포함 
DATA {
    # 버전 2.0.0 이하에는 알려진 취약점이 있으며
    # 심각하게 노출된 것으로 간주된다.
    :appV2 rdf:type :Component ;
           :version "2.0.0" ;
           :status :criticallyExposed .
}
참고

데이터 블록은 본문이 비어 있는 규칙과 동등하다. 해당 트리플은 어떠한 규칙도 평가하지 않고 추론 그래프의 일부가 된다.

3.8 규칙 집합의 평가

규칙은 규칙 집합으로 구성된다. 규칙 집합과 데이터 그래프(기본 그래프)는 평가의 입력이다. 출력은 추론 그래프라고 하는 그래프이며, 데이터 그래프에 나타나지 않는 트리플의 집합이다.

평가 중에 하나의 규칙을 기반으로 추론된 트리플은 다른 규칙에서 일치 여부를 확인하는 데 사용할 수 있다. 규칙 집합 평가는 추론 그래프가 규칙 집합과 데이터 그래프의 입력에서 나올 수 있는 모든 트리플을 포함할 때까지 진행된다.

평가는 규칙 자체를 평가하기 전에 규칙 집합을 준비하는 두 단계로 시작된다.

  1. 지원되는 경우 입력 규칙 집합의 가져오기를 해석하여 가져온 모든 규칙 집합의 모든 규칙을 포함하는 규칙 집합을 구성한다. 프로세서는 가져오기가 프로세서에서 허용되지 않는 경우 오류를 MUST 보고해야 한다 (4.5 가져오기 처리).
  2. 층화를 계산한다(4.4.2 층화 알고리즘 이를 통해 부정 요소와 할당 요소가 일관되고 예측 가능한 결과를 생성하도록 한다. 층화에는 규칙 간의 종속성을 검사하는 작업이 포함된다 (4.3.1 종속성 그래프).

규칙 집합의 준비가 완료되면, 평가는 계층화의 각 계층을 순서대로 가져와 해당 계층의 규칙을 완료될 때까지 평가한 다음 다음 계층으로 이동하는 방식으로 진행된다.

3.9 그라운드 데이터 일치

기초 데이터는 기본 그래프의 트리플이다. 규칙 집합 평가 중에는 추론된 트리플이 아닌 원래 트리플에 대해서만 패턴 매칭해야 할 필요가 있을 수 있다.

이에 대한 예로 기본값 설정이 있다. 규칙은 기본 그래프에 값이 이미 포함되어 있는지 테스트해야 하며, 그렇지 않은 경우 규칙은 기본값을 계산할 수 있다.

예제 9: NOT을 사용한 기초 데이터 
:A :distanceMiles 5 .
:A :distanceKilometers 8 .
:B :distanceMiles 10 .
RULE  { ?x :distanceKilometers ?kilometers }
WHERE {
    ?x :distanceMiles ?miles . 
    NOT DATA { ?x :distanceKilometers ?km }
    SET ( ?kilometers := xsd:integer(?miles *  1.60934))
}
:B :distanceKilometers 16 .

NOT DATA를 사용하면 규칙 본문의 다른 부분이 추론된 트리플과 매칭될 수 있다. 또한 WHERE DATA를 사용하여 모든 규칙 본문 매칭을 기본 그래프에 대해 수행할 수도 있다. 그러면 이러한 규칙은 기본 그래프에서의 매칭에만 의존한다.

예제 10: WHERE를 사용한 기초 데이터 
RULE  { ?x :distanceKilometers ?kilometers }
WHERE DATA {
    ?x :distanceMiles ?originalMiles .
    NOT { ?x :distanceKilometers ?km } 
    SET ( ?kilometers := xsd:integer(?originalMiles *  1.60934))
}

3.10 SHACL 통합

이슈 1074: FOR ?v IN <shape> SRL

FOR ?v IN <shape>는 해당 모델 위에 대상을 다시 도입합니다. 이는 단일 규칙을 SHACL 셰이프에 연결하므로 규칙은 셰이프를 준수하는 셰이프의 대상 포커스 노드에 대해서만 실행되며, 사용자가 명명한 "포커스 변수"는 이러한 각 노드에 미리 바인딩됩니다.

전체 제안

4. Shape Rules 추상 구문

Shape Rules 추상 구문은 SHACL Rules의 논리적 구조입니다. SHACL Rules의 실행 알고리즘을 정의하는 데 사용됩니다.

4.1 추상 구문의 요소

변수
변수는 트리플 패턴에서 가능한 RDF 항을 나타낸다. 변수는 표현식에서도 사용된다.
표현식
표현식은 함수 또는 함수형 형식이며, 인수는 RDF 항이다. 표현식은 솔루션 매핑을 기준으로 평가되어, 그 결과로 RDF 항을 제공한다. 표현식은 SHACL 목록 매개변수 함수 및 SPARQL 표현식과 호환된다.
데이터 블록
데이터 블록은 트리플 집합이다. 이러한 트리플은 추가 사실로 추론 그래프에 추가되며 추론 프로세스에 포함된다.
트리플 템플릿
트리플 템플릿은 각 요소가 변수 또는 RDF 항(트리플 항일 수도 있음)인 3-튜플이다. 튜플의 두 번째 요소는 IRI 또는 변수여야 한다. 트리플 템플릿은 헤드에 나타나는 규칙이다.
트리플 패턴
트리플 패턴은 각 요소가 변수 또는 RDF 항(트리플 항일 수도 있음)인 3-튜플이다. 튜플의 두 번째 요소는 IRI 또는 변수여야 한다.
필터 요소
필터 요소는 표현식이며 규칙 요소로 나타난다. 이는 패턴 일치에서 변수의 값을 제한하는 데 사용된다.
트리플 패턴 요소
트리플 패턴 요소는 트리플 패턴이며 규칙 요소로 나타난다.
부정 요소
부정 요소는 규칙 요소이다. 이는 부정 요소 본문을 가지며, 이는 일련의 트리플 패턴 요소와 필터 요소로 구성된다.
할당 요소
할당 요소는 규칙 요소이며, 한 쌍으로 구성된다. 즉, 할당 변수라고 하는 변수와, 할당 표현식이라고 하는 표현식이다.
규칙 요소
규칙 요소는 다음 중 하나이다. 트리플 패턴 요소, 필터 요소, 부정 요소 또는 할당 요소.
규칙 헤드
규칙 헤드는 일련의 트리플 템플릿이다.
규칙 본문
규칙 본문은 일련의 규칙 요소이며, 즉 각 시퀀스 요소는 다음 중 하나이다. 트리플 패턴 요소, 필터 요소, 부정 요소, 또는 할당 요소.
규칙 집합 임포트
규칙 집합 임포트(흔히 단순히 "임포트")는 평가 중에 포함될 다른 규칙 집합의 URL 모음이다.
규칙
규칙은 규칙 헤드(흔히 단순히 "헤드")와 규칙 본문(흔히 단순히 "본문")의 쌍이다. 규칙에는 식별을 돕기 위해 URI를 부여할 수 있다.
일회 실행 규칙
일회 실행 규칙은 규칙 집합 평가의 특정 시점에 정확히 한 번 실행되는 규칙이다.
일반 규칙
일반 규칙은 일회 실행 규칙이 아닌 규칙이다. 일반 규칙은 규칙 집합 평가 중 두 번 이상 실행될 수 있다.
규칙 집합
규칙 집합은 0개 이상의 규칙 모음, 0개 이상의 데이터 블록 모음, 그리고 0개 이상의 규칙 집합 임포트 모음이다. 해결된 규칙 집합은 규칙 집합이며 임포트가 없다. 해결된 규칙 집합은 다른 규칙 집합에서 임포트 프로세스를 적용하여 생성된다.
기본 그래프
기본 그래프는 평가 프로세스에 입력으로 주어진 RDF 그래프이다.
추론 그래프
추론 그래프는 규칙 집합 평가에 의해 생성된 RDF 그래프이다. 여기에는 기본 그래프에 없는 모든 추론된 트리플이 포함되며, 이는 규칙 집합을 기본 그래프에 적용하여 추론된다.
규칙 집합 평가
규칙 집합 평가는 규칙 집합을 기본 그래프에 적용하여 추론 그래프를 생성하는 프로세스이다. 규칙 평가는 규칙을 한 번 평가하는 프로세스이다. 규칙을 평가하면 규칙 헤드가 제공하는 모든 트리플이 규칙 본문의 평가에 따라 생성되며, 해당 트리플이 기본 그래프에 있거나, 이미 규칙 집합 평가 중에 추론되었거나, 새로 추론된 트리플인지 여부와 관계없이 그러하다. 규칙 집합 평가 중에는 규칙이 두 번 이상 평가될 수 있다.

Shape Rules Language는 추론과 질의라는 두 가지 연산을 제공한다.

추론
추론은 규칙 집합을 주어진 기본 그래프에 적용하고 추론된 트리플을 포함하는 추론 그래프를 생성하는 연산이다. 이는 전체 규칙 집합 평가를 적용한다.
질의

질의는 주어진 목표 패턴을 기본 그래프에서 규칙 집합을 사용하여 도출할 수 있는지 결정하는 연산이다. 모든 규칙을 평가하지 않을 수도 있으며, 대신 질의 목표에 답하는 데 필요한 규칙만 평가할 수 있다.

질의는 추론 연산을 수행한 다음, 목표 패턴을 결합된 기본 그래프와 추론 그래프에 매칭하는 것과 동등하다.

트리플 패턴 또는 트리플 템플릿에서, 튜플의 위치 1은 비공식적으로 주어, 위치 2는 비공식적으로 술어, 그리고 위치 3은 비공식적으로 목적어라고 한다.

참고

규칙 요소 시퀀스의 요소에는 1부터 번호가 지정된다.

4.2 올바른 형식 조건

정형성은 규칙 집합의 추상 구문에 적용되는 일련의 조건입니다. 이러한 조건은 함께 규칙의 변수가 헤드에 있을 경우 규칙의 본문에서 값이 정의되도록 하고, 필터 요소 또는 할당 표현식의 각 변수가 평가 시점에 값을 갖도록 하며, 규칙의 각 할당이 규칙 본문의 앞부분에서 사용되지 않은 새로운 변수를 도입하도록 보장합니다.

초기 변수 집합이 주어진 규칙 요소 시퀀스에 대한 정형성을 정의한다.

elti를 규칙 요소 시퀀스의 i번째 요소라고 하자.

varsi를 elti가 정의하는 변수 집합이라고 하자. 여기서:

  • elti가 트리플 패턴 요소이면
    • varsi는 변수 중 트리플 패턴 요소에 나타나는 것들의 집합이다.
  • elti가 할당 요소이면
    • varsi는 할당 변수의 집합이다.
  • 그 외의 경우,
    • varsi는 공집합이다.

V0를 시퀀스의 초기 변수라고 하자.

Vi를 V0와 i보다 작은 모든 j에 대한 varsj의 합집합이라고 하자.

Vall을 VN이라고 하자. 여기서 N은 시퀀스의 길이이다.

변수 집합 V0가 주어진 경우, 다음 조건을 충족하는 규칙 요소의 시퀀스를 정형 시퀀스라고 한다:

  • elti가 필터 요소이면
    • 변수 중 필터 요소에서 언급된 모든 변수는 Vi-1의 요소이다.
  • elti가 할당 요소이면
    • 할당 표현식에서 언급된 모든 변수는 Vi-1의 요소이다.
    • 할당 변수는 Vi-1의 요소가 아니다.
  • elti가 부정 요소이면
    • 부정 요소 본문의 규칙 요소 시퀀스는 변수 집합 Vi-1가 주어진 정형 시퀀스이다.

규칙은 V0가 공집합일 때 규칙 본문의 시퀀스가 정형 시퀀스이고, 규칙 헤드의 트리플 템플릿에 있는 각 변수가 Vall의 요소이면 정형 규칙이다.

규칙 집합은 규칙 집합의 모든 규칙이 정형 규칙인 경우에만 정형 규칙 집합이다.

4.3 규칙 의존성

규칙 R1은 두 번째 규칙의 출력이 첫 번째 규칙의 본문 평가에 영향을 미치는 경우 규칙 R2에 의존한다. 즉, R2의 헤드에는 R1 본문의 트리플 패턴과 매칭되는 트리플을 생성할 수 있는 트리플 템플릿이 있으며, 이는 트리플 패턴 요소이거나 부정 요소 내부에 있을 수 있다.

종속성에는 두 가지 종류가 있다: 폐쇄 종속성과 개방 종속성. 폐쇄 종속성은 규칙 R1이 실행되기 전에 규칙 R2가 가능한 모든 출력을 생성했음을 보장한다. 규칙 종속성이 폐쇄되어 있지 않으면 개방 종속성이며, 이를 통해 첫 번째 규칙 R1은 규칙 R2가 다시 실행되어 추가 트리플을 생성할 수 있는 동안 실행될 수 있고, 이후 R2의 새 트리플로 인해 R1이 다시 평가될 수 있다.

이 첫 번째 예제에서 첫 번째 규칙은 두 번째 규칙에 대해 개방 종속성을 가진다.

예제 11: 개방 종속성 
RULE { ?x :exposedTo ?v } WHERE { ?x :dependsOn ?y . ?y :hasVulnerability ?v }
RULE { ?x :dependsOn ?y } WHERE { ?x :callsService ?y }

이 두 번째 예제에서 첫 번째 규칙은 두 번째 규칙에 대해 폐쇄 종속성을 가진다: 트리플 패턴 ?x :status :criticallyExposed는 첫 번째 규칙의 부정 요소 내부에 나타나며, 두 번째 규칙의 헤드에 있는 트리플 템플릿과 매칭된다. 첫 번째 규칙은 두 번째 규칙이 가능한 모든 출력을 생성할 때까지 평가할 수 없다.

예제 12: 폐쇄 종속성 
RULE { ?x :status :safeToDeploy }
WHERE { ?x rdf:type :Component . NOT { ?x :status :criticallyExposed } }

RULE { ?x :status :criticallyExposed } WHERE { ?x :exposedTo ?v }
트리플 패턴 매칭

트리플 패턴은 트리플 템플릿이 트리플 패턴과 매칭되는 트리플을 생성할 수 있는 경우 해당 트리플 템플릿과 매칭된다.

트리플 패턴 종속성

트리플 패턴은 해당 트리플 패턴이 트리플 템플릿과 매칭될 가능성이 있는 경우 트리플 템플릿에 의존한다.

트리플 패턴은 해당 트리플 패턴이 규칙의 헤드에 있는 트리플 템플릿 중 하나에 종속되는 경우 규칙에 의존한다.

규칙 종속성

규칙 R1 본문의 트리플 패턴 중 하나가 트리플 패턴 요소로 있거나 부정 요소 내부에 있는지에 관계없이, R2의 헤드에 있는 트리플 템플릿에 의존하는 경우 규칙 R1은 R2에 의존한다.

폐쇄 종속성

규칙 R1의 규칙 R2에 대한 규칙 종속성은 다음 조건 중 하나라도 성립하면 폐쇄 종속성이다:

  • R1의 부정 요소 내부에 나타나는 트리플 패턴이 R2의 규칙 헤드에 있는 트리플 템플릿과 매칭된다.
  • 규칙 R1이 규칙 R2에 의존하고 R1에 할당 요소가 있다.
  • 규칙 R1이 규칙 R2에 의존하고 R1의 규칙 헤드에 빈 노드가 있다.
개방 종속성

규칙 R1의 규칙 R2에 대한 규칙 종속성은 해당 종속성이 폐쇄 종속성이 아닌 경우 개방 종속성이다. 즉, R2에 의존하는 R1의 모든 트리플 패턴은 트리플 패턴 요소로만 나타난다.

트리플 템플릿의 변수에 값을 대입하여 템플릿의 변수를 값으로 대체했을 때, T2가 T1과 같은 트리플 T2가 만들어지는 값이 존재하는 경우, 트리플 템플릿은 RDF 트리플 T1을 생성할 수 있다.

마찬가지로, 트리플 패턴의 변수에 값을 대입하여 패턴의 변수를 값으로 대체했을 때, T2가 T1과 같은 트리플 T2가 만들어지는 값이 존재하는 경우, 트리플 패턴은 트리플 T1과 매칭된다. 트리플 패턴의 경우 여기에는 대칭 트리플이 포함된다.

변수가 트리플 템플릿 또는 트리플 패턴에서 두 번 이상 사용되는 경우, 동일한 RDF 용어가 대체 값으로 사용된다.

변수를 RDF 용어로 대체하는 것은 트리플 용어 내부의 변수도 포함한다.

4.3.1 의존성 그래프

규칙 간의 종속성은 방향 그래프로 표현되며, 이를 종속성 그래프라고 한다. 그래프의 정점은 규칙 집합의 규칙이며, 간선에는 종속성이 개방 종속성인지 폐쇄 종속성인지에 따라 개방 또는 폐쇄라는 레이블이 지정된다.

종속성 그래프
규칙 집합의 종속성 그래프는 각 정점이 규칙 집합의 규칙이고, R1이 R2에 의존하는 경우 규칙 R1에서 규칙 R2로 향하는 간선이 존재하는 방향 그래프이다. 간선에는 종속성이 개방 종속성인지 폐쇄 종속성인지에 따라 개방 또는 폐쇄라는 레이블이 지정된다.
전이적 규칙 종속성
규칙 R1에서 R2로 이어지는 경로가 종속성 그래프에 존재하면 규칙 R1은 규칙 R2에 대해 전이적 종속성을 가진다.
재귀적 규칙 종속성

규칙 R을 포함하는 순환 경로가 종속성 그래프에 존재하면 규칙 R은 재귀적 종속성을 가진다.

참고

종속성 그래프는 데이터 그래프의 영향을 받지 않는다.

4.3.2 의존성 그래프 알고리즘

다음 알고리즘은 종속성 그래프를 규칙 집합에서 구성하는 한 가지 가능한 방법을 제시한다. 적합성은 이 절차의 사용 여부가 아니라 종속성 그래프의 정의를 충족하는 종속성 그래프를 생성하는지에 달려 있다. 

define mergeLabel(oldLabel, newLabel):
    ## 폐쇄 종속성이 개방 종속성보다 우선한다.
    if oldLabel == "open" and newLabel == "open":
        return "open"
    else:
        return "closed"
    endif
enddefine

## 출력 -- 규칙 정점과 레이블이 지정된 간선을 가진 종속성 그래프.
define buildDependencyGraph(ruleSet):
    ## edgeLabelMap은 (R1, R2)를 "open" 또는 "closed"에 매핑한다
    let edgeLabelMap be a map from pair (rule, rule) to label

    foreach rule R1 in ruleSet.rules:
        ## 규칙의 각 트리플 패턴 TP를 "open" 또는 "closed"가 필요한 것으로 분류한다
        ## 이는 해당 패턴이 부정 요소에 있는지 여부에 따라 결정된다.
        let bodyDependencies = {}
        foreach rule element RBE in R1.body:
            if RBE is a negation element:
                foreach triple pattern TP in RBE.inner
                    let item be a pair (TP, "closed")
                    add item to bodyDependencies
                endfor
            else if RBE is a triple pattern element of triple pattern TP:
                let item be a pair (TP, "open")
                add item to bodyDependencies
            else if RBE is a condition element:
                ## 아무 작업도 하지 않는다
            else if RBE is an assignment element:
                ## 아무 작업도 하지 않는다
            endif
        endfor

        foreach pair (triple pattern TP, depLabel) in bodyDependencies:
            if R1.body has an assignment element:
              set depLabel to "closed"
            endif
            if R1.head has a triple template with a blank node:
              set depLabel to "closed"
            endif
            ## 이 트리플 패턴 요소 또는 부정 요소의 종속성을 찾는다.
            foreach rule R2 in ruleSet.rules:
                foreach triple template TT in R2.head:
                    if triple pattern TP matches triple template TT:
                        let key = (R1, R2)
                        if edgeLabelMap contains key:
                            let oldLabel = edgeLabelMap.get(key)
                            let merged = mergeLabel(oldLabel, depLabel)
                            edgeLabelMap.set(key, merged)
                        else:
                            edgeLabelMap.set(key, depLabel)
                        endif
                    endif
                endfor
            endfor
        endfor
    endfor

    let DP = { }
    foreach entry ((R1, R2), label) in edgeLabelMap:
        add an edge (R1 -> R2) labeled with label to DP
    endfor

    the result is DP
    enddefine

4.4 계층화

층화는 규칙 집합을 순서가 지정된 층화 계층 시퀀스("계층"이라고도 하며, 단수형은 "계층")로 분할하는 프로세스이다. 더 낮은 계층의 규칙은 더 높은 계층의 규칙보다 먼저 평가된다.

층화는 규칙 간의 종속성에 제약을 부과하여 부정 요소, 할당 요소, 그리고 규칙 헤드에서 생성된 빈 노드가 이전의(더 낮은) 계층과 기본 그래프를 사용하여 계산된 결과에만 의존하도록 한다. 이는 주어진 기본 그래프에 대한 규칙 집합 평가에서 단일하고 명확하게 정의되며 유한한 결과가 나오도록 보장한다.

참고

층화 프로세스는 다른 평가 결정을 내리는 데에도 사용될 수 있다. 이 문서는 일관된 평가에 필요한 조건을 설명하고 층화를 구성하는 한 가지 가능한 방법을 제시한다. 구현은 호환되는 동작을 얻기 위해 여기에서 설명한 조건을 충족해야 하지만, 제시된 알고리즘을 그대로 구현할 필요는 없다.

층화 계층

층화 계층 SL은 서로소인 두 규칙 집합 (SL.once, SL.general)의 쌍이다. SL.once에는 일회 실행 규칙이 포함되며, 이는 할당 요소를 사용하거나 규칙 헤드에서 빈 노드를 생성하는 규칙이다. 이러한 규칙은 각각 층화 계층의 평가가 시작될 때 정확히 한 번 평가된다. SL.general에는 나머지 규칙이 포함되며, 새 트리플이 더 이상 추론되지 않을 때까지 반복해서 평가된다.

층화
규칙 집합의 층화는 층화 계층의 시퀀스이다. 규칙 집합의 각 규칙은 층화 계층 중 하나의 집합에 정확히 하나만 나타난다.

4.4.1 계층화 조건

층화는 다음 조건이 충족되는 경우에만 정의된다. 규칙 집합이 이 조건을 충족하지 않으면, 이 명세는 그러한 규칙 집합의 평가 결과를 정의하지 않는다.

층화 조건
층화 조건은 규칙 집합의 종속성 그래프에 폐쇄 종속성이 포함된 재귀적 종속성이 없어야 함을 요구한다.

즉, 트리플 템플릿에 빈 노드가 포함된 NOT 또는 일회 실행 규칙(할당 또는 규칙)은 종속성 그래프의 어떤 전이적 종속성 순환에도 존재하지 않는다.

4.4.2 계층화 알고리즘

다음 알고리즘은 규칙 집합만을 기반으로 하는 한 가지 가능한 층화를 제시한다. 

## 출력 -- 맵: 정수 -> 규칙 집합.

define stratification(ruleSet):

    let DP = Dependency graph for the rule set.
    let stratumMap be a map from rule to integer

    ## 종속성 그래프는 층화 조건을 충족해야 한다.
    ## 무제한 층화 검사는 층화 조건 위반으로 인한 
    ## 상황을 방지하기 위한 보호 장치이다.
    let limit = num rules + 1
    let maxStratum = 0

    ## stratumMap 초기화
    foreach rule in ruleSet.rules:
        stratumMap.set(rule, 0)
        endfor

    boolean changed = true;
    while changed:
        changed = false;
        foreach edge E in DP:
            ## 레이블이 있는 pRule에서 qRule로 향하는 간선
            let pRule = source of edge
            let qRule = destination of the edge
            let label = edge label

            if label == "open" :
                if stratumMap.get(pRule) < stratumMap.get(qRule) :
                    stratumMap.set(pRule, stratumMap.get(qRule))
                    changed = true;
                endif
            endif
            if label == "closed" :
                if stratumMap.get(pRule) <= stratumMap.get(qRule) :
                    let xStratum = 1 + stratumMap.get(qRule)
                    if ( xStratum > limit )
                        ## 층화 요구 사항 위반
                        error "Stratification error"
                        endif
                    stratumMap.set(pRule, xStratum)
                    maxStratum = max(maxStratum, xStratum)
                    changed = true;
                endif
            endif
        endfor
    endwhile

    ## 결과 맵을 초기화한다.
    let stratumRules be a map from integer to rules.
    for i = 0 to maxStratum
        stratumRules.set(i, {})
    endfor

    ## stratumMap에서 동일한 계층 번호를 가진 규칙을 수집한다
    for rule R in map stratumMap:
        let stratumNum = stratumMap.get(R)
        add R to stratumRules.get(stratumNum)
    endfor

    ## 각 계층을 once와 general로 분할한다
    let stratumLevels be a sequence of pairs of sets of rules.
    for i = 0 to maxStratum:
        let rules = stratumRules.get(i)
        let once = { R in rules | R is a run-once rule }
        let general = rules \ once
        stratumLevels.set(i, pair(once, general))
    endfor

    the result is stratumLevels
enddefine
참고

층화 조건의 결과 중 하나는 일회 실행 규칙이 평가되면, 규칙의 결과를 결정하는 데 사용되는 데이터가 이후 평가 중에는 변경되지 않는다는 것이다.

전체 규칙 집합에 종속성 분석과 층화를 단계별로 적용하고 평가까지 진행하는 예는 6.6 작업 예제에 제시되어 있다.

웹에서 문서를 읽는 것은 보안상 영향을 미친다. 규칙 집합 가져오기 지원은 SRL 프로세서에서 선택 사항이다. 또한 구현은 특정 규칙 집합의 가져오기는 지원하고 다른 규칙 집합의 가져오기는 지원하지 않는 방식과 같이 부분적인 지원을 제공할 MAY 있으며, 검증된 사본에서 가져오도록 할 수도 있다.

  • 프로세서는 IMPORTS 문을 처리할 때 무한 루프를 방지하기 위해 규칙 집합을 한 번만 가져와야 MUST 한다.

5. SRL과 SPARQL의 관계

이 섹션은 비규범적입니다.

SRL과 SPARQL은 밀접한 관계가 있습니다. SRL은 SPARQL과 호환되도록 설계되었으며, SRL의 많은 구문은 SPARQL에서 가져왔거나 SPARQL에서 영감을 받았습니다. 그러나 몇 가지 차이점이 있습니다.

SRL에서 RULE 변수는 FILTER 및 SET의 표현식에서 사용되든, 트리플 템플릿 또는 규칙 헤드에서 사용되든 항상 사용 전에 바인딩됩니다. SPARQL CONSTRUCT 쿼리는 변수가 CONSTRUCT 템플릿에 나타나지만 WHERE 절에서 값이 주어지지 않으면 부분적인 결과를 생성합니다.

  • 변수가 트리플 패턴 요소 중 적어도 하나에 나타나도록 보장하는 정형성 조건으로, 필터 요소 또는 할당 요소에서 사용되기 전에 규칙 본문 내에 나타나야 합니다.
  • SRL SET 형식과 SPARQL BIND 형식은 오류 처리 동작이 다릅니다. SET에서 발생한 오류는 현재 해를 필터링하여 제외하는 반면, BIND는 현재 해에서 변수를 설정하지 않고 해를 그대로 전달합니다. SET(?var := expr)은 SPARQL에서 BIND(expr AS ?var) 뒤에 FILTER(BOUND(?var))를 사용하는 것과 같습니다.
  • 규칙 본문의 WHERE 절 구문에는 UNION 또는 OPTIONAL 구문이 포함되지 않습니다. 이러한 SPARQL 요소는 바인딩되지 않은 변수를 만들 수 있습니다. UNION 또는 OPTIONAL의 효과는 정형 규칙을 사용하여 구현할 수 있으며, 이를 통해 규칙 집합을 분석할 수 있습니다.

그 밖의 차이점은 다음과 같습니다.

  • NOT의 구문은 내부 본문을 트리플 패턴과 필터로 제한하며, SPARQL FILTER NOT EXISTS와 달리 중첩 패턴을 허용하지 않습니다.
  • 속성 경로 구문은 트리플 패턴으로 확장할 수 있는 경로만 다룹니다. 임의 길이 연산자 * 및 +는 허용하지 않습니다. 임의 길이 경로는 SRL에서 더 일반적인 접근 방식인 재귀를 사용해 표현할 수 있습니다.
  • 일부 함수는 SRL 구문에 포함되지 않습니다. COALESCE도 BOUND도 없습니다. 해시 함수도 없습니다. 호출될 때마다 다른 결과를 반환하는 RAND도 없습니다.
    참고
    NOW()는 허용되며 규칙 집합 평가 전체에서 동일한 시점을 반환하도록 정의됩니다. 이는 SPARQL의 NOW()와 동일합니다.

6. 규칙 집합 평가

이 절은 주어진 데이터에 대해 규칙 집합을 평가한 결과를 정의합니다. 이는 구현 방법으로서 알고리즘을 규정하지 않습니다. 구현은 동일한 결과를 생성하는 어떤 알고리즘도 사용할 수 있습니다. 

Inputs: data graph G, called the base graph, and a rule set RS.
Output: an RDF graph GI of inferred triples

추론된 트리플은 기본 그래프의 트리플 집합에 존재하는 트리플을 포함하지 않습니다.

6.1 평가 정의

해답 매핑
해답 매핑 μ는 부분 함수 μ : V → T이며, 여기서 V는 모든 변수의 집합이고 T는 모든 RDF 용어의 집합이다. μ의 정의역은 dom(μ)로 나타내며, 이는 μ가 정의된 V의 부분집합이다. 해답 매핑을 의미한다는 것이 명확한 경우 해답이라는 용어를 사용한다. dom(μ0)가 공집합인 해답 매핑을 μ0으로 표기한다.
치환 함수
치환 함수, 또는 간단히 치환은 함수 subst(μ, 트리플 패턴) 로, 트리플 패턴을 반환하며, 여기서 트리플 패턴 내에서 dom(μ) 에 포함된 변수의 각 출현은 var에 대한 솔루션 매핑이 제공하는 RDF 항으로 대체된다. 트리플 패턴 결과에 변수가 없으면, 이는 RDF 트리플이다.
평가 그래프
평가 그래프는 RDF 그래프로, 기본 그래프와 규칙 집합을 평가하는 동안 생성된 모든 트리플을 결합한다.
그래프 매칭
그래프 매칭은 트리플 패턴을 RDF 그래프의 트리플에 매핑하는 방법을 찾는다.

G를 RDF 그래프라고 하고 TP를 트리플 패턴이라고 하자. 함수 graphMatch(G, TP)는 트리플 패턴에 적용했을 때 평가 그래프에 있는 트리플을 생성하는 가능한 모든 솔루션의 집합을 반환한다.

G를 RDF 그래프, TP를 트리플 패턴, 그리고 V를 TP에 나타나는 변수의 집합이라고 하자. 

graphMatch(G, TP) = { μ | dom(μ) = V and subst(μ, TP) is a triple in G }
솔루션 호환
두 솔루션 S1과 S2는 공통 변수에 대해 일치하면 호환된다.

S1과 S2를 솔루션이라고 하자. 

compatible(μ1, μ2) = true
                      if forall v in dom(μ1) intersection dom(μ2)
                          μ1(v) = μ2(v)
compatible(μ1, μ2) = false otherwise
솔루션 시퀀스
솔루션 시퀀스는 솔루션의 다중 집합이다. 이 시퀀스에는 정의된 순서가 없다. 이는 순서가 없는 목록과 동등하며 중복을 포함할 수 있다.
솔루션 병합
두 솔루션이 호환되는 경우, 두 솔루션의 병합은 각 솔루션의 변수를 어느 한 솔루션의 RDF 항에 매핑하는 솔루션이다.
μ1, μ2를 솔루션 매핑이라고 하고, S1과 S2를 솔루션 시퀀스라고 하자. 
merge(μ1, μ2) = { μ |
                    μ(v) = μ1(v) if v in dom(μ1)
                    μ(v) = μ2(v) otherwise }
merge(S1, S2) = { μ |
                    μ1 in S1, μ2 in S2
                    and compatible(μ1, μ2)
                    μ(v) = merge(μ1, μ2) }
참고

merge(S1, S2)의 정의역은 domain(S1) ∪︀ domain(S2)이다.

두 솔루션에 공통 변수가 없으면 서로 호환되며, 두 솔루션의 병합은 S1과 S2의 합집합이다.

유효 불리언 값
함수 EBV(x)는 RDF 항에 대한 유효 불리언 값을 반환한다.

6.3 표현식 평가

필터 요소 또는 할당 요소에서 사용되는 표현식은, 표현식 안의 각 변수에 대해 RDF 용어인 값을 제공하는 해 매핑과 관련하여 평가됩니다. 4.2 올바른 형식 조건의 올바른 형식 요구사항은 표현식 안의 모든 변수가 해 매핑에 나타나도록 보장합니다. 

define evalFunction(F, μ):
    ## F is an expression: an RDF term, a variable, or op(expr1, ..., exprN)
    ## where op is a function or a functional form.
    if F is an RDF term:
        return F
    if F is a variable:
        ## By well-formedness, F ∈ dom(μ).
        return μ(F)
    ## F is of the form F= op(expr1, ..., exprN)
    if op is a functional form (e.g. IF, logical-or):
        ## Evaluated specifically for op; op may evaluate only some arguments.
        ## For example, IF(c, t, f) evaluates c, then exactly one of t or f.
        return the value defined for op over expr1, ..., exprN under μ
    ## op is an ordinary function: evaluate all arguments first.
    return F(evalFunction(expr1, row), ..., evalFunction(exprN, row))
enddefine

6.4 규칙의 평가

규칙은 규칙 본문에서 해답 시퀀스를 계산한 다음, 해답 시퀀스의 각 해답 매핑을 사용하여 규칙 헤드를 통해 트리플을 생성하는 방식으로 평가된다.

트리플 패턴 내의 빈 노드는 변수처럼 동작한다. 이는 SPARQL 그래프 패턴 매칭과 호환된다. 

# Evaluate rule body
# This function returns a sequence of solutions

define evalRuleElements(B, SEQ, G, GD):
    where 
        B is a sequence of rule elements
        SEQ is a solution sequence 
        G and GD are RDF graphs

    for each rule element rElt in B:

        if rElt is a triple pattern TP:
            X = graphMatch(G, TP)
            SEQ1 = {}
            for each μ1 in X:
                for each μ2 in SEQ:
                    if compatible(μ1, μ2)
                      μ3 = merge(μ1, μ2)
                      add μ3 to SEQ1
                    endif
                endfor
            endfor
        endif

        if rElt is a condition element F:
            SEQ1 = {}
            for each solution μ in SEQ:
                let x = evalFunction(F.expr, μ)
                if EBV(x) is true:
                    add μ to SEQ1
                endif
            endfor
        endif

        if rElt is a negation expression N:
            SEQ1 = {}
            for each solution μ in SEQ:
                S = sequence{ μ }
                if rElt with DATA:
                    NEG = evalRuleElements(N.inner, S, GD, GD)
                else:
                    NEG = evalRuleElements(N.inner, S, G, GD)
                if NEG is empty
                    add μ to SEQ1
                endif
            endfor
        endif

        if rElt is an assignment A:
            SEQ1 = {}
            for each solution μ in SEQ:
                let x = evalFunction(A.expr, μ)
                if x is not an error:
                    ## Add mapping V -> x to solution μ
                    let μ2 be a solution mapping μ ∪︀ { (A.var, x) }
                    add μ2 to SEQ1
                else
                    # Error: drop solution μ
                endif
            endfor
        endif

        SEQ = SEQ1
    endfor

    return SEQ
enddefine

define evalRule(R, G, GD):
    where 
        R is a well-formed rule
        G and GD are RDF graphs
    let B be R.body 
        where each blank node in a triple pattern in R.body
        is replaced by a variable which is not used in the rule. 
        The same variable is used for each occurrence of the
        same blank node, and a different variable is used for 
       each different blank node.

    # Solution sequence of one solution that does not map any variables.
    let SEQ0: Solution sequence = { μ0 }

    if R.data:
        let SEQ = evalRuleElements(B, SEQ0, GD, GD)
    else
        let SEQ = evalRuleElements(B, SEQ0, G, GD)
    
    # Evaluate rule head
    let OUT = empty set
    for each μ in SEQ:
        let S = {}
        for each triple template TT in R.head:
            let triple = subst(μ, TT)
            Add triple to S
        endfor
        OUT = OUT union S
    endfor
    return OUT
enddefine
참고

OUT에는 데이터 그래프에도 있는 트리플이 포함될 수 있다.

6.5 규칙 집합의 평가

규칙 집합의 평가는 해당 규칙 집합의 계층화에 있는 각 계층을 실행하는 것으로 정의되며, 각 계층은 다음 계층으로 이동하기 전에 순서대로 완전히 실행된다. 계층은 먼저 해당 계층의 각 일회 실행 규칙을 평가한 다음, 새 트리플이 더 이상 생성되지 않을 때까지 해당 계층의 일반 규칙을 반복해서 평가하는 방식으로 평가된다. 

let G0 be the input base graph
let RS be the rule set
let D be the graph of all DATA triples in RS

Apply stratification to RS

let LS be the sequence of layers after stratification

# Inference graph
let GI = { t ∈ D | t ∉ G0 }

let GD = G0 ∪︀ D

# Evaluation graph.
let GE = GD

for each stratum ST in LS:
    for each rule R in ST.once:
        let X = evalRule(R, GE, G0)
        let Y = { t ∈ X | t ∉ GE }
        GI = GI ∪︀ Y
        GE = GE ∪︀ Y
    endfor

    let finished = false
    while !finished:
        finished = true
        for each rule R in ST.general:
            let X = evalRule(R, GE, G0)
            let Y = { t ∈ X | t ∉ GE }
            if Y is not empty:
                finished = false
                GI = GI ∪︀ Y
                GE = GE ∪︀ Y
            endif
        endfor
    endwhile
endfor
the result is GI

6.6 실제 예제

이 절은 비규범적이다.

이 절에서는 완전한 규칙 집합의 평가를 단계별로 설명한다. 즉, 규칙 의존성을 결정하고 (4.3 규칙 의존성), 계층화를 계산한 다음 (4.4 계층화), 각 계층을 차례로 평가하여 추론 그래프를 생성한다 (6.5 규칙 집합 평가).

이 예제는 소프트웨어 구성 요소와 그 의존성을 설명한다. 프런트엔드는 애플리케이션 서버에 의존하고, 애플리케이션 서버는 데이터베이스와 로깅 라이브러리에 의존한다. 데이터베이스에는 알려진 취약점이 있다. 규칙은 의존성 체인을 따라 취약점에 대한 노출을 전파하고, 심각한 취약점에 노출된 구성 요소에는 :criticallyExposed 상태를 부여하며, 심각하지 않은 구성 요소에는 :safeToDeploy 상태를 부여하고, 심각하게 노출된 각 구성 요소에 대한 알림을 생성한다. (실제로 취약점이 구성 요소에 영향을 미치는지는 배포된 버전에 따라 달라진다. 이 예제에서는 버전을 생략하고 취약점을 직접 명시한다.) 간결성을 위해 기본 그래프는 3.1 기본 패턴에서처럼 더 구체적인 관계로부터 도출하는 대신 :dependsOn 트리플을 직접 명시한다.

예제 13: 상세 예제: 데이터와 규칙 
:frontend rdf:type :Component ;
          :dependsOn :app .
:app      rdf:type :Component ;
          :dependsOn :db ;
          :dependsOn :logger .
:db       rdf:type :Component ;
          :hasVulnerability :vuln1 .
:logger   rdf:type :Component .
:vuln1    :severity 9.1 .
# R1
RULE { ?x :exposedTo ?v } WHERE { ?x :hasVulnerability ?v }

# R2
RULE { ?x :exposedTo ?v } WHERE { ?x :dependsOn ?y . ?y :exposedTo ?v }

# R3
RULE { ?x :status :criticallyExposed }
WHERE { ?x :exposedTo ?v . ?v :severity ?s . FILTER(?s >= 9.0) }

# R4
RULE { ?x :status :safeToDeploy }
WHERE { ?x rdf:type :Component . NOT { ?x :status :criticallyExposed } }

# R5
RULE { [] rdf:type :Notification ; :concerns ?x }
WHERE { ?x :status :criticallyExposed }

규칙은 주석에서 R1부터 R5까지의 레이블로 표시되며, 이 절의 나머지 부분에서는 이러한 레이블로 참조된다. 이는 3.2 재귀부터 3.5 할당 및 RDF 항 생성까지에서 소개된 규칙이다. 규칙 집합에는 IMPORTS가 없으므로 가져오기 처리를 거쳐도 변경되지 않으며, DATA 블록도 없으므로 평가는 기본 그래프만으로 시작된다.

6.6.1 종속성 결정

어떤 규칙이 어떤 규칙에 종속되는지 결정하기 위해 각 규칙 본문의 각 트리플 패턴을 모든 규칙 머리부의 트리플 템플릿과 비교한다 (4.3 규칙 종속성).

  • R1의 본문은 단일 트리플 패턴 ?x :hasVulnerability ?v이다. 어떤 규칙 머리부에도 술어가 :hasVulnerability인 트리플을 생성할 수 있는 트리플 템플릿이 없으므로 이 패턴은 데이터와만 일치할 수 있다. R1에는 종속성이 없다.
  • R2의 본문에는 두 개의 트리플 패턴이 있다. ?x :dependsOn ?y는 어떤 규칙 머리부와도 일치할 수 없으므로 데이터와만 일치한다. ?y :exposedTo ?v는 R1의 머리부 템플릿 ?x :exposedTo ?v과 일치하고, R2 자체의 머리부와도 일치한다. 두 항목 모두 트리플 패턴 요소이다 (부정 요소 내부에 나타나지 않으며, R2에는 할당 요소도 없고 머리부에 빈 노드도 없다). 따라서 R2는 R1에 대한 개방 종속성과 자기 자신에 대한 개방 종속성을 가진다. R2의 자기 자신에 대한 종속성으로 인해 R2는 재귀 규칙이 된다.
  • R3의 본문에서 패턴 ?x :exposedTo ?v는 R1과 R2의 머리부와 일치하므로 R3는 각각에 대해 개방 종속성을 가진다. 패턴 ?v :severity ?s는 어떤 규칙 머리부와도 일치하지 않는다.
  • R4의 본문에서 패턴 ?x rdf:type :Component는 어떤 규칙 머리부와도 일치하지 않는다. 술어가 rdf:type인 유일한 머리부 템플릿은 R5에 있으며, 그 목적어 :Notification은 :Component와 다른 RDF 용어이므로 생성된 어떤 트리플도 일치할 수 없다. 패턴 ?x :status :criticallyExposed는 부정 요소 NOT { ?x :status :criticallyExposed } 내부에 나타나며 R3의 머리부 템플릿과 일치한다. 패턴이 부정 요소에 나타나므로 R4는 R3에 대한 폐쇄 종속성을 가진다.
  • R5의 본문에서 패턴 ?x :status :criticallyExposed는 R3의 머리부와 일치한다. R5의 머리부에는 빈 노드가 포함되므로, 해당 패턴이 일반 트리플 패턴 요소임에도 R3에 대한 종속성은 폐쇄 종속성이다. 어떤 규칙 본문의 패턴도 R5의 머리부 템플릿과 일치하지 않으므로 어떤 규칙도 R5에 종속되지 않는다.

따라서 종속성 그래프에는 정점 5개와 간선 6개가 있다.

  • R2 → R1 (개방)
  • R2 → R2 (개방)
  • R3 → R1 (개방)
  • R3 → R2 (개방)
  • R4 → R3 (폐쇄)
  • R5 → R3 (폐쇄)

R4와 R5는 R1 또는 R2에 직접 종속되지 않지만, 각각 R3을 통해 양쪽 모두에 전이적 종속성을 가진다.

그래프의 유일한 순환은 자기 간선 R2 → R2이며, 이는 개방 종속성이다. 폐쇄 종속성이 포함된 순환은 없으므로 계층화 조건이 충족되며 규칙 집합은 명확하게 정의된 결과를 가진다.

6.6.2 계층화 계산

계층화 알고리즘에 따라 모든 규칙은 계층 0에서 시작한다. 그런 다음 아무것도 변경되지 않을 때까지 간선을 반복해서 검사한다.

  • 개방 간선에서는 출발 규칙이 대상 규칙과 동일하거나 더 높은 계층에 있어야 한다. 모든 규칙이 계층 0에 있을 때 네 개의 개방 간선이 이미 이 조건을 충족하므로 변경이 발생하지 않는다.
  • 폐쇄 간선에서는 대상 규칙이 먼저 완료되어야 하므로 출발 규칙이 대상 규칙보다 엄격히 더 높은 계층에 있어야 한다. 간선 R4 → R3 (폐쇄)을 검사하면 R4와 R3이 모두 계층 0에 있으므로 R4를 계층 1로 이동한다. 마찬가지로 간선 R5 → R3 (폐쇄)은 R5를 계층 1로 이동한다.

간선을 한 번 더 순회해도 변경이 발생하지 않으므로 계층은 확정된다. 그런 다음 각 계층을 일회 실행 규칙과 일반 규칙으로 나눈다. R5의 머리부에는 빈 노드가 있으므로 일회 실행 규칙이다. 다른 규칙에는 할당 요소나 머리부의 빈 노드가 없다. 계층화 결과는 다음과 같다.

  • 계층 0: 일반 규칙 R1, R2, R3; 일회 실행 규칙 없음
  • 계층 1: 일회 실행 규칙 R5; 일반 규칙 R4

이 순서는 더 높은 계층에 있는 규칙의 의도를 반영한다. 구성 요소를 안전하게 배포할 수 있는지와 어떤 구성 요소에 알림이 필요한지는 모든 :status :criticallyExposed 트리플이 도출된 후에만 결정할 수 있다. 그리고 이를 도출하는 규칙 R3은 데이터를 제공하는 규칙 R1 및 R2와 함께 아래 계층에서 완료된다.

6.6.3 계층 평가

평가는 6.5 규칙 집합 평가 알고리즘을 따른다. 평가 그래프 GE는 기본 그래프로 시작하고 추론 그래프 GI는 빈 상태로 시작한다. 각 계층은 순서대로 완료될 때까지 평가한다. 계층의 규칙을 여러 차례 순회하여 평가하며, 한 번의 순회에서 새 트리플이 생성되지 않을 때까지 순회를 반복한다. 알고리즘은 한 번의 순회 중에 계층의 규칙을 평가하는 순서를 정하지 않는다. 이 추적에서는 R1, R2, R3 순서를 사용한다. 다른 순서는 동일한 추론을 서로 다른 횟수의 순회에 분산시킬 수 있지만, 계층 0을 완료될 때까지 실행하므로 동일한 최종 그래프를 생성한다.

이 규칙 집합에는 DATA 블록이 없으므로 평가의 모든 시점에서 GE는 G0와 GI를 합친 것이다. 따라서 이 추적에서는 GI만 추적하고, 평가가 진행됨에 따라 그 상태를 표시하며 각 새 트리플에 이를 생성한 규칙을 표시한다.

계층 0, 첫 번째 순회.

  • R1: 본문이 :db :hasVulnerability :vuln1과 일치하여 ?x = :db와 ?v = :vuln1을 바인딩한다. 머리부는 :db :exposedTo :vuln1을 생성한다. 이 트리플은 GE에 없으므로 GE와 GI에 추가한다.
  • R2: 본문은 ?x :dependsOn ?y와 ?y :exposedTo ?v를 조인한다. 이제 GE에는 :db :exposedTo :vuln1이 포함되어 있으므로 조인 결과로 하나의 해가 나온다. ?x = :app, ?y = :db, ?v = :vuln1이다 (:app :dependsOn :db에서 유래). 머리부는 새로운 :app :exposedTo :vuln1을 생성하여 추가한다. 아직 :frontend에 대한 해는 없다. 이 R2 평가가 시작될 때 :app :exposedTo :vuln1이 GE에 없었기 때문이다.
  • R3: 이제 ?x :exposedTo ?v는 :db와 :app에 대해 일치한다. :vuln1 :severity 9.1과 조인하고 FILTER(?s >= 9.0)을 적용하면 두 해가 모두 유지된다. 머리부는 새로운 :db :status :criticallyExposed와 :app :status :criticallyExposed를 생성한다. 
# 계층 0의 첫 번째 순회 후 GI
:db  :exposedTo :vuln1 .                    # 신규 (R1)
:app :exposedTo :vuln1 .                    # 신규 (R2)
:db  :status :criticallyExposed .           # 신규 (R3)
:app :status :criticallyExposed .           # 신규 (R3)

새 트리플이 생성되었으므로 계층 0의 평가는 다음 순회로 계속된다.

계층 0, 두 번째 순회.

  • R1: 이전과 같이 일치한다. :db :exposedTo :vuln1은 이미 GE에 있으므로 새로운 것은 생성되지 않는다.
  • R2: 이제 조인 결과에 ?x = :frontend, ?y = :app, ?v = :vuln1도 포함되어 새로운 트리플 :frontend :exposedTo :vuln1을 생성한다. 노출이 종속성 체인의 두 단계를 이동하는 데 두 번의 순회가 걸렸다.
  • R3: 새로운 트리플 :frontend :status :criticallyExposed을 생성한다. 
# 계층 0의 두 번째 순회 후 GI
:db       :exposedTo :vuln1 .
:app      :exposedTo :vuln1 .
:frontend :exposedTo :vuln1 .               # 신규 (R2)
:db       :status :criticallyExposed .
:app      :status :criticallyExposed .
:frontend :status :criticallyExposed .      # 신규 (R3)

계층 0, 세 번째 순회. 이제 모든 규칙의 모든 해는 이미 GE에 있는 트리플만 생성한다. GI는 변경되지 않는다. 새 트리플이 없으므로 계층 0이 완료된다. 도출될 수 있는 모든 :exposedTo 트리플과 모든 :status :criticallyExposed 트리플이 도출되었다.

계층 1, 일회 실행 규칙. 계층의 일회 실행 규칙을 먼저 각각 정확히 한 번씩 평가한다.

  • R5: 본문은 세 개의 :status :criticallyExposed 트리플과 일치하여 ?x = :db, ?x = :app, ?x = :frontend인 해를 얻는다. 각 해에서 머리부를 인스턴스화하면 새로운 빈 노드가 생성되어 해마다 두 개의 트리플, 즉 심각한 각 구성 요소에 대한 알림을 생성한다. 이제 계층의 일반 규칙을 반복적으로 평가하더라도 R5는 다시 평가하지 않는다.

계층 1, 일반 규칙의 첫 번째 순회.

  • R4: 패턴 ?x rdf:type :Component는 :frontend, :app, :db, :logger와 일치한다. (R5가 방금 생성한 rdf:type :Notification 트리플과는 일치하지 않는다.) 부정 요소 NOT { ?x :status :criticallyExposed }는 :frontend, :app, :db에 대한 해를 거부한다. GE에 각각에 대한 :status :criticallyExposed 트리플이 포함되어 있기 때문이다. ?x = :logger인 해만 남아 새로운 트리플 :logger :status :safeToDeploy을 생성한다. 
# 계층 1 이후의 GI
:db       :exposedTo :vuln1 .
:app      :exposedTo :vuln1 .
:frontend :exposedTo :vuln1 .
:db       :status :criticallyExposed .
:app      :status :criticallyExposed .
:frontend :status :criticallyExposed .
_:n1      rdf:type :Notification .          # 신규 (R5)
_:n1      :concerns :db .                   # 신규 (R5)
_:n2      rdf:type :Notification .          # 신규 (R5)
_:n2      :concerns :app .                  # 신규 (R5)
_:n3      rdf:type :Notification .          # 신규 (R5)
_:n3      :concerns :frontend .             # 신규 (R5)
:logger   :status :safeToDeploy .           # 신규 (R4)

계층 1, 일반 규칙의 두 번째 순회. 새 트리플은 없다. 평가가 완료되었으며, 위에 표시된 GI가 결과 추론 그래프이다.

계층화는 이 결과를 신뢰할 수 있도록 한다. :frontend :status :criticallyExposed이 도출되기 전인 계층 0의 첫 번째 순회 중에 평가했다면, R4는 :frontend :status :safeToDeploy이라고 잘못 결론 내렸을 것이며, R5는 :db와 :app에 대한 알림은 생성했지만 :frontend에 대한 알림은 생성하지 않았을 것이다. 두 규칙을 계층 1까지 지연하면 완전한 :status :criticallyExposed 트리플 집합을 확인하게 되므로 각 계층 내에서 규칙을 평가하는 순서가 최종 결과에 영향을 주지 않는다.

7. Shape Rules Language 문법

SPARQL-RL 문서는 UTF-8 [RFC3629]로 인코딩된 RDF 문자열이며, RuleSet 생성 규칙으로 시작하고 7.6 문법에 정의된 추가 제약 조건을 준수한다. U+0000에서 U+D7FF까지와 U+E000에서 U+10FFFF까지의 범위에 있는 유니코드 스칼라 값만 허용된다. 여기에는 U+D800에서 U+DFFF까지의 범위인 서로게이트 코드 포인트가 제외된다.

하나의 SPARQL-RL 문서에 여러 VERSION 지시문이 나타날 수 있습니다. 각 지시문은 해당 지시문 다음에 오는 문서 부분에 적용되며, 다른 지시문을 만나거나 문서의 끝에 도달할 때까지 적용됩니다.

버전 레이블은 미디어 유형의 version 매개변수로도 지정할 수 있습니다. 현재 적용되는 VERSION 지시문이 없는 경우 미디어 유형의 일부로 지정된 버전을 고려합니다.

7.2 공백

공백 (생성 규칙 WS)은 그렇지 않으면 하나의 터미널로 (잘못) 인식될 두 터미널을 구분하는 데 사용됩니다. 아래의 대문자로 된 규칙 이름은 공백이 중요한 위치를 나타냅니다. 이들은 Shape Rules Language 파서를 구성할 때 사용할 수 있는 터미널 선택지 중 하나를 이룹니다.

생성 규칙 String에서는 공백이 중요합니다.

7.3 주석

주석은 IRIREF, STRING_LITERAL1, STRING_LITERAL2, STRING_LITERAL_LONG1 또는 STRING_LITERAL_LONG2 외부의 #로 시작하며, 줄 끝( LF 또는 CR로 표시됨)까지 계속됩니다. 주석 표식 뒤에 줄 끝이 없으면 파일의 끝까지 계속됩니다. 주석은 공백으로 취급됩니다.

7.4 IRI 참조

상대 IRI 참조는 URI(Uniform Resource Identifier): 일반 구문 [RFC3986]에 따라 기본 IRI를 사용하여 해석되며, 섹션 5.2의 기본 알고리즘만 사용합니다. 구문 기반 정규화와 스킴 기반 정규화 (RFC3986의 섹션 6.2.2 및 6.2.3에 설명됨)는 수행되지 않습니다. IRI 참조에서 추가로 허용되는 문자는 국제화된 리소스 식별자 (IRI) [RFC3987]의 섹션 6.5에 따라 URI 참조의 비예약 문자가 처리되는 것과 동일한 방식으로 처리됩니다.

BASE 지시문은 [RFC3986]에 따라 상대 IRI 참조를 해석하는 데 사용되는 기본 IRI를 정의합니다. 섹션 5.1.1, "콘텐츠에 포함된 기본 URI". 섹션 5.1.2, "캡슐화 엔터티의 기본 URI"는 범위 내 기본 IRI가 캡슐화 문서에서 올 수 있는 방식을 정의합니다. 예를 들어 xml:base 지시문이 있는 SOAP 봉투나 Content-Location 헤더가 있는 MIME 멀티파트 문서가 이에 해당합니다. 5.1.3, "검색 URI의 기본 URI"에서 식별된 "검색 URI"는 특정 SPARQL-RL 문서가 검색된 URL입니다. 위의 어느 것도 기본 URI를 지정하지 않는 경우 기본 기본 URI(섹션 5.1.4, "기본 기본 URI")가 사용됩니다. 각 BASE 지시문은 이전 URI를 기준으로 새로운 범위 내 기본 URI를 설정합니다.

7.5 이스케이프 시퀀스

SRL 문서에는 세 가지 형태의 이스케이프가 사용됩니다.

  • 숫자 이스케이프 시퀀스는 유니코드 코드 포인트의 값을 나타냅니다.

    숫자 이스케이프 시퀀스는 유니코드 서로게이트 범위인 U+D800에서 U+DFFF 사이의 코드 포인트 값을 생성해서는 안 됩니다.

    이스케이프 시퀀스 유니코드 코드 포인트
    \u hex hex hex hex 유니코드 코드 포인트로, U+0000에서 U+D7FF까지의 범위와 U+E000에서 U+FFFF까지의 범위에 있으며, 최상위 자릿수부터 최하위 자릿수까지 해석한 네 개의 16진수 숫자로 인코딩된 값에 대응합니다.
    \U hex hex hex hex hex hex hex hex 유니코드 코드 포인트로, U+0000에서 U+D7FF까지의 범위와 U+E000에서 U+10FFFF까지의 범위에 있으며, 최상위 자릿수부터 최하위 자릿수까지 해석한 여덟 개의 16진수 숫자로 인코딩된 값에 대응합니다.

    여기서 hex는 16진수 문자입니다

    HEX ::= [0-9] | [A-F] | [a-f]

  • 문자열 이스케이프 시퀀스는 문자열 리터럴에서 전통적으로 이스케이프되는 문자를 나타냅니다.

    이스케이프 시퀀스 유니코드 코드 포인트
    \t U+0009
    \b U+0008
    \n U+000A
    \r U+000D
    \f U+000C
    \" U+0022
    \' U+0027
    \\ U+005C

A. 예제 가져오기 알고리즘

다음 알고리즘은 참조된 모든 문서를 재귀적으로 방문하여 가져오기 문을 해석하는 한 가지 방법을 보여준다.

두 규칙 집합 RS1과 RS2의 규칙 집합 병합은 다음과 같이 정의되는 규칙 집합 MR이다: 

define ruleSetMerge(rule set R1,rule Set RS2):
    MR.rules = RS1.rules ∪︀ RS2.rules
    MR.data = rdf_merge(RS1.data, RS2.data)
    MR.imports = {}
    the result is MR
enddefine

define imports(rule set RS, set of URLs V), returning rule set
    let I = the set of import URLs declared for the rule set RS
    let RS2 be a rule set formed from RS.rules and RS.data
    foreach URL x in I:
        if x ∉ V:
            V = V ∪︀ { x }
            read rule set RS3 from URL x
            RS2 = rulesetMerge(RS2, imports(RS3, V))
        endif
    endfor
    the result is RS2
enddefine

let RS be a rule set
let V = {}
if RS has a location, V = { location of RS }
result is imports(RS, V)

여기서 rdf_merge는 RDF 병합 연산이다.
