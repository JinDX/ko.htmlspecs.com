초록

주석은 일반적으로 리소스 또는 리소스 간의 연관성에 대한 정보를 전달하는 데 사용됩니다. 간단한 예로는 한 웹페이지나 이미지에 대한 댓글 또는 태그, 뉴스 기사에 대한 블로그 게시글 등이 있습니다.

Web Annotation Data Model 명세는 주석이 서로 다른 하드웨어와 소프트웨어 플랫폼 간에 공유되고 재사용될 수 있도록 구조화된 모델과 포맷을 설명합니다. 일반적인 사용 사례는 간단하고 편리한 방식으로 모델링할 수 있으며, 동시에 임의의 콘텐츠를 특정 데이터 포인트나 시간 멀티미디어 리소스의 일부 구간에 연결하는 등 더 복잡한 요구사항도 지원할 수 있습니다.

이 명세는 이러한 사용 사례를 수용하는 개념 모델을 기반으로, 주석의 생성과 소비를 쉽게 할 수 있도록 특정 JSON 포맷과 이를 표현하는 용어 집합을 제공합니다.

1. 소개

이 절은 비규범적입니다.

주석은 서로 다른 정보 단위 사이에 연관 관계를 만드는 행위로, 온라인에서 다양한 형태로 널리 이루어지고 있습니다. 웹 사용자들은 호스팅 웹사이트에 내장된 도구, 외부 웹 서비스 또는 주석 클라이언트의 기능을 사용하여 온라인 리소스에 대해 댓글을 남깁니다. 공유 사진이나 동영상에 대한 댓글, 제품 리뷰, 웹 리소스에 대한 소셜 네트워크 언급 등도 모두 주석으로 볼 수 있습니다. 또한 "스티커 노트" 시스템, 독립형 멀티미디어 주석 시스템 등이 매우 다양합니다. 본 명세서는 이러한 주석을 공통적으로 표현하는 방법 등을 설명합니다.

Web Annotation Data Model은 다양한 플랫폼 사이에서 주석을 쉽게 공유할 수 있도록 확장 가능하고 상호운용성 있는 프레임워크를 제공합니다. 복잡한 요구사항을 충족시킬 만큼 표현이 풍부하면서도, 텍스트를 단일 웹 리소스에 연결하는 등 가장 일반적인 사용 사례를 단순하게 처리할 수 있도록 설계되었습니다.

주석은 보통 본문과 대상 등 서로 연결된 리소스 집합으로 간주되며, 본문이 대상과 관련이 있음을 전달합니다. 이러한 관계의 정확한 의미는 주석의 의도에 따라 달라지지만, 본문은 대개 대상에 대해 "관련" 내용입니다. 이러한 관점에서 아래와 같이 세 부분으로 구성된 기본 모델을 갖게 됩니다. 전체 모델은 추가 기능을 지원하여, 콘텐츠를 주석 내에 내장하거나 임의의 리소스 세그먼트를 선택하고, 리소스의 적절한 표현을 선택하며, 클라이언트가 적절히 주석을 렌더링하도록 스타일링 힌트를 제공할 수 있습니다. 기계에 의해 생성되거나 기계를 위한 주석도 가능하므로, 데이터 웹 역시 인간 중심의 문서 웹과 마찬가지로 고려됩니다.

Web Annotation Data Model은 주석의 생성, 관리 및 조회를 위한 전송 프로토콜을 규정하지 않습니다. 대신, 다양한 프로토콜 위에서 사용할 수 있는 리소스 지향 구조와 그 직렬화 방법을 설명합니다. 관련 [annotation-protocol] 명세에서는 권장되는 전송 계층을 안내하며, 별도로 적용될 수 있습니다.

1.1 모델의 목표

Web Annotation Data Model의 주요 목표는 표준화된 기술 모델과 포맷을 제공하여 주석이 시스템 간에 공유될 수 있도록 하는 것입니다. 이러한 상호운용성은 타인과의 공유뿐 아니라, 디바이스나 플랫폼 간에 개인 주석을 이동시키는 경우에도 필요합니다. 공유된 주석은 기존 컬렉션에 통합되어도 주요 정보의 손실 없이 재사용 가능해야 합니다. 본 모델은 가능한 많은 주석 사용 사례를 다루면서도, 단순한 주석 작업은 쉽게 처리하고, 그 기반 위에서 복잡한 사용까지 확장 가능하도록 설계되어야 합니다.

Web Annotation Data Model은 모든 참여자들이 사용할 수 있는 하나의 일관된 모델입니다. 생산자와 소비자 모두를 위해 구현 비용을 최소화하도록 모든 노력이 기울여졌습니다. 하나의 사용 사례에 대해 여러 방법보다는 하나의 방식으로 충족시키는 것이 원칙이지만, 기존 표준과의 호환 등이 필요한 경우에는 예외가 있을 수 있습니다. Data Model은 Linked Data의 기반 위에 구축되었지만, 풍부하고 효율적인 비-그래프 기반 구현도 가능하도록 설계되어 있습니다. 따라서 인퍼런싱 및 기타 그래프 기반 질의는 본 모델 설계에 있어 최적화의 우선순위가 아닙니다.

1.2 모델의 직렬화

본 명세서의 예시들은 [JSON-LD]로 직렬화되며, Annotation Vocabulary [annotation-vocab] 부록 A의 Context를 사용합니다. 이는 우선 권장되는 직렬화 포맷입니다. 이 포맷의 미디어 타입은 Annotation Protocol [annotation-protocol] 3장에 application/ld+json;profile="http://www.w3.org/ns/anno.jsonld"로 정의되어 있습니다.

주석에서 기록된 유일한 정보가 리소스의 IRI일 경우, 해당 IRI 자체가 관계의 값으로 사용됩니다(예제 1). 리소스에 대한 추가 정보가 있다면, IRI는 관계의 값이 되는 객체의 id 속성의 값이 됩니다(예제 2).

1.3 적합성

비규범적이라고 표시된 절뿐 아니라, 본 명세서의 모든 저작 지침, 도표, 예제, 주석은 비규범적입니다. 그 외의 모든 내용은 규범적입니다.

본 명세에서 MAY, MUST, MUST NOT, NOT RECOMMENDED, RECOMMENDED, SHOULD, SHOULD NOT 등의 용어는 [RFC2119]에서 설명된 의미로 해석되어야 합니다.

1.3.1 셀렉터 관련 적합성 요구 사항

모든 셀렉터가 모든 미디어 타입에 의미있는 것은 아니며, 일부 조합은 무의미하거나 공식적으로 정의되지 않았을 수 있습니다. 따라서 구현체는 해당 미디어 타입을 지원하지 않는 경우에는 특정 종류의 셀렉터를 무시할 수 있습니다.

A. 미디어 타입과 셀렉터의 대응에 있는 표는 본 명세에서 다루는 주요 미디어 타입과 셀렉터의 대응 관계를 보여줍니다. 각 표 항목의 의미와, 구현 적합성에 미치는 영향은 다음과 같습니다.

  • 표에 “✔︎”가 있으면, 해당 셀렉터 유형이 그 미디어 타입에 대해 관련이 있음을 의미합니다. 이를 지원하는 구현체는 그 조합을 반드시 구현해야 합니다 해당 미디어 타입을 지원한다면.
  • 표에 “✘”가 있으면, 셀렉터 유형이 해당 미디어 타입에 무관함을 의미합니다. 이에 대해 무시해야 합니다.
  • 표에 “?”가 있으면 일반적으로 그 조합의 의미 여부를 지정할 수 없음을 의미합니다(예: fragment 식별자는 특정 미디어 타입에 정의되어 있으며, 일반 텍스트가 아닌 특정 텍스트 미디어 타입에 대해 정의될 수 있으나 표에는 나열되지 않을 수 있음). 어떤 경우에는 그 조합의 유용성이 분명하지 않을 수도 있습니다(예: 바이너리 이미지의 Data Position 셀렉터 등). 구현체는 해당 조합을 구현할 수도 있습니다.

1.4 용어

IRI
IRI는 Internationalized Resource Identifier(국제화 리소스 식별자)로, URI 스펙을 확장하여 Unicode 문자를 허용합니다(URI는 ASCII의 하위 집합만 허용). IRI와 인코딩된 URI 간의 변환 알고리즘이 정의되어 있으며, IRI는 [rfc3987]에 정의되어 있습니다.
Resource
IRI로 식별될 수 있는 항목.
Web Resource
Resource 중 IRI로 반드시 식별되어야 하는 것(Web Architecture [webarch] 참조). Web Resource는 dereferencable할 수 있음.
External Web Resource
Web Resource 중 주석의 표현에 포함되지 않은 것(예: 웹페이지, 이미지, 동영상). 이러한 External Web Resource는 IRI로 dereferencable합니다.
Property
Resource의 속성으로, 일반적으로 특정 데이터 타입을 가짐. 본 모델에서는 "Property"라는 용어를 관계가 아니고 문자열, 정수, 날짜 등 리터럴 값인 특징에 한정해서 사용합니다. Property 값은 객체를 제외한 데이터 타입(또는 허용될 경우 데이터 타입 멤버의 배열)입니다.
Relationship
본 모델에서는 "Relationship"을 Resource에 관한 기능(IRI 참조 또는 객체 내 상세 설명 등)으로 구분합니다. Relationship 값은 인용부호로 감싼 IRI, id 프로퍼티를 가진 객체, 혹은 이러한 것의 배열입니다.
Class
Resource는 "클래스"라 불리는 그룹으로 개념적으로 나눌 수 있으며, 클래스의 각 멤버는 인스턴스입니다. 리소스는 타입을 통해 특정 클래스와 연관될 수 있습니다. 클래스는 IRI로 식별됩니다. 즉, 클래스 역시 Web Resource입니다.
Type
인스턴스를 해당 클래스와 연관시키는 특수한 관계.
Instance
특정 클래스가 표현하는 Resource 그룹의 구성원.

2. 웹 주석 원칙

Web Annotation Data Model은 아래 기본 원칙에 따라 정의됩니다:

  • 주석은 리소스 간의 관계를 표현하는 루트가 있는 유향 그래프입니다.
  • 이 관계에 참여하는 리소스는 본문(Body)과 대상(Target)으로 두 가지 주요 유형이 있습니다.
  • 주석은 본문(Body)을 0개 이상 가질 수 있습니다.
  • 주석은 대상(Target)을 1개 이상 가질 수 있습니다.
  • 본문 리소스의 내용은 대상 리소스의 내용과 연관되어 있으며, 일반적으로 대상에 "관한" 내용입니다.
  • 주석, 본문, 대상은 생성 및 설명 정보를 포함하여 자체 속성 및 관계를 가질 수 있습니다.
  • 주석 생성 또는 특정 본문/대상 포함의 의도는 중요한 속성으로, Motivation 리소스로 표현됩니다.

다음 원칙들은 Target과 Body의 구체적 특성에 관한 추가 구분입니다:

  • 대상 또는 본문 리소스는 해당 리소스의 IRI만으로 식별한 개체보다 더 구체적일 수 있습니다.
  • 특히,
    • 대상 또는 본문 리소스가 리소스의 특정 세그먼트를 의미할 수 있습니다.
    • 대상 또는 본문 리소스가 특정한 스타일을 가질 수 있습니다.
    • 대상 또는 본문 리소스가 리소스의 특정 상태일 수 있습니다.
    • 대상 또는 본문 리소스가 특정 역할을 수행하기 위해 주석 내에 포함될 수 있습니다.
    • 위의 조건들이 조합될 수도 있습니다.
  • 이러한 제약 조건이 적용된 리소스는 Annotation, Body, Target과 별개의 리소스로서, SpecificResource라 불립니다.
  • SpecificResource는 소스 리소스와, 이를 더 구체적으로 만드는 조건을 참조합니다.
  • SpecificResource의 정체성은 제약 조건 설명과는 별개입니다.
  • 본문 리소스는 복수 리소스 중 하나를 선택하는 형태일 수도 있습니다.

Annotation 문서 내에 포함된 본문 및 대상 등 외부 리소스의 속성 정보는 클라이언트에 대한 힌트로 제공되는 것이며, 신뢰원(authoritative) 정보로 간주해서는 안 됩니다. 여기에는 생성 시간, 생성 주체, 수정 시점, 권리 주장, 포맷, 언어, 텍스트 방향 등 외부 리소스의 속성이 포함됩니다.

3. 웹 주석 프레임워크

3.1 주석

주석(Annotation)은 웹 리소스입니다. 일반적으로 주석은 코멘트 또는 기타 설명 리소스인 하나의 본문(Body)과, 본문이 "관한" 어떤 대상(Target)을 가집니다. 또한 주석에는 추가적인 설명 속성들이 있을 수 있습니다.

예시 활용 사례: Alice는 특정 웹 페이지에 대한 의견을 담은 포스트를 작성했습니다. 그녀의 클라이언트는 그 포스트를 body 리소스로, 웹 페이지를 target 리소스로 하여 주석을 생성합니다.

모델

용어 유형 설명
@context 속성 주석의 JSON 의미를 결정하는 컨텍스트.
주석은 1개 이상의 @context 값을 반드시 포함해야 하며, http://www.w3.org/ns/anno.jsonld가 그 중 하나여야 합니다. 값이 하나뿐인 경우 문자열로 제공되어야 합니다.
id 속성 주석의 식별자.
주석은 자신을 식별하는 정확히 1개의 IRI를 반드시 가져야 합니다.
type 관계 주석의 유형.
주석은 하나 이상의 type 값을 반드시 가져야 하며, Annotation 클래스가 그 중 하나여야 합니다.
Annotation 클래스 웹 주석을 위한 클래스.
Annotation 클래스는 type을 통해 주석과 반드시 연관되어야 합니다.
body 관계 주석과 본문(Body) 간의 관계.
주석에는 1개 이상의 body 관계가 권장되지만 0개일 수도 있습니다 허용.
target 관계 주석과 대상(Target) 간의 관계.
주석에는 1개 이상의 target 관계가 반드시 있어야 합니다.

예시

예시 1: 기본 주석 모델 
{
  "@context": "http://www.w3.org/ns/anno.jsonld",
  "id": "http://example.org/anno1",
  "type": "Annotation",
  "body": "http://example.org/post1",
  "target": "http://example.com/page1"
}

3.2 본문과 대상

웹은 분산되어 있으며, 서로 다른 시스템들이 함께 작동하여 콘텐츠 접근을 제공합니다. 주석은 이러한 리소스들을 본문과 대상으로 연결하는 데 사용할 수 있습니다. 대상 리소스는 항상 외부 웹 리소스이지만, 본문은 주석 내에 임베디드될 수도 있습니다. 외부 웹 리소스는 별도로 dereference하여 상태 표현을 가져올 수 있지만, 임베디드된 본문은 그 표현이 주석 내에 포함되어 있으므로 dereference가 필요하지 않습니다.

3.2.1 외부 웹 리소스

웹 리소스는 IRI로 식별되며, 리소스 콘텐츠의 포맷이나 언어 등 다양한 속성을 가질 수 있습니다. 이 정보는 주석의 일부로 기록될 수 있으며, 리소스의 표현을 웹에서 따로 가져와야 하더라도 가능합니다.

예시 활용 사례: Beatrice는 한 특허에 대한 긴 분석을 녹음하여 자신의 웹사이트에 mp3로 올리고, mp3를 본문으로, 특허의 PDF를 대상으로 하는 주석을 생성합니다.

모델

용어 유형 설명
id 속성 본문 또는 대상 리소스를 식별하는 IRI.
외부 웹 리소스인 본문이나 대상은 정확히 1개의 id를 반드시 가져야 하며, 그 값은 해당 리소스의 IRI여야 합니다.
format 속성 웹 리소스 콘텐츠의 포맷.
본문 혹은 대상은 정확히 1개의 format을 가지는 것이 바람직하나, 0개 이상도 가능합니다. 값은 [rfc6838] 명세에 따른 미디어 타입이어야 합니다.
language 속성 웹 리소스 콘텐츠의 언어.
본문이나 대상은 정확히 1개의 language를 가지는 것이 바람직하지만, 식별 불가나 혼합 언어 등으로 0개 이상일 수도 있습니다. 값은 [bcp47] 명세에 따른 언어 코드여야 합니다.
processingLanguage 속성 줄 바꿈, 하이픈 처리, 폰트 선택 등 텍스트 처리 알고리즘에 사용할 언어.
각 본문 및 대상은 정확히 1개의 processingLanguage를 가질 수 있습니다. 값은 [bcp47] 명세의 언어 코드이어야 합니다. 이 속성이 없고, language만 단일 값으로 있다면, 클라이언트는 처리를 위해 그 언어를 사용해야 합니다.
textDirection 관계 리소스 내 텍스트의 전체 기본 방향성.
본문이나 대상은 정확히 1개의 textDirection을 가질 수 있습니다. 값은 아래에서 정의하는 ltr, rtl, auto 중 하나여야 합니다.
ltr 인스턴스 리소스 값이 명시적으로 왼쪽에서 오른쪽으로의 방향임을 나타냅니다.
rtl 인스턴스 리소스 값이 명시적으로 오른쪽에서 왼쪽으로의 방향임을 나타냅니다.
auto 인스턴스 리소스 값이 명시적으로 방향성이 주어지고, 그 방향은 값에 따라 프로그램적으로 결정됨을 나타냅니다.
참고
[iana-media-types] 문서는 format 속성과 함께 사용할 수 있는 공식 미디어 타입 레지스트리를 제공합니다. [w3c-language-tags] 글에서는 language 속성에 사용자가 마주칠 수 있는 값에 대한 전반적인 설명을 제공합니다. 텍스트 방향 및 auto, ltr, rtl 값의 정의는 HTML5 [html5]의 dir 속성에서 가져온 것입니다. 또한, 외부 리소스가 제공하는 정보가 이에 대한 주석이 제공하는 정보와 모순된다면, 외부 리소스가 신뢰원이며 주석의 정보는 무시되어야 함을 유의하세요.

예시

예시 2: 외부 웹 리소스
{
  "@context": "http://www.w3.org/ns/anno.jsonld",
  "id": "http://example.org/anno2",
  "type": "Annotation",
  "body": {
    "id": "http://example.org/analysis1.mp3",
    "format": "audio/mpeg",
    "language": "fr"
  },
  "target": {
    "id": "http://example.gov/patent1.pdf",
    "format": "application/pdf",
    "language": ["en", "ar"],
    "textDirection": "ltr",
    "processingLanguage": "en"
  }
}

3.2.2 클래스

클라이언트가 웹 리소스의 일반적인 타입을 미리 아는 것은 유용합니다. 클라이언트가 비디오를 렌더링할 수 없다면, 본문이 비디오임을 알면 불필요하게 큰 콘텐츠 스트림을 다운로드하지 않아도 됩니다. 많은 데이터 포맷처럼 명확한 미디어 타입이 없는 리소스의 경우에도, 포맷이 text/csv인 리소스는 미디어 타입의 앞부분과 상관없이 단순 텍스트로 렌더링하면 안 되고, application/pdf는 메인 타입이 'application'이더라도 사용자 에이전트가 렌더링할 수 있음을 클라이언트가 아는 것이 유용합니다.

예시 활용 사례: Corina는 웹사이트에 대한 자신의 의견을 동영상으로 찍어 휴대폰에 업로드합니다. 그녀는 이 동영상을 웹사이트와 Annotation을 통해 연결하고, 클라이언트는 타입 정보를 소비 시스템을 위한 힌트로 추가합니다.

모델

용어 유형 설명
type 관계 본문 또는 대상 리소스의 타입.
본문과 대상은 1개 이상의 type을 가질 수 있으며, 값은 아래 제시된 클래스 중에서 선택하는 것이 좋지만 다른 용어집에서 올 수도 있습니다.
Dataset 클래스 정의된 구조로 데이터를 인코딩하는 리소스의 클래스입니다.
Image 클래스 주로 시각적으로 보여주기 위한 이미지 리소스의 클래스입니다.
Video 클래스 오디오가 있거나 없는 비디오 리소스의 클래스입니다.
Sound 클래스 주로 청각적으로 소비하기 위한 리소스의 클래스입니다.
Text 클래스 주로 읽기 위해 제공되는 리소스의 클래스입니다.

예시

예시 3: 본문과 대상의 타입 정보
{
  "@context": "http://www.w3.org/ns/anno.jsonld",
  "id": "http://example.org/anno3",
  "type": "Annotation",
  "body": {
    "id": "http://example.org/video1",
    "type": "Video"
  },
  "target": {
    "id": "http://example.org/website1",
    "type": "Text"
  }
}

3.2.3 외부 리소스의 세그먼트

많은 주석은 외부 웹 리소스 전체가 아니라 그 일부분을 포함합니다. 웹 [webarch]에서, 리소스의 세그먼트는 fragment 컴포넌트를 가진 IRI를 사용해 식별됩니다. 이는 원하는 세그먼트 추출 방법을 명시하면서 추출된 콘텐츠도 식별합니다. 단순한 주석의 경우, fragment가 포함된 IRI를 본문 또는 대상 식별자로 사용하는 것이 가치 있습니다.

예시 활용 사례: Dawn은 이미지의 특정 영역을 설명하고 싶습니다. 그녀는 클라이언트에서 그 영역에 하이라이트를 하고 설명을 입력합니다. 클라이언트가 해당 fragment를 target으로 포함한 IRI를 만듭니다.

모델

용어 유형 설명
id 속성 본문 또는 대상 리소스를 식별하는 IRI.
외부 웹 리소스인 본문이나 대상은 해당 리소스의 IRI 값 1개의 id를 가져야 하며, 그 IRI는 fragment 컴포넌트를 포함할 수 있습니다.
참고
리소스의 type, format, language와 아래 기타 속성에서 설명된 항목 등은 전체 리소스와 마찬가지로 세그먼트에도 적용될 수 있습니다.

fragment가 포함된 IRI를 사용할 때의 부작용 및 그것이 구현체에 미치는 제약을 인지하는 것이 중요합니다.

  • fragment는 각 미디어 타입 별로 정의됩니다. 예를 들어 HTML은 fragment 부분에 대한 특정 의미론을 가집니다.
  • 모든 미디어 타입이 fragment 사양을 가지는 것은 아닙니다. 예를 들어, 오피스 문서는 미디어 타입이 있을 수 있지만, fragment 의미론이 없을 수 있습니다.
  • 미디어 타입에 fragment 정의가 있더라도, 흥미로운 세그먼트를 충분히 정확하게 표현할 수 없는 경우가 많습니다. 예를 들어 HTML fragment는 임의의 텍스트 범위를 정확하게 표현하지 못합니다.
  • 어떤 것이 식별되는지 확실히 알려면 미디어 타입을 알아야 하며, 동일한 fragment 문자열이 다른 사양에서 사용될 수 있습니다. 예컨대 동일한 fragment 문자열이 이미지에서는 사각 영역, HTML에서는 이름이 특이한 섹션일 수도 있습니다.
  • fragment를 가진 IRI는 리소스 세그먼트를 더 구체적으로 기술하는 다른 방법과 호환되지 않습니다. 올바른 표현을 가져오는 방법, 스타일 정보 추가, 리소스에 역할 연관 등은 이러한 IRI만으로는 불가능합니다. 이러한 요구를 해결하는 방법은 Fragment Selector와 Specific Resources 절에 서술되어 있습니다.
  • IRI는 불투명한 문자열로 간주되므로, fragment가 없는 IRI로 검색하면 fragment가 포함된 주석을 찾을 수 없습니다. 예를 들어, http://example.com/image.jpg#xywh=1,1,1,1를 Target으로 가진 주석은 http://example.com/image.jpg 검색에서는 발견되지 않습니다.
fragment가 포함된 IRI 사용에 관한 추가 정보는 Best Practices for Fragment Identifiers and Media Type Definitions [fragid-best-practices]를 참고하세요.

예시

예시 4: fragment를 포함한 IRI
{
  "@context": "http://www.w3.org/ns/anno.jsonld",
  "id": "http://example.org/anno4",
  "type": "Annotation",
  "body": "http://example.org/description1",
  "target": {
    "id": "http://example.com/image1#xywh=100,100,300,300",
    "type": "Image",
    "format": "image/jpeg"
  }
}

3.2.4 임베디드 텍스트 본문

많은 상황에서 주석의 본문은 텍스트 포맷이며, 별도 IRI 없이 주석과 동시에 생성됩니다. 이럴 때는 본문의 텍스트를 Annotation에 직접 포함할 수 있어 여러 시스템과의 불필요한 상호작용을 줄일 수 있습니다. 본문에는 외부 웹 리소스의 속성(특히 텍스트 언어 및 포맷 등)도 함께 포함할 수 있습니다.

예시 활용 사례: Emily는 사진 공유 사이트에서 이미지를 얼마나 좋아하는지에 대해 댓글을 썼습니다. 그녀의 클라이언트는 그 댓글을 주석 내에 임베디드하고, 해당 댓글이 프랑스어이며 HTML 형식임을 추가합니다.

모델

텍스트 본문의 기본 속성은 다음과 같습니다:
용어 유형 설명
id 속성 텍스트 본문을 식별하는 IRI.
본문은 자신을 식별하는 IRI를 가질 수 있음.
type 관계 텍스트 본문 리소스의 타입.
본문은 TextualBody 클래스를 가지는 것이 좋고, 다른 클래스를 가질 수도 있음.
TextualBody 클래스 본문에 텍스트 리소스를 임베드할 때 사용하는 클래스.
본문은 TextualBody 클래스를 가지는 것이 바람직.
value 속성 텍스트 본문의 내용을 구성하는 문자 시퀀스.
1개의 value 속성을 반드시 포함해야 합니다.

시스템은 TextualBody에 클래스에서 설명된 Text 클래스가 명시적으로 type에 포함되어 있지 않더라도 포함된 것으로 가정해야 합니다.

language와 format 등 외부 웹 리소스의 속성들도 임베디드 텍스트 본문 리소스에 적용됩니다.

예시

예시 5: 텍스트 본문
{
  "@context": "http://www.w3.org/ns/anno.jsonld",
  "id": "http://example.org/anno5",
  "type": "Annotation",
  "body": {
    "type" : "TextualBody",
    "value" : "<p>j'adore !</p>",
    "format" : "text/html",
    "language" : "fr"
  },
  "target": "http://example.org/photo1"
}

3.2.5 문자열 본문

가장 단순한 본문 유형은 추가 정보나 속성 없이 plain text 문자열입니다. 이 유형의 본문은 오직 가장 단순한 Annotation에만 적합하며, 본문이 주석 외부에서 참조되어야 할 필요가 있는 경우에는 권장되지 않습니다.

예시 활용 사례 Franceska는 간단한 커맨드 라인 클라이언트에서 빠르게 주석을 생성하고자 합니다. 그녀는 텍스트 파일로 JSON 직렬화를 만들고, 이를 Annotation 서버로 전송하여 저장합니다.

모델

용어 유형 설명
bodyValue 속성 주석 본문의 문자열 값.
주석에는 정확히 1개의 bodyValue가 있을 수 있으며, 그 값은 아래 요구사항을 반드시 충족해야 합니다. bodyValue 속성이 존재할 경우, body 관계는 동시에 존재하면 안 됩니다.

이 형식을 언제 사용하고 어떻게 해석할지는 몇 가지 제한이 있습니다.
문자열 본문:

  • 반드시 하나의 xsd:string이어야 하며, 데이터 타입이 직렬화에 등장하면 안 됨.
  • 언어 정보를 가질 수 없습니다.
  • Textual Body의 value 속성과 같은 방식으로 해석되어야 합니다.
  • Textual Body 리소스의 format 속성이 text/plain인 것과 같은 의미로 해석해야 합니다.
  • Annotation 리소스에 있는 유사 속성으로부터, Textual Body의 다른 속성값을 추론하면 안 됩니다.

상기 해석 중 하나라도 충족되면, 반드시 TextualBody 방식을 사용해야 합니다.

참고
시스템은 주석을 bodyValue 대신 TextualBody 방식으로 변환할 수 있습니다. TextualBody 방식이 권장되며, 언어나 포맷 정보가 Annotation 처리에 중요합니다.

예시

예시 6: 문자열 본문
{
  "@context": "http://www.w3.org/ns/anno.jsonld",
  "id": "http://example.org/anno6",
  "type": "Annotation",
  "bodyValue": "Comment text",
  "target": "http://example.org/target1"
}
이것은 아래와 동등합니다:
예시 7: 동등한 텍스트 본문
{
  "@context": "http://www.w3.org/ns/anno.jsonld",
  "id": "http://example.org/anno7",
  "type": "Annotation",
  "body": {
    "type": "TextualBody",
    "value": "Comment text",
    "format": "text/plain"
  },
  "target": "http://example.org/target1"
}

3.2.6 본문과 대상의 수

어떤 주석은 본문이 전혀 없을 수도 있습니다. 예를 들어 별도의 텍스트 없이 단순히 하이라이트 표시하거나 북마크만 남기는 경우입니다. 또한, 한 개의 주석에 여러 개의 본문 또는/그리고 여러 개의 대상을 가질 수도 있습니다. 이 경우 각 본문은 모든 대상의 집합이 아닌 각각의 대상과 동일하게 관련이 있는 것으로 간주합니다.

예시 활용 사례: Gretchen은 전자책의 특정 부분을 초록색으로 하이라이트하고, 그 의미를 이미 알기 때문에 별도의 댓글은 달지 않습니다. 그녀의 클라이언트는 주석과 연관된 스타일시트를 추가하지만, 본문은 생성하지 않습니다.

예시 활용 사례: Hannah는 하나의 주석으로 태그와 설명을 두 장의 이미지에 함께 연결합니다.

모델

주석에 본문이 없을 경우 body 속성은 생략됩니다.

주석의 body 및/또는 target 속성은 단일 객체 대신 배열이 될 수 있습니다. 값은 리소스의 IRI 문자열이거나 객체일 수 있습니다.

예시

예시 8: 본문이 없는 주석
{
  "@context": "http://www.w3.org/ns/anno.jsonld",
  "id": "http://example.org/anno8",
  "type": "Annotation",
  "target": "http://example.org/ebook1"
}
예시 9: 여러 본문 또는 여러 대상
{
  "@context": "http://www.w3.org/ns/anno.jsonld",
  "id": "http://example.org/anno9",
  "type": "Annotation",
  "body": [
    "http://example.org/description1",
    {
      "type": "TextualBody",
      "value": "tag1"
    }
  ],
  "target": [
    "http://example.org/image1",
    "http://example.org/image2"
  ]
}

3.2.7 본문 선택

Choice는 애플리케이션이 처리하거나 표시할 리소스를 하나만 선택해야 하는 순서가 있는 목록을 의미합니다. 순서는 주석 작성자나 발행자가 가장 우선적으로 보기 원하는 순서로 나열됩니다.

예시 활용 사례: Irina는 한 웹사이트에 대해 토론한 글을 프랑스어와 영어로 모두 작성합니다. 두 게시글이 완전히 동등하므로 둘 다 표시할 필요는 없으며, 프랑스어 사용자는 프랑스어 댓글을, 다른 이용자는 영어 댓글을 보길 원합니다. 그녀의 클라이언트는 영어를 먼저 나열하여 Choice를 만듭니다.

모델

용어 유형 설명
id 속성 Choice를 식별하는 IRI.
Choice는 1개의 IRI를 가질 수 있음.
type 관계 리소스의 타입.
Choice는 정확히 1개의 type이 반드시 필요하며, 그 값은 Choice 클래스여야 합니다.
Choice 클래스 애플리케이션이 나열된 항목 중 하나만 사용자에게 표시하도록 하는 구조입니다. 모두 렌더링하지 않아야 함.
items 관계 선택할 수 있는 리소스의 목록, 기본(default) 옵션이 가장 먼저 나옴.
참고
클라이언트는 선택할 리소스를 결정하는 데 임의의 알고리즘을 사용할 수 있으며, 가능한 정보를 활용해 자동으로 선택하는 것이 바람직하지만, 사용자가 직접 선택하도록 목록을 보여줄 수도 있습니다.

예시

예시 10: Choice
{
  "@context": "http://www.w3.org/ns/anno.jsonld",
  "id": "http://example.org/anno10",
  "type": "Annotation",
  "body": {
    "type": "Choice",
    "items": [
      {
        "id": "http://example.org/note1",
        "language": "en"
      },
      {
        "id": "http://example.org/note2",
        "language": "fr"
      }
    ]
  },
  "target": "http://example.org/website1"
}

3.3 기타 속성

주석과 외부 웹 리소스가 생성, 수정 및 사용된 맥락에 대한 정보는 종종 중요합니다. 특히,
  • 리소스가 언제 생성, 수정되었거나 생성되었는지
  • 주석 또는 다른 리소스의 직렬화 형태를 누가 생성하거나 수정했는지, 그리고 그것이 누구를 대상으로 하는지
  • 리소스가 왜 주석에 포함되었는지, 혹은 주석이 왜 생성되었는지
  • 리소스가 가지고 있는 다른 식별자들
  • 권리 및 라이선스에 따라 리소스를 어떻게 사용할 수 있는지
참고
이 절에 설명된 기능 외에도, 다른 속성들이 주석이나 모델 내의 어떤 리소스에 추가될 수 있습니다 MAY. 이러한 확장 방법에 대해서는 [annotation-vocab]의 Extension 절을 참고하십시오.

3.3.1 라이프사이클 정보

주석 또는 참조된 리소스에 책임이 있는 개인, 조직 또는 기계는 그 기여에 대해 인정받을 가치가 있으며, 해당 리소스가 생성된 시점은 표시 순서나 오래되어 관련성이 떨어지는 콘텐츠 필터링에 유용합니다. 주석의 작성자는 또한 주석의 신뢰성을 판단하는 데 유용합니다. 주석을 생성하고 직렬화하는 데 사용된 소프트웨어와 그 활동이 발생한 시점은 광고 및 디버깅 모두에 유용합니다.

예시 활용 사례: Jane은 온라인에서 식당에 대한 리뷰를 작성하고, 친구들이 그 리뷰가 본인이 작성한 것임을 알고 신뢰할 수 있도록 작성자 정보가 연결되길 원합니다. 그녀의 클라이언트는 그녀 계정의 정체성과 클라이언트 자체의 정체성, 그리고 해당 리소스들이 생성된 적절한 타임스탬프를 주석에 추가합니다.

모델

용어 유형 설명
creator 관계 리소스를 생성한 에이전트. 이는 인간, 조직 또는 소프트웨어 에이전트일 수 있습니다.
주석과 본문에 대해 정확히 1개의 creator 관계가 있는 것이 권장되지만, 작성자가 익명으로 남기를 원하거나 여러 에이전트가 공동 작업했을 수 있으므로 0개 또는 그 이상일 수 있습니다. 이러한 관계는 다른 리소스와도 연결될 MAY 있습니다.
created 속성 리소스가 생성된 시점.
주석과 본문에 대해 정확히 1개의 created 속성이 있는 것이 권장되며, 1개를 초과해서는 안 됩니다 MUST NOT. 이 속성은 다른 리소스에도 연결될 MAY 있습니다. 날짜-시간 값은 UTC 타임존을 "Z"로 표기한 xsd:dateTime이어야 합니다 MUST.
generator 관계 주석의 직렬화를 생성한 에이전트.
주석 당 0개 이상의 generator 관계가 있을 MAY 있습니다.
generated 속성 주석 직렬화가 생성된 시점.
주석 당 정확히 1개의 generated 속성이 있을 수 있으며, 1개를 초과해서는 안 됩니다 MUST NOT. 날짜-시간 값은 UTC 타임존을 "Z"로 표기한 xsd:dateTime이어야 합니다 MUST.
modified 속성 생성 후 리소스가 수정된 시점.
주석과 본문에 대해 정확히 1개의 modified 속성이 있을 수 있으며, 1개를 초과해서는 안 됩니다 MUST NOT. 이 속성은 다른 리소스에도 연결될 MAY 있습니다. 날짜-시간 값은 UTC 타임존을 "Z"로 표기한 xsd:dateTime이어야 합니다 MUST.

예시

예시 11: 라이프사이클 정보
{
  "@context": "http://www.w3.org/ns/anno.jsonld",
  "id": "http://example.org/anno11",
  "type": "Annotation",
  "creator": "http://example.org/user1",
  "created": "2015-01-28T12:00:00Z",
  "modified": "2015-01-29T09:00:00Z",
  "generator": "http://example.org/client1",
  "generated": "2015-02-04T12:00:00Z",
  "body": {
    "id": "http://example.net/review1",
    "creator": "http://example.net/user2",
    "created": "2014-06-02T17:00:00Z"
  },
  "target": "http://example.com/restaurant1"
}

3.3.2 주체

주석 작성에 관여한 에이전트에 대한 추가 정보는 단순한 IRI 식별자 이상의 정보가 일반적으로 필요합니다. 여기에는 개인인지, 그룹인지, 소프트웨어인지 여부 및 실제 이름, 계정 닉네임, 이메일 주소와 같은 속성이 포함됩니다.

예시 활용 사례: Kelly는 자신의 신원을 관리하지 않는 시스템에 주석을 제출하려 하고, 표시될 때 가명(pseudonym)이 나오길 원합니다. 그녀의 클라이언트는 이 정보를 주석에 추가하여 서비스로 보냅니다.

모델

용어 유형 설명
id 속성 에이전트를 식별하는 IRI.
에이전트는 자신을 식별하는 정확히 1개의 IRI를 가지는 것이 권장되며, 1개를 초과해서는 안 됩니다 MUST NOT.
type 관계 에이전트의 타입.
에이전트는 아래에 나열된 클래스들 중 하나 이상의 클래스를 가지는 것이 권장됩니다.
Person 클래스 인간 에이전트에 대한 클래스입니다.
Organization 클래스 개인이 아닌 조직에 대한 클래스입니다.
Software 클래스 사용자의 클라이언트나 주석을 생성하는 머신러닝 시스템과 같은 소프트웨어 에이전트에 대한 클래스입니다.
name 속성 에이전트의 이름.
각 에이전트는 정확히 1개의 name 속성을 가지는 것이 권장되며, 0개 이상일 수 있습니다 MAY.
nickname 속성 에이전트의 닉네임.
각 에이전트는 정확히 1개의 nickname 속성을 가지는 것이 권장되며, 0개일 수 있습니다 MAY.
email 관계 mailto: IRI 스킴을 사용한 에이전트와 연관된 이메일 주소 [rfc6086].
각 에이전트는 1개 이상의 email 주소를 가질 수 있습니다 MAY.
email_sha1 속성 에이전트의 이메일 IRI(예: 'mailto:' 접두사 포함, 공백 없음)에 대해 sha1 알고리즘을 적용한 결과의 텍스트 표현입니다. 이는 이메일 주소를 공개하지 않고 식별자로 사용할 수 있게 합니다.
각 에이전트는 email_sha1 속성에 1개 이상의 값을 가질 수 있습니다 MAY.
homepage 관계 에이전트의 홈페이지.
각 에이전트는 1개 이상의 홈페이지를 가질 수 있습니다 MAY.

  "id": "http://example.org/anno12",
  "type": "Annotation",
  "creator": {
    "id": "http://example.org/user1",
    "type": "Person",
    "name": "My Pseudonym",
    "nickname": "pseudo",

  },
  "generator": {

3.3.3 의도된 대상

주석 및 기타 리소스의 생성 및 관리와 관련된 에이전트 외에도, 리소스가 의도된 소비자나 에이전트의 클래스(청중)를 아는 것이 유용합니다. 이는 역할(예: 교사 대 학생)이나 대상 클래스의 속성(예: 권장 연령대) 등을 기록할 수 있게 합니다.

예시 활용 사례: Lynda는 특정 교재를 수업에서 사용하는 방법에 대해 메모를 작성합니다. 그녀는 이 주석의 의도된 대상이 교재를 사용하는 교사임을 추가하여, 학습용으로 사용하는 학생들을 대상으로 한 다른 주석들과 구분합니다.

모델

용어 유형 설명
id 속성 Audience를 식별하는 IRI.
Audience를 식별하는 정확히 1개의 IRI가 제공될 수 있습니다 MAY.
type 관계 Audience의 타입은 schema.org 클래스 구조에서 가져옵니다.
Audience는 1개 이상의 type을 가지는 것이 권장되며, 그 값은 schema.org 클래스 구조에서 오는 것이 SHOULD합니다.
audience 관계 주석과 의도된 Audience 간의 관계.
각 주석에 대해 0개 이상의 Audience가 있을 수 있습니다 MAY.

대상을 설명하는 추가 속성들은 schema.org의 Audience 클래스에서 사용됩니다. 이러한 속성명과 클래스명은 다른 속성이나 클래스와 혼동되지 않도록 JSON에서 schema: 접두사를 붙여야 합니다 MUST.

audience의 사용은 주석을 보지 못하게 하는 접근 제한을 암시하거나 가능하게 하지 않습니다. 시스템은 사용자의 정보에 기반해 주석 표시를 필터링하는 데 이 정보를 사용하는 것이 권장되며, 주석이나 다른 리소스가 인증 및 권한 부여를 필요로 한다고 가정해서는 안 됩니다.

예시

예시 13: 대상
{
  "@context": "http://www.w3.org/ns/anno.jsonld",
  "id": "http://example.org/anno13",
  "type": "Annotation",
  "audience": {
    "id": "http://example.edu/roles/teacher",
    "type": "schema:EducationalAudience",
    "schema:educationalRole": "teacher"
  },
  "body": "http://example.net/classnotes1",
  "target": "http://example.com/textbook1"
}

3.3.4 콘텐츠 접근성

정보에 대한 접근은 유엔이 인정하는 기본 인권으로 여겨집니다. 웹은 다양한 신체적 제약에도 불구하고 의사소통 및 상호작용의 장벽을 제거할 수 있습니다. 이는 사회적 포용을 지원하며 정보의 잠재적 청중을 늘립니다. 주석의 본문이나 대상으로 사용되는 리소스에 대해, 다양한 능력을 가진 사용자들이 더 쉽게 접근할 수 있도록 하는 리소스의 특징을 기록하는 것이 유용합니다.

예시 활용 사례: Megan은 청력이 매우 제한적이어서 동영상과 상호작용할 때 자막을 읽는 것을 선호합니다. 그녀는 그런 동영상에 대해 주석을 달며, 같은 상황의 다른 사용자를 돕기 위해 클라이언트는 그 동영상이 이 접근성 기능을 갖추고 있음을 포함합니다.

모델

용어 유형 설명
accessibility 속성 리소스가 가지고 있는 접근성 기능을 설명하는 값들의 열거된 목록 중 하나 이상의 문자열.
각 본문 또는 대상 리소스에 대해 0개 이상의 접근성 기능이 나열될 수 있습니다 MAY.
참고

값 목록은 schema.org의 accessibilityFeature 설명에서 참조됩니다.

예시

예시 14: 접근성
{
  "@context": "http://www.w3.org/ns/anno.jsonld",
  "id": "http://example.org/anno14",
  "type": "Annotation",
  "motivation": "commenting",
  "body": "http://example.net/comment1",
  "target": {
    "id": "http://example.com/video1",
    "type": "Video",
    "accessibility": "captions"
  }
}

3.3.5 동기와 목적

많은 경우 주석이 생성된 이유나 텍스트 본문이 주석에 포함된 목적을 이해하는 것이 중요합니다. 즉 이전 절에서 설명한 '누가'와 '언제'뿐만 아니라 '왜'가 제공되어야 합니다. 이러한 이유는 주석 생성의 동기나 텍스트 본문이 주석에 포함된 목적을 선언함으로써 제공됩니다.

예시 활용 사례: Noelle은 나중에 참고하기 위해 리소스를 북마크하려는 의도로 주석을 달고, 다시 찾기 쉽도록 설명과 태그를 제공합니다. 그녀의 클라이언트는 이를 캡처하기 위해 주석과 텍스트 본문 리소스에 적절한 동기를 추가합니다.

모델

용어 유형 설명
motivation 관계 주석과 Motivation 간의 관계.
각 주석에 대해 정확히 1개의 motivation이 있는 것이 권장되며, 0개 또는 그 이상일 수 있습니다 MAY.
purpose 관계 텍스트 본문이 주석에 포함된 이유.
TextualBody에 대해 0개 이상의 purpose가 있을 수 있습니다 MAY.
Motivation 클래스 주석의 동기는 생성 이유로, 다른 주석에 답글을 다는 것, 리소스에 댓글을 다는 것, 관련 리소스로 연결하는 것 등이 포함될 수 있습니다.
동기들
assessing 인스턴스 사용자가 대상 리소스를 단순히 논평하는 것이 아니라 어떤 방식으로 평가하려는 동기입니다. 예: 책의 리뷰나 데이터셋의 품질 평가, 학생의 작업에 대한 평가 제공 등.
bookmarking 인스턴스 사용자가 대상이나 그 일부를 북마크하려는 동기입니다. 예: 독자가 읽기를 끝낸 텍스트 지점을 북마크하는 주석.
classifying 인스턴스 사용자가 대상을 어떤 것으로 분류하려는 동기입니다. 예: 이미지를 초상화로 분류하는 경우.
commenting 인스턴스 사용자가 대상에 대해 댓글을 달려는 동기입니다. 예: 특정 PDF 문서에 대한 해설 제공.
describing 인스턴스 사용자가 대상의 내용을 서술하려는 동기입니다(예: 정확성에 대한 논평이 아닌 대상의 내용 설명).
editing 인스턴스 사용자가 대상 리소스에 수정을 요청하거나 편집을 요구하려는 동기입니다. 예: 오타 수정을 요청하는 주석.
highlighting 인스턴스 사용자가 대상 리소스나 그 일부를 강조하려는 동기입니다. 예: 주석자가 동의하지 않는 선택된 텍스트에 주의를 환기하기 위해 강조 표시.
identifying 인스턴스 사용자가 대상에 정체성을 할당하려는 동기입니다. 예: 웹 페이지에서 도시를 언급한 부분에 도시를 식별하는 IRI를 연결하는 경우.
linking 인스턴스 사용자가 대상과 관련된 리소스에 연결하려는 동기입니다.
moderating 인스턴스 사용자가 대상에 어떤 값이나 품질을 부여하려는 동기입니다. 예: 신뢰 네트워크나 스레드 토론에서 주석을 상향 조정하는 주석에 태그를 다는 경우.
questioning 인스턴스 사용자가 대상에 대해 질문하려는 동기입니다. 예: 특정 텍스트 부분에 대해 도움을 요청하거나 진위 여부를 질문하는 경우.
replying 인스턴스 사용자가 이전 진술(주석 또는 다른 리소스)에 답하려는 동기입니다. 예: 위에서 요청된 도움에 응답을 제공하는 경우.
tagging 인스턴스 사용자가 대상에 태그를 연결하려는 동기입니다.
참고
동기들이 서로 어떻게 연관될 수 있는지와 새로운 동기를 만드는 방법에 대한 자세한 내용은 Annotation Vocabulary 문서 [annotation-vocab]를 참고하세요. 절 4.1은 외부 웹 리소스와 Motivation을 연관시키는 방법을 설명합니다.

예시

  "id": "http://example.org/anno15",
  "type": "Annotation",
  "motivation": "bookmarking",
  "body": [
    {
      "type": "TextualBody",
      "value": "readme",
      "purpose": "tagging"
    },
    {
      "type": "TextualBody",

3.3.6 권리 정보

리소스의 사용 조건을 설명하기 위해 라이선스나 권리 성명을 리소스와 연관시키는 것은 일반적인 관행입니다. 이를 통해 사용자는 리소스를 적절히 사용할 수 있고 일부 자동화된 시스템은 사용이 허용되는지 확인할 수 있습니다. 주석, 본문 및 대상은 서로 다른 라이선스나 권리를 가질 수 있으므로 각각 별도로 기술할 수 있습니다. 주석 자체가 아닌 다른 리소스의 권리는 소비 클라이언트 애플리케이션에 대한 참고적 힌트로 간주됩니다.

예시 활용 사례: Ophelia는 제품에 대한 리뷰를 작성하고 자신을 리뷰의 저자로 명시하길 원하지만, 리뷰와 제품을 연결하는 주석이 어떻게 사용되는지는 개의치 않습니다. 그녀는 주석과 본문에 각각 별도의 권리 성명을 명시합니다. 대상 리소스에 대해 권리를 모르는 경우 아무것도 지정하지 않습니다.

모델

용어 유형 설명
rights 관계 주석, 본문 또는 대상과 리소스의 사용 조건(권리 성명 또는 라이선스)을 포함하는 웹 리소스 간의 관계.
각 리소스에서 0개 이상의 rights 성명이나 라이선스를 연결할 수 있으며, 그 값은 IRI여야 합니다 MUST.

예시

예시 16: 권리
{
  "@context": "http://www.w3.org/ns/anno.jsonld",
  "id": "http://example.org/anno16",
  "type": "Annotation",
  "rights": "https://creativecommons.org/publicdomain/zero/1.0/",
  "body": {
    "id": "http://example.net/review1",
    "rights": "http://creativecommons.org/licenses/by-nc/4.0/"
  },
  "target": "http://example.com/product1"
}

3.3.7 기타 식별자

웹과 같은 대규모 분산 시스템에서는 정보가 종종 복사됩니다. 주석 및 관련 리소스의 출처를 추적하기 위해, 리소스를 추가로 식별하는 IRI들을 기록할 수 있습니다. 이러한 IRI는 dereferencable한 "퍼머링크", 웹을 알지 못한 채 클라이언트가 오프라인에서 할당한 식별자, 또는 현재 수집 시스템이 리소스를 발견한 위치일 수 있습니다.

예시 활용 사례: Petra는 주석을 생성하여 개인용과 공개용 등 여러 시스템에 전송하여 보관합니다. 그녀는 복사본들을 정렬할 수 있도록 표준 IRI로 UUID를 설정하고, 서비스는 이를 위해 HTTP IRI를 할당합니다. 이후 시스템이 공개 복사본을 수집하여 표준 UUID를 유지한 뒤, 원래의 HTTP IRI를 via로 옮기고 자신이 제어하는 IRI로 바꿀 수 있습니다.

모델

용어 유형 설명
canonical 관계 리소스의 접근 위치와 상관없이 그 정체성을 추적하는 데 사용되어야 하는 IRI와 주석/본문/대상 간의 관계입니다. 이 속성이 설정되어 있으면, 시스템은 이를 변경하거나 삭제해서는 안 됩니다 MUST NOT. 또한 시스템은 사전 합의 없이 canonical IRI를 부여해서는 안 됩니다 SHOULD NOT, 왜냐하면 주석이 이미 다른 곳에 canonical IRI를 가질 수 있기 때문입니다.
각 리소스에 대해 정확히 1개의 canonical IRI가 있을 수 있습니다 MAY.
via 관계 리소스가 그 시스템에 의해 제공되기 위해 해당 시스템이 리소스를 얻은 위치의 IRI와 주석/본문/대상 간의 관계.
각 리소스에 대해 0개 이상의 via IRI가 제공될 수 있습니다 MAY.

예시

예시 17: 기타 식별자
{
  "@context": "http://www.w3.org/ns/anno.jsonld",
  "id": "http://example.org/anno17",
  "type": "Annotation",
  "canonical": "urn:uuid:dbfb1861-0ecf-41ad-be94-a584e5c4f1df",
  "via": "http://other.example.org/anno1",
  "body": {
    "id": "http://example.net/review1",
    "rights": "http://creativecommons.org/licenses/by/4.0/"
  },
  "target": "http://example.com/product1"
}

4. 특정 리소스

위에서 설명한 구성만으로 fragment가 포함된 IRI를 사용하여 리소스의 일부를 참조하는 주석을 생성할 수 있지만, 이러한 방법만으로는 충분하지 않은 경우가 많습니다. 예를 들어, 이미지의 단순한 원형 영역이나 사선 등은 fragment로도 표현할 수 없습니다. HTML 페이지에서 임의의 텍스트 구간을 선택하는 것 역시 가장 단순한 주석 개념이지만, fragment로 지원되지 않습니다. 또한, 특정 상태나 표현을 클라이언트가 가져와야 하는 경우, 특정 스타일로 리소스를 렌더링해야 하는 경우, 주석에서만 의미를 갖는 역할을 할당해야 하는 경우, 특정 맥락에서 사용될 때만 적용되는 주석 등 비세그먼트적 사용 사례도 존재합니다.

웹 주석 데이터 모델은 이러한 주석 특화 요구사항을 포착하기 위해 새로운 타입의 리소스인 SpecificResource를 사용합니다. SpecificResource는 Annotation과 Body/Target 사이에서 적절히 사용되어 Annotation에서 어떻게 쓰였는지에 대한 추가 정보를 저장합니다. 이러한 설명은 일반적으로 SpecificResource에서 별도의 엔티티로 참조되며, 다양한 요구사항을 포착하기 위해 여러 유형일 수 있습니다. 예를 들어, 주석의 대상이 이미지의 원형 영역이라면, SpecificResource가 원형 영역 자체이고, Selector로 설명되며, 소스 이미지 리소스와도 연결됩니다.

Specific Resource와 Specifier는 Selector 구성의 예처럼 고유 IRI를 가지는 외부 웹 리소스가 될 수도 있지만, Annotation을 처리하는데 필요한 모든 정보를 얻기 위해 불필요한 네트워크 요청을 피하기 위해 Annotation 표현 내에 포함하는 것이 권장됩니다.

이 문서에서 정의하는 추가 특이점의 유형은 다음과 같습니다:

  • 목적(Purpose): Annotation에 소스 리소스를 포함하는 목적을 설명
  • 셀렉터(Selector): Annotation에 사용할 소스 리소스의 세그먼트를 설명
  • 상태(State): Annotation을 위한 소스 리소스의 표현을 설명
  • 스타일(Style): Annotation에서 소스 리소스를 표시할 스타일을 설명
  • 렌더링(Rendering): 주석을 만들 때 클라이언트가 리소스를 렌더링하는 데 사용한 시스템을 설명
  • 스코프(Scope): Annotation에 대해 소스 리소스가 적용되는 범위를 설명

모델

용어 유형 설명
id 속성 특정 리소스의 식별자.
특정 리소스는 자신을 식별하는 정확히 1개의 IRI를 가질 수 있습니다.
type 관계 특정 리소스의 클래스.
특정 리소스는 SpecificResource 클래스를 가지고 있어야 합니다.
SpecificResource 클래스 특정 리소스를 위한 클래스.
SpecificResource 클래스는 다른 리소스의 보다 특정한 영역이나 상태임을 알 수 있도록 특정 리소스와 연관되어야 합니다.
source 관계 특정 리소스와, 그것이 더 구체적으로 표현하는 리소스 간의 관계.
특정 리소스는 source 관계를 정확히 하나 가져야 하며, source 리소스는 위에서 정의한 것처럼 상세 기술될 수도, 단순하게 그 리소스의 IRI만 있을 수도 있습니다.

동일한 Specific Resource와 Specifier 클래스는 Target과 Body 모두에서 사용됩니다. 이 절의 예제는 둘 중 하나만 사용하지만 동일한 모델이 모두에 적용됩니다.

4.1 외부 웹 리소스의 목적

텍스트 본문뿐 아니라, 외부 웹 리소스도 Annotation 내에 포함되는 동기를 명시할 수 있습니다. 이는 Specific Resource 패턴을 사용하며, 목적은 Selector가 세그먼트를 설명하거나 State가 표현을 설명하는 것처럼 Annotation 문맥에서 리소스가 사용되는 방식을 명시합니다.

예시 활용 사례: Qitara는 사진에 도시의 이름이 아닌 식별자로 태그를 달고 싶어합니다(이름은 모호할 수 있기 때문). 그녀의 클라이언트는 검색을 통해 널리 알려진 IRI를 찾아 도시 식별자로 사용하고, 목적 할당을 관리하기 위해 Specific Resource를 생성합니다.

모델

용어 유형 설명
purpose 관계 웹 리소스를 Annotation에 포함하는 이유.
SpecificResource에는 purpose를 사용하여 0개 이상의 동기가 연결될 수 있습니다 MAY.

예시

예시 18: 목적이 있는 리소스
{
  "@context": "http://www.w3.org/ns/anno.jsonld",
  "id": "http://example.org/anno18",
  "type": "Annotation",
  "body": {
    "type": "SpecificResource",
    "purpose": "tagging",
    "source": "http://example.org/city1"
  },
  "target": {
    "id": "http://example.org/photo1",
    "type": "Image"
  }
}

4.2 셀렉터

많은 주석은 전체 리소스가 아닌 일부만을 대상으로 합니다. 우리는 이를 리소스의 세그먼트(관심 부분, Segment of Interest)라고 부릅니다. Selector는 소스 리소스 내에서 세그먼트를 어떻게 결정하는지 설명하는 데 사용합니다. Selector의 특성은 리소스 유형에 따라 달라지며, 다양한 미디어 타입의 세그먼트를 설명하는 방법도 다릅니다. 같은 세그먼트를 여러 방식(selector)로 기술해 두면 나중에 찾기 쉽고, 최소한 하나의 Selector만을 사용하더라도 소비 클라이언트는 원하는 컨텐츠를 활용할 수 있습니다.

예시 활용 사례: Ramona는 웹 페이지 내에서 텍스트를 선택하고, 데이터셋의 한 조각을 동시에 선택하여 연결하고 싶습니다. 그녀는 클라이언트를 통해 둘 다 선택하고 Body와 Target 각각에 Selector가 할당된 SpecificResource로 주석을 생성합니다.

모델

용어 유형 설명
selector 관계 특정 리소스와 Selector 간의 관계.
특정 리소스에는 selector 관계가 0개 이상 연결될 수 있습니다. 여러 Selector는 동일한 컨텐츠를 선택해야 바람직하지만, 일부 Selector는 정밀도가 다를 수 있습니다. 소비 클라이언트는 만약 세그먼트가 다르다면 반드시 하나를 선택해야 합니다.

예시

예시 19: 셀렉터 
{
  "@context": "http://www.w3.org/ns/anno.jsonld",
  "id": "http://example.org/anno19",
  "type": "Annotation",
  "body": {
    "source": "http://example.org/page1",
    "selector": "http://example.org/paraselector1"
  },
  "target": {
    "source": "http://example.com/dataset1",
    "selector": "http://example.org/dataselector1"
  }
}

4.2.1 프래그먼트 셀렉터

세그먼트를 지정하는 가장 널리 알려진 메커니즘은 표현 미디어 타입에서 정의되는 IRI의 fragment 부분이므로, 이를 Selector를 통해 기술하는 방법을 허용하는 것은 유용합니다. 이를 통해 기존 및 향후 fragment 사양을 SpecificResource와 일관되게 사용할 수 있습니다. 어떤 fragment 타입이 사용되는지 명확히 하기 위해, Selector는 이를 정의한 사양을 참조할 수 있습니다.

예시 활용 사례: Sally는 비디오의 일부 구간을 이미지 설명으로 활용하고 싶습니다. 그녀는 비디오 내 시간 구간을 선택하고, 그것이 대상을 설명한다고 클릭합니다. 클라이언트는 FragmentSelector와 describing 동기를 가지는 SpecificResource로 Annotation을 생성합니다.

모델

용어 유형 설명
type 관계 셀렉터의 클래스.
FragmentSelector는 반드시 type이 하나 뿐이어야 하며 그 값은 FragmentSelector여야 합니다.
FragmentSelector 클래스 IRI의 fragment 컴포넌트를 이용해 세그먼트를 설명하는 리소스.
value 속성 세그먼트를 설명하는 IRI fragment 컴포넌트의 내용.
FragmentSelector는 정확히 1개의 value 속성을 가져야 합니다.
conformsTo 관계 FragmentSelector와 value 속성에 있는 IRI fragment의 문법을 정의하는 사양 간의 관계.
Fragment Selector는 사양에 대한 conformsTo 링크를 정확히 1개 가져야 하며, 여러 개 가져서는 안 됩니다 MUST NOT.

FragmentSelector를 사용하는 것이 다른 특정리소스 기술 방법과 일관성을 가지므로, fragment가 포함된 IRI를 직접 사용하는 것보다는 이 방식을 권장합니다. 소비 애플리케이션은 두 가지 모두를 알아야 합니다 SHOULD.

아래 IRI들은 fragment의 의미를 정의하는 일부 사양들이며, conformsTo 관계에 사용할 수 있습니다. 그 외에도 다른 IRI가 사용될 수 있습니다.

이름 Fragment 사양 설명
HTML http://tools.ietf.org/rfc/rfc3236 [rfc3236] 예: namedSection
PDF http://tools.ietf.org/rfc/rfc3778 [rfc3778] 예: page=10&viewrect=50,50,640,480
Plain Text http://tools.ietf.org/rfc/rfc5147 [rfc5147] 예: char=0,10
XML http://tools.ietf.org/rfc/rfc3023 [rfc3023] 예: xpointer(/a/b/c)
RDF/XML http://tools.ietf.org/rfc/rfc3870 [rfc3870] 예: namedResource
CSV http://tools.ietf.org/rfc/rfc7111 [rfc7111] 예: row=5-7
Media http://www.w3.org/TR/media-frags/ [media-frags] 예: xywh=50,50,640,480
SVG http://www.w3.org/TR/SVG/ [SVG11] 예: svgView(viewBox(50,50,640,480))
EPUB3 http://www.idpf.org/epub/linking/cfi/epub-cfi.html [cfi] 예: epubcfi(/6/4[chap01ref]!/4[body01]/10[para05]/3:10)

참고
fragment를 사용하는 IRI는 source, #, value를 연결하여 재구성할 수 있습니다. 예를 들어, 아래 예제에서 IRI는 http://example.org/video1#t=30,60이 됩니다.

예시

예시 20: Fragment Selector
{
  "@context": "http://www.w3.org/ns/anno.jsonld",
  "id": "http://example.org/anno20",
  "type": "Annotation",
  "body": {
    "source": "http://example.org/video1",
    "purpose": "describing",
    "selector": {
      "type": "FragmentSelector",
      "conformsTo": "http://www.w3.org/TR/media-frags/",
      "value": "t=30,60"
    }
  },
  "target": "http://example.org/image1"
}

4.2.2 CSS 선택자

HTML 문서 객체 모델에서 요소를 선택하는 가장 일반적인 방법 중 하나는 CSS 선택자 [CSS3-selectors]를 사용하는 것입니다. CSS 선택자는 웹 페이지 내 요소로 가는 경로를 다양한 방식으로 기술할 수 있게 하며, 이는 웹 주석의 많은 기본 사용 사례를 포괄할 수 있습니다. CSS 선택자가 Document Object Model을 따르지 않는 표현에 적용될 때의 결과는 정의되어 있지 않습니다.

CSS는 주석 내에서 리소스를 스타일링하는 데에도 사용될 수 있습니다. 이 클래스는 Document Object Model을 따르는 리소스의 세그먼트를 선택하기 위해 CSS 선택자 메커니즘을 재사용하는 데 집중되어 있습니다.

예시 활용 사례: Teynika는 웹 페이지의 단락을 선택하여 메모를 남기고자 합니다. 그녀의 클라이언트는 해당 요소를 정확히 식별하는 CSS 경로를 계산해 이를 주석에 추가합니다.

모델

용어 유형 설명
type 관계 선택자의 클래스.
CssSelector는 반드시 하나의 type을 가져야 하며, 그 값은 CssSelector여야 합니다.
CssSelector 클래스 CSS 선택자 리소스의 타입.
CSS 선택자는 반드시 이 클래스를 연관시켜야 합니다.
value 속성 세그먼트에 대한 CSS 선택 경로.
CSS Selector에는 반드시 하나의 value가 연결되어야 합니다.
참고
구현자는 시스템 간 상호운용성을 극대화하기 위해 스타일이나 변형보다는 요소 또는 콘텐츠 선택에 직접적으로 기여하는 CSS의 일반적으로 지원되는 기능만을 사용할 것을 권장합니다.

예시

예시 21: CSS 선택자
{
  "@context": "http://www.w3.org/ns/anno.jsonld",
  "id": "http://example.org/anno21",
  "type": "Annotation",
  "body": "http://example.org/note1",
  "target": {
    "source": "http://example.org/page1.html",
    "selector": {
      "type": "CssSelector",
      "value": "#elemid > .elemclass + p"
    }
  }
}

4.2.3 XPath 선택자

Document Object Model(DOM)을 지원하는 리소스(예: XML이나 HTML 문서)에서 요소 및 콘텐츠를 선택하는 또 다른 일반적인 방법은 XPath 선택 [DOM-Level-3-XPath]을 사용하는 것입니다. XPath는 선택된 콘텐츠로 향하는 구조적 경로를 매우 유연하게 기술할 수 있습니다. XPath 선택자가 DOM을 따르지 않는 표현에 적용될 때의 결과는 정의되어 있지 않습니다.

참고
구현자는 HTML5 명세에서 파서가 DOM에 부족한 요소를 추가할 수 있음을 주의해야 합니다. XPath는 문서 내 구조가 아니라 실제 DOM에 포함될 수 있는 이러한 요소까지 포괄하여 생성하는 것이 권장됩니다.

예시 활용 사례: Ulrika는 HTML 페이지의 표 안에서 span을 선택하여 그 내용을 주석으로 남깁니다. 이 요소를 명확히 지칭하기 위해, 그녀의 클라이언트는 정확히 지목하는 XPath를 조심스럽게 계산해 Annotation의 target으로 추가합니다.

모델

용어 유형 설명
type 관계 선택자의 클래스.
XPathSelector는 반드시 하나의 type을 가져야 하며, 그 값은 XPathSelector여야 합니다.
XPathSelector 클래스 XPath 선택자 리소스의 타입.
XPath 선택자는 반드시 이 클래스를 연관시켜야 합니다.
value 속성 선택된 세그먼트로의 xpath.
XPath Selector에는 반드시 하나의 value가 연결되어야 합니다.
참고
구현자는 시스템 간 상호운용성을 극대화하기 위해 요소 또는 콘텐츠 선택에 직접적으로 기여하는 XPath의 일반적으로 지원되는 부분만을 사용할 것을 권장합니다.

예시

예시 22: XPath 선택자
{
  "@context": "http://www.w3.org/ns/anno.jsonld",
  "id": "http://example.org/anno22",
  "type": "Annotation",
  "body": "http://example.org/note1",
  "target": {
    "source": "http://example.org/page1.html",
    "selector": {
      "type": "XPathSelector",
      "value": "/html/body/p[2]/table/tr[2]/td[3]/span"
    }
  }
}

4.2.4 텍스트 인용 선택자

이 선택자는 본문의 일부 텍스트 자체를 복사하고, 동일한 문자가 여러 번 등장하는 경우 식별을 위해 직전/직후 문맥(접두사/접미사)도 함께 포함하여 텍스트 범위를 설명합니다.

예를 들어, 문서가 "abcdefghijklmnopqrstuvwxyz"라면 "efg"를 선택하기 위해 접두사 "abcd", 매치 "efg", 접미사 "hijk"를 지정할 수 있습니다.

예시 활용 사례: Valeria는 웹 페이지에서 오타('anotation')를 선택하여, 올바른 철자('annotation')로 바꿔야 한다고 댓글을 남깁니다.

모델

용어 유형 설명
type 관계 선택자의 클래스.
TextQuoteSelector는 반드시 하나의 type을 가져야 하며, 그 값은 TextQuoteSelector여야 합니다.
TextQuoteSelector 클래스 인용과 직전/직후 구문으로 텍스트 세그먼트를 기술하는 선택자의 클래스.
TextQuoteSelector는 반드시 이 클래스를 연관시켜야 합니다.
exact 속성 선택된 텍스트의 복사본(정규화 후).
각 TextQuoteSelector마다 정확히 하나의 exact 속성이 필요합니다.
prefix 속성 선택된 텍스트 바로 앞에 위치하는 텍스트 조각.
각 TextQuoteSelector는 정확히 하나의 prefix를 가져야 하며, 여러 개 존재하면 안 됩니다.
suffix 속성 선택된 텍스트 바로 뒤에 위치하는 텍스트 조각.
각 TextQuoteSelector는 정확히 하나의 suffix를 가져야 하며, 여러 개 존재하면 안 됩니다.

텍스트 선택은 반드시 유니코드 코드 포인트(문자 번호) 기준이어야 하며, 코드 유닛 등 다른 타입으로 해석되지 않습니다. 선택은 글자 클러스터의 중간에서 시작하거나 끝나면 안 됩니다. 선택은 반드시 텍스트의 논리적 순서를 따릅니다. 자세한 문자 모델은 [charmod]를 참고하세요.

텍스트는 Annotation에 기록되기 전에 반드시 정규화되어야 합니다. 따라서 HTML/XML 태그는 제거하고, 문자 엔티티는 실제 문자로 변환하는 것이 좋습니다. 이 처리는 주석의 기록 방법만 바꿀 뿐, 실제 문서 내용은 영향을 받지 않습니다.

접두사, exact, 접미사 처리 후 사용자 에이전트가 일치하는 텍스트를 여러 개 발견했다면, 선택은 그 모두에 일치하는 것으로 간주하는 것이 권장됩니다.

참고
콘텐츠가 저작권 보호 중이거나 사용에 제한이 있을 경우, 이런 방식의 텍스트 선택은 위험할 수 있습니다. 사용자가 문서의 전체 텍스트를 주석으로 복사할 수 있는데, 이는 바람직하지 않을 수 있습니다. 접근/배포 제한이 있는 정적 텍스트의 경우에는 Text Position Selector가 더 적합할 수 있습니다.

예시

예시 23: 텍스트 인용 선택자
{
  "@context": "http://www.w3.org/ns/anno.jsonld",
  "id": "http://example.org/anno23",
  "type": "Annotation",
  "body": "http://example.org/comment1",
  "target": {
    "source": "http://example.org/page1",
    "selector": {
      "type": "TextQuoteSelector",
      "exact": "anotation",
      "prefix": "this is an ",
      "suffix": " that has some"
    }
  }
}

4.2.5 텍스트 위치 선택자

이 선택자는 선택 영역의 시작 및 끝 위치를 기록하여 텍스트의 범위를 표현합니다. 위치 0은 첫 번째 문자 바로 앞, 위치 1은 두 번째 문자 바로 앞을 의미합니다. 시작 문자는 범위에 포함되고, 끝 문자는 포함되지 않습니다.

예를 들어 문서가 "abcdefghijklmnopqrstuvwxyz"이고, 시작이 4, 끝이 7이면 선택 영역은 "efg"가 됩니다.

예시 활용 사례: Wendy는 콘텐츠를 추출하거나 복사할 수 없는 전자책에 대한 리뷰를 씁니다. 그녀의 클라이언트는 선택 범위를 콘텐츠 내 시작/끝 위치로 기술합니다.

모델

용어 유형 설명
type 관계 선택자의 클래스.
TextPositionSelector는 반드시 하나의 type을 가져야 하며, 그 값은 TextPositionSelector여야 합니다.
TextPositionSelector 클래스 시작 및 끝 위치에 기반해 텍스트 범위를 기술하는 선택자의 클래스.
TextPositionSelector는 반드시 이 클래스를 연관시켜야 합니다.
start 속성 텍스트 세그먼트의 시작 위치. 전체 텍스트의 첫 번째 문자는 위치 0, 이 문자는 세그먼트에 포함됩니다.
각 TextPositionSelector는 정확히 하나의 start 속성이 필요하며, 값은 0 이상의 정수여야 합니다.
end 속성 텍스트 세그먼트의 끝 위치. 이 문자는 세그먼트에 포함되지 않습니다.
각 TextPositionSelector는 정확히 하나의 end 속성이 필요하며, 값은 0 이상의 정수여야 합니다.

텍스트는 시작 및 끝 위치를 판단하기 전에 Text Quote Selector에서와 동일하게 선택 및 정규화되어야 합니다.

참고
이 선택자는 Text Quote Selector와 달리, 원본 문서에서 텍스트를 Annotation 그래프로 복사할 필요가 없으나, 리소스가 변경될 경우 매우 취약합니다. 편집 또는 동적 트랜스클루전이 있을 경우 선택 내용이 바뀔 수 있으므로, 올바른 표현을 판별하기 위해 State를 추가로 사용하는 것이 권장됩니다.

예시

예시 24: 텍스트 위치 선택자
{
  "@context": "http://www.w3.org/ns/anno.jsonld",
  "id": "http://example.org/anno24",
  "type": "Annotation",
  "body": "http://example.org/review1",
  "target": {
    "source": "http://example.org/ebook1",
    "selector": {
      "type": "TextPositionSelector",
      "start": 412,
      "end": 795
    }
  }
}

4.2.6 데이터 위치 선택자

텍스트 위치 선택자와 유사하게, 데이터 위치 선택자는 동일한 속성을 사용하지만 텍스트 내 문자 단위가 아니라 비트스트림 내 바이트 단위에서 동작합니다.

예시 활용 사례: Xena는 포렌식 목적으로 온라인 디스크 이미지의 영역에 대해 코멘트를 작성하고 에뮬레이션 요구사항을 설명합니다. 그녀의 클라이언트는 사람이 보기 쉬운 화면이 아니라 이진 스트림에서 시작과 끝 위치를 추출합니다.

모델

용어 유형 설명
type 관계 선택자의 클래스.
Data Position Selector는 반드시 하나의 type만을 가져야 하며, 그 값은 DataPositionSelector여야 한다.
DataPositionSelector 클래스 바이트 스트림 내 시작 및 끝 위치를 기준으로 데이터 영역을 설명하는 선택자의 클래스.
DataPositionSelector는 반드시 이 클래스와 연관되어야 한다.
start 속성 데이터 세그먼트의 시작 위치. 첫 번째 바이트는 문자 위치 0이다.
각 DataPositionSelector에는 정확히 하나의 start 속성이 있어야 한다.
end 속성 데이터 세그먼트의 끝 위치. 마지막 문자는 세그먼트에 포함되지 않는다.
각 DataPositionSelector에는 정확히 하나의 end 속성이 있어야 한다.

예시

  "id": "http://example.org/anno25",
  "type": "Annotation",
  "body": "http://example.org/note1",
  "target": {
    "source": "http://example.org/diskimg1",
    "selector": {
      "type": "DataPositionSelector",
      "start": 4096,
      "end": 4104
    }
  }
}

4.2.7 SVG 선택자

SvgSelector는 Scalable Vector Graphics [SVG11] 표준을 사용하여 영역을 정의합니다. 사용자가 SVG를 이용해서 원, 다각형 등 비사각형 영역을 표현할 수 있으며, SVG는 Annotation 내에 임베디드되거나 외부 웹 리소스로 참조될 수 있습니다.

SvgSelector는 리소스 영역 선택에 SVG를 사용합니다. SVG 표현의 세그먼트는 FragmentSelector 또는 SvgSelector 같은 선택자를 통해 추가로 선택될 수 있습니다.

예시 활용 사례: Yadira는 온라인 고지도에서 옛 도로의 대각선 영역을 태깅합니다. 그녀의 클라이언트는 이미지 콘텐츠를 기준으로 해당 영역을 설명하는 SVG 다각형을 생성합니다.

모델

용어 유형 설명
type 관계 선택자의 클래스.
SVG Selector는 반드시 하나의 type만을 가져야 하며, 그 값에는 SvgSelector를 포함해야 한다.
SvgSelector 클래스 SVG 표준을 이용해 선택된 영역의 도형을 정의하는 선택자의 클래스.
이 선택자는 반드시 이 클래스와 연관되어야 한다.
value 속성 SVG 콘텐츠의 문자인 시퀀스.
Selector에 정확히 하나의 value 속성이 연결될 수 있으며, 이 속성이 있을 경우 값은 well-formed SVG XML이어야 한다.

SVG 도형/캔버스의 크기는 소스 리소스의 크기를 기준으로 반드시 상대적으로 지정되어야 하며, 도형을 이미지 전체 크기로 스케일링하면 원하는 영역을 올바르게 나타낼 수 있어야 합니다.

참고
구현자는 시스템간 상호운용성을 극대화하기 위해 스타일링이나 변형이 아닌 영역 자체 설명에 직접적으로 기여하는 SVG의 일반적으로 지원되는 기능만을 사용해야 합니다. SVG 요소 내에 스타일 정보, JavaScript, 애니메이션, 텍스트 또는 도형과 무관한 정보 포함은 권장되지 않으며, 클라이언트는 그런 정보가 있을 경우 이를 무시해야 합니다.

예시

예시 26: SVG 선택자
{
  "@context": "http://www.w3.org/ns/anno.jsonld",
  "id": "http://example.org/anno26",
  "type": "Annotation",
  "body": "http://example.org/road1",
  "target": {
    "source": "http://example.org/map1",
    "selector": {
      "id": "http://example.org/svg1",
      "type": "SvgSelector"
    }
  }
}
예시 27: SVG 선택자, 임베디드
{
  "@context": "http://www.w3.org/ns/anno.jsonld",
  "id": "http://example.org/anno27",
  "type": "Annotation",
  "body": "http://example.org/road1",
  "target": {
    "source": "http://example.org/map1",
    "selector": {
      "type": "SvgSelector",
      "value": "<svg:svg> ... </svg:svg>"
    }
  }
}

4.2.8 범위 선택자

사용자가 범위를 선택하면, 표현 내 내부 경계를 넘거나 광범위하게 선택하는 경우 단일 선택자로 정확한 콘텐츠를 견고하게 설명하기 어렵습니다. 범위 선택자(Range Selector)는 다른 선택자들을 활용하여 선택의 시작점과 끝점을 식별할 수 있습니다. 이렇게 하면 가장 적합한 선택 메커니즘으로 두 지점을 정확하게 지정하고, 이를 연결해 범위를 구성할 수 있습니다. 선택 영역은 시작 선택자의 시작부터 끝 선택자의 시작 전까지 모든 내용을 포함합니다.

예시 활용 사례: Zara는 웹 페이지의 표 내 두 인접 셀에 의견을 달고자 합니다. 그녀는 두 셀을 선택하고, 클라이언트는 첫 번째 셀과 두 번째 셀 다음 셀의 XPath를 각각 계산합니다. 클라이언트는 첫 번째 XPath 선택자를 start로, 두 번째를 end로 하여 범위 선택자를 생성합니다.

모델

용어 유형 설명
type 관계 선택자의 클래스.
Range Selector는 반드시 하나의 type만을 가져야 하며, 그 값은 RangeSelector여야 한다.
RangeSelector 클래스 범위 선택자 리소스의 타입.
Range Selector는 반드시 이 클래스와 연관되어야 한다.
startSelector 관계 범위의 포함된 시작 지점을 설명하는 선택자.
Range Selector에는 반드시 하나의 startSelector가 지정되어야 한다 MUST.
endSelector 관계 범위의 제외된 종료 지점을 설명하는 선택자.
Range Selector에는 반드시 하나의 endSelector가 지정되어야 한다 MUST. startSelector와 endSelector는 동일한 클래스여야 한다.

예시

예시 28: 범위 선택자
{
  "@context": "http://www.w3.org/ns/anno.jsonld",
  "id": "http://example.org/anno28",
  "type": "Annotation",
  "body": "http://example.org/comment1",
  "target": {
    "source": "http://example.org/page1.html",
    "selector": {
      "type": "RangeSelector",
      "startSelector": {
        "type": "XPathSelector",
        "value": "//table[1]/tr[1]/td[2]"
      },
      "endSelector": {
        "type": "XPathSelector",
        "value": "//table[1]/tr[1]/td[4]"
      }
    }
  }
}

4.2.9 선택 정밀화

관심 영역을 전체 리소스가 아닌 선택의 선택으로 기술하는 것이 더 쉽거나, 신뢰성이 높거나, 더 정확할 수 있습니다. 특히 다른 리소스를 포함하는 다양한 패키징 포맷 등에서는 컴포넌트에 고유 식별자가 없을 때 선택 메커니즘을 분해하는 데 이 방식이 유용합니다. 이는 선택자들이 체인 형태로 연결되어 각각 이전 결과를 더욱 세분화하여 표현하는 방식으로 이루어집니다.

예시 활용 사례: Alexandra는 텍스트의 한 단락을, 그리고 그 안에서 짧은 구절을 선택해서 의견을 답니다. 그녀의 클라이언트는 그 구절을 텍스트 인용 선택자로 기록하고, 그 부모 단락 식별에는 FragmentSelector를 사용하여, TextQuoteSelector가 FragmentSelector를 한 번 더 정밀화하는 구조로 만듭니다.

모델

용어 유형 설명
refinedBy 관계 더 넓은 선택자와 그 결과를 정밀하게 한 더 구체적인 선택자 간의 관계.
하나의 선택자는 1개 이상의 refinedBy 선택자와 연결될 수 있으며 MAY, 여러 개일 경우 그들은 모두 같은 선택 결과를 도출하는 대안들로 간주합니다.

예시

예시 29: 선택 정밀화
{
  "@context": "http://www.w3.org/ns/anno.jsonld",
  "id": "http://example.org/anno29",
  "type": "Annotation",
  "body": "http://example.org/comment1",
  "target": {
    "source": "http://example.org/page1",
    "selector": {
      "type": "FragmentSelector",
      "value": "para5",
      "refinedBy": {
        "type": "TextQuoteSelector",
        "exact": "Selected Text",
        "prefix": "text before the ",
        "suffix": " and text after it"
      }
    }
  }
}

4.3 상태

상태는 특정 주석에 적용되는 리소스의 의도한 상태를 설명하며, 그 리소스의 올바른 표현을 가져오는 데 필요한 정보를 제공합니다. 웹 리소스는 시간에 따라 변경되므로, 상태는 의도한 이전 버전을 복원하는 방법을 설명하는 데 사용될 수 있습니다. 또한 웹 리소스는 여러 포맷을 가질 수 있어, 상태는 특정 포맷을 가져오는 방법을 설명하는 데에도 동일하게 사용될 수 있습니다. 같은 표현을 설명하기 위해 여러 상태를 제공할 수도 있는데, 이는 소비 클라이언트가 표현을 올바르게 찾을 가능성을 극대화하기 위함입니다.

예시 활용 사례: Britney는 자주 변경되는 웹 페이지에 댓글을 남깁니다. 그녀의 클라이언트는 다른 클라이언트가 주석의 원래 대상을 재구성할 수 있도록 정보를 기록합니다.

모델

용어 유형 설명
state 관계 SpecificResource와 상태 간의 관계.
각 SpecificResource에 대해 state 관계가 0개 이상 있을 수 있습니다 MAY. 여러 상태는 동일한 표현을 SHOULD 설명해야 하지만, 일부 상태는 다른 것보다 정밀하지 않을 수 있습니다. 소비 클라이언트는 MUST 다르다면 하나를 선택해야 합니다.

상태는 반드시 Selector나 Style 정보 처리 전에 처리해야 합니다.

예시

예시 30: 상태
{
  "@context": "http://www.w3.org/ns/anno.jsonld",
  "id": "http://example.org/anno30",
  "type": "Annotation",
  "body": "http://example.org/note1",
  "target": {
    "source": "http://example.org/page1",
    "state": {
      "id": "http://example.org/state1"
    }
  }
}

4.3.1 시간 상태

Time State 리소스는 해당 리소스가 주석에 적합한 시점을 기록합니다. 보통 주석이 작성된 시간이나 현재 버전의 영구 링크 등이 여기에 해당합니다. 리소스의 타임스탬프는 RFC 7089 [rfc7089]에서 설명하는 Memento 프로토콜로도 확인할 수 있습니다.

예시 활용 사례: Carla는 뉴스 웹사이트의 메인화면 현재 상태에 대해 메모를 남기며 이 페이지가 자주 변경될 수 있다고 표시합니다. 그녀의 클라이언트는 페이지 버전을 설명하기 위해 현재 시간을 포함하는 상태를 추가합니다.

모델

용어 유형 설명
type 관계 상태의 클래스.
Time State는 반드시 하나의 type만을 가져야 하며, 그 값은 TimeState여야 함.
TimeState 클래스 주석에 대해 시간적으로 적합한 소스 리소스 표현을 검색하는 방법에 대한 설명입니다.
상태는 반드시 이 클래스를 연관시켜야 함.
sourceDate 속성 주석에서 소스 리소스를 해석해야 하는 타임스탬프.
각 TimeState당 sourceDate가 0개 이상일 수 MAY 있습니다. 하나 이상이면 각각 대체 타임스탬프를 의미합니다. MUST xsd:dateTime 형태이고 MUST UTC 타임존(“Z”)이어야 합니다. sourceDate가 있으면 sourceDateStart와 sourceDateEnd는 절대 동시에 제공되면 안 됩니다.
sourceDateStart 속성 주석에서 소스 리소스를 해석할 구간의 시작 타임스탬프.
각 TimeState당 sourceDateStart는 정확히 1개 있을 수 있음. MUST xsd:dateTime 형태이고 UTC 타임존(“Z”)을 사용. sourceDateStart가 있으면 sourceDateEnd도 반드시 함께 있어야 함.
sourceDateEnd 속성 주석에서 소스 리소스를 해석할 구간의 종료 타임스탬프.
각 TimeState당 sourceDateEnd는 정확히 1개 있을 수 있음. MUST xsd:dateTime 형태이고 UTC 타임존(“Z”)을 사용. sourceDateEnd가 있으면 sourceDateStart도 반드시 함께 있어야 함.
cached 관계 주석에 적합한 소스 리소스의 표현 복사본 링크.
TimeState마다 cached 관계가 0개 이상 있을 수 MAY 있습니다. 여러 개면 각각 대체 복사본을 의미함.

예시

예시 31: 시간 상태
{
  "@context": "http://www.w3.org/ns/anno.jsonld",
  "id": "http://example.org/anno31",
  "type": "Annotation",
  "body": "http://example.org/note1",
  "target": {
    "source": "http://example.org/page1",
    "state": {
      "type": "TimeState",
      "cached": "http://archive.example.org/copy1",
      "sourceDate": "2015-07-20T13:30:00Z"
    }
  }
}

4.3.2 요청 헤더 상태

리소스 하나의 IRI로도 다양한 표현을 제공할 수 있어, SpecificResource는 그 중 하나에만 적용될 수도 있습니다. 올바른 표현을 가져오기 위해 어떤 HTTP 요청 헤더가 필요했는지 기록할 수 있는 것이 중요합니다. HttpRequestState 리소스는 표현을 얻을 때 재생할 요청 헤더의 복사본을 저장합니다.

예시 활용 사례: Devina는 HTML, PDF, 평문 텍스트 등 다양한 표현을 제공하는 웹 리소스에서 PDF 표현을 받아 그에 대한 설명을 작성합니다. 그녀는 자신의 설명이 PDF에만 해당된다고 명시하며, 클라이언트는 대상을 얻는 방법을 설명하는 상태를 추가합니다.

모델

용어 유형 설명
type 관계 상태의 클래스.
Request Header State는 반드시 하나의 type만을 가져야 하며, 그 값은 HttpRequestState여야 함.
HttpRequestState 클래스 주석을 위한 소스 리소스의 적합한 표현을 HTTP 요청 헤더로 지정하여 가져올 수 있도록 설명하는 클래스입니다.
상태는 반드시 이 클래스를 연관시켜야 함.
value 속성 요청 시 전송해야 할 HTTP 요청 헤더 전체.
HttpRequestState에는 정확히 하나의 value 속성이 있어야 함.
참고
최초 주석자의 클라이언트가 서버에서 표현을 얻을 때, 요청 헤더만으로 완전히 표현이 결정되지 않을 수도 있습니다. 예를 들어, 클라이언트 IP주소가 사용자가 위치한 국가의 언어를 근거로 표현을 판단할 수 있습니다. 서버가 Content-Location 헤더를 반환한다면 클라이언트는 주석의 target으로 요청 IRI 대신 해당 값을 사용할 수도 있습니다.

예시

예시 32: HTTP 요청 상태
{
  "@context": "http://www.w3.org/ns/anno.jsonld",
  "id": "http://example.org/anno32",
  "type": "Annotation",
  "body": "http://example.org/description1",
  "target": {
    "source": "http://example.org/resource1",
    "state": {
      "type": "HttpRequestState",
      "value": "Accept: application/pdf"
    }
  }
}

4.3.3 상태 정밀화

선택 정밀화와 마찬가지로, 리소스의 적합한 상태를 원자적 상태 리소스 계층구조로 지정하는 것이 더 쉽거나, 신뢰성이 높거나, 더 정확할 수 있습니다. 내부 변환과 외부 요청 결과가 조합된 상태 표현 등에 특히 적합합니다. 이런 분해는 여러 상태가 Selector처럼 체인 형태로 연결되는 방식으로 달성됩니다.

또한 상태 적용 결과 특정 표현이 된다면, 그 표현의 특정 세그먼트를 기술하기 위해 적합한 Selector가 존재할 수 있습니다. 이를 위해 States는 Selector로 정밀화될 수도 있습니다.

예시 활용 사례: Erin은 시간이 흐름에 따라 여러 버전과 다양한 포맷이 제공되는 여행 e-book에 대해, 특정 버전·포맷에 관한 의견을 남기고자 합니다. 그녀의 클라이언트는 시간 정보를 캡처하는 TimeState, 포맷 정보를 캡처하는 HttpRequestState, 그 포맷에 해당하는 FragmentSelector 모두를 추가합니다.

모델

용어 유형 설명
refinedBy 관계 더 넓은 State와 그 결과에 적용해야 하는 더 구체적 State 또는 Selector 간의 관계.
각 State는 1개 이상의 다른 State 또는 Selector로 refinedBy될 수 있으며 MAY, 여러 개일 경우 이는 동일한 결과로 간주합니다.

예시

예시 33: 상태 정밀화
{
  "@context": "http://www.w3.org/ns/anno.jsonld",
  "id": "http://example.org/anno33",
  "type": "Annotation",
  "body": "http://example.org/comment1",
  "target": {
    "source": "http://example.org/ebook1",
    "state": {
      "type": "TimeState",
      "sourceDate": "2016-02-01T12:05:23Z",
      "refinedBy": {
        "type": "HttpRequestState",
        "value": "Accept: application/pdf",
        "refinedBy": {
          "type": "FragmentSelector",
          "value": "page=10",
          "conformsTo": "http://tools.ietf.org/rfc/rfc3778"
        }
      }
    }
  }
}

4.4 스타일

특정 주석이나 주석의 본문 해석이, 주석의 렌더링 스타일이 구현체 간에 일관성을 유지하는 것에 의존할 수 있습니다. 이미지나 비디오 같은 바이너리 콘텐츠에 대한 주석에서는 대상의 배경색을 주석 클라이언트가 접근하지 못할 수도 있고, 기본 색상이 예를 들어 밤하늘 사진에서 검은 사각형처럼 인식하기 어려울 수 있습니다. 렌더링 정보는 CSS 스타일시트와 그 스타일시트에 정의된 클래스 참조를 통해 기록합니다.

예시 활용 사례: Felicity는 문서 내 두 단락을 하이라이트하고, 각각 빨강, 노랑으로 표시되도록 클라이언트에서 선택합니다. 그리고 노란색 부분이 빨간 부분과 모순된다고 코멘트합니다. 클라이언트는 빨강/노랑 색상 지정 선택 사실을 기록합니다.

모델

용어 유형 설명
type 관계 스타일의 클래스.
CSS 스타일시트는 가질 수 있으며 값으로 CssStylesheet가 와야 합니다.
CssStylesheet 클래스 주석에 참여하는 리소스들의 스타일을 CSS로 기술하는 리소스.
이 클래스는 스타일시트 리소스에 연관될 수 있습니다.
stylesheet 관계 주석과 스타일 간의 관계.
각 주석당 stylesheet 관계가 0개 또는 1개 있을 수 있습니다.
styleClass 속성 Specific Resource에 적용되어야 하는 CSS 설명 내 클래스 이름.
Specific Resource에는 0개 이상 styleClass 속성을 가질 수 있습니다.

CSS 스타일시트는 주석 자체와 연관되며, 그 내용이 주석의 구성 리소스에 대한 렌더링 힌트를 제공합니다. 정보 제공용으로 별도의 dereferenceable IRI를 가질 수도, 주석 내에 임베드될 수도 있습니다. 이는 각 리소스별로 한 줄짜리 스타일시트를 두는 것을 방지하고, 특정 구현이 사용하는 전체 스타일 모음을 하나의 IRI로 참조 가능하게 하기 위함입니다.

퍼블리싱 시스템은 스타일시트가 실제로 처리된다고 가정해서는 안 되며, 스타일은 요구사항이 아니라 힌트입니다.

Specific Resource를 렌더링할 때, 소비 애플리케이션은 styleClass 속성이 있는지 확인해야 하며, 있다면 해당 CSS 문서에서 적합한 selector를 찾아 css-value 블록을 적용해야 합니다. styleClass 값이 있는데, 주석에 연결된 stylesheet에 해당 클래스 정의가 없다면 styleClass는 무시해야 합니다.

예시

예시 34: CSS 스타일 
{
  "@context": "http://www.w3.org/ns/anno.jsonld",
  "id": "http://example.org/anno34",
  "type": "Annotation",
  "stylesheet": "http://example.org/style1",
  "body": "http://example.org/comment1",
  "target": {
    "source": "http://example.org/document1",
    "styleClass": "red"
  }
}
예시 35: CSS 스타일, 임베디드
{
  "@context": "http://www.w3.org/ns/anno.jsonld",
  "id": "http://example.org/anno35",
  "type": "Annotation",
  "stylesheet": {
    "type": "CssStylesheet",
    "value": ".red { color: red }"
  },
  "body": "http://example.org/body1",
  "target": {
    "source": "http://example.org/target1",
    "styleClass": "red"
  }
}

4.5 렌더링 소프트웨어

주석을 만들 때 Target 리소스를 처리 및 렌더링할 때 사용된 소프트웨어를 아는 것은 가치가 있을 수 있습니다. 이런 정보는 나중에 시스템들이 그 환경을 재구성해서, 주석이 Target의 적절한 표현부와 더 쉽게 정확하게 다시 연결될 수 있도록 할 수 있습니다. 이러한 라이프사이클 정보는 Specific Resource와 연관되는데, 동일한 Target에 대한 여러 주석마다 다를 가능성이 크기 때문에 Target과 직접 연결할 수 없습니다.

예시 활용 사례: Gabrielle은 브라우저 기반 클라이언트로 학술 논문의 PDF를 렌더링합니다. 그녀의 브라우저는 특정 라이브러리를 사용해 PDF를 HTML로 렌더링합니다. 그녀는 자신이 보는 HTML 렌더링의 단락에 주석을 달고, 클라이언트는 렌더링에 사용된 라이브러리, 코멘트, 그리고 대상 PDF를 주석에 기록합니다.

모델

용어 유형 설명
renderedVia 관계 주석 내 Target을 나타내는 Specific Resource와, 주석 작성 시 Target 렌더링에 사용된 소프트웨어 혹은 시스템 간의 관계.
각 Specific Resource에 renderedVia가 0개 이상 있을 수 있습니다.
참고
렌더링 시스템에는 schema:softwareVersion, 접근성 기능, 레이블, 실제 코드 참조 등 다양한 속성이 추가될 수 있습니다. 이런 확장은 본 명세 범위를 벗어나지만 자세한 정보는 [annotation-vocab]의 확장(Extensions) 절을 참고하세요.

예시

예시 36: 렌더링 소프트웨어
{
  "@context": "http://www.w3.org/ns/anno.jsonld",
  "id": "http://example.org/anno36",
  "type": "Annotation",
  "body": "http://example.org/comment1",
  "target": {
    "source": "http://example.edu/article.pdf",
    "selector": "http://example.org/selectors/html-selector1",
    "renderedVia": {
      "id": "http://example.com/pdf-to-html-library",
      "type": "Software",
      "schema:softwareVersion": "2.5"
    }
  }
}

4.6 리소스의 범위

주석이 작성된 맥락, 즉 주석자가 당시 보고 있던 리소스들을 포착하는 것이 중요한 경우가 있습니다. 이는 주석이 이미지가 그 페이지 컨텍스트에 있을 때만 유효함을 주장하는 것이 아니라, 단지 그 페이지가 보여지고 있었음을 기록하는 것에 불과합니다.

예시 활용 사례: Heather는 특정 웹페이지에서 이미지가 잘못된 조직의 로고임을 지적하는 코멘트를 남깁니다. 그녀의 클라이언트는 이미지가 렌더링된 페이지를 포함하지만, 주석은 이미지 리소스 자체와 연관됩니다.

모델

용어 유형 설명
scope 관계 Specific Resource와, 이 Annotation에서 그 범위 또는 맥락을 제공하는 리소스 간의 관계.
각 Specific Resource에 scope 관계가 0개 이상 있을 수 있습니다.

예시

5. 컬렉션

주석들을 하나의 목록(주석 컬렉션)으로 모으는 것이 유용할 때가 많습니다. 이 목록은 항상 순서가 있으며, 그 안에 포함된 주석들을 참조하거나 컬렉션 자체에 관한 정보를 관리하는 수단이 됩니다.

컬렉션 모델은 두 부분으로 나눠집니다. 컬렉션 자체의 정체성과 설명을 관리하는 주석 컬렉션, 그리고 그 컬렉션 소속 주석들을 나열하는 주석 페이지입니다.

예시 활용 사례: Ingeborg는 출판사 소속으로, 저자의 스팀펑크 소설에 대한 코멘터리를 주석 세트로 변환하여 판매용으로 만들었습니다. 회사는 기존에 소설을 구입한 고객을 위한 애드온, 그리고 신규 판매용 번들로 제공하기를 원합니다.

5.1 주석 컬렉션

주석 컬렉션이 매우 커질 수 있으므로, 모델은 컬렉션 자체와, 내부에 주석들을 나열하는 컴포넌트 페이지 시퀀스를 구분합니다. 컬렉션은 자신에 대한 생성/설명 등 검색 및 이해를 돕는 정보를 유지하며, 최소한 첫 번째 주석 페이지에 대한 참조도 가집니다. 첫 페이지의 첫 주석부터 시작해, 각 페이지를 따라 마지막 주석까지 순회하면 컬렉션 내의 모든 주석을 발견할 수 있습니다.

주석들은 동시에 여러 컬렉션에 포함될 수 있으며, 컬렉션은 포함된 주석의 생성/유지자와 별개인 에이전트가 새로 만들거나 유지할 수도 있습니다.

모델

용어 유형 설명
@context 속성 JSON이 주석 컬렉션임을 결정하는 컨텍스트.
컬렉션은 반드시 1개 이상의 @context 값을 가지며, http://www.w3.org/ns/anno.jsonld가 그중 하나여야 합니다.
id 속성 컬렉션의 식별자.
컬렉션은 반드시 정확히 1개의 IRI로 식별되어야 합니다.
type 속성 컬렉션의 타입.
컬렉션은 1개 이상 타입을 가지며, AnnotationCollection 클래스가 그 중 하나여야 합니다.
AnnotationCollection 클래스 주석이 순서대로 모인 컬렉션의 클래스.
이 클래스는 반드시 type을 통해 컬렉션에 연관되어야 합니다.
label 속성 컬렉션의 이름에 해당하는 사람이 읽는 레이블.
컬렉션은 1개 이상의 label을 가져야 하며, 값은 반드시 문자열이어야 합니다.
total 속성 컬렉션 내 주석의 총 수.
컬렉션은 정확히 1개의 total을 가지는 것이 바람직하며, 존재한다면 값은 반드시 xsd:nonNegativeInteger여야 합니다.
first 관계 컬렉션에 포함된 주석의 첫 번째 페이지.
주석이 1개 이상이면 반드시 첫 페이지에 대한 1개 first 참조를 가져야 하며, 이는 컬렉션 내에 임베드되어도, 별도 IRI로 주어져도 됩니다.
last 관계 컬렉션에 포함된 주석의 마지막 페이지.
주석이 1개 이상이면 가능하다면 마지막 페이지의 IRI를 last로 참조하는 것이 바람직합니다.

5.2 주석 페이지

주석 페이지는 주석 컬렉션의 일부이며, 컬렉션 내 일부 또는 전체 주석을 순서대로 나열합니다. 각 컬렉션은 여러 페이지를 가질 수 있으며, 각 페이지 사이를 next와 prev 링크로 이동합니다.

모델

용어 유형 설명
@context 속성 JSON이 주석 컬렉션 페이지임을 결정하는 컨텍스트.
페이지가 컬렉션 내에 임베드되어 있지 않으면 반드시 1개 이상의 @context를 가지며, http://www.w3.org/ns/anno.jsonld가 그중 하나여야 합니다. 임베드된 경우 @context 속성이 포함되지 않아야 합니다.
id 속성 페이지의 식별자.
페이지는 반드시 1개의 IRI로만 식별되어야 합니다.
type 속성 페이지의 타입.
페이지는 1개 이상 타입을 가져야 하며, AnnotationPage 클래스가 그 중 하나여야 합니다.
AnnotationPage 클래스 주석 페이지의 클래스.
이 클래스는 반드시 type을 통해 페이지와 연관되어야 합니다.
partOf 관계 페이지와, 페이지가 속한 주석 컬렉션 간의 관계.
각 페이지는 정확히 1개 partOf 관계를 가져야 하며, 값은 컬렉션의 IRI 또는 최소 id를 포함한 컬렉션 객체이어야 합니다.
items 관계 페이지에 속하는 주석들의 목록.
각 페이지는 반드시 1개 이상의 주석을 items의 배열 값으로 가져야 합니다.
next 관계 컬렉션을 구성하는 페이지 시퀀스에서 다음 페이지에 대한 참조.
해당 페이지가 컬렉션의 마지막이 아니면 현재 페이지는 반드시 다음 페이지의 IRI를 참조해야 합니다.
prev 관계 컬렉션을 구성하는 페이지 시퀀스에서 이전 페이지에 대한 참조.
해당 페이지가 첫 페이지가 아니면 되도록 이전 페이지의 IRI를 참조하는 것이 좋습니다.
startIndex 속성 items 목록에서 첫 주석이 컬렉션 전체 기준으로 몇 번쨰인지.
첫 페이지 첫 엔트리는 0.
각 페이지는 정확히 1개의 startIndex만을 가져야 하며, 1개 초과는 금지. 값은 xsd:nonNegativeInteger여야 합니다.

D. Body 및 Target 집합

이 부분은 규범적이지 않은 섹션입니다.

여러 target에 대한 주석을 달 수 있지만, 그 의미는 각각의 body가 각 target에 독립적으로 적용된다는 것입니다. 이는 주석자가 의도한 바와 다를 수 있으며, 예를 들어 모든 target이 있어야 주석이 올바르게 이해되는 경우가 그렇습니다. 이런 요구를 표현할 수 있도록 Choice와 유사한 리소스, Composite(순서 없음) 또는 List(순서 있음)를 사용할 수 있습니다.

이 패턴의 기술적 구현은 Choice와 거의 동일하므로 어렵지 않습니다. 하지만 사용자 인터페이스 관점에서 사람의 상호작용을 관리하여 클라이언트가 그 차이를 구분할 수 있도록 하는 부분은 매우 도전적인 과제로 확인되었습니다. 따라서 이 패턴은 부록에 참고용으로만 소개합니다.

예시 활용 사례: Karin은 여러 웹페이지를 함께 볼 때 연구 가설에 대한 증거로 작용한다고 논평합니다. 클라이언트는 웹페이지 집합에 고유한 순서가 없으므로 Composite을 생성합니다.

예시 활용 사례: Lana는 책의 여러 페이지에 중요하다는 태그를 답니다. 책의 페이지에는 순서가 있으므로, 그녀의 클라이언트는 List로 그 순서를 유지합니다.

예시 활용 사례: Melanie는 여러 이미지를 초상화로 분류하는 주석을 답니다. 분류는 각 이미지에 독립적으로 적용되므로, 클라이언트는 이들을 그룹화하는 Independents 리소스를 만듭니다.

용어 타입 설명
id 속성 집합을 식별하는 IRI.
집합 리소스는 MAY 정확히 1개의 IRI를 가질 수 있습니다.
type 관계 리소스 타입.
집합은 MUST 아래 옵션 중 하나 타입을 정확히 1개 가져야 합니다.
Composite 클래스 주석이 올바르게 해석되려면 모두 필요한 리소스 집합.
List 클래스 주석이 올바르게 해석되려면 모두 필요한, 순서가 있는 리소스 목록.
Independents 클래스 각 리소스가 별도의 body나 target을 가지는 효과로, 각각 독립적으로 동일 해석을 갖는 집합.
items 관계 Composite, List, Independents 내 리소스 목록.

예제

Example 42: Composite
{
  "@context": "http://www.w3.org/ns/anno.jsonld",
  "id": "http://example.org/anno39",
  "type": "Annotation",
  "motivation": "commenting",
  "body": {
    "type": "TextualBody",
    "value": "These pages together provide evidence of the conspiracy"
  },
  "target": {
    "type": "Composite",
    "items": [
      "http://example.com/page1",
      "http://example.org/page6",
      "http://example.net/page4"
    ]
  }
}
Example 43: List 
{
  "@context": "http://www.w3.org/ns/anno.jsonld",
  "id": "http://example.org/anno40",
  "type": "Annotation",
  "motivation": "tagging",
  "body": {
    "type": "TextualBody",
    "value": "important"
  },
  "target": {
    "type": "List",
    "items": [
      "http://example.com/book/page1",
      "http://example.com/book/page2",
      "http://example.com/book/page3",
      "http://example.com/book/page4"
    ]
  }
}
Example 44: Independents
{
  "@context": "http://www.w3.org/ns/anno.jsonld",
  "id": "http://example.org/anno41",
  "type": "Annotation",
  "motivation": "classifying",
  "body": "http://example.org/vocab/art/portrait",
  "target": {
    "type": "Independents",
    "items": [
      "http://example.com/image1",

G.6 Open Annotation 초안 대비 주요 변경점

Open Annotation Community Group's draft에서 본 명세의 주요 기술적 변경은 다음과 같습니다:

  • JSON-LD 키에 직관적이고 기억하기 쉬운, 개발자 친화적인 이름 사용 (text)

  • bodyText를 통한 본문에 문자열 리터럴 허용 (text)
  • Choice에서 옵션의 순서 있는 목록 허용 (text)
  • 리소스의 권리 정보(rights information)와 대상 청중(intended audience) 등 핵심 라이프사이클 메타데이터 추가 (text)
  • 동등 식별성, 외부 표준과 정렬 (text)
  • Body/Target별로 Motivation 역할/목적 부여 허용, Tag, Semantic Tag와의 정렬 (text)
  • 구현 경험에서 CSS Selector, XPath Selector, Range Selector 도입
  • 복수 지정자는 리소스가 아니라 구조로 표현 (text)
  • 렌더링 소프트웨어 기술 기능 추가 (text)
  • 정의된 패턴으로 주석 컬렉션 추가 (Collections of Annotations)
  • 온톨로지를 모델‧JSON 직렬화와 분리([annotation-vocab])
  • 모델에서 임베디드 그래프 비권장, 대신 직렬화된 그래프를 포함/참조
