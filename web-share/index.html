요약

이 명세서는 텍스트, 링크 및 기타 콘텐츠를 사용자가 선택한 임의의 대상에 공유하기 위한 API를 정의합니다.

사용 가능한 공유 대상은 이 문서에서 명시하지 않으며, 사용자 에이전트가 제공합니다. 예를 들어 앱, 웹사이트 또는 연락처일 수 있습니다.

콘텐츠 공유 기능은 종종 기본 운영체제가 "공유" 기능을 제공하는지와 OS UI 관례에 따라 달라집니다. 예를 들어, 일부 운영체제는 "공유 시트"를 제공하고, 다른 운영체제는 팝업 메뉴를 사용합니다. 이러한 의존성으로 인해 Web Share API를 모든 OS에 적용하기 위한 구현자들의 작업이 진행 중입니다. 이 진행 상황은 구현 보고서의 실패 사례로 나타나며, 해당 보고서는 제한된 OS에서 테스트를 수행하여 생성됩니다. 그러나 워킹 그룹은 Web Share API가 시간이 지남에 따라 모든 OS에서 더 널리 사용될 것으로 낙관하고 있으며, 이미 다양한 기기의 인기 OS에서 널리 사용되고 있습니다.

1. 사용 예시

이 섹션은 비규범적입니다.

1.1 텍스트와 링크 공유

이 예시는 기본적인 공유 동작을 보여줍니다. 버튼 클릭에 응답하여 이 JavaScript 코드는 현재 페이지의 URL을 공유합니다.

예시 1: 텍스트와 URL 공유 
shareButton.addEventListener("click", async () => {
  try {
    await navigator.share({ title: "Example Page", url: "" });
    console.log("Data was shared successfully");
  } catch (err) {
    console.error("Share failed:", err.message);
  }
});

url이 ''일 경우, 이는 링크에서처럼 현재 페이지의 URL을 의미합니다. 다른 절대 또는 상대 URL도 사용할 수 있습니다.

share()를 호출하면, 사용자 에이전트가 선택기 또는 대화상자를 표시하여 사용자가 제목과 페이지 URL을 공유할 대상을 선택할 수 있도록 합니다.

1.2 파일 공유

이 예시는 파일을 공유하는 방법을 보여줍니다. files 멤버는 배열이므로 여러 파일을 공유할 수 있습니다.

예시 2: 파일 공유 
shareButton.addEventListener("click", async () => {
  const file = new File(data, "some.png", { type: "image/png" });
  try {
    await navigator.share({
      title: "Example File",
      files: [file]
    });
  } catch (err) {
    console.error("Share failed:", err.message);
  }
});

1.3 공유 유효성 검사

canShare() 메서드를 ShareData 딕셔너리와 함께 호출하면 공유 데이터의 유효성 검증을 수행합니다. share()와 달리, 일시적 활성화 없이 호출할 수 있습니다.

예시 3 
const file = new File([], "some.png", { type: "image/png" });

// 파일 지원 여부 확인
if (navigates.canShare({files: [file]})) {
  // png 파일 공유가 가능할 수 있습니다...
}

// 공유 가능한 URL인지 확인
if (navigates.canShare({ url: someURL })) {
  // URL이 유효하며 공유가 가능할 수 있습니다...
}

1.4 멤버 지원 여부 확인

WebIDL 딕셔너리 동작 특성상, 사용자 에이전트가 인식하지 못하는 멤버가 share()에 전달되면 무시됩니다. 여러 멤버를 공유할 때 사용자 에이전트가 일부 멤버를 지원하지 않을 경우 문제가 될 수 있습니다. 전달하는 모든 멤버가 지원되는지 확실히 하려면 각 멤버를 개별적으로 canShare()로 확인할 수 있습니다.

예시 4: 미래 호환 공유 
const data = {
  title: "Example Page",
  url: "https://example.com",
  text: "This is a text to share",
  someFutureThing: "some future thing",
};
const allSupported = Object.entries(data).every(([key, value]) => {
  return navigator.canShare({ [key]: value });
});
if (allSupported) {
  await navigator.share(data);
}

또는, 지원되지 않는 멤버에 대해 UI 컴포넌트를 표시하지 않도록 애플리케이션 UI를 조정할 수 있습니다.

예시 5: 지원되지 않는 멤버 필터링 
const data = {
  title: "Example Page",
  url: "https://example.com",
  text: "This is a text to share",
  someFutureThing: "some future thing",
};

// 지원되지 않는 멤버들
const unsupported = Object.entries(data).filter(([key, value]) => {
  return !navigator.canShare({ [key]: value });
});

1.5 서드파티 컨텍스트에서 API 활성화

기본 허용 목록이 'self'로 되어 있어 Web Share API는 기본적으로 퍼스트파티 컨텍스트에서만 사용할 수 있습니다.

서드파티에서는 iframe의 allow 속성으로 API 사용을 허용할 수 있습니다:

예시 6: 서드파티 컨텍스트에서 web-share API 활성화 
<iframe
  src="https://third-party.example"
  allow="web-share">
</iframe>

또는, 퍼스트파티 컨텍스트에서 HTTP 응답 헤더를 지정하여 API를 비활성화할 수 있습니다:

예시 7: Permissions Policy로 Web Share API 비활성화 
Permissions-Policy: web-share=()

자세한 내용과 출처별 권한 정책 제어 방법은 Permissions Policy 명세서를 참고하세요.

2. API 정의

2.1 Navigator 인터페이스 확장 

WebIDLpartial interface Navigator {
  [SecureContext] Promise<undefined> share(optional ShareData data = {});
  [SecureContext] boolean canShare(optional ShareData data = {});
};

2.1.1 내부 슬롯

이 API는 Navigator 인터페이스에 다음 내부 슬롯을 추가합니다.

Promise? [[sharePromise]]
this.[[sharePromise]]는 사용자가 일부 데이터를 공유 대상에 공유하려는 현재 의도를 나타내는 promise입니다. 처음에는 null로 초기화됩니다.

2.1.2 share() 메서드

share() 메서드가 인수 data와 함께 호출되면, 다음의 보안 영향을 고려하면서 아래에 나열된 단계를 실행합니다.

Web Share를 사용하면 웹사이트에서 공유 대상으로 데이터를 전송할 수 있으며, 공유 대상은 네이티브 애플리케이션일 수 있습니다. 이러한 기능은 Web Share에만 고유한 것은 아니지만, 심각도가 달라질 수 있는 여러 잠재적 보안 위험이 수반됩니다(기반 플랫폼에 따라 달라집니다).

share()에 전달된 데이터는 공유를 수신하는 공유 대상의 버퍼 오버플로 또는 기타 원격 코드 실행 취약점을 악용하는 데 사용될 수 있습니다. 이에 대해 보호할 수 있는 일반적인 방법은 없지만, 구현자는 이러한 가능성이 있다는 점을 인지해야 합니다(특히 파일을 공유할 때).

공유된 URL을 역참조하고 해당 정보를 전달하는 공유 대상은 다른 경우라면 기밀일 수 있는 정보를 의도치 않게 전달할 수 있습니다. 공유가 해당 애플리케이션, 애플리케이션이 실행되는 호스트 또는 그 네트워크 위치에서만 접근할 수 있는 콘텐츠를 참조하는 경우, 예상치 못한 정보 유출로 이어질 수 있습니다.

악성 사이트는 최종적으로 로컬 리소스로 확인되는 URL을 제공하여 정보를 유출하는 공유 대상을 악용할 수 있으며, 여기에는 "file:" URL 또는 다른 방법으로는 접근할 수 없는 로컬 서비스 등이 포함되지만 이에 한정되지는 않습니다. 이 API가 공유할 수 있는 URLS를 제한된 공유 가능 스킴 집합으로 제한하더라도, 다른 URL로의 리디렉션 또는 이러한 URL에 포함된 호스트의 DNS 레코드 변경을 사용하여 애플리케이션이 콘텐츠를 가져오도록 만들 수 있습니다.

이러한 공격에 이용되는 것을 방지하기 위해, 공유 대상은 URL을 사용하고 콘텐츠를 가져온 다음 해당 정보를 공유하지 않은 채 처리할 수 있습니다. 예를 들어, 사진 편집 애플리케이션은 자신과 "공유된" 이미지를 가져올 수 있습니다. 공유 대상은 참조된 콘텐츠를 가져오지 않고 URL 자체를 공유할 수도 있습니다.

미리 보기를 제공하거나 콘텐츠를 공유하기 위해 콘텐츠를 가져오는 공유 대상에는 정보 유출 위험이 있습니다. 사용자가 미리 보고 승인한 콘텐츠는 전달해도 안전할 수 있지만, 정보가 언제 기밀이어야 하는지를 사람이 항상 식별할 수 있는 것은 아니므로 어떤 콘텐츠든 전달하는 것은 위험을 수반합니다. 특히, title은 공격자가 사용자를 속여 콘텐츠의 성격을 잘못 해석하게 만드는 데 사용될 수 있습니다(5. 접근성 고려 사항도 참조하십시오).

DOMException을 사용하는 다른 경우와 마찬가지로, 구현자는 share()가 거부될 때 오류 메시지에서 어떤 정보가 노출되는지를 신중하게 고려해야 합니다. 사용 가능한 공유 대상이 없는 경우와 사용자가 취소한 경우를 구분하는 것만으로도 사용자의 기기에 어떤 공유 대상이 설치되어 있는지에 관한 정보가 노출될 수 있습니다.

  1. global을 this의 관련 전역 객체로 둡니다.
  2. document를 global의 연결된 Document로 둡니다.
  3. document가 완전히 활성 상태가 아니면, "InvalidStateError" DOMException으로 거부된 프로미스를 반환합니다.
  4. document가 사용하도록 허용되지 않은 "web-share"인 경우, "NotAllowedError" DOMException으로 거부된 프로미스를 반환합니다.
  5. this.[[sharePromise]]이 null이 아니면, "InvalidStateError" DOMException으로 거부된 프로미스를 반환합니다.
  6. global에 일시적 활성화가 없으면, "NotAllowedError" DOMException으로 거부된 프로미스를 반환합니다.
  7. global의 사용자 활성화를 소비합니다.
  8. base를 this의 관련 설정 객체의 API 기본 URL로 둡니다.
  9. data와 base를 사용하여 공유 데이터 검증을 수행한 결과가 false를 반환하면, TypeError로 거부된 프로미스를 반환합니다.
  10. data의 url 멤버가 존재하는 경우:
    1. url을 data의 url에 대해 base를 사용하여 URL 파서를 실행한 결과로 둡니다.
    2. 단언: url은 URL입니다.
    3. data를 data의 복사본으로 설정하되, 그 url 멤버를 url에 대해 URL 직렬화기를 실행한 결과로 설정합니다.
  11. 보안상의 고려로 인해 파일 유형이 차단되고 있는 경우, "NotAllowedError" DOMException으로 거부된 프로미스를 반환합니다.
  12. this.[[sharePromise]]을 새 프로미스로 설정합니다.
  13. this.[[sharePromise]]을 반환하고 병렬로 다음을 수행합니다:
    1. 사용 가능한 공유 대상이 없으면, global을 사용하여 사용자 상호작용 태스크 소스에서 전역 태스크를 큐에 추가하여 다음을 수행합니다:
      1. this.[[sharePromise]]을 "AbortError" DOMException으로 거부합니다.
      2. this.[[sharePromise]]을 null로 설정합니다.
      3. 이 알고리즘을 종료합니다.
    2. 사용자에게 하나 이상의 공유 대상 중에서 선택할 수 있는 선택지와 작업을 중단할 수 있는 기능을 제공합니다. 이 UI 표면은 보안 확인 수단으로 작동하여 웹사이트가 네이티브 애플리케이션으로 데이터를 몰래 전송하지 못하도록 합니다. 사용자 에이전트는 OS 수준 UI가 이 기능을 제공하지 않는 경우, 사용자가 공유되는 콘텐츠를 확인할 수 있는 중간 UI를 제공하는 것이 좋습니다.
    3. 사용자의 선택을 기다립니다.
    4. 사용자가 공유 작업을 중단하기로 선택한 경우, global을 사용하여 사용자 상호작용 태스크 소스에서 전역 태스크를 큐에 추가하여 다음을 수행합니다:
      1. this.[[sharePromise]]을 "AbortError" DOMException으로 거부합니다,
      2. this.[[sharePromise]]을 null로 설정합니다.
      3. 이 알고리즘을 종료합니다.
    5. 선택한 공유 대상을 활성화하고, data를 대상에서 받아들이기에 적합한 형식으로 변환한 다음, 변환된 데이터를 대상에 전송합니다.
    6. 대상을 시작하거나 데이터를 전송하는 동안 오류가 발생하면, global을 사용하여 사용자 상호작용 태스크 소스에서 전역 태스크를 큐에 추가하여 다음을 수행합니다:
      1. this.[[sharePromise]]을 "DataError" DOMException으로 거부합니다.
      2. this.[[sharePromise]]을 null로 설정합니다.
      3. 이 알고리즘을 종료합니다.
    7. 데이터가 공유 대상에 성공적으로 전송되었거나, 공유 대상으로의 전송을 확인할 수 없는 경우 OS에 성공적으로 전송되면, global을 사용하여 사용자 상호작용 태스크 소스에서 전역 태스크를 큐에 추가하여 다음을 수행합니다:
      참고
      공유 대상에 페이로드가 전달되면 공유가 성공한 것으로 간주됩니다. 대상이 해당 데이터를 허용할 수 없다고 판단하거나 오류가 발생하면, 대상은 정상적으로 복구하거나 최종 사용자에게 오류 메시지를 표시할 수 있으며, 오류 처리를 송신자에게 의존할 수는 없습니다. 즉, share() 메서드는 "전송 후 잊기" 방식이며, 대상이 페이로드를 승인하거나 거부할 때까지 기다리지 않습니다.
      1. this.[[sharePromise]]을 undefined로 이행합니다.
      2. this.[[sharePromise]]을 null로 설정합니다.

2.1.3 canShare(data) 메서드

canShare() 메서드를 ShareData data 인자와 함께 호출하면, 다음 단계를 실행합니다:

  1. document를 this의 관련 전역 객체의 연결된 Document로 둡니다.
  2. document가 완전히 활성 상태가 아니면, false를 반환합니다.
  3. document가 사용하도록 허용되지 않은 "web-share"인 경우, false를 반환합니다.
  4. data와 this의 관련 설정 객체의 API 기본 URL을 사용하여 공유 데이터 검증을 수행한 결과를 반환합니다.
참고: canShare()는 미래 호환성이 없습니다

Web Share API의 canShare() 메서드는 ShareData 딕셔너리에 정의되지 않은 멤버가 포함된 객체로 사용할 때 false positive 결과를 반환할 수 있습니다. WebIDL 동작 특성상, 브라우저는 입력 객체에서 알 수 없는 멤버를 제거하고 남은 멤버만 테스트하여 true를 반환합니다. 이 동작은 미래 호환성이 없습니다.

공유 가능성 테스트의 신뢰성을 높이려면, 개발자는 ShareData 딕셔너리에 정의된 멤버만 사용하여 입력 객체를 생성해야 합니다. 추가 멤버가 있는 경우에는 객체를 분해해 정의된 멤버만 개별적으로 테스트해야 합니다.

현재 구현에는 영향을 미치지 않지만, 워킹 그룹은 향후 명세 개정에서 이 문제를 해결할 예정입니다. ShareData 딕셔너리에 수정이 있을 경우 특히 그렇습니다. 이 이슈 해결에 대한 아이디어를 기여하려면 GitHub 이슈 #108을 참고하세요.

2.1.4 공유 데이터 유효성 검사

공유 가능한 스킴(sharable scheme)은 다음 URL 스킴 중 하나입니다:

  • http
  • https
  • 사용자 에이전트가 공유 목적으로 지원하는 허용된(safelisted) 스킴

data와 base로 공유 데이터 유효성 검사(validate share data)를 하려면, 다음 단계를 실행합니다:

  1. data의 title, text, url 또는 files 멤버 중 아무것도 없으면, false를 반환합니다.
  2. title, text, url 중 하나라도 있으면 titleTextOrUrl을 true로 설정합니다.
  3. data의 files 멤버가 있으면:
    1. titleTextOrUrl이 false이고, data의 files가 빈 배열이면 false를 반환합니다.
      참고

      { files: [] } 딕셔너리는 빈 딕셔너리로 처리됩니다. 하지만 {text: "text", files: []}와 같이 전달하면 files는 무시되므로 괜찮습니다.

    2. 구현이 파일 공유를 지원하지 않으면 false를 반환합니다.
    3. 사용자 에이전트가 files의 파일 중 하나라도 잠재적으로 악성 공유(예: 내용, 크기, 기타 특성상 악성으로 판단)로 간주하면 false를 반환합니다.
  4. data의 url 멤버가 있으면:
    1. url을 data의 url 멤버에 base를 사용하여 URL 파서를 실행한 결과로 설정합니다(인코딩 오버라이드 없음).
    2. url이 실패면 false를 반환합니다.
    3. url의 스킴이 로컬 스킴이거나, file, javascript, ws, wss이면 false를 반환합니다.
    4. url의 스킴이 공유 가능한 스킴이 아니면 false를 반환합니다.
  5. true를 반환합니다.

2.2 ShareData 딕셔너리 

WebIDLdictionary ShareData {
  sequence<File> files;
  USVString title;
  USVString text;
  USVString url;
};

ShareData 딕셔너리는 여러 개의 선택적 멤버로 구성됩니다:

files 멤버
공유할 파일들입니다.
text 멤버
공유되는 메시지의 본문이 되는 임의의 텍스트입니다.
title 멤버
공유되는 문서의 제목입니다. 대상에 따라 무시될 수 있습니다.
url 멤버
공유되는 리소스를 참조하는 URL 문자열입니다.
참고
이 멤버들은 USVString(DOMString과는 다름) 타입입니다. 이는 서러게이트 코드 포인트를 포함할 수 없음을 의미합니다. 이로 인해 사용자 에이전트는 UTF-8 등 어떤 유니코드 인코딩으로도 변경이나 데이터 손실, 대체 문자 생성 없이 직렬화할 수 있습니다.

3. 공유 대상

공유 대상은 사용자 에이전트가 공유 데이터를 전송할 추상적인 목적지 개념입니다. 공유 대상의 정의는 사용자 에이전트의 재량에 따릅니다.

공유 대상은 ShareData를 직접 받아들일 수 없을 수도 있습니다(이 API를 고려하지 않고 작성된 경우). 하지만 반드시 MUST ShareData에 노출된 일부 또는 전체 개념에 대응하는 데이터를 받을 수 있어야 합니다. 공유 대상에 적합한 형식으로 데이터 변환을 하려면, 사용자 에이전트는 SHOULD ShareData의 멤버를 대상의 동등 개념에 매핑해야 하며, 필요하면 멤버를 버리거나 합칠 수도 있습니다 MAY. 페이로드 각 멤버의 의미는 공유 대상의 재량입니다.

참고
ShareData를 공유 대상(또는 운영 체제)의 네이티브 형식에 매핑하는 것은 일부 플랫폼에 동등한 멤버 집합이 없을 수 있으므로 까다로울 수 있습니다. 예를 들어, 대상에 "text" 멤버는 있지만 "URL" 멤버는 없는 경우(Android가 이에 해당함), 한 가지 해결 방법은 text 및 url 멤버를 ShareData에서 모두 연결하고 그 결과를 대상의 "text" 멤버로 전달하는 것입니다.

각 공유 대상은 전달받는 ShareData 페이로드에 따라 조건부로 사용 가능해질 수 있습니다 MAY. 이 페이로드는 share() 메서드에 전달됩니다.

3.1 공유 대상 예시

이 섹션은 비규범적입니다.

공유 대상 목록은 사용자 에이전트와 호스트 운영체제에 따라 다양한 출처에서 채워질 수 있습니다. 예를 들면:

  • 내장 서비스(예: "클립보드로 복사").
  • 호스트 운영체제용으로 작성된 네이티브 애플리케이션.
  • 연락처(예: 사용자 에이전트가 주소록에 있는 특정 앱을 통해 사람에게 직접 공유).
  • 웹사이트(예: 사용자 에이전트가 ShareData의 멤버로 템플릿 URL을 채우고 새 브라우징 컨텍스트로 이동).
참고
마지막 경우를 위해 웹사이트가 공유 데이터를 받을 수 있도록 등록하는 표준화 시도도 있습니다. 자세한 내용은 Web Share Target을 참고하세요.

일부 경우에는 호스트 운영체제가 Web Share와 유사한 공유 또는 인텐트 시스템을 제공합니다. 이때는 사용자 에이전트가 공유 데이터를 운영체제에 바로 전달하고 네이티브 앱과 직접 통신하지 않을 수 있습니다.

4. Permissions Policy 통합

이 명세서는 "web-share"라는 문자열로 식별되는 정책 제어 권한을 정의합니다. 기본 허용 목록은 'self'이며, 이는 서드파티 컨텍스트가 기본적으로 API를 사용할 수 없음을 의미합니다.

사용자 에이전트가 Permissions Policy의 Permissions-Policy HTTP 헤더를 지원하는 것은 OPTIONAL입니다.

개발자는 Permissions Policy 명세에서 제공하는 방법을 사용해 서드파티 컨텍스트가 이 API를 사용할 수 있는지 제어할 수 있습니다.

참고: Permissions Policy 구현 현황

사용자 에이전트는 서드파티 컨텍스트에서 Web Share API가 사용되지 않도록 일관적으로 막지만, 발행 시점 기준으로 Permissions Policy에 의존해 서드파티 컨텍스트에서 API를 활성화하는 것은 상호운용성 문제가 있습니다. 특히, allow 속성은 널리 지원되지만, allow 속성의 업데이트된 문법은 지원되지 않습니다. 또한 Permissions-Policy: HTTP 헤더도 아직 널리 지원되지 않습니다. 개발자는 서드파티 컨텍스트에서 Web Share API를 활성화하기 전에 Permissions Policy 명세의 구현 현황을 확인해야 합니다.

Permissions-Policy HTTP 헤더 지원이 널리 확산되면, 워킹 그룹은 이 명세를 수정해 해당 헤더 지원을 요구할 계획입니다.

5. 접근성 고려사항

이 섹션은 비규범적입니다.

이 명세가 사용자 인터페이스에 정보를 표시하는 데 사용될 때, 구현자는 해당 플랫폼의 OS 수준 접근성 지침을 따라야 합니다. 또한 공유는 최종 사용자에게 잠재적 보안 영향을 미칠 수 있으므로 share() 메서드의 일환으로 설명된 대로, 공유 UI는 접근성 있게 제공되어야 하며, 각 플랫폼의 보안 UI 지침도 고려해야 합니다. 주요 고려사항은 다음과 같습니다:

  • 이미지 등 비텍스트 콘텐츠에 대체 텍스트를 제공하여 시각 장애가 있는 사용자가 공유되는 콘텐츠의 유형과/또는 성격을 이해할 수 있도록 합니다.
  • 사용자가 키보드만으로 미리보기 콘텐츠를 탐색할 수 있고, 키보드 포커스가 명확하게 보이도록 합니다.
  • 미리보기 콘텐츠가 올바르게 구조화되어 보조 기술을 사용하는 사용자가 이해할 수 있도록 제목과 라벨을 사용합니다.
  • 공유 UI에서 충분한 색상 대비와 글꼴 크기를 보장하고, 널리 인식되고 쉽게 이해할 수 있는 글꼴, 아이콘, 이미지를 사용합니다.

이러한 요소들은 시각, 운동, 인지 장애가 있는 사용자가 웹 페이지가 공유하는 콘텐츠의 성격을 더 잘 이해할 수 있도록 돕습니다.

6. 프라이버시 고려사항

  • API 설계상, 웹사이트는 어떤 공유 대상이 사용 가능한지, 사용자가 share()에서 어떤 공유 대상을 선택했는지 알 수 없습니다. 이는 지문 채취(fingerprinting)나 사용자의 디바이스 또는 선호 공유 대상에 관한 정보 유출을 막기 위한 설계입니다.
  • share()를 프라이버시 브라우징 모드에서 사용하면, 사용자의 프라이버시 설정을 존중하지 않는 서드파티 애플리케이션에 개인 데이터가 유출될 수 있습니다. 사용자 에이전트는 추가 경고를 제공하거나 MAY 프라이버시 모드에서 기능을 완전히 비활성화할 수 있지만, 선택 UI가 충분한 경고로 간주될 수 있으므로 필수는 아닙니다.

7. 적합성

비규범적 마크가 된 섹션뿐 아니라, 이 명세서의 모든 저작 지침, 도표, 예시, 참고도 비규범적입니다. 그 외 모든 내용은 규범적입니다.

이 문서의 MAY, MUST, OPTIONAL, SHOULD 키워드는 BCP 14 [RFC2119] [RFC8174] 에 설명된 대로, 반드시 대문자로 표기된 경우에만 해당 의미로 해석됩니다.

다음은 권고안 제안(Proposed Recommendation) 단계에서 명세에 적용된 규범적 변경사항입니다. 전체 변경 내역은 커밋 로그를 참고하세요.

  • Permissions-Policy HTTP 헤더를 OPTIONAL로 변경 (#275)

다음은 최초 공개 작업 초안(First Public Working Draft)에서 후보 권고안(Candidate Recommendation)까지 명세에 적용된 규범적 변경사항입니다. 전체 변경 내역은 커밋 로그를 참고하세요.

  • Priv/Sec을 명세에 포함 (#245)
  • 공유 가능한 스킴 정의 및 체크 추가 (#244)
  • 비활성 문서 처리 (#219)
  • canShare() 메서드 추가 (#177)
  • "공유 데이터 유효성 검사" 알고리즘 도입 (#185)
  • OS에 전달 후 promise resolve (#209)
  • sharePromise 이후 일시적 활성화 체크 (#183)
  • url 멤버에 대해 http URL 아닌 경우 reject (#174)
  • files에 시퀀스(sequence) 사용 (#170)
  • "web-share" 기능 정책(feature policy) 도입 (#166)
  • BREAKING CHANGE: share()가 사용자 활성화를 소비하도록 변경 (#137)
  • 파일 공유 기능 추가 (#133)
  • 접근성 고려사항 추가 (#146)

A. 감사의 글

편집자들은 명세 개선에 큰 기여를 한 다음 W3C 그룹들에 감사드립니다: Accessible Platform Architectures 워킹 그룹, Internationalization 워킹 그룹, Privacy Interest Group, 그리고 Technical Architecture Group.

Web Intents 팀에도 감사드립니다. 이들은 웹 앱 상호운용성(use case) 기초를 마련했습니다. 특히 Paul Kinlan은 Web Share 초기 옹호에 많은 기여를 했습니다.
